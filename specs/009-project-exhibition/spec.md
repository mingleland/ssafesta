## User Scenarios & Testing

### User Story 1 — 내 프로젝트를 전시한다 (Priority: P0)

부스 소유자가 프로젝트 정보·영상·링크를 등록하면, 방문자가 부스에서 그것을 본다.

**Why this priority**: 서비스의 원래 문제의식("프로젝트 결과물이 흩어진다")에 직접 답하는 기능.

**Independent Test**: 프로젝트 등록 → 부스에 패널·영상 배치 → 공개 → 방문자가 내용을 확인.

**Acceptance Scenarios**:

1. **Given** 부스 소유자, **When** 프로젝트 정보를 등록하면, **Then** 이름·설명·대표 정보가 저장된다.
2. **Given** 프로젝트, **When** 영상 주소를 등록하면, **Then** 부스의 영상 오브젝트에서 재생할 수 있다.
3. **Given** 프로젝트, **When** 배포·저장소·포트폴리오 링크를 등록하면, **Then** 방문자가 그 링크로 이동할 수 있다.
4. **Given** 공개된 부스, **When** 방문자가 프로젝트 패널과 상호작용하면, **Then** 프로젝트 정보가 표시된다.

### User Story 2 — 잘못된 링크로 사고가 나지 않는다 (Priority: P1)

**Acceptance Scenarios**:

1. **Given** 형식이 잘못된 주소, **When** 등록을 시도하면, **Then** 거부되고 사유가 안내된다.
2. **Given** 외부 링크, **When** 방문자가 클릭하면, **Then** 외부로 이동함이 안내된다 (D09).

### Edge Cases

- 영상 제공자가 임베드를 막는 경우 → **016과 같은 문제.** 새 탭 fallback 필요
- 링크 대상이 사라진 경우
- 프로젝트가 이미 있는 부스에 또 등록하는 경우 → **부스당 1개 확정**(C-01)이므로 거절한다. 덮어쓰기 금지 — 수정은 `PATCH`
- 임대 만료 후 프로젝트 데이터 보존 (004 FR-010)

## Requirements

### Functional Requirements

- **FR-001**: 소유자는 프로젝트 이름·설명·대표 정보를 등록·수정할 수 있어야 한다.
- **FR-002**: 소유자는 영상 주소를 등록할 수 있어야 한다.
- **FR-003**: 소유자는 외부 링크(배포·저장소·포트폴리오)를 등록할 수 있어야 한다.
- **FR-004**: 링크는 `http/https` 형식이 검증되어야 한다 (D09).
- **FR-005**: 방문자는 공개된 부스에서 프로젝트 정보를 볼 수 있어야 한다.
- **FR-006**: 외부 링크 이동 시 외부로 나감이 안내되어야 한다 (D09).
- **FR-007**: 프로젝트 표시 UI는 **React 오버레이**가 담당하고 Unity는 트리거만 발생시킨다 (헌법 25조).
- **FR-008**: 임대가 만료돼도 프로젝트 데이터는 보존되어야 한다.
- **FR-009**: 영상이 임베드 불가한 경우 **새 탭 열기 대안**을 제공해야 한다.

### Key Entities

- **Project**: 전시 대상. 부스, 이름, 설명, 대표 이미지 주소, 영상 주소,
  외부 링크 3종(배포·저장소·포트폴리오), 등록 시각 — **부스당 1개**(C-01)

> **`Project Link` 엔티티는 삭제됐다** (C-05, 2026-08-28). 링크는 목록형 별도 엔티티가 아니라
> V1 `projects`의 3칼럼(`deploy_url`·`git_url`·`portfolio_url`)이다. `유형·표시명`을 요구한 화면이
> 존재하지 않아 지금 만들면 추측이 된다. 필요해지면 그때 `project_links`를 신설한다.

## Success Criteria

- **SC-001**: 소유자가 안내 없이 프로젝트를 등록해 부스에 표시되게 할 수 있다.
- **SC-002**: 방문자가 부스에서 프로젝트 정보와 링크에 도달하는 비율이 100%다.
- **SC-003**: 임베드 불가 영상에서도 방문자가 결국 그 영상에 도달할 수 있다.
- **SC-004**: 형식이 잘못된 링크가 등록된 사례가 0건이다.

| C-06 | `PATCH`에서 필드 누락과 명시적 `null`의 의미는? | BE 결정 · FE 통보 | ✅ **2026-08-28 확정 — 키 존재 여부로 판정. 누락=유지, `null`=삭제.** 일반 `record`로 받으면 둘 다 `null`이라 구분이 불가능하므로 **presence 추적 클래스**로 받는다. 016에서 밟은 자리다 — `PUT /booths/{boothId}/homepage`를 `record`로 받아 `{}`가 조용한 해제가 됐다(T-97). **FE를 제약하지 않는다** — 바뀐 필드만 보내도, 전체를 보내도 의도대로 동작한다. 다만 "지운다"는 키를 빼지 말고 `null`을 명시해야 한다 |
| C-07 | 프로젝트 전용 오류 코드를 신설하는가? | BE 결정 · FE 통보 | ✅ **2026-08-28 확정 — `PROJECT_NOT_FOUND` 신설.** 이 저장소는 이미 `BOOTH_NOT_FOUND`·`GAME_NOT_FOUND`·`WALLET_NOT_FOUND`·`CONFIG_NOT_FOUND`로 도메인별 코드를 둔다. FE가 분기할 값이라 계약이다 |
