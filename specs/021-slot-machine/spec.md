## User Scenarios & Testing

### User Story 1 — 광장 슬롯머신에 코인을 걸고 돌린다 (Priority: P1)

방문자가 광장에 놓인 슬롯머신 앞에서 **10코인을 걸고 한 판을 돌린다.** 서버가 결과를 정하고,
당첨이면 배수만큼 코인을 받는다. 릴 연출은 서버가 내려준 등급에 맞춰 돈다.

**Why this priority**: 코인을 쓸 곳을 만든다. 신규 200·일일 50 으로 코인이 들어오기만 하고 나갈 곳이
없으면 잔액이 의미를 잃는다. 다만 서비스 핵심이 아니므로 P1.

**Independent Test**: 광장 슬롯머신 상호작용 → 잔액 확인 → 스핀 → 릴이 등급에 맞게 멈춤 → 지갑
내역에 차감·지급 두 줄이 남음.

**Acceptance Scenarios**:

1. **Given** 잔액이 10 이상인 회원, **When** 스핀하면, **Then** 10코인이 차감되고 서버가 정한 등급과
   지급액이 내려오며, 지급이 있으면 같은 판에서 함께 반영된다.
2. **Given** 낙첨(등급 0), **When** 판이 끝나면, **Then** 지급은 0이고 **지급 원장은 남지 않는다.**
   차감 원장 한 줄만 남는다.
3. **Given** 잔액이 10 미만인 회원, **When** 스핀하면, **Then** `409 INSUFFICIENT_COIN` 이고 **잔액은
   변하지 않으며**, 응답 본문의 `balance` 가 현재 잔액이다.
4. **Given** 게스트, **When** 스핀하면, **Then** `403 MEMBER_ONLY` 다. 게스트는 코인을 쓸 수 없다
   (헌법 12조).
5. **Given** 오늘 타이밍 스톱으로 일일 한도 50코인을 다 채운 회원, **When** 슬롯을 돌리면, **Then**
   정상적으로 베팅·지급이 된다. **슬롯에는 일일 한도가 없다.**

### Edge Cases

- 서버가 모르는 `machineId` → `404 SLOT_MACHINE_NOT_FOUND`, **차감 없음**
- 요청의 `bet` 이 서버 설정값과 다름 → `400 VALIDATION_FAILED`, **차감 없음**. 조용히 설정값으로
  고쳐 주지 않는다
- 차감은 됐는데 지급 직전에 실패 → **있을 수 없다.** 한 판이 한 트랜잭션이라 둘 다 커밋되거나 둘 다
  롤백된다
- 판 도중 접속이 끊김 → 서버 트랜잭션은 이미 끝났다. 클라이언트는 결과를 못 보지만 원장은 맞다.
  다음 잔액 조회에서 드러난다

## Requirements

### Functional Requirements

- **FR-001**: 회원만 베팅할 수 있어야 한다. 게스트는 거부한다 (헌법 12조).
- **FR-002**: 서버는 **자신이 아는 기계에서만** 스핀을 받아야 한다. 모르는 `machineId` 는 거부한다 —
  존재하지 않는 기계로 원장이 쌓이면 나중에 어느 기계의 매출인지 말할 수 없다.
- **FR-003**: 베팅 차감과 당첨 지급은 **하나의 트랜잭션**이어야 한다. 코인만 빠지고 지급이 안 되는
  중간 상태가 존재해서는 안 된다.
- **FR-004**: 두 움직임 모두 원장에 남아야 한다 — 차감은 `SLOT_BET`, 지급은 `SLOT_PAYOUT`
  (spec 003 계약). **타이밍 스톱의 `MINIGAME_REWARD` 와 다른 사유여야 한다.**
- **FR-005**: **결과는 서버가 정한다** (헌법 16조). 확률표는 서버 설정이고 클라이언트가 보낸 결과를
  신뢰하지 않는다.
- **FR-006**: 슬롯에는 **일일 한도를 두지 않는다.** RTP 가 1 미만이라 이 기계는 코인 공급원이 아니라
  소각처이고, 지급 쪽에만 한도를 걸면 한도 도달 후 베팅만 빠져나가 원장이 이상해진다.
- **FR-007**: **베팅액은 서버가 정하고** 요청값은 일치 검증만 한다 (헌법 16조). 불일치는 거부한다.
- **FR-008**: 응답은 **당첨 등급(`tier`)을 포함**해야 한다. Unity 가 릴 연출 프리셋을 이 값으로 고르므로
  계약의 일부이지 디버그 필드가 아니다.
- **FR-009**: 잔액 부족 응답은 **현재 잔액을 포함**해야 한다. 클라이언트가 들고 있는 잔액은 이 오류가
  나는 시점에 이미 낡았다.
- **FR-010**: 게임 실패·중단이 월드 이용에 영향을 주어서는 안 된다 (spec 014 FR-007 과 같은 원칙).

### Key Entities

- **Spin**: 한 판. **표를 만들지 않는다** — 회원·금액·순서·식별자가 이미 원장 두 줄에 있고, 같은 사실을
  두 곳에 두면 한 곳이 틀릴 수 있다. 감사 추적은 spec 003 의 원장이다.
- **Tier**: 당첨 등급. `0` 낙첨 · `1` ×2 · `2` ×3 · `3` ×5. 설정(`app.minigame.slot-machine.tiers`)이
  정본이다.

## Success Criteria

- **SC-001**: 잔액과 원장 합계가 항상 일치한다 (spec 003 불변식 I-1).
- **SC-002**: 지급액이 등급의 배수와 다른 판이 0건이다.
- **SC-003**: 슬롯 지급이 타이밍 스톱 일일 한도에 집계된 사례가 0건이다.
- **SC-004**: 거부된 요청(모르는 기계·잘못된 베팅액·잔액 부족)이 잔액을 바꾼 사례가 0건이다.

## 알려진 한계 — 스핀 재전송 (C-08)

`sessionId` 는 **서버가 만드는** 값이다. 요청 본문에는 `bet` 하나뿐이라, 서버는 새 스핀과
"방금 그 스핀의 재전송" 을 구분할 방법이 없다. 멱등성 키는 그 `sessionId` 에서 파생되므로
**한 판의 두 원장 줄이 두 번 적용되는 것**은 막지만 **클라이언트 재시도**는 막지 못한다.

실제 노출 범위는 좁다 — Unity 는 스핀이 진행 중일 때 두 번째 입력을 무시하고
(`SlotMachineSession.Spin` 이 `Ready`/`Result` 밖에서 즉시 반환), 자동 재시도도 하지 않는다.
남는 것은 **타임아웃 뒤 사용자가 직접 다시 누르는 경우**이고, 그때는 한 판이 더 돌아간다.

**닫지 않고 기록해 두는 이유**: 닫으려면 요청 계약이 바뀌고, 그 계약은 2026-09-16 에 두 파트가
합의한 것이다. 필요해지면 `Idempotency-Key` 헤더를 더하는 것이 가장 작은 변경이다 —
`WalletService` 는 이미 클라이언트 제공 키를 받도록 되어 있다.

## Out of Scope

- 잭팟·누진 배당 — 확률표가 정적이다
- 스핀 이력 조회 API — 지갑 거래 내역(`GET /api/v1/wallets/me/transactions`)이 같은 것을 보여 준다
- 가변 베팅
- 슬롯 랭킹·통계 대시보드
- 부스 내부 슬롯머신 — 이 기계들은 월드 고정물이라 임대·소유권 판정이 없다
