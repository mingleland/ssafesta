# Phase 0 Research: 부스 슬롯 / 임대

**Spec**: `004-booth-slot-lease` | **Date**: 2026-08-19

정책(D01~D11)은 2026-08-12에, Clarification(C-01~C-05)은 2026-08-19에 확정됐다. 남은 미지수는 구현 방식이다.

---

## R-01. 코인 차감과 임대 생성의 원자성

- **Decision**: 하나의 `@Transactional` 안에서 `임대 INSERT → WalletService.spend()` 순으로 수행한다. 003의 `WalletService`는 `REQUIRED` 전파라 호출자 트랜잭션에 그대로 참여한다.
- **Rationale**: 두 작업이 같은 트랜잭션이면 "코인만 차감되고 임대가 없는" 상태가 **표현 자체로 불가능**해진다 (FR-003, SC-002). 보상 트랜잭션이나 REFUND 복구 로직을 만들 필요가 없다.
- **순서를 임대 먼저로 두는 이유**: 원장 멱등성 키에 `leaseId`를 쓰기 위해서다(R-04). 어느 쪽이 먼저든 원자성은 같지만, 이 순서라야 원장 항목이 임대를 참조할 수 있다.
- **Alternatives considered**:
  - *차감 후 임대 생성, 실패 시 REFUND*: 003 FR-013이 REFUND 경로를 갖고 있지만, 보상 트랜잭션은 그 자체가 실패할 수 있어 "코인만 사라짐"을 완전히 막지 못한다. D06이 REFUND를 "서버 오류 복구용"으로 남긴 것은 최후 수단이지 기본 설계가 아니다.
  - *분산 트랜잭션*: 같은 DB·같은 애플리케이션이라 필요 없다.

## R-02. 슬롯 독점(한 슬롯 한 명)

- **Decision**: V1의 부분 UNIQUE 인덱스에 맡긴다.
  ```sql
  CREATE UNIQUE INDEX ux_booth_leases_active_slot ON booth_leases(slot_id) WHERE status = 'ACTIVE';
  ```
  애플리케이션은 "이미 임대됨"을 **사전 검사로도** 확인해 정상 경로에서 친절한 오류를 주되, 경합에서의 최종 방어는 제약에 맡긴다.
- **Rationale**: 슬롯이 12개뿐이라 동시 요청이 실제로 발생한다(spec US2). "조회해서 비었으면 INSERT"는 두 트랜잭션이 모두 통과할 수 있다. 제약 위반은 정확히 하나만 살아남는다 (FR-004, SC-001).
- **제약 위반이 나면 트랜잭션 전체가 롤백된다 — 그게 정확히 원하는 동작이다.** 실패한 쪽은 코인도 차감되지 않는다 (US2-2). 003에서는 rollback-only가 문제였지만(003 R-03) 여기서는 반대로 이점이다: 004는 실패 시 **아무것도 남기지 않는 것**이 정답이기 때문이다.
- **Alternatives considered**:
  - *슬롯 행 비관적 락*: 동작하지만 제약이 이미 있는데 락을 더하는 건 중복이다. 락을 잊은 경로가 생기면 뚫린다.
  - *`booth_slots.status` 컬럼으로 관리*: 임대와 별개 상태가 하나 더 생겨 어긋날 수 있다. 활성 임대의 존재가 곧 점유다.

## R-03. 만료 판정 — 읽기 시 판정 + 쓰기 시 전이

- **Decision**: 두 층으로 나눈다.
  - **읽기(권위)**: `status = 'ACTIVE' AND ends_at > now()`. 슬롯 목록·입장 판정·활성 임대 한도 검사가 전부 이 술어를 쓴다.
  - **쓰기(정리)**: 재임대 트랜잭션이 그 슬롯의 만료된 `ACTIVE` 임대를 `EXPIRED`로 전이하고 `booths.current_slot_id`를 해제한다.
- **Rationale (읽기)**: 스케줄러가 멈춰도 만료 부스 입장이 막힌다 — spec이 Edge Case로 꼽은 상황이다 (SC-003).
- **Rationale (쓰기) — 이게 없으면 재임대가 불가능하다**: R-02의 부분 UNIQUE 인덱스는 `ends_at`을 보지 않는다. 만료된 임대를 `ACTIVE`로 두면 그 슬롯에 **영원히 새 임대를 넣을 수 없어** D05(만료 후 재임대)가 깨진다. `booths.current_slot_id`도 UNIQUE라 같은 문제가 생긴다.
- **스케줄러를 두지 않는 이유**: 읽기 판정이 정확성을 책임지므로 배치는 정리 작업일 뿐이다. 004 범위를 임대 자체에 집중시킨다. 필요해지면 이 위에 얹을 수 있다.
- **위험과 대응**: 만료 술어를 한 곳에서라도 빠뜨리면 조용히 틀린다. 그래서 술어를 **`BoothLeaseRepository`의 쿼리로만** 표현하고 서비스가 직접 `status`를 비교하지 않는다.
- **Alternatives considered**: *스케줄러 단독* — 스케줄러 장애가 곧 SC-003 위반이다.

## R-04. 임대 결제의 멱등성 키

- **Decision**: `LEASE_PAYMENT:BOOTH_LEASE:{leaseId}`. 임대 INSERT로 얻은 id를 그대로 쓴다.
- **Rationale**: 003 계약이 요구하는 "같은 업무 행위는 같은 키"를 만족하면서, **재임대 때는 자연히 다른 키**가 된다. 슬롯·사용자 조합으로 키를 만들면 같은 사람이 같은 슬롯을 나중에 다시 임대할 때 키가 겹쳐 **두 번째 차감이 무시된다** — 코인을 안 내고 임대하는 구멍이 된다.
- **재시도 안전은 자연 키가 담당한다**: 응답이 유실돼 클라이언트가 재요청하면 슬롯이 이미 점유돼 있으므로 새 임대가 생기지 않는다. 요청자가 그 슬롯의 현재 임차인이면 **기존 임대를 그대로 반환**한다 (FR-018).
- **Alternatives considered**: *클라이언트 제공 `Idempotency-Key`* — `docs/08`의 `DUPLICATE_REQUEST` 오류가 이를 암시한다. 자연 키만으로 충분히 막히므로 P0에서는 도입하지 않되, 계약에서 배제하지는 않는다.

## R-05. Booth의 귀속 — 소유자인가 슬롯인가

- **Decision**: **소유자에 귀속**한다. `booths.owner_user_id`가 주인이고 `current_slot_id`는 임대 중에만 채워지는 연결이다. 재임대자는 자기 Booth를 새로 받는다.
- **Rationale**: C-01 확정값이자 spec의 Edge Case("이전 소유자의 콘텐츠가 새 소유자에게 보이면 안 된다")를 구조로 보장한다. 콘텐츠(Layout·AI 문서·설문 응답)가 Booth에 매달려 있으므로, Booth가 슬롯에 귀속되면 **재임대만으로 남의 데이터에 접근**하게 된다. `docs/09`도 같은 결론이다 — *"새 임차인에게 이전 Booth의 Facade를 승계하지 않는다"*.
- **결과**: 만료 시 Booth는 지우지 않고 슬롯 연결만 끊는다. FR-010(콘텐츠 보존)과 SC-004(이전 게시본 비공개)가 같은 조치로 충족된다.

## R-06. 임대 기간과 가격

- **Decision**: `LeaseProperties`로 외부화한다 — 가격 100코인, 기간 24시간. `ends_at = 결제 시각 + 24h` (D02).
- **Rationale**: 003의 `WalletProperties`와 같은 방식이다. 가격은 기획이 바꿀 수 있는 값이라 코드 상수로 두지 않는다.
- **`durationDays`**: `docs/08` 요청 예시에 있으나 D05가 연장을 금지하고 D02가 1일로 고정하므로, P0에서는 **1만 허용**하고 다른 값은 거부한다. 필드를 없애지 않는 이유는 계약 호환성이다.

## R-07. 슬롯 시딩

- **Decision**: `V5__booth_slot_seed.sql`로 USER_RENTAL 슬롯 7개를 **11층**에 넣는다. `slot_code`는 `F11-R01` ~ `F11-R07`.
  *(→ **12개로 확장** — Unity 축제 존·내부 홀이 12실로 만들어져 세계와 맞춘다. V12가 `F11-R08`~`F11-R12`를 추가하고 `slotId` 1~12를 Unity 앵커 `01~12`에 대응 고정한다. 임대료·정산 영향 0 — #62, 2026-08-23)*
- **Rationale**: 슬롯은 운영 데이터지 사용자 생성물이 아니다. 마이그레이션에 두면 모든 환경이 같은 슬롯을 갖고 테스트가 재현 가능해진다.
- **미결(U-03)**: 층 배치는 기획 미확정(C-04)이라 spec 메모의 "1차는 11층"을 따른다. 확정되면 **데이터만** 교체하면 되므로 코드 변경이 없다.

## R-08. 만료 부스 접근 처리

- **Decision**: 만료된 부스에 접근하면 거부하고 사유를 안내한다. 슬롯·부스 조회 응답에 `entryAvailable`을 담아 클라이언트가 미리 알 수 있게 하고, 그럼에도 접근하면 명시적 오류를 준다 (FR-019).
- **Rationale**: 실시간 전파가 없으므로 월드에는 만료된 부스가 잠시 남는다. **입장을 막는 것이 하드 요구**(FR-008, SC-003)이고 시각적 제거는 아니다. 조용히 빈 화면을 주는 대신 "만료된 부스"라고 말해야 사용자가 상황을 이해한다.
- **받아들이는 결과**: 부스가 보이는데 못 들어가는 상태가 생긴다. 진짜 해결(변경 신호)은 005·006과 함께 확정한다 — `docs/HDD/부스_변경_신호_계약.md`.

## R-09. 게스트 차단

- **Decision**: 컨트롤러에서 JWT role이 `MEMBER`가 아니면 `403`. 003의 `WalletController`와 같은 방식이다.
- **Rationale**: 게스트는 지갑이 없으므로(003 FR-003b) 차감 자체가 불가능하지만, 헌법 12조는 "임대·결제·영구 자산 불가"를 명시하므로 **의도를 코드로 드러낸다.** 지갑 부재로 인한 부수적 실패에 기대지 않는다.
