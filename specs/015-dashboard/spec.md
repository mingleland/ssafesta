# Feature Specification: 운영 Dashboard

**Spec**: `015-dashboard`
**Created**: 2026-08-12
**Status**: Draft — **BE + FE 검토 대기** | **P1 (2차 MVP)**
**주 담당**: Backend + Frontend
**선행 spec**: 007~012 (데이터 소스가 먼저 있어야 한다)
**근거 문서**: docs/02 §2.12(DASH-01~05), 임대부스 논의 D11

> 이 spec은 **가장 마지막에 만든다.** 보여줄 데이터를 만드는 spec들이 먼저 끝나야 한다.
> 지금 작성하는 이유는 **다른 spec들이 어떤 데이터를 남겨야 하는지 미리 알리기 위해서**다.

## User Scenarios & Testing

### User Story 1 — 내 부스가 어떻게 쓰이는지 본다 (Priority: P1)

부스 운영자가 방문·AI 이용·설문·상담·수익 지표를 한 화면에서 확인한다.

**Independent Test**: 부스에 방문·AI 상담·설문 응답을 발생시킨 뒤 대시보드에서 그 수치가 보이는지 확인.

**Acceptance Scenarios**:

1. **Given** 운영 중인 부스, **When** 대시보드를 열면, **Then** 방문 횟수를 확인할 수 있다.
2. **Given** AI 상담이 있었던 부스, **When** 대시보드를 보면, **Then** AI 이용 건수를 확인할 수 있다.
3. **Given** 설문이 있는 부스, **When** 대시보드를 보면, **Then** 응답 현황을 확인할 수 있다.
4. **Given** 사람 상담이 있었던 부스, **When** 대시보드를 보면, **Then** 상담 건수를 확인할 수 있다.
5. **Given** 수익이 발생한 부스, **When** 대시보드를 보면, **Then** 수익 내역을 확인할 수 있다.
6. **Given** 데이터가 없는 신규 부스, **When** 대시보드를 열면, **Then** 빈 상태가 오류 없이 표시된다.

### Edge Cases

- 데이터가 0건인 항목 → 0으로 나누는 오류 없이 표시
- 권한이 없는 사용자의 접근 → 거부
- 다른 부스의 지표 조회 → 거부
- 임대 만료 후 지표 조회 [NEEDS CLARIFICATION: 만료 후에도 과거 지표를 보는가]
- 지표 집계가 느려지는 경우

## Requirements

### Functional Requirements

- **FR-001**: 운영자는 자기 부스의 방문 지표를 확인할 수 있어야 한다.
- **FR-002**: 운영자는 AI 상담 이용 건수를 확인할 수 있어야 한다.
- **FR-003**: 운영자는 설문 응답 현황을 확인할 수 있어야 한다.
- **FR-004**: 운영자는 사람 상담 건수를 확인할 수 있어야 한다.
- **FR-005**: 운영자는 수익 내역을 확인할 수 있어야 한다.
- **FR-006**: 지표는 **집계 수치 중심**으로 제공한다 — 사용자별 상세 로그를 축적하지 않는다 (D11).
- **FR-007**: Owner와 허용된 Staff만 조회할 수 있어야 한다.
- **FR-008**: 다른 부스의 지표를 조회할 수 없어야 한다.
- **FR-009**: 데이터가 없어도 오류 없이 빈 상태가 표시되어야 한다.
- **FR-010**: 집계는 서버가 계산해야 한다 (프론트가 원본을 받아 계산하지 않는다).

### Key Entities

- **Metric Snapshot**: 부스별 집계 지표. 부스, 기간, 방문 수, AI 이용 수, 설문 응답 수, 상담 수, 수익 합계

## 다른 spec에 요청하는 것 (이 spec이 미리 알리는 이유)

대시보드가 성립하려면 아래 spec들이 **집계 가능한 흔적**을 남겨야 한다. 나중에 추가하면 과거 데이터가 없다.

| 필요한 데이터 | 남겨야 하는 spec |
|---|---|
| 부스 방문 발생 | 006 (Booth Runtime) 또는 002 (세션) |
| AI 상담 시작·완료 | 008 |
| 설문 응답 제출 | 010 |
| 사람 상담 요청·완료 | 011 |
| 수익 발생 | 012 |

각 spec 구현 시 **최소한 "언제, 어느 부스에서, 무엇이 일어났다"는 집계용 기록**을 남길 것.
개인 식별 정보는 최소화한다 (D11).

## Success Criteria

- **SC-001**: 표시된 수치가 실제 발생 건수와 일치한다.
- **SC-002**: 데이터 0건 부스에서 오류가 발생한 사례가 0건이다.
- **SC-003**: 다른 부스 지표가 조회된 사례가 0건이다.
- **SC-004**: 운영자가 대시보드만 보고 자기 부스의 상태를 파악할 수 있다.

### BE 검토 (2026-09-13) — `S15P21A604-501` 구현과 함께

계약은 `contracts/dashboard-summary-api.md` 에 고정했다. 여기에는 **구현하며 드러난 것**만 적는다.

#### ① Clarification 답변

| # | 답 | 근거 |
|---|---|---|
| **C-01** "방문" 정의 | **부스 구역 진입**으로 잡았다 (`S15P21A604-240`). 게스트도 센다 | 상호작용 기준으로 하면 "지나갔지만 아무것도 안 한" 방문이 안 잡혀 Coin 유효성 검증의 분모가 사라진다 |
| **C-02** 기간 필터 | **`from`·`to` 필수.** 단, 일별 추이(시계열 배열)는 넣지 않았다 | FE 의 "단일 기간부터" 의견 중 **미루자고 한 것은 추이**다. 기간 인자 자체를 나중에 넣으면 기존 호출이 전부 바뀐다 |
| **C-03** 만료 임대의 과거 지표 | **보인다** | 행사가 끝난 뒤에 정산을 한다. 임대 만료로 지표까지 닫으면 운영자는 자기 행사 결과를 볼 기회가 없다. 기획이 반대로 정하면 게이트 한 줄이다 |
| **C-04** 실시간 vs 사전 집계 | **실시간** (권장안 채택) | 부스 12개 규모에서 원본 스캔이 더 싸고, 사전 집계는 갱신이 실패해도 조용히 그럴듯한 숫자를 계속 보여준다. `booth_daily_metrics` 는 비워 둔다 |
| **C-05** 관리자용 전체 지표 | **없다** | 전역 관리자 권한 모델이 미정이다. `docs/26` 결정 요청, `S15P21A604-165` |

#### ② "다른 spec에 요청하는 것" — 전달 현황

FE 의 "007~012 가 데이터층을 확정한 뒤 한 번에" 라는 판단은 맞았다. 다만 **기다리는 동안 006 쪽 데이터가 실제로 비어 있었다**.

| 필요한 데이터 | 상태 |
|---|---|
| 부스 방문 발생 | ✅ `S15P21A604-240` 으로 생겼다. 표(`booth_visit_events`)는 V1 부터 있었고 **쓰는 코드가 없었다** |
| 사람 상담 요청·완료 | ✅ `S15P21A604-137` (spec 011 US1) |
| 설문 응답 제출 | ✅ 이미 있었다 (`survey_responses`) |
| AI 상담 시작·완료 | ❌ **표가 없다.** `docs/26` 결정 요청 |
| 수익 발생 | ❌ **경로가 없다.** 아래 ③ |

#### ③ 빠진 요구사항 — BE 가 더한 2건

| 구분 | 내용 |
|---|---|
| **FR-005 의 전제가 틀렸다** | **부스로 코인이 들어오는 경로가 하나도 없다.** 원장에서 부스와 닿는 사유는 임대료(소유자의 *지출*)와 설문 보상(차감 지갑 없이 *발행*)뿐이다. `revenueCoin` 과 `booth_daily_metrics.revenue_coin` 은 있지도 않은 유입을 가정한 자리다. 임의로 정하지 않고 `docs/26` 에 올렸다(헌법 30조) |
| **"없음" 과 "0" 을 구분하는 규약이 없다** | SC-002 가 "0건 부스에서 오류 0" 을 요구하는데, **셀 원천이 없는 칸**과 **세어 보니 0인 칸**이 같은 `0` 으로 나가면 FE 는 둘을 구분할 수 없고 "AI 이용 0건" 카드를 영원히 띄운다. `null` = 원천 없음, `0` = 원천 있고 0건으로 고정했다 |

**FE 가 적은 ③ 세 건 중 서버 쪽에 걸리는 것**: "FE 가드는 UX 보조이고 **서버 판정이 정본**" — 그대로다. 게이트는 `BoothAccessGuard.requireEditor` 하나이고 `CONSULTANT` 는 거부된다. 화면 상태(Loading/Error/Empty/Forbidden)와 진입점은 FE 몫이라 여기서 정하지 않는다.

### FE 검토 (2026-09-05) — Frontend 파트분

이 spec 은 **P1(2차 MVP)** 이고 FE 착수 계획이 없다. 그래서 구현 경험이 아니라 **문서만 읽고 하는 검토**임을 밝힌다.

| 구분 | 내용 |
|---|---|
| ① C-02 기간 필터 | **MVP 제외 의견.** 추이를 그리려면 시계열 집계와 차트가 함께 오고, D11 의 집계 중심 권장과도 맞는다. 단일 기간(전체 누계) 하나로 시작하고 필터는 지표가 쌓인 뒤에 얹자 |
| ① C-01·C-03·C-05 | 기획 사안이라 FE 의견 없음. C-04(실시간 vs 사전 집계)는 BE 결정 — FE 는 응답 모양만 같으면 어느 쪽이든 무관하다 |
| ② 중복 | Edge Cases 의 `임대 만료 후 지표 조회 [NEEDS CLARIFICATION]` 과 **C-03 이 같은 질문**이다. 상태를 두 곳에 두면 한쪽만 갱신된다 — C-03 하나로 모으고 Edge Case 는 그 결정을 참조하는 편이 낫다 |
| ③ 화면 상태 | **Loading / Error / Empty / Forbidden 상태 정의가 없다.** SC-002 가 "0건 부스에서 오류 0" 을 요구하는데 그 화면이 무엇인지 없다. spec 005 에도 같은 지적을 했고 같은 이유다(`parts/FE.md` 공통 비기능) |
| ③ 진입점 | **대시보드로 들어가는 경로가 없다.** 현재 부스 운영 진입은 World 의 Booth Management NPC → `BoothManagementOverlay` 하나이고(`-414`, D-08), 대시보드가 그 안의 탭인지 별도 화면인지에 따라 라우트·가드가 달라진다 |
| ③ 권한 | Edge Case 에 "권한 없는 접근 거부"·"다른 부스 지표 조회 거부" 가 있는데 대응 FR 이 없다. FE 가드는 UX 보조이고 **서버 판정이 정본**이라는 것이 명시돼야 한다(헌법 16조, 005 와 같은 결) |

**② 미전달 사유**: 이 spec 의 목적이 "다른 spec 들이 어떤 데이터를 남겨야 하는지 미리 알리는 것" 인데, 그 전달은 **각 spec 이 아직 구현 중이라 지금 보내면 낡는다**. 007~012 가 데이터층을 확정한 뒤 한 번에 전달하는 편이 맞다고 본다 — 전달 주체·시점은 리드 판단이 필요하다.
