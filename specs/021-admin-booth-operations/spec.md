# Feature Specification: 관리자 부스 운영 권한

**Feature Branch**: `feat/S15P21A604-742-admin-operations`

**Created**: 2026-09-16

**Status**: Draft — S15P21A604-742 첫 구현 슬라이스

**Input**: Jira S15P21A604-742의 전역 관리자 운영 범위 중, 기존 부스 운영 기능에 관리자가 안전하게 접근하는 권한 경로를 구현한다.

## User Scenarios & Testing

### User Story 1 - 관리자가 일반 부스를 운영한다 (Priority: P1)

전역 관리자는 소유자나 부스 직원이 아니어도, 운영상 필요한 다른 회원의 부스 콘텐츠와 운영 정보를 기존 관리 기능에서 열람·수정한다.

**Why this priority**: 742의 부스 운영 블록은 이미 구현된 부스 관리 기능을 재사용할 수 있으며, 별도 관리자용 복제 화면이나 API를 만들지 않고도 운영 개입의 기반을 제공한다.

**Independent Test**: 관리자가 타 회원의 활성 부스에 대해 기존 초안 조회·저장·게시와 대시보드 조회를 수행하고, 일반 회원은 같은 요청에서 거부되는 것을 확인한다.

**Acceptance Scenarios**:

1. **Given** 다른 회원이 소유한 활성 부스와 전역 관리자, **When** 관리자가 기존 부스 운영 요청을 하면, **Then** 소유자·허용 직원과 동일한 운영 권한으로 처리된다.
2. **Given** 다른 회원의 부스와 일반 회원, **When** 일반 회원이 같은 요청을 하면, **Then** 부스 운영 권한 없음으로 거부된다.
3. **Given** 만료된 타 회원 부스, **When** 관리자가 기존의 활성 임대를 요구하는 변경 요청을 하면, **Then** 기존 만료 규칙대로 거부된다.

---

### User Story 2 - 마스터 계정의 부스는 보호한다 (Priority: P1)

전역 관리자는 마스터 계정이 소유한 부스의 콘텐츠·가시성을 변경할 수 없다.

**Why this priority**: 마스터 계정 보호는 이미 계정·코인 관리자 기능에 적용된 운영 불변식이며, 부스 경로에서 빠지면 우회가 된다.

**Independent Test**: 관리자가 마스터 소유 부스의 수정·게시 요청을 하면 보호 오류를 받고, 마스터 자신은 기존 소유자 권한으로 계속 운영할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 마스터 계정이 소유한 부스와 다른 전역 관리자, **When** 관리자가 부스 콘텐츠를 변경하려 하면, **Then** 마스터 보호 오류로 거부된다.
2. **Given** 마스터 계정이 소유한 부스, **When** 마스터 자신이 자신의 부스를 운영하면, **Then** 기존 소유자 권한이 유지된다.

---

### User Story 3 - 기존 부스 권한이 바뀌지 않는다 (Priority: P2)

부스 소유자와 허용된 직원은 기존과 동일하게 운영하고, 상담 전용 직원과 게스트는 계속 거부된다.

**Why this priority**: 전역 관리자 예외가 기존 부스 역할 모델을 넓혀서는 안 된다.

**Independent Test**: 기존 역할 조합별 부스 접근 회귀 검증에서 Owner·ADMIN·CONTENT_EDITOR만 허용되고 CONSULTANT·게스트는 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 부스 소유자 또는 콘텐츠 편집 권한 직원, **When** 부스 운영 요청을 하면, **Then** 이전과 동일하게 처리된다.
2. **Given** 상담 전용 직원 또는 게스트, **When** 부스 운영 요청을 하면, **Then** 이전과 동일한 권한 오류로 거부된다.

### Edge Cases

- 관리자였던 계정이 강등된 직후 요청하면, 다음 요청부터 전역 관리자 예외가 적용되지 않는다.
- 존재하지 않는 부스는 호출자의 역할과 무관하게 기존의 부스 없음 오류를 반환한다.
- 관리자가 소유자와 직원 역할을 함께 가진 경우에도 권한 판정은 하나의 성공으로 끝나며, 직원 역할 레코드는 변경하지 않는다.
- 마스터 보호는 열람이 아닌 변경·게시 같은 운영 행위에만 적용한다. 해당 부스의 공개 방문자 경로는 이 기능으로 바꾸지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 시스템은 전역 관리자가 기존 부스 운영 권한 게이트를 통과하도록 허용해야 한다.
- **FR-002**: 시스템은 전역 관리자 예외를 기존 부스 관리·레이아웃·프로젝트·설문·AI 직원 및 문서·운영 대시보드의 공통 권한 경로에 일관되게 적용해야 한다.
- **FR-003**: 시스템은 전역 관리자의 타 부스 변경·게시 요청이 마스터 계정 소유 부스를 대상으로 하면 거부해야 한다.
- **FR-004**: 시스템은 부스 소유자와 이미 허용된 직원의 기존 접근 결과를 변경하지 않아야 한다.
- **FR-005**: 시스템은 게스트·일반 회원·상담 전용 직원이 타 부스 운영 권한을 얻지 못하게 해야 한다.
- **FR-006**: 시스템은 활성 임대, 부스 없음, 게시 상태 등 기존 부스 상태 규칙과 오류 순서를 유지해야 한다.
- **FR-007**: 시스템은 강등된 관리자의 이후 요청을 일반 회원과 동일하게 처리해야 한다.
- **FR-008**: 이 슬라이스는 신규 관리자 화면, 강제 임대 회수·강제 비공개, 신고·모더레이션, 이벤트 운영·전체 집계를 구현하지 않는다. 이 기능들은 742의 후속 독립 작업으로 남긴다.

### Key Entities

- **전역 관리자**: 플랫폼 전체 운영 권한을 가진 회원. 기존 부스 소유·직원 역할과 별개로 판단된다.
- **마스터 계정**: 다른 관리자의 변경 대상이 될 수 없는 보호된 관리자 계정.
- **부스 운영 권한**: 소유자·허용된 직원·전역 관리자가 기존 부스 관리 기능을 수행하는 자격.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 관리자는 기존 부스 운영 기능의 권한 검증이 필요한 대표 요청 4종 이상에서 타 회원 부스를 운영할 수 있다.
- **SC-002**: 마스터 소유 부스에 대한 관리자의 변경·게시 대표 요청 2종 이상이 모두 보호 오류로 거부된다.
- **SC-003**: Owner·ADMIN·CONTENT_EDITOR·CONSULTANT·게스트의 기존 권한 회귀 사례가 모두 기대 결과를 유지한다.
- **SC-004**: 일반 회원이 타 부스 운영 권한을 얻는 사례가 통합 검증에서 0건이다.

## Assumptions

- S15P21A604-743으로 전역 관리자 판정·마스터 보호·감사 기반은 이미 develop에 병합돼 있다.
- 기존 부스 운영 기능은 공통 접근 게이트를 사용하므로, 그 게이트에 예외를 추가하는 것이 중복 권한 API를 만드는 것보다 안전하다.
- 마스터 보호의 구체적 강제 조치와 감사 범위는 각 후속 기능의 계약에서 확장한다. 이 슬라이스에서는 기존 콘텐츠 운영 경로의 보호만 보장한다.
- 742의 나머지 70여 운영 기능은 이 기능의 완료 조건이 아니며, 별도의 Jira 하위 작업으로 분리한다.
