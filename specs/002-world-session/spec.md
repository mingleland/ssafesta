## User Scenarios & Testing

### User Story 1 — 브라우저에서 월드에 들어가 서로를 본다 (Priority: P0) [구현됨]

사용자가 웹 브라우저에서 SSAFY 월드에 접속하면 다른 접속자가 보이고, 서로의 이동이 실시간으로 보인다.

**Why this priority**: 프로젝트의 기술적 심장. 이것이 안 되면 메타버스가 성립하지 않는다.

**Independent Test**: 브라우저 탭 2개로 접속 → 각자 이동 → 서로의 움직임이 보이는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 월드에 입장하면, **Then** 자신의 캐릭터가 생성되고 이미 접속 중인 다른 사용자들이 보인다.
2. **Given** 두 사용자가 접속 중, **When** 한 사용자가 이동하면, **Then** 다른 사용자 화면에서 그 이동이 보인다.
3. **Given** 두 사용자가 접속 중, **When** 한 사용자가 브라우저를 닫으면, **Then** 다른 사용자 화면에서 해당 캐릭터가 사라진다.
4. **Given** 배포 환경, **When** 사용자가 접속하면, **Then** 암호화된 연결이 사용된다. **[신규 — AWS 실측 필요]**

### User Story 2 — 접속 주소를 서버에서 받는다 (Priority: P0) [신규]

Unity 클라이언트는 접속할 게임 서버 주소를 **하드코딩하지 않고** 서버 응답으로 받는다.

**Why this priority**: 나중에 채널이 늘어나거나 서버 주소가 바뀔 때 Unity 재빌드가 필요해지면 운영이 불가능해진다.

**Independent Test**: 서버 응답의 주소를 다른 값으로 바꿨을 때, Unity 재빌드 없이 그 서버로 접속되는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 월드 세션을 요청하면, **Then** 접속에 필요한 주소 정보와 1회용 접속 토큰을 받는다.
2. **Given** 잘못되거나 만료된 접속 토큰, **When** 게임 서버에 접속을 시도하면, **Then** 승인이 거부된다. **[부분 구현 — 승인 골격은 있고 실제 검증은 신규]**
3. **Given** 서버가 다른 주소를 응답하면, **When** 클라이언트가 접속하면, **Then** 클라이언트 재빌드 없이 그 주소로 연결된다.

### User Story 3 — 접속 실패를 이해할 수 있다 (Priority: P1) [신규]

**Acceptance Scenarios**:

1. **Given** 게임 서버가 응답하지 않는 상황, **When** 사용자가 입장을 시도하면, **Then** 실패 사실과 재시도 수단이 안내된다.
2. **Given** 접속 중 연결이 끊긴 경우, **When** 사용자가 감지하면, **Then** 끊김이 안내된다. [NEEDS CLARIFICATION: 자동 재접속을 하는가]

### Edge Cases

- 월드 정원이 가득 찬 상태에서 입장 요청 [NEEDS CLARIFICATION: 정원 초과 시 동작 — 거부 / 대기열 / 다른 채널]
- 접속 토큰을 받은 뒤 실제 접속까지 시간이 오래 걸린 경우(Unity Web 로딩) → 토큰이 먼저 만료될 수 있음
- 같은 계정으로 두 탭에서 동시 접속 (001 C-07과 동일 결정)
- 게임 서버는 살아있으나 Spring이 죽은 경우 → 이미 접속 중인 사용자는 계속 놀 수 있어야 한다

## Requirements

### Functional Requirements

- **FR-001** [구현됨]: 사용자는 웹 브라우저에서 월드에 접속할 수 있어야 한다.
- **FR-002** [구현됨]: 접속·퇴장 시 해당 사용자의 캐릭터가 다른 사용자 화면에서 생성·제거되어야 한다.
- **FR-003** [구현됨]: 같은 월드의 사용자들은 서로의 위치와 방향을 실시간으로 볼 수 있어야 한다.
- **FR-004** [구현됨]: 클라이언트 간 연결은 브라우저가 지원하는 방식(WebSocket)을 사용해야 한다.
- **FR-005** [신규]: 시스템은 월드 접속에 필요한 **접속 주소와 1회용 토큰**을 제공하는 수단을 가져야 한다.
- **FR-006** [구현됨]: Unity 클라이언트는 접속 주소를 하드코딩해서는 안 된다 (헌법 8조).
- **FR-007** [신규]: 게임 서버는 접속 승인 단계에서 **토큰 서명을 자체 검증**하고, 사용된 토큰 식별자를 기록해 재사용을 차단해야 한다. Spring에 매 접속마다 조회하지 않는다 (헌법 14조).
- **FR-008** [구현됨]: 게임 서버는 실시간 월드 상태(위치·스폰·존)만 권위를 가지며, 코인·임대 등 영구 상태를 변경해서는 안 된다 (헌법 2조).
- **FR-009** [신규]: 배포 환경에서 연결은 암호화되어야 하며 비암호화 연결을 노출해서는 안 된다 (헌법 6조).
- **FR-010** [신규]: 사용자는 접속 실패 시 실패 사실과 재시도 방법을 알 수 있어야 한다.
- **FR-011**: 1차 MVP의 월드는 **11층 단일 구역**이다. 층 이동은 spec 018(2차)에서 다룬다.
- **FR-012**: 세션 발급 수단은 **목적 구역(층)을 입력으로 받아야** 한다. **1차 MVP부터 포함한다** (헌법 9조).
  *1차에서는 11층만 유효하지만 파라미터 자리를 지금 열어두어 2차(spec 018)에서 계약 변경이 없게 한다.*

### Key Entities

- **World Session**: 한 사용자의 월드 접속 단위. 세션 식별자, 월드/채널 식별자, 접속 주소, 접속 토큰, 만료 시각
- **Player**: 월드 내 캐릭터. 소유자, 위치, 방향, 이동 상태

## Success Criteria

- **SC-001**: 브라우저 2개가 동시에 접속해 서로의 이동을 볼 수 있다. *(POC 달성 완료 — 3탭까지 확인)*
- **SC-002**: 목표 인원 30명이 한 채널에서 동시 접속했을 때 이동 동기화가 유지된다. *(부하 테스트 필요)*
- **SC-003**: 게임 서버 주소를 변경했을 때 클라이언트 재빌드 없이 새 주소로 접속된다.
- **SC-004**: 유효하지 않은 토큰으로 접속에 성공한 사례가 0건이다.
- **SC-005**: 배포 환경에서 비암호화 연결로 접속 가능한 경로가 존재하지 않는다.

## 부록 — 현재 구현 상태 (참고용, 요구사항 아님)

| 항목 | 상태 |
|---|---|
| WebSocket 강제 + 서버 자동 기동 | 완료 (`NetworkBootstrap`) |
| 접속 승인(Connection Approval) 골격 | 완료 — 토큰 payload 수신 구조 존재, 실제 검증 로직만 신규 |
| 암호화 연결 분기 | 완료 (`scheme == "wss"` 시 전환) — AWS 실측 미실시 |
| 스폰 위치 분산 | 완료 |
| Docker 전용 서버 | 완료 (`festa-unity/Docker/`), 컨테이너명 `festa-world-01` |
| 계약 DTO | `WorldSessionDto` 정의 완료 (부록 참조: 001) |

**BE가 만들어야 할 것은 사실상 하나** — 위 `WorldSessionDto` 형태를 반환하는 API와 토큰 검증. 나머지는 이미 돈다.
