## User Scenarios & Testing

### User Story 1 — 타이머를 정확히 멈추고 코인을 받는다 (Priority: P1)

방문자가 관리자 게임 부스에서 **무작위로 제시된 목표 시간(5~10초)에 맞춰 타이머를 멈추고**, 오차에 따라 코인을 받는다.

**Why this priority**: 월드 재방문 동기를 만든다. 다만 서비스 핵심(부스 제작·AI 상담)이 아니므로 P1.

**Independent Test**: 게임 부스 진입 → 목표 시간 확인 → 타이머 시작 → 정지 → 오차 표시 → 보상이 지갑에 반영됨.

**Acceptance Scenarios**:

1. **Given** 게임 부스에 있는 사용자, **When** 게임을 시작하면, **Then** **5~10초 사이의 목표 시간이 무작위로 제시**되고 타이머가 흐르기 시작한다.
2. **Given** 타이머가 흐르는 중, **When** 사용자가 정지하면, **Then** 목표 시간과의 **오차가 표시**되고 결과가 서버에 전달된다.
2a. **Given** 사용자가 정지하지 않고 목표 시간을 크게 넘긴 경우, **When** 제한에 도달하면, **Then** 실패로 종료된다.
3. **Given** 게임 결과, **When** 보상 조건을 충족하면, **Then** 정책에 따른 코인이 지급된다.
4. **Given** 일일 보상 한도에 도달한 사용자, **When** 게임을 다시 하면, **Then** 게임은 할 수 있으나 보상은 지급되지 않고 그 사실이 안내된다.

### Edge Cases

- 게임 도중 연결이 끊긴 경우 → **무보상**
- 같은 결과를 여러 번 전송하는 경우 → **중복 지급이 발생해서는 안 된다**
- 클라이언트가 조작된 점수를 보내는 경우
- 여러 명이 동시에 같은 게임 부스를 이용하는 경우 → **각자 개별 플레이**

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 게임 부스에서 미니게임을 시작할 수 있어야 한다.
- **FR-001a**: 시스템은 매 판마다 **5~10초 사이의 목표 시간을 무작위로** 제시해야 한다.
- **FR-001b**: 사용자는 타이머가 흐르는 동안 임의 시점에 정지할 수 있어야 한다.
- **FR-001c**: 시스템은 목표 시간과 정지 시각의 **오차를 사용자에게 표시**해야 한다.
- **FR-001d**: 목표 시간을 크게 초과하면 실패로 종료되어야 한다.
- **FR-002**: 게임 결과(목표 시간·정지 시각·오차)는 서버에 전달되어야 한다.
- **FR-003**: 보상 지급은 **서버가 판단**해야 하며 클라이언트가 지급을 결정해서는 안 된다.
- **FR-004**: 같은 게임 결과로 **중복 지급이 발생해서는 안 된다** (멱등성).
- **FR-005**: 일일 보상 한도가 적용되어야 한다.
- **FR-006**: 보상 지급은 원장(Ledger)에 기록되어야 한다 (헌법 16조, spec 003 계약).
- **FR-007**: 게임 실패·중단이 월드 이용에 영향을 주어서는 안 된다.
- **FR-008**: 서버는 클라이언트가 보낸 점수를 검증 없이 신뢰해서는 안 된다 (헌법 12조).
- **FR-009**: 미니게임은 **1종만** 구현한다 (헌법 19조 범위 통제).

### Key Entities

- **Game Session**: 한 번의 게임 플레이. 사용자, 시작 시각, 종료 시각, 결과, 보상 여부
- **Game Result**: 목표 시간, 정지 시각, 오차, 성패

---

## Success Criteria

- **SC-001**: 사용자가 안내 없이 게임을 시작해 완료할 수 있다.
- **SC-002**: 중복 지급 사례가 0건이다.
- **SC-003**: 일일 한도를 초과한 지급이 0건이다.
- **SC-004**: 게임 중단이 월드 접속에 영향을 준 사례가 0건이다.

## 마피아 확장 메모 (GAME-05, P2 — spec 미작성)

2026-08-12 팀 논의에서 나온 아이디어. **P0/P1 안정 후 판단**하며 지금은 기술 쟁점만 기록한다.

> 구상: 접속 중인 플레이어들에게 역할(마피아/시민 등)이 주어지고, 중간중간 "지직" 하는 연출과 함께 게임이 진행된다.

**미리 알아야 할 기술 쟁점 3가지**:

1. **비밀 정보 전달이 일반 동기화와 다르다.**
   "너는 마피아다"는 정보는 **그 사람에게만** 가야 한다. 지금 쓰는 상태 동기화 방식은
   값을 전원에게 뿌리므로 그대로 쓰면 **다른 플레이어가 역할을 볼 수 있다.**
   대상을 지정해 보내는 방식이 따로 필요하다. 이건 구조가 다른 작업이다.
2. **클라이언트를 신뢰할 수 없는 정도가 다르다.**
   일반 기능은 조작해도 본인만 손해지만, 마피아는 **조작하면 게임이 성립하지 않는다.**
   역할·투표·판정 전부 서버가 권위를 가져야 한다.
3. **게임 진행 상태 관리가 월드와 별개로 필요하다.**
   낮/밤 같은 단계 전환, 타이머, 투표 집계는 월드 상태와 다른 수명주기를 갖는다.

**규모 감각**: 이건 "미니게임 하나 더"가 아니라 **별도의 게임 시스템**이다.
넣기로 한다면 다른 P2 항목보다 비용이 크다는 전제로 판단할 것.
