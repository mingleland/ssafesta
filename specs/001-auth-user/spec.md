## User Scenarios & Testing

### User Story 1 — 소셜 계정으로 처음 가입하고 로그인한다 (Priority: P0)

사용자는 별도 가입 양식을 작성하지 않고 Google·Kakao·SSAFY 중 하나의 인증을 완료해 SSAFY FESTA 계정을 만들거나 기존 계정으로 로그인한다.

**Why this priority**: 로그인 사용자를 전제로 하는 월드 입장, 부스 임대, 코인, 스튜디오 등 모든 핵심 기능의 시작점이다.

**Independent Test**: 새 소셜 계정으로 최초 로그인한 뒤 로그아웃하고 같은 제공자 계정으로 다시 로그인했을 때 신규 계정이 중복 생성되지 않고 동일한 사용자 정보가 복원되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서비스에 연결된 적 없는 Google·Kakao·SSAFY 계정, **When** 소셜 인증에 성공하면, **Then** 서비스 계정이 한 번만 자동 생성되고 로그인된다.
2. **Given** 이미 연결된 소셜 계정, **When** 같은 제공자 계정으로 다시 인증하면, **Then** 기존 서비스 계정으로 로그인된다.
3. **Given** 동일한 소셜 인증 완료 요청이 중복 도착한 상황, **When** 계정 생성을 처리하면, **Then** 서비스 계정과 최초 가입 혜택은 각각 한 번만 생성·지급된다.
4. **Given** 사용자가 소셜 인증을 취소하거나 제공자가 실패를 반환한 상황, **When** 로그인 화면으로 돌아오면, **Then** 실패 또는 취소 사실과 재시도 방법이 표시된다.
5. **Given** 정지 상태의 계정, **When** 연결된 소셜 계정으로 인증하면, **Then** 보호 기능에 로그인되지 않고 해당 상태와 가능한 후속 행동이 안내된다.
6. **Given** 소셜 인증에는 성공했지만 닉네임 등 필수 가입값이 비어 있는 사용자, **When** 가입 흐름을 계속하면, **Then** 누락된 필수값이 표시되고 가입 완료 화면으로 이동한다.
7. **Given** 필수 가입값 입력 중 뒤로 가거나 화면을 닫아 가입을 완료하지 못한 사용자, **When** 같은 소셜 계정으로 다시 인증하면, **Then** 중복 회원을 만들지 않고 필수값 입력 단계로 다시 안내된다.
8. **Given** 필수 가입값이 모두 유효한 사용자, **When** 가입을 확정하면, **Then** 활성 회원·지갑·최초 가입 혜택이 각각 한 번만 생성되고 회원용 인증 수단이 발급된다.
9. **Given** 두 소셜 제공자가 같은 검증된 이메일을 반환하고 한쪽 계정이 이미 가입된 경우, **When** 다른 제공자로 가입을 시도하면, **Then** 중복 계정 생성을 차단하고 기존 가입 경로로 로그인하도록 안내한다.
10. **Given** 소셜 인증이 성공한 사용자, **When** 백엔드가 프론트엔드로 반환하면, **Then** 기존·신규 가입 여부와 무관하게 동일한 `/auth/callback` 화면으로 이동하고 OAuth 결과 ticket은 URL·브라우저 스크립트에 노출되지 않는다.
11. **Given** `/auth/callback` 화면, **When** 프론트엔드가 OAuth 완료 API를 호출하면, **Then** 기존 회원은 한 번의 호출로 Access Token 본문과 Refresh Token 쿠키를 받고, 최초 회원은 `NICKNAME_REQUIRED` 상태를 받은 뒤 같은 API에 닉네임을 제출해 가입을 완료한다.

### User Story 2 — 게스트로 즉시 둘러본다 (Priority: P0)

사용자는 소셜 로그인을 원하지 않을 때 게스트로 월드를 둘러볼 수 있다. 게스트 활동은 영속 계정이나 자산으로 남지 않는다.

**Why this priority**: 가입 장벽 없이 핵심 월드 경험을 보여 주면서도 영구 자산과 경제 상태의 무결성을 지켜야 한다.

**Independent Test**: 게스트 Access Token으로 월드를 둘러본 뒤 외형 변경·부스 임대·코인·스튜디오 기능을 각각 시도하여 모두 차단되고, Refresh Token과 영속 사용자 데이터가 생성되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 방문자, **When** 게스트 입장을 선택하면, **Then** 응답 본문으로 게스트 Access Token만 받고 계정 생성 없이 관람 가능한 월드에 입장할 수 있다.
2. **Given** 게스트 로그인 응답, **When** 응답 본문과 쿠키를 검사하면, **Then** Refresh Token은 존재하지 않는다.
3. **Given** 게스트 사용자, **When** 외형 변경·부스 임대·코인·스튜디오 또는 기타 상태 변경 기능을 시도하면, **Then** 실행이 모두 거부되고 소셜 로그인이 필요하다는 안내가 표시된다.
4. **Given** 게스트 사용자, **When** 공개된 월드와 부스를 이동하며 관람하면, **Then** 상태 변경 없이 공개 콘텐츠를 볼 수 있다.
5. **Given** 게스트 사용자, **When** 소셜 로그인을 선택하면, **Then** 신규 회원가입 흐름을 시작하며 게스트 활동 데이터는 회원 계정으로 이전되지 않는다.
6. **Given** 게스트 Access Token이 만료된 상황, **When** 사용자가 계속 관람하려면, **Then** 게스트 입장을 다시 선택해 새 Access Token을 받아야 한다.

### User Story 3 — 로그인 상태를 안전하게 유지하고 종료한다 (Priority: P0)

로그인 사용자는 한 브라우저 세션에서만 보호 기능을 이용하며, 다른 브라우저에서 새로 로그인하면 이전 브라우저 세션과 월드 접속은 즉시 종료된다.

**Why this priority**: 세션이 예기치 않게 끊기거나 로그아웃 뒤에도 사용할 수 있으면 핵심 흐름과 보안이 모두 깨진다.

**Independent Test**: 브라우저 A에서 로그인한 뒤 브라우저 B에서 같은 계정으로 로그인하여, A의 인증 갱신과 보호 기능 접근이 차단되고 B만 계속 이용할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 로그인 세션, **When** 사용자가 보호 기능을 연속 이용하면, **Then** 허용된 세션 범위 안에서 불필요한 재로그인 없이 이용할 수 있다.
2. **Given** 인증 갱신이 불가능하거나 세션이 만료된 상황, **When** 보호 기능을 요청하면, **Then** 요청이 거부되고 작업 손실을 최소화하는 재로그인 안내가 제공된다.
3. **Given** 로그인한 사용자, **When** 로그아웃하면, **Then** 현재 인증 세션이 종료되고 해당 세션의 인증 수단으로 보호 기능을 이용할 수 없다.
4. **Given** 브라우저 A에서 월드에 접속한 사용자, **When** 같은 계정으로 브라우저 B에서 새 로그인을 완료하면, **Then** A의 인증 세션·Refresh Token·월드 접속은 즉시 종료되고 A에는 재로그인 안내가 표시되며 B의 새 세션만 보호 기능과 월드를 이용할 수 있다.
5. **Given** 일반 회원 로그인 성공, **When** 로그인 응답을 확인하면, **Then** Access Token은 응답 본문에 있고 Refresh Token은 보안 속성이 적용된 쿠키에만 있다.
6. **Given** 유효한 Refresh Token으로 Access Token을 갱신한 상황, **When** 갱신이 성공하면, **Then** 기존 Refresh Token은 폐기되고 새 Refresh Token으로 교체된다.
7. **Given** 이미 교체되어 폐기된 Refresh Token이 다시 사용된 상황, **When** 서버가 재사용을 감지하면, **Then** 관련 인증 세션이 차단되고 재로그인이 요구된다.

### User Story 4 — 내 프로필과 계정을 관리한다 (Priority: P1)

로그인 사용자는 내 정보와 계정 상태를 확인하고 허용된 프로필 정보를 수정하며 회원 탈퇴를 요청할 수 있다.

**Why this priority**: 사용자가 서비스에 저장된 자신의 상태를 이해하고 통제할 수 있어야 한다.

**Independent Test**: 내 정보 조회 → 닉네임 변경 → 재로그인 후 변경값 확인 → 탈퇴 확인 절차 → 이후 로그인 차단까지 독립적으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 내 정보를 열면, **Then** 닉네임, 연결된 로그인 제공자, 계정 상태, 코인 잔액, 부스 상태, 아바타 요약을 확인할 수 있다.
2. **Given** 활성 사용자, **When** 허용된 형식의 닉네임으로 변경하면, **Then** 변경값이 저장되고 이후 화면과 월드 입장에 동일하게 반영된다.
3. **Given** 허용되지 않은 프로필 값, **When** 저장을 요청하면, **Then** 기존 값은 유지되고 거부 사유와 수정 방법이 표시된다.
4. **Given** 탈퇴하려는 사용자, **When** 영향 범위와 복구 가능 여부를 확인하고 탈퇴를 확정하면, **Then** 계정은 즉시 보호 기능에 사용할 수 없는 상태가 되고 모든 활성 인증 세션이 종료된다.
5. **Given** 탈퇴를 확정한 사용자, **When** 삭제 Workflow가 완료되면, **Then** User와 직접 연결된 소유·참여 데이터, 파일, OAuth 연결, Redis 세션을 즉시 hard delete하고 더 이상 회원 테이블에 남기지 않는다.

### User Story 5 — 관리자가 회원 상태를 운영한다 (Priority: P1)

관리자는 서비스 운영을 위해 회원을 검색하고 상태를 확인하며, 필요한 경우 기간 없는 수동 정지와 수동 정지 해제를 수행한다.

**Why this priority**: 부정 이용 대응과 서비스 운영에 최소한의 회원 관리 수단이 필요하다.

**Independent Test**: 일반 사용자로 관리자 기능 접근이 차단되는지 확인한 뒤, 관리자 계정으로 회원 검색 → 정지 → 로그인 차단 → 정지 해제 → 로그인 복구 흐름을 검증한다.

**Acceptance Scenarios**:

1. **Given** 관리자, **When** 식별자·닉네임·상태 조건으로 회원을 찾으면, **Then** 일치하는 회원 목록과 현재 상태를 확인할 수 있다.
2. **Given** 활성 회원, **When** 관리자가 사유를 입력해 기간 없는 수동 정지를 수행하면, **Then** 새 로그인·보호 기능·월드 접속이 차단되고 활성 인증 세션과 월드 접속이 종료된다.
3. **Given** 정지 회원, **When** 관리자가 수동으로 정지를 해제하면, **Then** 해당 회원은 기존 소셜 계정으로 다시 정상 로그인할 수 있다.
4. **Given** 일반 사용자, **When** 회원 관리 기능에 접근하면, **Then** 다른 회원의 정보가 노출되지 않고 접근이 거부된다.
5. **Given** 관리자가 회원 상태를 변경한 상황, **When** 운영 이력을 확인하면, **Then** 대상, 변경 전후 상태, 사유, 수행자, 시각을 추적할 수 있다.

### User Story 6 — 인증된 신원으로 월드에 입장한다 (Priority: P0)

로그인 사용자와 게스트는 자신의 승인된 신원으로만 월드에 입장하며, 장기 인증 수단은 Unity 클라이언트나 게임 서버에 전달되지 않는다.

**Why this priority**: 웹 계정과 실시간 월드 신원을 안전하게 연결하는 공통 계약이며 spec 002의 전제다.

**Independent Test**: 월드 입장 권한을 발급받아 한 번 사용한 뒤 재사용·만료·변조된 권한으로 입장을 시도하고 모두 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 월드 입장이 허용된 사용자, **When** 월드 입장을 요청하면, **Then** 짧은 시간 동안 한 번만 사용할 수 있는 입장 권한과 목적 층·접속 위치 정보를 받는다.
2. **Given** 이미 사용했거나 만료되거나 변조된 입장 권한, **When** 월드 접속을 시도하면, **Then** 입장이 거부되고 재시도 가능한 방식으로 안내된다.
3. **Given** 정지·탈퇴 사용자의 기존 입장 권한, **When** 월드 접속을 시도하면, **Then** 승인되지 않는다.
4. **Given** 임의의 사용자 식별자·닉네임을 주장하는 클라이언트, **When** 월드 접속을 시도하면, **Then** 승인된 신원만 적용되고 클라이언트 주장은 신뢰되지 않는다.
5. **Given** Unity 클라이언트와 게임 서버, **When** 배포 산출물·통신·로그를 검사하면, **Then** 로그인 갱신용 인증 수단이 존재하지 않는다.
6. **Given** 특정 월드 채널의 접속 인원이 40명인 상황, **When** 사용자가 월드 입장을 요청하면, **Then** 수용 가능한 다른 채널의 입장 정보를 받고 해당 채널로 이동할 수 있다.

### Edge Cases

- Google 또는 Kakao가 같은 인증 결과를 재전송하거나 사용자가 여러 탭에서 동시에 최초 로그인을 완료하는 경우
- 소셜 제공자는 인증에 성공했지만 서비스 계정 생성 또는 최초 혜택 지급 중 일부가 실패한 경우
- 소셜 인증 성공 후 필수 가입값 입력 화면에서 뒤로 가기·새로고침·창 닫기를 수행한 경우
- 필수 가입값 완료 요청이 여러 탭에서 동시에 제출된 경우
- Google과 Kakao가 같은 이메일을 제공하지만 서비스에 연결된 제공자 식별자는 서로 다른 경우
- 소셜 제공자가 이메일·프로필 이름 등 선택 정보를 제공하지 않거나 사용자가 제공 동의를 철회한 경우
- 로그인 콜백 직전에 창이 닫히거나 네트워크가 끊긴 뒤 사용자가 다시 시도하는 경우
- 닉네임 변경과 월드 입장이 동시에 발생해 이전·새 닉네임이 섞일 수 있는 경우
- 관리자 정지와 인증 갱신 또는 월드 입장이 동시에 발생하는 경우
- 정지된 회원이 자동 만료를 기대하거나, 정지 해제 전 재로그인을 반복하는 경우
- 같은 계정이 다른 브라우저에서 새 로그인하는 동시에 기존 브라우저가 인증 갱신 또는 보호 기능을 요청하는 경우
- 다른 브라우저 로그인으로 세션이 종료된 사용자가 월드 안에 남아 있는 경우
- 특정 월드 채널의 인원이 40명에 도달한 경우
- 최종 탈퇴 Job이 외부 파일·Vector·OAuth 처리 중 일부 실패한 뒤 재실행되는 경우
- 게스트 Access Token이 만료되거나 여러 탭에서 재사용되는 경우
- 폐기된 Refresh Token을 공격자 또는 다른 기기가 재사용하는 경우
- 인증 시스템이 일시 장애인 동안 이미 월드에 입장한 사용자의 세션 처리

## Requirements

### Functional Requirements

#### 가입·로그인

- **FR-001**: 시스템은 Google·Kakao·SSAFY 소셜 로그인만 제공해야 한다.
- **FR-002**: 시스템은 자체 이메일·비밀번호 회원가입, 로그인, 비밀번호 찾기를 제공해서는 안 된다.
- **FR-003**: 시스템은 소셜 제공자의 계정 식별자를 검증한 뒤 최초 로그인 시 서비스 계정을 자동 생성해야 한다.
- **FR-004**: 같은 소셜 제공자와 제공자 계정 식별자의 조합은 하나의 서비스 계정에만 연결되어야 한다.
- **FR-005**: 동일한 최초 로그인 요청이 반복되거나 동시에 처리되어도 서비스 계정과 최초 가입 혜택은 중복 생성되지 않아야 한다.
- **FR-006**: 동일한 연결 소셜 계정으로 재로그인하면 기존 서비스 계정과 영구 데이터를 복원해야 한다.
- **FR-006a**: 서로 다른 소셜 제공자가 같은 검증된 이메일을 반환하고 기존 활성 또는 탈퇴 계정이 있으면 자동 병합·새 계정 생성을 하지 않고 중복 계정으로 판정해야 한다.
- **FR-006b**: 중복 계정으로 판정된 사용자는 기존 가입에 사용한 소셜 제공자로 로그인하도록 안내해야 한다.
- **FR-007**: 인증 취소·실패·계정 상태 차단 시 실패를 조용히 삼키지 않고 사용자에게 원인 범주와 재시도 또는 문의 방법을 알려야 한다.
- **FR-007a**: 소셜 인증 성공 후 닉네임 등 필수 가입값을 검증하고, 누락되거나 유효하지 않으면 어떤 값이 필요한지 표시하며 가입 완료 단계로 안내해야 한다.
- **FR-007b**: 필수 가입값을 완료하기 전에는 활성 User, 지갑, 최초 가입 혜택과 회원용 인증 수단을 생성해서는 안 된다.
- **FR-007c**: 미완성 사용자가 같은 소셜 계정으로 다시 인증하면 중복 회원을 만들지 않고 필수 가입값 입력 단계로 다시 안내해야 한다.
- **FR-007d**: 필수 가입값 완료 요청이 반복되거나 동시에 처리되어도 User, 지갑과 최초 가입 혜택은 각각 한 번만 생성되어야 한다.
- **FR-007e**: 닉네임은 [닉네임 정책](contracts/nickname-policy.md)의 정규화·금칙어·예약어·광고 및 개인정보 유도 패턴 검사를 모두 통과해야 하며, 실패 시 이유를 노출하지 않는 일반 안내와 수정 방법을 표시해야 한다.

#### 게스트

- **FR-008**: 시스템은 계정 생성 없는 게스트 입장을 제공하고 게스트 Access Token만 응답 본문으로 발급해야 한다.
- **FR-009**: 게스트에게 Refresh Token을 발급하거나 Refresh Token 쿠키를 설정해서는 안 된다.
- **FR-009a**: 게스트 Access Token의 유효기간은 30분으로 하고, 만료 후 계속 관람하려면 게스트 입장을 다시 시작해 새 Access Token을 받아야 한다.
- **FR-010**: 게스트는 공개된 월드·부스를 관람하는 기능만 사용할 수 있어야 하며 외형 변경, 부스 임대, 코인 조회·지급·사용, 스튜디오, 결제, 보상, 영구 자산 획득과 기타 상태 변경 기능을 사용할 수 없어야 한다.
- **FR-011**: 게스트가 제한 기능을 시도하면 소셜 로그인이 필요하다는 안내와 로그인 진입점을 제공해야 한다.
- **FR-012**: 게스트가 소셜 계정으로 전환할 때 게스트의 경제·자산 상태를 신규 계정에 이전해서는 안 된다.
- **FR-012a**: 게스트 인증 정보와 활동은 영속 User, 지갑, 임대, 인벤토리 또는 저장 아바타를 생성해서는 안 된다.

#### 인증 세션·월드 입장

- **FR-013**: 일반 회원 로그인 성공 시 Access Token은 응답 본문으로, Refresh Token은 쿠키로 발급해야 한다.
- **FR-013a**: Refresh Token 쿠키는 `Secure`, `HttpOnly` 속성을 가져야 하며 Access Token보다 긴 만료시간을 가져야 한다.
- **FR-013b**: Refresh Token 쿠키의 `Path`는 Access Token 갱신 endpoint로 제한해야 한다.
- **FR-013c**: 서버는 Refresh Token 사용 시마다 토큰을 교체하고 기존 토큰을 폐기하는 rotation을 수행해야 한다.
- **FR-013d**: 서버는 폐기된 Refresh Token의 재사용을 탐지하고 관련 토큰 계열과 인증 세션을 차단한 뒤 재로그인을 요구해야 한다.
- **FR-013e**: Refresh Token 쿠키의 `SameSite` 정책은 `Lax`로 하고 배포 환경 전체에 일관되게 적용해야 한다.
- **FR-014**: 인증 수단은 갱신용, 서비스 기능 호출용, 월드 입장용, 실시간 상담용의 네 경계로 분리되어야 한다.
- **FR-015**: 로그인 갱신용 인증 수단은 Unity 클라이언트와 게임 서버에 전달되거나 로그에 기록되어서는 안 된다.
- **FR-016**: 월드 입장 권한은 짧은 수명을 가진 1회용이어야 하며 사용·만료·변조 시 거부되어야 한다.
- **FR-017**: 게임 서버는 Spring에 매번 조회하지 않고 월드 입장 권한의 서명과 승인된 사용자 신원을 검증할 수 있어야 한다.
- **FR-018**: 게임 서버는 사용된 월드 입장 권한 식별자를 기록해 재사용을 차단해야 한다.
- **FR-019**: 서버는 클라이언트가 보낸 사용자 식별자, 닉네임, 역할을 검증 없이 신뢰해서는 안 된다.
- **FR-020**: 로그아웃 시 최소한 현재 인증 세션을 즉시 사용할 수 없게 해야 한다.
- **FR-020a**: 일반 회원 계정은 동시에 하나의 브라우저 인증 세션만 활성 상태로 유지해야 하며, 다른 브라우저에서 새 로그인이 성공하면 이전 브라우저의 인증 세션과 Refresh Token을 즉시 종료해야 한다.
- **FR-020b**: 다른 브라우저 로그인으로 종료된 세션이 Access Token 갱신 또는 보호 기능을 요청하면 요청을 거부하고, 다른 곳에서 로그인되어 세션이 종료되었다는 재로그인 안내를 제공해야 한다.
- **FR-020c**: 다른 브라우저 로그인으로 세션이 종료되면 기존 월드 접속도 즉시 종료하고, 기존 Connection Token과 월드 세션은 재사용할 수 없게 해야 한다.
- **FR-021**: 계정 정지 또는 탈퇴 확정 시 해당 사용자의 활성 인증 세션·Refresh Token·Unity 월드 세션을 모두 종료하고 새 인증을 차단해야 한다.
- **FR-021a**: OAuth 인증 요청·콜백은 요청 위조와 다른 서비스의 콜백 재사용을 방지해야 하며, 검증된 제공자·허용된 반환 주소의 응답만 로그인 처리해야 한다.
- **FR-021b**: OAuth 인증 성공 후 백엔드는 기존 회원과 최초 가입자를 모두 프론트엔드의 단일 `/auth/callback` 경로로 redirect해야 한다. OAuth handoff 식별자는 URL query·fragment·프론트 JavaScript에 노출하지 않고, 1회성·짧은 TTL의 `Secure`·`HttpOnly`·`SameSite=Lax` 쿠키로만 전달한다.
- **FR-021c**: `POST /api/v1/auth/oauth/complete`는 OAuth handoff 쿠키를 기준으로 기존 회원 또는 미완성 가입 시도를 식별해야 한다. 기존 회원은 Access Token 본문과 Refresh Token 쿠키를 반환하고 handoff를 소비한다. 최초 가입에서 닉네임이 없으면 `NICKNAME_REQUIRED`만 반환하고 handoff를 보존하며, 유효한 닉네임 제출 시에만 handoff를 소비해 회원·세션을 생성한다.
- **FR-021b**: 소셜 제공자에서 받은 계정 식별 정보는 제공자가 발급한 유효한 응답인지 확인한 뒤에만 서비스 계정에 연결해야 한다.
- **FR-021c**: 로그인·게스트 토큰 발급과 월드 입장 요청은 악의적 반복 요청으로 서비스가 불안정해지지 않도록 제한해야 한다.
- **FR-021d**: 각 월드 채널은 동시 접속자 40명을 초과해서는 안 되며, 채널이 가득 차면 수용 가능한 다른 채널의 입장 정보를 제공해야 한다. 채널 배정·이동 상세 계약은 spec 002에서 정의한다.

#### 내 계정 관리

- **FR-022**: 로그인 사용자는 자신의 식별 정보, 연결 로그인 제공자, 닉네임, 계정 상태, 코인 잔액, 부스 상태, 아바타 요약을 조회할 수 있어야 한다.
- **FR-023**: 사용자는 허용된 프로필 정보만 수정할 수 있으며 소셜 제공자 식별자, 계정 상태, 권한은 직접 수정할 수 없어야 한다.
- **FR-024**: 프로필 수정값이 거부되면 기존 값을 유지하고 구체적인 거부 사유를 표시해야 한다.
- **FR-025**: 탈퇴 전 즉시 hard delete 대상(본인 소유·참여 데이터와 타인 참여 종속 데이터 포함)을 확인하고 재확인해야 한다.
- **FR-026**: 탈퇴 확정 즉시 프로필·공개 Booth/콘텐츠를 비노출하고 세션·토큰·월드 접속을 종료한 뒤, 관련 데이터 전체 삭제 Workflow를 시작해야 한다.
- **FR-027**: idempotent 삭제 Workflow는 User를 마지막으로 hard delete하며, User/Profile/OAuth/Wallet/Coin Ledger/Booth·Layout·Draft/Project/AI Agent·Document·Vector/Survey·Response/Like·Vote/Consultation·Conversation·Message/Inventory/업로드 파일 및 사용자와 직접 연결된 참여 데이터를 소유 방향과 무관하게 삭제해야 한다.
- **FR-027a**: 삭제 Workflow는 Redis·파일 저장소·Vector·OAuth revoke/unlink 등 외부 처리를 재실행 가능하게 수행하고 연결된 모든 소셜 제공자(Google·Kakao·SSAFY)의 revoke/unlink 및 식별 정보 삭제를 최종 단계에서 수행해야 한다.

#### 관리자 회원 관리

- **FR-028**: 관리자만 회원 목록·상세·운영 상태를 조회할 수 있어야 한다.
- **FR-029**: 관리자는 식별자, 닉네임, 소셜 제공자, 계정 상태로 회원을 검색·필터링할 수 있어야 한다.
- **FR-030**: 관리자는 사유를 입력해 활성 회원을 기간 없는 수동 정지 상태로 전환하고, 정지 회원을 수동으로 해제할 수 있어야 한다.
- **FR-031**: 정지 회원은 새 로그인, 토큰 갱신, 보호 기능과 월드 접속이 차단되어야 하며 활성 인증 세션과 월드 접속은 종료되어야 한다. 정지에는 자동 만료가 없고, 관리자 해제 후에만 기존 소셜 계정으로 다시 로그인할 수 있어야 한다.
- **FR-032**: 회원 상태 변경 이력에는 대상 회원, 변경 전후 상태, 사유, 수행 관리자, 시각이 남아야 한다.
- **FR-033**: 일반 사용자와 게스트는 다른 회원의 비공개 정보나 관리자 회원 관리 기능에 접근할 수 없어야 한다.
- **FR-034**: 관리자도 사용자의 소셜 제공자 계정 식별자를 다른 사용자에게 이전하거나 임의 변경할 수 없어야 한다.

| 외형 변경·부스 임대·코인·스튜디오·결제·보상 | 차단 | 허용 | 차단 | 회원 권한에 따름 |

| 회원 탈퇴 요청 | 차단 | 본인만 | 중복 요청 차단 | 대리 탈퇴 제외 |
| 회원 목록·상태 조회 | 차단 | 차단 | 차단 | 허용 |
| 회원 정지·정지 해제 | 차단 | 차단 | 차단 | 허용 |

### Key Entities

- **User**: 영속 서비스 계정. 상태는 `ACTIVE`·`SUSPENDED`만 사용하며 최종 탈퇴 후 row는 존재하지 않는다.
- **Social Identity**: 소셜 제공자와 제공자 계정 식별자의 연결. 한 연결은 하나의 User에만 속한다. 같은 검증된 이메일을 가진 서로 다른 제공자 연결은 자동 병합하지 않고 중복 가입을 차단한다.
- **Guest Session**: 영속 User가 없는 임시 둘러보기 세션. 만료·종료 기준만 가지며 영구 자산과 연결되지 않는다.
- **Auth Session**: 로그인 사용자의 브라우저별 인증 세션. 사용자, 생성·만료·종료 시각, 상태와 연결되며 일반 회원은 한 번에 하나만 활성 상태일 수 있다.
- **Registration Attempt**: 소셜 인증은 성공했지만 필수 가입값을 완료하지 않은 임시 가입 시도. 활성 User·지갑·가입 혜택을 생성하지 않으며 재인증 시 가입 완료 단계로 연결한다.
- **OAuth Handoff**: OAuth callback과 React 완료 API 사이에만 존재하는 1회성·짧은 TTL 전달 상태. Redis의 기존 회원 세션 또는 미완성 가입 시도를 가리키며, 식별자는 HttpOnly 쿠키로만 브라우저에 전달한다.
- **Refresh Token Family**: 일반 회원의 Refresh Token 교체 계보. 현재 토큰, 만료·폐기 상태와 재사용 탐지 결과를 추적하며 게스트에게는 존재하지 않는다.
- **World Entry Grant**: 특정 사용자 또는 게스트가 특정 목적 층·세션에 한 번 입장할 수 있음을 나타내는 단기 권한. 사용 여부와 만료를 가진다.
- **Account Status History**: 회원 상태 변경 감사 기록. 대상, 이전·이후 상태, 사유, 수행자, 시각을 가진다.
- **Deletion Workflow**: 탈퇴 확정 시 DB·Redis·파일·Vector·OAuth 삭제 단계를 idempotent하게 기록·재실행하는 작업 단위. User row 삭제는 마지막 단계다.

### Scope Boundaries

**포함**:

- Google/Kakao 최초 소셜 로그인 기반 자동 가입과 재로그인
- 비영속 게스트 입장과 기능 제한
- 인증 유지·갱신·로그아웃의 사용자 결과
- 내 정보 조회, 닉네임 수정, 회원 탈퇴
- 관리자 회원 검색, 상태 조회, 정지·정지 해제, 감사 이력
- spec 002에 전달할 안전한 월드 입장 권한의 인증 경계

**제외**:

- 이메일/비밀번호 회원가입·로그인·비밀번호 재설정
- Google과 Kakao 계정 간 사용자가 직접 수행하는 연결·통합·분리 기능
- 관리자 권한 부여·회수, 세부 운영자 권한 체계
- 관리자에 의한 회원 영구 삭제 또는 타인 계정 대리 탈퇴
- 월드 채널 배정, 중복 월드 접속, 재접속 정책의 상세 동작(spec 002 범위)
- 코인 지급 금액·원장 처리 상세(spec 003 범위)
- 아바타 저장 형식과 편집 UI 상세(spec 013 범위)

## Success Criteria

### Measurable Outcomes

- **SC-001**: 신규 사용자의 90% 이상이 소셜 제공자 선택부터 서비스 홈 도달까지 30초 이내에 완료한다(소셜 제공자 체류 시간 제외).
- **SC-002**: 동일 소셜 계정의 반복·동시 최초 로그인 시험에서 중복 사용자 계정과 중복 최초 혜택 생성이 0건이다.
- **SC-003**: 게스트 이용 후 영속 사용자·지갑·임대·인벤토리·아바타 데이터와 Refresh Token이 생성된 사례가 0건이다.
- **SC-004**: 게스트의 외형 변경·부스 임대·코인·스튜디오·결제·보상·영구 자산 획득 시도가 100% 차단된다.
- **SC-005**: 로그아웃·정지·탈퇴 또는 다른 브라우저의 새 로그인으로 종료된 인증 세션을 이용한 보호 기능 접근·토큰 갱신·월드 접속이 100% 차단된다.
- **SC-017**: 채널별 동시 접속자는 40명을 초과하지 않으며, 가득 찬 채널에 입장을 시도한 사용자는 수용 가능한 채널로 100% 안내된다.
- **SC-018**: 정책에 정의된 금칙어·예약어·광고 및 개인정보 유도 패턴을 포함한 닉네임은 100% 등록·변경이 거부된다.
- **SC-006**: 사용·만료·변조된 월드 입장 권한으로 월드에 진입한 사례가 0건이다.
- **SC-007**: Unity 빌드 산출물, 게임 서버 통신과 로그에서 로그인 갱신용 인증 수단이 발견된 사례가 0건이다.
- **SC-008**: 일반 사용자 또는 게스트가 다른 회원의 비공개 정보와 관리자 회원 관리 기능에 접근한 사례가 0건이다.
- **SC-009**: 관리자 회원 상태 변경의 감사 항목(대상, 전후 상태, 사유, 수행자, 시각) 누락이 0건이다.
- **SC-010**: 사용자의 90% 이상이 도움 없이 내 정보 조회와 닉네임 변경을 1분 이내에 완료한다.
- **SC-011**: 탈퇴를 확정한 사용자의 새 로그인과 보호 기능 접근이 10초 이내에 차단된다.
- **SC-012**: 필수 가입값이 누락된 사용자가 활성 회원으로 로그인하거나 지갑·최초 가입 혜택을 받은 사례가 0건이다.
- **SC-013**: 필수 가입값 입력을 중단한 사용자가 재인증했을 때 100% 가입 완료 단계로 다시 안내된다.
- **SC-014**: Refresh Token rotation 시험에서 폐기 토큰 재사용이 100% 탐지되고 관련 인증 세션이 차단된다.
- **SC-015**: 동일한 검증 이메일의 소셜 제공자 교차 가입 시험(Google·Kakao·SSAFY 전 조합)에서 중복 User·지갑·가입 혜택 생성이 0건이다.
- **SC-016**: 탈퇴 확정 뒤 User 및 직접 연결된 소유·참여 데이터가 남은 사례는 0건이다.

## Assumptions & Dependencies

### Assumptions

- 닉네임은 소셜 프로필 이름이 있으면 초기 제안값으로만 사용하며, 서비스 내부 사용자 식별자는 별도로 유지한다.
- 닉네임 중복 여부와 무관하게 권한 판단·월드 신원 확인은 변경 불가능한 내부 사용자 식별자를 기준으로 한다.
- 소셜 제공자가 전달한 이메일은 표시·연락 정책에 활용할 수 있지만 계정 병합의 단독 근거로 사용하지 않는다.
- 서로 다른 소셜 제공자가 같은 검증된 이메일을 반환하면 보안상 자동 병합하지 않고, 기존 계정이 있으면 신규 가입을 차단한다.
- 탈퇴는 취소 불가능하며, 확정 즉시 관련 데이터 전체를 hard delete한다. 같은 소셜 계정으로 다시 인증하면 신규 가입으로 처리한다.
- OAuth 세부 구현은 사용자가 직접 관리하지 않는다. 서비스는 요청 위조 방지값, 허용된 반환 주소, 제공자 응답의 유효성을 검증하는 표준 소셜 로그인 흐름을 사용한다.
- OAuth callback 이후 프론트엔드 계약은 단일 `/auth/callback`과 `POST /api/v1/auth/oauth/complete`다. URL ticket을 읽거나 `/exchange`, `/registration/complete`를 호출하는 계약은 사용하지 않는다.
- 일반 회원은 브라우저 프로필 단위로 한 번에 하나의 활성 인증 세션만 허용한다. 새 브라우저 로그인은 기존 브라우저 세션을 종료하며, 같은 브라우저의 탭은 하나의 세션을 공유할 수 있다.
- 게스트에서 소셜 회원으로 전환할 때 경제·자산은 이전하지 않으며, 전환 UX에 필요한 일시적 화면 상태만 유지할 수 있다.
- 관리자 회원 관리의 MVP는 검색·조회·정지·정지 해제에 한정한다.
- 회원 정지는 기간을 두지 않는 수동 운영 정책이며, 자동 해제·경고·누적 제재·이의 제기 기능은 MVP 범위에서 제외한다.
- 인증 실패는 소셜 제공자 오류, 사용자 취소, 세션 만료, 계정 상태 차단처럼 사용자가 행동을 선택할 수 있는 범주로 안내한다.
- 미완성 가입 시도는 활성 User로 취급하지 않으며 필수값 완료 후에만 V1 스키마의 `users.nickname NOT NULL UNIQUE` 조건을 만족하는 User를 생성한다.

### Dependencies

- Google 및 Kakao 소셜 인증 서비스와 해당 서비스의 운영 설정
- spec 003의 신규 회원 최초 코인 지급 중복 방지 계약
- spec 002의 목적 층을 포함한 world-session 응답 및 월드 입장 권한 소비 계약
- spec 013의 회원 아바타 저장과 게스트 기본 외형 고정 경계
- 회원 탈퇴 데이터 보존 정책에 대한 팀 결정

## Clarifications

아래 항목은 헌법 30조에 따라 구현자가 임의 확정하지 않는다.

### Session 2026-08-18

- Q: 소셜 인증 후 필수 가입값을 완료하지 못한 사용자를 어떻게 처리하는가? → A: 필수값을 다시 확인·입력하도록 가입 완료 단계로 안내하고, 완료 전에는 활성 회원·지갑·가입 혜택을 만들지 않는다.
- Q: 게스트에게 어떤 인증 수단과 권한을 주는가? → A: 응답 본문의 Access Token만 발급하고 Refresh Token 없이 공개 월드·부스 관람만 허용한다.
- Q: 게스트가 할 수 없는 행위는 무엇인가? → A: 외형 변경, 부스 임대, 코인, 스튜디오, 결제, 보상과 모든 상태 변경을 금지한다.
- Q: 일반 회원의 Access/Refresh Token은 어떻게 전달하고 보호하는가? → A: Access Token은 응답 본문, Refresh Token은 Secure·HttpOnly·제한 Path·장수명 쿠키로 전달하며 서버 rotation과 reuse detection을 적용한다.
- Q: 탈퇴 후 같은 소셜 계정으로 인증하면 어떻게 처리하는가? → A: 기존 계정과 연결 데이터가 삭제되므로 신규 가입으로 처리한다.
- Q: Google과 Kakao가 같은 검증된 이메일을 반환하면 어떻게 처리하는가? → A: 자동 병합하지 않고 중복 계정으로 판정해 신규 계정 생성을 차단하고 기존 가입 경로로 로그인하도록 안내한다.
- Q: 게스트 Access Token의 만료와 재입장은 어떻게 처리하는가? → A: Refresh Token 없이 Access Token만 발급하며 30분 만료 후 게스트 입장을 다시 선택해 새 토큰을 받는다.
- Q: Refresh Token 쿠키의 SameSite 정책은 무엇인가? → A: `SameSite=Lax`를 적용한다.
- Q: 다른 브라우저에서 새 로그인하면 기존 월드 접속은 어떻게 처리하는가? → A: 기존 인증 세션·토큰을 만료시키고 월드에서 즉시 퇴장시킨다.
- Q: 탈퇴 데이터의 보존·삭제는 어떻게 처리하는가? → A: 탈퇴 확정 즉시 User와 직접 연결된 소유·참여 데이터 전체를 hard delete하고 익명화 보존하지 않는다.
- Q: 월드 접속 인원과 가득 찬 채널 처리는 어떻게 하는가? → A: 채널당 40명으로 제한하고 가득 차면 다른 수용 가능 채널의 입장 정보로 이동시킨다.
- Q: 닉네임 금칙어는 어떻게 적용하는가? → A: 별도 닉네임 정책의 정규화·HARD_BLOCK·RESERVED·광고/개인정보 유도 패턴을 적용한다.
- Q: 회원 정지 기간은 어떻게 운영하는가? → A: 기간 없는 수동 정지·수동 해제로 운영하며 자동 만료는 없다.
