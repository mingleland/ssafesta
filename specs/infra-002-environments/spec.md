# Feature Specification: dev/demo 실행 환경

**Feature Branch**: `infra-002-environments` *(spec 식별자이며 Git 브랜치명과는 독립)*

**Created**: 2026-08-20

**Status**: Ready for Planning — **Infra 리뷰 완료** *(C-01·C-02 운영 입력 대기)*

**Input**: `docs/sdd/parts/INFRA.md`의 `infra-002` 초안과 `docs/30_NEW_AI_시스템_설계서.md`의 IAM 없는 단일 서버 제안을 바탕으로, 기존 `infra-001` 파이프라인이 배포할 dev/demo 실행 환경을 명세한다. 초기에는 제공받은 서버 주소와 SSH·서버 방화벽 설정 권한만 사용하며, 비용을 발생시키지 않는 범위에서 외부 문서 저장소와 최종 DNS/CDN 적용을 목표로 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 파트별 dev 환경을 독립적으로 운영한다 (Priority: P0)

파트 개발자는 자기 파트의 변경을 dev 환경에 배포하고, 다른 파트가 사용 중인 서비스와 데이터를 불필요하게 중단하지 않은 채 결과를 확인한다.

**Why this priority**: `infra-001`의 파트별 독립 배포가 실제 실행 대상을 가져야 네 파트가 서로 기다리지 않고 개발할 수 있다.

**Independent Test**: `ai`, `back`, `front`, `game` 중 한 파트의 새 릴리스를 dev 대상에 적용하고, 해당 파트만 갱신되며 다른 파트의 실행 상태와 영속 데이터가 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 네 파트의 dev 서비스가 실행 중일 때, **When** 한 파트의 유효한 릴리스를 배포하면, **Then** 해당 파트만 갱신되고 나머지 파트는 재시작되지 않는다.
2. **Given** 한 파트가 아직 준비되지 않았을 때, **When** 다른 파트가 dev 환경을 사용하면, **Then** 승인된 Mock 또는 대체 경로로 자기 파트의 기능을 검증할 수 있다.
3. **Given** dev 배포가 실패했을 때, **When** 실패 결과를 확인하면, **Then** demo 환경과 다른 파트 dev 환경은 기존 상태를 유지한다.

### User Story 2 - develop을 통합 demo 환경으로 제공한다 (Priority: P0)

팀원과 시연 담당자는 `develop`에서 검증된 전체 서비스를 하나의 demo 환경으로 사용하고, 웹·API·AI 기능이 동일한 공개 진입점 체계에서 연결되는지 확인한다.

**Why this priority**: 개별 파트 성공만으로는 최종 사용자 여정이 이어지는지 알 수 없으며, demo는 실사용 기준선 역할을 해야 한다.

**Independent Test**: 통합 릴리스를 demo에 적용한 뒤 공개 웹 접속, 로그인 API, AI 상태 확인과 문서 처리 경로를 순서대로 검증하고 각 결과를 동일 릴리스에 연결한다.

**Acceptance Scenarios**:

1. **Given** 검증된 통합 릴리스가 있을 때, **When** demo 환경에 배포하면, **Then** 공개 웹·Backend·AI 서비스가 환경별 주소를 통해 접근 가능하다.
2. **Given** 일부 서비스가 준비되지 않았거나 실패했을 때, **When** demo 검증을 수행하면, **Then** 실패 서비스와 정상 서비스를 구분할 수 있고 정상인 비AI 기능을 불필요하게 중단하지 않는다.
3. **Given** demo 배포가 성공했을 때, **When** 담당자가 현재 환경을 조회하면, **Then** 실행 중인 각 파트 릴리스를 원본 변경까지 추적할 수 있다.

---

### User Story 3 - 영구 데이터와 AI 문서를 안전하게 보존한다 (Priority: P0)

사용자는 서비스 재배포와 컨테이너 재생성 이후에도 영구 비즈니스 데이터와 업로드한 AI 문서를 잃지 않고 계속 이용한다.

**Why this priority**: 단일 서버 재배포 때 데이터가 사라지면 로그인·부스·AI 문서 기능을 시연할 수 없으며 복구도 불가능하다.

**Independent Test**: 테스트 영구 데이터와 비공개 문서를 저장한 뒤 관련 서비스만 재생성하고, 메타데이터·원본 문서·검색 가능 상태가 그대로 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 영구 데이터와 문서가 저장되어 있을 때, **When** 애플리케이션 서비스가 재배포되면, **Then** 저장된 데이터와 문서가 유지된다.
2. **Given** 권한 있는 사용자가 문서를 업로드할 때, **When** 업로드가 진행되면, **Then** 파일 본문은 애플리케이션 서버를 불필요하게 경유하지 않고 비공개 저장소에 전달된다.
3. **Given** 클라이언트가 업로드 완료를 알렸을 때, **When** 서버가 저장 결과를 확인하면, **Then** 실제 파일의 존재·크기·형식이 유효한 경우에만 후속 처리를 시작한다.
4. **Given** 문서 저장소가 일시적으로 실패했을 때, **When** 사용자가 비AI 기능을 이용하면, **Then** 해당 장애가 월드·부스·로그인 등 비AI 기능 전체 장애로 전파되지 않는다.

### User Story 4 - Secret과 내부 서비스를 외부에 노출하지 않는다 (Priority: P0)

운영 담당자는 필요한 공개 서비스만 외부에 제공하고, 데이터 저장소·관리 화면·인증정보는 승인된 경로에서만 접근되도록 운영한다.

**Why this priority**: 서버 주소가 공개된 환경에서 관리 포트나 Secret 노출은 즉시 보안 사고가 되며 헌법 15조를 위반한다.

**Independent Test**: 외부 네트워크에서 공개 포트와 주요 URL을 검사하고, 저장소·로그·배포 기록을 검색하여 내부 포트와 Secret 원문이 노출되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** demo 환경이 실행 중일 때, **When** 외부에서 포트를 검사하면, **Then** 승인된 SSH·웹 진입점 외의 데이터·관리 포트는 접근할 수 없다.
2. **Given** 환경별 Secret이 필요한 서비스가 배포될 때, **When** 설정·로그·산출물을 검사하면, **Then** 저장소와 보존 대상에 Secret 원문이 남지 않는다.
3. **Given** dev와 demo가 같은 물리 서버를 사용할 때, **When** 한 환경의 서비스가 다른 환경의 내부 주소나 Secret에 접근하려 하면, **Then** 승인되지 않은 접근은 차단된다.

---

### User Story 5 - 정적 콘텐츠 전송 부하를 외부로 분산한다 (Priority: P1)

최종 사용자는 React와 Unity Web 정적 콘텐츠를 안정적으로 내려받고, 반복 요청은 원본 서버의 전송 부하를 최소화한 경로로 제공받는다.

**Why this priority**: CDN 없이도 P0 기능은 동작할 수 있지만, 용량이 큰 Unity Web 산출물을 단일 서버가 반복 전송하면 시연 중 애플리케이션과 AI 처리에 필요한 자원을 잠식할 수 있다.

**Independent Test**: 버전이 지정된 정적 산출물을 배포한 뒤 최초 요청과 반복 요청의 원본 도달 여부, 압축 Header, 캐시 정책과 이전 버전 복구를 확인한다.

**Acceptance Scenarios**:

1. **Given** 새 정적 릴리스가 배포되었을 때, **When** 사용자가 웹에 접속하면, **Then** HTML과 정적 산출물이 올바른 형식과 압축 정보로 제공된다.
2. **Given** 동일한 버전의 정적 파일이 반복 요청될 때, **When** 외부 전송 계층이 정상일 때, **Then** 반복 요청은 원본 서버 도달을 줄이는 캐시 경로로 처리된다.
3. **Given** 외부 DNS/CDN을 사용할 수 없을 때, **When** demo 환경을 검증하면, **Then** 원본 서버의 정적 제공 경로로 핵심 기능을 계속 사용할 수 있다.
4. **Given** API·AI Streaming·게임 연결 요청이 발생할 때, **When** 외부 전송 계층을 통과하면, **Then** 사용자별 동적 응답이 정적 캐시로 저장되거나 다른 사용자에게 재사용되지 않는다.

### Edge Cases

- 서버 방화벽은 열렸지만 상위 네트워크 또는 AWS Security Group이 80/443을 차단한 경우
- 도메인 또는 DNS 변경 권한이 최종 배포 시점까지 제공되지 않은 경우
- 인증서 발급·갱신에 실패하거나 만료가 임박한 경우
- dev와 demo가 같은 포트·주소·볼륨·환경 식별자를 사용하려는 경우
- 한 서비스의 과도한 CPU·메모리·디스크 사용이 같은 서버의 다른 서비스와 CI/CD를 압박하는 경우
- 영속 데이터 볼륨은 남아 있지만 애플리케이션 버전과 데이터 스키마가 호환되지 않는 경우
- 외부 문서 저장소의 무료 사용량 또는 팀이 정한 무과금 안전 한도에 가까워진 경우
- 서명된 업로드 주소가 만료되었거나 서명 시 지정한 파일 형식과 실제 요청 Header가 다른 경우
- 클라이언트가 업로드 완료를 알렸지만 원본 객체가 없거나 크기·형식이 허용 범위를 벗어난 경우
- 문서 처리 작업이 시작되기 전에 다운로드 권한이 만료된 경우
- CDN에 이전 HTML 또는 Unity Web 산출물이 남아 새 릴리스와 혼합되는 경우
- 외부 DNS/CDN 또는 문서 저장소 장애가 발생했지만 원본 서버와 비AI 기능은 정상인 경우
- 같은 서버의 백업만 존재하여 서버 또는 디스크 전체 유실 시 함께 사라지는 경우
- 외부 Object Storage 계정 접근 불가 또는 원본 문서 손실이 발생했지만 별도 2차 문서 백업이 없는 경우
- Redis 재시작·장애로 세션·Presence·임시 Lock·캐시가 유실되거나 만료된 경우
- 문서 삭제·비활성화 또는 새 설문 응답 이후 이전 RAG 검색 결과·설문 집계 캐시가 남아 있는 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 `ai`, `back`, `front`, `game` 파트별 dev 배포 대상을 논리적으로 구분해야 한다.
- **FR-002**: 한 파트의 dev 배포는 다른 파트 dev 서비스와 demo 서비스의 실행 상태를 변경해서는 안 된다.
- **FR-003**: 시스템은 `develop` 통합 릴리스를 모든 필수 서비스가 연결되는 단일 demo 환경으로 제공해야 한다.
- **FR-004**: dev는 승인된 Mock 연동을 허용하되, demo는 실제 사용자 경로와 동일한 서비스 계약을 사용해야 한다.
- **FR-005**: 모든 서비스 주소와 환경별 연결정보는 배포 설정 또는 권위 있는 API 응답에서 주입되어야 하며 클라이언트 산출물에 환경별 서버 주소를 고정해서는 안 된다.
- **FR-006**: 최종 demo의 공개 웹·Backend·AI 서비스는 도메인 기반의 암호화된 단일 진입점 체계로 접근 가능해야 한다.
- **FR-007**: dev 환경은 승인된 공개 진입점을 통한 EC2 공인 IP 접근으로 제한적으로 검증하고, 최종 demo 환경은 사람이 기억할 수 있는 안정적인 도메인과 TLS를 사용해야 하며 두 환경의 검증 수준을 구분해야 한다.
- **FR-008**: 외부에 공개하는 기본 포트는 SSH·HTTP·HTTPS 용도로 제한하고 데이터 저장소·관측·CI 관리 포트는 외부에서 접근할 수 없게 해야 한다.
- **FR-009**: 서버 방화벽과 상위 네트워크 접근 정책을 각각 검증하고, 어느 계층이 연결을 차단하는지 구분할 수 있어야 한다.
- **FR-010**: 영구 비즈니스 데이터와 AI Vector 데이터는 애플리케이션 재배포·재생성으로 삭제되지 않는 저장 경계를 가져야 한다.
- **FR-011**: AI 원본 문서는 기본 비공개이며 애플리케이션 서버와 다른 장애 영역의 저장소를 우선 사용해야 한다.
- **FR-012**: 문서 저장 계약은 기존 S3-compatible 업로드·조회 계약을 유지하여 저장소 교체가 API 전면 변경으로 이어지지 않게 해야 한다.
- **FR-013**: 문서 업로드 권한과 안전한 Object Key는 영구 메타데이터의 Source of Truth가 결정해야 하며, 클라이언트가 주장한 사용자·부스·에이전트·경로를 그대로 신뢰해서는 안 된다.
- **FR-014**: 브라우저는 짧은 유효기간과 단일 객체·단일 작업 범위를 가진 업로드 권한으로 원본 문서를 저장소에 직접 전송할 수 있어야 한다.
- **FR-015**: 업로드 완료 처리는 저장소에서 실제 객체의 존재·크기·형식을 확인한 뒤에만 문서 처리 상태를 진행시켜야 한다.
- **FR-016**: AI 처리 서비스가 원본 문서를 읽는 권한은 최소 범위와 짧은 유효기간을 가져야 하며, 재시도 시 만료된 권한을 안전하게 갱신할 수 있어야 한다.
- **FR-017**: 외부 문서 저장소를 사용할 수 없는 경우 신규 업로드를 차단하고, 운영자가 검증된 S3-compatible 대체 저장소로 명시적으로 수동 전환한 뒤 업로드를 재개해야 한다. 자동 failover는 사용하지 않으며, 단순 로컬 파일 저장은 명시적인 비상 fallback으로만 허용해야 한다.
- **FR-018**: PostgreSQL 영구 데이터는 외부 Object Storage의 비공개 Backup 영역에 정기적으로 복구 가능한 형태로 백업해야 하며, 같은 EC2 안의 다른 경로에만 복사한 결과를 완전한 백업으로 간주해서는 안 된다. 원본 문서는 초기 범위에서 별도 2차 백업을 두지 않으며, Object Storage 계정 또는 데이터 손실 시 복구할 수 없다는 제한을 운영 문서에 명시해야 한다.
- **FR-019**: 실제 Secret은 저장소에 커밋하지 않고 승인된 비밀정보 경계에서 런타임에 주입해야 한다.
- **FR-020**: Secret·서명된 임시 URL·인증서 개인 키는 로그, 캐시, 배포 기록과 관측 데이터에 원문으로 남아서는 안 된다.
- **FR-021**: dev와 demo는 서비스 이름·내부 네트워크·환경 설정·영속 데이터·배포 상태가 서로 충돌하지 않게 구분되어야 한다.
- **FR-022**: 단일 서버에서 실행하는 서비스는 자원 사용량을 측정할 수 있어야 하며, 실측 전 임의의 용량·동시성 수치를 완료 기준으로 확정해서는 안 된다.
- **FR-023**: 빌드와 시연 서비스가 자원을 경쟁할 경우 핵심 demo 사용자 경로의 가용성을 우선 보호할 수 있어야 한다.
- **FR-024**: 담당자는 외부 Object Storage의 월간 무료 저장량과 요청량 사용률을 확인할 수 있어야 하며, 어느 한 지표라도 무료 한도의 80%에 도달하면 경고를 받아야 한다.
- **FR-025**: 외부 Object Storage의 월간 무료 저장량 또는 요청량 중 어느 한 지표라도 무료 한도의 90%에 도달하면 신규 업로드를 차단하고 기존 문서 조회는 유지해야 한다.
- **FR-026**: 정적 Web 산출물은 버전별로 구분하고 현재 릴리스와 마지막 정상 릴리스를 식별·전환할 수 있어야 한다.
- **FR-027**: HTML 진입 파일과 내용 기반 식별자가 있는 정적 파일은 변경 특성에 맞는 서로 다른 캐시 정책을 가져야 한다.
- **FR-028**: 정적 콘텐츠 전송 계층은 반복 다운로드가 원본 서버에 주는 부하를 줄여야 하며, 사용할 수 없을 때 원본 제공 경로로 기능을 유지해야 한다.
- **FR-029**: API, 인증 응답, AI Streaming, 서명된 업로드 주소와 게임 연결은 정적 콘텐츠 캐시 대상에서 제외해야 한다.
- **FR-030**: 외부 DNS/CDN·문서 저장소·관측 구성요소의 장애는 정상인 비AI 서비스와 CI/CD를 불필요하게 중단시키거나 전체 환경을 정상으로 오판하게 해서는 안 된다.
- **FR-031**: 환경 구성은 장기적으로 관리형 DNS/CDN·Object Storage·Database·Cache·Container Runtime으로 교체할 수 있도록 공급자별 값과 애플리케이션 계약을 분리해야 한다.
- **FR-032**: 현재 단일 서버 구조와 장기 관리형 확장 구조는 운영 문서와 시연 설명에서 명확히 구분되어야 한다.
- **FR-033**: Redis는 세션·Presence·임시 Lock과 TTL이 있는 RAG 검색 결과·설문 집계처럼 유실을 허용하거나 Source of Truth에서 재생성할 수 있는 데이터만 저장해야 한다. RAG 원본 문서·메타데이터·청크·Vector와 설문·문항·응답을 Redis에만 저장해서는 안 된다.
- **FR-034**: RAG 문서 삭제·비활성화와 설문 응답 추가·수정처럼 원본 데이터가 바뀌면 관련 Redis 캐시를 무효화해야 하며, Redis 장애·재시작 시 영구 데이터 손실 없이 PostgreSQL·R2 원본 조회 또는 캐시 재생성 경로로 복구해야 한다.

### Key Entities

- **Environment**: 파트별 dev 또는 통합 demo 실행 대상. 환경 식별자, 공개 주소, 내부 서비스 집합, 데이터 경계와 현재 릴리스를 가진다.
- **Runtime Service**: 환경에서 실행되는 웹·Backend·AI·게임 구성요소. 소유 파트, 내부 주소, 상태와 릴리스 식별자를 가진다.
- **Public Entry**: 외부 사용자가 환경에 접근하는 승인된 진입점. 도메인, 인증서 상태, 대상 서비스와 캐시 허용 여부를 가진다.
- **Persistent Data Store**: 재배포 후에도 유지되어야 하는 영구 데이터와 Vector 데이터의 저장 경계.
- **Object Storage Contract**: 비공개 AI 원본 문서의 업로드·조회·검증·삭제에 사용하는 공급자 독립 계약.
- **Temporary Object Grant**: 단일 객체와 작업에 한정된 만료 가능한 업로드 또는 다운로드 권한.
- **Static Release**: 함께 제공되는 React·Unity Web 정적 산출물의 버전 묶음과 캐시 정책.
- **Secret Reference**: 실제 값을 포함하지 않고 환경에서 주입할 비밀정보를 가리키는 참조.
- **Backup Set**: 외부 Backup 영역에 보관한 PostgreSQL 백업과 스키마·릴리스 정보, 같은 시점에 주 Object Storage에 남아 있는 원본 문서 참조를 연결한 검증 대상. 원본 문서의 별도 복제본은 포함하지 않는다.
- **Usage Guardrail**: 외부 저장소의 무료 범위와 단일 서버 자원 한도를 넘기 전에 경고·제한하기 위한 운영 기준.
- **Ephemeral Cache Store**: Redis에 저장하는 세션·Presence·임시 Lock·RAG 검색 결과·설문 집계 캐시. 환경·부스·Agent 또는 설문 범위와 만료 기준을 가지며 영구 데이터의 Source of Truth가 아니다.

## Assumptions

- 초기 제공 자원은 주소와 SSH 접근 권한을 가진 단일 EC2이며, 서버 내부에서 Docker·Compose·UFW를 사용할 수 있다.
- AWS Console/API와 IAM 권한은 제공되지 않았으므로 Route53·ALB/NLB·RDS·ElastiCache·ECS·ECR·S3를 초기 필수조건으로 삼지 않는다.
- UFW 변경 권한과 AWS Security Group 변경 권한은 별개이며, 상위 80/443 허용이 없으면 AWS 관리자 협조가 필요하다.
- 단일 EC2에서는 PostgreSQL 인스턴스 하나를 공유하되 Spring의 영구 비즈니스 데이터와 AI의 pgvector 데이터는 별도 데이터베이스와 별도 서비스 계정으로 분리한다. 각 서비스 계정은 상대 데이터베이스에 접근할 수 없어야 한다.
- `infra-001-ci-cd-pipelines`가 빌드·패키징·배포·검증·롤백·Secret Scan·관측 기반을 제공하며, 이 기능은 그 계약을 소비한다.
- dev는 파트별 독립 실행 대상으로 Mock 연동을 허용하고, demo는 `develop` 통합 릴리스의 실사용 기준 환경이다.
- 도메인 구매 전에는 Nginx가 EC2 공인 IP의 HTTP 진입점을 제공한다. 도메인 구매 후에도 dev는 EC2 IP 기반의 제한적 검증 경로를 유지하고, 신규 도메인과 TLS는 최종 demo에 적용한다. HTTPS·소셜 로그인·Secure Cookie와 최종 WSS 검증은 demo 완료 조건으로 다룬다.
- 외부 S3-compatible Object Storage는 EC2의 디스크·네트워크·운영 부하를 줄이는 우선 경로이며 Cloudflare R2를 사용한다. Cloudflare DNS/CDN과 R2는 팀 소유 계정으로 관리하고 과금 책임자를 지정하며, 결제수단 등록과 초과 과금 위험 때문에 애플리케이션 측 무과금 안전 한도를 적용한다.
- 외부 Object Storage를 사용할 수 없을 때는 신규 업로드를 차단하고, 운영자가 단일 서버 내 S3-compatible 대체 저장소의 연결과 쓰기 동작을 검증한 뒤 수동 전환한다. 같은 서버 장애로 데이터가 함께 유실되는 한계는 수용하지 않고 기록한다.
- 추가 서버나 별도 외부 백업 서비스는 도입하지 않는다. PostgreSQL 백업은 기존 R2의 비공개 Backup Bucket에 보관하고, R2 원본 문서는 별도 2차 백업 없이 R2 자체 보존성에 의존하는 한계를 수용한다.
- 최종 demo에는 Cloudflare DNS/CDN을 적용하되, CDN 장애 시에도 원본 서버에서 핵심 정적 콘텐츠를 제공할 수 있어야 한다.
- Unity Dedicated Server의 최종 `wss://` 노출·idle timeout·층별 게임 컨테이너 실측은 `infra-003-unity-server-deploy`가 소유한다. `infra-002`는 공통 도메인·인증서·공개 진입점 계약만 제공한다.
- Backend·FastAPI Endpoint와 payload, 문서 상태, SSE Event 상세 계약은 각각 `docs/08`, `docs/14`, `docs/16`과 spec 007·008이 소유하며 이 기능은 임의로 변경하지 않는다.
- 단일 EC2는 고가용성이나 수평 확장을 제공하지 않으며, 서버 중단 시 내부 서비스 전체가 함께 중단될 수 있다.
