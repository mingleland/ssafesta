## ⛔ 폐기 사유 (2026-08-21, Issue #31)

**1층을 폐기하고 월드를 11층 단일로 확정**했다. 엘리베이터는 없애지 않고 **11층에 붙여 입장 게이트**
(접속 로딩 대기실)로 재활용한다 — 층 이동 수단이 아니다. 따라서 이 spec 의 전제(두 개 층 + 층 간 전환)가
성립하지 않는다.

FR 14개 중 **2개만 살아남아 spec 002(world-session)로 이전**했다. 입장 게이트는 층 이동이 아니라
**월드 접속**의 관심사이고, 남는 FR 2개로 spec 하나를 유지할 값이 없다.

| 이전된 FR | spec 002 에서 | 이유 |
|---|---|---|
| FR-006 (진행 상황 인지) | **FR-013** | 게이트 로딩 진행 표시 |
| FR-011 (전환 실패 시 갇히면 안 된다) | **FR-014** | 게이트는 문이 닫힌 밀폐 공간이라 이 요구가 그대로 성립 |

**폐기된 것**: FR-001·002(두 층·1층 콘텐츠), FR-004·005(층 이동·층수 연출), FR-007·008(다른 층 비표시·동기화 제외),
FR-009(필요한 층만 다운로드), FR-010(층 이동 = 세션 전환), FR-013(층별 정원), FR-014(1차 11층 단일 — 항상 단일이라 무의미).
FR-003(11층 임대 부스)은 spec 004·006 에 이미 있어 중복이었다. FR-012(현재 층 정보 참조)는 **고정값으로 축소** — spec 017 참조.

**파일을 남겨두는 이유**: 폐기 근거와 이전 내역을 추적할 수 있게 한다. 새 작업의 근거로 쓰지 않는다.


## User Scenarios & Testing

### User Story 1 — 엘리베이터로 층을 이동한다 (Priority: P1)

사용자가 엘리베이터에 들어가면 내부 공간으로 화면이 바뀌고, 층수가 올라가는 연출을 거쳐 도착한 층에서 문이 열린다.

**Why this priority**: 층 이동 자체보다 **"진짜 건물에 있다"는 감각**이 목적이다.
단순 순간이동으로도 기능은 되지만, 엘리베이터 연출이 SSAFY 건물이라는 정체성을 만든다.

**Independent Test**: 11층에서 엘리베이터 탑승 → 연출 → 1층 도착 → 1층 부스가 보임 → 다시 11층으로 복귀.

**Acceptance Scenarios**:

1. **Given** 11층에 있는 사용자, **When** 엘리베이터에 들어가면, **Then** 엘리베이터 내부 화면으로 전환된다.
2. **Given** 엘리베이터 안, **When** 목적 층을 선택하면, **Then** 층수가 변하는 연출과 함께 이동이 진행된다.
3. **Given** 이동 완료, **When** 문이 열리면, **Then** 해당 층의 공간에 서 있고 그 층의 다른 사용자들이 보인다.
4. **Given** 이동 중, **When** 로딩이 진행되면, **Then** 사용자는 진행 상황을 알 수 있고 멈춘 것처럼 보이지 않는다.
5. **Given** 이동 중 목적 층 접속에 실패, **When** 일정 시간이 지나면, **Then** 실패가 안내되고 **이전 층으로 복귀하거나 재시도**할 수 있다. *(갇히는 상태가 없어야 한다)*

### User Story 2 — 층마다 다른 공간이 있다 (Priority: P1)

**Acceptance Scenarios**:

1. **Given** 1층, **When** 사용자가 둘러보면, **Then** 축제 관련 부스와 **포토존**이 있다.
2. **Given** 11층, **When** 사용자가 둘러보면, **Then** 기존 임대 부스 구역과 광장이 있다.
3. **Given** 서로 다른 층의 두 사용자, **When** 각자 이동하면, **Then** **서로 보이지 않는다**.

### Edge Cases

- **목적 층 서버가 죽어 있거나 정원이 찬 경우** → 이전 층으로 복귀 가능해야 한다 (FR-011)
- **이전 층에서 나온 뒤 목적 층 접속 전에 연결이 끊긴 경우** → 어느 층으로도 못 가는 상태가 되면 안 된다
- 이동 중 완전히 창을 닫은 경우 → **마지막에 있던 층**에서 시작. 조회 실패 시 **11층** 폴백
- 엘리베이터에 여러 명이 동시에 탄 경우 → **각자 개별 이동**
- 이동 중 다른 사용자에게 내 캐릭터가 어떻게 보이는가 (권장: 사라짐 — 세션에서 빠지므로 자연스럽다)
- 한 층에 인원이 몰리는 경우 → 층별 정원 관리 (FR-013)
- 1층에도 임대 부스를 둘 것인가 → **두지 않는다.** 임대 슬롯 7개는 11층 유지
- 층별 씬을 어떻게 배포하는가 → Addressables 등 분리 로드 수단 필요

## Requirements

### Functional Requirements

- **FR-001**: 월드는 **1층과 11층** 두 구역을 가져야 한다.
- **FR-002**: 1층에는 축제 관련 부스와 포토존이 배치될 수 있어야 한다.
  *2026-08-12 결정: **1차 범위는 "부스가 들어갈 자리"까지의 뼈대만** 만든다. 구체 콘텐츠는 추후 기획한다.*
- **FR-003**: 11층에는 기존 임대 부스 구역이 유지되어야 한다.
- **FR-004**: 사용자는 엘리베이터를 통해 층을 이동할 수 있어야 한다.
- **FR-005**: 이동 시 엘리베이터 내부 연출과 층수 변화가 표시되어야 한다.
- **FR-006**: 이동 중 사용자는 진행 상황을 인지할 수 있어야 한다.
- **FR-007**: **다른 층의 사용자는 서로 보이지 않아야 한다.**
- **FR-008**: 다른 층의 데이터는 동기화 대상이 아니어야 한다 (대역폭·부하 절약).
- **FR-009**: 층별 콘텐츠는 **필요한 층만 내려받아야** 한다 — 접속 시 전 층을 다운로드해서는 안 된다.
- **FR-010**: 층 이동은 **세션 전환**으로 처리하며, 전환 과정은 엘리베이터 연출이 가려야 한다.
- **FR-011**: **전환 실패 시 사용자가 갇혀서는 안 된다** — 실패 사유가 안내되고 이전 층 또는 기본 층으로 복귀할 수 있어야 한다.
- **FR-012**: 사용자의 현재 층 정보는 다른 기능(음성채팅 등)이 참조할 수 있어야 한다.
- **FR-013**: 각 층은 **독립적인 정원**을 가진다 (한 층의 혼잡이 다른 층에 영향을 주지 않는다).
- **FR-014**: **1차 MVP는 11층 단일**이며, 이 spec은 2차에서 활성화된다.

### Key Entities

- **Floor / Zone**: 월드의 한 구역. 식별자, 표시 이름, 씬, 스폰 위치, 정원
- **Elevator**: 층 사이 이동 지점. 위치, 연결된 층 목록
- **Floor Transition**: 한 번의 층 이동. 출발 층, 목적 층, 상태(진행/완료/실패)

## 설계 방침 — 층 = 별도 씬 + 별도 세션 (2026-08-12 리드 확정)

**층마다 씬을 나누고, 각 층은 독립된 월드 세션을 갖는다.** 엘리베이터는 그 전환을 가리는 로딩 연출이다.

```text
11층 씬 / 11층 세션          1층 씬 / 1층 세션
      │                            ▲
      │  엘리베이터 탑승            │  문 열림
      ▼                            │
  [연결 종료] → [1층 씬 로드] → [1층 세션 접속] → [스폰]
        ─────── 엘리베이터 내부 연출이 이 구간을 가린다 ───────
```

**이 방식을 택한 이유 (Unity Web 제약이 결정적)**

| 근거 | 내용 |
|---|---|
| **다운로드 용량** | 단일 씬이면 두 층 에셋이 초기 다운로드에 전부 포함된다. 현재 빌드 86.9MB에 1층을 더하면 웹에서 접속 자체가 부담이 된다. 층별 분리 로드로 **필요한 층만** 받는다 |
| **메모리** | Unity Web은 힙 한도가 있다. 두 층 + 다수 캐릭터를 동시에 올리는 건 위험하다 |
| **서버 부하** | 층마다 세션이 분리되면 인원과 부하가 층 단위로 나뉜다. 한 층에 몰려도 다른 층이 영향받지 않는다 |
| **기존 계약 재사용** | `WorldSessionDto`에 이미 `worldId`/`channelId`가 있다. 층은 이 개념의 확장이며 **새 계약이 필요 없다** |

**대신 감수하는 것 — 반드시 설계에 반영할 것**

층 이동이 **연결을 끊고 다시 붙는 것**이므로, 재접속 실패가 사용자에게 보이는 문제가 된다.
"엘리베이터를 탔는데 아무 층에도 도착하지 못하는" 상태가 절대 없어야 한다 (FR-011).
전환은 **원자적으로** 다루고, 실패하면 이전 층으로 되돌리거나 명확한 오류와 재시도를 제공한다.

> **참고**: 한 세션 안에서 클라이언트마다 다른 씬을 갖는 방식이 불가능하지는 않다(로드 제외 콜백 존재).
> 다만 그 방식으로는 **다운로드 용량도 서버 부하도 줄지 않아** 위 네 근거 중 세 개를 해결하지 못한다.

**다른 파트에 미치는 영향** (spec 002·INFRA에 반영 필요)

- **BE**: world-sessions API가 **목적 층을 입력으로 받아야** 한다. 현재 계약은 층 개념이 없다
- **Infra**: 층 수만큼 게임 서버 인스턴스가 필요하다 (NGO는 프로세스당 세션 1개)
- **FE**: 층 전환 중 로딩·실패 UI가 필요할 수 있다 (Unity 연출과 역할 분담 필요)

## Success Criteria

- **SC-001**: 사용자가 안내 없이 엘리베이터를 찾아 다른 층으로 이동할 수 있다.
- **SC-002**: 층 이동이 **5초 내외**에 끝나며, 연출이 전환 시간을 덮어 멈춘 화면이 보이지 않는다.
- **SC-003**: **층 이동에 실패해 사용자가 어느 층에도 없는 상태가 된 사례가 0건이다.** ← 이 spec의 최우선 성공 기준
- **SC-004**: 다른 층의 사용자가 화면에 보인 사례가 0건이다.
- **SC-005**: 초기 접속 시 **접속하는 층의 콘텐츠만** 내려받는다 (전 층 다운로드 0건).
- **SC-006**: 한 층에 목표 인원이 몰려도 다른 층의 이용에 영향이 없다.
