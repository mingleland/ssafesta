## Summary

**층 = 별도 씬 + 별도 월드 세션.** 엘리베이터는 세션 전환을 가리는 로딩 연출이다.

이 설계에서 Unity의 핵심 작업은 씬 제작이 아니라 **전환을 안전하게 만드는 것**이다.
연결을 끊고 다시 붙는 구조이므로, "엘리베이터를 탔는데 어느 층에도 도착하지 못하는" 상태를
구조적으로 불가능하게 만드는 것이 이 spec의 성패를 가른다.

## 전환 상태 머신 (이 spec의 핵심)

```text
Idle
 ├─ 탑승 → Requesting   목적 층 세션 요청 (아직 현재 층에서 나가지 않는다)
 │           ├─ 실패 → Failed → 이전 층 유지 + 안내
 │           └─ 성공 ↓
 │        Leaving      현재 세션 종료
 │           ↓
 │        Loading      목적 층 씬 로드
 │           ↓
 │        Connecting   새 세션 접속
 │           ├─ 실패 → Recovering → 이전 층 재접속 시도 → 그것도 실패 시 Failed(재시도 UI)
 │           └─ 성공 ↓
 └────────  Arrived    스폰 + 연출 종료
```

**설계 원칙 3가지**

1. **세션을 먼저 확보하고 나서 떠난다.** 목적 층 세션 요청이 실패하면 아직 현재 층에 있으므로
   아무 일도 일어나지 않은 것처럼 되돌릴 수 있다. 이 순서만으로 실패 케이스의 절반이 사라진다.
2. **연출 시간이 전환 시간을 덮도록** 설계한다. 연출이 먼저 끝나면 "멈춘 화면"이 보인다.
   최소 연출 시간을 두고, 전환이 더 걸리면 연출을 연장한다.
3. **어떤 실패에서도 갈 곳이 있다.** 최후 수단은 기본 층(11층) 재접속 또는 명시적 재시도 화면이다.

## 접근 방식

1. **1층은 임시 도형으로 먼저 만든다.** 전환 로직 검증에 실제 에셋이 필요 없다.
   에셋 조달이 늦어도 전환 개발이 막히지 않는다 (Booth Runtime과 같은 전략).
2. **층 정보는 Spring이 소유**한다. "마지막에 있던 층"은 영구 상태이므로 게임 서버가 아니라 프로필에 둔다 (C-04).
3. **음성채팅(017)은 자동으로 해결된다.** 세션이 다르면 음성 방도 다르므로,
   층 격리를 위한 별도 처리가 필요 없다 — 017의 `floorId` 전달도 단순해진다.
4. **1층 부스는 기존 Booth Runtime 그대로**. 층별 분기를 만들면 헌법 4조 위반이다.
