## Clarifications

### Session 2026-08-27

- Q: 현재 프로젝트의 Unity 6000.0.78f1 Dedicated Server를 OCI Ampere A1 ARM64에서 실행할 수 있는가? → A: 불가능하다. 해당 버전의 Linux Server 모듈과 설치 variation은 x86_64 전용이며 ARM64 sysroot는 Embedded Linux 전용이다. OCI는 WebGL 정적 배포까지만 검증하고 Dedicated Server는 x86_64 EC2에서 검증한다.
- Q: OCI 임시 검증을 위해 Unity 엔진을 6000.2+로 올리거나 x86_64 에뮬레이션을 사용할 것인가? → A: 사용하지 않는다. 기준선 동결과 임시 환경의 목적을 지키기 위해 엔진 업그레이드·에뮬레이션을 범위에서 제외한다.

### Session 2026-08-24

- Q: Unity Dedicated Server 한 대의 목표 동시 접속 인원은 몇 명인가? → A: 40명.
- Q: infra-003 명세에도 프로젝트 관례인 담당자 리뷰 섹션을 둘 것인가? → A: Infra 담당 리뷰 3칸을 두고 모두 완료해야 명세를 확정한다.
- Q: 일시적인 네트워크 단절 후 사용자는 어떤 방식으로 월드에 다시 접속해야 하는가? → A: 사용자에게 연결 종료를 안내하고, 사용자가 새 월드 입장 권한으로 직접 재접속한다.
- Q: 한 번 사용된 월드 입장 권한은 새 배포 또는 게임 서버 재시작 뒤에도 재사용을 차단해야 하는가? → A: 새 릴리스 배포, 컨테이너 교체·재시작과 비정상 재기동 뒤에도 원래 만료 시각까지 재사용을 차단한다.
- Q: P0 배포 완료를 위한 사용자 무입력 연결 유지 시험 시간은 얼마인가? → A: 로그인 회원과 게스트 모두 10분 동안 유지한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 브라우저에서 안전하게 월드에 입장한다 (Priority: P0)

방문자는 HTTPS로 제공되는 demo 페이지에서 월드 입장을 요청하고, 서비스가 발급한 월드 접속 정보와 1회용 권한을 사용해 11층 단일 채널에 암호화된 연결로 입장한다. 브라우저에는 내부 게임 서버 주소가 노출되지 않는다.

**Why this priority**: 외부 브라우저가 실제 배포 경로로 월드에 들어갈 수 있어야 시연이 성립하며, 암호화되지 않은 게임 연결은 HTTPS 페이지에서 사용할 수 없다.

**Independent Test**: 외부 네트워크의 브라우저에서 demo에 로그인한 뒤 월드 세션을 발급받아 `world.<domain>:443`으로 입장하고 플레이어가 생성되는지 확인한다. 같은 외부 네트워크에서 내부 게임 포트로 직접 연결할 수 없는지도 함께 확인한다.

**Acceptance Scenarios**:

1. **Given** 배포된 demo와 유효한 월드 입장 권한이 있을 때, **When** 사용자가 월드 입장을 요청하면, **Then** 브라우저는 유효한 인증서가 적용된 암호화 연결로 11층 단일 채널에 입장하고 자신의 플레이어를 확인한다.
2. **Given** 서로 다른 두 브라우저가 유효한 월드 입장 권한을 받았을 때, **When** 두 사용자가 동시에 같은 채널에 입장해 이동하면, **Then** 각 브라우저에서 상대 플레이어의 생성과 이동을 확인한다.
3. **Given** 외부 사용자가 서버의 내부 게임 포트에 직접 접근하려 할 때, **When** 연결을 시도하면, **Then** 연결은 차단되고 공개 진입점만 사용할 수 있다.
4. **Given** 인증서의 호스트 이름이 다르거나 신뢰할 수 없는 경우, **When** 브라우저가 월드에 접속하면, **Then** 인증서 검증을 우회하지 않고 연결이 실패한다.

### User Story 2 - 운영자가 단일 월드 서버를 안전하게 배포한다 (Priority: P0)

운영자는 검증된 Unity 서버 릴리스를 x86_64 단일 EC2의 demo 환경에 11층·단일 채널 서버 하나로 배포하고, 다른 demo 서비스의 실행 상태를 바꾸지 않은 채 기동·접속 가능 여부와 릴리스 식별자를 확인한다.

**Why this priority**: 서버 프로세스가 실행 중이라는 사실만으로는 실제 브라우저 접속 성공을 보장하지 못한다. 배포 산출물, 정적 클라이언트와 실제 외부 접속 결과가 같은 릴리스로 추적되어야 안전하게 시연할 수 있다.

**Independent Test**: 검증된 새 Unity 서버 릴리스를 game 대상에만 배포한 뒤 기동 상태, 내부 수신 상태, 외부 WSS 입장과 릴리스 식별자를 확인하고 다른 demo 서비스의 재시작 횟수가 0인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검증된 Unity 서버 릴리스와 호환되는 Web 클라이언트 릴리스가 있을 때, **When** 운영자가 game 대상 배포를 실행하면, **Then** 11층·단일 채널 서버 하나가 비관리자 권한으로 시작되고 해당 릴리스를 식별할 수 있다.
2. **Given** 새 Unity 서버 배포가 진행될 때, **When** 배포가 완료되면, **Then** Backend·AI·정적 demo 서비스는 재시작되지 않는다.
3. **Given** 새 릴리스가 기동 또는 외부 접속 검증에 실패했을 때, **When** 배포 결과를 판정하면, **Then** 실패 릴리스는 현재 릴리스로 승격되지 않고 마지막 정상 릴리스로 복구할 수 있다.
4. **Given** 서버 프로세스는 실행 중이지만 외부 WebSocket 핸드셰이크가 실패할 때, **When** 배포 검증을 수행하면, **Then** 배포는 정상으로 기록되지 않고 실패 계층을 구분할 수 있는 근거가 남는다.

### User Story 3 - 유효한 사용자만 월드에 입장한다 (Priority: P0)

로그인 사용자와 둘러보기 권한이 있는 게스트는 서비스가 발급한 짧은 수명의 1회용 월드 입장 권한으로 접속한다. 게임 서버는 매 접속마다 Backend 가용성에 의존하지 않고 권한을 검증하며, 변조·만료·재사용된 권한과 클라이언트가 임의로 주장한 신원을 거부한다.

**Why this priority**: 외부에 공개된 게임 진입점이 현재 POC의 비어 있지 않은 문자열 검사만 사용하면 다른 사용자 사칭과 권한 재사용을 막을 수 없다.

**Independent Test**: 정상·만료·변조·재사용된 월드 입장 권한과 서로 다른 사용자 정보를 조합해 접속하고, 정상 권한은 한 번만 승인되며 나머지는 모두 거부되는지 확인한다. 검증 중 Backend 접속을 차단해도 이미 발급된 정상 권한의 최초 입장이 가능한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서명과 만료 시간이 유효하고 아직 사용하지 않은 월드 입장 권한이 있을 때, **When** 사용자가 대상 채널에 최초 접속하면, **Then** 권한에 연결된 검증된 신원으로 입장이 승인된다.
2. **Given** 만료·변조되었거나 대상 채널이 다른 권한이 있을 때, **When** 접속을 시도하면, **Then** 입장이 거부되고 플레이어가 생성되지 않는다.
3. **Given** 한 번 사용된 월드 입장 권한이 있을 때, **When** 동일 권한으로 다시 접속하면, **Then** 재사용이 거부된다.
4. **Given** 유효한 권한이 이미 발급되었고 Backend가 일시적으로 응답하지 않을 때, **When** 사용자가 최초 접속하면, **Then** 게임 서버는 접속마다 Backend에 조회하지 않고 권한을 자체 검증한다.
5. **Given** 사용된 월드 입장 권한의 원래 만료 시각이 지나지 않았을 때, **When** 새 릴리스 배포나 게임 서버 재시작 뒤 동일 권한으로 접속하면, **Then** 재사용이 거부된다.

### User Story 4 - 무입력 연결과 재접속을 검증한다 (Priority: P0)

시연 중 사용자가 잠시 조작하지 않아도 월드 연결이 예기치 않게 끊기지 않는다. 사용자가 연결을 종료하거나 일시적인 네트워크 단절을 겪으면 연결 종료 안내를 받고, 직접 재접속을 선택해 새 월드 입장 권한으로 다시 입장할 수 있으며 이전 플레이어 상태가 남지 않는다.

**Why this priority**: 외부 프록시의 유휴 시간 제한과 게임 전송 계층의 heartbeat가 맞지 않으면 시연 중 정지한 사용자부터 연결이 끊길 수 있다.

**Independent Test**: 로그인 회원과 게스트를 포함한 외부 브라우저 두 개를 같은 채널에 연결한 뒤 사용자 입력 없이 10분 동안 관찰하고, 한 브라우저의 연결을 종료한 다음 새 월드 입장 권한으로 다시 접속해 중복 플레이어 없이 상호 이동을 재개하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 회원 또는 게스트의 두 브라우저가 같은 월드에 정상 접속했을 때, **When** 10분 동안 키보드·마우스 입력 없이 정상 네트워크 상태를 유지하면, **Then** 두 연결 모두 유지되고 상대 플레이어가 임의로 사라지지 않는다.
2. **Given** 접속한 브라우저 하나가 정상적으로 연결을 종료했을 때, **When** 서버가 종료를 처리하면, **Then** 해당 플레이어가 다른 브라우저에서 제거되고 서버의 세션 상태도 정리된다.
3. **Given** 이전 연결이 종료되어 사용자에게 안내가 표시되었을 때, **When** 사용자가 직접 재접속을 선택하고 새 월드 입장 권한을 받으면, **Then** 중복 플레이어 없이 새 세션으로 입장하고 상호 이동을 재개한다.
4. **Given** 외부 경로의 초기 유휴 시간 후보가 적용되어 있을 때, **When** heartbeat와 무입력 연결을 실측하면, **Then** 운영자는 관찰된 연결 동작을 근거로 최종 유휴 시간 값을 확정하고 기록한다.

### User Story 5 - 한 채널의 시연 수용량을 확인한다 (Priority: P1)

운영자는 단일 월드 서버가 목표 동시 접속자 40명을 수용할 수 있는지 같은 외부 접속 계약으로 측정하고, 통과하지 못하면 검증된 안전 수용량을 시연 기준으로 사용한다.

**Why this priority**: P0 시연에는 두 브라우저의 실제 상호작용 검증이 우선이지만, 공개 시연 인원이 늘기 전에 단일 서버의 안전 수용 범위를 수치로 확인해야 한다.

**Independent Test**: 동일 채널에 최대 40개의 유효한 클라이언트를 단계적으로 연결해 10분 동안 유지하면서 입장 성공, 예기치 않은 종료, 서버 재시작과 demo 핵심 경로 상태를 기록한다.

**Acceptance Scenarios**:

1. **Given** 외부 WSS 경로와 유효한 개별 입장 권한이 있을 때, **When** 동시 접속 수를 40명까지 단계적으로 늘리면, **Then** 각 단계의 입장 성공 수, 연결 유지 결과와 서버 자원 사용량이 기록된다.
2. **Given** 40명 목표를 만족하지 못했을 때, **When** 운영자가 시연 허용 인원을 정하면, **Then** 성공이 반복 검증된 최대 인원 이하로 제한하고 40명 수용을 완료로 표시하지 않는다.
3. **Given** 부하 시험 중 게임 서버가 불안정해질 때, **When** demo의 로그인·웹·AI 상태를 확인하면, **Then** 게임 서버 문제와 다른 서비스 상태가 구분되어 기록된다.

### Edge Cases

- Cloudflare DNS는 올바른 원본을 가리키지만 Proxy 또는 WebSocket 전달이 비활성화된 경우
- 원본 서버 인증서가 만료되었거나 `world.<domain>`과 인증서 호스트 이름이 다른 경우
- 외부 TLS는 성공하지만 WebSocket Upgrade 헤더가 내부 게임 서버까지 전달되지 않는 경우
- 내부 게임 포트가 실수로 호스트 또는 상위 네트워크 정책에 공개된 경우
- 월드 세션 응답이 `ws`, 잘못된 호스트·포트 또는 지원하지 않는 경로를 제공하는 경우
- Unity Web 클라이언트와 Dedicated Server가 서로 호환되지 않는 릴리스인 경우
- x86_64 전용 Unity 서버 이미지가 ARM64 호스트에 배포되거나 에뮬레이션으로 실행되는 경우
- 컨테이너는 실행 중이지만 게임 프로세스가 아직 접속을 받을 준비가 되지 않은 경우
- 접속 권한이 Web 클라이언트 로딩 중 만료되거나 동일 권한으로 동시에 접속하는 경우
- 사용된 접속 권한의 만료 전 새 릴리스 배포, 컨테이너 교체·재시작 또는 비정상 재기동이 발생하는 경우
- 클라이언트가 권한에 포함된 신원과 다른 사용자 ID·닉네임·아바타 값을 주장하는 경우
- 무입력 상태에서 heartbeat가 중단되거나 프록시 유휴 시간보다 늦게 전송되는 경우
- 연결이 끊긴 사용자의 플레이어 또는 사용된 권한 기록이 서버에 남는 경우
- 배포·빌드 부하로 게임 서버가 종료되거나 다른 demo 서비스가 재시작되는 경우
- Cloudflare 장애 중 내부 게임 서버는 정상이지만 외부 WSS 진입점을 사용할 수 없는 경우
- 단일 EC2 또는 게임 서버 컨테이너가 중단되어 모든 활성 월드 연결이 함께 끊기는 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 현재 MVP에서 Unity 6000.0.78f1 서버 산출물과 호환되는 x86_64 실행 환경에 11층·단일 채널을 담당하는 Unity Dedicated Server 실행 단위를 하나만 제공해야 한다.
- **FR-002**: 게임 서버 배포는 infra-001이 검증한 불변 릴리스 식별자를 사용하고, 함께 제공되는 Web 클라이언트와 서버 릴리스의 호환 관계를 추적할 수 있어야 한다.
- **FR-003**: 게임 서버는 동결된 로컬 검증 기준선의 WebSocket 전송, 비관리자 실행, 표준 출력 로그와 기존 컨테이너 산출물을 재사용해야 하며 배포를 위해 이를 재설계해서는 안 된다.
- **FR-004**: 외부 브라우저의 게임 연결은 `wss://world.<domain>:443`으로만 제공해야 한다.
- **FR-005**: 외부 게임 연결은 Cloudflare DNS/Proxy를 거치고 Cloudflare와 단일 EC2 Nginx 사이에서도 TLS를 유지하며, Nginx가 원본 TLS를 종료한 뒤 내부 게임 서버로 전달되어야 한다.
- **FR-006**: Cloudflare와 원본 서버 구간은 인증서의 유효기간·신뢰 체인·호스트 이름을 모두 검증해야 하며 인증서 오류를 우회해서는 안 된다.
- **FR-007**: 내부 게임 서버의 평문 WebSocket 포트 7777은 인터넷에 공개되어서는 안 되며 승인된 demo 내부 네트워크의 공개 진입점에서만 접근할 수 있어야 한다.
- **FR-008**: 현재 배포 경로는 ALB·NLB·ACM·ECS를 요구하거나 사용 중인 것으로 간주해서는 안 된다.
- **FR-009**: 공개 진입점은 WebSocket Upgrade와 장시간 양방향 연결을 보존하고, 게임 연결을 정적 콘텐츠 캐시 대상으로 취급해서는 안 된다.
- **FR-010**: 월드 세션 응답은 `scheme`, `host`, `port`와 1회용 접속 권한을 제공해야 하며, 배포 환경에서는 `wss`, `world.<domain>`, `443`을 반환해야 한다.
- **FR-011**: Unity Web 클라이언트는 게임 서버 주소를 빌드 산출물에 고정하지 않고 월드 세션 응답의 구조화된 endpoint를 사용해야 한다.
- **FR-012**: Unity Dedicated Server는 WebSocket 접속 승인 단계에서 월드 입장 권한의 서명, 만료, 대상 월드·채널과 사용자 신원을 자체 검증해야 한다.
- **FR-013**: Unity Dedicated Server는 접속 승인 시마다 Backend에 조회해서는 안 되며 이미 발급된 유효한 권한을 Backend의 일시 장애와 분리해 검증할 수 있어야 한다.
- **FR-014**: 사용된 월드 입장 권한 식별자는 원래 만료 시각까지 다시 사용할 수 없도록 기록해야 하며, 새 릴리스 배포, 컨테이너 교체·재시작 또는 비정상 재기동으로 게임 서버가 바뀌어도 이 차단 기록을 유지해야 한다. 변조·만료·재사용·대상 불일치 권한은 플레이어 생성 전에 거부해야 한다.
- **FR-015**: 게임 서버는 클라이언트가 전송한 사용자 ID·닉네임·아바타 값을 권한의 검증된 신원과 대조하지 않고 신뢰해서는 안 된다.
- **FR-016**: 두 외부 브라우저는 같은 채널에 동시에 입장해 서로의 생성, 이동과 연결 종료를 관찰할 수 있어야 한다.
- **FR-017**: 사용자 입력이 없는 동안에도 heartbeat와 공개 진입점의 유휴 시간 정책이 정상 연결을 불필요하게 종료해서는 안 된다.
- **FR-018**: 공개 진입점의 초기 유휴 시간 후보는 180초로 적용하되, 최종값은 실제 외부 경로의 heartbeat·무입력 연결 실측 후 확정하고 검증 근거에 기록해야 한다.
- **FR-019**: 연결이 종료되면 해당 플레이어와 세션 상태를 정리하고 사용자에게 연결 종료를 안내해야 하며, 사용자가 직접 재접속을 선택하면 새 월드 입장 권한으로 중복 상태 없이 입장할 수 있어야 한다. P0에서는 자동 재접속을 수행하지 않는다.
- **FR-020**: 게임 서버 준비 상태는 프로세스 실행 여부만이 아니라 내부 수신 상태와 실제 외부 WSS 접속을 구분해 판정해야 한다.
- **FR-021**: game 대상 배포는 다른 dev·demo 컴포넌트를 재시작하거나 환경 전체를 중단해서는 안 된다.
- **FR-022**: 새 릴리스의 기동·접속 검증이 실패하면 현재 릴리스로 승격하지 않고 infra-001이 보유한 마지막 정상 릴리스로 복구할 수 있어야 한다.
- **FR-023**: 서버 시작, 접속 승인·거부, 연결 종료와 배포 릴리스 식별에 필요한 운영 로그를 제공하되 접속 권한·Secret·개인정보 원문을 기록해서는 안 된다.
- **FR-024**: 외부 경로 검증은 DNS, 인증서, 공개 진입점, 내부 수신기, 접속 승인 중 어느 계층에서 실패했는지 구분할 수 있는 민감정보 제거 근거를 남겨야 한다.
- **FR-025**: P0 완료 검증은 로그인 회원과 게스트에 대한 외부 브라우저 2개의 동시 접속·상호 이동, 10분 무입력 연결 유지, 연결 종료 정리와 새 권한 재접속을 포함해야 한다.
- **FR-026**: P1 수용량 검증은 단일 채널 40명 목표를 단계적으로 시험하고 성공한 최대 동시 접속자 수, 예기치 않은 종료, 자원 사용량과 다른 demo 서비스 상태를 기록해야 한다.
- **FR-027**: 실측으로 검증되지 않은 동시 접속자 수를 운영 수용량으로 표시해서는 안 되며, 목표에 미달하면 반복 검증된 안전 수용량을 사용해야 한다.

### Key Entities

- **World Server Deployment**: x86_64 단일 EC2에서 실행되는 11층·단일 채널 게임 서버 배포 단위. 환경, 릴리스 식별자, 상태, 내부 수신 주소와 현재·마지막 정상 릴리스 참조를 가진다.
- **World Endpoint**: 클라이언트가 월드 세션 응답으로 받는 구조화된 접속 위치. 암호화 방식, 공개 호스트와 포트로 구성되며 환경별 주소를 클라이언트에 고정하지 않게 한다.
- **World Entry Grant**: 검증된 사용자 또는 게스트가 특정 월드·채널에 한 번 입장할 수 있음을 나타내는 짧은 수명의 서명 권한. 식별자, 대상, 검증된 신원, 만료와 사용 상태를 가진다.
- **World Connection**: 승인된 클라이언트와 채널 사이의 활성 연결. 권한 식별자, 플레이어 식별자, 연결·종료 시각과 종료 사유를 가진다.
- **External Path Evidence**: DNS, 인증서, 공개 진입점, 내부 수신기, 접속 승인, 무입력 유지와 재접속 결과를 릴리스에 연결한 민감정보 제거 검증 기록.
- **Capacity Observation**: 동시 접속자 수 단계별 입장 성공, 유지 시간, 예기치 않은 종료, 자원 사용량과 다른 demo 서비스 상태를 기록한 수용량 측정 결과.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 외부 네트워크에서 수행한 정상 월드 입장 시험의 100%가 유효한 인증서의 암호화 경로로 성공하고 내부 게임 포트 직접 접근 성공 건수는 0건이다.
- **SC-002**: 외부 브라우저 2개가 같은 채널에 동시에 입장한 시험에서 상호 플레이어 생성·이동 확인 성공률은 100%이고 예기치 않은 연결 종료는 0건이다.
- **SC-003**: 만료·변조·재사용·대상 불일치 월드 입장 권한 시험의 100%가 플레이어 생성 전에 거부되고 정상 권한의 최초 사용 승인률은 100%다. 사용된 권한은 새 배포·재시작 뒤에도 원래 만료 시각까지 100% 재사용이 거부된다.
- **SC-004**: 로그인 회원과 게스트를 포함한 외부 브라우저 2개의 10분 무입력 시험에서 연결 유지율은 100%이며 임의 플레이어 제거는 0건이다.
- **SC-005**: 연결 종료 후 새 권한으로 수행한 재접속 시험의 100%에서 30초 이내 월드 입장이 완료되고 중복 플레이어는 0건이다.
- **SC-006**: game 대상 배포 시험의 100%에서 비대상 dev·demo 서비스의 재시작 횟수는 0이고 실패 릴리스의 현재 승격 건수는 0건이다.
- **SC-007**: 완료된 배포 검증의 100%에서 릴리스 식별자, 외부 WSS, 두 브라우저 상호작용, 무입력 유지, 종료 정리와 재접속 결과를 한 검증 기록에서 추적할 수 있다.
- **SC-008**: 저장소·배포 설정·서버 로그·검증 근거에서 접속 권한, Secret과 인증서 개인 키 원문 검출 건수는 0건이다.
- **SC-009**: P1 부하 시험은 1명부터 40명까지 단계별 결과를 100% 기록하며, 운영 문서에 표시한 안전 수용량은 반복 시험에서 성공한 최대 인원을 초과하지 않는다.

## Assumptions

- `v0.0.1-poc` 기준선에서 WebSocket 기반 Unity 멀티플레이, Linux Dedicated Server 컨테이너와 로컬 브라우저 다중 접속은 이미 검증되었다. 이 기능은 해당 코드를 재구현하지 않고 외부 배포에 필요한 최소 변경과 검증만 수행한다.
- `infra-001-ci-cd-pipelines`가 Unity 빌드, 불변 이미지 식별자, 릴리스 매니페스트, 현재·마지막 정상 릴리스와 복구 절차를 제공한다.
- `infra-002-environments`가 단일 EC2의 demo 환경, Cloudflare DNS/Proxy, Nginx 공개 진입점, TLS·네트워크·자원 격리의 공통 경계를 제공한다. 이 기능은 게임 경로의 최종 연결과 실측 결과를 소유한다.
- 현재 프로젝트의 Unity 6000.0.78f1 Linux Dedicated Server 산출물은 x86_64 전용이다. OCI Ampere A1 ARM64는 WebGL 정적 배포 검증에만 사용하며 게임 서버 실행·WSS·브라우저 간 동기화 완료 근거로 사용하지 않는다.
- 초기 MVP의 월드는 11층·단일 채널 `11F-01`이며 Unity Dedicated Server 실행 단위는 하나다.
- 실제 루트 도메인, EC2 사양과 80/443 상위 네트워크 권한은 infra-002의 C-01/C-02 입력이 배포 전 제공된다.
- 현재 공개 진입점은 Nginx이며 Caddy 전환은 이 명세의 결정 사항이 아니다.
- 단일 EC2에는 무중단 고가용성이 없다. 게임 서버 교체·장애 중 활성 사용자는 연결이 끊길 수 있으며 새 릴리스 또는 마지막 정상 릴리스가 준비된 뒤 새 권한으로 수동 재접속한다.
- 월드 입장 권한 발급과 수명 정책은 `001-auth-user` 및 `002-world-session`이 소유하고, 이 기능은 실제 외부 게임 서버에서 해당 계약을 검증한다.
- P0에서는 자동 재접속을 제공하지 않는다. 연결 종료 안내를 받은 사용자가 직접 재접속을 선택하고 새 월드 입장 권한을 받는 흐름만 검증한다.
- 서버 한 대의 목표 동시 접속 인원과 실행 상한은 40명이다. P0의 실제 사용자 경로는 브라우저 2개로 판정하고, 40명 수용 가능 여부는 P1 부하 시험으로 검증한다.
