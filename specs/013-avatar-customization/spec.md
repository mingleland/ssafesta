## User Scenarios & Testing

### User Story 1 — 캐릭터를 만들고 월드에 들어간다 (Priority: P0)

사용자가 월드 입장 전 캐릭터 생성 화면에서 외형을 고르고, 확정하면 그 모습으로 월드에 들어간다.

**Why this priority**: 팀이 필수로 지정. 메타버스에서 "나"의 정체성이며 접속 유지 동기의 핵심.

**Independent Test**: 캐릭터 생성 화면 → 파츠 선택 → 확인 → 월드 입장 → 선택한 외형으로 보임.

**Acceptance Scenarios**:

1. **Given** 캐릭터 생성 화면, **When** 카테고리를 고르면, **Then** 선택 가능한 항목들이 썸네일로 보인다.
2. **Given** 항목을 선택하면, **When** 클릭 즉시, **Then** **미리보기 캐릭터가 바로 바뀐다**.
3. **Given** 미리보기 화면, **When** 드래그·휠을 쓰면, **Then** 캐릭터가 회전·확대된다.
4. **Given** 외형을 고른 뒤, **When** 확인을 누르면, **Then** 외형이 저장되고 월드로 입장한다.
5. **Given** 월드에 입장하면, **When** 자신을 보면, **Then** 고른 외형이 적용되어 있다.
6. **Given** 초기화·랜덤 버튼, **When** 누르면, **Then** 기본값 복원 / 무작위 조합이 적용된다.

### User Story 2 — 남들에게도 그 모습으로 보인다 (Priority: P0)

**Independent Test**: 브라우저 2개가 서로 다른 외형으로 접속 → 각자 화면에서 상대의 실제 외형이 보임.

**Acceptance Scenarios**:

1. **Given** 서로 다른 외형의 두 사용자, **When** 같은 월드에 있으면, **Then** 각자 상대의 실제 외형이 보인다.
2. **Given** 외형을 변경하면, **When** 변경 즉시, **Then** 다른 사용자 화면에 반영된다.
3. **Given** 외형 데이터, **When** 네트워크를 관찰하면, **Then** **메시·텍스처가 아니라 ID만** 오간다.
4. **Given** 이동 중인 캐릭터, **When** 네트워크를 관찰하면, **Then** 외형 데이터가 **이동 주기와 함께 반복 전송되지 않는다**.

### User Story 3 — 다음에 들어와도 그 모습이다 (Priority: P0)

**Acceptance Scenarios**:

1. **Given** 외형을 저장한 사용자, **When** 나갔다 다시 들어오면, **Then** 마지막 외형이 복원된다.
2. **Given** 저장이 실패한 경우, **When** 계속 플레이하면, **Then** 이번 세션의 외형은 유지되고 월드 이용이 중단되지 않는다.
3. **Given** 알 수 없는 항목 ID가 저장돼 있는 경우, **When** 접속하면, **Then** 기본값으로 대체되고 오류로 중단되지 않는다.
4. **Given** 게스트 사용자, **When** 종료하면, **Then** 외형이 영속 저장되지 않는다 (헌법 12조).

### Edge Cases

- **선택 조합이 서로 충돌하는 경우** — 특정 모자가 특정 헤어와만 맞물리는 등. 조합 규칙이 필요할 수 있다
- 옷을 입었을 때 **신체가 옷 밖으로 튀어나오는 문제** (클리핑)
- 항목이 카탈로그에서 제거되었는데 사용자가 그 ID를 갖고 있는 경우
- 다른 사용자가 조작된 ID를 보내는 경우 → 서버 검증
- 목표 인원이 서로 다른 외형으로 동시 접속했을 때의 렌더링·용량 부담
- 색상 변경이 다른 플레이어에게까지 적용되는 버그 (공유 머티리얼 수정)

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 카테고리별로 외형 항목을 선택할 수 있어야 한다. *(실제 카테고리는 에셋 조사 결과로 확정)*
- **FR-002**: 사용자는 색상을 선택할 수 있어야 한다.
- **FR-003**: 선택은 **미리보기에 즉시 반영**되어야 한다.
- **FR-004**: 외형 변경은 **같은 월드의 모든 사용자에게 즉시** 반영되어야 한다.
- **FR-005**: 외형은 **ID 집합으로 표현**되며, 네트워크에는 **작은 고정 크기 데이터만** 전송되어야 한다. 메시·텍스처·머티리얼을 전송해서는 안 된다 (헌법 5조).
- **FR-006**: 외형 데이터는 **Spawn 시점과 변경 시점에만** 전송되어야 한다 — 이동 동기화 주기와 분리한다.
- **FR-007**: 외형 3D 표현은 각 클라이언트가 로컬 생성하며 **네트워크 오브젝트가 아니어야** 한다.
- **FR-008**: 아바타는 **Spawn·변경 시점에만 조립**되어야 한다. 매 프레임 재생성해서는 안 된다.
- **FR-009**: 캐릭터당 `NetworkObject`는 **하나**여야 한다. 파츠마다 붙이지 않는다.
- **FR-010**: 알 수 없는 항목 ID는 기본값으로 폴백해야 한다 (구버전 클라이언트 호환).
- **FR-011**: 서버는 전달받은 ID가 **카탈로그 범위 내인지 검증**해야 한다 (헌법 16조).
- **FR-012**: 요청이 거부되면 **사유가 사용자에게 표시**되어야 한다. 조용히 기본값으로 대체해서는 안 된다.
- **FR-013**: 시스템은 사용자의 외형을 **영구 저장**하고 재접속 시 복원해야 한다.
- **FR-014**: 저장 실패가 월드 이용을 중단시켜서는 안 된다.
- **FR-015**: **게스트의 외형은 영속 저장하지 않는다** (헌법 12조). 기본 프리셋을 제공한다.
- **FR-016**: 캐릭터 생성 화면은 **월드 접속 이전 단계**에 위치해야 한다.
- **FR-017**: 색상 변경이 **다른 플레이어의 외형에 영향을 주어서는 안 된다** (공유 머티리얼 직접 수정 금지).
- **FR-018**: 옷 착용 시 **가려지는 신체 부위가 노출되지 않아야** 한다 (클리핑 처리).
- **FR-019**: 새 항목 추가에 **코드 수정이 필요해서는 안 된다** — 에셋 등록만으로 선택지에 나타나야 한다.
- **FR-020**: 정식 커스터마이징 창은 최종적으로 **웹 레이어**로 이관 가능해야 한다 (헌법 25조). Unity 화면은 그때까지의 구현이자 개발용이다.
- **FR-021**: 이동 애니메이션(Idle/Walk/Run)이 조립된 캐릭터에서 정상 재생되어야 한다.

### Key Entities

- **Avatar Config**: 한 사용자의 외형. 성별 + 카테고리별 항목 ID + 색상 ID
- **Avatar Item Definition**: 선택 가능한 항목 하나. 안정적 itemId, 표시명, 카테고리, 성별, 시각 자산 참조, 썸네일, 선택 가능 색상, 가려질 신체 부위, 기본값 여부
- **Avatar Catalog**: 항목 정의의 모음. 항목 추가의 유일한 등록 지점
- **Avatar Preset**: 기본 외형 (게스트·초기값용)

## 계약 — 외형 데이터 (3파트 공통)

**표현 원칙**: 외형은 **ID 집합**이다. 실제 3D 데이터는 각 클라이언트가 로컬에 갖고 있고 네트워크로 오가지 않는다.

| 용도 | 형식 | 이유 |
|---|---|---|
| **네트워크 전송** | 고정 크기 구조체 (`INetworkSerializable`) | 수십 바이트. 이동 대역폭을 잠식하지 않는다 |
| **영구 저장 / API** | 짧은 직렬화 문자열 | 스키마 변경 없이 항목이 늘어날 수 있게 |

**itemId 규칙**: 배열 인덱스를 그대로 쓰지 않는다. 항목을 추가·삭제해도 **기존 사용자의 외형이 바뀌지 않아야** 한다.
한 번 부여한 itemId는 재사용·재배치하지 않는다.

**BE에 필요한 것**: 사용자 외형 저장 필드. 항목이 늘어나도 스키마를 바꾸지 않도록 **`TEXT`(또는 넉넉한 가변 문자열)** 로 만든다.
*(구 계약서의 "avatarCode 29~32자"는 무효다.)*

**저장 형식**: `카테고리:itemId` 쌍의 짧은 직렬화. 미지의 값은 무시하고 기본값 폴백.
정확한 구분자는 카테고리 확정(tasks Phase 1) 시 결정한다.

## Success Criteria

- **SC-001**: A가 외형을 바꾸면 B 화면에 1초 이내 반영된다.
- **SC-002**: 재접속 후 외형 복원율이 100%다.
- **SC-003**: 저장 서버가 정지해도 월드 이용과 외형 변경(세션 한정)이 계속된다.
- **SC-004**: 사용자가 안내 없이 캐릭터를 만들어 월드까지 입장할 수 있다.
- **SC-005**: 외형 변경 요청이 무반응으로 끝나는 사례가 0건이다.
- **SC-006**: 외형 동기화가 이동 동기화 성능을 저하시키지 않는다.
- **SC-007**: **Web 빌드 용량이 현재(약 87MB)를 넘지 않는다.** 초과 시 텍스처 해상도 → 항목 수 순으로 줄인다.
- **SC-008**: 새 항목 하나를 추가하는 데 코드 수정이 0줄이다.

### ✅ 리드 확정 (2026-08-12)

| # | 확정값 |
|---|---|
| C-01 카테고리·항목 수 | **에셋 실조사 산출물로 확정** (tasks T001~T005). 조사 전에는 코드에 개수를 넣지 않는다 |
| C-02 조합 규칙 | **필요함 — 확인됨.** 모자가 헤어스타일별 변형으로 존재하므로 Catalog에 **조합 정보를 포함**한다. 모자 단독 ID로 표현하지 않는다 |
| C-03 용량 목표 | **현재 Web 빌드(약 87MB)를 넘지 않는다.** 구 에셋 제거분(약 22MB)을 감안해 신규 아바타 예산을 잡고, 초과하면 텍스처 해상도 → 항목 수 순으로 줄인다 |
| C-04 저장 문자열 형식 | **`카테고리:itemId` 쌍의 짧은 직렬화.** 미지의 카테고리·항목은 무시하고 기본값 폴백 (forward compatible). 정확한 구분자는 C-01 확정 후 |
| C-05 썸네일 | **에디터 스크립트로 항목별 캡처 자동화.** 수작업으로 만들지 않는다 |
| C-06 구매·보유 개념 | **MVP는 전체 개방.** 상점·소유권은 spec 012(P1) |
| C-07 React 이관 방식 | **기존 `AvatarBridge` 경계 유지. 인코딩 생성은 Unity가 소유**하고 React는 의미 단위(카테고리·항목)로 조작한다 |
| C-08 게스트 커스터마이징 | **편집은 허용, 영속 저장만 하지 않는다** (헌법 12조) |
