# Phase 0 Research: 캐릭터 커스터마이징

**Spec**: `013-avatar-customization` | **Date**: 2026-08-12

이 문서는 plan의 Technical Context에서 미확정이던 항목을 해소한다.
**실측이 필요한 두 항목(R-01 카테고리, R-02 용량)은 구현 착수 전 반드시 채워야 한다.**

---

## R-01. 실제 카테고리와 항목 수 — ⏳ 조사 산출물

**Decision**: 벤더 에셋 실조사 결과로 확정한다. **개수를 추측해 코드에 넣지 않는다.**

**Rationale**: 과거 외부 SDK 판정에서 "문서·실물 확인 없이 단정"이 두 번 사고를 냈다 (T-20 판정 정정).
카테고리 수는 `AvatarConfig` 필드 구성과 네트워크 struct 크기를 직접 결정하므로, 틀리면 계약을 다시 만든다.

**확인된 구조 (사전 조사)**:

| 항목 | 내용 |
|---|---|
| 성별 구분 | 남/녀 전신 프리팹 각각 존재 (`*_FullBody`, `*_FullBody AllEquipments`) |
| 파츠 프리팹 | 헤어 / 액세서리(안경·모자) 폴더 분리 |
| 메시 | 파츠별 개별 FBX |
| 리그 | **Humanoid** — 벤더 아이템 정의가 `HumanBodyBones`로 부착 대상을 지정 |
| 벤더 아이템 정의 | ScriptableObject. `bodyParts[]`(숨길 신체 부위) + `meshes[]`(SkinnedMesh) + `objects[]`(프리팹+본) |
| 신체 부위 태그 | Torso(Hips/Spine01~03/Shoulders/Head) / Arms(Upper/Lower/Hand) / Legs(Upper/Knees/Lower/Feet) |
| 데모 | 커스터마이징 씬 + UI 스크립트 + 회전/줌 유틸 + 에셋 로딩 인터페이스 |

**Alternatives considered**: 인터넷 정보나 스토어 페이지의 "헤어 17종" 같은 수치 인용 → **기각**.
버전에 따라 다르고, 실제 import된 것과 어긋나면 런타임에 null 참조가 난다.

**Open**: 카테고리별 실제 항목 수 (tasks T001~T005에서 확정)

## R-02. Web 빌드 용량 예산 — ⏳ 실측 산출물

**Decision**: **현재 Web 빌드(약 87MB)를 넘지 않는다.** 초과 시 ① 텍스처 해상도 ② 항목 수 순으로 줄인다.

**Rationale**: 이 프로젝트의 지배적 제약은 다운로드 용량이다 (spec 018에서 층 구조 설계를 바꾼 것과 같은 이유).
신규 에셋 소스는 약 141MB이며 그중 텍스처가 약 80MB로 압도적이다. 구 아바타 에셋(약 22MB)을 제거하면
그만큼 여유가 생기므로 **구 에셋 제거를 선행 조건이 아니라 예산 확보 수단**으로 계산에 넣는다.

**측정 방법**: 캐릭터 1종만 포함한 최소 구성으로 Web 빌드 1회 → 산출물 크기 확인 →
항목당 증가분을 추정해 카테고리·항목 수를 역산.

**Alternatives considered**:
- "일단 다 넣고 나중에 최적화" → **기각**. 용량이 초과되면 카테고리 설계 자체가 바뀌므로 되돌리는 비용이 크다
- 항목을 런타임 다운로드(Addressables 원격) → 지금은 과설계. 018에서 층 분리 로드를 도입할 때 함께 검토

**Open**: 실측치 (tasks T006~T009)

## R-03. 파츠 조합 규칙 — ✅ 해소

**Decision**: **조합 규칙이 필요하다.** Catalog에 조합 정보를 포함한다.

**Rationale**: 모자 프리팹이 **헤어스타일별 변형**으로 존재한다 (같은 모자의 짧은머리용/긴머리용/묶은머리용 등).
따라서 "모자 itemId" 하나로는 렌더링할 프리팹을 결정할 수 없고, **모자 × 헤어 조합**이 필요하다.

**설계**: `AvatarItemDefinition`에 조합 조건을 두고, Assembler가 (모자 ID, 헤어 ID) 쌍으로 실제 프리팹을 해석한다.
사용자에게는 여전히 "모자 하나"로 보인다 — 변형 선택은 시스템이 한다.

**Alternatives considered**:
- 모자 변형을 각각 독립 항목으로 노출 → **기각**. 같은 모자가 UI에 5번 나오고, 헤어를 바꾸면 모자가 어긋난다
- 헤어를 모자에 포함 → **기각**. 헤어 단독 선택이 불가능해진다

## R-04. 클리핑(옷 밖으로 몸이 나옴) 처리 — ✅ 해소

**Decision**: **벤더의 신체 부위 태그 시스템을 그대로 활용한다.** 아이템 정의의 "숨길 신체 부위" 목록을 읽어 해당 렌더러를 끈다.

**Rationale**: 벤더 아이템 정의 SO에 이미 `bodyParts[]` 필드가 있고, 신체 부위 enum이 Torso/Arms/Legs 세분화까지 되어 있다.
우리가 `hiddenBodyParts`를 새로 설계할 필요가 없다.

**Alternatives considered**: 셰이더 기반 클리핑 마스크 → **기각**. WebGL 셰이더 변형이 늘고 머티리얼 수가 증가한다

---

## R-05. 색상 변경 방식 — ✅ 해소

**Decision**: **공유 머티리얼을 직접 수정하지 않는다.** `MaterialPropertyBlock` 또는 벤더 권장 방식을 사용하고,
플레이어당 머티리얼 인스턴스가 무한정 늘지 않도록 관리한다.

**Rationale**: 공유 머티리얼을 수정하면 **모든 플레이어의 색이 함께 바뀐다** — 30~40명 월드에서 즉시 드러나는 버그다.
반대로 플레이어마다 머티리얼을 복제하면 WebGL에서 드로우콜과 메모리가 급증한다.

**Alternatives considered**: 색상별 머티리얼 에셋 사전 생성 → 조합 수만큼 에셋이 늘어 용량 예산(R-02)을 잠식

## R-06. Animator 연결 — ✅ 해소

**Decision**: 조립 직후 Animator의 **Controller와 Avatar(휴머노이드 정의)가 채워졌는지 확인**하고,
비어 있으면 명시적으로 채운다. 채우지 못하면 **조용히 넘어가지 않고 원인을 로그로 남긴다**.

**Rationale**: T-27에서 정확히 이 문제로 캐릭터가 T포즈로 굳었다.
벤더가 Animator를 붙여주더라도 **Controller까지 채워준다는 보장이 없다**.
애니메이션 클립의 Rig가 Humanoid여야 리타게팅된다는 점도 함께 확인한다.

**Alternatives considered**: 실패 시 기본 포즈로 폴백 → **기각**. T-24의 교훈대로 조용한 폴백은 무반응 버그가 된다

---

## R-07. 네트워크 표현 — ✅ 해소

**Decision**: `INetworkSerializable`을 구현하는 **고정 크기 struct**. 카테고리별 항목 ID + 색상 ID + 성별.
전송은 **Spawn 시점과 변경 시점에만**.

**Rationale**: 구 방식은 파츠 이름 문자열이라 실측 600자를 넘었고, 길이 초과 시 조용히 잘려 무반응이 됐다 (T-24).
ID 집합이면 수십 바이트로 끝나고 **길이 초과라는 실패 모드 자체가 사라진다**.

**Alternatives considered**:
- JSON 문자열 동기화 → **기각**. 파싱 비용 + 크기 + 이동 대역폭 잠식
- 매 프레임 전송 → **기각**. 외형은 거의 변하지 않는 상태다

---

## R-08. 저장 경로 — ✅ 해소

**Decision**: `IAvatarProfileStore` 인터페이스 + `LocalAvatarProfileStore`(PlayerPrefs)로 1차 동작.
Spring API는 **계약만 제안**하고 호출하지 않는다 (`contracts/avatar-profile-api.md`).

**Rationale**: Backend 아바타 API가 아직 없다. 존재하지 않는 엔드포인트를 가정해 호출하면
BE 구현 시점에 URL·형식이 어긋나고, 그때까지 실패 로그만 쌓인다.
기존 `IUserApiClient`에 아바타 저장 경로가 이미 있으므로 **중복 시스템을 만들기 전에 그것부터 조사**한다.

**Alternatives considered**: 가짜 URL로 미리 배선 → **기각** (작업지시서 §9 금지 사항)
