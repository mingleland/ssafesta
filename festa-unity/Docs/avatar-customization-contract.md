## 1. 개요

캐릭터 외형은 **Rukha93 모듈 파츠 조립 방식**이다. 머리·헤어·모자·안경·상의·하의·한벌옷·신발과
피부·헤어·홍채·눈썹·입술·상의·하의·흰자위·동공 색상을 런타임에 조립한다. 입술색은 원본 얼굴 명암을 보존하도록 피부색과 혼합한 색조로 적용한다. Sidekick 패키지는 신규 생성 경로에서 사용하지 않는다.

피부색 한 슬롯은 얼굴과 목·몸통·팔·손·다리·발의 모든 노출 신체 메시가 함께 사용한다. 얼굴과 신체 피부 셰이더는 동일한 기본 조명 계산을 사용해 목 경계에서 색이 갈라지지 않아야 한다.

기본 Body의 속옷은 Body RGB 마스크의 녹색 채널로 피부와 분리하고 검정색으로 고정한다. 속옷 색은 `AvatarConfig`나 네트워크 외형 문자열에 포함하지 않으며 피부색을 바꿔도 함께 변하지 않는다.

상의·하의·한벌옷·신발·모자·안경은 각각 RGB 마스크 A/B/C 세 영역을 가진다. UI에는 A/B/C나 어두운색·밝은색 같은 내부 개념을 표시하지 않고, 현재 아이템에 맞는 구체적인 부위마다 한 행과 한 색상 컨트롤만 제공한다. 예를 들어 서스펜더 반바지는 `상의 원단/반바지 원단/멜빵·단추`, 사각 안경은 `안경테/브리지·다리`로 표시한다. 선택한 한 색은 해당 영역의 내부 두 슬롯에 동일하게 기록한다. 각 `AvatarItemDefinition`은 전·후면 렌더 변화량으로 검증한 `garmentColorAreaMask`를 가지며, 가장 잘 보이는 영역 대비 변화가 5% 미만인 영역은 그 아이템의 UI에서 표시하지 않는다. 따라서 같은 카테고리라도 아이템에 따라 색상 행이 1~3개로 달라진다. 안경 렌즈는 프레임과 분리된 투명 머티리얼을 유지하며 두 번째 부위 색을 사용한다.

런타임 캐릭터 로비 UI는 좌·우 패널에 같은 상단 패딩과 `제목 → 큰 탭 → 섹션 제목 → 2열 아이템 목록 → 하단 색상 영역` 수직 기준선을 사용한다. 탭 아이콘은 설명과 분리해 크게 표시하고, 색상 영역은 필요한 높이만 패널 하단에 고정해 아이템 목록의 탐색 범위를 우선 확보한다. 카드·버튼·색상 행·팝업은 따뜻한 중성 계열의 둥근 표면과 동일한 선택 강조색을 사용한다. 얼굴·의상·모자·안경 썸네일은 같은 회색 배경을 사용하고 어두운 헤어만 더 밝은 대비 배경을 사용한다. 왼쪽 의상 카테고리 아이콘은 원본의 어두운 카드·금색 장식을 제거한 투명 누끼를 사용하고, 오른쪽 탭과 비슷한 카드 간격 및 프레임 안쪽 여백을 둔다. 색상 행의 왼쪽 표시는 흰 테두리가 포함된 장식 이미지가 아니라 단색 마커이며, 오른쪽 색상칩은 동일 크기의 둥근 정사각형이다. 색상 팝업에는 실제 부위명과 색상환·밝기·현재 색상·HEX·취소·완료만 표시하고 전체 화면 스크림 없이 팝업 Rect에서만 미리보기 입력을 차단하며, 제목 영역을 드래그해 위치를 옮길 수 있다. 개발용 외형 정보 버튼이나 동작 없는 설정 버튼은 노출하지 않는다.

커스터마이징 최초 진입은 고정 기본값 대신 자연스러운 추천 무작위 외형을 생성하되 상의·하의 조합으로 시작해 기본 의상 탭을 `상의`로 유지한다. 현재 로컬 플레이어나 사용자 프로필에 유효한 `fa` 모듈형 외형이 있으면 추천 무작위보다 저장 외형을 우선 복원한다. 무작위 생성은 자연스러운 얼굴 팔레트와 조화된 의상 색 테마를 공유하고 모자·안경을 동시에 선택하지 않는다.

```
[커스터마이징 창]  →  avatarCode 문자열  →  ┬→ Unity 월드: 즉시 동기화 (전원에게 보임)
                                          └→ Spring: 프로필에 영구 저장
```

**핵심**: 외형 전체가 짧은 문자열 하나(`avatarCode`)로 표현된다.
파트별로 이 문자열만 주고받으면 되고, 3D 데이터는 오가지 않는다.

## 2. avatarCode 포맷 (3파트 공통 계약)

의상 A1/A2·B1/B2·C1/C2는 네트워크 하위 호환을 위해 유지하는 내부 슬롯이다. UI에서 부위 색 하나를 바꾸면 대응하는 두 슬롯에 같은 RGB를 기록한다. Unity는 원본 머티리얼의 `_MaskRemap`·`_Mask_Factor`와 A → B → C 순차 영역 선택을 유지하며, 겹치는 마스크 픽셀을 색 평균으로 처리하지 않는다.

```
fa|g=1|i=<8개 파츠 ID>|p=<9개 팔레트 ID>|q=<9개 정밀 RGB 값>|w=<36개 의상·모자·안경 RGB 값>
```

| 규칙 | 내용 |
|---|---|
| 최대 길이 | **3800자** — Unity `FixedString4096Bytes` 안전 범위 |
| 구분자 | `\|` (파이프), 세그먼트는 `키=값` |
| 알 수 없는 세그먼트 | **무시한다** — 구버전 클라이언트가 깨지지 않음 (forward compatible) |
| 빈 값/오류 | Catalog 기본 외형으로 폴백 |
| 정밀 색상 | `q=`에 피부·헤어·홍채·눈썹·입술·상의·하의·흰자위·동공 순서로 각 슬롯을 `RRGGBB`로 기록하며 미지정은 `-` |
| 파츠 영역 색상 | `w=`에 상의·하의·한벌옷·신발·모자·안경 순서로 각 파츠의 A1·A2·B1·B2·C1·C2를 기록한다. 현재 UI는 각 부위의 슬롯 쌍에 같은 RGB를 기록한다. 총 36개 `RRGGBB`이며 미지정은 `-`. 기존 24개·30개 입력도 읽어 하위 호환한다. |
| 구버전 7·8색 입력 | 기존 7개 또는 8개 `p`/`q` 값도 허용하며 누락된 흰자위는 흰색, 동공은 짙은 기본색으로 복원 |

과거 `sk_01` 프리셋과 `rt` Sidekick 코드는 읽기 호환만 유지한다. 신규 생성과 저장은 `fa`만 사용하며,
파츠·아이템 목록의 Source of Truth는 Unity `AvatarConfig`와 `AvatarItemDefinition`이다.

## 3. Backend(Spring)에 요청하는 것

### 3-1. User 테이블

`avatar_code VARCHAR(3800)` 이상 또는 `TEXT` 컬럼. 신규 사용자는 `NULL`을 허용하고 Unity의 추천 무작위 최초 외형을 저장한다. (doc 09 User 엔티티에 반영 필요)

### 3-2. API 2개

> **계약 권위는 `specs/013-avatar-customization/contracts/avatar-profile-api.md` 다.**
> 이 문서가 `PATCH` + 필드 `avatarCode` 로 적고 있었으나 spec 계약서와 `docs/sdd/parts/BE.md` 는 둘 다
> **`PUT`** 이다. spec 을 기준으로 맞췄다 (2026-08-21, Issue #24). 필드명은 이후 #24 에서
> **`avatarCode` 로 확정**됐다(BE 통보) — DB `avatar_code`·JPA `avatarCode`·Unity `AvatarCode` 세 층이
> 이미 같은 이름이라 와이어만 `avatar` 로 다르게 둘 이유가 없다는 근거다. spec 계약서 3곳은 BE 가 고친다.
>
> **길이** — spec 은 컬럼을 `TEXT`(넉넉한 가변 문자열)로 규정하고 `VARCHAR(32)` 를 명시적으로 금지한다.
> `BE.md` 는 검증 상한을 500자로 적고 있는데 **현재 `fa` 형식에는 충분하다** — `Encode()` 의 `fa` 분기를
> 재현해 재 보면 기본값 138자, 색 전부 지정 + tint 406자, item ID 4자리여도 414자다. 필드 수가
> 고정(`g` 1 + `i` 8 + `p` 9 + `q` 9 + `w` 36)이라 길이가 거의 변하지 않는다.
> 단 **여유는 86자(17%)뿐**이라 의상 색 슬롯(`w`, 현재 36개)이 12개만 늘어도 500을 넘는다.
> `AvatarAppearance.MaxEncodedLength = 3800` 은 `fa` 가 아니라 **구 `rt` 모드**(Sidekick 파츠 이름
> ~25자 × 16종) 때문에 잡은 값이고, `rt` 는 읽기 호환만 유지한다.

**조회** — 전용 엔드포인트가 기본. 기존 내 정보 조회(`GET /users/me`)에 `avatar` 필드를 포함시키는 형태도 허용된다.
```http
GET /api/v1/users/me/avatar
→ 200 { "avatarCode": "fa|g=1|i=...|p=...|q=...|w=..." }
```

**저장**
```http
PUT /api/v1/users/me/avatar
Content-Type: application/json
{ "avatarCode": "fa|g=1|i=...|p=...|q=...|w=..." }

→ 200 { "avatarCode": "fa|g=1|i=...|p=...|q=...|w=..." }
→ 400 잘못된 형식 (길이 초과, 허용되지 않은 포맷)
→ 401 미인증
```

검증 권장 사항:
- 길이 상한과 허용 문자셋만 검증한다. **문자열 내용을 파싱하지 않는다** — 항목 해석은 클라이언트 책임이다 (spec 계약서 규정). 첫 세그먼트는 신규 저장 시 `fa`
- `|`, `=`, `,`, `-`, 영문·숫자와 6자리 HEX로 구성된 세그먼트 구조를 검증한다. 알 수 없는 세그먼트는 forward compatibility를 위해 허용한다.
- Unity가 모르는 파츠 ID는 클라이언트가 기본 파츠로 폴백하되, 서버는 길이 초과나 구조 오류를 명확한 400 응답으로 거부한다.
- (P1) 상점에서 구매하지 않은 아이템 차단이 필요해지면 같은 저장 경계에서 검증한다.

## 4. 정식 Unity UI와 외부 연동 경계

정식 커스터마이징 화면은 Unity `CharacterLobbyController`가 담당한다. Frontend는 동일한 파츠 목록·색상 선택·미리보기를 React로 재구현하지 않는다. AI 채팅·상담·설문처럼 한글 장문 입력이 필요한 화면에만 React 오버레이 원칙을 적용한다.

### 4-1. Unity 화면 책임

- `AvatarConfig`를 기준으로 얼굴·헤어·모자·안경·상의·하의·한벌옷·신발의 썸네일과 선택 상태를 표시한다.
- 같은 디자인의 여성·남성 상의·하의·한벌옷은 실제 메시와 itemId만 성별별로 유지하고, 한국어 이름과 일러스트 썸네일은 공통 표시 원본을 사용한다.
- 아이템별로 실제 화면 변화가 확인된 색상 영역만 제공하고, 선택 즉시 중앙 캐릭터와 네트워크 외형에 반영한다.
- 최초 진입은 저장된 `fa` 외형을 우선 복원하고, 값이 없으면 자연스러운 추천 무작위 외형을 생성한다.
- 확정 시 `IUserApiClient.UpdateMyAvatarAsync`를 통해 Spring에 저장하며 실패해도 세션 외형은 유지한다.

### 4-2. Frontend/WebGL 호스트 책임

- Unity WebGL 로더, 인증 세션과 API 접근 토큰 전달, 화면 진입/이탈 같은 호스트 수준 통합만 담당한다.
- 외부에서 커스터마이징 화면을 여는 요구가 생기면 기존 `AvatarBridge`를 선택적으로 사용할 수 있다.
- `AvatarBridge`는 호환·통합 경계이며 정식 UI의 상태 원본이나 React 재구현 계약이 아니다.

```js
// 선택적 외부 연동 예시. 일반 커스터마이징 흐름에서는 Unity UI가 직접 처리한다.
unityInstance.SendMessage('AvatarBridge', 'ApplyAppearance', 'fa|g=1|i=...|p=...|q=...|w=...');
```

별도 jslib 콜백이나 Spring 프리셋 목록 API는 정식 UI 구현에 필요하지 않다.

## 5. Unity 측 현재 구현 (완료)

| 파일 | 역할 |
|---|---|
| `AvatarAppearance` | avatarCode 인코딩/디코딩, forward-compatible 파서 |
| `AvatarConfig` / `AvatarItemDefinition` | 모듈 파츠·썸네일·표시 이름·아이템별 유효 색상 영역의 Source of Truth |
| `IAvatarVisualProvider` / `CatalogAvatarVisualProvider` | 외형 생성 경계. 신규 `fa` 코드는 Rukha93 `AvatarAssembler`로 로컬 생성 |
| `PlayerAvatarVisual` | avatarCode 구독 → 외형 재생성 + 틴트 + Animator 연결 |
| `PlayerAppearanceController` | 변경 요청(ServerRpc) → 서버 반영 → 전원 전파 + 프로필 저장 호출 |
| `CharacterLobbyController` | **정식 Unity 커스터마이징 화면** — 파츠·색상·무작위·미리보기·저장 흐름 |
| `AvatarCustomizationHud` | 월드 단독 검증용 레거시 HUD. 정식 화면이 아님 |
| `AvatarBridge` | 선택적 WebGL 호스트 연동 및 하위 호환 경계 |

**동기화 방식**: `avatarCode` 문자열만 NetworkVariable로 동기화된다. 신규 모듈 외형은 `fa|g=...|i=...|p=...|q=...|w=...` 형식이며 로비와 월드가 동일한 `AvatarConfig`를 사용한다. 과거 `rt`(Sidekick) 형식은 읽기 호환만 유지하고 신규 생성에는 사용하지 않는다.
3D 모델·머티리얼은 각 클라이언트가 로컬에서 생성하며 NetworkObject가 아니다
(Booth Runtime과 동일 원칙 — doc 07 §9).

크롭형 상의처럼 일부 신체를 다시 노출해야 하는 의상은 `forcedVisibleBodyParts`를 사용한다. 이 값은 성별 Body의 파츠 번호가 다를 수 있으므로 여성·남성을 각각 정의하며, 현재 `Top.07-A`는 여성 Spine01과 남성 Spine01/Spine02를 표시해 하의 위 허리가 끊기지 않게 한다.

**검증 완료**: 클라이언트 A가 프리셋/색상을 바꾸면 클라이언트 B 화면에서 즉시 반영됨.

## 6. 모듈 파츠를 추가하는 방법 (Unity 담당)

1. Rukha93 모듈 파츠의 라이선스와 WebGL 호환성을 확인한다.
2. 해당 파츠를 `AvatarConfig`의 카테고리에 등록하고 `AvatarItemDefinition`에 표시 이름·썸네일·숨김 신체 부위를 설정한다.
