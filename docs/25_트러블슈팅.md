### T-164. 자정을 넘기자 테스트가 깨졌다 — 기대값에 날짜를 문자열로 박아 두었다 (2026-09-18, 해결)

- **증상**: `!1133`(back 통합분 develop 반입)의 `back-test` 가 `DailyMissionServiceTest.claimUsesTheDailyMissionLedgerKeyAndRejectsASecondClaim` 에서 `expected: <DAILY_MISSION:42:AI_CONSULT:2026-09-17> but was: <DAILY_MISSION:42:AI_CONSULT:2026-09-18>` 로 실패했다. 같은 커밋의 전날 실행은 초록이었다.
- **원인**: 테스트가 원장 멱등 키의 기대값을 `"DAILY_MISSION:42:AI_CONSULT:2026-09-17"` 로 **문자열째 박아** 두었고, 구현은 `LocalDate.now(Asia/Seoul)` 로 키를 만든다. 간헐 실패가 아니라 **그 날짜가 지나면 영구 실패**다 — 작성일에는 통과하므로 리뷰에서도 보이지 않는다.
- **해결**: 기대값을 구현이 쓰는 같은 헬퍼(`DailyMissionService.claimKey(userId, mission, LocalDate.now(zone))`)로 계산한다. `Clock` 주입이나 새 유틸은 넣지 않았다 — 공개 헬퍼가 이미 있었다.
- **예방**: **"오늘" 이 들어가는 단정에는 날짜 리터럴을 쓰지 않는다.** 구현이 시각을 얻는 경로와 같은 경로로 기대값을 만들거나, 시각 자체를 주입해 고정한다. 데이터로 쓰는 고정 `Instant`(생성 시각 등)는 문제가 아니다 — `now` 와 비교되는 값만 그렇다.
- **관련**: S15P21A604-882 · MR !1133 · `backend/src/test/java/com/example/ssafesta/mission/DailyMissionServiceTest.java`

### T-163. 파트 브랜치를 반입할 때 같은 마이그레이션 번호가 둘이 되고, 남의 트리 스냅샷이 고아 테스트를 남긴다 (2026-09-18, 해결)

- **증상**: `!1133` 의 `back-test` 가 컨텍스트 자체를 못 띄웠다 — `Error creating bean 'flywayInitializer': Found more than one migration with version 39`. 같은 파이프라인의 `front-test` 는 `unityHostPreparing.test.tsx` 한 건이 `expected 'uh-status' to contain 'uh-status--opaque'` 로 실패했다.
- **원인**: 둘 다 **병행 브랜치의 합류**가 원인이다. ① `V39__avatar_presets.sql`(develop 에서 먼저 머지)과 `V39__booth_lease_expiry_warning.sql`(파트 브랜치)이 각자 다음 번호를 집었다. 번호 충돌은 파일 목록을 봐야 보이고, 텍스트 충돌이 아니라 자동 병합이 조용히 통과시킨다. ② 파트 브랜치 커밋 하나가 프런트·Unity 트리를 통째로 스냅샷으로 담고 있어, 그 트리에만 있던 구현(`uh-status--opaque`)은 FE 소유 규칙대로 develop 판을 채택하면서 빠지고 **그 구현을 검사하는 테스트만 남았다.**
- **해결**: 파트 쪽 마이그레이션을 `V40__` 으로 재번호하고(파일명을 참조하는 코드·테스트·문서는 없었다), 고아 테스트는 develop 판으로 되돌렸다. 함께 섞여 들어온 1.4MB 미참조 에셋(`public/booth-preview/default.png` — FE 폴백은 `default.webp` 다)도 지웠다.
- **예방**: 파트 브랜치를 develop 에 반입할 때 **병합 결과의 마이그레이션 번호 중복을 먼저 본다**(`ls db/migration | sed 's/__.*//' | sort -V | uniq -d`). 그리고 **자기 파트 밖 트리가 스냅샷으로 들어온 커밋이 있으면, 그 트리에서 남은 diff 가 "테스트만" 인지 확인한다** — 구현 없이 남은 테스트는 병합 직후에만 잡을 수 있다.
- **곁가지**: 재번호 뒤에도 같은 Flyway 오류가 로컬에서 재현됐다. 원인은 `backend/target/classes/db/migration` 에 남아 있던 옛 파일이었다(T-160 과 같은 뿌리). 마이그레이션을 건드린 뒤에는 `clean` 이나 해당 파일 삭제가 먼저다.
- **관련**: S15P21A604-882 · MR !1133 · `backend/src/main/resources/db/migration/V40__booth_lease_expiry_warning.sql` · T-160

### T-162. AI 문서 재배차 테스트가 다른 QUEUED Job의 정상 호출을 자기 재배차로 오인한다 (2026-09-17, 해결)

- **증상**: 슬롯 MR !1126의 최신 develop 기준 CI에서 `AiDocumentUploadIntegrationTest.theSweeperResendsAnUndeliveredJobWithTheSameAttempt`가 `위임 호출이 1건이어야 하는데 2건입니다`로 실패했다. 슬롯 테스트는 모두 성공했고, 실패는 AI 문서 스위퍼의 전역 fake 호출 수 단정이었다.
- **원인**: `processing.reset()`은 fake의 목록만 비우며 공유 Testcontainers DB의 다른 `QUEUED` Job은 남는다. 스위퍼가 대상 문서를 같은 attempt로 재배차하면서 다른 문서의 정상 대기 Job도 함께 보냈고, `onlyRequest()`가 전역 호출 수 1건을 요구해 실패했다.
- **해결**: 전역 `onlyRequest()` 대신 이 테스트가 만든 `documentId`로 호출을 필터링해 정확히 한 번 재배차됐는지 검사한다. 다른 문서의 정상 dispatch를 허용해도 대상 attempt·documentId·DB attemptNo 단정은 유지된다.
- **예방**: 스케줄러 통합 테스트는 fake client 목록 전체를 상태 근거로 쓰지 않고 fixture가 만든 식별자별 호출만 단정한다. T-161과 같은 공유 DB·공유 fake 경계 문제이므로 새 스위퍼 테스트도 같은 규칙을 따른다.
- **관련**: S15P21A604-635 · MR !1126 · `backend/src/test/java/com/example/ssafesta/ai/AiDocumentUploadIntegrationTest.java` · T-161

### T-161. AI 문서 스위퍼 통합 테스트가 앞선 테스트의 처리 요청을 자기 결과로 간주한다 (2026-09-17, 해결)

- **증상**: 프리셋 MR !1107의 전체 backend CI에서 `AiDocumentUploadIntegrationTest.theSweeperLeavesADeliveredJobAlone`만 실패했다. 이 테스트는 워커 전송 목록이 비어야 한다고 기대했지만, 앞선 AI 문서 테스트가 만든 5개의 `ProcessingRequest`가 남아 있었다.
- **원인**: fake client는 `@BeforeEach`에서 비워도 DB의 다른 `QUEUED` 작업은 공유 Testcontainers DB에 남는다. 스위퍼가 그 행들을 정상 전송한 것을, 테스트가 `received()` 전체가 빈 배열이어야 한다는 전역 단정으로 자기 `RUNNING` 작업의 재전송으로 오인했다. 프리셋 테이블·컨트롤러·마이그레이션은 이 경로를 호출하지 않는다.
- **해결**: 단정을 전역 전송 목록이 아니라 이 테스트가 만든 `documentId`가 목록에 없는지로 바꿨다. 따라서 다른 작업의 정상 배차는 허용하면서도 `RUNNING`인 대상 작업의 중복 워커 전송은 계속 막는다.
- **예방**: 공유 fake 클라이언트·스케줄러를 쓰는 통합 테스트는 전역 큐가 비었다는 가정 대신 자신이 만든 식별자에 대한 관찰만 단정한다. 전역 초기화가 필요한 경우에는 DB 작업 행과 fake client 양쪽을 함께 정리한다.
- **관련**: S15P21A604-858 · MR !1107 · `backend/src/test/java/com/example/ssafesta/ai/AiDocumentUploadIntegrationTest.java`

### T-159. Unity가 활동을 전송해도 BE 수신·사실 저장이 없으면 일일 미션은 영구 미완료다 (2026-09-17, 해결)

### T-158. 로컬에서 프론트를 두 포트로 띄워 A/B 하면 인증이 성립하지 않아 비교 자체가 무효다 (2026-09-17, 해결)

- **증상**: Unity 빌드를 변수로 두고 같은 dev 서버를 5173·5174 두 포트로 띄워 비교했는데, 5174에서는 게스트 입장이 막히고 OAuth는 로그인에 성공해도 5173으로 돌아갔다.
- **원인**: 세 가지가 겹친다. BE `app.frontend-base-url` 기본값이 `http://localhost:5173` 하나라 OAuth 성공 리다이렉트가 그 주소로 고정된다. 게스트 입장은 `VITE_AUTH_BASE_URL`로 8080에 교차 출처 호출을 하므로 허용 출처가 아닌 포트에서는 막힌다. 인증 쿠키는 host-only라 포트를 가리지 않아 두 포트가 같은 세션을 공유하고, 서버가 `issue()`마다 `sid`를 회전시키므로 두 창이 서로의 세션을 폐기한다(T-142와 같은 뿌리).
- **영향**: 그 구성에서 얻은 정상·비정상 두 줄을 근거로 게임 파트에 blocker 이슈를 열었다가, 재현되지 않아 취소하고 정정했다(GitLab #243).
- **해결**: 두 번째 출처를 걷고 5173 하나만 남겼다. 비교 변수는 정적 서버가 어느 WebGL 빌드를 내보내는지로 옮겼고, dev와 빌드본은 같은 포트를 번갈아 쓴다.
- **예방**: 로컬 비교에서 출처를 늘리지 않는다. 포트를 바꾸면 인증 계약이 함께 바뀌므로 비교군이 아니라 다른 환경이 된다. 그리고 재현 절차를 확보하기 전에는 타 파트에 blocker를 열지 않는다 — 코드 독해만으로 원인을 단정하면 정정 비용이 상대 파트로 넘어간다.
- **관련**: GitLab #243 · #232 · `backend/src/main/resources/application-local.yml` · T-142

### T-157. React StrictMode 재마운트에서 Unity 진행률 콜백이 폐기된 첫 마운트에 남는다 (2026-09-17, 해결)

- **증상**: Unity 인스턴스 로딩은 계속되지만 새 진행률 게이지가 초기값에서 움직이지 않는다. 개발 환경의 React StrictMode에서 재현된다.

### T-154. 배포 Redis 재시작 한 번이 로그인한 전 사용자의 세션을 지운다 (2026-09-16, 확인 대기 — Infra 결정 필요)

- **증상**: 탭 하나만 쓰던 회원 세션이 갑자기 끝나고 로그인 화면으로 튕긴다. 사용자가 로그아웃을 누르지 않았고 서버도 살아 있다. 콘솔 순서는 `ws-token 401` → `/auth/refresh 401` → Access Token 해제다. 보고는 GitLab [#211](https://lab.ssafy.com/s15-metaverse-game-sub1/S15P21A604/-/issues/211).
- **원인 (미확정, 가장 유력한 후보)**: `infra/environments/redis/redis.conf` 가 `appendonly no` 이고 `save ""` 다. save point 가 없으므로 SIGTERM 정상 종료에서도 저장하지 않는다 — `redis-data:/data` 볼륨은 마운트돼 있지만 아무것도 쓰지 않는다. 회원 로그인 세션(`auth:refresh` · `auth:active` · `auth:session` · `auth:family`, TTL `P7D`)은 Redis 에만 있으므로, **컨테이너가 어떤 이유로든 재시작하면 그 시점 로그인 사용자 전원의 세션이 동시에 사라진다.** 서버 어디에도 그 사실을 적는 로그가 없다.

- **BE 가 한 것 (S15P21A604-816)**: 인증 거절의 **사유를 로그로 드러냈다.** 그 전에는 `/auth/refresh` 401 의 갈래 셋(쿠키 미도달 / 키 없음 / 회전 직후 재생)이 모두 로그가 없어 사후에 구분할 수 없었다. 세션이 통째로 사라진 사건은 `SessionRevocationFilter` 거절이 유일한 신호인데 그것도 조용했다. 인증 판정과 401 봉투는 바꾸지 않았다.
- **Infra 결정 필요**: ① redis 컨테이너 재시작 이력 확인 ② `appendonly` 또는 save point 를 켤지 결정 — 켜지 않기로 한다면 "인증 세션은 Redis 재시작마다 전원 소멸한다" 가 운영 계약이 되고, **시연 중 재배포가 전 관객을 로그인 화면으로 보낼 수 있다**는 뜻이므로 명문화가 필요하다 ③ `maxmemory` 와 `mem_limit` 설정 ④ `FESTA_ENVIRONMENT`(키 네임스페이스) 변경 이력.
- **예방**: 재생성 가능한 캐시와 재생성 불가능한 세션을 같은 저장소에 두었다면, 그 저장소의 영속 설정이 **가장 강한 요구사항** 쪽을 따라야 한다. redis.conf 첫 줄은 "재생성 가능한 임시 상태만 보관한다" 로 시작하는데 내용물이 그렇지 않다.

- **원인**: Player 프리팹의 `ClientAuthoritativeNetworkTransform`이 `UseUnreliableDeltas=0`이라 매 틱의 일반 이동 상태까지 `Reliable Fragmented Sequenced`로 보냈다. 패킷 하나가 유실·지연되면 뒤의 최신 위치도 재전송 완료까지 대기한다. 동시에 `PositionInterpolationType=0`, `RotationInterpolationType=0`인 `Legacy Lerp`가 오래된 버퍼를 순차 소비해 복구 순간의 급가속을 키웠다. NGO 2.4 공식 문서도 일반 델타에는 손실 내성 목적의 Unreliable 전송을 제공하고, 새 Lerp가 다음 목표까지 일정한 시간을 유지하며 버퍼를 소비한다고 설명한다.
- **해결**: `ClientAuthoritativeNetworkTransform.Awake`에서 `UseUnreliableDeltas=true`, 위치·회전 보간을 `InterpolationTypes.Lerp`로 설정한 뒤 `base.Awake()`가 보간기를 만들게 했다. 프리팹 YAML을 직접 수정하지 않고 런타임 컴포넌트가 설정의 단일 출처가 되게 했다. 초기 상태·텔레포트·주기적 축 전체 동기화는 NGO가 Reliable로 유지하므로 스폰과 포털 이동 의미는 바뀌지 않는다.
- **검증**: Unity 6000.0.78f1 / NGO 2.4.3 실 API reflection에서 세 필드가 존재하며 변경 가능함을 확인했다. 강제 스크립트 컴파일 오류 0건, 해당 파일 정적 진단 오류·경고 0건이다. 콘솔의 기존 경고 16건은 벤더 obsolete API 등 이번 변경 외 항목이다. 실제 2클라이언트의 이동 시작·정지 지연과 손실 복구 체감은 develop 배포본에서 재측정해야 한다.
- **예방**: 연속 상태는 최신 값 도착이 재전송 완료보다 중요하므로 일반 이동 델타를 Reliable 큐에 넣지 않는다. 네트워크 이동 설정을 프리팹 기본값에만 맡기지 않고 파생 컴포넌트에서 명시하며, 변경 시 정상 RTT뿐 아니라 패킷 손실 후 멈춤·따라잡기까지 검증한다.

### T-147. 멀티플레이 원격 아바타가 평지에 무릎까지 박혀 이동함 (2026-09-14, 코드 해결·배포 확인 대기)

- **남은 확인**: develop 반영 후 새 클라이언트 빌드에서 원격 캐릭터 평지 이동과 실제 단차 보행을 각각 실측해야 한다.
- **예방**: 시각물 자식 Transform을 접지 기준으로 사용하지 않는다. 발 IK 골반 보정은 절대 월드 높이가 아니라 양발 접촉면의 상대 차이로 계산하고, 릴리스 체크리스트에서 평지와 단차를 따로 판정한다.

### T-137. FQDN WSS 접속에서 응답 포트 443이 실제 WebSocket URL의 0으로 변함 (2026-09-08, 패키지 수정·Release 빌드 진행)

- **증상**: GitLab #142의 2026-09-08 13:01 Infra 댓글에서 `StartClient wss://world.ssafesta.world:443 → True` 직후 브라우저가 `wss://world.ssafesta.world:0/` 접속에 실패. 재접속도 동일하며 서버까지 도달하지 않았다고 보고했다.
- **원인**: 전달 산출물 기준 SHA `e4ea8c26`(작업 브랜치 `perf/S15P21A604-493-shader-prewarm`)의 manifest와 현재 manifest/lock은 Unity Transport 2.5.1. Unity 공식 2.5.3 변경 이력은 hostname 인자를 받는 `NetworkDriver.Connect`로 WSS 접속할 때 포트 0을 사용하는 버그 수정을 명시한다. 증상·버전·접속 조건이 일치해 게임 클라이언트의 Transport 의존성 문제로 판단한다. `ConnectionManager.cs:78`은 전달받은 포트를 그대로 설정한다. 기존 FQDN define 수정은 주소 검증 차단만 풀었고 종단 접속까지 검증하지 못했다.
- **해결**: 미실행. 최소 수정 후보는 Transport 2.5.3으로 갱신하고 WebGL 재빌드 후 외부 WSS 실측. 성공 기준은 브라우저의 목적 포트 443(기본 포트라 URL에서 생략되는 경우 포함), WebSocket 101 및 NGO 승인·스폰, 재접속 정상 동작이다. `StartClient=True`만으로 성공 판정하지 않는다. 직접 패키지 내부 코드를 재현하거나 수정한 것은 아니며, 공식 수정 내역과 보고된 실측을 대조한 진단이다.
- **별도 설정 문제**: `world.ssafesta.world` 대신 `world-dev.ssafesta.world`를 주입하는 WORLD_HOST 복구는 Infra가 진행한다고 밝혔다. 호스트 주입 누락과 포트 0 버그는 별개다.
- **예방**: define 활성화·빌드 문자열 존재만으로 접속 완료를 선언하지 않는다. 브라우저가 실제 생성한 URL과 승인·스폰까지 확인한다.
- **후속 실행**: 사용자 빌드 지시로 UPM을 통해 2.5.3 설치, Refresh/Compile 및 Console Error 0 확인. manifest/lock 변경은 Transport 버전 2줄뿐이며 전이 의존성은 동일. 최신 develop `a3ec3aee` 기반 `fix/S15P21A604-505-wss-port` 워크트리에 같은 수정분을 분리했다. 열린 에디터의 `e4ea8c26-dirty` 작업본으로 `Builds/web-release-wss-505-20260908-1312`에 WebGL Release 빌드를 시작했다(Development OFF, Brotli+Fallback, Prod API, Mock OFF). 완료 여부는 [빌드 상태](./KHS/verify/2026-09-08-wss-port-505/build-status.json)로 확인한다. API와 압축 설정은 finally에서 복원한다. 이 산출물은 develop 정본 빌드가 아니며 외부 WSS 종단 검증·배포는 아직 미실행이다.
- **근거**: [GitLab #142](https://lab.ssafy.com/s15-metaverse-game-sub1/S15P21A604/-/work_items/142), [Unity Transport 공식 변경 이력 2.5.3](https://docs.unity3d.com/Packages/com.unity.transport@2.6/changelog/CHANGELOG.html#253---2025-08-06), S15P21A604-505 후속.

- **예방**: 비균등 스케일 오브젝트의 자식에 텍스트/UI를 두지 말거나 역스케일 보정

## Web(WebGL) 빌드

### T-06. 빌드했더니 빈 씬만 나옴 (HUD/부스/바닥 없음)
- **증상**: 브라우저에 스카이박스만 렌더링
- **원인**: Build Profiles **Scene List**에 Main 씬 누락/순서 문제, 또는 씬 미저장(`main*`) 상태로 빌드
- **해결**: Scene List에 Main만 남기고 맨 위 + 씬 저장 후 재빌드
- **예방**: 빌드 전 타이틀바 `*`(미저장) 확인 습관

### T-07. WebGL에서 부스/AI Mock이 영원히 로딩 안 됨
- **증상**: `[BoothRuntime] built` 로그가 안 찍힘. 에디터는 정상
- **원인**: **`Task.Delay`는 WebGL(단일 스레드)에서 완료되지 않음**
- **해결**: Mock 3종을 `Awaitable.WaitForSecondsAsync`로 교체
- **예방**: WebGL 타깃 코드에서 Task.Delay/스레드 API 금지. Unity `Awaitable` 사용
- **부수효과**: 에디터의 무해한 `TaskCanceledException`도 함께 사라짐

### T-08. 런타임 생성 오브젝트가 전부 마젠타(핑크)
- **증상**: 에디터는 정상, 빌드에서만 핑크
- **원인**: `CreatePrimitive` 기본 머티리얼의 셰이더가 빌드에 포함되지 않음
- **해결**: `Shader.Find("Universal Render Pipeline/Lit")`로 머티리얼 명시 생성 (씬 머티리얼이 이미 셰이더를 빌드에 포함시키므로 Find 가능)
- **예방**: 런타임 생성 렌더러는 항상 명시적 셰이더/머티리얼 사용

### T-09. 빌드에서 IMGUI(OnGUI) 패널이 아예 안 보임
- **증상**: 에디터에선 보이는 Dev HUD가 브라우저에서 사라짐
- **원인**: **Active Input Handling이 "Input System Package (New)"만이면 플레이어 빌드에서 OnGUI가 렌더링되지 않음**
- **해결**: Project Settings > Player > Other Settings > Configuration > Active Input Handling = **Both** (에디터 재시작)
- **예방**: DevConnectionHud를 정식 uGUI로 교체하면 원복 검토

### T-10. HUD에 웹페이지 주소를 넣어 접속 실패
- **증상**: Connect 무반응
- **원인**: 웹페이지 http 포트(예: 62385/8000)와 **게임 서버 포트(7777)** 혼동
- **해결**: 브라우저 주소창 = 웹페이지(localhost:8000), HUD Addr/Port = 게임 서버(127.0.0.1:7777)
- **예방**: 정식 구현에서는 world-sessions API가 endpoint를 내려주므로 수동 입력 자체가 사라짐

### T-13. Build And Run 포트가 매번 바뀌고 플랫폼에 묶임
- **증상**: 테스트 URL 고정 불가, Linux Server로 스위치하면 웹 서빙 불가
- **원인**: Build And Run은 에디터 임시 서버 (랜덤 포트, 에디터 종속)
- **해결**: Web Publishing Settings **Compression Format = Disabled** (개발용) 후 빌드 → `python -m http.server 8000 --directory Builds/web` → localhost:8000 고정
- **예방**: 빌드 산출물은 에디터와 무관하게 서빙 가능. 실배포는 Brotli + CloudFront 헤더로 복원 (deployment-handoff.md)

### T-17. `python -m http.server --directory`로 띄웠는데 404
- **증상**: 빌드 폴더에 index.html이 있는데도 브라우저가 404
- **원인**: PowerShell의 현재 위치가 달라 상대경로 `--directory Builds/web-...`가 엉뚱한 폴더를 가리킴
- **해결**: 대상 폴더로 `cd` 후 `python -m http.server <port>` (옵션 없이) 또는 절대경로 지정
- **예방**: 서버 실행 후 브라우저 접속 시 PowerShell에 요청 로그가 찍히는지로 정상 서빙 확인

### T-18. Sidekick 툴 등 에디터 창이 안 열림 (`Attempted to open unsupported window in cloned player systems`)
- **증상**: Synty 툴 창이 열리지 않고 `NullReferenceException` + 이어서 `Failed to load tool data`
- **원인**: **Multiplayer Play Mode의 가상 플레이어(Player 2/3)가 활성 상태**이면 MPPM이 복제 에디터에서 에디터 창 열기를 차단한다
- **해결**: Play 정지 → Window > Multiplayer > Multiplayer Play Mode → Player 2/3 **체크 해제** → **Unity 재시작**(부트스트랩이 이미 꼬였으면 필수)
- **예방**: 에디터 툴(Sidekick 등) 작업 시엔 가상 플레이어를 끈다. 멀티 테스트할 때만 켠다

### T-19. `WebAssembly streaming compilation failed` / Content-Encoding 에러
- **증상**: 브라우저에서 빌드 로드 실패
- **원인**: 빌드가 압축(Brotli/Gzip)돼 있는데 로컬 서버가 `Content-Encoding` 헤더를 안 보냄 (또는 반대)
- **해결**: Build Profiles > Web > Player Settings > Publishing Settings > **Compression Format = Disabled** 후 재빌드 (개발용). 실배포는 Brotli + CloudFront 헤더 설정
- **확인법**: `Builds/web/Build/`에 `.br`/`.gz` 확장자가 있으면 압축된 것
- **부가**: `Tools/serve.py` 사용 시 wasm MIME·캐시 문제도 함께 예방됨

### T-20. `LinkError: wasi_snapshot_preview1 / fd_sync` (Sidekick SQLite)
- **증상**: WebGL 빌드가 아예 로드되지 않음
- **원인**: Sidekick의 SQLite 플러그인이 요구하는 WASI 호출을 런타임이 제공하지 못함. **재빌드 후 정상 동작** — 정확한 트리거는 미확정 (스테일 빌드/캐시 가능성)
- **해결**: 재빌드 + 캐시 무시 새로고침으로 해소됨
- ⚠️ **판정 정정**: 이 에러를 근거로 "Sidekick 런타임은 WebGL 불가, Synty 폴더 삭제 필요"라고 결론 냈으나 **오판**이었다. 근거:
  - Synty 체인지로그 v1.0.2 *"Updated SQLite build targets to allow Web build targets"*
  - `sqlite3.c.meta`에 `WebGL: enabled: 1`
  - `DatabaseManager`는 플레이어 빌드에서 파일 I/O를 쓰지 않음 (TextAsset → `:memory:` Deserialize)
  - 실제로 Synty를 둔 채 WebGL 빌드 성공
- **교훈**: 에러 하나로 "플랫폼 미지원"을 단정하지 말 것. 벤더 문서·플러그인 메타·실제 재현을 교차 확인한다

### T-23. 코드를 고쳤는데 브라우저 결과가 그대로 / 옛 외형이 나옴
- **증상**: 에디터에선 새 기능이 되는데 브라우저는 이전 모습
- **원인**: **Web 빌드를 다시 하지 않음.** 브라우저는 빌드 산출물만 보므로 에디터 변경이 자동 반영되지 않는다
- **해결**: Build Profiles → Scene List에 Main 씬만 체크 → Build → `Builds/web` 덮어쓰기 → Ctrl+Shift+R
- **예방**: 빌드 전 씬 저장(`Ctrl+S`, 타이틀 `*` 없음) 확인. `Tools/serve.py`는 캐시를 차단하므로 새로고침만으로 반영됨

## 코드/에셋 규칙

### T-21. SerializeField 이름을 바꿨더니 Inspector 값이 전부 사라짐
- **증상**: ScriptableObject/프리팹에 입력해둔 값이 빈 값으로 초기화됨 (AvatarCatalog의 preset 코드 소실)
- **원인**: Unity 직렬화는 **필드 이름 기준**. `avatarCode` → `presetCode`로 리팩터링하면 기존 asset 데이터와 매칭이 끊긴다
- **해결**: `[FormerlySerializedAs("이전이름")]` 부착 (`using UnityEngine.Serialization;`)
- **예방**: 직렬화 필드 이름 변경 시 **항상** FormerlySerializedAs를 함께 붙인다. 이미 값이 날아갔다면 붙인 뒤 재입력

### T-24. 커스터마이징 Custom 버튼이 무반응 — 인코딩 길이 초과가 조용히 삼켜짐 (2026-08-12)
- **증상**: HUD의 Custom 버튼을 눌러도 아무 변화 없음. 에러도 안 보임. 서버(Docker)를 재빌드해도 동일
- **원인**: `AvatarAppearance.Encode()`가 500자 초과 시 **조용히 `sk_01`을 반환**하도록 되어 있었음. Sidekick 파츠 이름이 길어(파츠당 ~25자 × 16종) 런타임 조립 인코딩이 500자를 넘으면, 서버에 "현재와 같은 값"이 전송되어 OnValueChanged가 발화하지 않음 → 완전한 무반응
- **해결**:
  1. 동기화 필드를 `FixedString512Bytes` → **`FixedString4096Bytes`**로 확대, `MaxEncodedLength` 500 → 3800
  2. Encode의 몰래 되돌리기 제거 — 초과 판단은 호출자(RequestChange)가 하고 거부 사유를 `LastRequestError`로 노출
  3. HUD가 `LastRequestError`를 **화면에 표시** (콘솔을 안 봐도 원인이 보이게)
  4. `SyncMirrorParts`의 이름 치환 실패 시 인덱스 매칭 폴백 (오른팔/오른다리 소실 방지)
- **주의**: NetworkVariable **타입이 바뀌었으므로 Web 빌드와 Linux Server(Docker) 빌드를 반드시 둘 다 다시** 해야 한다 (한쪽만 바꾸면 직렬화 불일치)
- **교훈**: 실패를 조용히 기본값으로 대체하는 코드는 "무반응 버그"가 된다. 거부/실패는 반드시 사용자 또는 로그에 드러낸다

#### T-24 후속 — "클라만 새 빌드, 서버는 옛 빌드"의 함정
- **증상**: 클라 로그에는 `[MockUserApi] 아바타 저장(모의): rt|1=SK_HUMN...`처럼 **긴 인코딩이 정상 생성**되는데, `[AvatarVisual] 적용`은 계속 `runtime=False`
- **판독법**: 이 조합은 "클라는 새 코드 / 서버는 옛 코드"의 지문이다
  - 클라(새 코드)는 600자 인코딩을 만들어 RPC 전송 ✅
  - 서버(옛 코드)의 `RequestChangeServerRpc`가 `Decode(...).Encode()`로 재인코딩 → 옛 500자 제한에 걸려 **`sk_01` 반환** → 현재 값과 동일 → `OnValueChanged` 미발화 → 화면 무변화
- **해결**: Linux Server 빌드 → 이미지 재빌드 → 컨테이너 교체 (Web 빌드와 **항상 쌍으로**)
- **재발 방지 (코드에 반영)**:
  1. 서버 RPC에서 **재인코딩 제거** — 길이 검증 후 받은 값을 그대로 기록
  2. 클라가 요청 후 2초 내 반영이 없으면 HUD에 `server did not apply the change — 서버(Docker) 빌드가 최신인지 확인` 표시
- **서버 로그 확인법**: 브라우저 콘솔에는 서버 로그가 안 나온다. `docker logs -f festa-world`로 `[Appearance] 서버 반영: client=.. len=..`이 찍히는지 본다 (안 찍히면 서버가 옛 빌드)

### T-25. 서버를 새로 빌드했는데 계속 옛 동작 — 이름 다른 옛 컨테이너가 포트를 점유 (2026-08-12)
- **증상**: Linux Server 재빌드·이미지 재생성을 반복해도 서버 동작이 그대로. `docker run` 시 `Bind for 0.0.0.0:7777 failed: port is already allocated`, `docker rm -f festa-world` 는 `No such container`
- **원인**: 실제로 돌고 있는 컨테이너 이름이 **`festa-world-01`**(README 표기)인데 `festa-world`로 지우려 해서 제거 실패. 옛 컨테이너가 계속 7777을 점유한 채 **옛 코드로 응답**하고 있었다
- **해결**:
  ```powershell
  docker ps                                   # 실제 이름 확인
  docker rm -f festa-world-01 festa-world     # 전부 제거
  ```
- **예방**: 서버 갱신은 항상 `docker ps` → `rm -f` → `build` → `run` 순서. 컨테이너 이름을 **`festa-world-01` 하나로 통일**한다 (Docker/README.md 기준)

### T-26. Docker 빌드가 `chmod: cannot access '/app/festa-unity.x86_64'`로 실패 (2026-08-12)
- **증상**: `[6/6] RUN chmod +x /app/festa-unity.x86_64` 단계에서 no such file. 로그의 `transferring context: 3.57kB`가 단서
- **원인**: **빌드 컨텍스트를 `Docker/` 폴더로 지정**했다. 이 Dockerfile은 `COPY . /app`으로 컨텍스트 전체를 복사하므로 컨텍스트가 **Linux Server 빌드 출력 폴더**여야 한다
- **해결**: `docker build -t festa-world:dev -f Docker/Dockerfile Builds/linux-server` (festa-unity 폴더에서 실행)
- **판별법**: `transferring context`가 수 KB면 실행 파일이 안 들어간 것 (정상은 수십~수백 MB)

### T-27. 파츠를 바꾸면 캐릭터가 T포즈로 굳는다 (2026-08-12)
- **증상**: Custom 모드로 파츠를 조립하면 외형은 정상인데 애니메이션이 전혀 재생되지 않고 T포즈. 프리셋 모드에서는 정상
- **원인**: Sidekick `SidekickRuntime.CreateCharacter()`는 생성한 캐릭터에 Animator를 붙이고 **avatar(휴머노이드 정의)까지 복사**하지만, `runtimeAnimatorController`는 **생성자에 넘긴 컨트롤러가 있을 때만** 설정한다.
  ```csharp
  // Synty 원본 (SidekickRuntime.cs)
  Animator newModelAnimator = newSpawn.AddComponent<Animator>();
  newModelAnimator.avatar = baseModelAnimator.avatar;
  newModelAnimator.Rebind();
  if (_currentAnimationController != null)          // ← 우리는 null로 생성했다
      newModelAnimator.runtimeAnimatorController = _currentAnimationController;
  ```
  우리는 `new SidekickRuntime(baseModel, material, null, _db)`로 만들었으므로 **Controller가 비어 있는 Animator**가 생성된다 → 재생할 상태 머신이 없어 바인드 포즈(T포즈) 그대로 멈춘다
- **해결**:
  1. `PlayerAvatarVisual`의 인스펙터 슬롯 **Animator Controller에 `AvatarAnimator` 할당** (근본 해결)

### T-54. 플레이 중 Game View 강제 갱신으로 PlayerLoop 재귀 오류 발생 (2026-08-14)
- **증상**: 최종 화면 캡처를 강제로 갱신하는 과정에서 `PlayerLoop internal function has been called recursively` 오류가 기록되고 Unity MCP 연결이 일시적으로 끊겼다.
- **원인**: 플레이 모드에서 `EditorApplication.QueuePlayerLoopUpdate()`와 `InternalEditorUtility.RepaintAllViews()`를 함께 호출해 실행 중인 PlayerLoop 안에서 추가 PlayerLoop 갱신을 요청했다.
- **해결**: Unity 연결을 복구한 뒤 강제 갱신 호출을 제거하고, Game View 창에 포커스만 준 다음 한 프레임 이상 기다려 일반 스크린샷을 촬영했다. 최종 재컴파일 후 Console Error 0건을 확인했다.
- **예방**: 플레이 모드 캡처에서는 PlayerLoop/Repaint 강제 호출을 사용하지 않고 `GameView.Focus()` → 대기 → 캡처 순서만 사용한다.

### T-97. `jsonPath(...).doesNotExist()`가 명시적 `null`도 통과시켜 계약을 못 지킴 (2026-08-28, 해결)
- **증상**: spec 016 계약은 "`homepageUrl` 키는 항상 응답에 있고 값이 `null`로 의미를 전달한다"(FE가 `null` 하나로 미등록/미공개를 분기)인데, 검증을 `jsonPath("$.homepageUrl").doesNotExist()`로 써서 **키가 아예 없어도 통과**하는 상태였다. 나중에 Jackson null 제외 설정이 들어오면 계약이 깨져도 테스트는 계속 green.
- **원인**: Spring의 `doesNotExist()`는 JsonPath 평가 결과가 `null`이면 통과한다 — 필드 부재와 명시적 `null`을 구분하지 못한다. 실제로 같은 응답에서 `doesNotExist()`와 `has() && isNull()`이 **둘 다** 통과하는 것으로 확인했다(현재는 null이 직렬화되고 있음, 전역 `default-property-inclusion` 미설정).
- **해결**: 응답 본문을 `JsonMapper.readTree`로 파싱해 **`has(field)`와 `get(field).isNull()`을 따로 단언**하는 헬퍼로 5곳 전부 교체(등록 해제 응답·`/mine`·미공개 부스 조회·미등록 공개 부스 조회 + 게이트 입력 `publishedLayoutVersion`).
- **예방**: "필드가 있고 값이 null"이 계약이면 `doesNotExist()`·`exists()`를 쓰지 않는다 — `exists()`는 명시적 null에서 실패하고 `doesNotExist()`는 부재에서도 통과하므로 **둘 다 그 계약을 표현할 수 없다.** 본문 파싱으로 두 조건을 명시한다.
- **⚠️ Jackson 3**: 이 저장소는 `tools.jackson`(Jackson 3)이다. `com.fasterxml.jackson.databind.ObjectMapper` 빈은 **존재하지 않는다** — `tools.jackson.databind.json.JsonMapper`를 주입한다(annotation 패키지만 `com.fasterxml.jackson.annotation`으로 남아 혼동하기 쉽다).
- **관련**: S15P21A604-109

### T-98. `java.net.URI` 를 URL 신뢰 경계로 쓰다 6 건이 연속으로 샜다 (2026-08-28, 해결)
- **증상**: spec 009 URL 검증기(`common/HttpUrlValidator`)가 리뷰 4 라운드에 걸쳐 결함 6 건을 받았다. 전부 "파싱은 되는데 목적지로는 쓸 수 없는 주소"이거나 "검증한 구조와 저장되는 문자열이 갈리는" 종류였다.

  | # | 입력 | 무슨 일이 났나 |
  |:--:|---|---|
  | 1 | `https://x.com:99999` | RFC 3986 은 포트를 `*DIGIT` 로만 정의한다. host·port 가 멀쩡히 파싱되지만 연결 불가 |
  | 2 | `https://한글도메인.com` | `URI` 가 authority 를 RFC 2396 으로 읽어 `getHost()` 가 `null`. **한국 서비스가 한국 도메인을 거부**하고 있었다 |
  | 3 | `https://user@한글.com` | 고치려고 `IDN.toASCII` 에 authority 를 통째로 넘겼더니 `xn--user@-lt1tk15s.com` — `@` 를 라벨 안으로 삼켜 **다른 이름**이 됐다 |
  | 4 | `https://한글도메인.com@evil.com` | userinfo 거부를 IDN 경로에만 걸어 둬서, host 가 ASCII 면 조기 반환에 걸려 검사가 아예 안 돌았다 |
  | 5 | `https://한글.com＠evil.com` | 전각 `＠`(U+FF20)는 raw 검사 시점엔 `@` 가 **아니다**. IDN 매핑 후 `@` 가 되어 `evil.com` 으로 해석됐다 |
  | 6 | `https://한글.com：8080/x` | 전각 `：` 도 같은 방식으로 **원본에 없던 포트**를 만들었다. 값이 정상 범위라 포트 규칙에도 안 걸렸다 |

- **원인**: `java.net.URI` 는 **문법 파서**이지 도달 가능성·구조 무결성 검사기가 아니다. 파싱 성공을 "쓸 수 있는 주소"로 읽은 것이 1·2 의 원인이고, 3~6 은 그것을 고치려고 **정규화 함수의 출력을 재해석**하면서 생겼다. `IDN.toASCII` 는 인자를 도메인 이름 하나로 보므로 구분자를 이름의 일부로 삼키거나 반대로 구조 문자를 만들어 낸다.
- **해결**: 문자를 하나씩 쫓는 것을 그만두고 규칙을 뒤집었다 — **변환 결과가 이름의 모양인지 묻는다.**

### T-104. SSAFY OAuth 가 동의 제출에서 400 `OAuth 2.0 Parameter: client_id` 로 막혔다 (2026-09-01 우회 → 2026-09-07 해결 — SSAFY 측이 고쳤다)

  ```
  POST /ssafy/oauth2/authorize
  Content-Type: application/json

  {"client_id":"<우리 client id>","state":"<state>","scope":[["email","name"],"project"]}
  ```

  **`client_id` 는 본문에 정상적으로 들어 있다.** 그런데도 400 인 이유는 전송 형식이다 — Spring Authorization Server 의 동의 엔드포인트는 `request.getParameter("client_id")` 로 읽고, 서블릿은 `application/x-www-form-urlencoded` 본문만 파라미터로 파싱한다. `application/json` 이면 본문이 통째로 무시돼 `client_id` 가 `null` 이 되고, 그 결과가 정확히 이 오류다. SPA 가 쓰는 axios 인스턴스가 `headers: {"Content-Type": "application/json"}` 으로 고정돼 있는데 `FormData` 를 실어 보내서 생긴 불일치로 보인다.

- **확정 실험**: 같은 동의 제출을 `Content-Type: application/x-www-form-urlencoded` 로 한 번 보내면 **302 에 인가 코드가 나온다.** 형식만 바꾼 것이고 나머지는 동일하다.

  ```
  JSON            → 400 {"code":400,"message":"OAuth 2.0 Parameter: client_id"}
  form-urlencoded → 302 Location: /ssafy/oauth2/callback?code=...
  ```

- **우회 (최초 1회)**: SSAFY 는 부여된 동의를 저장하므로, **계정당 한 번만** 아래를 수행하면 그 뒤로는 동의 화면이 뜨지 않고 브라우저 로그인이 정상 동작한다. SSAFY 세션 JWT 가 필요하다 — 브라우저 개발자 도구의 `/ssafy/...` 요청 `Authorization: Bearer` 헤더에서 가져온다. **이 값은 계정 자격이므로 저장소·문서·이슈 어디에도 남기지 않는다.**

  ```javascript
  javascript:(async()=>{

    const cid=q.get('client_id'), ru=q.get('redirect_uri');
    if(!cid||!ru){alert('sso-check 주소에서 실행하세요');return;}

        {client_id:cid,redirect_uri:ru,response_type:'code',scope:sc}),
        {headers:H,redirect:'manual'});

    if(!st){alert('state 못 얻음 — 이미 동의됨일 수 있음');return;}
    const b=new URLSearchParams();
    b.set('client_id',cid); b.set('state',st);
    sc.trim().split(/\s+/).forEach(s=>b.append('scope',s));
    const r=await fetch('/ssafy/oauth2/authorize',{method:'POST',headers:
        {...H,'Content-Type':'application/x-www-form-urlencoded'},body:b,redirect:'manual'});
    alert('동의 제출 완료 ('+r.status+') — 이제 다시 로그인하세요');

  ```

### T-103. 전체 스위트에서만 `nickname` 이 `VARCHAR(30)` 을 넘어 1건 실패했다 (2026-08-31, 해결)
- **증상**: `BoothLayoutConfigLinkIntegrationTest.aLaptopCarryingAConfigIdIsReportedAsUnverified` 가 `leasedOwner:216` 에서 `value too long for type character varying(30)` 로 죽는다. **그 클래스만 단독 실행하면 10건 전부 통과**한다. 러너가 없어 develop 이 이 1건으로 red 인 것을 아무도 몰랐다.
- **원인**: `users.nickname` 은 `VARCHAR(30) NOT NULL UNIQUE`(V1:6)인데 헬퍼가 `prefix + SEQUENCE + "_" + System.nanoTime()` 으로 만들었다. **`nanoTime` 하나가 16~19자리를 먹는다.** 실패한 호출부 prefix 는 `"노트북configId"` 11자다 — 단독 실행이면 `11 + 1 + 1 + 17 = 30` 으로 상한에 딱 걸려 통과하고, 전체 스위트에서는 앞선 클래스들이 이미 수백 번 호출해 순번이 3자리가 되어 `11 + 3 + 1 + 17 = 32` 로 넘친다. 즉 **`SEQUENCE` 가 몇 자리인지가 통과와 실패를 갈랐다.**
- **해결**: `nanoTime` 을 뺀다. `SEQUENCE` 는 JVM 당 유일하고 Testcontainers 컨테이너는 `withReuse` 를 안 써서 실행마다 새로 뜨므로 **실행 간 충돌이 애초에 불가능**했다 — `nanoTime` 은 없는 위험을 막느라 예산 17자를 쓰고 있었다. 다만 헬퍼마다 `SEQUENCE` 가 따로여서 그냥 빼면 서로 같은 값을 낼 수 있다(`nickname` 은 UNIQUE 다). 그래서 헬퍼별 태그 한 글자를 넣는다 — `b`(Booth)·`w`(Wallet)·`g`(Game)·`a`(Avatar)·`v`(World). 다섯 곳 전부 같은 방식으로 고쳤다. 전체 549 테스트 실패 0.
- **예방**: 테스트 픽스처가 만드는 문자열은 **컬럼 폭 안에 여유를 두고** 만든다. 유일성 재료를 둘(순번 + 타임스탬프) 겹치면 폭을 넘기기 쉽고, 넘긴 뒤에도 실행 순서에 따라 통과해 버려 회귀로 잡히지 않는다. 그리고 **`nanoTime` 을 뺄 때는 그것이 무엇의 유일성을 지키고 있었는지 먼저 본다** — 여기서는 실행 간이 아니라 헬퍼 간이었다.
- **관련**: S15P21A604-352, `BoothTestSupport`·`WalletTestSupport`·`GameTestSupport`·`MyAccountAvatarApiIntegrationTest`·`WorldSessionApiIntegrationTest` · `V1__initial_schema.sql:6`. S15P21A604-347 검증 중 발견했고 그 변경과는 무관하다

### T-127. amd64 Unity 전용 서버가 Apple Silicon 에서 기동하지 않는다 — Mono JIT x86-codegen assertion (2026-09-06, 해결)

- **증상**: 게임 파트 공유 패키지의 `festa-world:dev`(linux/amd64)를 Apple Silicon Mac 의 Docker Desktop 에서 띄우면 컨테이너는 `Up` 인데 서버가 서지 않는다. 로그에 `Assertion at ../../mono/arch/amd64/../x86/x86-codegen.h:410, condition 'offset == (gint32)offset' not met` → `Caught fatal signal - signo:6`. `[NetworkBootstrap] Dedicated server start=True` 가 영영 찍히지 않아 클라이언트는 7777 에 붙지 못한다.
- **원인**: **user-mode 번역 계층의 한계다.** QEMU binfmt 든 Rosetta 든 amd64 명령어를 호스트 arm64 로 바꿔 실행하는데, Mono JIT 은 자기가 생성한 코드와 데이터가 32비트 변위(±2GB) 안에 있다고 가정한다. 번역 계층이 만든 주소 배치가 그 가정을 깨서 코드 생성 단계에서 죽는다. Unity 설정·시크릿·볼륨 문제가 **아니다** — [mono/mono#21423](https://github.com/mono/mono/issues/21423)·[FragPipe#1741](https://github.com/Nesvilab/FragPipe/issues/1741) 에 같은 assertion 이 보고돼 있고 두 이슈 모두 해법이 달리지 않았다.
- **듣지 않은 것 (전부 실측)**: Docker Desktop 의 Rosetta 에뮬레이션 전환(`UseVirtualizationFrameworkRosetta`, `/proc/self/maps` 로 적용 확인) · 메모리 제한 `-m 2g`(주소 공간 축소) · `WORLD_REPLAY_LEDGER` 경로 변경·미지정 · `MONO_ENV_OPTIONS` 의 `--interpreter`·`--interp`·`-O=-inline`. **에뮬레이터를 바꾸는 접근은 전부 같은 층이라 결과가 같다.**
- **해결**: **번역 계층을 없앤다 — 전체 시스템 x86_64 VM 을 띄운다.** 게스트 커널이 진짜 amd64 이므로 Mono 가 네이티브로 돌고 assertion 이 사라진다.

  ```bash
  brew install colima qemu lima-additional-guestagents
  colima start --profile amd64 --arch x86_64 --vm-type qemu --cpu 4 --memory 8 --disk 40

  # 이미지를 VM 안 docker 로 직접 흘려 넣는다 (호스트 마운트가 비어 있어도 된다)
  gunzip -c festa-world-dev-<sha>.tar.gz | \
    LIMA_HOME=~/.colima/_lima limactl shell colima-amd64 -- docker load

  docker --context colima-amd64 run -d --name festa-world-01 -p 7777:7777 \
    -e CONNECTION_TOKEN_SECRET="<backend/.env 값>" \
    -e WORLD_REPLAY_LEDGER=/app/used-grants.log festa-world:dev
  ```

  결과: assertion **0건**, `[ReplayLedger] 준비 완료`, `[NetworkBootstrap] Dedicated server start=True port=7777 maxPlayers=40 (WebSocket)`. lima 가 호스트 `127.0.0.1:7777` 로 포트를 전달하므로 FE·serve.mjs 설정은 그대로 둔다.
- **함정 둘**: ① `lima-additional-guestagents` 를 빼먹으면 VM 이 `guest agent binary could not be found for Linux-x86_64` 로 죽는다 — Lima 2.2 가 guest agent 를 별도 패키지로 분리했다. ② colima 의 호스트 마운트가 비어 있을 수 있다. 이미지를 파일 경로로 넘기지 말고 **표준입력으로 흘려 넣으면** 마운트에 의존하지 않는다.
- **비용**: TCG 전체 에뮬레이션이라 느리다 — VM 기동 약 2분, 서버 씬 로드 약 1분. 한 번 띄우면 접속·플레이는 정상이다.
- **예방**: **Apple Silicon 에서 amd64 Unity(Mono) 산출물을 Docker Desktop 으로 돌리려 하지 않는다.** 위 VM 경로를 쓰거나, 게임 파트가 arm64 또는 IL2CPP 서버 빌드를 내면 그것을 쓴다(IL2CPP 는 JIT 을 안 써서 에뮬레이션에서도 동작한다). 컨테이너가 `Up` 이어도 서버가 섰다는 뜻이 아니다 — **`Dedicated server start=True` 를 확인**하고, `Assertion at`·`fatal signal` 건수를 함께 센다.
- **관련**: S15P21A604-462, GitLab #127, `docs/LJH/verify/` 로컬 통합 실측, T-25(컨테이너를 이름이 아니라 포트로 확인)


### T-128. 정적 서버가 옛 폴더를 계속 서빙해 빌드 검증 네 번이 전부 무효였다 (2026-09-07, 해결)
- **증상**: WebGL 빌드를 새로 뽑고 검증하는데 코드 수정이 **전혀 반영되지 않았다.** BGM 수정이 안 먹고, 화면에 심은 진단 IMGUI 도 안 뜨고, `LateUpdate` 진단 로그도 0건이었다. 그런데 `Update` 는 돌고 있었다(볼륨이 변했다). 같은 MonoBehaviour 에서 `Update` 는 돌고 `LateUpdate` 는 안 도는 건 불가능하다.

- **해결**: `netstat -ano | grep ":8010"` 로 실제 점유 PID 를 찾아 죽이고 다시 띄운 뒤, **서버가 내주는 `manifest.json` 의 확장자로 대상을 확인**했다(개발 `.data` / 릴리스 `.data.unityweb`). 에디터 Play 에서 진단 로그가 즉시 나온 것이 코드는 처음부터 정상이었다는 증거였다.
- **예방**: 정적 서버를 띄울 때 **출력을 버리지 않는다** — `serve.js → http://localhost:PORT/ (경로)` 한 줄이면 바인드 실패를 즉시 안다. 검증 전에 **서버가 실제로 어느 산출물을 내주는지 응답으로 확인**한다. `curl 200` 은 "무언가 응답한다" 는 뜻이지 "방금 뽑은 빌드를 준다" 는 뜻이 아니다. "고쳤는데 그대로" 의 의심 목록에 **서빙**을 넣는다.
- **관련**: S15P21A604-471, T-23, T-25

### T-129. 프록시가 CORS 헤더를 덧붙여 중복되면 브라우저가 응답 전체를 거절한다 (2026-09-07, 해결)
- **증상**: FE 임베드(`:5173`)에서 Unity 가 `:8000/api/...` 를 부를 때 전부 `Unknown Error (CORS/네트워크/타임아웃)`. 월드 접속이 안 돼 플레이어가 스폰되지 않았고, "월드에 못 들어가고 엉뚱한 곳에서 시작" 하는 것처럼 보였다.
- **원인**: Unity 빌드는 API 를 자기 오리진(`localhost:8000`)에서 찾는데 거긴 정적 서버다. `/api/*` 를 Spring(18080)으로 넘기는 프록시를 붙였는데, **응답에 `Access-Control-Allow-Origin` 을 하나 더 붙였다.** Spring 이 이미 `localhost:5173` 을 허용해 같은 헤더를 보내고 있어 **중복**됐고, 브라우저는 중복 ACAO 응답을 통째로 거절한다.

- **예방**: 이미 CORS 를 처리하는 서버 앞에 프록시를 둘 때는 **헤더를 더하지 않는다.** `curl` 로 헤더를 세기 전에는 "CORS 를 열었다" 고 말하지 않는다.

### T-132. `git checkout <브랜치> -- <파일>` 로 커밋 안 한 작업을 날렸다 (2026-09-07, 재작성)

### T-133. HUD 의 오른쪽 ms 를 GPU 시간으로 읽고 최적화 근거로 삼았다 (2026-09-07, 정정)
- **증상**: 조명 최적화 결과를 "**GPU 49 → 27 ms**" 로 커밋 메시지·작업일지·MR·Jira·GitLab #143 에 모두 기록했다. 코덱스 진단이 **그 값은 GPU 시간이 아니다** 라고 지적했고, 확인 결과 맞았다.
- **원인**: `PerfHud.cs:204` 는 한 줄에 세 값을 찍는다.
  ```csharp
  Sb.AppendFormat("FPS {0,6:F1}   평균 {1,5:F1} ms   최악 {2,5:F1} ms\n", _fps, _avgMs, _worstMs);
  ```

### T-145. 세션 폐기 필터의 `sendError` 가 오류 봉투를 우회했다 — 로그아웃 뒤 남은 탭은 본문 없는 401 을 받았다 (2026-09-13, 해결)
- **증상**: 로그아웃한 뒤 다른 탭이 들고 있던 Access Token 으로 요청하면 `401` 인데 **본문이 비어 있다** — `code`·`requestId` 가 없다. 만료·위조 토큰은 정상 봉투 `{"code":"UNAUTHORIZED", …}` 를 받으므로 FE 는 이 한 경로에서만 분기할 값이 없다. `S15P21A604-693` 코드리뷰에서 발견, 프로브로 실측(`contentType=null body=[]`).
- **원인**: `SessionRevocationFilter` 가 `response.sendError(401, …)` 를 썼다. 필터는 `@RestControllerAdvice` 밖이라 `ApiErrorWriter` 를 직접 불러야 하는데, `sendError` 가 "401 을 보냈다" 는 착각을 준다. 봉투 우회는 반복된 모양이다 — T-113 계열, `S15P21A604-402`(도메인 예외 6종, 4차 재발), 이번이 필터 계층 판이다. 기존 테스트는 그 요청을 `status().isUnauthorized()` 로만 봤다.
- **해결**: 두 분기를 `ApiErrorWriter` 로 바꿨다 — 세션 폐기는 `UNAUTHORIZED` + "로그인 세션이 종료되었습니다.", 숫자가 아닌 회원 subject 는 refresh 와 같은 `INVALID_MEMBER_TOKEN`. 둘 다 `$.code` 를 단정하는 테스트를 넣고, 고치기 전 실패를 먼저 확인했다.
- **예방**: 필터에서 응답을 끝내는 코드는 `ApiErrorWriter` 하나다. 401·403 단정은 status 와 `$.code` 를 함께 본다 — status 만 보는 단정은 봉투 이탈을 영영 못 잡는다.
- **관련**: S15P21A604-693 · `backend/src/main/java/com/example/ssafesta/auth/SessionRevocationFilter.java` · `docs/HDD/트러블슈팅.md` T-157
