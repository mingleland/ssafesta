# 트러블슈팅 모음

> **운영 규칙 (필수)**
> 1. 작업 중 문제가 발생하면 **해결 여부와 무관하게 즉시 여기 등록**한다. "나중에 정리"는 없다 — 그 자리에서 T-번호를 따고 한 줄이라도 적는다.
> 2. 형식: 증상 / 원인 / 해결 / 예방. 원인 미상이면 원인란에 "조사 중"으로 두고 해결되면 갱신한다.
> 3. `24_작업일지.md`에서 T-번호로 참조한다.
> 4. 같은 증상이 재발하면 새 항목을 만들지 말고 기존 항목에 재발 기록을 추가한다.

## Unity 에디터 / 씬

### T-01. 캡슐·오브젝트가 납작한 원반/종잇장으로 보임
- **증상**: 플레이어 캡슐이 파란 원반처럼 찌부러져 렌더링
- **원인**: "NetworkTransform의 Scale 동기화 체크 해제" 지시를 **Transform 컴포넌트의 Scale 값에 0 입력**으로 오해 → Scale (0,1,0)
- **해결**: 프리팹/부모 오브젝트 Transform Scale을 (1,1,1)로 복원
- **예방**: Scale "체크 해제"는 NetworkTransform의 Syncing 체크박스를 뜻함. Transform 숫자값 아님. 부모 오브젝트 Scale도 자식 전체를 찌그러뜨리므로 함께 확인

### T-02. 알록달록한 소용돌이/얼룩이 떠다님 (글자 깨짐)
- **증상**: 이름표·라벨 위치에 글리치 텍스처 얼룩
- **원인**: **Unity 6는 런타임 생성 TextMesh에 기본 폰트를 자동 지정하지 않음**
- **해결**: `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")` 지정 + MeshRenderer material에 font.material 할당
- **예방**: 코드로 TextMesh를 만들면 폰트 지정 필수 (NetworkPlayer, BoothObjectFactory에 반영됨)

### T-03. 라벨 글자가 찌그러져 보임
- **증상**: 비디오 스크린 등 위의 라벨이 눌린 형태
- **원인**: 비균등 스케일(2.4×1.4×0.1) 오브젝트의 **자식**으로 라벨을 붙여 부모 스케일이 글자에 전파
- **해결**: 라벨 localScale에 부모 스케일의 역수 적용
- **예방**: 비균등 스케일 오브젝트의 자식에 텍스트/UI를 두지 말거나 역스케일 보정

### T-04. 오브젝트가 바닥에 절반 묻힘
- **증상**: 스폰된 캡슐/부스 도형의 하반이 지면 아래
- **원인**: Unity primitive는 **피벗이 중심** — Y=0에 스폰하면 절반이 묻힘
- **해결**: 스폰 위치에 절반 높이 가산 (Player 스폰 Y=1, BoothObjectFactory groundLift)
- **예방**: 프리팹 제작 시 피벗을 바닥 기준으로 만들거나, 코드 스폰 시 높이 보정

### T-05. 코드를 고쳤는데 실행 결과가 그대로
- **증상**: 파일은 갱신됐는데 Play 결과 불변
- **원인**: 에디터가 Play 중이거나 포커스를 안 받아 재컴파일이 안 됨 (외부에서 파일이 변경된 경우)
- **해결**: Play 정지 → Unity 창 포커스 → Ctrl+R → 우하단 스피너 종료 후 Play
- **예방**: 외부(AI 세션 등)에서 파일을 수정하면 반드시 Play 정지 상태에서 Refresh
- **2026-08-14 재확인**: 플레이 중 스크립트 컴파일 뒤 첫 캡처가 이전 의상 레일을 유지했다. `Stop → Play`로 도메인을 새로 시작한 뒤 왼쪽 탭형 UI가 반영된 화면을 다시 검증했다.

### T-14. 자기 캡슐이 화면에 안 보임
- **증상**: 접속은 되는데 캡슐이 화면 밖
- **원인**: 카메라가 고정이라 스폰 위치를 안 비춤
- **해결**: `PlayerCameraFollow` (Owner 전용 3인칭 추적) 프리팹에 추가
- **예방**: POC용 — 정식 카메라 워크는 spec 확정 후 교체

## Web(WebGL) 빌드

### T-06. 빌드했더니 빈 씬만 나옴 (HUD/부스/바닥 없음)
- **증상**: 브라우저에 스카이박스만 렌더링
- **원인**: Build Profiles **Scene List**에 Main 씬 누락/순서 문제, 또는 씬 미저장(`main*`) 상태로 빌드
- **해결**: Scene List에 Main만 남기고 맨 위 + 씬 저장 후 재빌드
- **예방**: 빌드 전 타이틀바 `*`(미저장) 확인 습관

### T-07. WebGL에서 부스/AI Mock이 영원히 로딩 안 됨
- **증상**: `[BoothRuntime] built` 로그가 안 찍힘. 에디터는 정상
- **원인**: **`Task.Delay`는 WebGL(단일 스레드)에서 완료되지 않음**
- **해결**: Mock 3종을 `Awaitable.WaitForSecondsAsync`로 교체
- **예방**: WebGL 타깃 코드에서 Task.Delay/스레드 API 금지. Unity `Awaitable` 사용
- **부수효과**: 에디터의 무해한 `TaskCanceledException`도 함께 사라짐

### T-08. 런타임 생성 오브젝트가 전부 마젠타(핑크)
- **증상**: 에디터는 정상, 빌드에서만 핑크
- **원인**: `CreatePrimitive` 기본 머티리얼의 셰이더가 빌드에 포함되지 않음
- **해결**: `Shader.Find("Universal Render Pipeline/Lit")`로 머티리얼 명시 생성 (씬 머티리얼이 이미 셰이더를 빌드에 포함시키므로 Find 가능)
- **예방**: 런타임 생성 렌더러는 항상 명시적 셰이더/머티리얼 사용

### T-09. 빌드에서 IMGUI(OnGUI) 패널이 아예 안 보임
- **증상**: 에디터에선 보이는 Dev HUD가 브라우저에서 사라짐
- **원인**: **Active Input Handling이 "Input System Package (New)"만이면 플레이어 빌드에서 OnGUI가 렌더링되지 않음**
- **해결**: Project Settings > Player > Other Settings > Configuration > Active Input Handling = **Both** (에디터 재시작)
- **예방**: DevConnectionHud를 정식 uGUI로 교체하면 원복 검토

### T-10. HUD에 웹페이지 주소를 넣어 접속 실패
- **증상**: Connect 무반응
- **원인**: 웹페이지 http 포트(예: 62385/8000)와 **게임 서버 포트(7777)** 혼동
- **해결**: 브라우저 주소창 = 웹페이지(localhost:8000), HUD Addr/Port = 게임 서버(127.0.0.1:7777)
- **예방**: 정식 구현에서는 world-sessions API가 endpoint를 내려주므로 수동 입력 자체가 사라짐

### T-13. Build And Run 포트가 매번 바뀌고 플랫폼에 묶임
- **증상**: 테스트 URL 고정 불가, Linux Server로 스위치하면 웹 서빙 불가
- **원인**: Build And Run은 에디터 임시 서버 (랜덤 포트, 에디터 종속)
- **해결**: Web Publishing Settings **Compression Format = Disabled** (개발용) 후 빌드 → `python -m http.server 8000 --directory Builds/web` → localhost:8000 고정
- **예방**: 빌드 산출물은 에디터와 무관하게 서빙 가능. 실배포는 Brotli + CloudFront 헤더로 복원 (deployment-handoff.md)

### T-17. `python -m http.server --directory`로 띄웠는데 404
- **증상**: 빌드 폴더에 index.html이 있는데도 브라우저가 404
- **원인**: PowerShell의 현재 위치가 달라 상대경로 `--directory Builds/web-...`가 엉뚱한 폴더를 가리킴
- **해결**: 대상 폴더로 `cd` 후 `python -m http.server <port>` (옵션 없이) 또는 절대경로 지정
- **예방**: 서버 실행 후 브라우저 접속 시 PowerShell에 요청 로그가 찍히는지로 정상 서빙 확인

### T-18. Sidekick 툴 등 에디터 창이 안 열림 (`Attempted to open unsupported window in cloned player systems`)
- **증상**: Synty 툴 창이 열리지 않고 `NullReferenceException` + 이어서 `Failed to load tool data`
- **원인**: **Multiplayer Play Mode의 가상 플레이어(Player 2/3)가 활성 상태**이면 MPPM이 복제 에디터에서 에디터 창 열기를 차단한다
- **해결**: Play 정지 → Window > Multiplayer > Multiplayer Play Mode → Player 2/3 **체크 해제** → **Unity 재시작**(부트스트랩이 이미 꼬였으면 필수)
- **예방**: 에디터 툴(Sidekick 등) 작업 시엔 가상 플레이어를 끈다. 멀티 테스트할 때만 켠다

### T-19. `WebAssembly streaming compilation failed` / Content-Encoding 에러
- **증상**: 브라우저에서 빌드 로드 실패
- **원인**: 빌드가 압축(Brotli/Gzip)돼 있는데 로컬 서버가 `Content-Encoding` 헤더를 안 보냄 (또는 반대)
- **해결**: Build Profiles > Web > Player Settings > Publishing Settings > **Compression Format = Disabled** 후 재빌드 (개발용). 실배포는 Brotli + CloudFront 헤더 설정
- **확인법**: `Builds/web/Build/`에 `.br`/`.gz` 확장자가 있으면 압축된 것
- **부가**: `Tools/serve.py` 사용 시 wasm MIME·캐시 문제도 함께 예방됨

### T-20. `LinkError: wasi_snapshot_preview1 / fd_sync` (Sidekick SQLite)
- **증상**: WebGL 빌드가 아예 로드되지 않음
- **원인**: Sidekick의 SQLite 플러그인이 요구하는 WASI 호출을 런타임이 제공하지 못함. **재빌드 후 정상 동작** — 정확한 트리거는 미확정 (스테일 빌드/캐시 가능성)
- **해결**: 재빌드 + 캐시 무시 새로고침으로 해소됨
- ⚠️ **판정 정정**: 이 에러를 근거로 "Sidekick 런타임은 WebGL 불가, Synty 폴더 삭제 필요"라고 결론 냈으나 **오판**이었다. 근거:
  - Synty 체인지로그 v1.0.2 *"Updated SQLite build targets to allow Web build targets"*
  - `sqlite3.c.meta`에 `WebGL: enabled: 1`
  - `DatabaseManager`는 플레이어 빌드에서 파일 I/O를 쓰지 않음 (TextAsset → `:memory:` Deserialize)
  - 실제로 Synty를 둔 채 WebGL 빌드 성공
- **교훈**: 에러 하나로 "플랫폼 미지원"을 단정하지 말 것. 벤더 문서·플러그인 메타·실제 재현을 교차 확인한다

### T-23. 코드를 고쳤는데 브라우저 결과가 그대로 / 옛 외형이 나옴
- **증상**: 에디터에선 새 기능이 되는데 브라우저는 이전 모습
- **원인**: **Web 빌드를 다시 하지 않음.** 브라우저는 빌드 산출물만 보므로 에디터 변경이 자동 반영되지 않는다
- **해결**: Build Profiles → Scene List에 Main 씬만 체크 → Build → `Builds/web` 덮어쓰기 → Ctrl+Shift+R
- **예방**: 빌드 전 씬 저장(`Ctrl+S`, 타이틀 `*` 없음) 확인. `Tools/serve.py`는 캐시를 차단하므로 새로고침만으로 반영됨

## 코드/에셋 규칙

### T-21. SerializeField 이름을 바꿨더니 Inspector 값이 전부 사라짐
- **증상**: ScriptableObject/프리팹에 입력해둔 값이 빈 값으로 초기화됨 (AvatarCatalog의 preset 코드 소실)
- **원인**: Unity 직렬화는 **필드 이름 기준**. `avatarCode` → `presetCode`로 리팩터링하면 기존 asset 데이터와 매칭이 끊긴다
- **해결**: `[FormerlySerializedAs("이전이름")]` 부착 (`using UnityEngine.Serialization;`)
- **예방**: 직렬화 필드 이름 변경 시 **항상** FormerlySerializedAs를 함께 붙인다. 이미 값이 날아갔다면 붙인 뒤 재입력

### T-24. 커스터마이징 Custom 버튼이 무반응 — 인코딩 길이 초과가 조용히 삼켜짐 (2026-08-12)
- **증상**: HUD의 Custom 버튼을 눌러도 아무 변화 없음. 에러도 안 보임. 서버(Docker)를 재빌드해도 동일
- **원인**: `AvatarAppearance.Encode()`가 500자 초과 시 **조용히 `sk_01`을 반환**하도록 되어 있었음. Sidekick 파츠 이름이 길어(파츠당 ~25자 × 16종) 런타임 조립 인코딩이 500자를 넘으면, 서버에 "현재와 같은 값"이 전송되어 OnValueChanged가 발화하지 않음 → 완전한 무반응
- **해결**:
  1. 동기화 필드를 `FixedString512Bytes` → **`FixedString4096Bytes`**로 확대, `MaxEncodedLength` 500 → 3800
  2. Encode의 몰래 되돌리기 제거 — 초과 판단은 호출자(RequestChange)가 하고 거부 사유를 `LastRequestError`로 노출
  3. HUD가 `LastRequestError`를 **화면에 표시** (콘솔을 안 봐도 원인이 보이게)
  4. `SyncMirrorParts`의 이름 치환 실패 시 인덱스 매칭 폴백 (오른팔/오른다리 소실 방지)
- **주의**: NetworkVariable **타입이 바뀌었으므로 Web 빌드와 Linux Server(Docker) 빌드를 반드시 둘 다 다시** 해야 한다 (한쪽만 바꾸면 직렬화 불일치)
- **교훈**: 실패를 조용히 기본값으로 대체하는 코드는 "무반응 버그"가 된다. 거부/실패는 반드시 사용자 또는 로그에 드러낸다

#### T-24 후속 — "클라만 새 빌드, 서버는 옛 빌드"의 함정
- **증상**: 클라 로그에는 `[MockUserApi] 아바타 저장(모의): rt|1=SK_HUMN...`처럼 **긴 인코딩이 정상 생성**되는데, `[AvatarVisual] 적용`은 계속 `runtime=False`
- **판독법**: 이 조합은 "클라는 새 코드 / 서버는 옛 코드"의 지문이다
  - 클라(새 코드)는 600자 인코딩을 만들어 RPC 전송 ✅
  - 서버(옛 코드)의 `RequestChangeServerRpc`가 `Decode(...).Encode()`로 재인코딩 → 옛 500자 제한에 걸려 **`sk_01` 반환** → 현재 값과 동일 → `OnValueChanged` 미발화 → 화면 무변화
- **해결**: Linux Server 빌드 → 이미지 재빌드 → 컨테이너 교체 (Web 빌드와 **항상 쌍으로**)
- **재발 방지 (코드에 반영)**:
  1. 서버 RPC에서 **재인코딩 제거** — 길이 검증 후 받은 값을 그대로 기록
  2. 클라가 요청 후 2초 내 반영이 없으면 HUD에 `server did not apply the change — 서버(Docker) 빌드가 최신인지 확인` 표시
- **서버 로그 확인법**: 브라우저 콘솔에는 서버 로그가 안 나온다. `docker logs -f festa-world`로 `[Appearance] 서버 반영: client=.. len=..`이 찍히는지 본다 (안 찍히면 서버가 옛 빌드)

### T-25. 서버를 새로 빌드했는데 계속 옛 동작 — 이름 다른 옛 컨테이너가 포트를 점유 (2026-08-12)
- **증상**: Linux Server 재빌드·이미지 재생성을 반복해도 서버 동작이 그대로. `docker run` 시 `Bind for 0.0.0.0:7777 failed: port is already allocated`, `docker rm -f festa-world` 는 `No such container`
- **원인**: 실제로 돌고 있는 컨테이너 이름이 **`festa-world-01`**(README 표기)인데 `festa-world`로 지우려 해서 제거 실패. 옛 컨테이너가 계속 7777을 점유한 채 **옛 코드로 응답**하고 있었다
- **해결**:
  ```powershell
  docker ps                                   # 실제 이름 확인
  ```

### T-26. Docker 빌드가 `chmod: cannot access '/app/festa-unity.x86_64'`로 실패 (2026-08-12)
- **증상**: `[6/6] RUN chmod +x /app/festa-unity.x86_64` 단계에서 no such file. 로그의 `transferring context: 3.57kB`가 단서
- **원인**: **빌드 컨텍스트를 `Docker/` 폴더로 지정**했다. 이 Dockerfile은 `COPY . /app`으로 컨텍스트 전체를 복사하므로 컨텍스트가 **Linux Server 빌드 출력 폴더**여야 한다
- **해결**: `docker build -t festa-world:dev -f Docker/Dockerfile Builds/linux-server` (festa-unity 폴더에서 실행)
- **판별법**: `transferring context`가 수 KB면 실행 파일이 안 들어간 것 (정상은 수십~수백 MB)

### T-27. 파츠를 바꾸면 캐릭터가 T포즈로 굳는다 (2026-08-12)
- **증상**: Custom 모드로 파츠를 조립하면 외형은 정상인데 애니메이션이 전혀 재생되지 않고 T포즈. 프리셋 모드에서는 정상
- **원인**: Sidekick `SidekickRuntime.CreateCharacter()`는 생성한 캐릭터에 Animator를 붙이고 **avatar(휴머노이드 정의)까지 복사**하지만, `runtimeAnimatorController`는 **생성자에 넘긴 컨트롤러가 있을 때만** 설정한다.
  ```csharp
  // Synty 원본 (SidekickRuntime.cs)
  Animator newModelAnimator = newSpawn.AddComponent<Animator>();
  newModelAnimator.avatar = baseModelAnimator.avatar;
  newModelAnimator.Rebind();
  if (_currentAnimationController != null)          // ← 우리는 null로 생성했다
      newModelAnimator.runtimeAnimatorController = _currentAnimationController;
  ```
  우리는 `new SidekickRuntime(baseModel, material, null, _db)`로 만들었으므로 **Controller가 비어 있는 Animator**가 생성된다 → 재생할 상태 머신이 없어 바인드 포즈(T포즈) 그대로 멈춘다
- **해결**:
  1. `PlayerAvatarVisual`의 인스펙터 슬롯 **Animator Controller에 `AvatarAnimator` 할당** (근본 해결)
  2. 코드: 슬롯이 비어 있으면 **Player 루트 Animator의 Controller를 폴백**으로 사용하고, 그것도 없으면 콘솔에 원인을 명시
- **확인 사항**: 애니메이션 FBX(Idle/Walking)의 **Rig가 Humanoid**여야 리타게팅된다. Generic이면 다른 스켈레톤에 적용되지 않는다. Animator 인스펙터의 `Clip Count: 0`은 컨트롤러에 클립이 없다는 신호
- **교훈**: 외부 SDK가 컴포넌트를 "붙여준다"고 해서 **설정까지 채워주는 건 아니다**. 생성 직후 상태를 확인하고 부족분을 우리 코드가 메운다

### T-28. Codex 첨부 한글 작업지시가 깨져 보임 (2026-08-13)
- **증상**: `Get-Content`로 첨부된 작업지시를 읽으면 한글이 `?덈뒗` 같은 문자로 깨지고, 여러 문서를 한 번에 읽는 조회가 응답 없이 멈춤

- **예방**: 한글 문서는 처음부터 UTF-8을 명시해 읽고, 긴 문서는 필요한 파일별로 나눠 출력한다

### T-62. 얼굴형에 포함된 눈·입술을 별도 탭으로 분리해 색상 대상이 불명확해짐 (2026-08-14)

### T-70. 외형 전체 재조립 직후 QA 렌더에 머리가 중복 표시됨 (2026-08-14)

- **예방**: MCP 시각 QA에서 대상 없는 `Camera.Render()`를 호출하지 않고 일반 Game View 캡처 또는 명시적 `RenderTexture`를 사용한다.

### T-76. 입술 색상 마스크가 중앙의 얇은 부분만 덮음 (2026-08-14)
- **증상**: 입술색을 변경해도 위·아래 입술 전체가 아니라 입 중앙의 가느다란 부분만 어둡게 변했다.
- **원인**: 여성·남성 얼굴 텍스처의 실제 입술 UV는 세로 약 `0.238~0.293`인데, 기존 위·아래 타원 마스크의 세로 반경이 각각 `0.0048`, `0.0043`에 불과했고 디테일 임계값도 지나치게 높아 가장 어두운 중심부만 통과했다.
- **해결**: 위·아래 입술의 전체 UV 섬을 덮는 범위로 중심과 반경을 재측정하고, 얼굴 RGB 디테일의 낮은 대비까지 포함하도록 임계값을 조정해 실제 입술 윤곽 전체를 채색했다.
- **예방**: 절차 마스크는 화면 추측으로 반경을 정하지 않고 원본 텍스처 픽셀 범위와 강한 시험색·기본색 렌더를 함께 검증한다.

### T-77. 입술 전체 절차 마스크가 원본보다 진한 립스틱처럼 보임 (2026-08-14)
- **증상**: 입술 전체 UV를 덮도록 확장한 뒤에는 색상 경계는 맞았지만 캐릭터의 위·아래 입술이 뭉친 진한 립스틱처럼 보여 원본 얼굴 인상과 달라졌다.
- **원인**: 원본 셰이더의 복합 얼굴 색상 처리를 단일 색상 절차 마스크로 대체하면서 입술의 미세 명암과 피부색 혼합을 잃었다.
- **해결**: 사용자 요구에 따라 입술색 조절을 UI와 렌더 경로에서 제거하고, 얼굴 디테일 텍스처와 내부 입 재질의 기본 표현만 유지했다. 문자열 슬롯은 이전 데이터 파싱 호환을 위해 예약 상태로 남겼다.
- **예방**: 얼굴처럼 인상 변화가 큰 영역은 색상 슬롯 추가 전에 원본 셰이더가 제공하는 마스크·명암 구조를 완전히 재현할 수 있는지 확인하고, 불가능하면 원본 표현을 우선한다.

### T-78. 근접 입술 QA에서 카메라 거리 가정이 모델 스케일과 맞지 않음 (2026-08-14)
- **증상**: 얼굴 프리셋 거리와 첫 위치 지정 캡처가 기대보다 멀어 입술 상태를 판독하기 어려웠다.
- **원인**: 조립 캐릭터의 실제 월드 스케일보다 큰 거리 값을 사용했고 런타임 카메라의 보간 목표와 직접 지정 위치가 연속으로 바뀌었다.
- **해결**: 미리보기 카메라의 실제 FOV와 현재 위치를 조회하고 더 가까운 명시적 위치에서 UI 제외 근접 렌더를 촬영한 뒤, 일반 Game View에서 최종 패널 상태를 별도로 확인했다.
- **예방**: 얼굴 디테일 QA는 모델 바운드·카메라 FOV를 먼저 확인하고 근접 렌더와 전체 UI 검증을 각각 독립 캡처한다.

### T-79. 강한 입술 시험색 검증에서 전체 재조립으로 얼굴이 중복됨 (2026-08-14)
