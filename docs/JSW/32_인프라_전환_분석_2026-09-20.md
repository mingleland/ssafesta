현재 정본은 `docs/infra/canonical/`이며, 이 문서의 “현재”, “미완료”, “다음 작업” 표현보다 우선한다.

### 반드시 바로잡아 읽을 항목

| 이 문서의 과거 서술 | 2026-09-21 현재 정본 |
|---|---|

| Runner 확장·lane 분리를 추가 검토 | `concurrent=4`, 단일 호스트·단일 Runner가 최종값. c=5는 한계 초과 |
| Docker 이미지가 retention 5보다 많으면 쓰레기 | state·receipt·current·known-good·rollback 참조 이미지는 정상 보호 대상 |

### 이 문서에서 계속 유효한 내용

- 수동 컨테이너와 canonical Compose 컨테이너의 이름·소유권 차이
- 파일의 env와 실행 중 컨테이너 env가 자동 동기화되지 않는다는 설명
- Jenkins credential과 호스트 secret 파일이 서로 다른 입력일 수 있다는 실측
- Demo/Production의 포트·DB·Redis·domain을 섞으면 안 된다는 원칙
- `docker exec ... psql`의 Unix socket 성공이 TCP 비밀번호 검증은 아니라는 설명
- 배포 state가 deploy agent의 named volume에 있다는 관찰

### 현재 공식 carry-forward는 네 건뿐이다

1. 실제 GitLab provenance Unity 번들 입고 시 canonical gate 1회 확인
2. 다음 Production 승격 때 AI/Back stale·dead env 키 제거
3. Production Gate G에서 Human Gate 대기 중 deploy executor 해제 실측
4. 당첨 인원·시각 확정 뒤 raffle 경품 manifest 반영 및 provisioning

Redis AOF·ACL, readonly role, EC2 drift 등 이 문서의 추가 관찰은 **공식 미완료 목록이 아니다.**
재현 가능한 최신 증거가 있을 때만 새 Jira 이슈 후보로 올리고, Batch 1~3을 다시 여는 근거로 쓰지 않는다.

## 0. 한 문단 요약

이번 변경의 본질은 "환경이 둘에서 셋이 됐다"가 아니라 **"배포가 사람 손에서 상태기계로 넘어갔다"**이다.
예전에는 사람이 `docker run`·`docker compose up`을 직접 쳤고, 어떤 이미지가 어디 올라가 있는지는
`docker ps`로 눈으로 확인하는 것이 전부였다. 지금은 Demo가 Jenkins 자동 배포로 고정되고,
Production은 receipt(영수증) → 검증 → maintenance → 교체 → 공개 검증 → 사람 승인이라는
상태 전이를 거치지 않으면 손으로 띄울 수 없게 막혀 있다.

그리고 **2026-09-18에 만든 `ssafesta.world` 조기 오픈(C-14)은 공식 폐기됐다.**
대신 Production 전용 런타임이 별도로 생겼다. 자세한 건 9장.

### 2.1 지금의 정본 배치

| demo | Back | `festa-demo-back-1` | `127.0.0.1:18081 → 8080` | `festa-demo-ai-back-private` |

출처: `infra/deploy/compose/production/compose.yaml`, `infra/environments/compose/demo/*.yaml`.

### 2.2 컨테이너 이름이 헷갈렸던 이유

이름 규약이 **두 시대에 걸쳐 섞여 있다.**

- 수동 시대: `docker run --name festa-demo-back` → 접미사 없음
- Compose 시대: 프로젝트명 + 서비스명 + 인덱스 → `festa-demo-back-1`

`27_Backend_CD_작업_가이드.md`는 아직 **접미사 없는 옛 이름**으로 쓰여 있다.
그 문서를 그대로 따라 치면 `No such container`가 난다. 문서와 현실이 갈린 지점이다.

또 하나 — EC2에는 **도커 데몬이 두 개** 있다.

- Rootful `/var/run/docker.sock` — 실제 서비스 컨테이너
- Rootless `/run/user/1000/docker.sock` — Jenkins agent가 이미지를 굽는 곳

이미지는 rootless에서 구워져 rootful로 `transfer-local-images.sh`가 옮긴다.
`sudo docker images`에 안 보이면 아직 안 옮겨진 것이지 빌드가 실패한 게 아니다.

### 2.3 Production은 DB 인스턴스를 공유하되 논리적으로 격리한다

물리 PostgreSQL·Redis 컨테이너는 demo와 **같은 것**을 쓴다(`festa-data-private` 외부 네트워크).
하지만 데이터베이스와 계정은 완전히 갈라진다.

| 용도 | Production | Demo |
|---|---|---|
| Back DB / role | `festa_prod_business` / `festa_prod_back_app` | `festa_demo_business` / `festa_demo_back_app` |
| AI DB / role | `festa_prod_ai` / `festa_prod_ai_app` | `festa_demo_ai` / `festa_demo_ai_app` |
| Redis 사용자 | `prod_back` (`~prod:*`), `prod_ai` (`~prod:ai:*` + `~conversation:*`) | `demo_back` (`~demo:*`), `demo_ai` (`~demo:ai:*`) |

Production 초기화는 demo 데이터를 **복사하지 않는다**
(`bootstrap-production-data.sh`가 `bootstrapMode=fresh-isolated`, `demoDataCopied=false` 기록).
즉 2026-09-18에 논의했던 "A안 = demo DB 공유"는 **채택되지 않았다.** 완전 분리가 확정이다.

이 때문에 Production에서 이벤트 상점 상품이 비어 보이는 사고가 났다(T-167).
카탈로그성 데이터는 Flyway가 아니라 사람이 관리자 API로 넣은 운영 데이터였기 때문이다.

### 3.1 현재 매핑 (ROOT_DOMAIN=ssafesta.world 기준)

| `api.ssafesta.world` | 전부 | `127.0.0.1:18081` (**Demo Back**) | `api.conf.template` (미변경) |

### 3.2 가장 중요한 변화 두 가지

**1) `demo.conf.template`의 `location /`가 `$http_upgrade`로 분기한다.**

예전엔 무조건 Front(18080)로 갔다. 지금은 `map` 두 개로 갈린다.

```nginx
map $http_upgrade $festa_demo_root_upstream {
    default   http://127.0.0.1:18080;
    websocket http://127.0.0.1:17777;
}
```

이유: Unity의 `UnityTransport`는 host:port만 받고 **항상 루트 경로로 Upgrade**한다.
경로 분기(`/world/` 같은 것)를 못 쓰므로, 같은 호스트에서 프로토콜로 가르는 수밖에 없다.

**2) Production Front는 same-origin이다.**

demo Front는 `PUBLIC_API_BASE_URL=https://api.ssafesta.world`로 **다른 호스트**를 부른다.
Production Front는 `PUBLIC_API_BASE_URL`이 root domain 자기 자신이다.
그래서 Production에는 `/api/`, `/oauth2/`, `/login/oauth2/` location이 새로 필요했다.

### 3.3 아직 안 고쳐진 것

`api.conf.template`은 이번에 손대지 않았다. `api.ssafesta.world`는 여전히 **Demo Back(18081)** 으로 간다.
Production이 same-origin이라 당장 문제는 없지만, 이름만 보면 프로덕션 API처럼 보이는 함정이다.

## 4. `develop` push가 하는 일 — 이전 → 현재

### 4.1 결론

**`develop` push는 지금도 demo까지 자동 배포한다.** 바뀐 것은 "얼마나 많이"다.

근거: `infra/jenkins/pipelines/develop.groovy:178` 의 `FESTA_DEPLOY_ENVIRONMENT=demo`.

### 4.2 흐름 대조

| 단계 | 예전 | 지금 |
|---|---|---|
| base 선택 | `GIT_BEFORE_SHA` → previous | 동일 |
| 판정 | components / deployComponents | **4축** (5장) |

## 5. 컴포넌트 판정 — 2축에서 4축으로

### 5.1 출력 축

| 필드 | 뜻 | 예전 |
|---|---|---|
| `validationComponents` | CI 검증 범위 | (없음) |
| `buildComponents` | 이미지·Unity artifact 생성 범위 | (없음) |
| `deployComponents` | demo 런타임 변경 범위 | 있었음 |
| `components` | 하위호환 별칭 = `validationComponents` | 배포 대상이었음 |
| `gameBuildRequired` | Unity full build 필요 여부 | (없음) |
| `sharedCiChanged` / `runtimeSharedChanged` | 공용 변경 종류 | (없음) |

**함정**: `components`는 더 이상 배포 대상이 아니다. CI 변경이면
`components=[ai,back,front,game]`이면서 `deployComponents=[]`일 수 있다.

### 5.2 경로별 판정

| 변경 경로 | validation | build | deploy |
|---|---|---|---|
| `festa-ai/**` / `backend/**` / `festa-frontend/**` | 해당 1종 | 해당 1종 | 해당 1종 |
| `festa-unity/**`, `infra/unity-server/**` | game | game | game |
| `infra/environments/compose/demo/{ai,back,front}.yaml` | 해당 1종 | 해당 1종 | 해당 1종 |
| **runtime-shared** (demo base compose, demo manifest, deploy/verify-environment, preflight, `infra/versions.env`, `.dockerignore`, package-local-image) | 4종 | 앱 3종 | 앱 3종 |
| **ci-only-shared** (`Jenkinsfile`, `.gitlab-ci.yml`, `ci/**`, `infra/jenkins/**`, `infra/deploy/scripts/**`) | 4종 | 없음 | 없음 |
| **validation-only** (`infra/**/tests/**`, `compose/dev/**`) | 없음 | 보통 없음 | 없음 |
| `docs/**`, `specs/**`, `infra/evidence/**` | 없음 | 없음 | 없음 |
| **미분류** | **실패** | 실패 | 실패 (fail-closed) |

### 5.3 예전 대비 실질 차이

예전에는 `infra/deploy/**`, `infra/environments/**`, `infra/tests/**`가 광범위하게 shared로 잡혀
**네 컴포넌트를 전부 full build하면서 배포는 비우는** 비효율이 있었다.
지금은 CI 변경은 검증만, runtime 공용 변경만 재빌드·재배포한다.

**fail-closed 주의**: `infra/environments/compose/demo/` 아래에 임의 파일을 새로 만들면
미분류로 판정돼 파이프라인이 죽는다. 분류표(`detect-changed-components.sh`)를 같이 고쳐야 한다.

## 6. Unity / WebGL / World — 수동에서 자동으로

### 6.1 예전

1. Unity 담당자가 로컬 Editor로 Release Build (약 40분)
2. 임의 release ID로 zip 수동 업로드
3. 업로더가 `festa-webgl-package-deploy` job 호출
4. WebGL만 배포. Dedicated Server는 **완전히 별개 경로**

이 분리가 2026-09-17 사고의 원인이었다 — WebGL과 서버 프리팹이 어긋난 채 배포됐다.

### 6.2 지금

1. develop merge → `gameBuildRequired` 판정
2. `resolve-game-artifacts.sh`가 Registry·로컬 상태로 5분기 결정
   - `SKIP_TO_DEPLOY` / `PUBLISH_WEBGL` / `PUBLISH_WORLD` / `PUBLISH_BOTH` / `BUILD_REQUIRED`
   - 한쪽만 Registry에 있고 로컬로 못 채우면 `PARTIAL_REGISTRY` → **exit 65로 정지**
3. 필요하면 Unity agent에서 **한 checkout, 두 세션**으로 WebGL → Linux Server 순차 빌드
   - preflight: 라이선스 79 / LFS pointer 78 / dirty checkout 65
4. deploy agent가 SCM identity gate 통과 후 게시
   - `festa-webgl/<8sha>`, `festa-world/<8sha>` (**버전 = source SHA 앞 8자**)
   - 같은 version + 같은 SHA → `*_RELEASE_EXISTS` (exit 0)
   - 같은 version + 다른 SHA → **exit 65 하드 페일**
5. World candidate → readiness → WebGL `current` 전환 → World promote

### 6.3 핵심 안전장치

- **prefab tree 해시 대조**: WebGL과 World의 `festa-unity/Assets/_Project/Prefabs` 트리 해시가
  같아야 한다. 다르면 `deploy-game.sh`가 exit 75로 **건너뛴다**(운영 월드 보존).
- **SCM identity gate**: `check-game-source-identity.sh`가 commit이 origin에 존재하고
  `origin/develop` 조상인지 강제. 로컬에만 있는 커밋으로 빌드한 artifact는 승격 불가(T-170).
- **라이선스 preflight**: `festa-unity/ci/preflight-license`가 Unity 실행 전 2초 만에 검사하고
  실패하면 exit 79. 45분 기다렸다가 죽는 일이 없어졌다(T-169).
- `festa-world-package-publish` job은 **정상 경로가 아니다**. HISTORICAL/FALLBACK 전용.

## 7. Production 승격 — 없던 것이 상태기계로

### 7.1 스크립트 12종

### 7.2 상태 전이 (실제 pipeline 순서)

```
receipt 검증 → [사람 승인] → MAINTENANCE_ACTIVE → legacy 제거 + canonical 기동
  → RUNNING_UNVERIFIED → VERIFIED → CURRENT(공개) → EXTERNAL_VERIFIED
  → [사람 승인] → KNOWN_GOOD
```

**CURRENT ≠ KNOWN_GOOD.** CURRENT는 "공개됐다", KNOWN_GOOD은 "사람이 보고 괜찮다고 했다"이다.
롤백 기준선은 KNOWN_GOOD이다.

### 7.3 최초 전환의 특수 규칙 (C-16)

첫 canonical migration에는 `previous`가 없다. 실패하면 **maintenance 503을 유지하고
깨진 legacy를 복원하지 않는다.** 이건 의도된 설계다 — 깨진 것으로 되돌아가느니 닫아두는 쪽.

### 7.4 상태 파일 위치

```
/var/lib/festa-environments/production/
  receipts/<id>.json                      승격 영수증 (입력)
  data/bootstrap.json                     DB/Redis 준비 증거
  cutovers/<id>.prepare.json              maintenance 증거
  candidates/...                          candidate 상태
  current.json / known-good.json / previous.json
/srv/festa/webgl/prod/{candidate,current,previous}
```

## 8. Demo DB 조회 — 계정 안 주고 보기

`festa_demo_readonly` role이 생겼다 (infra-002 T014A).

- `festa_demo_business`, `festa_demo_ai` **SELECT만**
- **비밀번호 없음** → host 경로(`scram-sha-256`)로는 로그인 불가, 컨테이너 내부 unix socket 전용

```bash
sudo docker exec -i festa-data-postgres-1 \
  psql -U festa_demo_readonly -d festa_demo_business -c '\dt'
```

이게 만들어진 이유: PostgreSQL은 호스트 포트가 없어서 계정을 넘겨도 얻는 건 DB 접속이 아니라
**호스트 루트**다. 그래서 조회 대행 role로 대신한다.

> 곁가지로 알아둘 것: 컨테이너 내부 unix socket은 `trust`라 **비밀번호 없이 붙는다.**
> 그래서 `docker exec ... psql -U festa_demo_back_app`이 성공해도
> 그게 "비밀번호가 맞다"는 증거가 아니다. 앱은 TCP(`host ... scram-sha-256`)로 붙기 때문이다.
> 이 차이가 2026-09-19 Postgres 인증 실패를 오래 끌게 만든 원인이었다.

## 10. 다음에 인프라를 만질 때 기억할 것

1. **compose를 손으로 부르지 마라.** `RELEASE_ID`, `SOURCE_COMMIT`, `COMPONENT_IMAGE_REF`,
   `COMPONENT_ENV_FILE`은 `deploy-environment.sh`가 export하는 값이다.
   사람이 직접 `docker compose up`을 치면 `required variable ... is missing`으로 죽는다.
2. **같은 키가 여러 곳에 있으면 compose `environment:` 블록이 이긴다.** `env_file`보다 우선한다.
   `WORLD_HOST` 사고가 정확히 이것이었다.
3. **EC2에서 템플릿을 쓰려면 먼저 `git pull`** 해야 한다. 저장소에 파일이 있어도
   EC2 체크아웃이 낡으면 없는 파일이다.
4. **이미지 태그는 커밋 SHA다.** "최신 이미지"가 내 화면 변경을 담고 있다는 보장이 없다.
   인프라 커밋으로도 프론트 이미지는 다시 구워진다.
5. **Demo는 Jenkins가 소유한다.** 손으로 고쳐도 다음 develop push가 덮는다.
6. **`docker exec psql` 성공은 비밀번호 증명이 아니다.** unix socket은 trust다.

### 12.4 Redis AOF 복원이 재시작마다 일부 실패한다 (신규 발견)

Redis는 `2026-09-20T03:45:06Z`(12:45 KST)에 재시작됐다. ACL 파일 mtime과 같은 초라
`prod_back`·`prod_ai` 규칙은 정상 로드됐다. 그런데 그 직후 로그에 이게 16줄 찍혔다.

```
# == CRITICAL == This server is sending an error to its AOF-loading-client:
'-NOPERM ACLs rules changed between the moment the transaction was accumulated
 and the EXEC call. This command is no longer allowed ...' after processing 'exec'
```

**AOF 재생 중 MULTI/EXEC 트랜잭션 16건이 권한 부족으로 거절됐다. 그만큼 복원되지 않았다.**

원인 구조:

1. `infra/environments/redis/redis.conf`가 `appendonly yes` (infra-001 T022G)
2. ACL 파일 첫 줄이 `user default off`
3. Redis의 AOF-loading client는 `default` 사용자 컨텍스트로 동작한다
4. 개별 명령은 통과하지만 `EXEC`는 큐에 쌓인 명령의 ACL을 **다시 검사**한다
5. `default`가 off이므로 모든 트랜잭션이 NOPERM으로 거절된다

**이건 1회성 사고가 아니라 재시작할 때마다 반복되는 구조다.**
Redis에 MULTI/EXEC으로 쓰는 주체(Spring Session, 대화 저장 등)의 최근 쓰기가
재시작마다 소실된다. 사용자 입장에서는 "재시작하면 로그인이 풀린다"로 보인다.

이번 재시작은 `bootstrap-production-data.sh`가 Redis ACL을 적용하려고 한 것이므로,
**Production bootstrap이 demo Redis 데이터 일부를 날린 셈**이다.

실용적 회피책 (근본 수정 전):

```bash
# 재시작 직전에 AOF를 rewrite 하면 트랜잭션 블록이 평탄화되어 문제가 사라진다
redis-cli ... BGREWRITEAOF
```

근본 해법은 셋 중 하나이고 셋 다 명세 결정이 필요하다.

- `default` 사용자를 AOF 재생용으로만 살리고 네트워크로 격리
- AOF 대신 RDB 스냅숏
- 재시작 전 `BGREWRITEAOF`를 배포 절차에 명문화

명세·트러블슈팅 어디에도 이 항목이 없다.

### 12.5 `prod_ai`에 `+@connection`이 빠졌다 — demo에서 이미 물린 구멍

EC2의 실제 ACL을 나란히 놓으면 보인다.

```
demo_ai on ... ~demo:ai:* ~conversation:* +@read +@write +@connection -@dangerous +@scripting
prod_ai on ... ~prod:ai:* ~conversation:* +@read +@write             -@dangerous +@scripting
```

2026-09-16에 `NoPermissionError User demo_ai has no permissions to run the 'ping' command`로
AI 상담이 터져 `+@connection`을 넣었던 바로 그 자리다. **`prod_ai`에는 반영되지 않았다.**

게다가 저장소 `infra/environments/redis/users.acl.example`도 `prod_ai`에 `+@connection`이 없다.
**명세·코드·EC2 셋 다 같은 구멍이다.** demo에서 배운 것이 prod로 옮겨지지 않았다.

redis-py가 `health_check_interval`을 켜면 PING을 쓰므로 Production AI 대화가
어느 시점에 같은 오류로 끊길 수 있다.

### 12.6 `users.acl.example`이 EC2보다 낡았다

| | `demo_ai` 규칙 |
|---|---|
| EC2 실물 | `~demo:ai:* ~conversation:* ... +@connection ... +@scripting` |
| 저장소 example | `~demo:ai:* ... +@scripting` (`~conversation:*`·`+@connection` 없음) |

운영에서 고친 것이 저장소로 돌아오지 않았다. 다음에 ACL을 새로 만들면 퇴행한다.

### 12.7 비밀번호 표기가 환경별로 다르다

| 사용자 | 저장 방식 |
|---|---|
| `health`, `dev_*`, `demo_*` | `>평문` |
| `prod_back`, `prod_ai` | `#SHA-256 해시` |

`bootstrap-production-data.sh`가 hashed로 넣기 때문이다. Production만 해시라 보안 수준이
환경별로 다르고, 이 차이도 문서에 없다. dev/demo도 hashed로 통일하는 것이 맞다.
