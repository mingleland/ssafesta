# 운영 데이터 카탈로그와 수집 우선순위

> 관련 Jira: `S15P21A604-581`
> 기계 판독 정본: `infra/observability/signal-catalog.json`
> 검증기: `infra/observability/scripts/validate-signal-catalog.py`

## 1. 결론

새 분석 DB나 이벤트 웨어하우스는 만들지 않는다. 필요한 원천 대부분은 이미 PostgreSQL에 있고,
호스트·컨테이너 지표와 로그 수집 골격도 Alloy + Prometheus + Loki + Grafana로 존재한다.

지금 부족한 것은 세 가지다.

1. 준비된 관측 스택을 24~72시간 실제로 돌려 retention·자원 상한·임계치를 실측하는 일
2. PostgreSQL·Redis·공개 엔드포인트·백업·R2·World처럼 아직 Prometheus로 들어오지 않는 신호
3. 사용자 데이터 중 무엇을 집계할 수 있고 무엇을 절대 메트릭 label이나 로그에 넣지 않을지의 계약

`signal-catalog.json`은 이 셋을 `implemented`, `ready_on_demand`, `available`, `missing`으로 구분한다.
CI는 카탈로그의 필수 필드, 증거 경로, 개인정보 label 금지를 검사한다.

| 상태 | 뜻 |
|---|---|
| `implemented` | 서비스나 운영 흐름이 실제 원천을 기록·조회한다 |
| `ready_on_demand` | 코드는 준비됐지만 관측 스택이 상시 실행·실측되지는 않았다 |
| `available` | 원천 데이터/스크립트는 있으나 수집·대시보드 연결이 없다 |
| `missing` | 신뢰할 원천 또는 연속 수집 코드부터 없다 |

## 2. 데이터는 세 군데에만 둔다

| 성격 | 정본 | 용도 |
|---|---|---|
| 회원·부스·상담·설문·코인 같은 업무 상태 | PostgreSQL | 거래, 감사, 관리자 조회, 기간 집계 |
| CPU·메모리·연결 수·오류율 같은 수치 시계열 | Prometheus | 대시보드, 임계치, 용량 추세 |
| 장애 원문과 요청 상관관계 | Loki | 장애 조사. 저장 전 redaction |

같은 사실을 새 통계 테이블에 복사하지 않는다. 현재 규모에서는 기존 원천 표를 기간 조건으로
집계하는 편이 더 단순하고 정확하다. 실제 쿼리가 느려졌다는 측정이 생길 때만 사전 집계나 materialized
view를 검토한다. `booth_daily_metrics`가 있어도 현재 대시보드가 실시간 원천 집계를 쓰는 이유도 같다.

## 3. 지금 바로 필요한 운영 신호

### 이미 준비됐지만 상시 운영·실측이 안 된 것

- EC2 CPU·메모리·디스크·네트워크·PSI: Alloy unix exporter
- 컨테이너 CPU·메모리·네트워크: Alloy cAdvisor profile
- Docker 로그 수집과 Secret/PII redaction: Alloy → Loki
- Prometheus self metric과 Grafana host/component dashboard
- candidate/current/known-good/rollback과 source commit·image ref 릴리스 이력

이 항목은 새 도구를 설치하는 작업이 아니라 `infra/observability/BASELINE.md`의 빈칸을 실제 EC2
24~72시간 값으로 채우는 작업이다. 임계치와 보존기간을 먼저 추정해서 설정하지 않는다.

### 데이터는 있으나 수집기가 없는 것

| 우선순위 | 신호 | 현재 원천 | 다음 최소 구현 |
|---:|---|---|---|
| P0 | PostgreSQL 연결·lock·rollback·DB 크기 | `pg_stat_*` | Alloy postgres exporter |
| P0 | Redis 메모리·eviction·client·AOF | `INFO` | Alloy redis exporter와 read-only 자격증명 |
| P0 | 공개 HTTP/TLS, WSS 101 | 배포 검증 스크립트 | Alloy blackbox 또는 외부 probe |
| P0 | 백업 성공·마지막 성공 시각·복원 검증 | backup receipt | metric 변환과 age alert |
| P0 | R2 사용률·PUT/HEAD/CORS | collector/evaluator/probe | 15분 scheduler와 metric 출력 |
| P1 | GitLab/Jenkins duration·queue | 각 API | 배포와 무관한 read-only collector |
| P1 | Flyway 버전·실패 상태 | `flyway_schema_history` | 배포 증거 또는 DB exporter query |

PostgreSQL/Redis exporter는 새 독립 제품 컨테이너보다 Alloy 내장 component를 먼저 검토한다. 같은
역할의 `node_exporter`, 별도 cAdvisor, Promtail, Alertmanager를 중복 설치하지 않는다.

### 원천부터 없는 것

- 전체 EC2 장애 알림: 같은 EC2의 Grafana는 호스트가 죽으면 같이 죽는다. 외부 uptime monitor나
  CloudWatch heartbeat처럼 다른 실패 영역이 필요하다.
- World CCU·정원 초과 거절·비정상 disconnect: Dedicated Server가 집계 수치를 내보내야 한다.
- 정확한 DAU: 로그인 성공 또는 권위 있는 활동 이벤트가 없다. `users.created_at`을 DAU로 쓰면 안 된다.
- AI 대화 사용량·응답 결과: 대화 원천 표가 없어 `BoothDashboardService.aiUsages`도 `null`이다.
- HTTP route별 latency/error: Actuator health는 있지만 Prometheus registry/scrape endpoint는 없다.

없는 값을 `0`으로 내보내지 않는다. `0`은 측정했더니 0건이라는 뜻이고, 원천이 없다는 뜻은
`missing` 또는 `null`이다.

## 4. 운영자가 실제로 볼 사용자·서비스 데이터

모두 기존 PostgreSQL 원천에서 집계한다.

| 데이터셋 | 원천 | 권장 집계 |
|---|---|---|
| 가입·계정 상태 | `users`, `account_status_histories` | 상태별 회원 수, 정지·탈퇴 추이 |
| 로그인 제공자 | `oauth_identities` | provider별 인원 비율 |
| 부스 운영 | `booths`, `booth_leases`, published versions | 생성·공개·임대 상태 수 |
| 부스 방문 | `booth_visit_events` | 방문 수, 회원 unique, 닫힌 방문 평균 체류, 열린 방문 |
| 상담 | `consultations` | 요청·수락·종료 수, 종료된 상담 시간 |
| AI 문서 | `ai_document_jobs` | 상태·오류 코드·재시도 구간·처리시간 |
| 설문 | responses/answers/options | 참여·완료 수, 선택/평점 집계 |
| 미니게임 | `minigame_sessions` | 시작·완료·거절·보상 코인 |
| 경제 | `coin_ledger_entries`, reconciliation runs | 지급·사용·환불 사유별 합계, 불일치 수 |
| 이벤트 상점 | prizes/purchases | 구매·처리·취소·추첨 상태 |
| 피드백 | `feedback_submissions` | 접수 수, 최초 발견 판정 수 |

부스 방문·설문 결과는 이미 서비스 계층과 API가 집계한다. 이 값을 다시 별도 analytics API로
복제하지 않는다. 플랫폼 전체 운영 화면이 필요해질 때는 관리자 권한 아래 read-only 집계 query만
추가한다.

## 5. 개인정보 경계

### 원문 조회가 필요한 데이터

- 닉네임과 OAuth provider subject
- 상담 summary·message
- 설문 주관식 답변
- 피드백 본문
- 문서 원래 파일명·object key
- 홈페이지·프로젝트 URL

이 값은 PostgreSQL과 권한이 확인된 API에만 둔다. 사용자 요청 처리, 관리자 운영, 탈퇴 정리처럼
업무상 필요한 경우에만 원문을 읽는다.

### Prometheus label·Loki label에 금지하는 값

- `user_id`, nickname, email, phone, IP, user-agent
- request/trace/session ID
- token, document ID, original filename, object key

Prometheus label은 `environment`, `service`, `status`, `reason_type`처럼 종류 수가 제한된 값만 쓴다.
request ID는 장애 한 건을 찾는 Loki **본문 field**로만 유지하고 label로 승격하지 않는다. 그렇지
않으면 요청 수만큼 시계열/로그 stream이 생겨 저장소가 급증한다.

게스트 설문 식별자는 임시 세션 범위를 넘겨 보관하지 않는다. IP나 브라우저 fingerprint로 게스트를
추적해 DAU를 만들지 않는다.

## 6. 보존 원칙

- Prometheus/Loki 기간과 용량: `BASELINE.md` 실측 뒤 승인. Loki는 24시간 미만으로 두지 않는다.
- 업무 데이터: 각 도메인의 현재 삭제·탈퇴 계약을 따른다. 관측 편의를 이유로 별도 복사하지 않는다.
- 릴리스 이력: 최근 10개 + known-good가 참조하는 이력 보호.
- 관리자 감사와 코인 원장: 현재 업무 정본으로 유지한다. 대시보드가 원문을 복제하지 않는다.
- 원시 사용자 행동 로그를 무기한 보존하는 신규 저장소는 만들지 않는다.

법정 보존기간이나 개인정보 처리방침이 팀에서 확정되기 전에는 임의의 장기 보존 숫자를 코드에
박지 않는다.

## 7. 구현 순서

한 MR에 전부 넣지 않는다. 실패 영역과 자격증명이 다르므로 다음처럼 분리한다.

1. **현재 변경**: 신호 카탈로그 + privacy/cardinality 검증 + US5 acceptance 연결
2. **EC2 실측**: 관측 스택 24~72시간 실행, `BASELINE.md`와 resource/retention 승인값 확정
3. **무자격증명 probe**: 공개 HTTP/TLS/WSS와 외부 host-down 감시
4. **데이터 계층**: PostgreSQL/Redis exporter를 read-only credential로 연결
5. **데이터 보호**: Production DB 백업·pre-migration backup·복원 리허설
6. **스토리지 보호**: R2 evaluator 15분 실행, runtime upload gate, Grafana metric/alert
7. **애플리케이션 신호**: World CCU/disconnect, AI conversation event, HTTP route metric
8. **운영 화면**: 기존 표에서 필요한 플랫폼 aggregate만 read-only query로 제공

각 단계는 카탈로그의 `status`와 `evidence`를 같이 갱신한다. 코드가 있어도 실행·실측 증거가 없으면
`implemented`로 올리지 않는다.

## 8. 이번 범위에서 일부러 만들지 않은 것

- 새 analytics DB, Kafka, ClickHouse, Elasticsearch
- 사용자 행동 원문을 Prometheus/Loki로 복제하는 exporter
- 측정 없는 임의 alert threshold
- 기존 Alloy 기능과 겹치는 exporter/agent 컨테이너
- DAU와 AI 사용량의 가짜 대체값

필요성이 실제 부하·조회시간·운영 요구로 확인될 때만 추가한다.
