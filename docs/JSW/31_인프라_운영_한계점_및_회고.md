# 인프라 운영 한계점 및 회고 — JSW

> 프로젝트 진행 중 인프라 설계와 실제 팀 운영 사이의 괴리로 인해 발생했던
> 병목, 지연, 운영 실수들을 솔직하게 기록하고 재발 방지 교훈을 정리한 문서입니다.

---

## 1. 초기 브랜치 전략 소통 부재와 CI 장기 방치

- **상황 및 한계점**:
  - 초기 명세서(`infra-001`)에는 feature 브랜치 단위로 세분화된 CI 게이트를 설계했으나, 팀 전체가 `develop` 중심의 통합 흐름으로 작업하기로 합의한 맥락을 제대로 이해하지 못했다.
  - 파이프라인 생성 규칙(`workflow.rules`)이 실제 개발자들의 브랜치 명명이나 작업 흐름과 어긋나 있었음에도 이를 인프라 파트에서 능동적으로 파악하지 못해, **프로젝트 초기 수 주 동안 GitLab CI가 단 1회도 정상적으로 돌지 않고 방치**되었다.
  - 결국 개발 지연을 견디다 못한 타 파트 팀원(박준우 님 등)이 이슈(`#149`)를 제기하고 임시 게이트를 손수 구성해서야 비로소 CI가 굴러가기 시작했다.
- **교훈**:
  - 인프라 설계는 문서를 넘어 **"개발팀이 실제로 터미널에서 어떤 명령어로 브랜치를 파고 올리는가"**를 매일 관찰하고 즉각 피드백해야 한다. 혼자 문서만 붙잡고 있으면 현실과 완전히 단절된다.

## 2. 가상 `dev` 환경 설계 낭비와 수동 배포 고착화

- **상황 및 한계점**:
  - `dev.ssafesta.world`(개발환경 자동배포)와 `demo.ssafesta.world`(시연환경 승격배포)의 2단계 환경을 설계했으나, 실제로는 단일 EC2의 리소스 한계와 도메인/인증서 미비로 **`dev.ssafesta.world`는 단 한 번도 제대로 활용되지 못한 채 가상으로 겉돌았다**.
  - 젠킨스 자동 배포 파이프라인(`develop.groovy`)은 아무도 보지 않는 `dev` 배포를 향해 돌고 있었고, 팀원들이 실제 접속하고 검증해야 하는 `demo` 환경은 **인프라 담당자가 EC2에 들어가 일일이 손으로 `docker run`·`docker compose`를 치는 수동 배포만 주구장창 반복**했다.
  - 자동화 파이프라인이 라이브 서비스를 전혀 책임지지 못하는 반쪽짜리 구조가 수 주간 이어졌다.
- **교훈**:
  - 쓸 수 없는 다단계 환경을 이상적으로 늘려놓기보다, **"팀이 실제로 보고 있는 단 하나의 환경(demo)"**을 완벽하게 자동 배포하는 것이 100배 중요하다.

## 3. 긴급 규약(`#206`)의 반쪽 적용과 우회 브랜치 삽질 유발

- **상황 및 한계점**:
  - 백엔드 MR이 1회당 수 분씩 걸려 러너 2개 슬롯이 꽉 막히자, 각 파트 브랜치(`front`, `back`, `ai`, `game`)에 작업을 모아 한 번에 올리자는 긴급 규약(`#206`, `!933`)을 만들었다.
  - 하지만 파트 브랜치에서 모으는 것만 신경 쓰고, **정작 파트 브랜치에서 `develop`으로 최종 머지할 때 기존 브랜치명 정규식 제약(`feat/`, `fix/` 등)에 걸려 파이프라인이 0개로 뜨는 문제를 간과**했다.
  - `Pipelines must succeed`에 걸려 머지 버튼이 잠기자, 팀원들은 `chore/S15P21A604-xxx-front-to-develop` 같은 꼼수 우회 브랜치를 매번 새로 파서 코드를 복사해 올리는 극심한 피로와 시간 낭비를 겪어야 했다 (`!1026`, `!1033`, `!1055`).
- **교훈**:
  - 운영 규칙을 변경할 때는 시작부터 끝(파트 브랜치 생성 ➔ 취합 ➔ develop 최종 머지)까지의 **E2E 라이프사이클 전체를 시뮬레이션하고 검증**해야 한다.

## 4. 수동 배포 시 이미지 역행 및 502 서비스 중단 장애

- **상황 및 한계점**:
  - 자동 승격이 안 되어 수동 배포를 이어가던 중, "최신 이미지를 반영하라"는 요청을 받았음에도 호스트 도커 데몬의 이원화 구조(Rootful vs Rootless)와 태그 관리가 미숙했다.
  - 최신 이미지가 아닌 며칠 전 구버전(09-10 빌드) 이미지를 실수로 띄우거나, 컨테이너 환경변수 주입을 누락하여 **정상 동작하던 프론트엔드가 과거로 역행하고 연속 502 에러가 터지는 중대 장애를 유발**했다 (`#191`).
  - 원인을 빠르게 시인하지 못하고 환경 탓으로 돌리려다 팀의 신뢰를 잃을 뻔했다.
- **교훈**:
  - 수동 작업은 반드시 실수를 부른다. 불가피하게 수동 작업을 할 때는 `docker inspect`로 기존 컨테이너 스냅샷을 남기고 번들 해시와 헬스체크를 철저히 교차 검증해야 하며, 궁극적으로는 완전 자동화로 전환해야 한다.

## 5. 백엔드 CI 낭비 방치 (중복 스캔, 파이썬 설치, 캐시 부재)

- **상황 및 한계점**:
  - 백엔드 테스트가 353초(약 6분)나 걸려서 팀 전체가 대기하느라 고통받았는데, 분석해 보니 **진짜 테스트 코드는 84초**였고 인프라가 낭비한 시간이 1분 이상이었다.
  - `mr-status`가 이미 프로젝트 전체를 스캔했는데도, `.component-ci` 부모 템플릿에서 `secret-scan.sh --path .`를 무차별 중복 실행하여 **유니티 1GB 에셋까지 훑느라 매번 42초를 낭비**했다.
  - 메이븐/노드 도커 이미지에 파이썬이 없다는 이유로 `apt-get install python3`를 매번 돌려 16초를 버렸고, Maven 캐시(`.m2`)도 달아두지 않아 806개 의존성을 매번 인터넷에서 새로 받았다.
- **교훈**:
  - CI 파이프라인의 각 단계별 소요 시간(로그 타임스탬프)을 정기적으로 프로파일링하지 않고 방치한 것은 인프라의 명백한 태만이다.

## 6. WebGL ↔ 게임 서버 불일치 배포로 인한 클라이언트 즉사 사고

- **상황 및 한계점**:
  - WebGL 클라이언트는 수동 패키지 업로드 주기로 09-14 빌드를 바라보고 있는데, 젠킨스는 `develop`에 머지되자마자 리눅스 전용 게임 서버를 09-16 최신 코드로 혼자 배포해버렸다.
  - 클라이언트와 서버의 프리팹(NGO 네트워크 객체) 계보가 어긋나 브라우저에서 `RuntimeError: function signature mismatch`가 발생하며 **유저 월드 입장이 완전히 불가능해지는 장애**가 발생했다.
- **교훈 및 조치**:
  - 독립된 배포 주기를 가진 두 컴포넌트가 맞물릴 때는 반드시 **배포 전 정합성 검증 가드**가 있어야 한다. `deploy-game.sh`에 WebGL manifest의 sourceCommit과 서버 후보의 프리팹 트리 해시를 대조해 어긋나면 도커 호출 전에 안전하게 스킵(`exit 75 SKIP`)하는 가드를 추가하여 재발을 막았다.

## 종합 회고 및 향후 원칙

1. **현실을 반영하지 못하는 이상적인 설계는 부채다**: 스모크 러너 3시간 빌드, 미사용 dev 환경 등 현실성 없는 전제들을 과감히 쳐내고 단순하고 동작하는 구조(Ponytail 원칙)로 가야 한다.
2. **인프라 병목이 팀의 속도를 결정한다**: CI 실패, 45분 대기, 우회 브랜치 생성은 단순 불편이 아니라 프로젝트 전체의 마일스톤을 갉아먹는다.
3. **기록과 투명성이 신뢰를 만든다**: 실수와 한계를 숨기지 않고 팩트 기반으로 기록(작업일지, 트러블슈팅, 아키텍처 비교)하여 시스템으로 방어해야 한다.
