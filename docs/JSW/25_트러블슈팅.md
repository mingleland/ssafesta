### INFRA-T-111. WebGL 클라이언트와 전용 서버가 어긋난 채 이틀을 돌았다 — NGO 프리팹 색인 불일치 (2026-09-16, 해결)

- **증상**: demo 월드에 입장은 되는데 돌아다니다 브라우저가 죽었다. Unity 콘솔에 `RuntimeError: function signature mismatch` 와 `invoke_viii` · `dynCall_iiiji` 스택이 남았다. 서버 로그에는 아무 흔적이 없다.
- **원인**: 배포된 WebGL(`bf90136a`, 09-14 14:32 빌드)과 돌고 있던 전용 서버(`festa-world:85ae541f`, 09-12 커밋)의 `PlayerAvatar.prefab` 이 달랐다.

  | | 프리팹 컴포넌트 | 추가된 것 |
  | --- | --- | --- |
  | 서버 `85ae541f` | 13개 | — |
  | WebGL `bf90136a` | 15개 | `PlayerPostureCollider`(MonoBehaviour) · **`NappingStaffNetwork`(NetworkBehaviour)** |

  NGO 는 프리팹 위 NetworkBehaviour 를 **순서 인덱스**로 식별한다. 클라이언트에만 있는 NetworkBehaviour 가 하나 생기면서 그 지점 이후의 RPC 가 전부 다른 컴포넌트로 디스패치됐고, 잘못된 인덱스로 함수 포인터를 부른 결과가 wasm 트랩이다. 입장 직후가 아니라 **'자는 직원' NPC 근처에 가야** 터지는 것도 어긋난 것이 그 동기화이기 때문이다.
- **왜 이틀이나 몰랐나**: 게임팀이 09-14 인계에 "WebGL 과 전용 서버를 **반드시 같은 커밋**으로 동시 배포해달라, 낡은 서버 때문에 자는 직원 상호작용이 안 된다"고 **정확히 적어 뒀다.** 그 조건을 검사하는 장치가 배포 경로 어디에도 없어서 구두 요청으로만 남았다. WebGL 은 `festa-webgl-package-deploy` 로 앞으로 나갔는데 전용 서버에는 09-15 까지 배포 경로 자체가 없어 09-12 에 멈춰 있었다.
- **해결**:
  1. 응급 — 배포된 WebGL 과 `festa-unity/Assets/_Project/Prefabs` 트리 해시가 **같은** 이미지를 골라 올렸다. 60개 `festa-game:<SHA>` 중 8개가 일치했고, `festa-unity/` 전체에서 WebGL 커밋과 한 줄(`Docker/README.md` 의 CI 트리거 주석)만 다른 `festa-game:48c8e390` 을 썼다. 크래시가 멎었다.
  2. 재발 방지 — `deploy-game.sh` 가 교체 **전에** `/srv/festa/webgl/current/manifest.json` 의 `sourceCommit` 을 읽어 후보와 프리팹 트리 해시를 대조하고, 어긋나면 `exit 75` 로 건너뛴다. docker 를 부르기 전이라 **돌고 있는 컨테이너는 손도 타지 않는다.** `develop.groovy` 는 75 를 실패가 아닌 `NOT_BUILT` 로 처리한다.
- **커밋 SHA 로 대조하지 않은 이유**: 문서·인프라 커밋도 SHA 는 달라진다. 그렇게 짜면 게임 배포가 영영 나가지 못하고, 결국 사람이 검사를 꺼 버린다. 실제로 복구에 쓴 `48c8e390` 도 커밋은 다르지만 프리팹은 같다. 색인을 결정하는 것은 프리팹이므로 프리팹 트리만 본다.
- **한계**: 프리팹을 건드리지 않고 RPC 시그니처만 바꾸는 변경은 이 검사로 잡지 못한다. 그 부류가 실제로 나오면 그때 대조 범위를 넓힌다.
- **검증**: 사고의 실제 커밋 셋으로 회귀 시험을 넣었다(`tests/integration/game-webgl-prefab-guard.sh`). ① `85ae541f` 후보 → `exit 75`, docker 미도달, candidate 미기록 ② `48c8e390` 후보(커밋 다름·프리팹 같음) → 통과 ③ WebGL 미배포 → 검사 비활성. 통과만 보고 넘기지 않으려고 docker 를 부르면 97 로 죽는 stub 을 PATH 에 심어 판정이 docker 앞에서 끝나는 것까지 확인했다.
- **예방**:
  - 짝을 맞춰 움직여야 하는 산출물은 **한쪽만 자동화하지 않는다.** 자동화가 한쪽만 밀면 배포가 성공할수록 어긋난다.
  - 타 파트가 "반드시 같이" 라고 말한 조건은 회신으로 끝내지 말고 그날 안에 검사로 옮긴다. 구두 조건은 다음 사람에게 전달되지 않는다.
  - 운영 중인 대상을 교체하는 스크립트는 **거부 판정을 교체보다 앞에** 둔다. 뒤에 두면 "검사 실패 = 이미 망가진 뒤" 가 된다.

### INFRA-T-112. demo AI 가 dev 백엔드를 호출하고 외부망·R2 버킷이 어긋나 문서 처리가 전량 실패 (2026-09-16, 해결)

- **증상**: demo 부스의 AI 직원 근거 문서가 `QUEUED` 에서 넘어가지 않았고, `POST https://demo.ssafesta.world/ai/v1/conversations` 는 405 였다. AI 로그에 `BOOTH_ACCESS_CHECK_FAILED` 와 `spring_failure_callback_undelivered` 가 1 분 주기로 반복됐다.
- **원인**: 네 가지가 겹쳐 있었고, 하나를 고칠 때마다 다음 것이 드러났다.
  1. `festa-demo-ai` 가 `festa-data-private` 한 곳에만 연결돼 있었다. 이 망은 `internal: true` 라 외부 인터넷이 없는데, AI 는 임베딩·LLM 을 `https://gms.ssafy.io/gmsapi/api.openai.com` 으로 호출한다. 컨테이너 안에서 이름 해석부터 실패했다(`Temporary failure in name resolution`). dev 는 인터넷이 열린 `festa-dev-ai-back-private` 를 함께 달고 있어 이 증상이 없었다.
  2. AI 의 `SPRING_INTERNAL_BASE_URL` 이 기본값 `http://back:8080` 그대로였다. `festa-data-private` 는 dev·demo 공용이고 Compose 로 뜬 dev 백엔드가 그 망에서 `back` 별칭을 갖는다. 그래서 **demo AI 가 dev 백엔드(`172.19.0.5`)에 부스 권한을 묻고 있었다** — 실제 demo 백엔드는 같은 망의 `172.19.0.8` 이다. `BOOTH_ACCESS_CHECK_FAILED` 는 권한 거부가 아니라 호출 자체가 실패했을 때 붙는 코드다(`failure_policy.py`). 결과 콜백이 전부 `UNDELIVERED` 라 dev 쪽에 기록된 것은 없다.
  3. AI 의 `R2_BUCKET` 이 옛 이름 `festa_documents` 였고 자격증명도 백엔드와 달랐다. 위 둘을 고친 뒤 `STORAGE_UNAVAILABLE` 로 드러났다.
  4. AI 컨테이너가 호스트 포트를 열지 않아 demo nginx 가 `/ai/v1/` 을 프록시할 대상이 없었다. 브라우저 요청이 catch-all `location /` 로 떨어져 FE(18080)가 POST 를 405 로 거절했다(이슈 #209).
- **해결**:
  1. 런타임 즉시 조치 — `festa-demo-ai` 를 `festa-demo-runtime` 에도 연결하고, `SPRING_INTERNAL_BASE_URL=http://festa-demo-back:8080` 과 `demo-back.env` 와 동일한 R2 버킷·자격증명을 주입해 `127.0.0.1:18082:8000` 으로 재생성했다. 문서 업로드가 `managed_embedding` 호출까지 도달해 에러 없이 끝나는 것을 확인했다.
  2. 레포 반영 — `infra/deploy/compose/integration/compose.yaml` 의 ai 에 `127.0.0.1:${AI_LOOPBACK_PORT:-18082}:8000` 을 추가하고, `demo.conf.template` 에 `/ai/v1/ → 127.0.0.1:18082` 라우트(`no-store`, `proxy_buffering off`)를 넣었다. `demo-webgl.sh` 와 `test-foundation.sh` 에 계약 검증을 붙여 포트와 라우트가 어긋나면 CI 가 잡도록 했다.
- **예방**:
  - `festa-data-private` 는 dev·demo 공용이다. 그 망에서 `back`·`ai` 같은 **서비스명은 다른 환경의 컨테이너에 걸릴 수 있다.** 수동 배포에서 환경 간 호출 주소는 서비스명이 아니라 환경이 붙은 컨테이너 이름으로 고정한다.
  - 환경별 env 를 고칠 때 back 만 고치고 ai 를 빠뜨리지 않는다. INFRA-T-110(`-729`) 때의 누락이 `SPRING_INTERNAL_BASE_URL`·`R2_BUCKET`·R2 자격증명 **세 값에서 반복**됐다.
  - 수동 컨테이너는 compose 라벨이 없어 재현이 어렵다. 재생성 전 `docker inspect` 로 env 를 스냅샷하고, 이전 컨테이너는 지우지 말고 이름만 바꿔 남긴다(`festa-demo-ai-prev-0916`).


### INFRA-T-110. Cloudflare R2 demo 버킷 오타 및 전용 토큰 부재로 문서 업로드 OPTIONS 400 및 401 실패 (2026-09-16, 해결)

- **증상**: demo 환경(`demo.ssafesta.world`)의 부스 관리에서 AI 직원 답변 근거 문서 업로드 시 브라우저의 Presigned PUT 에 대한 `OPTIONS` preflight 가 `400 Bad Request` 로 실패하고, 백엔드 기동 중 `S3ObjectStorage` 에서 R2 요청이 `401 Unauthorized` 로 거절당함.
- **원인**:
  1. R2 버킷에 `festa-dev-documents` 만 CORS 가 적용되어 있었고, demo 버킷은 `festa-demo-document`(단수형 오타)로 생성되어 실제 요청 대상인 `festa-demo-documents` 버킷과 CORS 설정이 누락됨.
  2. 기존 발급된 R2 API 토큰들이 모두 dev 버킷 전용(bucket-scoped)으로 제한되어 있어 demo 백엔드가 demo 버킷에 접근할 권한(401)이 없었음.
  3. 백엔드 수동 재생성 시 최신 Spring 코드가 요구하는 `AI_INTERNAL_BASE_URL`(http://festa-demo-ai:8000), 내부 통신 토큰 3종(`INTERNAL_SPRING_TO_AI_TOKENS`, `INTERNAL_AI_TO_SPRING_TOKENS`, `INTERNAL_INFRA_TO_SPRING_TOKENS`), 그리고 정식 데모 월드 호스트 `WORLD_HOST=world.ssafesta.world` 주입이 누락되어 기동 실패 및 월드 연결 거부 유발.
- **해결**:
  1. Cloudflare R2에 정식 버킷 `festa-demo-documents` 생성 및 CORS 정책(`PUT`, `AllowedHeaders: [*]`, `AllowedOrigins: [https://demo.ssafesta.world, https://dev.ssafesta.world]`) 적용.
  2. 환경 격리 원칙(`secret-management.md`)에 맞춰 demo 전용 토큰 `festa-demo-ai-r2-rw` 를 신규 발급하여 `festa-demo-documents` 에 대한 Object Read & Write 권한 부여.
  3. EC2 `/opt/festa/secrets/demo-back.env` 에 R2 버킷/토큰 정보, `AI_INTERNAL_BASE_URL`, `WORLD_HOST`, 내부 토큰 3종을 정합화하고 `festa-demo-back` 컨테이너를 재생성하여 401 오류 및 월드 연결 거부를 해소.
- **예방**:
  - dev/demo 환경 분리 시 버킷 생성 및 토큰 발급, CORS 정책 배포를 1:1 체크리스트로 일괄 수행한다.
  - Docker 컨테이너의 `docker restart` 는 `--env-file` 을 다시 읽지 않으므로 환경 파일 수정 시 컨테이너 재생성을 거친다.

### INFRA-T-109. Unity Dedicated Server 컨테이너 UID 불일치(10001 vs 1000)로 stat permission denied 발생 (2026-09-16, 해결)

- **증상**: Jenkins develop 파이프라인의 `Deploy Dedicated Server` 단계에서 빌드된 `festa-game:<SHA>` 이미지로 `festa-demo-world-demo-game-1` 컨테이너를 올릴 때 `OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "/app/festa-unity.x86_64": stat /app/festa-unity.x86_64: permission denied` 에러와 함께 `Created` 상태로 멈추고 17777 웹소켓이 다운됨.
- **원인**:
  1. 동결 기준선인 `festa-unity/Docker/Dockerfile` 은 `useradd -m -d /app unity` 로 사용자를 생성하여 UID/GID 1000 이 부여되고, `/app` 디렉터리와 실행 파일도 `1000:1000`(모드 0750)으로 소유권이 설정되어 있음.
  2. 반면 `infra/unity-server/compose.yaml` 은 `user: "${GAME_CONTAINER_UID:-10001}:${GAME_CONTAINER_GID:-10001}"` 로 기본 UID 를 10001 로 지정하고 있었음.
  3. 컨테이너 런타임(`runc`)이 10001 사용자 권한으로 `/app/festa-unity.x86_64` 를 실행하려 했으나, `/app` 디렉터리가 1000 소유(모드 0750)라 다른 사용자(others)에게 실행 권한이 없어 stat 단계에서 즉시 거부됨.
- **해결**:
  1. `infra/unity-server/compose.yaml` 및 `infra/unity-server/.env.example` 의 기본 UID/GID 를 `1000` 으로 수정 (`user: "${GAME_CONTAINER_UID:-1000}:${GAME_CONTAINER_GID:-1000}"`).
  2. EC2 호스트 `infra/.env` 에 `GAME_CONTAINER_UID=1000`, `GAME_CONTAINER_GID=1000` 반영.
  3. 장애 즉시 응급 조치로 기존 검증 이미지 `festa-world:85ae541f871be1c612538b9898349a3935d25664` 로 복구 기동하여 17777 웹소켓(`101 Switching Protocols`) 및 데모 월드 정상화.
- **예방**:
  - 이미지 빌드 시 생성된 런타임 사용자 UID(1000)와 compose 의 실행 UID 기본값을 일치시킨다.
  - 컨테이너 보안 설정 시 임의의 UID(10001 등)를 지정하지 않고, 이미지의 Dockerfile 및 마운트된 볼륨 소유자(1000:1000)를 단일 기준으로 유지한다.

### INFRA-T-108. 인프라 작업이 FE 티켓 키로 커밋돼 왔다 — `S15P21A604-155` 오용 (2026-09-15, 확인·전환)

- **증상**: PostgreSQL R2 백업 수정을 커밋한 뒤 Jira `S15P21A604-155` 를 열었더니 `[FE] GameProject v1.1 스키마·에디터 반영 (#78)` 이었다. 담당 박준우, 컴포넌트 Frontend (React), 에픽 Game Studio 다. 인프라 커밋과 MR 이 다른 파트 티켓의 Development 패널에 쌓이고 있었다.
- **원인**: 작업일지의 이전 인프라 기록이 `S15P21A604-155` 를 쓰고 있었고 워크트리 이름도 `S15P21A604-155-*` 로 깔려 있어, 그것을 정본으로 보고 같은 키를 이어 썼다. Jira 에서 그 키가 실제로 무엇인지 열어 확인하지 않았다.
- **영향**: 이미 `develop` 에 도달한 커밋의 키는 되돌릴 수 없다. 해당 FE 티켓의 커밋·MR 이력이 오염됐고, 인프라 작업은 Jira 상에서 추적되지 않았다.
- **해결**: 오늘부터 영역별 정확한 키로 전환한다.

  | 영역 | 키 |
  | --- | --- |
  | PostgreSQL 외부 백업·복구 리허설 | `S15P21A604-226` |
  | PostgreSQL·Redis 환경별 데이터 격리 | `S15P21A604-227` |
  | R2·MinIO 저장소 구성·사용량 보호 | `S15P21A604-232` |
  | R2 장애 시 수동 MinIO fallback·reconcile | `S15P21A604-215` |

- **예방**:
  - **키를 다른 문서나 브랜치 이름에서 베끼지 않는다.** 브랜치를 만들기 전에 Jira 에서 그 키를 열어 제목·담당자·컴포넌트가 작업과 맞는지 한 번 본다. 10초면 된다.
  - 작업일지에 키를 적을 때 **이슈 제목을 괄호로 함께 적는다.** 제목이 붙어 있으면 다음 사람이 베껴 쓸 때 어긋남이 눈에 띈다.
  - 워크트리·브랜치 이름은 근거가 아니다. 앞 작업이 틀렸으면 그대로 전파된다.

### INFRA-T-107. `detect-changed-components.sh` 분류표에 없는 경로가 develop 파이프라인을 즉시 거부함 (2026-09-15, 해결)

- **증상**: develop 파이프라인 #358이 `Develop Push Dispatch` 단계에서 `unclassified path(s); refusing build/deploy: infra/unity-server/scripts/deploy-game.sh`로 종료했다. Agent Preflight·Security Preflight는 모두 통과한 뒤였고, 컴포넌트 빌드는 한 개도 시작되지 않았다.
- **원인**: `detect-changed-components.sh`는 변경 경로를 `source_roots`·`component_config`·`shared_*`·`docs_*` 네 분류에 넣지 못하면 `SystemExit`로 빌드를 거부한다(fail-closed). 그런데 인프라가 상시 수정하는 경로 다수가 분류표에 없었다 — `infra/unity-server/`, `infra/environments/{postgres,redis,storage}/`, `infra/environments/compose/data/`, `infra/deploy/compose/integration/`, `spikes/`, `.gitignore`, `.gitattributes`, `.claude/`. 09-01 이후 develop에 들어간 이 경로 변경이 30건이었고, 그동안 같은 이유로 조용히 실패를 반복했다.
- **해결**: 분류표를 하위 경로별로 나눠 채웠다.

  | 경로 | 분류 | 근거 |
  | --- | --- | --- |
  | `infra/unity-server/` | `source_roots` → `game` | Dedicated Server 배포 경로다. 재배포로 검증되어야 하고 ai·back·front를 끌고 올 이유가 없다 |
  | `infra/deploy/`, `infra/environments/` | `shared_prefixes` | 전 컴포넌트 런타임 설정이다. 하위 dev component compose는 `component_config`가 먼저 잡아 component 선택이 유지된다 |
  | `infra/unity-server/runbooks/`, `spikes/`, `.claude/` | `docs_prefixes` | 빌드 산출물에 들어가지 않는다 |
  | `.gitignore`, `.gitattributes` | `docs_exact`(신설) | 같은 이유 |
  | `.dockerignore` | `shared_exact` | 도커 빌드 컨텍스트 제외 규칙이라 이미지 내용에 영향을 줄 수 있다. 문서 취급하면 검증 없이 통과한다 |

  아울러 docs 판정을 분류 루프 **맨 앞**으로 옮겼다. `infra/unity-server/`가 `source_roots`에 들어간 뒤로는 `runbooks/*.md` 한 줄 수정이 Unity 빌드를 끌고 오기 때문이다. `.md` 확장자 일반 규칙은 원래 자리(맨 뒤)에 남겨 뒀다 — `festa-frontend/README.md`는 계속 front 변경으로 잡혀야 하고, 그게 INFRA-T-097의 긴급 재빌드 수단이다.
- **검증**: 분류표를 스크립트에서 직접 읽어 판정하는 검증기로 대표 경로 32건을 대조해 전부 기대값과 일치했고, #358 실패 범위와 09-01 이후 develop 전체 변경 경로에서 미분류가 0건임을 확인했다.
- **예방**:
  - 새 최상위 디렉터리나 `infra/` 하위 새 영역을 추가하는 MR은 분류표 갱신을 같은 커밋에 포함한다. fail-closed 설계이므로 빠뜨리면 그 경로를 건드리는 **다음 사람**이 원인 모를 거부를 밟는다.
  - `infra/*`를 통째로 `shared_prefixes`에 넣는 방법은 택하지 않았다. 그렇게 하면 인프라 파일 한 줄 수정마다 Unity 빌드(15분+)와 `Deploy Dedicated Server`가 딸려온다 — `develop.groovy`의 게임 배포 조건이 `deployComponents`가 아니라 `components.contains('game')`이라, shared의 `deploy_components.clear()`가 게임에는 적용되지 않는다. 운영 중인 월드 서버가 문서 커밋마다 재시작된다.

### INFRA-T-106. `deploy-game.sh`에서 `GAME_ENV_FILE`을 source하지 않아 `FAIL: demo network does not exist`로 배포 중단 (2026-09-15, 해결)

- **증상**: Jenkins develop 파이프라인(#357)의 `Deploy Dedicated Server` 단계에서 `deploy-game.sh` 실행 중 `PASS: host and game image are native x86_64` 다음 줄에서 `FAIL: demo network does not exist`가 발생하며 exit code 1로 빌드가 중단됐다.
- **원인**: `preflight.sh`는 도커 네트워크 존재를 `docker network inspect "${DEMO_NETWORK_NAME:-festa-demo}"`로 확인한다. 실제 EC2 데모 환경의 네트워크 이름은 `festa-demo-runtime`이며 이 값은 `/srv/festa/config/game.env`(`GAME_ENV_FILE`)에 선언되어 있다. 그러나 호출자인 `deploy-game.sh`가 `GAME_ENV_FILE` 파일 존재만 체크하고 `source`(export)하지 않아, `preflight.sh`가 기본값인 `festa-demo`를 조회하다 실패했다.
- **해결**: `infra/unity-server/scripts/deploy-game.sh`에서 `GAME_ENV_FILE` 유효성 검사 직후 `set -a && source "${GAME_ENV_FILE}" && set +a`를 추가하여 `DEMO_NETWORK_NAME`을 자식 프로세스 환경변수로 export했다 (MR `!952`).
- **예방**: 하위 스크립트가 참조하는 env 파일은 compose 호출 시뿐만 아니라 bash 서브스크립트(`preflight.sh` 등) 진입 전에도 명시적으로 export되었는지 확인한다.

### INFRA-T-112. demo AI 가 dev 백엔드를 호출하고 외부망·R2 버킷이 어긋나 문서 처리가 전량 실패 (2026-09-16, 해결)

- **증상**: demo 부스의 AI 직원 근거 문서가 `QUEUED` 에서 넘어가지 않았고, `POST https://demo.ssafesta.world/ai/v1/conversations` 는 405 였다. AI 로그에 `BOOTH_ACCESS_CHECK_FAILED` 와 `spring_failure_callback_undelivered` 가 1 분 주기로 반복됐다.
- **원인**: 네 가지가 겹쳐 있었고, 하나를 고칠 때마다 다음 것이 드러났다.
  1. `festa-demo-ai` 가 `festa-data-private` 한 곳에만 연결돼 있었다. 이 망은 `internal: true` 라 외부 인터넷이 없는데, AI 는 임베딩·LLM 을 `https://gms.ssafy.io/gmsapi/api.openai.com` 으로 호출한다. 컨테이너 안에서 이름 해석부터 실패했다(`Temporary failure in name resolution`). dev 는 인터넷이 열린 `festa-dev-ai-back-private` 를 함께 달고 있어 이 증상이 없었다.
  2. AI 의 `SPRING_INTERNAL_BASE_URL` 이 기본값 `http://back:8080` 그대로였다. `festa-data-private` 는 dev·demo 공용이고 Compose 로 뜬 dev 백엔드가 그 망에서 `back` 별칭을 갖는다. 그래서 **demo AI 가 dev 백엔드(`172.19.0.5`)에 부스 권한을 묻고 있었다** — 실제 demo 백엔드는 같은 망의 `172.19.0.8` 이다. `BOOTH_ACCESS_CHECK_FAILED` 는 권한 거부가 아니라 호출 자체가 실패했을 때 붙는 코드다(`failure_policy.py`). 결과 콜백이 전부 `UNDELIVERED` 라 dev 쪽에 기록된 것은 없다.
  3. AI 의 `R2_BUCKET` 이 옛 이름 `festa_documents` 였고 자격증명도 백엔드와 달랐다. 위 둘을 고친 뒤 `STORAGE_UNAVAILABLE` 로 드러났다.
  4. AI 컨테이너가 호스트 포트를 열지 않아 demo nginx 가 `/ai/v1/` 을 프록시할 대상이 없었다. 브라우저 요청이 catch-all `location /` 로 떨어져 FE(18080)가 POST 를 405 로 거절했다(이슈 #209).
- **해결**:
  1. 런타임 즉시 조치 — `festa-demo-ai` 를 `festa-demo-runtime` 에도 연결하고, `SPRING_INTERNAL_BASE_URL=http://festa-demo-back:8080` 과 `demo-back.env` 와 동일한 R2 버킷·자격증명을 주입해 `127.0.0.1:18082:8000` 으로 재생성했다. 문서 업로드가 `managed_embedding` 호출까지 도달해 에러 없이 끝나는 것을 확인했다.
  2. 레포 반영 — `infra/deploy/compose/integration/compose.yaml` 의 ai 에 `127.0.0.1:${AI_LOOPBACK_PORT:-18082}:8000` 을 추가하고, `demo.conf.template` 에 `/ai/v1/ → 127.0.0.1:18082` 라우트(`no-store`, `proxy_buffering off`)를 넣었다. `demo-webgl.sh` 와 `test-foundation.sh` 에 계약 검증을 붙여 포트와 라우트가 어긋나면 CI 가 잡도록 했다.
- **예방**:
  - `festa-data-private` 는 dev·demo 공용이다. 그 망에서 `back`·`ai` 같은 **서비스명은 다른 환경의 컨테이너에 걸릴 수 있다.** 수동 배포에서 환경 간 호출 주소는 서비스명이 아니라 환경이 붙은 컨테이너 이름으로 고정한다.
  - 환경별 env 를 고칠 때 back 만 고치고 ai 를 빠뜨리지 않는다. INFRA-T-110(`-729`) 때의 누락이 `SPRING_INTERNAL_BASE_URL`·`R2_BUCKET`·R2 자격증명 **세 값에서 반복**됐다.
  - 수동 컨테이너는 compose 라벨이 없어 재현이 어렵다. 재생성 전 `docker inspect` 로 env 를 스냅샷하고, 이전 컨테이너는 지우지 말고 이름만 바꿔 남긴다(`festa-demo-ai-prev-0916`).

### INFRA-T-110. Cloudflare R2 demo 버킷 오타 및 전용 토큰 부재로 문서 업로드 OPTIONS 400 및 401 실패 (2026-09-16, 해결)

- **증상**: demo 환경(`demo.ssafesta.world`)의 부스 관리에서 AI 직원 답변 근거 문서 업로드 시 브라우저의 Presigned PUT 에 대한 `OPTIONS` preflight 가 `400 Bad Request` 로 실패하고, 백엔드 기동 중 `S3ObjectStorage` 에서 R2 요청이 `401 Unauthorized` 로 거절당함.

  3. 백엔드 수동 재생성 시 최신 Spring 코드가 요구하는 `AI_INTERNAL_BASE_URL`(http://festa-demo-ai:8000), 내부 통신 토큰 3종(`INTERNAL_SPRING_TO_AI_TOKENS`, `INTERNAL_AI_TO_SPRING_TOKENS`, `INTERNAL_INFRA_TO_SPRING_TOKENS`), 그리고 정식 데모 월드 호스트 `WORLD_HOST=world.ssafesta.world` 주입이 누락되어 기동 실패 및 월드 연결 거부 유발.
- **해결**:
  1. Cloudflare R2에 정식 버킷 `festa-demo-documents` 생성 및 CORS 정책(`PUT`, `AllowedHeaders: [*]`, `AllowedOrigins: [https://demo.ssafesta.world, https://dev.ssafesta.world]`) 적용.
  2. 환경 격리 원칙(`secret-management.md`)에 맞춰 demo 전용 토큰 `festa-demo-ai-r2-rw` 를 신규 발급하여 `festa-demo-documents` 에 대한 Object Read & Write 권한 부여.
  3. EC2 `/opt/festa/secrets/demo-back.env` 에 R2 버킷/토큰 정보, `AI_INTERNAL_BASE_URL`, `WORLD_HOST`, 내부 토큰 3종을 정합화하고 `festa-demo-back` 컨테이너를 재생성하여 401 오류 및 월드 연결 거부를 해소.
- **예방**:
  - dev/demo 환경 분리 시 버킷 생성 및 토큰 발급, CORS 정책 배포를 1:1 체크리스트로 일괄 수행한다.
  - Docker 컨테이너의 `docker restart` 는 `--env-file` 을 다시 읽지 않으므로 환경 파일 수정 시 컨테이너 재생성을 거친다.

### INFRA-T-107. `detect-changed-components.sh` 분류표에 없는 경로가 develop 파이프라인을 즉시 거부함 (2026-09-15, 해결)

- **원인**: `detect-changed-components.sh`는 변경 경로를 `source_roots`·`component_config`·`shared_*`·`docs_*` 네 분류에 넣지 못하면 `SystemExit`로 빌드를 거부한다(fail-closed). 그런데 인프라가 상시 수정하는 경로 다수가 분류표에 없었다 — `infra/unity-server/`, `infra/environments/{postgres,redis,storage}/`, `infra/environments/compose/data/`, `infra/deploy/compose/integration/`, `spikes/`, `.gitignore`, `.gitattributes`, `.claude/`. 09-01 이후 develop에 들어간 이 경로 변경이 30건이었고, 그동안 같은 이유로 조용히 실패를 반복했다.
- **해결**: 분류표를 하위 경로별로 나눠 채웠다.

  | 경로 | 분류 | 근거 |
  | --- | --- | --- |
  | `infra/unity-server/` | `source_roots` → `game` | Dedicated Server 배포 경로다. 재배포로 검증되어야 하고 ai·back·front를 끌고 올 이유가 없다 |
  | `infra/deploy/`, `infra/environments/` | `shared_prefixes` | 전 컴포넌트 런타임 설정이다. 하위 dev component compose는 `component_config`가 먼저 잡아 component 선택이 유지된다 |
  | `infra/unity-server/runbooks/`, `spikes/`, `.claude/` | `docs_prefixes` | 빌드 산출물에 들어가지 않는다 |
  | `.gitignore`, `.gitattributes` | `docs_exact`(신설) | 같은 이유 |
  | `.dockerignore` | `shared_exact` | 도커 빌드 컨텍스트 제외 규칙이라 이미지 내용에 영향을 줄 수 있다. 문서 취급하면 검증 없이 통과한다 |

  아울러 docs 판정을 분류 루프 **맨 앞**으로 옮겼다. `infra/unity-server/`가 `source_roots`에 들어간 뒤로는 `runbooks/*.md` 한 줄 수정이 Unity 빌드를 끌고 오기 때문이다. `.md` 확장자 일반 규칙은 원래 자리(맨 뒤)에 남겨 뒀다 — `festa-frontend/README.md`는 계속 front 변경으로 잡혀야 하고, 그게 INFRA-T-097의 긴급 재빌드 수단이다.
- **검증**: 분류표를 스크립트에서 직접 읽어 판정하는 검증기로 대표 경로 32건을 대조해 전부 기대값과 일치했고, #358 실패 범위와 09-01 이후 develop 전체 변경 경로에서 미분류가 0건임을 확인했다.
- **예방**:
  - 새 최상위 디렉터리나 `infra/` 하위 새 영역을 추가하는 MR은 분류표 갱신을 같은 커밋에 포함한다. fail-closed 설계이므로 빠뜨리면 그 경로를 건드리는 **다음 사람**이 원인 모를 거부를 밟는다.
  - `infra/*`를 통째로 `shared_prefixes`에 넣는 방법은 택하지 않았다. 그렇게 하면 인프라 파일 한 줄 수정마다 Unity 빌드(15분+)와 `Deploy Dedicated Server`가 딸려온다 — `develop.groovy`의 게임 배포 조건이 `deployComponents`가 아니라 `components.contains('game')`이라, shared의 `deploy_components.clear()`가 게임에는 적용되지 않는다. 운영 중인 월드 서버가 문서 커밋마다 재시작된다.

### INFRA-T-106. `deploy-game.sh`에서 `GAME_ENV_FILE`을 source하지 않아 `FAIL: demo network does not exist`로 배포 중단 (2026-09-15, 해결)

- **증상**: Jenkins develop 파이프라인(#357)의 `Deploy Dedicated Server` 단계에서 `deploy-game.sh` 실행 중 `PASS: host and game image are native x86_64` 다음 줄에서 `FAIL: demo network does not exist`가 발생하며 exit code 1로 빌드가 중단됐다.
- **원인**: `preflight.sh`는 도커 네트워크 존재를 `docker network inspect "${DEMO_NETWORK_NAME:-festa-demo}"`로 확인한다. 실제 EC2 데모 환경의 네트워크 이름은 `festa-demo-runtime`이며 이 값은 `/srv/festa/config/game.env`(`GAME_ENV_FILE`)에 선언되어 있다. 그러나 호출자인 `deploy-game.sh`가 `GAME_ENV_FILE` 파일 존재만 체크하고 `source`(export)하지 않아, `preflight.sh`가 기본값인 `festa-demo`를 조회하다 실패했다.
- **해결**: `infra/unity-server/scripts/deploy-game.sh`에서 `GAME_ENV_FILE` 유효성 검사 직후 `set -a && source "${GAME_ENV_FILE}" && set +a`를 추가하여 `DEMO_NETWORK_NAME`을 자식 프로세스 환경변수로 export했다 (MR `!952`).
- **예방**: 하위 스크립트가 참조하는 env 파일은 compose 호출 시뿐만 아니라 bash 서브스크립트(`preflight.sh` 등) 진입 전에도 명시적으로 export되었는지 확인한다.

### INFRA-T-112. demo AI 가 dev 백엔드를 호출하고 외부망·R2 버킷이 어긋나 문서 처리가 전량 실패 (2026-09-16, 해결)

- **증상**: demo 부스의 AI 직원 근거 문서가 `QUEUED` 에서 넘어가지 않았고, `POST https://demo.ssafesta.world/ai/v1/conversations` 는 405 였다. AI 로그에 `BOOTH_ACCESS_CHECK_FAILED` 와 `spring_failure_callback_undelivered` 가 1 분 주기로 반복됐다.
- **원인**: 네 가지가 겹쳐 있었고, 하나를 고칠 때마다 다음 것이 드러났다.
  1. `festa-demo-ai` 가 `festa-data-private` 한 곳에만 연결돼 있었다. 이 망은 `internal: true` 라 외부 인터넷이 없는데, AI 는 임베딩·LLM 을 `https://gms.ssafy.io/gmsapi/api.openai.com` 으로 호출한다. 컨테이너 안에서 이름 해석부터 실패했다(`Temporary failure in name resolution`). dev 는 인터넷이 열린 `festa-dev-ai-back-private` 를 함께 달고 있어 이 증상이 없었다.
  2. AI 의 `SPRING_INTERNAL_BASE_URL` 이 기본값 `http://back:8080` 그대로였다. `festa-data-private` 는 dev·demo 공용이고 Compose 로 뜬 dev 백엔드가 그 망에서 `back` 별칭을 갖는다. 그래서 **demo AI 가 dev 백엔드(`172.19.0.5`)에 부스 권한을 묻고 있었다** — 실제 demo 백엔드는 같은 망의 `172.19.0.8` 이다. `BOOTH_ACCESS_CHECK_FAILED` 는 권한 거부가 아니라 호출 자체가 실패했을 때 붙는 코드다(`failure_policy.py`). 결과 콜백이 전부 `UNDELIVERED` 라 dev 쪽에 기록된 것은 없다.
  3. AI 의 `R2_BUCKET` 이 옛 이름 `festa_documents` 였고 자격증명도 백엔드와 달랐다. 위 둘을 고친 뒤 `STORAGE_UNAVAILABLE` 로 드러났다.
  4. AI 컨테이너가 호스트 포트를 열지 않아 demo nginx 가 `/ai/v1/` 을 프록시할 대상이 없었다. 브라우저 요청이 catch-all `location /` 로 떨어져 FE(18080)가 POST 를 405 로 거절했다(이슈 #209).
- **해결**:
  1. 런타임 즉시 조치 — `festa-demo-ai` 를 `festa-demo-runtime` 에도 연결하고, `SPRING_INTERNAL_BASE_URL=http://festa-demo-back:8080` 과 `demo-back.env` 와 동일한 R2 버킷·자격증명을 주입해 `127.0.0.1:18082:8000` 으로 재생성했다. 문서 업로드가 `managed_embedding` 호출까지 도달해 에러 없이 끝나는 것을 확인했다.
  2. 레포 반영 — `infra/deploy/compose/integration/compose.yaml` 의 ai 에 `127.0.0.1:${AI_LOOPBACK_PORT:-18082}:8000` 을 추가하고, `demo.conf.template` 에 `/ai/v1/ → 127.0.0.1:18082` 라우트(`no-store`, `proxy_buffering off`)를 넣었다. `demo-webgl.sh` 와 `test-foundation.sh` 에 계약 검증을 붙여 포트와 라우트가 어긋나면 CI 가 잡도록 했다.
- **예방**:
  - `festa-data-private` 는 dev·demo 공용이다. 그 망에서 `back`·`ai` 같은 **서비스명은 다른 환경의 컨테이너에 걸릴 수 있다.** 수동 배포에서 환경 간 호출 주소는 서비스명이 아니라 환경이 붙은 컨테이너 이름으로 고정한다.
  - 환경별 env 를 고칠 때 back 만 고치고 ai 를 빠뜨리지 않는다. INFRA-T-110(`-729`) 때의 누락이 `SPRING_INTERNAL_BASE_URL`·`R2_BUCKET`·R2 자격증명 **세 값에서 반복**됐다.
  - 수동 컨테이너는 compose 라벨이 없어 재현이 어렵다. 재생성 전 `docker inspect` 로 env 를 스냅샷하고, 이전 컨테이너는 지우지 말고 이름만 바꿔 남긴다(`festa-demo-ai-prev-0916`).

### INFRA-T-110. Cloudflare R2 demo 버킷 오타 및 전용 토큰 부재로 문서 업로드 OPTIONS 400 및 401 실패 (2026-09-16, 해결)

- **증상**: demo 환경(`demo.ssafesta.world`)의 부스 관리에서 AI 직원 답변 근거 문서 업로드 시 브라우저의 Presigned PUT 에 대한 `OPTIONS` preflight 가 `400 Bad Request` 로 실패하고, 백엔드 기동 중 `S3ObjectStorage` 에서 R2 요청이 `401 Unauthorized` 로 거절당함.

  3. 백엔드 수동 재생성 시 최신 Spring 코드가 요구하는 `AI_INTERNAL_BASE_URL`(http://festa-demo-ai:8000), 내부 통신 토큰 3종(`INTERNAL_SPRING_TO_AI_TOKENS`, `INTERNAL_AI_TO_SPRING_TOKENS`, `INTERNAL_INFRA_TO_SPRING_TOKENS`), 그리고 정식 데모 월드 호스트 `WORLD_HOST=world.ssafesta.world` 주입이 누락되어 기동 실패 및 월드 연결 거부 유발.
- **해결**:
  1. Cloudflare R2에 정식 버킷 `festa-demo-documents` 생성 및 CORS 정책(`PUT`, `AllowedHeaders: [*]`, `AllowedOrigins: [https://demo.ssafesta.world, https://dev.ssafesta.world]`) 적용.
  2. 환경 격리 원칙(`secret-management.md`)에 맞춰 demo 전용 토큰 `festa-demo-ai-r2-rw` 를 신규 발급하여 `festa-demo-documents` 에 대한 Object Read & Write 권한 부여.
  3. EC2 `/opt/festa/secrets/demo-back.env` 에 R2 버킷/토큰 정보, `AI_INTERNAL_BASE_URL`, `WORLD_HOST`, 내부 토큰 3종을 정합화하고 `festa-demo-back` 컨테이너를 재생성하여 401 오류 및 월드 연결 거부를 해소.
- **예방**:
  - dev/demo 환경 분리 시 버킷 생성 및 토큰 발급, CORS 정책 배포를 1:1 체크리스트로 일괄 수행한다.
  - Docker 컨테이너의 `docker restart` 는 `--env-file` 을 다시 읽지 않으므로 환경 파일 수정 시 컨테이너 재생성을 거친다.

- **원인**: `detect-changed-components.sh`는 변경 경로를 `source_roots`·`component_config`·`shared_*`·`docs_*` 네 분류에 넣지 못하면 `SystemExit`로 빌드를 거부한다(fail-closed). 그런데 인프라가 상시 수정하는 경로 다수가 분류표에 없었다 — `infra/unity-server/`, `infra/environments/{postgres,redis,storage}/`, `infra/environments/compose/data/`, `infra/deploy/compose/integration/`, `spikes/`, `.gitignore`, `.gitattributes`, `.claude/`. 09-01 이후 develop에 들어간 이 경로 변경이 30건이었고, 그동안 같은 이유로 조용히 실패를 반복했다.
- **해결**: 분류표를 하위 경로별로 나눠 채웠다.

  | 경로 | 분류 | 근거 |
  | --- | --- | --- |
  | `infra/unity-server/` | `source_roots` → `game` | Dedicated Server 배포 경로다. 재배포로 검증되어야 하고 ai·back·front를 끌고 올 이유가 없다 |
  | `infra/deploy/`, `infra/environments/` | `shared_prefixes` | 전 컴포넌트 런타임 설정이다. 하위 dev component compose는 `component_config`가 먼저 잡아 component 선택이 유지된다 |
  | `infra/unity-server/runbooks/`, `spikes/`, `.claude/` | `docs_prefixes` | 빌드 산출물에 들어가지 않는다 |
  | `.gitignore`, `.gitattributes` | `docs_exact`(신설) | 같은 이유 |
  | `.dockerignore` | `shared_exact` | 도커 빌드 컨텍스트 제외 규칙이라 이미지 내용에 영향을 줄 수 있다. 문서 취급하면 검증 없이 통과한다 |

  아울러 docs 판정을 분류 루프 **맨 앞**으로 옮겼다. `infra/unity-server/`가 `source_roots`에 들어간 뒤로는 `runbooks/*.md` 한 줄 수정이 Unity 빌드를 끌고 오기 때문이다. `.md` 확장자 일반 규칙은 원래 자리(맨 뒤)에 남겨 뒀다 — `festa-frontend/README.md`는 계속 front 변경으로 잡혀야 하고, 그게 INFRA-T-097의 긴급 재빌드 수단이다.
- **검증**: 분류표를 스크립트에서 직접 읽어 판정하는 검증기로 대표 경로 32건을 대조해 전부 기대값과 일치했고, #358 실패 범위와 09-01 이후 develop 전체 변경 경로에서 미분류가 0건임을 확인했다.
- **예방**:
  - 새 최상위 디렉터리나 `infra/` 하위 새 영역을 추가하는 MR은 분류표 갱신을 같은 커밋에 포함한다. fail-closed 설계이므로 빠뜨리면 그 경로를 건드리는 **다음 사람**이 원인 모를 거부를 밟는다.
  - `infra/*`를 통째로 `shared_prefixes`에 넣는 방법은 택하지 않았다. 그렇게 하면 인프라 파일 한 줄 수정마다 Unity 빌드(15분+)와 `Deploy Dedicated Server`가 딸려온다 — `develop.groovy`의 게임 배포 조건이 `deployComponents`가 아니라 `components.contains('game')`이라, shared의 `deploy_components.clear()`가 게임에는 적용되지 않는다. 운영 중인 월드 서버가 문서 커밋마다 재시작된다.

### INFRA-T-106. `deploy-game.sh`에서 `GAME_ENV_FILE`을 source하지 않아 `FAIL: demo network does not exist`로 배포 중단 (2026-09-15, 해결)

- **예방**: 하위 스크립트가 참조하는 env 파일은 compose 호출 시뿐만 아니라 bash 서브스크립트(`preflight.sh` 등) 진입 전에도 명시적으로 export되었는지 확인한다.

### INFRA-T-105. internal 네트워크에 단독으로 붙이면 `-p` 포트 공개가 조용히 무시됨 (2026-09-15, 해결)

- **증상**: `docker run --network festa-data-private -p 127.0.0.1:18081:8080 ... festa-back:<sha>`로 demo Backend를 교체했는데 호스트 `curl http://127.0.0.1:18081/...`이 `000`(연결 실패)이었다. 컨테이너 로그는 정상이었다 — Flyway 통과, `Started SsafestaApplication`, 코인 정합성 점검까지 돌았다. `docker ps`의 Ports 칸이 `8080/tcp`뿐이고 host binding이 없었다. `api.<domain>`도 같은 이유로 502였다.
- **원인**: `festa-data-private`는 `Internal: true` 네트워크다(`docker network inspect`로 확인). internal 네트워크에만 연결된 컨테이너는 외부와 격리되므로 Docker가 published port를 만들지 않는다. **에러도 경고도 없이 무시된다** — `docker run`은 정상 종료하고 컨테이너 ID까지 돌려준다.
- **해결**: 기본 브릿지로 띄워 `-p`를 적용시킨 뒤 내부망을 추가로 연결한다. 순서를 바꾸면 안 된다.

  ```bash
  docker run -d --name festa-demo-back \
    -p 127.0.0.1:18081:8080 \
    --env-file /home/ubuntu/festa/runtime-secrets/demo-back.env \
    festa-back:<sha>
  docker network connect festa-data-private festa-demo-back
  ```

  기본 브릿지는 포트 공개뿐 아니라 **외부 인터넷 접근에도 필요하다**. internal 네트워크에만 붙이면 Google·Kakao·SSAFY OAuth 공급자로 나가는 요청이 전부 막힌다.
- **예방**:
  - 컨테이너 교체 후 `docker ps --format '{{.Names}} {{.Ports}}'`로 host binding을 눈으로 확인한다. 애플리케이션 로그의 `Started ...`는 포트 공개를 보장하지 않는다 — 둘은 별개다.
  - `--network`로 붙일 네트워크가 internal인지 먼저 본다. `docker network inspect <name> --format '{{.Internal}}'`
  - 같은 증상을 09-14 아침과 09-15 오후에 demo Backend에서 두 번 반복했다. 원인이 조용해서 매번 "포트가 이미 사용 중인가"부터 뒤지게 된다. 교체 절차의 첫 확인 항목을 Ports 칸으로 고정한다.

### INFRA-T-104. `Deploy Dedicated Server`가 `game environment file is missing`으로 중단됨 — deploy agent 마운트 누락 (2026-09-15, 해결)

- **증상**: develop 파이프라인 #331이 새 `Deploy Dedicated Server` 단계에서 `game environment file is missing`, exit 66으로 종료했다. 그 앞 단계(Unity 빌드, 이미지 transfer/import)는 모두 통과했다.
- **원인**: `f3ecbc17`이 develop 파이프라인에 게임 자동 배포를 결선하면서 `deploy-game.sh`에 `GAME_ENV_FILE=/srv/festa/config/game.env`와 `CONNECTION_TOKEN_SECRET_FILE=/opt/festa/secrets/dev-game-connection-token-secret`을 주입했다. 그런데 deploy agent 컨테이너에는 두 경로가 모두 마운트돼 있지 않았다. `/opt/festa/secrets/...` 마운트는 unity-agent에만 있었다. 호스트에 파일을 만들어도 agent 안에서는 보이지 않으므로, env 검사를 통과시켜도 그다음 compose `secrets.connection_token_secret.file`에서 같은 이유로 실패한다.
- **해결**: `infra/jenkins/agents/compose.yaml`의 deploy-agent에 두 경로를 read-only bind mount로 추가하고 environment에 기본값을 선언했다(MR `!899`). 호스트에 `/srv/festa/config/game.env`를 만든 뒤 agent를 재생성했고, agent 안에서 `game.env` 내용과 시크릿 읽기가 모두 되는 것을 확인했다.
- **`game.env` 내용**: 한 줄이다. `infra/unity-server/compose.yaml`의 나머지 변수는 기본값이 실제 컨테이너와 일치하고 네트워크만 어긋난다.

  ```
  DEMO_NETWORK_NAME=festa-demo-runtime
  ```

  실측 근거 — `festa-demo-world-demo-game-1`의 network는 `festa-demo-runtime`(기본값 `festa-demo`와 다름), port는 `127.0.0.1:17777->7777`(기본값 일치), volume은 `festa-demo-world-replay`(기본값 일치)다.
- **예방**:
  - 파이프라인에 호스트 경로를 주입하는 변경은 그 경로가 **해당 agent 컨테이너에 마운트돼 있는지**를 같은 MR에서 확인한다. agent마다 마운트 집합이 다르다 — 이번 건은 unity-agent에만 있던 시크릿 마운트를 deploy agent에도 있다고 가정한 것이 원인이다.
  - bind mount 원본 파일은 **agent 재생성 전에** 호스트에 만든다. 원본이 없으면 Docker가 그 경로에 빈 디렉터리를 만들고, `[[ -f ]]` 검사가 같은 자리에서 다시 실패한다.
  - compose 기본값을 그대로 믿지 않는다. 배포 대상이 이미 떠 있으면 `docker inspect`로 network·port·volume을 대조한 뒤 어긋나는 값만 env 파일에 적는다.

- **해결**: rootless 데몬 이미지 목록에서 `!875` 머지 커밋 태그 `festa-front:f342e46bb5ded01d91372c8f87fb2e67d691d84c`(09-14 22:01)를 찾아 컨테이너를 재생성했다. Jenkins는 `!867`·`!874`·`!875` 이미지를 이미 구워 뒀고 rootless 쪽에 있었다. 브라우저 DOM 실측으로 `전체화면` 체크박스 존재(`!867`), HUD 단일 컨테이너 통합(`!875`), 조작 안내 축약형, 랜딩 WebP를 확인했고 `/runtime-config.js` 200을 확인했다.
- **예방**:
  - demo/dev 컨테이너 교체 시 태그는 **반드시 rootless 데몬 목록**에서 고른다. `DOCKER_HOST=unix:///run/user/1000/docker.sock docker images | grep festa-front`
  - 태그를 고른 뒤 올리기 전에 `git show <TAG> -s --format=%ad --date=iso`로 커밋 날짜를 대조한다. `docker images`의 정렬 순서를 최신성의 근거로 쓰지 않는다.
  - 교체는 `docker rm -f` → `docker run` 순서로 하되, **새 이미지가 이미 존재함을 확인한 뒤**에 지운다. 존재하지 않는 태그로 교체를 시작하면 서비스가 내려간 채 복구 수단을 찾게 된다.
  - `festa-frontend/Dockerfile`은 `COPY dist`라 저장소만으로 빌드되지 않는다. 수동 빌드가 필요하면 `docker run --rm -v "$PWD":/app -w /app node:24 sh -c "npm ci && npm run build"`로 `dist`를 먼저 만든다. 호스트에 node를 설치하지 않는다.

### INFRA-T-102. `ci/package`의 front 검증 블록이 `docker_bin: unbound variable`로 죽어 front 이미지 생산이 중단됨 (2026-09-15, 해결)

- **증상**: develop 파이프라인 #324가 `ci/lib.sh: line 32: docker_bin: unbound variable` / `script returned exit code 1`로 종료했다. 이 때문에 09-14 22:14 이후 front 이미지가 한 개도 생성되지 않았고, demo에 올릴 최신 후보가 없어 `-741` 배포 acceptance가 막혔다.
- **원인**: `!876`(`9d8d1e9f`, `-741` Booth 2.5D runtime asset 자동화)이 `ci/package`에 front 검증을 넣으면서 `trap '...' RETURN`을 등록했다. `docker_bin`은 `package_project` 함수의 `local` 변수인데 `RETURN` 트랩은 전역으로 등록되어, 함수 종료 후 상위 호출부(`ci/lib.sh:32 ci_dispatch_or`)가 반환할 때 트랩이 다시 발화하면서 스코프를 벗어난 `docker_bin`을 참조해 `set -u`(unbound variable)로 죽었다. 앞선 `!888`은 선언과 대입만 합쳤을 뿐 트랩의 스코프 탈출 문제를 해결하지 못했다.
- **해결**: 검증 로직 전체를 서브셸 `( ... )`로 격리하고 트랩을 `EXIT`로 교체했다. 서브셸 종료 시점에만 안전하게 컨테이너/임시 디렉터리가 정리되며 상위 호출 스코프로 트랩이 누출되지 않는다. 아울러 `ci/build`의 AI `.venv` 컴파일 제외(`-x '\.venv'`)와 백엔드 mvnw `clean` 누락도 함께 보완했다.
- **예방**: bash 트랩에서 함수 로컬 변수를 다룰 때는 `RETURN` 대신 서브셸 + `EXIT` 트랩을 사용해 변수 생명주기와 트랩 수명을 일치시킨다.

### INFRA-T-097. 변경 감지 기반 develop CI가 이전 실패 component를 자동 재시도하지 않음 (2026-09-14, 임시 해결·운영 보완 필요)

- **증상**: 2026-09-10 Front 이미지가 demo에 남아 있는 상태에서 이후 Front 변경이 develop에 병합됐지만, 다음 문서-only commit은 성공해도 `front: Test`·Build·배포를 실행하지 않았다. 따라서 `known-good/front.json`과 demo 번들은 오래된 이미지 상태로 남았다.

### INFRA-T-095. PostgreSQL R2 Backup `SignatureDoesNotMatch` — AWS CLI 기본 trailer checksum (2026-09-13~15, 해결)

- **결론(2026-09-15)**: 자격증명 문제가 아니었다. AWS CLI 2.23 부터 S3 업로드에 CRC32 trailer checksum 을 기본으로 붙이는데(`request_checksum_calculation` 기본값 `when_supported`), 그러면 요청이 `content-encoding: aws-chunked` + `x-amz-content-sha256: STREAMING-UNSIGNED-PAYLOAD-TRAILER` 로 나간다. R2 는 이 형태의 서명을 `SignatureDoesNotMatch` 로 거절한다. `backup_init` 이 만드는 AWS config 에 `request_checksum_calculation = when_required` 와 `response_checksum_validation = when_required` 를 추가해 해결했다.
- **실제 해소 확인(2026-09-15)**: 수정이 `develop` 에 들어간 뒤 `festa-postgres-backup` `#11` 을 `dev`/`manual-test` 로 실행해 `Finished: SUCCESS` 를 확인했다. 직전 실패 `#8` 과 같은 파라미터·같은 credential 이었고 달라진 것은 config 두 줄뿐이다.
- **왜 6개 가설이 전부 통과했나**: 실패하는 것은 **본문이 있는 요청뿐**이었다. 진단에 쓴 `head-bucket` 은 본문이 없어 checksum 이 붙지 않으므로 같은 credential·endpoint·bucket 으로 항상 성공한다. 그래서 credential·endpoint·clock·bucket 을 아무리 검증해도 전부 정상으로 나왔고, 수사가 계속 자격증명 쪽으로 향했다.
- **판별 실측(2026-09-15)**: 같은 config 에서 reader·writer 두 credential 로 `head-bucket` 을 각각 실행해 둘 다 `"BucketRegion": "APAC"` 성공을 확인했다. credential 형식도 Access Key ID 32자 hex, Secret 64자 hex, 비-hex 문자 0개로 정상이었다. 즉 서명 자체는 성립하며 `put-object` 만 실패했다.
- **오류 코드가 오해를 부른 지점**: R2 는 체크섬 값 불일치를 `BadDigest`/`InvalidDigest` 로 돌려준다. 이번 건은 체크섬 **값**이 아니라 체크섬 헤더가 만든 **서명 형태**가 문제였으므로 `SignatureDoesNotMatch` 가 나왔고, 코드만 보면 자격증명 문제로 읽힌다.
- **예방**:
  - **HEAD 는 되는데 PUT 만 실패하면 자격증명이 아니라 요청 형태를 의심한다.** 본문 유무로 갈리는 실패는 credential 검증으로 영원히 재현되지 않는다.
  - S3 호환 저장소(R2·MinIO)에 AWS CLI 를 쓸 때는 checksum 기본값을 `when_required` 로 고정한다. 무결성은 manifest 의 SHA-256 이 따로 보장하므로 잃는 것이 없다.
  - 외부 Support 로 넘기기 전에 **성공하는 요청과 실패하는 요청의 차이**를 먼저 분리한다. 이번 건은 그 차이가 본문 하나였다.
- **철회한 조치**: 아래 "다음 조치"의 Cloudflare Support 문의와 키 재발급은 원인이 우리 쪽 CLI 설정으로 밝혀져 진행하지 않았다.

- **증상**: Jenkins `festa-postgres-backup`이 dev `manual-test` 실행에서 PostgreSQL dump 생성 후 R2 `PutObject` 단계에서 `SignatureDoesNotMatch`로 종료했다. 마지막 실패 exit code는 `254`이다.
- **확인한 실행 경로**: Job은 `develop`의 path-style 수정이 포함된 `abce3d03a4cc1f19ef581e409842de4302ba0f56`를 checkout한 상태에서 실패했다. 따라서 수정 전 Pipeline 또는 수정 전 `aws s3 cp` 실행 결과가 아니다.
- **기각한 가설**:
  - `aws s3 cp` multipart 전환: dump를 5GiB 이하 단일 `s3api put-object`로 변경한 뒤에도 동일 오류가 재현됐다.
  - Jenkins credential ID 또는 binding 오류: writer credential은 `Username with password`이며 Access Key ID와 Secret Access Key를 Cloudflare 발급 원문과 각각 SHA-256 fingerprint로 대조했다.
  - endpoint/bucket 오류: agent에 주입된 endpoint와 bucket은 Cloudflare R2 Overview의 S3 API endpoint 및 `festa-postgres-backups`와 일치한다.
  - AWS 환경 잔재: deploy agent에 `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`, config/credential override 변수가 없음을 확인했다.
  - clock skew: deploy agent UTC와 R2 HTTP `Date` header가 같은 초였다.
  - virtual-host 주소 서명: backup/restore 공통 AWS CLI config에서 `s3.addressing_style = path`를 강제한 뒤에도 재현됐다.
  - token 설정: Writer R2 API token은 Active, Object Read & Write, bucket scope `festa-postgres-backups`, TTL Forever, Client IP filter 없음으로 확인했다.
- **실제 canonical request 증거**: 실패 뒤 read-only `HeadBucket` tracing에서 `HEAD /festa-postgres-backups`, host `0b0309a911217a33bb19fe8bdb2239b1.r2.cloudflarestorage.com`, `x-amz-date` UTC, signed header `host;x-amz-content-sha256;x-amz-date`, SigV4 scope `YYYYMMDD/auto/s3/aws4_request`가 출력됐다. R2 문서가 요구하는 standard endpoint와 `auto` region scope에 부합한다. Authorization header, Access Key ID, Secret Access Key, Signature 값은 로그에 출력하지 않았다.
- **결론**: 현재 증거만으로 Jenkins, agent 환경, AWS CLI signing input의 결함은 확인되지 않았다. R2 token credential mapping/provisioning 또는 Cloudflare 측 인증 처리 문제는 아직 미확정 외부 원인이다.
- **다음 조치**: 설정값을 다시 바꾸거나 키를 재발급하지 않는다. Cloudflare Support/Community에 endpoint, bucket, 실패 UTC, canonical request, `SignatureDoesNotMatch` 재현 사실을 제공하고 R2 S3 credential mapping을 확인 요청한다.

#### 전체 경과 — 시작 목표부터 현재 blocker까지

1. **시작 목표**
   - 이 작업은 infra-002 환경 복구 범위의 PostgreSQL backup/restore 경로를 실제로 준비하는 작업에서 시작했다.
   - dev/demo의 business DB와 AI DB를 custom-format dump로 만들고, private R2 bucket `festa-postgres-backups`에 저장하며, 필요 시 운영 DB를 건드리지 않는 `disposable-` 대상에서만 restore rehearsal을 수행하는 것이 목표였다.
   - R2-only가 현재 활성 운영 경로이고 MinIO는 장기 R2 장애 시 운영자 승인 fallback으로 남는다는 결정 아래, 이번 범위의 backup 저장소는 R2로 고정했다.

2. **목표를 위해 구현한 것**
   - `dump.sh`는 환경별 business/AI DB를 `pg_dump -Fc`로 만들고, SHA-256, 크기, PostgreSQL/pgvector 버전, schema fingerprint, table row count를 manifest에 기록한다.
   - `restore.sh`는 manifest와 dump checksum을 먼저 검증하고, `disposable-` prefix target만 허용한다. dev/demo 원본 DB 이름은 restore 경로에 넣지 않는다.
   - Jenkins에는 `festa-postgres-backup`, `festa-postgres-restore-rehearsal` Job을 만들었다. writer/read-only R2 credential과 PostgreSQL admin password를 Job별 최소 권한으로 binding한다.
   - local failure fixture는 live target 거부, checksum 불일치 시 `pg_restore` 미실행, R2 path-style config 생성을 검증한다.

3. **먼저 해결된 문제**
   - 초기 Job은 Controller 환경변수에 credential ID가 없으면 `withCredentials`에 null을 넘겨 NPE가 났다. Pipeline에 기본 credential ID를 두고 환경변수는 override로만 사용하도록 바꿔 해결했다.
   - Jenkins credential에는 R2 endpoint/bucket이 아니라 key 값만 넣고, endpoint와 bucket은 deploy agent 환경으로 분리했다. DB password는 `PGPASSWORD`로 container 내부 `pg_dump`/`psql`/`pg_restore`에만 전달한다.

4. **실제 미해결 지점**
   - PostgreSQL dump 생성 자체는 성공한다. 실패는 첫 R2 업로드 `PutObject`에서 발생한다.
   - 초기에는 business dump 뒤 더 큰 AI dump에서 보였으나, 이후 단일 `PutObject` 전환 후에도 동일 오류가 재현됐다. 따라서 DB 데이터 내용이나 dump 크기가 아니라 R2 S3 인증 단계가 blocker다.
   - backup이 R2에 성공적으로 올라간 적이 없으므로, 실제 R2 manifest를 이용한 restore rehearsal의 end-to-end acceptance도 아직 완료되지 않았다.

5. **조사 순서와 결과**
   - **multipart 가설**: `aws s3 cp`가 multipart로 전환하면서 R2와 충돌한다고 가정했다. 5GiB 이하 단일 `s3api put-object`로 변경했지만 동일 오류가 유지돼 기각했다.
   - **Jenkins credential 누락/종류 가설**: writer가 Global `Username with password`이고, username은 Access Key ID, password는 Secret Access Key로 binding되는 것을 확인했다. null ID NPE도 별도로 해결됐다.
   - **키 복사 또는 다른 키 쌍 가설**: Jenkins stored Access Key ID와 Secret Access Key의 SHA-256 fingerprint를 Cloudflare가 보여준 각 원문과 대조했다. Access Key ID 전체와 Secret 전체가 각각 일치했다. 길이·끝자리만 비교한 것이 아니라 전체값의 fingerprint를 비교했다.
   - **endpoint/bucket 가설**: deploy agent의 endpoint/bucket과 Cloudflare R2 Overview의 S3 API endpoint 및 bucket 이름을 대조해 일치했다.
   - **상속 AWS 환경 가설**: agent에 `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`이 상속되지 않았음을 확인했다.
   - **시간 오차 가설**: agent UTC와 R2 HTTP `Date` header가 같은 초여서 SigV4 clock skew를 기각했다.
   - **주소 방식 가설**: R2 custom endpoint에는 path-style이 안전하다고 보고 `s3.addressing_style = path`를 강제했다. 수정이 포함된 develop SHA `abce3d03...`를 Job이 실제 checkout한 뒤에도 같은 오류가 유지됐다.
   - **token 설정 가설**: writer token은 Active, Object Read & Write, `festa-postgres-backups` bucket scope, TTL Forever, Client IP filtering 없음으로 확인했다.
   - **실제 signer 동작 확인**: 실패 뒤 read-only `HeadBucket` tracing을 추가했다. canonical request는 `HEAD /festa-postgres-backups`, account endpoint host, UTC date, `host;x-amz-content-sha256;x-amz-date`, `YYYYMMDD/auto/s3/aws4_request` scope를 사용했다. 이는 Cloudflare R2 문서의 standard endpoint와 `auto` region 요구사항에 맞는다.

6. **현재 판단과 남은 일**
   - Jenkins Job, deploy agent, 저장된 credential, AWS CLI signing input에서 재현 가능한 오류는 찾지 못했다. 현재 정보만으로 Cloudflare 측 원인을 확정할 수는 없지만, R2 token credential mapping/provisioning 또는 R2 인증 처리 확인이 필요한 외부 blocker 상태다.
   - 같은 credential 재등록, endpoint 재입력, path-style 재수정, 키 재발급을 반복하지 않는다. 이미 각각 검증 또는 재현을 마쳤다.
   - Cloudflare Support/Community에 account ID, bucket, 실패 UTC, `SignatureDoesNotMatch`, canonical request와 `auto` scope를 제공해 R2 S3 credential mapping을 확인 요청한다.
   - 응답 또는 R2 인증 성공 전에는 PostgreSQL backup/restore 기능의 **코드·안전장치 구현은 완료**, **실제 R2 backup 및 restore rehearsal 운영 검증은 미완료**로 구분한다.

### INFRA-T-094. 부모 폴더 asmdef가 하위 계약 외 타입까지 분리해 Unity 전체 컴파일을 중단함 (2026-09-14, 해결·CI gate 후속)

- **예방**: 새·이동된 빌드 경계 설정(Unity `.asmdef`, Frontend `tsconfig`/workspace, Backend Gradle·Maven module)은 적용 전에 대상 폴더 **전체**의 소스와 외부 타입·모듈 참조를 확인한다. 테스트 코드 하나의 가시성을 위해 부모 공용 폴더를 분리하지 말고, 필요한 타입만 최소 하위 경계로 분리한다. 변경 후 해당 플랫폼의 실제 컴파일을 실행한다.

### INFRA-T-092. R2 multipart upload 가설이 단일 PutObject 재현으로 기각됨 (2026-09-13, 확인)

- **증상**: `festa_dev_business` dump 다음 더 큰 `festa_dev_ai` dump 업로드에서 `SignatureDoesNotMatch`가 발생했다.

- **후속**: Cloudflare 계정·버킷·Access Key ID 끝자리와 Jenkins 저장값을 대조해 일치함을 확인했다. 다음으로 AWS CLI의 R2 주소 서명 방식을 path-style로 강제해 검증한다.

### INFRA-T-093. R2 custom endpoint 서명 주소 방식 고정 (2026-09-14, 진행 중)

- **증상**: Jenkins `festa-postgres-backup`이 단일 `PutObject`에서도 `SignatureDoesNotMatch`로 실패한다.
- **확인한 제외 항목**: R2 endpoint 형식, bucket 이름, Cloudflare 계정 위치, Access Key ID 끝자리, Jenkins Credential scope, ingress는 원인이 아니다. Secret Access Key 쌍 자체의 정상 여부는 실제 R2 호출 성공 전까지 확정할 수 없다.
- **조치**: AWS CLI config에 `s3.addressing_style = path`를 고정한다. R2 account endpoint를 사용하는 모든 backup/restore S3 호출이 같은 canonical request 경로로 서명된다.

### INFRA-T-094. R2 PutObject 서명 불일치의 canonical request 증거 부족 (2026-09-14, 진행 중)

- **확인한 항목**: Jenkins writer credential의 Access Key ID와 Secret Access Key를 Cloudflare 발급값의 SHA-256 fingerprint로 각각 대조했다. R2 endpoint, path-style 설정, agent AWS 환경 잔재, agent UTC 시간도 정상이다.

- **목적**: 실제 R2가 검증한 host, URI, region scope, signed header를 확인해 추측 대신 요청 단위 원인을 판별한다. StringToSign의 timestamp·credential scope·canonical hash는 인증정보가 아니므로 함께 출력한다.

- **증상**: develop 빌드 `#468`이 `back`·`front` 빌드를 정상 완료한 뒤 `Waiting for next available executor on 'unity'`에서 50분을 대기하다 전체 타임아웃으로 `ABORTED` 됐다. `Candidate Manifest`와 `Deploy Selected Components`에 도달하지 못해 이미 만들어 둔 `back`·`front` 이미지가 demo에 배포되지 않았다. 사용자에게는 `DELETE /api/v1/documents/20` → `404`로 먼저 발견됐다 — develop에는 삭제 API(`!1175`)가 있는데 demo 백엔드에는 그 커밋을 담은 이미지가 없었다.

- **왜 무관한 파트까지 죽었는가**: `develop.groovy`의 `Candidate Manifest`가 `componentList` 전체의 `image-metadata.json`을 요구했다. `game` 빌드가 끝나지 않으면 매니페스트를 만들 수 없고, 그 매니페스트가 없으면 `back`·`front` 배포가 시작조차 못 한다. 그런데 `Deploy Selected Components`가 배포하는 대상은 `deployComponents.findAll { it in ['ai','back','front'] }`로 game을 제외한다. **배포에 쓰지도 않는 빌드 산출물을 기다리는 의존**이 병목의 실체였다.
- **왜 game이 선택됐는가 (오폭 아님)**: 12:59에 백엔드 배치 머지(`!1175`)와 게임 수정 머지(`d6dd45ac`, `fix(game): 오브젝트 접촉 밀림 완화 S15P21A604-508`)가 3초 차로 들어왔다. Jenkins는 MR 단위가 아니라 `GIT_BEFORE_SHA..GIT_COMMIT` 푸시 범위로 판정하므로 둘이 한 빌드로 묶였고, 그 범위에 `festa-unity/.../PlayerMovement.cs` 변경이 실제로 있었다. `SELECTED_COMPONENTS: back, front, game`이 규칙대로 나온 결과다. `shared` 판정(네 컴포넌트 전부 + `deployComponents` 비움)이 아니었음은 `ai`가 빠지고 `dev batch targets: back front`가 살아 있는 것으로 확인된다.
- **어제 고친 squash/Net Diff와 무관**: `compare_to: 'refs/heads/develop'`는 GitLab **MR 파이프라인**(머지 전 게이트)의 Net Diff 규칙이다. Jenkins develop 빌드는 그 규칙을 쓰지 않고 푸시 범위를 본다. 그래서 squash를 막아도 게임 파트가 실제로 소스를 고쳐 머지하면 game은 빌드된다.
- **해결(1차)**: `develop.groovy`에서 `game`을 앱 컴포넌트 뒤로 옮겼다. `appComponents`(ai·back·front)를 먼저 빌드해 `app` 매니페스트를 만들고 배포까지 끝낸 뒤, `game`을 빌드해 별도 `game` 매니페스트로 `Deploy Dedicated Server`를 탄다. 배포 단위가 서로 다르므로 release manifest도 각자 만든다 — `release-manifest.schema.json`이 `minItems: 1`이라 부분 조합이 계약상 허용된다. 상태 저장도 이미 `dev/batches/*`(앱)와 `demo/game/*`(게임)로 분리돼 있어 이 분할이 현실과 일치한다.
- **부수 조치**: `Jenkinsfile`의 전체 타임아웃을 60분에서 180분으로 올렸다. Unity 단독 빌드가 45분을 넘고 큐 대기까지 겹치면 60분으로는 완료된 작업까지 버려진다.
- **남은 한계(2차 미적용)**: 서로 다른 MR이 같은 푸시 범위에 묶이는 것 자체는 그대로다. MR 단위 배포로 가려면 머지 커밋별 빌드나 GitLab MR 머지 웹훅 기반 트리거로 트리거 구조를 바꿔야 한다. `infra-001 tasks.md`의 `T012A`로 분리해 남겼다.
- **재발 방지**: 앱 배포가 game 빌드를 기다리지 않는다. Unity가 붐비거나 죽어 있어도 `back`·`front`·`ai`는 배포되고, `game`만 늦거나 `exit 75 SKIP`으로 건너뛴다.
- **검증 한계**: Groovy 파이프라인은 로컬에서 실행 검증이 불가능하다. `infra/jenkins/tests/test-foundation.sh`의 정적 검사는 통과했으나 실제 동작은 다음 develop 빌드 1회로 확인해야 한다.

## INFRA-T-103. Redis ACL에 `@scripting`이 없어 채팅·세션 refresh 중단 (2026-09-18, 해결)

- **증상**: 월드 채팅이 동작하지 않고, 월드 입장 직후 연결이 순간적으로 끊겼다. 백엔드 로그에 `RedisSystemException: Error in execution`이 반복됐다.

- **배제된 가설**: 메모리·디스크 아님. Redis 사용량 1.6MiB(상한 15.42GiB), 호스트 디스크 63%. AOF 쓰기 실패도 아니었다.
- **해결**: 운영 ACL 파일의 네 사용자(`dev_back`·`dev_ai`·`demo_back`·`demo_ai`)에 `+@scripting`을 추가하고, 저장소의 `users.acl.example`과 `dev-back.sh` 계약 검사에도 반영했다(`!1182`). 키 범위(`~dev:*`, `~demo:*`)와 `-@dangerous`는 유지해 권한 확대 폭을 최소로 뒀다.
- **제약**: ACL에 관리자 권한(`+acl`) 사용자가 없어 `ACL LOAD`로 무중단 반영이 불가능했고 Redis 재기동이 필요했다. 그 시점 Redis는 AOF가 꺼진 9/16 기동분이라 로그인 세션이 전부 소멸했다. 같은 재기동에서 `!1135`의 `appendonly yes`와 `mem_limit: 256m`을 함께 적용해 이후 재기동에서는 세션이 살아남게 했다.

- **증상**: `festa-demo-front-1`이 `healthy`인데 `curl 127.0.0.1:18080`이 연결 거부되고 `demo.ssafesta.world`가 502를 냈다. `HostConfig.PortBindings`에는 `127.0.0.1:18080`이 있으나 `docker ps`의 `PORTS`는 `80/tcp`뿐이었다.
- **원인**: `infra/environments/compose/demo/base.yaml`의 `front-private`가 내부 전용 네트워크였다. 내부 전용 네트워크에만 붙은 컨테이너는 Docker가 DNAT를 걸지 않아 `ports:` 선언이 조용히 무시된다.
- **왜 지금 드러났는가**: 그동안 demo front는 기본 bridge에 수동 `docker run`으로 떠 있었다(`festa-integration-front-1`, `networks=bridge`). `!1152`가 demo compose 오버레이를 처음 도입하면서 front가 처음으로 `front-private`를 타게 됐고 그 순간 결함이 노출됐다. dev 오버레이에서 복사된 잠복 결함이며 `festa-dev-front-1`도 같은 증상을 갖고 있었다.
- **해결**: 내부 전용 선언을 제거하고 `demo-components.sh`에 회귀 검사를 추가했다(`!1163`). front는 정적 Nginx라 외부 egress가 필요 없지만 호스트 Nginx로부터의 ingress는 필수다.

## INFRA-T-105. 내부 서비스 토큰이 세 출처로 갈려 AI 양방향 호출 실패 (2026-09-18, 해결)

- **증상**: AI 문서 처리가 `BOOTH_ACCESS_CHECK_FAILED`로 실패하고 실패 콜백도 `spring_failure_callback_undelivered`로 전달되지 않았다. NPC 문서 업로드가 큐에서 막혔다.
- **원인**: 같은 토큰의 출처가 셋이었고 값이 서로 달랐다. Jenkins credential(파이프라인 배포본이 받는 값), `/opt/festa/secrets/demo-back.env`, `/opt/festa/secrets/demo-*-token`. `back.yaml`의 `environment:`가 `env_file`보다 우선하므로 실행 중 백엔드가 쥔 값은 Jenkins credential 값이다. 수동으로 AI를 올릴 때 파일에서 읽으면 어긋난다.
- **실측**: `INTERNAL_AI_TO_SPRING_TOKENS` 해시가 컨테이너 `4a6d2362`, 토큰 파일 `4a6d2362`, `demo-back.env` `28a82ec1`로 갈렸다. 반대 방향(`INTERNAL_SPRING_TO_AI_TOKENS`)도 파일이 컨테이너와 달라 한 번 더 어긋났다.
- **해결**: 실행 중 백엔드 컨테이너의 값을 정본으로 잡고(`docker exec ... printenv`) AI를 그 값으로 재배포한 뒤, 시크릿 파일 두 개와 `demo-back.env`를 같은 값으로 동기화했다.
- **예방**: 파이프라인 경로는 back·ai가 같은 Jenkins credential에서 받으므로 어긋나지 않는다. 어긋남은 수동 배포에서만 발생한다 — 수동 배포를 없애는 것이 근본 해결이다. 비교는 값 대신 `sha256sum | cut -c1-12`로 한다.

## INFRA-T-106. AI 상담이 `AGENT_CONFIG_UNAVAILABLE`로 즉시 실패 (2026-09-18, AI 파트 이관)

- **증상**: 대화는 생성되고(`POST /ai/v1/conversations` 201, `messages` 200) 스트림만 즉시 실패했다.
- **원인**: AI가 백엔드의 `GET /internal/ai/agent-config`를 호출하고 응답 필드 집합을 엄격 비교한다. `spring_agent_config.py`의 `_FOUND_FIELDS`는 6개(`found`·`role`·`tone`·`responseLength`·`systemPrompt`·`forbiddenTopics`)인데, 백엔드는 `projectFacts`를 포함해 7개를 반환한다. `if set(body) != _FOUND_FIELDS: raise SpringAgentConfigUnavailable`에서 전체가 거절된다.
- **근거**: 백엔드가 `projectFacts`를 추가한 커밋은 `f106c494`(2026-09-13, S15P21A604-597). `develop` 최신의 `festa-ai`에도 `projectFacts`가 없으므로 배포 버전 격차가 아니라 **코드 계약 불일치**다. 백엔드를 최신화해도 증상은 그대로다.
- **실측**: `GET /internal/ai/agent-config?boothId=10&agentId=5` → `HTTP 200`, 응답에 `projectFacts` 포함.
- **조치**: 인프라에서 고칠 지점이 없다. `_FOUND_FIELDS`에 `projectFacts`를 수용하고 프롬프트 컨텍스트에 반영하는 작업으로 AI 파트에 전달했다. 백엔드가 필드를 빼는 방향은 기능 후퇴라 채택하지 않는다.
