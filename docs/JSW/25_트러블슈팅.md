### INFRA-T-024. Unity 6 Linux ARM64 지원 일반화로 현재 프로젝트 배포 가능성을 오판 (2026-08-27, 해결)

- **증상**: OCI 구축 기록이 “Unity 6부터 Linux ARM64 지원”이라고 적어 Unity 6000.0.78f1 Dedicated Server를 Ampere A1 ARM64에서 빌드·실행할 수 있는 것처럼 안내했다.
- **원인**: Unity 6 전체 버전대의 후속 지원 정보를 현재 고정 버전 6000.0.78f1에 그대로 적용했고, 해당 버전의 `modules.json`과 `LinuxStandaloneSupport/Variations`를 확인하지 않았다. ARM64 sysroot 패키지의 Embedded Linux 전용 제한도 구분하지 않았다.
- **해결**: Unity 담당자가 6000.0.78f1의 Linux 서버 모듈과 설치 variation이 x86_64 전용임을 확인했다. 처음에는 OCI 범위를 WebGL 정적 배포로 제한했지만, 정적 파일 로딩만으로는 서버 기동·WSS·브라우저 동기화라는 원래 목적을 달성하지 못해 OCI Unity 검증 계획 전체를 취소했다. Jira 267, OCI 기록과 infra-003 spec·plan·tasks에는 취소 사유와 x86_64 EC2 확보 후 재개 조건을 보존했다.
- **예방**: 엔진·SDK의 플랫폼 지원 여부는 제품군 또는 메이저 버전 소개만 인용하지 않고 프로젝트 고정 버전의 모듈 카탈로그, 설치된 target variation과 라이선스·플랫폼 제한을 함께 확인한다. 임시 환경을 위해 엔진 업그레이드나 CPU 에뮬레이션을 기본 해결책으로 채택하지 않는다.

### INFRA-T-023. tasks 형식 검증 정규식의 PowerShell backtick 파싱 오류 재발 (2026-08-27, 해결)

- **증상**: `tasks.md`의 체크리스트 형식을 검증하는 PowerShell 명령이 정규식 안의 backtick과 보간 문자열을 잘못 해석해 parser 단계에서 중단됐다.
- **원인**: 경로 표기를 검사하려고 backtick을 포함한 정규식을 double-quoted 문자열 안에 직접 작성해 PowerShell escape·보간 규칙과 충돌했다. INFRA-T-015와 같은 계열의 검증기 자체 오류였다.
- **해결**: 정규식을 single-quoted 조각과 별도 Task ID 문자열로 조합하고 오류 메시지는 `-f` 형식화를 사용해 재실행했다. T001~T087 형식·연속성 검증이 통과했다.
- **예방**: PowerShell 검증 정규식에 Markdown backtick이나 변수 뒤 `:`가 포함되면 double-quoted 문자열을 사용하지 않고 literal 조각 조합과 `-f` 형식화를 사용한다.

### INFRA-T-022. setup-tasks가 Windows Bash 별칭과 비로그인 Git Bash에서 연속 실패 (2026-08-27, 해결)

- **증상**: 필수 `setup-tasks.sh --json`이 일반 `bash`에서는 `Bash/Service/CreateInstance/E_ACCESSDENIED`, Git Bash 직접 실행에서는 `dirname: command not found`로 실패했다.
- **원인**: PowerShell의 `bash`가 Git Bash가 아닌 Windows Bash 서비스였고, `C:\Program Files\Git\bin\bash.exe` 직접 실행은 로그인 초기화가 없어 Unix 도구 PATH를 구성하지 못했다. INFRA-T-017·INFRA-T-007의 실행 환경 문제가 재발했다.
- **해결**: `C:\Program Files\Git\bin\bash.exe --login .specify/scripts/bash/setup-tasks.sh --json`으로 한 번 실행해 FEATURE_DIR·AVAILABLE_DOCS·TASKS_TEMPLATE JSON을 정상 획득했다.
- **예방**: Windows에서 Spec Kit Bash 스크립트는 일반 `bash`를 사용하지 않고 처음부터 명시적 Git Bash `--login` 실행으로 시작한다.

### INFRA-T-021. 계약 모순 검색이 자동 원복 금지 문장을 오탐 (2026-08-25, 해결)

- **증상**: R2 자동 전환 금지 여부를 검사한 `rg` 패턴이 `자동 원복 금지`, `자동 원복하지 않는다` 같은 올바른 부정문까지 모순으로 판정했다.
- **원인**: `자동`과 전환 대상 단어의 존재만 검사하고 문장의 허용·금지 의미를 구분하지 않은 과도하게 넓은 정규식이었다.
- **해결**: 금지 문장은 정상 근거로 유지하고, 자동으로 `LOCAL_ACTIVE`·`R2_ACTIVE` 전환을 허용하는 긍정 표현과 `activeProvider` 혼입만 별도로 검사하도록 검증 범위를 좁혔다.
- **예방**: 정책 문서 모순 검사는 키워드 존재 여부만으로 실패시키지 않고 허용 표현과 금지 표현을 구분한 구체적인 패턴 및 필수 문장 assertion을 함께 사용한다.

### INFRA-T-020. 관리형 Windows 환경에서 Python JSON Schema 검증 실행 파일 접근 거부 (2026-08-25, 해결)

- **증상**: 신규 `storage-failover-state.schema.json`을 `jsonschema`로 검증하려고 `python.exe`를 실행했으나 실행 파일 접근 거부로 검증 명령이 시작되지 않았다.
- **원인**: JSON 또는 스키마 내용의 오류가 아니라 현재 관리형 Windows 환경의 실행 파일 접근 제한이며, PowerShell 5.1에도 `Test-Json`이 없어 같은 방식으로 대체할 수 없었다.
- **해결**: `ConvertFrom-Json`의 terminating error 설정으로 두 JSON 문법을 엄격히 검사하고, PowerShell assertion으로 Usage Admission enum, provider registry, 상태 enum과 상태별 `uploadEnabled`·`activeWriteProvider` 조건을 별도 검증했다.
- **예방**: 로컬 `python`·`jsonschema` 설치를 전제로 삼지 않고 저장소의 계약 검증 절차를 실행 환경과 독립적으로 유지한다. 이후 구현 단계의 계약 테스트에서도 문법 검사와 핵심 상태 불변식 검사를 분리한다.

### INFRA-T-019. 신규 infra-003 정적 검사 자체의 기대값·grep 옵션 오류 (2026-08-25, 해결)

- **증상**: 새 `run-static.sh`의 첫 실행에서 Markdown backtick 때문에 `HS256 only` 고정 문자열 검사가 실패했고, Compose 렌더링의 volume source를 최종 volume name으로 잘못 기대해 실패했다. Secret scan은 `-----BEGIN` 패턴을 `grep` 옵션으로 해석해 usage 오류를 냈지만 조건문이 이를 미검출처럼 처리했다.
- **원인**: 사람이 읽는 원문과 렌더링된 Compose의 실제 표현을 먼저 캡처하지 않고 assertion을 작성했고, 하이픈으로 시작하는 grep 패턴 앞에 `--`를 넣지 않았다.
- **해결**: 토큰 검사는 Markdown 표기와 무관한 고정 식별자로 바꾸고 실제 Compose 출력의 service volume source를 기준으로 assertion을 교정했다. 모든 민감 패턴 grep에 `--`를 추가하고 정적 검사 전체를 재실행해 전 항목 PASS를 확인했다.
- **예방**: 생성 파일과 검사기를 함께 추가할 때 parser·renderer의 실제 출력을 한 번 확인하고, 실패 코드 1과 실행 오류 코드 2를 구분한다. 하이픈으로 시작할 가능성이 있는 모든 검색 패턴은 `grep --` 형태로 전달한다.

### INFRA-T-018. plan 작성 요청을 기능 구현 요청으로 오해해 범위를 초과함 (2026-08-24, 해결)

- **증상**: infra-003의 `$speckit-plan` 결과를 저장해야 하는 상황에서 후속 문장 `Implement the plan`을 실제 Backend·Unity·배포 코드 구현 지시로 해석해 계획 범위를 넘는 파일을 추가·수정했다.
- **원인**: 직전 대화의 목적이 Spec Kit 계획 산출물 생성이라는 문맥보다 일반적인 Plan Mode 종료 문구의 의미를 우선했고, `tasks.md`와 선행 infra-002 구현이 없는 상태를 구현 중단 신호로 처리하지 않았다.
- **해결**: 사용자의 지적 직후 이번 세션에서 추가한 Backend world-session, Unity token validator, game Compose/Nginx·스크립트를 모두 삭제하고 기존 `User.java`, `application-local.yml`, `ConnectionManager.cs`를 원상복구했다. 검색으로 관련 코드 경로와 식별자가 남지 않았음을 확인하고 계획 산출물만 유지했다.
- **예방**: Spec Kit 문서 흐름에서 `plan.md`가 아직 생성되지 않았거나 `tasks.md`가 없으면 `Implement the plan`을 코드 구현으로 확대하지 않는다. 먼저 사용자가 요청한 단계의 산출물 범위를 확인하고, 코드 변경 전 대상 파일 종류를 짧게 명시한다.

### INFRA-T-017. infra-003 clarify prerequisite의 Windows Bash 서비스 접근 거부 (2026-08-24, 해결)

- **증상**: `$speckit-clarify` 필수 선행 명령 `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`가 JSON 대신 `Bash/Service/CreateInstance/E_ACCESSDENIED`를 반환해 clarify 절차가 중단됐다.
- **원인**: 현재 PowerShell 세션의 `bash`가 Git Bash 스크립트를 실행하지 못하고 Windows Bash 서비스 인스턴스 생성 단계에서 접근 거부됐다. 명세와 `.specify/feature.json`은 존재하지만 스킬이 요구하는 단일 prerequisite 실행에서 경로 JSON을 얻지 못했다.
- **해결**: 첫 실행은 스킬 규칙에 따라 중단했다. 다음 `$speckit-clarify` 실행에서 `C:\Program Files\Git\bin\bash.exe`와 `/usr/bin:/mingw64/bin` PATH를 명시해 prerequisite를 한 번 실행했고 infra-003의 `FEATURE_DIR`·`FEATURE_SPEC` JSON을 정상 반환받았다.
- **예방**: Windows의 Spec Kit Bash 스크립트는 일반 `bash` 별칭을 사용하지 않고 Git Bash 실행 파일과 Unix 도구 PATH를 명시한 동일한 실행 방식으로 시작한다.

### INFRA-T-016. 다중 기록 파일 패치의 불필요한 hunk 구분자 재발 (2026-08-24, 해결)

- **증상**: 작업일지와 트러블슈팅 문서를 한 번에 갱신하는 `apply_patch`가 두 번째 `Update File` 앞에서 `Unexpected line found in update hunk`로 거부됐다.
- **원인**: 첫 파일의 추가 hunk 뒤에 내용 없는 `@@`를 다시 넣어 다음 파일 선언이 열린 hunk 안의 잘못된 줄로 해석됐다. INFRA-T-009와 같은 작성 실수가 재발했다.
- **해결**: 거부된 패치가 파일을 변경하지 않았음을 확인하고 작업일지와 트러블슈팅 문서를 별도 `apply_patch` 호출로 나눠 적용했다.
- **예방**: 기록 파일은 원칙적으로 파일당 한 번의 `apply_patch`를 사용하고, 다중 파일 패치가 필요하면 다음 `Update File` 직전에 빈 `@@`가 없는지 실행 전 확인한다.

### INFRA-T-015. PowerShell 검증 메시지의 `$i:` 변수 경계 파싱 오류 (2026-08-24, 해결)

- **증상**: `tasks.md`의 ID 연속성을 검사하는 PowerShell 명령이 실행 전 parser 단계에서 `':' 뒤에 올바른 변수 이름 문자가 없습니다` 오류로 중단됐다.
- **원인**: double-quoted 오류 메시지 안의 `$i:`를 PowerShell이 변수 `i` 다음의 문자가 아니라 drive-qualified variable 구문으로 해석했다.
- **해결**: 메시지의 변수를 `${i}:`로 명시해 경계를 분리한 뒤 같은 검증을 재실행했고 T001~T087 연속 번호와 전체 checklist 형식이 통과했다.
- **예방**: PowerShell 보간 문자열에서 변수 바로 뒤에 `:`가 오면 항상 `${name}` 형식을 사용하고, 검증 스크립트 자체의 parser 성공 후 결과를 신뢰한다.

### INFRA-T-014. R2 usage guard JSON Schema 닫는 괄호 누락 (2026-08-24, 해결)

- **증상**: 생성한 `usage-guard.schema.json`을 `ConvertFrom-Json`으로 검증하자 마지막 `UPLOAD_BLOCKED` 조건에서 `':' 또는 '}'가 필요합니다` 오류가 발생했다. 첫 검증 명령은 PowerShell의 non-terminating error 뒤에도 `JSON_OK`를 출력했다.
- **원인**: 중첩된 `then.properties.ratios.properties.max` 객체를 한 줄로 작성하면서 닫는 중괄호 하나를 누락했고, 초기 검증에서 `$ErrorActionPreference='Stop'`을 설정하지 않았다.
- **해결**: 누락된 중괄호를 추가하고 terminating error 설정으로 두 JSON 파일을 다시 파싱해 모두 성공함을 확인했다.
- **예방**: JSON/Schema 생성 직후 모든 파일을 strict parser로 검증하고, PowerShell 검증 명령에는 `$ErrorActionPreference='Stop'`을 사용해 오류 뒤 성공 문구가 출력되지 않게 한다.

### INFRA-T-013. 같은 파일을 delete/add한 단일 `apply_patch` 거부 (2026-08-24, 해결)

- **증상**: `spec.md` 갱신과 `plan.md` 전체 교체를 한 패치에서 시도했으나 `multiple operations target ... plan.md`로 전체 패치가 거부됐다.
- **원인**: 하나의 `apply_patch` 입력에서 같은 경로에 `Delete File`과 `Add File` 작업을 함께 선언했다.
- **해결**: 첫 시도가 파일을 변경하지 않았음을 확인한 뒤 spec update, plan delete, plan add를 별도 패치로 순서대로 적용했다.
- **예방**: 동일 파일 전체 교체는 단일 update hunk를 사용하거나 delete와 add를 서로 다른 `apply_patch` 호출로 분리한다.

### INFRA-T-012. Git Bash setup-plan의 한글 workspace mkdir 권한 오인 (2026-08-24, 해결)

- **증상**: `setup-plan.sh --json`이 이미 존재하는 feature 경로에서 `mkdir: cannot create directory '/c/Users/SSAFY': Permission denied`로 실패했다.
- **원인**: Git Bash가 한글이 포함된 Windows workspace 절대 경로에서 `mkdir -p`를 실행할 때 managed sandbox가 MSYS 경로를 허용된 workspace write로 인식하지 못했다. `bash -x`로 계산된 전체 경로와 quoting은 정상임을 확인했다.
- **해결**: 동일한 정확한 setup 명령을 승인된 sandbox 외 실행으로 재시도해 plan template과 feature JSON 경로를 정상 생성했다.
- **예방**: 한글 Windows 경로의 Spec Kit Bash script는 먼저 경로 계산을 read-only trace로 확인하고, workspace 내부 대상임에도 MSYS `mkdir`만 권한 실패하면 정확한 명령·대상으로 제한해 승인 재실행한다.

### INFRA-T-011. 계획 조사 중 존재하지 않는 문서·디렉터리 경로 추정 (2026-08-24, 해결)

- **증상**: spec 연관 근거를 찾으며 존재하지 않는 `specs/008-ai-conversation`, `docs/14_AI_API_명세서.md`, `docs/16_AI_RAG_파이프라인.md`, `ai/`와 `docs/30_NEW_AI_시스템_설계서.md`를 위치 인자로 전달한 일부 검색이 실패했다.
- **원인**: spec 본문의 표시명과 번호를 현재 workspace의 물리 경로로 가정하고 `rg --files` 발견 단계를 먼저 수행하지 않았다.
- **해결**: `rg --files` 결과에서 실제 `specs/010-survey/spec.md`, `specs/020-erd-schema/spec.md`, `backend/compose.yaml`과 관련 소스 경로를 확정해 필요한 Redis·PostgreSQL 근거를 검증했다. 실패한 검색은 파일을 변경하지 않았다.
- **예방**: 번호·표시명·예상 top-level 디렉터리를 경로로 사용하기 전에 `rg --files`로 존재를 확인하고, 없는 소유 문서는 현재 spec의 계약 참조로만 기록한다.

### INFRA-T-010. `rg` 위치 인자 wildcard 오류 재발 (2026-08-24, 해결)

- **증상**: Redis 사용 근거를 검색하면서 `rg` 위치 인자에 `specs/001*`를 다시 전달해 Windows 경로 구문 오류가 발생했다.
- **원인**: INFRA-T-008에서 금지한 위치 인자 wildcard를 병렬 검색 명령 일부에 다시 사용했고, 실행 전 명령 전체의 경로 인자를 점검하지 않았다.
- **해결**: 필요한 근거를 정확한 spec 디렉터리와 `rg --files` 검색 결과로 확인했으며, 실패한 검색은 파일 변경을 일으키지 않았다.
- **예방**: Windows `rg` 명령 작성 후 모든 위치 인자를 검토해 `*`·`?`가 있으면 실행하지 않고, `rg --files`로 실제 경로를 확정하거나 `-g` 필터로만 wildcard를 사용한다.

### INFRA-T-009. 다중 파일 `apply_patch` hunk 종료 형식 오류 (2026-08-24, 해결)

- **증상**: Infra 리뷰 기록 두 파일을 한 번에 갱신하는 패치가 `Unexpected line found in update hunk`로 거부됐다.
- **원인**: 첫 파일의 hunk 뒤에 불필요한 `@@`를 두어 다음 `*** Update File` 구문을 hunk 내용으로 해석하게 했다.
- **해결**: 불필요한 hunk 구분자를 제거하고 각 파일의 update 구문을 올바르게 분리해 다시 적용했다. 첫 시도는 검증 단계에서 거부돼 파일 변경이 없었다.
- **예방**: 다중 파일 패치는 각 `*** Update File` 직전에 열린 hunk가 정상적으로 끝났는지 확인하고, 내용 없는 `@@` 구분자를 추가하지 않는다.

### INFRA-T-008. PowerShell에서 `rg` 위치 인자 wildcard 사용 실패 (2026-08-24, 해결)

- **증상**: Infra 리뷰 문서를 찾으면서 `rg` 위치 인자에 `specs/infra-*`를 전달하자 Windows 경로 구문 오류가 발생했다.
- **원인**: PowerShell/Windows 환경에서 `rg`가 위치 인자의 Unix식 wildcard를 파일 집합으로 확장하지 않았다.
- **해결**: 검색 대상을 정확한 파일 경로로 지정하고, 확장 검색에는 `-g '*.md'` 파일 필터를 사용했다.
- **예방**: Windows에서 `rg` 검색 범위는 확인된 디렉터리나 파일 경로로 지정하고 wildcard는 위치 인자가 아니라 `-g`로 전달한다.

### INFRA-T-007. PowerShell에서 직접 실행한 Git Bash의 기본 PATH 누락 (2026-08-24, 해결)

- **증상**: Spec Kit prerequisite를 `C:\Program Files\Git\bin\bash.exe`로 직접 실행했을 때 `dirname: command not found`와 `cd: null directory`가 발생해 JSON 경로를 반환하지 못했다.
- **원인**: PowerShell에서 `bash.exe`를 직접 호출한 프로세스의 Bash PATH에 Git Bash의 `/usr/bin`과 `/mingw64/bin`이 포함되지 않아 기본 Unix 명령을 찾지 못했다.
- **해결**: Bash 명령 안에서 `PATH=/usr/bin:/mingw64/bin`을 명시한 뒤 `check-prerequisites.sh --json --paths-only`를 다시 실행해 `FEATURE_SPEC`이 `specs/infra-002-environments/spec.md`를 가리키는 JSON을 확인했다.
- **예방**: Windows에서 Git Bash 스크립트를 직접 호출할 때는 로그인 셸 초기화 여부를 확인하고, 초기화가 생략되는 실행 방식이면 Bash 내부 PATH에 `/usr/bin:/mingw64/bin`을 명시한다.

### INFRA-T-001. Windows 문서 검색 경로 가정 오류 (2026-08-21, 해결)

- **증상**: `rg`에 `docs/15*` 같은 파일 glob을 직접 전달해 Windows 경로 구문 오류가 발생했고, 사용자 설명의 `INFRA.md`를 저장소 루트 파일로 추정해 존재하지 않는 경로 검색이 실패했다.
- **원인**: 실제 파일 목록을 먼저 확인하지 않고 Unix식 glob과 문서 표시명을 물리 경로로 가정했다.
- **해결**: `rg --files`로 실제 경로를 확인한 뒤 정확한 파일 경로를 사용하고, 파일 필터가 필요할 때는 `rg -g`를 사용했다.
- **예방**: Windows에서 문서 검색 전 `rg --files`로 경로를 확정하고, 파일 glob을 위치 인자로 직접 전달하거나 확인되지 않은 표시명을 경로로 사용하지 않는다.

### INFRA-T-002. 전역 기록 문서 원복 중 Git index 잠금 권한 오류 (2026-08-21, 해결)

- **증상**: INFRA 기록을 `docs/JSW`로 이관한 뒤 전역 `docs/24_작업일지.md`와 `docs/25_트러블슈팅.md`의 줄바꿈 상태까지 정확히 원복하는 `git restore --worktree`가 `.git/index.lock` 생성 권한 오류로 실패했다.
- **원인**: 현재 워크스페이스 권한은 `.git`을 읽을 수 있지만 Git index 잠금 파일 생성은 허용하지 않는다.
- **해결**: 두 전역 기록 파일만 대상으로 권한 승인을 받아 원복하고, `git diff --check`와 상태 조회로 전역 문서에 변경이 남지 않았음을 확인했다.
- **예방**: 샌드박스에서 Git worktree 복원 명령이 index 잠금을 요구하면 정확한 대상과 기존 변경 유무를 확인한 뒤 해당 파일만 승인 범위에 포함한다.

### INFRA-T-003. docs/15 전면 개정 후 Markdown 후행 공백 검사 실패 (2026-08-21, 해결)

- **증상**: `git diff --check`에서 문서 머리말 2줄의 trailing whitespace와 파일 끝 여분 줄을 검출했다.
- **원인**: Markdown 강제 줄바꿈용 공백 두 칸과 파일 생성 패치의 마지막 빈 줄이 Git whitespace 검사 규칙과 충돌했다.
- **해결**: 머리말의 후행 공백을 제거하고 파일 끝을 단일 newline으로 정리한 뒤 `git diff --check`를 재실행했다.
- **예방**: Markdown 줄바꿈은 문단 분리로 표현하고 전면 파일 교체 직후 `git diff --check`로 후행 공백과 EOF 상태를 확인한다.

### INFRA-T-004. speckit-clarify prerequisite가 Windows Bash 권한 오류로 실행되지 않음 (2026-08-21, 해결)

- **증상**: `SPECIFY_FEATURE_DIRECTORY=specs/infra-002-environments`를 지정한 `check-prerequisites.sh --json --paths-only` 실행이 `Bash/Service/CreateInstance/E_ACCESSDENIED`로 실패했고, 권한 승인 재실행도 필수 JSON을 반환하지 않았다. PowerShell 대체 경로도 저장소에 존재하지 않았다.

- **예방**: clarify 실행 전 Git Bash/WSL 실행 권한과 `.specify/scripts/bash/check-prerequisites.sh` 실행 가능 여부를 먼저 확인하고, Windows 전용 환경이면 동등한 PowerShell prerequisite 제공을 검토한다.

### INFRA-T-006. Unity WSS 준비 상태와 배포 문서의 이전 AWS 전제 불일치 (2026-08-21, 미해결)
