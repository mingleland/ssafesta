## 2. 공식 carry-forward 네 건

### 2.1 실제 Unity 번들 provenance gate

실제 GitLab source commit에서 생성된 Unity Release Bundle이 들어올 때 1회 확인한다.

- fixture `558d6624`를 Production 근거로 쓰지 않는다.
- `pipelineCommit`, `artifactSourceCommit`, `unityInputId`를 구분한다.
- Registry checksum·metadata·lineage와 Demo candidate 검증을 통과한다.
- Jenkins 안에서 Unity 릴리스를 다시 빌드하지 않는다.

### 2.2 Production AI/Back env 정리

다음 Production 승격에 편승해 stale/dead key만 제거한다.

- 현재 동작 중인 credential을 추측으로 재작성하지 않는다.
- 사용처 grep, rendered Compose, 컨테이너 Config.Env를 먼저 대조한다.
- secret 원문은 출력·문서화하지 않는다.
- 별도 대규모 env 체계 개편으로 확대하지 않는다.

### 2.3 Production Gate G 실측

Human Gate 대기 중 deploy executor가 즉시 반환되는지만 실측한다.

- Production 승격의 별도 승인 시점에 확인한다.
- 검증을 위해 불필요한 승격을 새로 만들지 않는다.
- Jenkins build number와 executor 점유 시간만 증거로 남긴다.

### 2.4 Raffle 운영 데이터

당첨 인원과 추첨 시각이 결정된 뒤 `event-prizes.json`에 경품을 추가하고 provisioning한다.

- 결정 전에는 placeholder를 만들지 않는다.
- 기존 real API 및 idempotent provisioning 경로를 재사용한다.
- Demo 확인 뒤 Production 운영 절차를 따른다.

## 3. 로컬 관찰을 다루는 방법

32·33 문서에는 Redis AOF/ACL, readonly role, EC2 env drift, 오래된 JSW 가이드 같은 관찰이 있다.
이는 공식 carry-forward가 아니므로 다음 게이트를 모두 통과하기 전에는 구현하지 않는다.

```text
현재 canonical 문서와 충돌하지 않는가
→ 최신 develop에서도 코드상 존재하는가
→ 운영 환경에서 읽기 전용으로 재현되는가
→ 사용자 영향과 우선순위가 있는가
→ 기존 Jira가 있는가, 없으면 새 이슈가 승인됐는가
```

판정은 네 가지 중 하나로 기록한다.

1. superseded historical observation
2. already resolved
3. accepted limitation
4. new evidence-backed issue candidate

## 4. 앞으로 코드 작업을 시작하는 순서

1. `git pull --ff-only origin develop` 후 SHA와 worktree를 확인한다.
2. `AGENTS.override.md`, `AGENTS.md`, 헌법, Jira/Git 규칙을 읽는다.
3. `34_로컬_작업_방식과_회고.md`, 이 문서, 관련 JSW 문서를 읽는다.
4. 인프라는 canonical `00 → 02 → 03 → 05 → 07 → 08` 순으로 확인한다.
5. 관련 spec·plan·tasks·contract와 실제 호출 경로를 읽는다.
6. tracked 변경이면 Jira 키를 확인하고 최신 develop에서 작업 브랜치를 만든다.
7. 가장 작은 diff와 가장 작은 관련 테스트를 선택한다.
8. 변경 전후 identity, 영향 환경, rollback 기준을 기록한다.
9. 사용자의 명시적 요청 전에는 commit, push, MR, EC2/Jenkins/GitLab/Cloudflare 변경을 하지 않는다.

## 5. 인프라 변경 게이트

```text
읽기 전용 진단
→ 단일 원인 가설
→ 설정 렌더링·contract test
→ 변경 대상과 비대상 환경 명시
→ 한 번에 한 변경
→ health/readiness 및 비대상 restart delta 확인
→ 실패 시 rollback
→ 공식 evidence와 문서 반영
```

특히 금지한다.

- `develop → main` squash
- Production에서 재빌드·재패키징
- “가장 최신 이미지”를 시간순으로 골라 수동 교체
- Demo compose/env로 Production 컨테이너 생성
- `festa-prod-*` legacy 복원
- CURRENT와 KNOWN-GOOD 동시 갱신
- state/receipt가 참조하는 이미지 강제 prune
- Jenkins Unity 릴리스 빌드 부활

## 6. 최종 산출물 기준

새 후속 작업은 완료 시 다음을 남긴다.

- Jira 이슈와 작은 범위의 MR
- 요구사항·구현·테스트의 연결
- 민감정보를 제거한 실행 evidence
- Demo/Production 중 실제 영향 환경
- artifact identity와 승인자
- 실패 시 복구 방법
- 필요한 작업일지·트러블슈팅·runbook 갱신

완료의 기준은 “컨테이너가 떴다”가 아니라, 다른 운영자가 정본 문서와 evidence만으로
같은 결과를 재현하고 실패 시 원래 상태로 돌아갈 수 있는가다.
