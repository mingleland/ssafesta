## 4. 포트 맵핑 (Network Ingress & Loopback)

외부 요청은 Cloudflare(443) -> 호스트 Nginx(443) -> Loopback 포트로 프록시됩니다.

| 공개 도메인 / 서브경로 | 외부 포트 | Nginx 프록시 목적지 (Loopback) | 담당 컨테이너 (서비스) |
|---|---|---|---|
| https://demo.ssafesta.world/ | 443 | http://127.0.0.1:18080 | festa-integration-front-1 (React SPA) |
| https://demo.ssafesta.world/ai/v1/ | 443 | http://127.0.0.1:18082 | festa-demo-ai (FastAPI RAG) |
| https://demo.ssafesta.world/unity/ | 443 | (로컬 정적 파일 서빙) | /srv/festa/webgl/current/ |
| https://api.ssafesta.world/ | 443 | http://127.0.0.1:18081 | festa-demo-back (Spring Boot) |
| wss://api.ssafesta.world/ws | 443 | http://127.0.0.1:18081 | festa-demo-back (STOMP WebSocket) |
| wss://world.ssafesta.world/ | 443 | http://127.0.0.1:17777 | festa-demo-world-demo-game-1 (Unity Server) |
| https://ci.ssafesta.world/ | 443 | http://127.0.0.1:8080 | festa-jenkins-controller |
| (내부 전용) | - | 5432 (내부망) | festa-data-postgres-1 |
| (내부 전용) | - | 6379 (내부망) | festa-data-redis-1 |

## 6. CI/CD 파이프라인 구조

1. **GitLab CI (MR Gate)**:
   - 개발자가 develop 브랜치를 타겟으로 생성한 MR에 대해 동작
   - 컴포넌트별(i, ack, front, game) 변경 파일에 따라 선택적 실행
   - ci/test -> ci/build 단계 수행 (이미지 패키징은 하지 않음)
   - 파트 브랜치 간 MR은 긴급 규약에 따라 mr-status(Secret Scan)만 통과 후 빠른 병합 허용
2. **Jenkins CI/CD (Develop 병합 후)**:
   - develop 브랜치 병합 시 자동 트리거 (festa-gitlab-develop_develop)
   - Agent Preflight -> Security Preflight -> 컴포넌트 변경 감지
   - package (Docker 이미지 빌드 & 태깅: festa-<comp>:<SHA>)
   - dev 환경 자동 배포 및 헬스체크
   - Unity Game 서버는 WebGL 배포본과의 프리팹 트리 해시 불일치 시 배포 스킵 가드 동작 (INFRA-T-111)

## 7. 수동 배포(현행) vs Compose 통합 배포(목표)

- **현행 (수동 컨테이너 운영)**:
  - 데모 환경의 안정적 운영을 위해 주요 컨테이너를 개별 Docker 명령어로 띄워둔 상태.
  - 컨테이너 재생성 시 SPRING_INTERNAL_BASE_URL, R2 버킷명, 네트워크 멀티 바인딩(festa-demo-runtime + festa-data-private)을 누락하지 않도록 주의해야 함.
- **목표 (Compose 통합 배포, infra/deploy/compose/integration/compose.yaml)**:
  - deploy-release.sh를 통해 4대 컴포넌트(front, ack, i, game)를 일괄 관리.
  - !1002에서 AI 서비스에 loopback 포트(127.0.0.1:18082:8000)를 추가하여 Nginx와의 계약을 일치시킴.
  - 추후 Jenkins의 festa-demo-promotion 파이프라인이 정식 가동되면 수동 배포가 완전 자동화로 대체될 예정.

## 8. demo DB 조회 요청 처리

파트에서 "demo DB 를 봐야 한다"는 요청이 오면 EC2 공인 IP·SSH 계정·docker 그룹·sudo 를 넘기지 않는다. PostgreSQL 은 `festa-data-private`(`internal: true`)에만 있고 호스트 포트가 없어서, 계정을 넘겨도 얻는 것은 DB 접속이 아니라 호스트 루트다. 대신 조회 전용 역할로 인프라가 대신 조회해 준다.

- 역할: `festa_demo_readonly` — `festa_demo_business`·`festa_demo_ai` 읽기 전용, 비밀번호 없음
- 정의: `infra/environments/postgres/init/00-databases-and-roles.sql`

### 8.1 조회 실행

```bash
# 테이블 목록
sudo docker exec -i festa-data-postgres-1 \
  psql -U festa_demo_readonly -d festa_demo_business -c '\dt'

# 임의 조회
sudo docker exec -i festa-data-postgres-1 \
  psql -U festa_demo_readonly -d festa_demo_business \
  -c 'SELECT id, created_at FROM documents ORDER BY id DESC LIMIT 20'
```

AI 데이터는 `-d festa_demo_ai` 로 바꾼다. 쓰기 쿼리는 권한이 없어 실패하는데 이건 방어막이지 제약이 아니다. demo 데이터를 고쳐야 하면 Flyway migration 으로 올린다. 손으로 UPDATE 하면 다음 배포에서 스키마 기대가 어긋나고, known-good 롤백은 컨테이너만 되돌리지 DB 는 되돌리지 못한다.

`psql -U festa_demo_readonly` 가 인증을 요구하면 이 이미지의 `pg_hba` 가 local 을 `trust` 로 두지 않는 것이다. 그때는 secret 파일을 추가하고 `ALTER ROLE festa_demo_readonly PASSWORD ...` 로 비밀번호를 걸어 `PGPASSWORD` 로 넘긴다.

### 8.2 init SQL 변경분 반영

`/docker-entrypoint-initdb.d` 는 데이터 볼륨이 비어 있을 때만 실행된다. 이미 떠 있는 PostgreSQL 에는 파일을 다시 적용해야 한다. init SQL 은 멱등하게 쓰여 있어 재실행해도 기존 role·database·권한은 그대로고, 컨테이너 재생성도 필요 없다.

```bash
cd ~/festa/S15P21A604
git pull

# 바인드 마운트라 호스트 파일 변경이 컨테이너에 즉시 보인다
sudo docker exec -i festa-data-postgres-1 \
  psql -v ON_ERROR_STOP=1 -U festa_admin -d postgres \
  -f /docker-entrypoint-initdb.d/00-databases-and-roles.sql

# 확인
sudo docker exec -i festa-data-postgres-1 \
  psql -U festa_demo_readonly -d festa_demo_business -c 'SELECT current_user, current_database()'
```
