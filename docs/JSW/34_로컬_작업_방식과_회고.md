# 로컬 작업 방식과 회고

> 이 문서는 정승욱의 개인 회고를 바탕으로 만든 팀 공유 작업 보조 문서다. 팀 정본이나 완료 증거는
> 아니며, 현재 정본과 충돌하면 `docs/infra/canonical/`을 우선한다. 2026-09-22부터 변경 이력 보존을
> 위해 Git에서 관리한다.
> 목적은 잘못을 자책하는 것이 아니라, 반복된 실패의 구조를 기억하고 다음 작업 순서를 고정하는 것이다.

## 1. 핵심 결론

지금까지 가장 큰 문제는 인프라 지식의 부족 자체가 아니었다. **구조와 정본을 확인하기 전에 실행 환경을 먼저 변경한 것**이 문제였다.

기존 작업 흐름은 대체로 다음과 같았다.

```text
증상 발견
→ EC2에서 즉시 명령 실행
→ 실행 상태가 달라짐
→ 다른 오류 발생
→ 다음 명령으로 다시 수정
→ 원래 상태와 원인을 잃음
```

앞으로는 다음 흐름으로 고정한다.

```text
요구사항과 대상 환경 고정
→ 공동 규칙·명세·최근 변경 읽기
→ 현재 상태를 읽기 전용으로 수집
→ 하나의 원인 가설 수립
→ 설정 렌더링·테스트로 먼저 검증
→ 한 번에 하나만 변경
→ 결과와 rollback 확인
→ 명세·증거·운영 문서에 반영
```

### 1.1 2026-09-21 이후 정본 우선순위

인프라에 대해서는 `docs/infra/canonical/`이 새로 동결됐다. 과거 JSW 문서나 미완료 체크박스가
canonical 완료 증거와 충돌하면, 과거 기록을 현재 TODO로 되살리지 않는다.

```text
docs/infra/canonical/00 Master Index
→ 02 Current Architecture
→ 03 Completion Evidence
→ 04·06 Runner Capacity Evidence
→ 05 Operations Runbook
→ 07 Handoff Package
→ 08 Source Map
→ 현재 develop 구현·테스트
→ 실제 receipt·운영 상태의 읽기 전용 실측
→ 과거 JSW 문서와 대화
```

현재 공식 판정은 다음과 같다.

- Batch 1, Batch 2 Consumer E2E, Batch 3 완료
- Runner `concurrent=4` 최종 확정
- GitLab 이슈 #220 종료
- 인프라 문서 동결 및 인계 준비 완료
- Unity 릴리스는 개발자 PC가 번들을 만들고 Jenkins는 검증·배포만 하는 Consumer-only

따라서 앞으로의 첫 질문은 “무엇을 더 구현할까”가 아니라
“이 요청이 공식 carry-forward 4건 중 하나인가, 아니면 새 증거가 있는 별도 문제인가”다.

## 2. 기존 방식과 현재 인프라 작업 방식의 차이

기존에는 EC2의 현재 상태를 직접 고치면서 시스템의 규칙을 알아내려 했다. 현재 인프라 구현은 저장소에 규칙·계약·테스트를 먼저 만들고, EC2가 그 규칙을 따르게 한다.

```text
기존: 서버를 고쳐 설계를 맞춤
현재: 설계를 코드로 고정하고 서버를 교체 가능하게 만듦
```

이정헌의 변경도 처음부터 완벽했던 것은 아니다. Production shell escaping, host/container loopback, Unity license, Jenkins job 등록, credential 타입, Testcontainers cleanup 등이 연속 MR로 보정됐다. 차이는 실패하지 않았다는 것이 아니라, **실패를 다음 실행에서도 재현 가능한 테스트와 계약으로 흡수했다는 것**이다.

## 3. 지금까지 반복된 좋지 않은 습관

### 3.1 확인보다 변경을 먼저 했다

기존 AI 컨테이너를 삭제한 뒤 compose를 실행했고, compose가 `RELEASE_ID` 누락으로 실패하면서 정상 컨테이너만 사라졌다.

앞으로는 다음 순서를 지킨다.

```text
compose config 검증
→ 필수 변수와 이미지 존재 확인
→ 새 인스턴스 생성 가능성 확인
→ 기존 상태 백업·rollback 기준 확인
→ 교체
→ health/readiness 검증
```

### 3.2 진단과 수정을 한 명령 묶음에 섞었다

비밀번호 파일 수정, 컨테이너 삭제, 최신 이미지 선택, 컨테이너 생성, 네트워크 연결, 시작을 한 번에 실행하면 어느 단계에서 실패했는지 알 수 없다. 중간 실패 뒤 후속 명령이 계속 실행되면 `No such container` 같은 2차 오류만 남는다.

앞으로는 다음 세 구간을 분리한다.

1. 읽기 전용 진단
2. 변경 전 검증과 예상 결과
3. 단일 변경과 즉시 검증

### 3.3 파일과 실행 중 상태를 같은 것으로 봤다

다음 세 값은 자동 동기화되지 않는다.

```text
infra/.env
/opt/festa/secrets/*.env
실행 중인 컨테이너의 Config.Env
```

컨테이너 환경변수는 생성 시점 복사본이다. 파일을 수정해도 기존 컨테이너에는 적용되지 않는다. 반대로 Jenkins file credential을 사용해 만든 컨테이너는 호스트의 같은 이름 파일을 고쳐도 바뀌지 않는다.

변경 전 반드시 확인한다.

- 이 값의 정본은 어디인가
- 누가 이 값을 읽는가
- 어느 시점에 복사되는가
- 변경 후 어떤 객체를 recreate해야 하는가
- 어떤 값이 compose `environment:`에 의해 덮이는가

### 3.4 목표 환경과 사용한 배포 경로가 달랐다

원하는 결과는 Demo와 Production의 완전 분리였다.

```text
demo.ssafesta.world → festa-demo-* 및 demo 데이터
ssafesta.world      → festa-production-* 및 prod 데이터
```

하지만 demo compose와 demo env를 이용해 도메인만 Production으로 바꾸면 별도 Production이 되지 않는다. demo 설정을 가진 복제품이 생길 뿐이다. OAuth, API URL, DB, Redis prefix, World host가 계속 Demo를 향할 수밖에 없다.

앞으로 작업 시작 시 한 문장으로 범위를 고정한다.

```text
이번 작업은 [Demo/Production/CI만] 변경하며 [변경하지 않을 환경]은 재시작하지 않는다.
```

### 3.5 컨테이너 이름을 정체로 믿었다

`festa-prod-back`, `festa-production-back-1`, `festa-demo-back-1`이라는 이름만으로 역할을 판단할 수 없다. 실제 정체는 다음 조합으로 판단한다.

- Compose project label
- image reference와 content ID
- source commit과 release receipt
- 환경변수
- 네트워크
- 포트
- DB명과 DB 사용자
- Redis 사용자와 key prefix

수동으로 만든 `festa-prod-*`는 이름과 달리 공식 Production 계보의 컨테이너가 아니었다.

### 3.6 최신 이미지를 정답 이미지로 봤다

가장 최근 생성된 이미지는 테스트 통과, develop 포함, known-good 승인, 동일 배치 여부를 보장하지 않는다. Production 승격의 정답은 시간이 아니라 다음 identity 묶음이다.

```text
releaseId
sourceCommit
imageRef
contentId
Demo batchId
known-good 승인
```

### 3.7 에러 메시지 하나만 따라갔다

502는 nginx 자체 문제가 아니라 DB 인증 실패로 Back이 시작하지 못한 결과일 수 있다. OAuth 오류도 redirect URI만의 문제가 아니라 잘못된 Front/API/Back 환경 조합일 수 있다.

장애는 항상 전체 요청 경로에서 본다.

```text
브라우저
→ Cloudflare
→ 호스트 Nginx
→ Front
→ API Nginx
→ Back/AI/World
→ PostgreSQL/Redis/R2
```

### 3.8 빠른 성공을 위해 안전장치를 건너뛰었다

수동 배포는 자동 배포보다 단순한 경로가 아니다. 자동화가 하던 manifest 검증, 변수 검증, readiness, rollback, evidence를 사람이 직접 책임져야 하므로 오히려 위험하다.

급할수록 기존 공식 스크립트와 receipt를 재사용한다. 즉석 `docker create`는 공식 경로가 존재하지 않는 긴급 상황에서만 사용하고, 실행 전 복구 계획을 작성한다.

### 3.9 낡은 대화 맥락을 현재 develop보다 앞에 뒀다

짧은 기간에 인프라 구조가 반복 변경됐다. 과거 대화에서 맞았던 컨테이너 이름과 스크립트가 현재 develop에서는 틀릴 수 있다.

앞으로의 신뢰 우선순위는 다음과 같다.

```text
헌법·공동 규칙
→ docs/infra/canonical의 CURRENT/FROZEN 문서
→ 현재 develop 구현·테스트
→ 확정된 spec/decision
→ 실제 release receipt와 EC2 읽기 전용 실측
→ runbook과 작업일지
→ 과거 대화와 기억
```

구현과 명세가 충돌하면 혼자 정답을 정하지 않고 충돌을 기록한다.

## 4. 개인 잘못과 구조적 문제를 구분한다

개인적으로 개선할 부분은 분명하다.

- 명령을 이해하기 전에 복사·실행한 것
- 삭제나 recreate 전에 대체 경로를 검증하지 않은 것
- 한 번에 너무 많은 상태를 바꾼 것
- 현재 정본을 읽기 전에 과거 이름을 사용한 것
- 오류가 급할수록 범위를 넓힌 것

하지만 다음은 개인의 실수만으로 설명할 수 없다.

- Jenkins credential과 호스트 secret이 중복되고 자동 동기화되지 않음
- env, env_file, Docker secret, Jenkins credential, compose environment의 소유권 규칙이 문서화되지 않음
- Demo, 수동 Production, canonical Production이 한 EC2에 공존함
- 배포 state가 Docker named volume 안에 있어 호스트에서 바로 보이지 않음
- Unity build 정책과 Production 구조가 짧은 시간에 바뀜
- 초기 지원 과정에서 현재 develop을 읽지 않은 명령이 제공됨

따라서 결론은 “나는 인프라를 못한다”가 아니다. **움직이는 시스템에서 실행 단계로 너무 빨리 들어갔고, 시스템도 그 실수를 막아줄 만큼 명확하지 않았다.**

## 5. 앞으로 Codex와 작업하는 규칙

### 세션 진입 순서

Codex는 코드·명세·설정에 손대기 전에 다음을 읽는다.

1. `AGENTS.override.md`, 루트 `AGENTS.md`
2. 헌법과 Jira/Git 워크플로 문서
3. 이 문서와 `35_로컬_인프라_마무리_로드맵.md`
4. `docs/JSW/` 목록 및 현재 작업 관련 문서
5. 인프라 작업이면 `docs/infra/canonical/00`, `02`, `03`, `05`, `07`, `08`
6. 관련 spec·plan·tasks·contracts와 현재 develop 구현

이 진입 순서는 로컬 `AGENTS.override.md`에 연결돼 있다. 이 문서들을 팀 정본이나 완료 증거로
인용하지 않고, tracked 변경이 필요하면 먼저 Jira 키와 공식 문서 반영 범위를 확정한다.

### 시작 전 Codex가 먼저 보고할 것

- 현재 브랜치와 기준 SHA
- 관련 Jira 키와 spec
- 읽은 정본 문서
- 변경 대상과 변경하지 않을 대상
- 현재 가설과 필요한 읽기 전용 증거
- 실행할 최소 테스트

### 명령을 제공할 때 지킬 것

- 읽기 전용 명령과 변경 명령을 분리한다.
- 여러 줄 명령은 각 단계의 성공 조건을 표시한다.
- 기존 객체를 삭제하는 명령은 대체 생성 검증 뒤에 둔다.
- 변수값이나 secret 원문을 출력하지 않는다. 필요하면 길이 또는 hash만 비교한다.
- `head -n 1`로 최신 이미지를 고르지 않는다. 정확한 identity를 사용한다.
- 명령 실패 시 다음 단계가 실행되지 않도록 한다.
- 실제 실행 전에 어떤 환경이 영향을 받는지 한 줄로 확인한다.

### 권한과 외부 변경

사용자가 명시적으로 요청하기 전에는 다음을 수행하지 않는다.

- commit 및 push
- MR 생성·수정·병합
- Jira 상태 또는 내용 변경
- EC2 파일·컨테이너·네트워크·서비스 변경
- Jenkins credential·job·controller 변경
- Cloudflare DNS·TLS·cache 변경

## 6. 작업 종료 체크

- 요구한 범위만 바뀌었는가
- Demo와 Production을 동시에 건드리지 않았는가
- secret이 로그·diff·문서에 노출되지 않았는가
- 관련 테스트가 실제로 통과했는가
- 실패 시 원래 상태로 돌아갈 수 있는가
- 명세와 구현이 일치하는가
- 완료 증거와 미해결 항목이 구분돼 있는가
- 작업일지·트러블슈팅·Jira에 반영할 내용이 무엇인가
