## 2. 잔액이 어긋날 수 없게 만든 방법

핵심은 **규칙을 코드가 아니라 DB 제약으로 표현**한 것이다. 코드 분기로 지키는 규칙은 경합에서 뚫린다.

| 규칙 | 지키는 것 |
|---|---|
| 같은 요청은 한 번만 반영 | `idempotency_key` **UNIQUE** |
| 하루에 일일 지급 한 번 | 키가 `DAILY_GRANT:{userId}:{KST 날짜}` — "하루 한 번"이 곧 UNIQUE 제약이다 |
| 잔액 = 원장 합계 | 원장 `amount`가 **부호 있는 값**이라 합계가 곧 잔액. 항상 한 트랜잭션에서 함께 변경 |
| 잔액 음수 불가 | 지갑 행 비관적 락 + `CHECK(balance >= 0)` |

### 지갑 락을 멱등성 검사보다 **먼저** 잡는 이유

`WalletService.applyEntry`의 순서는 `지갑 락 → 멱등성 키 조회 → 원장 INSERT → 잔액 UPDATE`다.

키를 먼저 조회하면 동시 요청 둘 다 "없음"을 보고 지나간 뒤 INSERT에서 충돌한다. JPA에서 제약 위반이 나면
그 트랜잭션은 rollback-only가 되어 **같은 트랜잭션 안에서 복구할 수 없다.** 락을 먼저 잡으면 두 번째 요청이
기다렸다가 커밋된 원장을 읽고 같은 결과를 돌려준다. UNIQUE 제약은 그래도 최후 방어선으로 남겨뒀다 —
그게 터지면 이 순서가 어딘가에서 무너진 것이므로 조용히 넘기지 않고 실패시킨다.

> 이 순서는 PostgreSQL 기본 격리 수준(READ COMMITTED)을 전제로 한다. 격리 수준을 올리면 재검토해야 한다.

## 3. 다른 spec이 지켜야 할 호출 규약 (004 · 007/008 · 010 · 012 · 014)

전체 계약: `specs/003-wallet-coin/contracts/wallet-service-api.md`

1. **차감 REST API는 없다.** `WalletService`를 스프링 빈으로 주입해 호출한다. 클라이언트가 금액·대상을
   지시할 수 있는 endpoint를 만들지 않는다 (헌법 2·16조).
2. **호출자의 트랜잭션 안에서 호출한다.** 임대 생성과 코인 차감이 하나의 트랜잭션이어야 한다.
   `WalletService`는 `REQUIRED` 전파라 호출자 트랜잭션에 참여한다.
3. **멱등성 키는 호출자가 만든다.** 같은 업무 행위는 재시도해도 **같은 키**여야 한다.
   시각·난수를 넣으면 재시도가 새 차감이 된다. 권장 형식 `{REASON}:{referenceType}:{referenceId}`, 최대 100자.
4. **금액은 양수로 넘긴다.** 부호는 `WalletService`가 붙인다.
5. **`InsufficientCoinException`을 삼키지 않는다.** 조용히 기본 동작으로 넘어가면 T-24가 반복된다.
   사유와 함께 사용자에게 도달시킨다 (권장 매핑 `409`).

### entry_type · reason_type 매핑 (현재 확정값)

| entry_type | 부호 | 용도 | reason_type 예 |
|---|---|---|---|
| `CHARGE` | + | 시스템 지급, 관리자 증액 | `INITIAL_GRANT`, `DAILY_GRANT`, `ADMIN_ADJUSTMENT` |
| `SPEND` | − | 사용 | `LEASE_PAYMENT`, `AI_SERVICE_FEE`, `ITEM_PURCHASE` |
| `REWARD` | + | 보상 | `SURVEY_REWARD`, `MINIGAME_REWARD` |
| `REFUND` | + | 환불 | `LEASE_REFUND` |

`reason_type`은 enum이 아니라 문자열 상수(`CoinReason`)다. 각 spec이 자기 값을 추가하면 되고,
003을 고칠 필요가 없다. 40자 제한을 넘으면 잘리지 않고 예외가 난다.

## 4. 미결 항목 — 임의로 확정하지 않았다 (헌법 30조)

### U-01. ADMIN 권한 모델 (미정)

현재 토큰 role은 `MEMBER` / `GUEST`뿐이고 `admin` 패키지는 비어 있다.
FR-013(관리자 조정)과 FR-014(정합성 점검)는 **서비스 계층까지 구현하고 테스트했지만 REST로 열지 않았다.**
권한 모델 없이 endpoint를 만들면 인증 없는 운영 API가 되기 때문이다.

001에서도 같은 이유로 관리자 endpoint를 제거한 선례가 있다 (`작업일지.md` 2026-08-19).

**필요한 결정**: role claim에 `ADMIN`을 추가할지, 별도 권한 테이블을 둘지, 관리자 계정을 어떻게 만들지.
결정되면 `CoinReconciliationService.run()`과 `WalletService.adjustByAdmin`에 컨트롤러만 붙이면 된다.

### ~~U-02~~. 시스템 지급을 `CHARGE`로 둔 것 → ✅ 확정 (2026-08-19)

**현금 충전은 하지 않는다. 코인은 게임 내 가상 재화로만 순환한다** (팀 결정 2026-08-19).
MVP 한정이 아니라 영구 정책이므로 "충전 vs 시스템 지급"을 구분할 필요가 생기지 않는다.
`CHARGE`는 **시스템 지급 전용**으로 굳었고 spec 012에서도 재검토하지 않는다.

이 결정으로 003에서 하지 않게 된 것: 결제(PG) 연동, 현금 환불 경로, 충전 API.
코인이 들어오는 경로는 **지급(초기·일일) · 보상 · 환불 · 관리자 조정** 네 가지뿐이다.

### 결정 대기 중 취한 태도

U-01은 **기능을 빼는 방향**으로 처리했다. 잘못 만든 권한 모델을 나중에 되돌리는 비용이,
지금 REST를 안 여는 비용보다 크다.

## 5. 일일 지급을 "요청 전역"에서 판정하는 이유

`/api/v1/**`의 모든 인증된 MEMBER 요청에서 판정한다. 로그인 시점에만 걸지 않은 이유:

- 새로고침(F5)은 access token이 아직 유효하면 **로그인을 거치지 않는다.** 로그인 시점 판정은 이 케이스를 놓친다.
- spec은 "당일 처음 인증된 상태로 서비스에 접속"이라고 썼고, 새로고침·재로그인을 명시적으로 요구한다 (AS1-4).

비용은 Redis 키(`wallet:daily:{userId}:{KST 날짜}`) 조회 1회다. **Redis는 캐시일 뿐 권위가 아니다** —
Redis가 죽어도 DB 경로로 내려가고 정확성은 UNIQUE 제약이 지킨다. 캐시 실패는 WARN 로그로 드러낸다.

### 지급 실패 시 원래 요청을 막지 않는다

`DailyCoinGrantInterceptor`는 지급 실패를 **ERROR 로그로 드러내되 요청은 계속 진행**시킨다.

T-24의 교훈은 "실패를 **보이지 않게** 기본값으로 되돌리지 마라"다. 여기서는 실패가 로그로 드러나고,
지급이 멱등하므로 다음 요청에서 자동 재시도되며, 누락은 정합성 점검에도 잡힌다.
반대로 지급 실패로 무관한 API를 전부 500으로 떨어뜨리면 부가 기능이 서비스 전체를 멈추게 한다.

## 6. 운영 시 주의

- **정합성 점검은 자동 보정하지 않는다.** 불일치가 나오면 원인을 먼저 찾는다. 잔액을 고치면 증거가 사라진다.
- 탈퇴는 001의 `AccountDeletionService`가 원장 → 지갑 순으로 이미 삭제한다. 003에서 중복 구현하지 않았다.
- 로컬 검증은 `backend/bruno/03-wallet`. 신규 계정 첫 조회는 **250**(200+50)이고, 반복해도 변하지 않아야 한다.
