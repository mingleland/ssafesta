## 0. 결론

**방향은 맞다. 계약은 지금 확정할 수 없다.**

요청서의 세 전제 — Spring이 영구 상태·공개본의 Source of Truth(헌법 1조), Unity가 GameProject를
읽지 않음(헌법 4조), Runtime의 점수 주장을 보상 근거로 신뢰하지 않음(헌법 16·20조) — 은 **전부 헌법과
일치한다.** 저장 경계(`games` / `game_versions(project_json JSONB)` / `game_portal_bindings`)와
"Booth Layout JSON과 GameProject JSON을 합치지 않고 `configId`로만 연결"도 005가 실제로 만든 구조와
같은 결이다.

그런데 **계약 확정을 막는 것이 셋 있고, 셋 다 BE가 혼자 풀 수 없다.**

| # | 막는 것 | 왜 계약보다 먼저인가 |
|---|---|---|
| **B-1** | **범위·우선순위 미결** | 헌법 28조 "미니게임은 **1종만** 만든다" · "Week 6 이후 핵심 아키텍처 변경 금지". spec 014는 Out of Scope에 **"미니게임 2종 이상"**을 명시한 확정 문서다. 이 기능은 편집기+런타임+에셋 파이프라인+버전관리를 가진 **별도 서브시스템**이지 "미니게임 하나 더"가 아니다 |
| **B-2** | **`project_json`이 데이터인가 코드인가** | 여기서 답이 갈리면 저장·검증·실행·업로드 계약이 **전부** 달라진다 (§4 M-1) |
| **B-3** | **소유 주체 미정 — Game은 부스의 것인가 사용자의 것인가** | 이 하나가 권한 경계(⑤)·Portal 검증(⑥)·삭제 연쇄(⑦)·업로드 소유권(⑧)을 **동시에** 결정한다 (§3-⑤) |

B-1은 헌법 30조에 따라 `docs/26` ①번(회의)으로 올릴 사안이다. BE가 API 표를 먼저 확정하면 **결정되지 않은
범위를 계약으로 굳히는** 셈이 된다.

## 2. 지금 확정하면 안 되는 것

### B-1. 범위 — 헌법 28조와 spec 014

014는 확정 문서이고 §Out of Scope에 **"미니게임 2종 이상"**이 있다. 014가 마피아 게임을 P2로 미룰 때 쓴
문장을 그대로 이 기능에 적용해야 한다 — *"이건 미니게임 하나 더가 아니라 별도의 게임 시스템이다."*

BE 관점의 실제 규모: 게임 CRUD·버전·검증 + 에셋 업로드/서빙 + 포탈 바인딩 + 삭제 연쇄 + 실행 격리.
**005(51 태스크) 이상**이며, 005는 P0이고 이건 아직 우선순위 자체가 없다.

→ **필요한 것**: `docs/26` ①번 표에 "사용자 제작 게임 Studio 도입 여부와 우선순위"를 등록하고,
채택 시 **헌법 28조 개정**(미니게임 1종 조항)을 함께 처리한다. 헌법 개정 없이 spec만 만들면
모든 PR 리뷰가 헌법 위반으로 걸린다 (Governance 조항).

### B-2. 번호·디렉터리

`020-game-studio`로 쓴다. 요청서의 완료 기준 중 **"docs/08·docs/09에 반영"은 spec 확정 이후**로 미룬다.
지금 반영하면 구현이 없는 계약이 설계 문서에 박히고, 그게 정확히 U-05(facade)와 docs/09 §9(layout 단일
테이블)에서 났던 사고다 — 문서가 실물과 어긋난 채로 남았다.

## 3. 항목별 검토 (요청서 10개 항목)

### ① Aggregate — `Game` / `GameVersion` / `GamePortalBinding`

**권고: 005의 2테이블 구조를 그대로 복제한다.** 요청서의 `games` / `game_versions` 2테이블에는
**Draft를 어디에 두는지가 빠져 있다.** `game_versions`에 `status` 컬럼으로 섞는 설계는 005에서 이미
기각했다 (docs/09 §9 "왜 2테이블인가").

```text
game_drafts                          game_versions
- game_id PK FK   ← 게임당 1개        - id PK
- schema_version                     - game_id FK
- project_json JSONB                 - version_no    ← UNIQUE(game_id, version_no)
- revision        ← 낙관적 잠금        - schema_version
- updated_by_user_id FK              - project_json JSONB  ← 공개 시점 스냅샷, 불변
- updated_at                         - published_by_user_id FK
                                     - published_at
games
- id PK / owner(§⑤에서 결정) / title / status
- published_version_no INTEGER NULL  ← 복합 FK (id, published_version_no) → game_versions(game_id, version_no)
```

**`MAX(version_no)`로 현재 공개본을 유도하지 말 것.** 005 I-3/FR-017의 핵심이다 — 유도하면 비공개·임대
만료로 내린 게임의 **이전 공개본이 되살아난다.** NULL 허용 포인터 컬럼이 있어야 "공개된 것이 없음"이
데이터로 표현된다. `ON DELETE SET NULL`은 **컬럼 목록 필수**다 (V8에서 이걸 빠뜨렸으면 회원 탈퇴가 깨졌다).

### ② Draft 저장의 낙관적 잠금 필드와 409 형식

**권고: 005와 같은 이름을 쓴다. 새로 만들지 말 것.**

- 필드명 `expectedRevision` (최초 저장은 `0`)
- `409 GAME_REVISION_CONFLICT` — **본문에 서버의 최신 Draft를 동봉**한다 (005 R-03: FE가 "다시 불러오기"든 "병합"이든 추가 왕복이 없다)
- 오류 봉투는 이미 있는 `{code, message, requestId, errors[], warnings[]}` 그대로

008에서 `BOOTH_LEASE_EXPIRED`를 새 코드로 만들지 말자고 한 이유와 같다 — **FE가 파서를 두 벌 관리하게
만들지 않는다** (헌법 24조).

### ③ Publish 검증 범위 (JSON Schema + ID 참조 + Scene 전환)

**권고: 005 data-model §3의 표 형식을 그대로 쓴다.** 규칙마다 ① error/warning ② **Draft 저장에도 적용하는가**
두 칸을 채운다. 두 번째 칸이 핵심이다.

| 규칙 | 분류 | Draft 저장에도 | 근거 |
|---|---|---|---|
| `schemaVersion`이 서버가 아는 값 | error | ✅ | 미래 버전을 저장해두면 조용히 못 읽는다 |
| `project_json` 바이트 상한 | error | ✅ | **R-05: 저장 때 막지 않으면 JSONB만 부푼다** |
| 엔티티·씬·에셋 참조 개수 상한 | error | ✅ | 헌법 22조 "오브젝트 12개"에 해당하는 수치가 **필요하다** — 미정 |
| 내부 ID 참조가 문서 안에 실재 | error | ✅ | 깨진 참조는 런타임에서 조용히 사라진다 |
| Scene 전환 대상이 실재 | error | ✅ | |
| 도달 불가능한 Scene 존재 | **warning** | ❌ | 편집 중에는 정상 상태다 |
| 에셋 참조가 **이 게임 소유**인지 | error | ❌ (공개 시점만) | 헌법 16조. 편집 중에는 아직 안 올렸을 수 있다 |

**BE는 값을 변형하지 않는다** (R-04). 반올림·기본값 주입·정규화 금지, 모르는 필드는 거부.
값을 조용히 고치면 편집기는 저장했다고 믿고 서버는 다른 것을 갖게 된다 — T-24의 모양이다.

### ④ Published Version 불변성 · 공개 조회 캐시 정책

**불변성**: 공개 = **복사**. 공개 후 `project_json`을 갱신하는 경로를 만들지 않는다 (005 I-7).

**캐시**: **`max-age` 금지, `ETag` + `If-None-Match` 권고.**

이유가 캐시 취향이 아니다. `docs/HDD/부스_변경_신호_계약.md` §2에서 코드로 확인했듯 **월드에는 무효화
신호가 없다.** `BoothRuntime`은 `Start()`에서 layout을 1회 읽고 저장소 전체에 재호출·구독·무효화가 없다.
여기에 장수명 캐시를 얹으면 "비공개했는데 계속 실행되는 게임"의 창이 캐시 TTL만큼 더 길어진다.
버전 URL로 immutable 캐싱을 하려면 삭제 시 CDN 무효화 경로가 필요한데, **지금 그 경로가 없다.**

### ⑤ Owner / Editor / Visitor / Guest 권한 경계

**먼저 정해야 하는 것: Game의 소유 주체.** 두 안의 파급이 다르다.

| 안 | 장점 | 대가 |
|---|---|---|
| **A. 부스 종속** (`games.booth_id NOT NULL`) | 005의 술어(owner + `booth_staffs`)·임대 만료 해제·탈퇴 삭제 그래프를 **그대로 재사용**. `LayoutConfigResolver`는 `ai_agents.booth_id`와 같은 모양으로 분기 하나만 추가하면 된다 | 부스가 없으면 게임을 못 만든다 |
| **B. 사용자 소유 + 바인딩** | 부스 없이 제작 가능 | **소유 검증이 성립하지 않는다.** "이 게임을 이 부스에 걸 수 있는가"의 판정 규칙을 새로 정의해야 하고, 임대 만료·탈퇴 연쇄가 전부 새 경로가 된다 |

**권고는 A**다. B를 택하려면 "게임 소유자가 그 부스의 편집 권한자일 것"을 **바인딩 생성 시점에** 검증하고,
**그 뒤 권한이 사라지면 어떻게 되는지**(스태프 해제, 임대 만료, 게임 소유자 탈퇴)를 전부 정의해야 한다.

**권한 표** (A 기준):

| 역할 | 판정 | 가능 |
|---|---|---|
| Owner | `booths.owner_user_id` | 전부 |
| Editor | `booth_staffs` 행 존재 | Draft 저장·검증·공개 (005 편집 가드 재사용) |
| Visitor (회원) | 인증만 | `GET /published`, 포탈 실행 |
| Guest | 게스트 토큰 | **`GET /published`·실행까지만.** 제작·저장·업로드 전면 금지 (헌법 12조: 게스트에게 영구 자산을 허용하지 않는다) |

Visitor와 Guest는 **MVP에서 권한이 같다** — 보상이 없으므로 갈릴 이유가 없다(⑩). 4단계로 나누지 말고
"편집 계열 = MEMBER + 부스 권한 / 조회·실행 = 전원"의 2단계로 두면 코드와 테스트가 준다.

### ⑥ 부스 오브젝트 `configId` ↔ Portal Binding 연결 — **여기가 가장 큰 결함이다**

제안된 `GET /api/v1/game-portals/{configId}`는 **성립하지 않는다.** 세 가지가 동시에 깨진다.

1. **`configId`는 전역 식별자가 아니다.** 005 계약에서 `configId`는 `int`이고 **타입별 네임스페이스**다.
   소유 검증 시그니처가 `belongsToBooth(type, configId, boothId)`인 이유가 그것이다.
   `configId=152`만으로는 AI 에이전트 152번인지 포탈 152번인지 서버가 알 수 없다.
2. **`boothId`가 없어 소유 검증이 불가능하다** (헌법 16조). 남의 부스 포탈 id를 알아내 자기 부스에 걸어도
   서버가 판정할 근거가 없다.
3. **임대 유효성 검사가 불가능하다** (005 I-5). 만료된 부스의 게임이 계속 실행된다.

**권고**: `GET /api/v1/booths/{boothId}/game-portals/{configId}`
— 응답에 `gameId` · `publishedVersion` · 실행에 필요한 최소 메타만 싣고, 서버가 같은 호출에서
`(바인딩이 이 부스 것 + 게임이 공개 중 + 임대 유효)`를 **전부** 확인한다.

**추가로 필요한 것 (헌법 24조 통보 대상)**:

- `LayoutObjectType`에 **`GAME_PORTAL` 추가** — 서버 화이트리스트다. 없는 타입은 저장 자체가 error다
- `LayoutConfigResolver`에 `GAME_PORTAL` 분기 추가 — 005가 만들어둔 자리에 한 줄
- **배포 순서: BE 먼저.** 모르는 필드·타입을 거부하므로 FE가 먼저 나가면 저장이 전부 실패한다 (docs/26 등록 사항)
- Unity 구버전은 모르는 타입을 **조용히 무시**한다 (006 SC-005). 오류가 아니라 **포탈이 안 보이는** 것으로 나타난다 → Unity 프리팹 추가가 선행

`configId`는 `int`를 유지해야 한다. `bigint`/UUID로 하려면 Layout `schemaVersion`을 2로 올리는 3파트 합의가 필요하다.

### ⑦ 게임 삭제 · 비공개 · 임대 만료 시 Portal 실행 정책

**실행 시점 서버 재확인이 유일한 방어선이다.** 선택이 아니라 구조적 사실이다 — 월드에 무효화 신호가
없으므로(§④), 이미 접속 중인 사용자는 **세션 내내** 낡은 layout을 들고 있다. 포탈을 누르는 순간의
서버 응답만이 최신이다.

| 상황 | 응답 | 코드 |
|---|---|---|
| 임대 만료 | 409 | **`BOOTH_LEASE_EXPIRED` 재사용** (004·005·008과 같은 코드) |
| 게임 비공개/미공개 | 404 | `GAME_NOT_PUBLISHED` |
| 바인딩 없음/해제됨 | 404 | `GAME_PORTAL_NOT_BOUND` |
| 게임 삭제됨 | 404 | 위와 같은 코드로 합친다 — 사용자에게는 같은 사건이다 |

**조용히 기본 게임으로 대체하거나 빈 화면으로 넘기지 말 것.** 실패는 드러낸다 (T-24의 원인, CLAUDE.md §4).

**관리자 강제 비공개는 아직 못 만든다** — `docs/26` ①-16 (ADMIN 권한 모델 U-01)에 막혀 있고, 004 C-05
신고·강제 비공개가 같은 벽에 걸려 기능을 빼는 방향으로 처리돼 있다. 016(노트북 홈페이지)의 악성 사이트
대응도 같은 결정에 종속이다. **셋을 따로 설계하지 말 것.**

### ⑧ 에셋 업로드 — 메타데이터 · 허용 형식 · 용량 · 소유권

**따로 정하지 말 것.** `docs/26` ②번의 **"AI 문서 허용 형식·최대 크기"(007 C-01)** 와 같은 결정이고,
저장 위치는 docs/15 §11(S3 · presigned URL "후보" 단계)에 종속이다. 게임 에셋만 먼저 확정하면
업로드 경로가 두 벌이 된다.

**BE가 지금 말할 수 있는 것 3가지**:

1. **소유권은 스키마가 아니라 삭제 그래프의 문제다.** docs/09 §회원 탈퇴는 *외부 공개 차단 → 파일/Vector →
   Redis → DB 종속 데이터 → OAuth → User* 순서이고 **재실행 가능해야 한다.** 게임·버전·에셋·바인딩을
   이 순서 어디에 넣을지가 테이블 설계보다 먼저다. V8에서 FK 하나가 탈퇴를 깨뜨릴 뻔했고
   `AccountDeletionService`에는 테스트가 0건이었다 — 같은 함정이 여기서는 더 크다 (S3 객체까지 얽힌다).
2. **저작권·부적절 에셋 신고는 U-01(⑦)에 종속**이다.
3. **형식 화이트리스트는 확장자가 아니라 실제 콘텐츠로 판정**해야 한다. 이건 실행 격리(§4 M-1)와 한 덩어리다.

### ⑨ 플레이 세션 · 완료 기록의 MVP 포함 여부

**권고: 제외.** 보상과 분리하면(⑩) 이 기록은 **아무 결정도 만들지 않는다** — 랭킹도 없고 지급 근거도 아니다.
쌓는 비용만 남는다.

넣는다면 두 가지를 지킨다:
- 이름을 `minigame_results`(docs/09 §24, 014 전용)와 **겹치지 않게** — 예: `game_play_records`
- "비보상 기록"임을 컬럼(`reward_coin=0`)이 아니라 **테이블 분리**로 못박는다. 컬럼이면 언젠가 누가 채운다

### ⑩ Coin / 랭킹 / 보상 제외를 서버 계약에 명시할지

**명시해야 한다. 그리고 "MVP 제외"가 아니라 "영구 제외"로.**

014가 검증 가능한 이유는 게임 규칙이 **서버 코드**이기 때문이다 — 목표 시간을 서버가 발급하고 경과를 서버가
잰다(014 C-06). 사용자 제작 게임은 **규칙 자체가 데이터**라서 서버가 판정 로직을 가질 수 없다.
즉 클라이언트 점수 검증이 **원리적으로 불가능**하다. 헌법 16조·20조를 지키는 유일한 방법은 보상 경로를
아예 만들지 않는 것이다.

형식은 선례가 있다 — `docs/26` 결정 로그의 **"현금 충전 영구 제외 (2026-08-19)"** 와 같은 줄로 남긴다.
"MVP 제외"로 적으면 데모 직전에 "이번만"이 들어온다.

## 4. 요청서에서 빠진 항목 6건

### M-1. **실행 격리 — `project_json`이 데이터인가 코드인가** ★ 최우선

요청서 10개 항목 전체보다 이게 먼저다. 게임 규칙을 표현하려면 조건·수식·이벤트 핸들러가 필요하고,
그게 문자열로 들어와 브라우저에서 평가되는 순간 **저장형 XSS**다. 부스는 남이 만들고 **모든 방문자가**
실행한다 — 영향 범위가 제작자 자신이 아니다.

정해야 할 것: ① 표현력 한계(선언적 데이터만 vs 스크립트 허용) ② Runtime을 **별도 origin + sandbox iframe**에
둘지 ③ CSP ④ 에셋 서빙 도메인 분리. 016이 이미 iframe·X-Frame-Options·새 탭 fallback을 다루므로
**같은 결정에 묶는다.** ①이 정해지기 전에는 ③의 검증 규칙도, ⑧의 형식 화이트리스트도 쓸 수 없다.

### M-2. Draft가 방문자에게 도달하지 않을 것 (005 I-4)

조회 경로를 물리적으로 가른다 — `GET /draft`는 권한 가드 필수, `GET /published`는 **published 테이블만** 읽는다.
"작업 중인 게임이 보였다"는 되돌릴 수 없다.

### M-3. 저장 시점 상한 (R-05)

`project_json` 바이트 상한과 요소 개수 상한. **공개 시점이 아니라 저장 시점부터** 막는다.
공개할 생각이 없는 사람도 저장은 하고, 그러면 DB만 부푼다.

### M-4. 회원 탈퇴 hard delete 그래프 편입 (§⑧-1)

### M-5. Publish 멱등성

`POST /publish`에 본문이 없으면 더블클릭이 v5·v6 **두 회차**를 만든다. `expectedRevision`을 publish에도
받아 "그 Draft 상태를 공개하겠다"는 뜻으로 쓰면 재시도가 안전해진다. docs/08 §1.4의 `Idempotency-Key`는
금전 요청 권고이므로 여기에는 과하다.

### M-6. `POST /validate`의 대상이 본문인가 저장된 Draft인가

005는 별도 validate가 없고 저장·공개 시점에 검증한다. 새로 만드는 것 자체는 좋다(공개 전 미리보기).
다만 **저장된 Draft를 검증**하는 편을 권고한다 — 본문 검증은 "검증은 통과했는데 저장된 것은 다름"을 만든다.
규칙 id(`rule`)는 저장·공개·validate **세 경로에서 같은 문자열**이어야 FE가 한 벌만 만든다.
