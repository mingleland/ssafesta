## ① Jira `S15P21A604-84` — 제목·본문의 `GET`을 `POST`로 정정

**대상**: Jira 이슈 편집 (본인 담당)

> 제목: ~~[BE] World Session 발급 API 구현 (GET /world-sessions)~~ → **[BE] World Session 발급 API 구현 (POST /world-sessions)**
>
> 정정 근거 — 정본 3곳이 모두 POST다.
> - `docs/08_Backend_API_명세서.md` §16 — `### POST /world-sessions`
> - `docs/21_착수전_기술결정_ADR.md`:210 — "MVP에서도 `POST /api/v1/world-sessions`를 반드시 존재시키고"
> - `specs/infra-003-unity-server-deploy/contracts/world-session.openapi.yaml` — `paths./api/v1/world-sessions.post`
>
> 의미상으로도 POST다. 호출마다 새 1회용 토큰이 발급되므로 멱등이 아니고, 캐시·프리페치 대상이 되어서는 안 된다.
> 이슈 본문(2026-08-21 작성)이 `docs/sdd/parts/BE.md`:68의 초안 표기(`GET`)를 따라간 것으로 보인다. 그 브리프도 "권장안(공식 결정 아님)"이다.

## ② Jira `S15P21A604-170` — 완료 조건 축소

**대상**: Jira 이슈 편집 (본인 담당)

> 작업 내용 ~~"토큰 발급 저장(1회용 마킹)·짧은 만료" / "사용·만료 토큰 정리"~~
> → **"`jti` 유일성 보장 + TTL 120초 발급"**
>
> 완료 조건 ~~"사용된 토큰 재검증 거부"~~ → **게임 서버 몫으로 이관**(아래 근거). BE 몫은 "만료 토큰이 거부된다"의 발급측 보증(TTL 120초)뿐이다.
>
> 근거 — 재사용 차단의 소유자가 게임 서버로 확정됐다(2026-08-24 infra-003).
> - `contracts/world-entry-token.md` — "Before player creation it atomically consumes `jti`"
> - `contracts/game-runtime.md` — replay ledger `/var/lib/festa-world/used-grants.log` (persistent volume)
> - infra-003 FR-013 — 게임 서버는 **접속 승인 시마다 Backend에 조회해서는 안 된다**
> - infra-003 FR-014 — 사용된 식별자는 **재배포·재시작 후에도** 만료까지 차단 기록 유지
>
> BE에 "사용된 토큰" 저장소를 만들면 ① 아무도 읽지 않거나 ② 읽게 만드는 순간 헌법 14조("Spring 장애가 월드 입장을 막으면 안 된다")를 위반한다. 그래서 이번 구현에 테이블·Redis 키·정리 스케줄러가 **0개**다.
> 이슈 본문의 "예: 60s"도 계약값 **120초**로 정정한다(`world-entry-token.md`).

## ③ Infra (정승욱) — OpenAPI 요청 본문에 `worldId` 추가 요청

**대상**: GitLab 이슈 (신규 또는 #52 코멘트) + `S15P21A604-169`/`-81` 관련자

> `specs/infra-003-unity-server-deploy/contracts/world-session.openapi.yaml`의 요청 본문에 **optional `worldId`** 를 추가해 주시길 요청합니다. 현재는 `preferredPartyId` 하나뿐입니다.
>
> 근거 — 층 파라미터는 이미 확정된 요구사항입니다.
> - 헌법 9조 — "world-sessions 요청은 **1차 MVP부터 목적 층 파라미터를 포함**한다"
> - `specs/002-world-session/spec.md` FR-012 — "세션 발급 수단은 목적 구역(층)을 입력으로 받아야 한다"
> - GitLab **#31**(1층 폐기, closed)에서 리드가 BE 앞으로 남긴 지시: *"층이 영구적으로 하나가 되어도 **그 파라미터는 그대로 두는 것을 권합니다** — 지우면 나중에 되돌릴 때 계약 변경이 됩니다. 값이 항상 `11F`로 고정될 뿐입니다"*
>
> 구현은 이미 계약을 깨지 않는 방향으로 넣었습니다 — **optional 필드**이고, 없으면 `11F`로 발급하며, `11F`가 아닌 값만 `400 VALIDATION_FAILED`(`field: "worldId"`)로 거부합니다. 기존 OpenAPI를 소비하는 코드(본문 없이 호출)는 그대로 동작합니다. 즉 **가산적 변경**이라 Breaking이 없습니다.
>
> 응답의 `worldId`/`channelId` const(`11F`/`11F-01`)는 계약 그대로 두었습니다.
>
> 덤으로 확인 부탁 — infra-003 tasks의 **T019·T020·T021**(`backend/.../world/` 경로)은 BE가 구현합니다. 파일 경로를 계약이 지정한 그대로 썼으니(`WorldSessionController`·`WorldSessionService`·`WorldEntryTokenIssuer`, 테스트는 T015·T040 경로) 이중 구현은 없습니다. infra-003 쪽에서는 배포·외부 검증 작업만 진행해 주시면 됩니다.

## ④ Unity (게임 파트) — 게스트 신원 규칙 + 토큰 크기 실측 요청

**대상**: GitLab 이슈 (신규) 또는 `S15P21A604-85` 코멘트

> `POST /api/v1/world-sessions`가 서버에 올라갔습니다. `MockWorldSessionClient`를 끄고 붙이실 수 있습니다(002 T003·T004). 접속 승인에서 읽을 claims 관련해 2건 확인 부탁드립니다.
>
> **(1) 게스트 claims — 서버가 파생합니다.** 계약(`world-entry-token.md`)이 claim 목록은 정했지만 게스트 닉네임 값 규칙은 어디에도 없어서, 임의 확정 대신 규칙을 밝히고 확인을 요청합니다(헌법 30조).
>
> | claim | 게스트 값 |
> |---|---|
> | `sub`·`playerId` | Access Token subject 그대로 (`guest:{uuid}`) |
> | `role` | `GUEST` |
> | `nickname` | `"게스트-" + uuid 앞 4자` — **서버 파생**, 클라이언트 입력을 받지 않습니다 (헌법 16조) |
> | `avatarCode` | **claim 자체가 없습니다** (게스트는 비영속 — 헌법 12조) |
>
> `avatarCode`는 회원이 아직 저장한 적 없을 때도 **키가 빠집니다**. 빈 문자열을 넣지 않은 이유는 Unity가 디코드할 수 없는 값이기 때문이고, 없으면 기본 외형을 쓰시면 됩니다. 표시용 값이라 되돌리기 쉬우니 다른 규칙을 원하시면 말씀해 주세요.
>
> **(2) `avatarCode` claim 크기가 NGO approval payload 상한을 견디는지 실측 부탁드립니다.** `avatarCode`는 013a 계약 상한이 **3800자**라 토큰이 이론상 5KB 수준까지 커질 수 있습니다. 실측 아바타 코드는 수백 자 수준이라 문제없을 것으로 보지만, 상한이 있다면 `S15P21A604-85`에서 드러날 지점입니다. claim 목록은 계약 확정값이라 BE가 임의로 빼지 않았습니다 — 걸리면 계약 변경 절차(헌법 24조)로 풀겠습니다.

## 게시 순서 제안

1. ①② — 본인 Jira 편집이라 즉시 가능. 다른 파트 영향 없음
