# 부스 변경 신호 계약 — 미확정 (spec 004·005·006)

> 황덕 백엔드 파트. **004 범위 밖으로 미룬 항목**을 나중에 바로 논의할 수 있게 근거까지 정리한다.
> 작성일: 2026-08-19 | 관련: spec 004(임대) · 005(Layout) · 006(Runtime) | 헌법 24조 합의 대상

---

## 1. 문제

**월드에 있는 사용자는 부스 변경을 보지 못한다.**

| | |
|---|---|
| A가 11층 입장 (T0) | 부스 layout을 조회해 그린다 |
| B가 부스를 수정·게시 (T1) | Spring DB만 바뀐다. **A에게 아무것도 가지 않는다** |
| C가 입장 (T2) | 조회 → **새 layout**을 그린다 |
| **결과** | A와 C가 **같은 공간에서 다른 것을 본다.** A는 세션 내내 낡은 상태 |

임대 만료도 같다 — 만료된 부스가 A의 화면에는 계속 서 있다.

## 2. 코드로 확인한 사실 (main 브랜치, 2026-08-19)

### 부스는 한 번 읽고 끝이다

`festa-unity/Assets/_Project/Scripts/Booth/Runtime/BoothRuntime.cs`

```csharp
async void Start()
{
    if (_loadOnStart) await LoadAndBuildAsync();   // Start()에서 1회
}
```

`LoadAndBuildAsync()`가 `GET /api/v1/booths/{id}/layout/published`를 한 번 호출하고 `Rebuild()`로 로컬 스폰한다.
**저장소 전체에 재호출하는 곳이 없다** — 폴링도 구독도 무효화도 없다. 갈라짐이 60초가 아니라 **세션 내내 영구**다.

### 렌더링은 클라이언트마다 따로다

`HttpBoothApiClient.cs`의 주석 — *"WebGL: 同一 오리진이 아니면 서버 측 CORS 헤더 필요"*.
CORS가 문제가 된다는 건 **그 HTTP 요청이 각 사용자의 브라우저에서 나간다**는 뜻이다.
Unity WebGL은 사용자마다 독립된 WASM 인스턴스이고, React는 캔버스를 담는 페이지일 뿐 렌더를 공유하지 않는다.
"프론트에 임베드되니 화면이 하나"는 성립하지 않는다. (픽셀 스트리밍이면 성립하지만 이 구조가 아니다.)

### 같은 문제를 아바타는 이미 풀었다

`World/Avatar/PlayerAvatarVisual.cs`

```csharp
void OnEncodedChanged(FixedString4096Bytes _, FixedString4096Bytes next) => Rebuild(next.ToString());
```

아바타는 `NetworkVariable`을 **구독**해서 모든 클라이언트가 동시에 다시 만든다.
부스와 원칙이 같은데(식별자만 동기화 + 로컬 스폰) **부스에만 구독이 없다.** 빠진 건 아키텍처가 아니라 **변경 신호**다.

### 동결 파일을 안 건드려도 된다

`BoothRuntime.Rebuild(BoothLayoutDto)`와 `Clear()`가 **이미 public**이다.
외부 컴포넌트가 `Rebuild(새_layout)`을 호출하면 되므로 동결 기준선(헌법 27조)을 수정할 필요가 없다.
아바타가 `NetworkPlayer`를 안 건드리고 `PlayerAvatarVisual`을 따로 둔 것과 같은 방식이다.

### 리드도 이미 알고 있었다

`docs/08_Backend_API_명세서.md` — Lease 만료 처리 계약 마지막 줄:

> 현재 내부 방문자 퇴장은 Unity Server가 처리할 수 있도록 Realtime event 또는 주기 검증 계약을 **별도로 확정한다.**

새로 발견한 문제가 아니라 **문서에 미확정으로 남아 있던 숙제**다.

## 3. 선택지

| | **A. Netcode 방송** (게임 서버 경유) | **B. SSE** (React 경유) |
|---|---|---|
| 경로 | Spring → Unity 서버 → 세션 전원 | Spring → 각 브라우저 React → 브리지 → Unity |
| 일관성 경계 | ✅ 전달 경계 = **월드 세션** 경계 | ❌ "SSE 연결이 살아있는 사람" 경계 |
| 동시성 | 세션 전원이 같은 틱에 받는다 | 클라이언트 연결 상태에 좌우 |
| 늦게 들어온 사람 | Spawn 시 현재 값 수신 (자동) | 연결 시 스냅샷을 별도 구현해야 함 |
| Spring 연결 수 | 세션당 1 | 접속자당 1 |
| Spring 장애 시 | 마지막 상태로 **전원 일관** | 클라이언트별로 제각각 낡음 |
| 선례 | 아바타 (`OnEncodedChanged`) | AI 스트리밍 (spec 008) |
| 새 비용 | Unity 서버 ↔ Spring 링크 (없던 것) | Unity 서버 무수정, 브리지 재사용 |

**BE 의견: A를 권한다.** 일관성 경계가 월드 세션이므로 전달도 그 경계로 나가야 한다.
B를 고르면 스냅샷·재연결 재동기화·버전 판별을 직접 만들어야 하는데, 그건 A에서 Netcode가 이미 주는 것들이다.

다만 B도 근거가 있다 — React가 이미 SSE 소비자이고 `AvatarBridge` 선례로 React→Unity 경로가 검증돼 있으며,
Unity 서버를 건드리지 않는다. **B로 간다면 아래 넷이 반드시 함께 와야 한다**: 연결 직후 전체 스냅샷 /
재연결 시 스냅샷 재전송 / 이벤트 버전 / 저빈도 폴백 폴링. 스냅샷 없는 SSE는 폴링보다 나쁘다(영구 불일치).

## 4. 신호에 데이터를 싣지 않는다

어느 경로든 Layout JSON을 통째로 방송하지 않는다 (부스당 오브젝트 12개, 헌법 22조).

```
서버 → 클라이언트:  { slotId, boothId, revision }
클라이언트: revision이 내가 그린 것과 다르면 → Spring 재조회 → BoothRuntime.Rebuild()
```

몇 바이트로 끝나고, revision 비교라 중복·순서 역전에 안전하며, 놓쳐도 다음 신호에서 따라잡는다.

## 5. BE가 준비해야 할 것 — revision

지금 스키마로는 부족하다.

| 대상 | 현재 | 상태 |
|---|---|---|
| Layout 게시 | `booth_layout_published_versions.version_no` | ✅ 있다 |
| 부스 외관 | `booths.facade_code` | ❌ 버전 없음 |
| 슬롯 점유 | `booth_leases.status` | ❌ 버전 없음 |

외관은 `booths`, layout은 별도 테이블이라 따로 두면 클라이언트가 둘을 각각 추적해야 한다.
**부스 단위 revision 하나로 묶어** 외관·layout·점유 중 무엇이 바뀌든 올라가게 하면 클라이언트 로직이
`revision 다르면 재조회` 한 줄이 된다.

## 6. 곁가지로 발견한 것 — facade 스키마 불일치

| | |
|---|---|
| V1 마이그레이션 | `booths.facade_code VARCHAR(50)` — **단일 컬럼** |
| `docs/09_DB_ERD_DB_설계서.md` | `facade_theme_code` · `facade_primary_color` · `facade_sign_text` · `facade_logo_url` — **4개 컬럼** |
| `docs/08_Backend_API_명세서.md` | 응답이 `facade: { themeCode, primaryColor, signText, logoUrl }` |
| 구현 | Unity·Backend **양쪽 다 없음**. `festa-unity` 전체에 `facade` 문자열 0건 |

외관은 `docs/02` 기준 **STUDIO-13, P1**이라 아직 아무도 안 쓴다. 지금 정리하면 비용이 0이지만
데이터가 쌓인 뒤에는 마이그레이션이 필요하다. **005 착수 전에 스키마를 어느 쪽으로 맞출지 정해야 한다.**

## 7. 004에서 내린 결정

실시간 전파를 넣지 않는다. **만료된 부스에 접근하면 거부하고 사유를 안내**하는 것까지만 한다 (FR-019).

그 결과 만료된 부스가 **화면에는 남아 있는데 들어가면 거부되는** 상태가 생긴다. 안내 문구가 그것을 설명한다.
P0에서 감당 가능하다고 판단했고, 진짜 해결은 005·006에서 부스 수정 기능이 생길 때 함께 한다.

## 8. 정해야 할 것

1. 전달 경로 **A(Netcode) vs B(SSE)** — Unity·FE 합의 (헌법 24조)
2. **부스 단위 revision** 도입 — BE, 소관이 004(점유)·005(layout·외관)에 걸침
3. **facade 스키마** — V1 단일 컬럼 vs docs/09 4컬럼 (005 착수 전)
