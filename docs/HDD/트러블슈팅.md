### T-122. GitHub 이슈만 보고 GitLab 전용 코멘트 3건을 놓쳤다 (2026-08-25, 해결)

- **증상**: 미푸시 작업 3건이 이슈 합의와 맞는지 정합성 보고를 썼는데, **GitLab에만 있는 노트 3건을 못 봤다** — #48의 내 승인 요청 2건(2026-08-24 13:19·14:48)과 #69 박준우 님 회신. 그래서 "019 초안은 아직 게시되지 않았다"고 보고했다. **이미 게시돼 있었고**, 그 노트에 담긴 개수 오류(아래 T-121)와 "docs/08은 이미 고쳤다"는 보고도 함께 놓쳤다.
- **원인**: `git remote`에 **GitLab 하나뿐이고** GitHub은 없다(`gh`는 `-R kanghyunsoon/ssafesta` 없이는 동작하지 않는다). 그래서 반사적으로 GitHub을 "원래 트래커"로 취급했는데, 실제로는 **GitLab #1~#83이 GitHub 이관 미러**이고(강형순, 2026-08-24 10:40 일괄 이관) **이관 후 새로 달린 노트는 GitLab에만 쌓인다.** 번호가 같아서 같은 내용이라고 착각한 것이 결정적이다. GitLab 고유 신규도 있다 — #84(내 배정)·#89~#96, #85~#88은 결번.
- **해결**: GitLab API로 92건 전수 + 관련 이슈의 노트 전수를 다시 읽었다. 미러 구조·고유 신규를 확인하고 1차 보고의 정정 3건을 다시 냈다. GitLab↔GitHub 사용자명도 대조해 두었다 — `gudtnslwkd`=강형순(GitHub `kanghyunsoon`) · `dream_hyeon`=김가현(`ghkim1632`) · `rammerg`=박준우(`busypark`) · `powerful7305`=정승욱(`Alexjung0115`, 커밋 이메일로 확인) · `colosair`=이정헌(동일) · `ejraks1548`=나(`strdeok`).
- **예방**: **이슈 상태는 GitLab을 정본으로 본다.** GitHub은 이관 이전 이력 참조용이다. 빠른 판별법 — GitLab `user_notes_count`가 GitHub 코멘트 수보다 크면 GitLab 전용 노트가 있다는 신호다(예: #48은 GitLab 15 vs GitHub 12). 멘션도 GitLab 핸들로 써야 걸린다 — `@kanghyunsoon`은 GitLab에서 아무에게도 닿지 않는다.

### T-121. 승인 요청 개수를 표의 행 수로 세어 틀리게 게시했다 (2026-08-24, 해결)

- **증상**: GitLab #48 승인 요청 노트에 새로 정한 이름을 **17개**(rule 15 + code 1 + `unavailableReason` 1)로 적었는데 실제는 **18개**였다. `ITEM_COUNT_INVALID` 하나가 빠졌다. 리드가 그대로 승인하면 그 rule은 미승인으로 남고, 구현 시점에 다시 승인을 받아야 한다.
- **원인**: 계약 문서가 `VARIABLE_COUNT_INVALID`·`ITEM_COUNT_INVALID`를 **상한이 같아(각 100) 한 행에 묶어** 놨고, 노트를 쓸 때 그 표를 **행 단위로 셌다.** 문서에는 *"행 수로 세면 15개로 잘못 나오니 이름으로 센다"* 는 경고를 **내가 직접 적어놓고 그 경고에 걸렸다.** 게시(14:48)가 개수 정정 커밋(`2f0b2f6`, 15:45)보다 **57분 앞서** 있어서, 노트는 문서의 옛 문장("★ 16개뿐이다")을 근거로 15+1+1을 재구성했다 — ★ 이름 집합은 처음부터 18개로 같았고 바뀐 것은 개수를 적은 **문장**뿐이다.
- **해결**: `game-api.md`에서 `` `NAME` ★ `` 패턴을 전수 추출해 18개(rule 16 + code 1 + reason 1)를 확정하고, GitLab #48에 정정 노트를 게시했다(note 2749214). MR !1 설명의 승인 요청 목록에도 18개 이름을 전부 나열했다. ④(`GAME_LIMIT_EXCEEDED`) 승인 시 19개가 된다는 것도 함께 정정했다(노트에는 18로 적혀 있었다).
- **예방**: **개수를 외부에 알릴 때 표를 눈으로 세지 않고 추출해서 센다.** 그리고 한 행에 이름 2개를 묶은 표는 개수의 근거가 될 수 없다 — 승인 대상은 표와 별도로 **이름 단위 평면 목록**을 두고 그것을 센다. 문서에 "이렇게 세면 틀린다"는 경고를 적어야 할 상황이면, 애초에 그 표를 개수의 출처로 쓰지 않는 편이 맞다.

### T-120. speckit 스크립트가 #43 파트 분리 구조에서 동작하지 않는다 (2026-08-24, 우회)

- **증상**: 013a BE 플랜을 만든 뒤 `bash .specify/scripts/bash/setup-tasks.sh --json`이 `ERROR: plan.md not found in .../specs/013-avatar-customization`으로 죽었다. plan.md는 `BE/` 아래에 있고 feature 루트에는 없다. 앞 단계 `setup-plan.sh`는 **실패하지 않고 더 나쁘게 동작**했다 — feature 루트에 plan.md를 만들어서, 손으로 `BE/`로 옮겨야 했다.
- **원인**: 스크립트가 `$FEATURE_DIR/plan.md`·`$FEATURE_DIR/spec.md`를 고정 경로로 본다(`setup-tasks.sh:32,38`). 그런데 이 저장소는 #43 합의로 **공통 spec.md는 루트, 실행 산출물(plan·research·data-model·quickstart·tasks)은 파트 디렉터리**에 두기로 했다. `feature.json`을 `BE/`로 돌려도 거기엔 spec.md가 없어서 두 번째 검사에 걸린다 — 어느 경로를 가리켜도 통과하지 못하는 구조다. spec 005·019가 이미 같은 배치(`BE/`+`FE/`)라 **파트 분리된 spec 전부에 해당**한다.
- **해결(우회)**: 스크립트를 건너뛰고 `.specify/templates/tasks-template.md`를 직접 읽어 `BE/tasks.md`를 생성했다. 스크립트가 제공하는 것은 경로 해석과 템플릿 내용뿐이라 산출물 품질에는 영향이 없다. 005의 `BE/tasks.md`도 같은 경로로 만들어진 것으로 보인다.
- **예방**: 파트 분리된 spec에서는 `setup-plan.sh`/`setup-tasks.sh`의 성공·실패를 게이트로 삼지 않는다. `setup-plan.sh`는 **성공해도 산출물 위치가 틀리므로** 실행 후 파트 디렉터리로 옮겼는지 확인한다. 스크립트를 고치는 편이 근본 해결이지만 `.specify/`는 spec-kit 원본 구조라 팀 합의 대상이다(AGENTS.md §1 — 재설치 금지 경고가 붙은 영역).

### T-119. Bean Validation 오류 계약을 실제로 태우는 요청이 본선에 하나도 없었다 (2026-08-23, 부분 해결)

- **증상**: #58 확정 계약(`rule: "FIELD_INVALID"` + `field`)을 `GlobalExceptionHandler`의 Bean Validation 분기에 반영하고 통합 테스트를 붙이려는데, **호출할 endpoint가 없었다.** `backend/src/main`에 `@Valid`·`@NotBlank`·`@Size`가 **0건**이라 `MethodArgumentNotValidException`이 던져지는 경로 자체가 존재하지 않는다. `spring-boot-starter-validation`은 의존성에 있어서 "쓰고 있다"고 착각하기 쉬웠다.
- **원인**: 검증을 전부 서비스 계층에서 손으로 하고(`BoothFacadeService`의 hex·길이·URL 검사가 그 예) `ApiException`으로 던져 왔다. Bean Validation 분기는 처음 작성된 이후 **한 번도 실행된 적이 없는 코드**였고, 그래서 필드명이 `rule` 자리에 들어가는 결함(#58 §3)이 그렇게 오래 남을 수 있었다. 아무도 응답을 본 적이 없으니 아무도 틀린 걸 못 봤다.
- **해결(부분)**: 테스트 소스에 `BeanValidationProbeController`(`@Valid` DTO 1개)를 두어 실제 요청 → 필터 → 시큐리티 → advice → 직렬화 전 구간으로 계약을 고정했다. 컨트롤러는 테스트 소스에 있고 앱의 컴포넌트 스캔에 잡히므로 통합 테스트 컨텍스트가 갈라지지 않는다(중첩 `@TestConfiguration`으로 만들면 Postgres·Redis 컨테이너가 한 벌 더 뜬다). **남은 것**: 본선 DTO가 Bean Validation을 채택하기 전까지 FE는 이 rule을 실물에서 볼 수 없다.
- **예방**: 오류 계약을 고칠 때 **그 분기를 실제로 실행하는 요청이 있는지 먼저 확인한다.** 없으면 계약은 "합의됨·미관측" 상태이고, 그 사실을 계약 문서에 적거나 프로브로 고정한다. 죽은 분기에 맞춘 계약은 첫 사용자가 디버깅하게 된다.

### T-118. Boot 4.1 테스트에서 `@Autowired ObjectMapper`가 빈 없음으로 컨텍스트를 못 띄움 (2026-08-23, 해결)

- **증상**: `ErrorEnvelopeIntegrationTest`에 `@Autowired ObjectMapper json`을 추가했더니 **컴파일은 통과하고** 그 클래스의 테스트 15개가 전부 `UnsatisfiedDependencyException`으로 죽었다 — `No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper'`. 새로 쓴 2개가 아니라 **원래 통과하던 13개까지 같이** 실패해서 처음엔 내 테스트가 아니라 컨텍스트가 깨진 줄 알았다(필드 주입이라 클래스 전체가 못 만들어진다).
- **원인**: Boot 4.1은 **Jackson 3**(`tools.jackson.core:jackson-databind:3.1.4`)로 웹 직렬화를 하고 `JacksonAutoConfiguration`이 등록하는 빈은 `tools.jackson.databind.json.JsonMapper`다. Jackson 2(`com.fasterxml.jackson.core:jackson-databind:2.21.4`)도 **클래스패스에는 그대로 있어서**(yaml·jsr310 등이 끌고 온다) IDE 자동 임포트가 조용히 Jackson 2 쪽 `ObjectMapper`를 골라준다. 타입은 존재하고 빈만 없는 조합이라 컴파일 단계에서 아무 경고가 없다. 애노테이션 패키지(`com.fasterxml.jackson.annotation.*`)는 3에서도 그대로라 `@JsonInclude` 임포트가 멀쩡한 것이 더 헷갈린다.
- **해결**: `tools.jackson.databind.json.JsonMapper`로 주입 타입 교체. 209/209 통과.
- **예방**: 이 저장소에서 Jackson 타입을 임포트할 때 **`tools.jackson.*`가 기본**이다. `com.fasterxml.jackson.databind.*`가 보이면 자동 임포트가 잘못 고른 것이다(애노테이션 `com.fasterxml.jackson.annotation.*`만 예외). 두 버전이 공존하므로 "임포트가 되니 맞다"는 근거가 되지 않는다.

### T-117. develop→back 머지가 festa-unity 1,456개를 충돌 없이 삭제 상태로 커밋함 (2026-08-21, 해결)

- **증상**: `origin/develop`을 back에 머지해 공유 문서 충돌 5건을 해소·커밋(`fbcbec0`)·푸시했는데, 사후 `git diff origin/develop back`에서 festa-unity 파일 1,456개가 back 트리에 없는 상태로 확인됐다. 이대로 back→develop PR을 만들면 develop의 festa-unity가 통째로 삭제 스테이징된다. 머지 전 `git merge-tree` 시뮬레이션은 "충돌은 문서 5건뿐"이라 정상처럼 보였다.
- **원인**: back에 Unity 프로젝트 제거 이력(`c3e1f90`)이 있고, develop의 festa-unity 대부분이 merge-base 이후 변경되지 않아 3-way 머지의 **"한쪽만 변경한 쪽이 이긴다"** 규칙으로 삭제가 조용히 채택됐다. `docs/26` ①-16이 back→develop 방향에서 경고한 원인("삭제 이력 → 1,462개 충돌 없이 삭제 스테이징")이 반대 방향 머지에서도 그대로 성립한다. **"충돌 0"은 "유실 0"이 아니다.**
- **해결**: `git checkout origin/develop -- festa-unity`로 전량 복원 후 후속 커밋. 예외 2건은 파일별 이력으로 판별 — ① `Assets/_Project/Scenes/main.unity`는 back 사본에 과거 충돌 마커(`<<<<<<< HEAD`/`>>>>>>> game`)가 커밋돼 있던 오염본이라 develop 정상본 채택. ② `Docs/avatar-customization-contract.md`는 base 이후 develop 무변경·back이 의도적으로 폐기 처리(specs/README §6과 세트)한 것이라 back본 유지.
- **예방**: 파트 브랜치 간 머지에서는 충돌 목록이 아니라 **머지 직후 `git diff --name-status <머지대상> HEAD`의 삭제(D)·추가(A) 목록**을 검증한다. 이 저장소는 브랜치마다 폴더 구성이 다르므로(T-115와 같은 뿌리) 폴더 단위 유실이 항상 조용히 성립할 수 있다. 시뮬레이션 단계에서도 `merge-tree`의 CONFLICT 줄만 보지 말고 결과 트리의 파일 수를 비교한다.

### T-116. PR 머지와 수정 푸시가 경합해 develop의 남의 문서를 지움 (2026-08-21, 해결)

- **증상**: PR #38(back→develop 반입)을 자체 점검하다 spec 005 `spec.md`가 develop 쪽 갱신분(colosair의 FE 검토 #12·SC-002 재작성 #15)을 덮어쓴다는 결함을 발견하고 수정 커밋(`5a078f0`)을 푸시했는데, **푸시 직전에 머지 버튼이 눌려** 수정 전 상태로 병합됐다. develop에서 남의 검토 기록이 지워진 채 한동안 노출됐다.
- **원인**: ① 파일 단위 checkout 반입이 "develop 쪽에서도 그동안 갱신된 파일"을 구분하지 않았다 — #24가 경고한 "같은 파일 두 갈래" 케이스를 코드 반입에서 재현. ② 열린 PR에 수정을 푸시하는 동안에도 머지가 가능하다 — 리뷰 시점 tip과 머지 시점 tip은 다를 수 있다. ③ 머지 확인 때 backend 파일 개수만 보고 **수정 커밋 포함 여부를 검증하지 않았다.**
- **해결**: 수정 커밋 하나만 담은 후속 PR #39로 복원. `git show origin/develop:...`으로 FE 검토 섹션과 FR-014~018이 공존함을 재확인.
- **예방**: ① 반입 전 수정 파일마다 `git log <merge-base>..origin/develop -- <파일>`로 develop 쪽 후속 커밋을 확인한다 — 0건이 아니면 통째 checkout 금지, 접붙임으로 간다. ② PR에 뒤늦게 수정을 푸시했으면 머지 전에 "tip == 마지막 검토 커밋"인지 확인을 요청한다. ③ 머지 검증은 파일 존재가 아니라 `git merge-base --is-ancestor <수정커밋> origin/develop`로 한다.

### T-115. develop 워킹트리에서 grep해 "avatar 코드 0건"으로 오판 → 이슈에 틀린 근거 게시 (2026-08-21, 해결)

- **증상**: issue #24 코멘트에 "Spring 미구현 — `backend/src/main/`에 avatar 관련 코드 0건"이라고 적었는데, 실제로는 `User.java`에 `avatarCode` 엔티티 필드가 있었다. 공개 정정 코멘트를 따로 올려야 했다.
- **원인**: develop 브랜치로 전환한 상태에서 디스크를 grep했다. develop에는 `backend/` 자바 소스가 없으므로(파트 브랜치 전용) 검색 결과 0건은 "코드가 없다"가 아니라 **"지금 체크아웃에 파일이 없다"**였다. 도구가 완전히 정상 동작했기 때문에 더 그럴듯해 보였다.
- **해결**: `git ls-tree -r origin/back` + `git show origin/back:<파일>` 조합으로 **브랜치를 명시해** 재검색하고, #24에 정정 코멘트를 게시했다.
- **예방**: **브랜치 상태에 의존하는 사실 확인은 워킹트리 grep을 믿지 않는다.** 특히 이 저장소는 브랜치마다 폴더 구성이 다르므로(back에만 `backend/`, game에만 `festa-unity/` 최신), 남에게 보고할 사실은 `git show origin/<branch>:<path>` 기준으로 확인한다.

### T-114. 최초 저장 경합에서 남의 저장이 조용히 덮어써짐 (2026-08-21, 해결)

- **증상**: `BoothLayoutConcurrencyIntegrationTest.onlyOneOfTheConcurrentFirstSavesWins`가 `expected:<1> but was:<2>`로 실패했다. 8스레드가 동시에 **최초 저장**을 하면 둘이 성공한다. **앞서 네 번 돌렸을 때는 전부 통과했다** — 타이밍으로 가려져 있었다.
- **원인**: `drafts.saveAndFlush(new BoothLayoutDraft(...))`가 INSERT가 아니었다. `booth_layout_drafts`는 **PK를 우리가 직접 할당**(`booth_id`)하므로 Spring Data의 `isNew()`가 `false`를 돌려주고, `save()`가 `persist()`가 아니라 **`merge()`**를 부른다. merge는 SELECT 후 없으면 INSERT, **있으면 UPDATE**다. 그래서 A가 커밋한 뒤 B의 merge가 SELECT에서 A의 행을 보고 UPDATE로 전환해 **A의 저장을 통째로 덮어쓰고 성공을 반환**했다. FR-014가 막으려던 바로 그 손실이다.
- **왜 안 잡혔나**: 두 스레드가 **둘 다 커밋 전에** INSERT를 시도하면 PK 제약이 하나를 떨궈서 기대대로 동작한다. 실패하려면 "A 커밋 → B의 merge SELECT" 순서가 필요한데 이게 매번 나오지 않는다. `@RepeatedTest(5)`가 아니었으면 영영 못 봤을 것이다.
- **해결**: 최초 저장을 **한 문장**으로 바꿨다 — `INSERT … ON CONFLICT (booth_id) DO UPDATE SET revision = booth_layout_drafts.revision WHERE booth_layout_drafts.revision = 0`. revision은 1에서 시작하므로 DO UPDATE 분기는 **절대 매치되지 않고**, 진 쪽은 영향 행 0을 받아 `LayoutRevisionConflictException`이 된다. 갱신 경로는 기존 조건부 UPDATE 그대로다.
- **예방**: **PK를 직접 할당하는 엔티티에 `save()`를 쓰지 않는다.** 그 조합은 조용히 merge가 되고, merge는 "없으면 만들고 있으면 덮어쓴다"라 낙관적 잠금과 정반대로 동작한다. 필요하면 `Persistable.isNew()`를 구현하거나 지금처럼 INSERT 문을 직접 쓴다. 그리고 **동시성 테스트는 반드시 반복 실행**한다 — 004의 T-110과 같은 교훈이 다른 얼굴로 다시 나왔다.

### T-113. 004 예외가 새 endpoint에서 500으로 나감 (2026-08-20, 해결)

- **증상**: spec 005 layout API 테스트에서 없는 부스 조회가 `404` 대신 **500**, 만료 부스 조회가 `409` 대신 **500**이었다. 같은 예외를 쓰는 004의 `GET /booths/{id}`는 정상이라 처음에는 새 코드 문제로 보였다.
- **원인**: `BoothNotFoundException`·`BoothExpiredException`이 **평범한 `RuntimeException`**이었다. 상태 코드는 예외가 아니라 **`BoothController`의 try/catch 안에** 있었고, 그 catch를 쓰지 않는 새 컨트롤러에서는 전역 핸들러의 catch-all에 걸려 500이 됐다. 004에서는 우연히 모든 사용처가 그 컨트롤러 하나였기 때문에 드러나지 않았다.
- **해결**: 두 예외를 `ApiException` 상속으로 바꿔 각자 `ErrorCode`를 갖게 했다. 컨트롤러의 번역 코드는 삭제했다 — 이제 어디서 던져도 같은 상태·같은 코드로 나간다.
- **예방**: **도메인 예외의 의미가 고정돼 있으면 상태 코드를 예외에 붙인다.** 컨트롤러에서 번역하면 "그 컨트롤러에서만" 맞는 코드가 되고, 두 번째 사용처가 생길 때 조용히 500이 된다. 전역 catch-all이 있으면 이런 누락이 **에러가 아니라 잘못된 성공 코드**로 보인다는 점이 특히 위험하다.

### T-112. Spring Boot 4에서 `ObjectMapper` 빈을 찾지 못함 (2026-08-20, 해결)

- **증상**: `ApiErrorWriter`를 추가한 뒤 `ErrorEnvelopeIntegrationTest` 9건이 전부 `ApplicationContext` 로딩 실패로 죽었다. 원인 줄은 `No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper' available`. **컴파일은 통과했기 때문에** 클래스패스에 그 타입이 존재하기는 한다.
- **원인**: **Spring Boot 4는 Jackson 3을 쓰고, Jackson 3의 databind는 `tools.jackson.databind` 패키지다.** 프로젝트에 남아 있는 `com.fasterxml.jackson.*`은 어노테이션(`jackson-annotations` 2.21 — Jackson 3도 어노테이션은 이 패키지를 그대로 쓴다)과 전이 의존성뿐이라, 컴파일은 되지만 **auto-configuration이 등록하는 빈은 `tools.jackson.databind.ObjectMapper`** 여서 주입 대상이 없었다.
- **해결**: `ApiErrorWriter`의 import를 `tools.jackson.databind.ObjectMapper`로 바꿨다. 어노테이션(`@JsonInclude`)은 `com.fasterxml.jackson.annotation` 그대로 둔다.
- **예방**: 이 프로젝트에서 Jackson 타입을 직접 주입·사용할 때는 **databind/core는 `tools.jackson`, 어노테이션은 `com.fasterxml.jackson.annotation`**. IDE 자동 import가 2.x 경로를 먼저 제안하므로 **컴파일 성공을 근거로 삼지 말 것** — 이 오류는 런타임 컨텍스트 로딩에서만 드러난다.

### T-111. 003 지갑 테스트가 004 부하 테스트 때문에 깨짐 (2026-08-20, 해결)

- **증상**: T-110 수정 후 004 테스트는 전부 통과하는데, 손대지도 않은 `WalletServiceIntegrationTest.spendingReducesTheBalanceAndRecordsANegativeEntry`가 `expected:<false> but was:<true>`로 실패했다. `alreadyApplied()`가 true — 이미 적용된 원장이라는 뜻이다.
- **원인**: 그 테스트가 멱등성 키를 **`"LEASE_PAYMENT:BOOTH_LEASE:317"`로 하드코딩**하고 있었다. `coin_ledger_entries.idempotency_key`는 **전역 UNIQUE**이고 테스트 DB는 클래스 간 공유된다. 004 부하 테스트가 임대를 1,400건 넘게 만들면서 **실제 lease id 317**에 도달했고, 004가 만든 진짜 결제 원장과 키가 겹쳤다. 003 작성 시점에는 임대가 40건 남짓이라 317에 닿을 일이 없어 드러나지 않던 잠복 결함이다.
- **해결**: 하드코딩된 키(`317`·`401`·`999`, 그리고 `MINIGAME_SESSION:7`)를 `leaseReference(userId)` = `"T" + userId`로 바꿨다. userId는 실행마다 유일하고, 접두사가 숫자가 아니라 **실제 참조값과 절대 겹칠 수 없다**.
- **예방**: **전역 UNIQUE 컬럼을 검증하는 테스트에 리터럴을 박지 않는다.** 특히 멱등성 키처럼 다른 spec이 같은 형식으로 실제 데이터를 만드는 값은 반드시 실행마다 유일한 값으로 만든다. "내 테스트만 통과하면 된다"가 성립하지 않는 이유는 DB가 공유되기 때문이다. 새 부하 테스트를 넣을 때는 **기존 테스트 전체를 한 번 돌려서** 이런 잠복 충돌을 깨워본다.

### T-110. 한 회원이 부스 7개를 동시에 임대하고 700코인을 지불 (2026-08-20, 해결)

- **증상**: 부하 시나리오 테스트를 새로 만들다가 발견했다. 한 회원이 **7개 슬롯에 동시에** 임대를 요청하면 7건 전부 성공한다. `보유임대=7 차감코인=700`, round 0에서 100% 재현. 100명이 한 슬롯을 경합하는 10,000건 시나리오는 완벽하게 통과(성공 정확히 100건)했기 때문에 기존 테스트로는 절대 안 잡혔다.
- **원인**: `booth_leases`의 인덱스는 `ux_booth_leases_active_slot` **하나뿐**이고 이건 `slot_id` 기준이다. **슬롯이 서로 다르면 아예 충돌하지 않는다.** "1인 1임대"(D01, FR-005)를 지키는 것은 `BoothLeaseService`의 `findValidByLesseeUserId` 조회 한 줄이 전부였는데, 이건 순수한 check-then-act라 7개 스레드가 전부 통과한 뒤 각자 다른 슬롯에 INSERT하면 전부 성공한다. 기존 2스레드 테스트는 **같은 슬롯**만 경합시켜서 이 경로를 밟은 적이 없었다.
- **해결**: 두 층으로 막았다.
  - **A. DB 제약** — `V6__booth_lease_one_active_per_member.sql`에 `ux_booth_leases_active_lessee`(`lessee_user_id` 부분 UNIQUE, `status='ACTIVE'`) 추가. 기존 위반 행을 정리한 뒤 인덱스를 만든다.
  - **B. 지갑 행 락 선점** — `WalletService.lockOwner(userId)`를 `lease()` 진입부에서 호출해 같은 회원의 동시 요청을 지갑 행 하나에서 직렬화한다. 뒤 요청은 재조회 시 앞선 임대를 보고 정상 경로로 거절된다.
  - A는 최종 방어선, B는 A가 발화하지 않게 하는 큐다. 수정 후 2b 시나리오 결과는 `{ActiveLeaseLimitException=180, SUCCESS=30}` — 제약 위반(`SlotAlreadyLeasedException`)이 **0건**이다.
- **함정 하나 더**: A를 넣으면 `ux_booth_leases_active_slot`이 만들었던 것과 **똑같은 덫**이 슬롯이 아니라 회원 쪽에 생긴다. 이 인덱스도 `ends_at`을 안 보므로, 내 만료 임대가 `ACTIVE`로 남아 있으면 내가 영구히 재임대 불가다. 그래서 `releaseStaleLeasesOfMember(userId, now)`를 같은 트랜잭션에 반드시 함께 넣어야 한다 (FR-017과 같은 처방).
- **덤**: B 덕분에 같은 슬롯 광클의 자기 요청 오탐도 사라졌다. 수정 전에는 1,500번 광클 중 **270번(18%)이 자기 임대에 대해 `BOOTH_SLOT_ALREADY_LEASED` 409**를 받았는데, 수정 후에는 전부 멱등 경로(`alreadyHeld`, 200 OK)로 처리된다.
- **같은 패턴이 하나 더 있었다 (2026-08-20 추가 조치)**: 고쳐놓고 나서 `booths`를 다시 봤더니 `owner_user_id`에도 UNIQUE가 없었다. `BoothRepository.findByOwnerUserId`는 `Optional`을 반환한다 — **코드가 "회원당 부스 1개"를 가정하는데 제약이 없다.** 두 행이 생기면 이 조회가 `IncorrectResultSizeDataAccessException`으로 터져서 그 회원은 임대가 영구히 불가능해진다. 실제로 7슬롯 동시 광클은 임대 7건뿐 아니라 **부스도 7개** 만들고 있었다. 지금은 B(지갑 락)가 유일한 생성 경로를 직렬화해서 가려져 있지만 그건 004의 우연이지 규칙이 아니다 — **005는 지갑을 안 거치고 부스를 편집한다.** `V7__booth_one_per_owner.sql`로 `ux_booths_owner`를 추가했다(중복 부스의 임대를 생존 부스로 재연결한 뒤 삭제). 부하 테스트 2b에 부스 개수 단언을 추가해 고정했다.
- **예방**: **"제약이 최종 방어선"이라고 적어둔 규칙마다 실제로 그 제약이 있는지 확인한다.** 004는 슬롯 독점만 제약으로 막고 1인 1임대는 코드로만 막았는데, 커밋 메시지와 plan에는 둘 다 DB가 지키는 것처럼 읽혔다. 그리고 동시성 테스트는 **같은 자원 경합만이 아니라 "한 행위자가 여러 자원을 동시에"도 반드시 넣는다** — 후자가 훨씬 늦게 발견된다.

### T-107. 임대 테스트가 잔액을 100 적게 계산 (2026-08-19, 해결)

- **증상**: spec 004 임대 API 테스트에서 `balanceAfter`가 `expected:<100> but was:<150>`로 실패했다. 서비스 계층 테스트는 전부 통과하는데 MockMvc 테스트만 틀렸다.
- **원인**: 코드가 아니라 **테스트가 틀렸다.** 003의 `DailyCoinGrantInterceptor`가 **인증된 모든 요청**에서 일일 50코인을 지급한다. 테스트가 `wallets.balanceOf()`로 잔액(200)을 먼저 읽고 그 뒤 HTTP 임대를 호출했는데, 그 호출이 먼저 일일 지급을 태워서 실제로는 250에서 100이 빠졌다. 서비스를 직접 부르는 테스트는 HTTP를 안 타서 이 간섭이 없었다.
- **해결**: 임대 전에 `GET /api/v1/wallets/me`를 한 번 호출해 일일 지급을 먼저 소진시킨 뒤 기준 잔액을 읽도록 했다. 003 지갑 테스트에서 쓴 것과 같은 방법이다.
- **예방**: 003을 소비하는 spec의 **HTTP 테스트는 일일 지급이 끼어든다는 것을 전제로** 짠다. 잔액 기대값을 상수로 박지 말고, 인증 요청을 한 번 흘린 뒤 기준값을 읽는다. 서비스 계층 테스트와 HTTP 테스트의 결과가 다르면 인터셉터를 먼저 의심한다.

### T-108. 만료 시나리오를 만들다가 CHECK 제약 위반 (2026-08-19, 해결)

- **증상**: 만료 부스 접근 테스트에서 `new row for relation "booth_leases" violates check constraint "booth_leases_check"`가 발생했다.
- **원인**: `UPDATE booth_leases SET ends_at = now() - interval '1 hour'`로 **종료 시각만** 과거로 당겼다. V1 스키마의 `booth_leases`에는 `CHECK(ends_at > starts_at)`가 걸려 있어서, `starts_at`은 방금인데 `ends_at`만 과거가 되면 제약에 걸린다.
- **해결**: `starts_at`도 함께 옮겼다 — `starts_at = now() - interval '25 hours', ends_at = now() - interval '1 hour'`. `specs/004-booth-slot-lease/quickstart.md`의 수동 검증 SQL에도 같은 오류가 있어서 함께 고쳤다.
- **예방**: 시간 필드를 손으로 조작해 만료를 재현할 때는 **두 끝을 함께 옮긴다.** 테스트뿐 아니라 문서에 적어둔 운영 SQL도 실제로 실행해 보고 넣는다 — 이번에는 문서에 못 쓰는 명령을 적어둘 뻔했다.

### T-109. `cd`가 실패한 `&&` 체인에서 파일 하나가 조용히 누락 (2026-08-19, 해결)

- **증상**: 004 리포지토리들을 한 번에 작성했는데 `BoothSlotRepository.java`만 생기지 않았다. 다른 파일은 전부 정상이었다.
- **원인**: `cd <이미 그 안에 있는 경로> && cat > BoothSlotRepository.java <<EOF` 형태로 시작한 스크립트에서 **`cd`가 실패**해 첫 번째 `cat`이 건너뛰어졌다. 뒤따르는 `cat`들은 `&&`로 묶이지 않아 그대로 실행됐다. 그래서 "대부분 성공, 하나만 누락"이라는 헷갈리는 결과가 나왔다.
- **해결**: 누락된 파일을 다시 작성했다. 컴파일 단계에서 잡혔다.
- **예방**: 여러 파일을 쓰는 스크립트는 **첫 명령만 `&&`로 묶지 않는다.** 작성 후 `ls`로 파일 수를 확인하고, 이후 단계는 절대 경로를 쓴다.

### T-105. Swagger UI가 401로 열리지 않음 (2026-08-19, 해결)

- **증상**: `http://localhost:8080/swagger-ui.html`이 `401`을 반환해 Swagger 화면에 들어갈 수 없었다. 반면 `/swagger-ui/index.html`과 `/v3/api-docs`는 `200`이었다.
- **원인**: `SecurityConfiguration`의 permitAll 목록에 `/swagger-ui/**`는 있지만 **`/swagger-ui.html`이 없었다.** springdoc의 진입점은 `/swagger-ui.html`이고 이것이 `/swagger-ui/index.html`로 redirect하는데, 패턴 `/swagger-ui/**`는 이 경로를 포함하지 않는다. 그래서 redirect가 일어나기 **전에** Security가 401로 막았다. 사람이 실제로 입력하는 주소만 정확히 막히는 형태였다.
- **해결**: permitAll 목록에 `/swagger-ui.html`을 명시적으로 추가했다. 새로 빌드한 앱을 8081에 띄워 확인한 결과 `302`(정상 redirect)로 바뀌었다.
- **예방**: 와일드카드 패턴이 진입점 URL을 덮는다고 가정하지 않는다. 공개해야 할 경로는 **사람이 실제 입력하는 주소로** curl 검증한다 (T-102와 같은 계열의 실수다).

### T-106. 옛 IntelliJ 실행 인스턴스가 8080을 점유해 새 API가 보이지 않음 (2026-08-19, 해결)

- **증상**: wallet API를 구현하고 테스트까지 통과했는데 `localhost:8080/v3/api-docs`에 `/api/v1/wallets/me`가 없었다. 대신 **이미 제거된 관리자 endpoint**(`/api/v1/admin/users/{userId}/suspend`)가 남아 있었다.
- **원인**: 8080을 점유한 프로세스가 IntelliJ에서 **12:27에 실행된 옛 인스턴스**였다. 코드는 최신인데 실행 중인 것이 옛 빌드였다. `Win32_Process`의 `CreationDate`와 노출 endpoint 목록 두 가지가 단서였다 — "이미 지운 endpoint가 보인다"면 실행 중인 것이 옛것이다.
- **해결**: 돌고 있는 인스턴스는 건드리지 않고 새로 빌드한 jar를 **8081**에 띄워 검증했다. 8080은 IDE에서 재시작하면 반영된다.
- **예방**: "고쳤는데 그대로"면 실행 중인 프로세스의 **시작 시각**과 **노출 endpoint 목록**을 먼저 본다 (T-25·T-23과 같은 계열). 포트만 보고 최신이라고 가정하지 않는다.

### T-104. 외부 빌드가 덮어쓴 테스트 클래스로 컴파일 오류가 재현 (2026-08-19, 해결)

- **증상**: `mvnw test-compile`은 성공하는데 `mvnw test`에서 `CoinReconciliationIntegrationTest`만 5건 전부 `java.lang.Error: Unresolved compilation problems: The import com.example.ssafesta.TestcontainersConfiguration cannot be resolved`로 실패했다. 같은 import를 쓰는 다른 테스트 3종은 정상이었다.
- **원인**: Maven 컴파일 직후에 IDE/린터의 백그라운드 빌드가 그 클래스 하나만 `target/test-classes`에 덮어썼다. `ls -la`로 보면 문제 클래스만 타임스탬프가 2분 늦고 크기가 8KB가 아니라 2KB였다. 소스에는 문제가 없었다 — 실행된 것이 옛 산출물이었다. 메시지의 "Unresolved compilation problems"는 javac가 아니라 Eclipse 컴파일러(ECJ) 형식이라는 것이 단서였다.
- **해결**: `rm -rf target/test-classes/com/example/ssafesta/wallet` 후 `mvnw test-compile`로 재생성했다. 이후 53건 전부 통과했다.
- **예방**: "소스는 맞는데 결과가 다르다"면 **산출물 타임스탬프와 크기를 먼저 본다** (T-23/T-05와 같은 계열). 컴파일러가 둘(javac·ECJ)이면 어느 쪽이 마지막에 썼는지 확인한다.

### T-101. HTTP localhost에서 OAuth handoff cookie 미전송 (2026-08-19, 해결)

- **증상**: OAuth 인증 뒤 Swagger의 `POST /api/v1/auth/oauth/complete`가 401을 반환했다.
- **원인**: OAuth handoff cookie가 `Secure`로 고정되어 HTTP `localhost:8080` 테스트에서 브라우저가 저장·전송하지 않을 수 있었다. 완료 API는 해당 cookie가 없거나 만료되면 의도적으로 401을 반환한다.
- **해결**: `app.auth.cookie-secure` 설정을 추가했다. local profile은 `AUTH_COOKIE_SECURE=false`로 HTTP 테스트를 허용하며, HTTPS 배포 환경에서는 반드시 `AUTH_COOKIE_SECURE=true`로 설정한다.
- **예방**: 보안 cookie 속성은 환경 설정으로 관리하고, HTTP 로컬 테스트와 HTTPS 배포 값을 함께 검증한다.

### T-102. OAuth 완료 endpoint가 인증 필요로 매칭됨 (2026-08-19, 해결)

- **증상**: `POST /api/v1/auth/oauth/complete`가 handoff 검증 전 `401`과 `WWW-Authenticate: Bearer`를 반환했다.
- **원인**: Spring Security의 OAuth 하위 경로 와일드카드 허용 규칙이 해당 완료 endpoint에 기대대로 적용되지 않았다.
- **해결**: OAuth 완료 endpoint를 JWT Resource Server와 분리된 별도 SecurityFilterChain으로 구성했다. 이 endpoint는 1회성 handoff cookie만으로 처리하므로 Bearer 필터를 거치지 않는다.
- **예방**: 인증 방식이 다른 공개 완료 endpoint는 와일드카드 허용 규칙에만 의존하지 않고 별도 security chain 및 curl 무인증 요청으로 검증한다.

### T-103. 새 OAuth handoff가 즉시 410으로 보이는 원인 추적 (2026-08-19, 해결)

- **증상**: 새 OAuth 인증 뒤에도 브라우저 cookie는 존재하지만 완료 API가 410을 반환한다.
- **원인**: Redis handoff는 정상 생성·소비됐지만, 값의 `|` 구분자를 분리하는 Java 정규식이 잘못되어 소비 직후 파싱 검증이 실패했다. 1회성 handoff는 이미 삭제돼 응답은 410이 됐다.
- **해결**: 구분자 정규식을 literal pipe인 `"\\|"`로 수정하고, 파싱 검증을 통과한 뒤에만 소비 성공 로그를 남긴다.
- **예방**: opaque handoff 직렬화·역직렬화는 기존 회원과 가입 대기 데이터 각각을 단위 테스트로 검증한다.

### T-100. 기존 소셜 회원 OAuth callback의 LazyInitializationException (2026-08-19, 해결)

- **증상**: 기존 Google 연결 회원이 OAuth 인증을 끝낸 뒤 callback URL에 머물고 프론트 redirect가 실행되지 않았다.
- **원인**: `OAuthIdentityRepository`가 반환한 `OAuthIdentity.user`가 lazy proxy였고, OAuth 성공 핸들러가 Repository 트랜잭션 밖에서 `user.getStatus()`를 호출했다.
- **해결**: provider identity 조회 메서드에 `@EntityGraph(attributePaths = "user")`를 적용해 User를 함께 조회했다. 이후 OAuth 완료 흐름은 URL ticket 대신 1회성 HttpOnly handoff cookie와 단일 완료 API로 통합했다.
- **예방**: 웹 인증 성공 핸들러처럼 Repository 호출과 엔티티 접근 사이에 트랜잭션 경계가 있는 코드에서는 필요한 연관 엔티티를 명시적으로 fetch하거나 서비스 계층 트랜잭션에서 DTO로 변환한다.

### T-99. OAuth 최초 가입 ticket을 소비할 프론트 화면 부재 (2026-08-19, 해결)

- **증상**: 신규 Google 계정으로 인증한 뒤 `http://localhost:5173/signup?ticket=...`에서 가입이 완료되지 않는다.
- **원인**: 기존 설계가 회원 여부에 따라 `/auth/callback?ticket=...`와 `/signup?ticket=...`으로 갈라졌고, 프론트가 URL ticket을 읽어 서로 다른 API를 호출해야 했다.
- **해결**: 양쪽을 `/auth/callback`으로 통일했다. OAuth 결과는 Redis의 5분 handoff와 `Secure`·`HttpOnly` cookie로만 전달한다. 프론트는 `POST /api/v1/auth/oauth/complete`를 호출해 `AUTHENTICATED` 또는 `NICKNAME_REQUIRED`를 받고, 후자에만 같은 API로 `{ "nickname": "..." }`를 재호출한다.
- **예방**: OAuth callback URL에는 인증 결과를 담지 않고, 기존 회원·최초 회원이 같은 화면과 같은 완료 API를 사용하도록 계약한다.

### T-98. 로컬 PostgreSQL 이미지 불일치로 pgvector 확장 생성 실패 (2026-08-19, 해결)

- **증상**: Spring Boot 시작 시 Flyway V1의 `CREATE EXTENSION IF NOT EXISTS vector`에서 `extension "vector" is not available` 오류가 발생했다.
- **원인**: `compose.yaml`은 `pgvector/pgvector:pg17`을 선언하지만, 기존에 생성된 `ssafesta-local-postgres-1` 컨테이너가 `postgres:17-alpine` 이미지로 실행 중이었다. 일반 PostgreSQL 이미지에는 pgvector 확장이 없다.
- **해결**: 데이터 볼륨은 유지한 채 `docker compose up -d --force-recreate`를 실행해 컨테이너만 Compose 선언 이미지로 재생성했다. 이어 Flyway V1→V3 적용과 `/actuator/health`의 `UP`을 확인했다.
- **예방**: `docker compose.yaml`의 이미지 변경 뒤에는 `docker compose ps`로 실제 실행 이미지를 확인하고, 기존 컨테이너가 남아 있으면 `docker compose up -d --force-recreate`를 실행한다.

### T-97. Docker Desktop 미기동으로 Testcontainers 통합 테스트 실패 (2026-08-19, 해결)

### T-95. pgvector Testcontainers 이미지 pull 타임아웃 (2026-08-18, 해결)

- **증상**: 초기 ERD Flyway migration 검증 중 `pgvector/pgvector:pg17` 이미지가 Docker Hub에서 2분 동안 내려받기 진전을 보이지 않아 `mvnw test`가 실패했다.

### T-96. Windows 환경에서 spec-kit Bash 선행조건 검사가 실행되지 않음 (2026-08-18, 2026-08-19 해결)
