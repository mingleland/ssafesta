# 트러블슈팅

### T-10. GMS 키는 있으나 pgvector DB URL이 비어 튜닝 실행 중단 (2026-09-01, 해결)

- **증상**: 370번 전체 조합 평가를 시작하자 `pgvector 실행에는 RAG_SPIKE_DATABASE_URL이 필요합니다`로 첫 실행이 종료됐다.
- **원인**: 기존 로컬 `.env`에는 GMS API Key와 endpoint가 있었지만 `RAG_SPIKE_DATABASE_URL` 값은 비어 있었다. 코드·Gold Label·GMS 인증 문제가 아니며 DB Store 생성 단계에서 실패했으므로 GMS 호출 비용은 발생하지 않았다.
- **해결**: 실행 중인 애플리케이션 DB를 재사용하지 않고, 캐시된 `pgvector/pgvector:0.8.6-pg16-trixie` 이미지로 370번 전용 임시 컨테이너를 로컬 55433 포트에 생성했다. `vector` extension을 활성화하고 프로세스 범위 DB URL만 주입해 세 문서를 평가한 뒤 컨테이너를 제거했다.
- **예방**: GMS 대량 평가 전 `GMS_API_KEY`와 `RAG_SPIKE_DATABASE_URL`의 비어 있지 않음, DB의 `vector` extension, 원본 문서 경로를 먼저 점검한다. 공유·실행 중인 DB에는 스파이크 테이블을 만들지 않고 격리된 임시 DB를 사용한다.

### T-09. GitLab MR 병합용 Browser·REST API 인증 경로 사용 불가 (2026-09-01, 우회)

- **증상**: in-app Browser 런타임이 경로 오류로 시작되지 않았고, Git push에 사용하는 Credential을 GitLab REST API의 `PRIVATE-TOKEN` 또는 Basic 인증으로 사용하면 401/404가 반환됐다.
- **원인**: 현재 호스트의 Browser 제어 런타임이 사용할 수 없으며, Git Credential은 저장소 push 권한은 있지만 GitLab API 토큰으로 사용할 수 있는 자격증명이 아니었다.
- **해결**: 자격증명을 출력하거나 별도 파일에 저장하지 않고 API 경로를 중단했다. GitLab 공식 push option으로 파이프라인 성공 후 자동 Squash Merge를 요청하는 경로로 전환했다.
- **예방**: 자동 MR 병합이 필요한 환경에는 `glab` 또는 최소 `api` scope의 전용 토큰을 Secret으로 제공한다. Git push Credential을 API 토큰으로 가정하지 않는다.

### T-08. GitLab push option의 MR 설명에 줄바꿈을 전달할 수 없음 (2026-09-01, 해결)

- **증상**: `git push -o merge_request.create`와 함께 여러 줄 MR 설명을 전달하자 `fatal: push options must not have new line characters`로 push 전에 종료됐다.
- **원인**: Git protocol push option은 실제 newline 문자를 허용하지 않는데 PowerShell 문자열의 `` `n``이 그대로 option 인수에 포함됐다.
- **해결**: MR 설명을 한 줄 요약으로 변경해 동일 커밋을 push하고 develop 대상 MR을 정상 생성했다. 첫 시도는 push 자체가 시작되기 전 실패해 원격에 중복 브랜치나 MR을 남기지 않았다.
- **예방**: push option으로 MR을 생성할 때 설명은 단일 행으로 전달하고, 여러 줄 템플릿이 필요하면 MR 생성 후 GitLab UI/API에서 갱신한다.

### T-07. 샌드박스 내부에서 GMS Embedding REST 호출 실패 (2026-09-01, 해결)

- **증상**: 로컬 `.env`의 GMS 키와 올바른 endpoint를 사용했지만 첫 OpenAI Embedding 요청이 공통 `RuntimeError`로 종료됐다.
- **원인**: 코드·키·Gold Label 문제가 아니라 제한된 실행 환경의 외부 네트워크 차단이었다.
- **해결**: 동일 명령을 승인된 외부 네트워크 실행으로 재시작해 OpenAI 2종과 Gemini 1종의 평가 결과를 정상 저장했다.
- **예방**: GMS 실제 Provider 평가에서 샌드박스 요청 실패가 발생하면 Secret을 출력하거나 endpoint를 변경하지 말고, 동일 재현 명령을 네트워크 승인 실행으로 전환한다.

### T-06. Windows `conda run`에서 한글 PDF 경로가 CP949로 깨짐 (2026-09-01, 해결)

- **증상**: `conda run -n ssafesta-rag-spike python -c ...`에 `C:\Users\SSAFY\Downloads\수달.pdf`를 전달하자 파일명이 대체 문자로 변환되고, Conda가 결과를 출력하는 과정에서도 `UnicodeEncodeError: 'cp949' codec can't encode character`로 종료됐다.
- **원인**: Windows의 `conda run` 래퍼가 한글 명령 인수와 자식 프로세스 출력을 현재 콘솔의 CP949 인코딩으로 중계하면서 Unicode 경로를 보존하지 못했다. PDF나 `pypdf`의 파싱 오류는 아니었다.
- **해결**: `C:\Users\SSAFY\miniforge3\envs\ssafesta-rag-spike\python.exe`를 직접 실행하고 `PYTHONIOENCODING=utf-8`을 설정해 PDF 16페이지와 26개 청크를 정상 처리했다. 한글 경로가 필요 없는 단위 테스트는 `conda run`으로 분리 실행했다.
- **예방**: Windows에서 한글 파일 경로를 Python에 전달할 때는 `conda run` 대신 해당 환경의 `python.exe`를 직접 호출하고, 표준 출력 인코딩을 UTF-8로 명시한다.

### T-05. SHA-256 원본 검증 요구와 OpenAPI 실패 코드가 연결되지 않음 (2026-08-31, 해결)

- **증상**: spec에는 FastAPI가 저장소 원본의 SHA-256을 다시 검증한다고 명시됐지만, 두 OpenAPI 계약의 진단·callback 오류 enum과 `tasks.md`에는 `SOURCE_HASH_MISMATCH` 실패 경로가 없었다.
- **원인**: Backend의 업로드 중복 판정 계약을 반영하면서 원본 무결성 검증의 실행 결과를 Job 진단 코드와 Spring callback enum까지 끝단 연결하지 않았다.
- **해결**: 다운로드 바이트의 SHA-256을 요청 `sourceHash`와 비교하고, 불일치 시 재시도·Parser·Embedding·Chunk 저장 없이 `DEAD`로 종료한 뒤 Spring에 `FAILED + SOURCE_HASH_MISMATCH`를 보내도록 계약·설계·테스트·구현 작업을 동기화했다.
- **예방**: 파트 간 실패 코드를 추가할 때 발생 조건, 내부 Job 상태, 외부 callback enum, 사용자 상태, 무부작용 검증을 하나의 경로로 점검한다.

### T-04. Windows Proactor 이벤트 루프에서 psycopg 비동기 연결 실패 (2026-08-28, 해결)

- **증상**: 실제 PostgreSQL 17을 사용하는 migration 테스트 5건은 통과했지만 async repository 테스트 3건이 `Psycopg cannot use the 'ProactorEventLoop'` 오류로 실행되지 않았다.
- **원인**: Windows의 asyncio 기본 `ProactorEventLoop`는 psycopg 비동기 연결이 지원하지 않는 이벤트 루프 구현이다. Job 로직이나 DB schema의 실패는 아니었다.
- **해결**: 실제 DB 통합 테스트의 session 범위 `event_loop_policy` fixture가 Windows에서 `WindowsSelectorEventLoopPolicy`를 사용하도록 설정했다. 이후 repository 통합 테스트 3건과 전체 테스트 83건이 통과했다.
- **예방**: Windows에서 psycopg async 통합 테스트를 추가할 때 Selector 정책 fixture를 공통 conftest에서 재사용하고, Linux 운영 환경과 분리된 테스트 런타임 차이로 기록한다.

### T-03. Windows 기본 Python·pytest 임시 경로로 테스트 실행 불가 (2026-08-28, 해결)

- **증상**: `python -m pytest`가 WindowsApps 실행 별칭을 시작하지 못했고, 번들 Python으로 만든 `.venv`에서도 기존 `tmp_path` 테스트가 사용자 Temp 아래 `pytest-of-SSAFY` 접근 거부로 중단됐다.
- **원인**: 기본 `python.exe`가 실제 설치가 아닌 Windows 앱 실행 별칭이었고, 현재 제한 환경에서 pytest 기본 임시 루트에 접근할 수 없었다.
- **해결**: Codex 번들 Python으로 worktree 내부 `.venv`를 만들고 테스트 의존성을 격리 설치한 뒤 `--basetemp .venv/pytest-tmp`를 지정해 단위 테스트 62건을 통과시켰다.
- **예방**: Windows 제한 환경에서는 실제 Python 경로를 먼저 확인하고, 프로젝트에서 무시되는 worktree 내부 경로를 pytest 임시 루트로 명시한다.

### T-02. 경로별 로그만 보고 파트 커밋을 단일 파일 커밋으로 오판함 (2026-08-26, 해결)

- **증상**: `git log -- <spec 경로>`에서 spec 008 커밋 하나만 확인하고 `cherry-pick --no-commit`을 시도했으나, 해당 커밋에 API 문서와 spec 004 변경도 포함돼 공유 문서 충돌이 발생했다.
- **원인**: 경로 제한 로그는 “그 경로를 변경한 커밋”만 보여줄 뿐 커밋의 전체 변경 파일 목록을 보여주지 않는다. 적용 전에 `git show --stat <commit>` 또는 `git diff-tree`로 전체 범위를 확인하지 않았다.
- **해결**: 충돌 적용분 세 파일을 작업 브랜치 HEAD로 복원한 뒤, `docs/jira-gitlab-workflow.md` §4-1의 얽힌 커밋 이식 절차에 따라 `specs/008-ai-conversation-rag/spec.md` 한 파일만 선택해 이식했다.
- **예방**: 파트 브랜치 커밋을 이식하기 전 `git show --stat --oneline <commit>`으로 전체 파일 범위를 확인한다. 이슈 외 파일이 섞여 있으면 cherry-pick하지 않고 `git checkout <파트-커밋> -- <허용 경로>`로 파일 단위 이식한다.

## T-001 — spec 007 산출물 간 확정 계약과 작업 목록 불일치

- **날짜**: 2026-08-26
- **증상**: 확정된 callback 404 정책과 저장소 운영 범위가 일부 산출물에만 반영됐고, 세 번째 OpenAPI 계약 테스트·callback 종료 컬럼 migration 작업이 누락됐다. `tasks.md`에는 표준 형식이 아닌 `T008a`, `T075a`, `T075b`도 남아 있었다.
- **원인**: GitLab 후속 합의를 기존 작업 목록에 증분 반영하면서 계약 수, 데이터 모델, migration, 작업 식별자와 의존성 참조를 함께 점검하지 않았다.
- **해결**: P0 수동 장애 정책과 미확정 항목 등록 위치를 통일하고, 세 OpenAPI 스키마 검증·storage reconciliation Backend 동작 테스트 및 callback 종료 필드를 작업에 추가했다. 작업 식별자와 모든 참조를 `T001~T079`로 재정렬한 뒤 중복·누락을 검사했다.
- **예방**: 파트 간 계약 변경 시 spec·plan·research·data-model·contracts·quickstart·tasks를 한 묶음으로 검색하고, 작업 ID 연속성·계약 파일 수와 테스트 수·DB 필드와 migration 작업 대응을 구현 착수 전 검사한다.
