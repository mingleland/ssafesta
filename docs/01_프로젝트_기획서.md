# SSAFY FESTA 프로젝트 기획서

> **문서 목적**: 프로젝트가 해결하려는 문제, 핵심 가치, 목표 사용자, 제품 범위와 우선순위를 정의한다.
> **문서 상태**: Working Baseline — 확정된 방향과 검증이 필요한 후보를 구분해 관리한다.
> **이 문서에서 다루지 않는 것**: 세부 API, DB 컬럼, 네트워크 패킷, 배포 리소스 설정, UI 수치

---

## 1. 프로젝트 정의

### 1.1 한 줄 소개

**SSAFY FESTA는 조직이 생산한 프로젝트와 지식을 일회성 결과물에서 지속적으로 발견·체험·운영·확장되는 디지털 자산으로 전환하는 UGC 기반 프로젝트 생태계 플랫폼이다.**

### 1.2 핵심 경험

```text
프로젝트·지식·아이디어 생성
→ Booth Studio / Game Studio / AI Agent로 콘텐츠 구성
→ Publish
→ 3D 월드·목록·공유 링크에서 발견
→ 전시·대화·게임·설문 체험
→ 피드백·상담·보상
→ 운영 개선과 새로운 창작
→ 재방문
```

SSAFY FESTA의 핵심은 가상 공간을 재현하는 데 있지 않다. **사람과 프로젝트가 발견되고, 참여가 데이터와 보상으로 남으며, 그 결과가 다시 새로운 콘텐츠 제작으로 이어지는 순환 구조**를 만드는 데 있다.

### 1.3 제품 구성의 역할

| 구성 | 제품에서의 역할 |
|---|---|
| 3D 월드 | 사람과 콘텐츠를 우연히 발견하고 함께 체험하는 공간 인터페이스 |
| Booth Studio | 프로젝트·영상·설문·상담·AI를 조합하는 전시·운영 도구 |
| AI Agent | 프로젝트 문서와 제작 의도를 방문자 수준에 맞게 전달하는 지식 인터페이스 |
| Game Studio | 비개발자가 2D 상호작용 콘텐츠를 제작·공개하는 웹 UGC 도구 |
| 코인·인벤토리 | 참여 보상을 성장과 다음 창작으로 연결하는 순환 장치 |
| 운영 도구 | 방문·상담·설문·콘텐츠 상태를 관리하고 개선하는 기반 |

각 구성은 독립된 기능이 아니라 하나의 사용자 여정을 완성한다. 모든 기능을 Unity 안에 넣지 않으며, 사용자 경험과 데이터 특성에 맞는 실행 환경을 사용한다.

## 2. 기획 배경

교육기관과 기업에서는 매년 수많은 프로젝트와 기술적 성과가 만들어지지만, 대부분 발표 자료, 저장소, 게시글, 설문 링크처럼 분리된 형태로 남는다.

이러한 방식은 기록에는 적합하지만, 새로운 사용자가 프로젝트를 **발견하고, 체험하고, 제작자와 연결되는 경험**까지 제공하지는 못한다. 프로젝트가 종료되면 결과물뿐 아니라 기획 과정, 기술적 판단, 시행착오와 같은 지식도 빠르게 소멸한다.

특히 SSAFY는 프로젝트와 스터디, 채용 정보, 기술 경험이 빠르게 생산되는 고밀도 프로젝트 커뮤니티지만, 이를 지속적으로 전시하고 체험하며 다시 활용할 수 있는 통합 환경은 부족하다.

SSAFY FESTA는 프로젝트를 단순한 결과물이 아니라 다음 흐름으로 이어지는 지속 가능한 디지털 자산으로 만들기 위해 기획됐다.

> **발견 → 체험 → 소통 → 피드백 → 새로운 참여와 창작**

3D 공간은 단순한 배경이 아니라 사람과 콘텐츠를 발견하는 인터페이스로 활용한다. 사용자는 아바타로 공간을 탐색하고 프로젝트 부스, AI Agent, 설문, 이벤트, 게임을 하나의 경험 안에서 이용한다.

또한 사용자가 직접 부스와 게임, AI Agent를 제작할 수 있도록 하여 콘텐츠 소비자에서 제작자와 운영자로 역할을 확장한다.

> **SSAFY FESTA의 목표는 가상 공간을 재현하는 것이 아니라, 조직 안에서 만들어지는 프로젝트와 경험이 지속적으로 발견되고 활용되는 프로젝트 생태계를 구축하는 것이다.**

## 3. 문제 정의

### 3.1 프로젝트 정보와 참여 경험이 분리되어 있다

프로젝트 소개, 코드, 배포 결과, 설문, 제작자와의 소통이 서로 다른 서비스에 흩어져 있어 사용자는 여러 링크를 오가야 한다. 그 결과 프로젝트의 맥락과 가치를 하나의 연결된 경험으로 이해하기 어렵다.

### 3.2 좋은 프로젝트가 자연스럽게 발견되기 어렵다

게시판과 검색 중심 구조에서는 프로젝트를 미리 알고 있거나 제작자가 지속적으로 홍보해야 노출될 수 있다. 프로젝트의 품질보다 게시 시점과 홍보 역량이 가시성을 좌우하고, 좋은 결과물이 충분히 활용되지 못한다.

### 3.3 참여자에게 충분한 동기가 없다

프로젝트 팀은 테스트와 설문을 통해 데이터를 얻지만, 참여자는 시간과 노력을 사용한 만큼의 가치를 얻기 어렵다. 참여 요청은 반복되고 사용자는 특별한 이유가 없다면 체험을 미루게 된다.

### 3.4 프로젝트 운영이 제작자에게 의존한다

프로젝트 설명과 반복 질의응답을 제작자가 직접 담당하면 부재 시 운영이 중단되고, 콘텐츠가 많아질수록 관리 비용도 증가한다. 방문자는 원하는 시점에 자신의 이해 수준에 맞는 설명을 받기 어렵다.

### 3.5 가상 공간만으로는 재방문을 만들기 어렵다

운영진이 제공한 공간을 한 번 둘러보는 것만으로는 지속적인 사용을 만들기 어렵다. 사용자가 직접 콘텐츠를 만들고, 다른 사용자의 참여가 다시 새로운 콘텐츠와 활동으로 이어지는 구조가 필요하다.

### 3.6 핵심 문제

> **조직 안에서 지속적으로 생산되는 프로젝트와 지식, 사람과 참여가 연결되지 못하고 일회성 결과물로 소멸하고 있다.**

SSAFY FESTA는 분리된 접점을 다음 하나의 흐름으로 연결한다.

> **발견 → 체험 → 소통 → 피드백 → 보상 → 창작 → 재방문**

## 4. 차별성

### 4.1 공간 자체가 콘텐츠 탐색 인터페이스

검색이나 목록에만 의존하지 않고, 사용자가 공간을 이동하고 다른 사람과 상호작용하는 과정에서 프로젝트와 콘텐츠를 자연스럽게 발견하게 한다. 의도적인 검색뿐 아니라 **우연한 발견과 사회적 상호작용**을 탐색 방식으로 활용한다.

3D 월드는 모든 콘텐츠를 직접 실행하는 단일 엔진이 아니라, 여러 경험을 연결하는 발견의 표면이다. 영상·설문·상담·2D 게임처럼 웹에 적합한 기능은 React 화면으로 열고, Unity는 월드 탐색과 아바타 상호작용에 집중한다.

### 4.2 전시를 넘어 제작까지 가능한 UGC 구조

사용자는 Booth Studio에서 프로젝트 영상, 설명, 서비스 링크, 설문, 상담 기능, AI Agent를 배치해 자신의 부스를 제작할 수 있다.

Game Studio에서는 타일과 오브젝트, 대화, 조건, 이벤트를 조합해 2D 게임을 만들고 웹에 공개할 수 있다. 공개된 게임은 독립 링크에서 바로 실행되며, 필요하면 부스의 NPC나 게임 포털에 연결한다.

사용자는 방문자에 머물지 않고 **공간 운영자·전시 기획자·게임 제작자·콘텐츠 운영자**로 확장된다.

### 4.3 생성형 AI를 프로젝트의 지식과 경험을 확장하는 디지털 에이전트로 활용

AI Agent는 단순한 챗봇이나 부재중 안내 기능이 아니다. 사용자가 설정한 역할·말투·운영 목적과 부스별 프로젝트 문서를 기반으로 해당 프로젝트에 특화된 디지털 에이전트로 동작한다.

방문자의 관심과 질문 수준에 맞춰 프로젝트를 설명하고, 기술·기획 자료를 근거로 답변하며, 필요한 경우 대화 맥락을 요약해 실제 담당자와의 상담으로 연결한다. 사용자는 복잡한 프롬프트 엔지니어링 없이 자연어와 문서만으로 AI의 역할을 설계한다.

따라서 AI는 제작자를 단순히 대신하는 운영 보조가 아니라, **축적된 프로젝트 지식에 접근하고 이해하며 다음 상호작용으로 이어지게 하는 핵심 인터페이스**다.

### 4.4 참여가 다시 창작으로 이어지는 경제 구조

사용자는 프로젝트 체험, 설문, 이벤트, 운영 정책상 허용된 활동을 통해 보상을 얻고 이를 아바타와 부스 꾸미기, 아이템 구매 등 다음 활동에 사용할 수 있다.

제작자는 피드백과 데이터를 얻고, 참여자는 자신의 캐릭터와 공간을 성장시키면서 다음 활동의 동기를 얻는다.

> **콘텐츠 제작 → 발견 → 체험·참여 → 보상 → 성장 → 새로운 콘텐츠 제작**

코인 지급·차감·보상은 클라이언트가 결정하지 않는다. Spring의 정책과 거래 원장이 최종 권위를 가지며, 중복 요청이 경제 상태를 이중 반영하지 않도록 한다.

### 4.5 기능에 맞는 기술을 배치한 하이브리드 구조

| 영역 | 담당 |
|---|---|
| 실시간 공간·아바타 상호작용 | Unity Web + Dedicated Server |
| Booth/Game 제작 도구와 2D 게임 실행 | React + TypeScript |
| 회원·부스·코인·Draft·Published 영구 상태 | Spring Boot |
| AI Agent 실행·문서 처리·RAG | FastAPI 기반 AI 서비스 |

모든 기능을 하나의 기술에 집중하지 않고 사용자 경험과 데이터 특성에 맞게 분리한다. 한 영역의 장애가 다른 핵심 경험까지 중단시키지 않도록 경계를 둔다.

### 4.6 다른 조직형 커뮤니티로 확장 가능

SSAFY는 프로젝트 생산과 참여가 활발해 플랫폼을 검증하기 좋은 시작점이지만, 핵심 구조는 특정 교육기관에 한정되지 않는다. 기업 기술 박람회, 대학 프로젝트 전시, 아이디어 공모전, 교육 성과 공유, 채용 행사 등에도 같은 구조를 적용할 수 있다.

## 5. 프로젝트 목표

1. 프로젝트·지식·사람·참여를 분리된 링크가 아니라 하나의 경험으로 연결한다.
2. 사용자가 3D 공간과 목록에서 좋은 프로젝트를 자연스럽게 발견하고 즉시 체험하게 한다.
3. 별도의 Unity 개발 없이 Booth Studio와 Game Studio에서 콘텐츠를 제작·공개하게 한다.
4. 프로젝트 특화 AI Agent가 문서를 근거로 설명하고, 필요하면 실제 담당자 상담으로 맥락을 이어주게 한다.
5. 참여 보상을 성장과 다음 창작으로 연결해 콘텐츠가 스스로 확장되는 UGC 순환을 만든다.
6. 영구 서비스 데이터, AI 실행, 웹 콘텐츠, 실시간 월드 상태를 분리해 장애와 확장에 대응한다.
7. SSAFY에서 검증한 구조를 다른 조직형 프로젝트 커뮤니티에도 적용할 수 있게 한다.

## 6. 핵심 사용자

### 6.1 프로젝트 전시·운영자

- 프로젝트 영상, 링크, 문서, AI 설명, 설문을 한 공간에서 제공하고 싶다.
- 제작자가 접속하지 않은 시간에도 방문자에게 프로젝트 맥락을 전달하고 싶다.
- 방문, 질문, 설문과 상담 반응을 확인해 프로젝트를 개선하고 싶다.

### 6.2 AI Agent 제작자

- 프로젝트 문서를 기반으로 목적과 개성이 분명한 AI Agent를 운영하고 싶다.
- 코드를 작성하거나 복잡한 프롬프트를 설계하지 않고 역할·말투·운영 목적을 설정하고 싶다.
- AI 대화가 실제 담당자 상담과 단절되지 않게 하고 싶다.

### 6.3 게임·상호작용 콘텐츠 제작자

- 전문 게임 엔진을 배우지 않고도 기획, 배치, 대화와 이벤트에 집중하고 싶다.
- 준비된 템플릿과 에셋을 사용하되 원하는 이미지와 연출은 교체하고 싶다.
- 만든 게임을 저장·공개하고 다른 사용자가 실제로 플레이하게 하고 싶다.

### 6.4 모집·커뮤니티 운영자

- 프로젝트·스터디 팀원을 모집하고 싶다.
- 소개 영상, 모집 공고, 지원 설문, AI 안내와 실시간 상담을 하나의 부스에서 연결하고 싶다.

### 6.5 방문·탐색 사용자

- 다른 팀의 프로젝트와 포트폴리오를 구경하고 싶다.
- AI Agent, 이벤트, 설문, 사용자 제작 게임을 가볍게 체험하고 싶다.
- 다른 접속자와 같은 공간에 있다는 느낌을 받으면서 관심 있는 제작자와 연결되고 싶다.

## 7. 서비스 공간

기본 월드는 실제 SSAFY 11층을 모티브로 한다. 1차 범위는 11층 단일 월드이며, 1층 축제 공간과 층 이동은 2차 범위에서 검증한다.

### 7.1 기본 공간

- 중앙 광장
- 사용자 임대 부스 구역
- 관리자 상시 부스
- 프로젝트·포트폴리오 전시 구역
- 이벤트·미니게임 공간
- 휴게·소통 공간

### 7.2 기본 부스 구성

## 9. 범위와 우선순위

> 우선순위는 전체 서비스 통합 순서를 뜻하며 개별 파트의 구현 완료 여부와 같지 않다. 상세 완료 상태는 각 기능 spec과 작업일지에서 관리한다.

- Google/Kakao 소셜 로그인 + 비영구 게스트 탐색
- Unity Web 월드와 Dedicated Server 접속
- Player Spawn / Despawn, 위치·회전 기본 동기화
- 부스 슬롯 조회·임대
- Wallet / Coin Ledger
- Booth Studio 기본 편집
- Layout 저장 / Draft / Publish
- Published Layout 기반 Unity Booth Runtime 생성
- 프로젝트 링크·영상 정보 등록
- AI Agent 역할·말투·지시문 설정
- 문서 업로드·비동기 처리·RAG 근거 답변

- 캐릭터 파츠 커스터마이징과 접속자 간 반영

게스트는 둘러보기와 공개 콘텐츠 체험만 가능하며 임대, 제작, 저장, Publish, 영구 자산과 경제 활동은 할 수 없다.

### 9.2 P1 — 실제 운영 가능한 서비스

### 9.3 P2 — 독립 UGC와 선택 확장

#### FESTA Game Studio

- React Web 기반 한국어 2D 제작 도구
- `TOP_DOWN`, `PLATFORMER` 이동 Runtime과 `DIALOGUE` 연출 Scene
- 타일, 오브젝트, 컴포넌트, Trigger / Condition / Action 조합

`DIALOGUE`는 미연시라는 별도 장르가 아니라 맵 플레이 중 Overlay 또는 전체 화면 연출로 삽입한다. 퍼즐과 퀘스트도 별도 Runtime을 늘리지 않고 공통 Event/Component 조합과 템플릿으로 제공한다.

## 11. 동시 접속과 용량 검증 방향

전체 서비스 동시 접속과 한 월드가 처리하는 인원을 분리한다. 다음 수치는 보장값이 아니라 성능·운영 검증을 위한 초기 목표다.

| 구분 | 초기 검증 목표 |
|---|---:|
| 전체 서비스 | 100명 이상으로 확장 가능한 구조 확인 |
| 11F World 1채널 | 30~40명 운영 가능성 검증 |
| 월드 부하 테스트 | 최대 50명 수준 측정 |
| Booth Instance 후보 | 8~12명 단위 검증 |
| 팀 기본 단위 | 최대 6명 후보 |

실제 운영값은 Unity Web 렌더링, 애니메이션, 네트워크 비용과 부하 테스트 결과를 근거로 확정한다.

Game Studio는 프로젝트 크기 상한, Scene/Object/Event 수, Asset 크기와 형식을 서버 검증 대상으로 둔다. 이미지·오디오 원본을 GameProject JSON에 포함하지 않고 서버가 발급한 Asset 참조로 연결해 저장소와 DB의 무제한 증가를 막는다.

```text
제작자 로그인
```

```text
→ 타일·오브젝트 배치
```

## 13. 구현 원칙과 순서

### 13.1 공통 원칙

1. 사용자에게 보이는 하나의 경험과 내부 시스템의 책임 분리를 함께 지킨다.
2. Draft와 Published 데이터를 분리해 편집 중 변경이 방문자에게 노출되지 않게 한다.
3. Unity, React, Spring, FastAPI 사이의 연결은 버전이 있는 JSON/API 계약으로 검증한다.
4. AI·Game Runtime·Unity 월드 중 한 영역의 장애가 다른 핵심 기능까지 종료시키지 않게 한다.
5. Coin·임대·보상·권한은 클라이언트가 최종 판정하지 않는다.
6. 합의되지 않은 API와 정책은 adapter·candidate 계약 뒤로 격리하고 핵심 제작 경험은 먼저 검증한다.

### 13.2 통합 순서

```text
공통 데이터 계약
→ 로컬 제작·Preview
→ Draft 저장과 충돌 복구
→ Publish 검증과 불변 버전
→ Unity 없는 독립 Published 체험
→ 부스·AI·설문·상담 연결
→ 선택적 Unity Portal 연결
→ 경제·통계·확장 기능
```

### 13.3 Game Studio 현재 경계

Game Studio Frontend candidate는 제작, 로컬 Preview, 기본 Asset, 한국어 튜토리얼, Published Runtime 껍데기와 오류 복구를 구현·검증하는 단계다. 여러 사용자가 같은 공개본을 조회하는 운영 배포를 완료하려면 Spring의 Draft/Publish/Asset/Portal API와 실제 Published E2E를 연결해야 한다.

AI는 향후 대화·이벤트 제작 보조를 제공할 수 있지만 Game Studio의 저장, Publish, 플레이에 필요한 필수 경로가 아니다. AI가 생성한 결과도 일반 GameProject 후보로 검증하고 사용자가 승인한 뒤 저장한다.

| 사용자 Asset이 DB·번들·Published를 오염 | 큼 | binary 분리, 형식·크기 제한, 안정 Asset 승격, 위치별 Publish 차단 안내 |
| 범위 과다 | 매우 큼 | P0/P1/P2, 파트 경계, Cut Line 준수 |

## 17. 프로젝트 대표 기술 포인트

1. **Spatial Discovery Interface** — 3D 공간 이동과 사회적 상호작용을 프로젝트 발견 방식으로 활용
2. **React Booth Studio** — 데이터 기반 전시·운영 UGC Editor
3. **FESTA Game Studio** — 공통 Event/Component 계약과 TOP_DOWN/PLATFORMER Runtime을 사용하는 웹 2D UGC 제작·실행 환경
4. **Data-driven Unity Booth Runtime** — Published Layout JSON 기반 Booth Runtime 생성
5. **Unity Multiplayer World** — 아바타와 공간 상호작용에 집중한 Dedicated Server 구조
6. **Project-specialized AI Agent** — 사용자 설정 + 문서 RAG + Human Handoff로 프로젝트 지식을 확장하는 디지털 에이전트
7. **Server-authoritative Economy** — Ledger와 idempotency로 참여 보상과 창작 경제의 신뢰성 확보
8. **Failure-isolated Hybrid Architecture** — React·Unity·Spring·FastAPI의 역할과 장애 범위를 분리

## 18. 최종 정의

> **SSAFY FESTA는 조직이 생산한 프로젝트와 지식을 일회성 결과물에서 지속적으로 발견·체험·운영·확장되는 디지털 자산으로 전환하는 UGC 기반 프로젝트 생태계 플랫폼이다.**

3D 월드는 **발견의 인터페이스**, 부스는 **프로젝트의 운영 단위**, AI Agent는 **프로젝트 지식과 방문자를 연결하는 디지털 에이전트**, Game Studio는 **상호작용 콘텐츠 제작 도구**, 코인 시스템은 **참여를 다시 성장과 창작으로 연결하는 동력**이다.

각 기능은 독립된 부가 기능이 아니라 다음 하나의 순환을 구성한다.

> **사람과 프로젝트의 발견 → 체험과 이해 → 소통과 피드백 → 보상과 성장 → 새로운 창작 → 재방문**
