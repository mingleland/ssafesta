# 작업 지시 — 모듈러 캐릭터 기반 아바타 커스터마이징 (spec 013 재구현)

> **대상**: Unity 파트 (AI 세션에 그대로 전달 가능한 작업 지시서)
> **작성**: 2026-08-12 | **관련 spec**: `specs/013-avatar-customization/`
> **전제**: 기존 아바타 구현(런타임 조립 방식)을 **모듈러 프리팹 방식으로 교체**한다.
> 멀티플레이·Booth Runtime·Dedicated Server는 **정상 동작 중이므로 절대 재작성하지 않는다.**

---

## 0. 이 작업이 기존과 무엇이 다른가

기존 구현은 **런타임에 파츠 DB를 읽어 메시를 합치는 방식**이었다. 새 에셋은 **파츠가 프리팹으로 미리 나뉘어 있는 방식**이다.
따라서 아래가 근본적으로 바뀐다.

| 항목 | 기존 | 신규 |
|---|---|---|
| 외형 표현 | 긴 파츠 이름 문자열 (실측 600자+) | **작은 ID 집합** |
| 네트워크 전송 | `FixedString4096Bytes` 문자열 | **`INetworkSerializable` 고정 크기 struct** |
| 조립 방식 | DB 조회 → 메시 병합 | 프리팹/SkinnedMesh 부착 |
| 파츠 목록 | 런타임 DB | **ScriptableObject Catalog** |

이 변경은 개선이다. 네트워크 payload가 수백 바이트에서 수십 바이트로 줄고, T-24(길이 초과 무반응)의 원인 자체가 사라진다.

## 1. 가장 먼저 — 에셋 실구조 조사 (추측 금지)

`Assets/` 아래 벤더 폴더에 모듈러 캐릭터 에셋이 import되어 있다.
식별 표지: `Assets/Body_OriginalVersion/{F,M}`, `Assets/Meshes`, `Assets/Textures`, `Prefabs/HairStyles`, `Prefabs/Accessories`, `Samples/Customization`, `Samples/Preview`.

**반드시 실제 파일을 열어 확인한다. 인터넷 정보나 개수 추측을 코드에 넣지 않는다.**

조사 항목:

- `Samples/Customization/Customization.unity` 데모 씬과 그 스크립트 전체 — **가장 먼저 분석할 것**
- 벤더가 제공하는 아이템 정의 ScriptableObject의 필드 구성
- 신체 부위 태그(body part) enum과 그 용도
- 프리팹의 실제 목록과 카테고리 (헤어·모자·안경·의상·신발 등 **실제로 존재하는 것만**)
- 남/녀 전신 프리팹의 차이와 스켈레톤 공유 여부
- Humanoid Avatar 사용 여부, 본 이름 체계
- 색상 변경을 벤더가 어떤 방식으로 하는지 (머티리얼 교체 / 프로퍼티 / 텍스처)
- BlendShape 존재 여부와 용도
- 데모의 회전·줌·색상 선택 UI 유틸리티

**⚠️ 반드시 확인해야 할 함정 하나**: 모자 프리팹이 **헤어스타일별 변형**으로 존재할 수 있다
(같은 모자인데 짧은머리용·긴머리용·묶은머리용 등). 이 경우 "모자 ID" 하나로는 표현이 안 되고
**모자 × 헤어 조합 규칙**이 필요하다. 실제 그런지 먼저 확인하고, 맞다면 Catalog 설계에 반영한다.

### 데모에서 재사용할 것 / 만들 것 구분

데모에 이미 있는 것을 다시 만들지 않는다. 특히 다음은 재사용 가능성이 높다.

- 아이템 정의 ScriptableObject 구조 (신체 부위 숨김 정보를 이미 갖고 있을 수 있음 → §7 클리핑)
- 본에 오브젝트를 부착하는 방식
- 프리뷰 회전/줌 유틸리티
- 색상 선택 UI

단, **데모 스크립트를 우리 런타임의 핵심 경로에 직접 얹지 않는다.** 벤더 코드는 언제든 교체될 수 있다.

## 5. AvatarConfig — 외형 표현

실제 메시나 프리팹을 담지 않는다. **ID만** 담는다.

```csharp
// 카테고리는 §1 조사 결과에 실제로 존재하는 것만 만든다.
// 없는 카테고리를 억지로 만들지 않는다.
public struct AvatarConfig
{
    public Gender Gender;
    public int HairId;
    public int HairColorId;
    public int SkinColorId;
    public int TopId;
    public int TopColorId;
    // ... 조사 결과에 따라 확정
}
```

**ID 설계 원칙**: 배열 인덱스를 그대로 쓰지 않는다. 아이템을 중간에 추가·삭제하면 기존 사용자의 외형이 뒤바뀐다.
Catalog가 소유하는 **안정적인 itemId**를 쓰고, 알 수 없는 ID를 만나면 기본값으로 폴백한다.

## 6. AvatarCatalog — 아이템 정의

`ScriptableObject` 기반. 새 옷을 추가할 때 **코드를 고치지 않고 에셋만 추가**하면 되게 만든다 (Item Driven).

`AvatarItemDefinition`이 가질 정보:

```text
itemId          안정적 식별자 (재사용·재배치 금지)
displayName
category
gender          공용/남/녀
visual          프리팹 또는 SkinnedMesh 참조
thumbnail
availableColors
hiddenBodyParts 이 아이템 착용 시 숨길 신체 부위 (§7)
isDefault

// 상점 대비 — 이번엔 사용하지 않고 자리만 만든다
shopVisible / price / unlockType
```

상점 시스템은 **이번 작업에서 구현하지 않는다** (spec 012, P1). Catalog가 나중에 그대로 쓰일 수 있게만 설계한다.

## 7. AvatarAssembler — 가장 중요한 클래스

```text
AvatarConfig → AvatarAssembler → 실제 외형
```

책임:

- 카테고리별 파츠 부착/교체
- 색상 적용
- 남/녀 전환
- **신체 부위 숨김 처리 (클리핑)** — 옷 안에서 몸이 튀어나오지 않게
- Humanoid 스켈레톤·Animator 유지

**클리핑**: 벤더 에셋이 신체 부위 태그 시스템을 이미 제공한다면 그것을 활용한다.
아이템 정의의 `hiddenBodyParts`를 읽어 해당 신체 렌더러만 끈다.

**금지**:

- 파츠마다 `NetworkObject` 붙이기 — 캐릭터당 `NetworkPlayer` 하나뿐이다
- 매 프레임 재조립 — **Spawn 시점과 외형 변경 시점에만** 조립한다

구조:

```text
NetworkPlayer (NetworkObject, NetworkTransform, 기존 컴포넌트 — 무수정)
└─ AvatarVisualRoot           ← 순수 로컬. NetworkObject 없음
   ├─ Skeleton / Body
   ├─ Hair
   ├─ Top / Bottom / Shoes
   └─ Accessory
```

## 9. 저장

`IUserApiClient`에 이미 아바타 저장 경로가 있다. **새 시스템을 만들기 전에 기존 코드를 먼저 조사한다.**

Backend 아바타 API는 아직 없다. 따라서:

- `IAvatarProfileStore` 인터페이스 + `LocalAvatarProfileStore`(PlayerPrefs) 구현으로 우선 동작시킨다
- **존재하지 않는 Backend 엔드포인트를 가정해서 가짜 URL을 만들지 않는다**
- 필요한 계약은 spec 013과 `festa-unity/Docs/avatar-customization-contract.md`에 제안으로만 남긴다

게스트 사용자는 영속 저장하지 않는다 (헌법 12조). 기본 프리셋(`AvatarPreset`)을 남/녀 최소 1종씩 만든다.

## 10. 네트워크 동기화

**메시·텍스처·머티리얼을 네트워크로 보내지 않는다. ID만 보낸다.**

```text
Owner → ServerRpc → 서버 검증 → NetworkVariable<NetworkAvatarConfig> → 전 클라이언트 → Assembler
```

- `NetworkAvatarConfig`는 `INetworkSerializable`을 구현하는 **작은 고정 크기 struct**
- 전송 시점은 **Spawn 시점과 외형 변경 시점뿐**. 이동 동기화 주기와 완전히 분리한다
- 서버는 최소한 **Catalog 범위 내 ID인지 검증**한다 (헌법 16조)
- ⚠️ **실패를 조용히 기본값으로 대체하지 않는다** (T-24의 교훈).
  거부하면 사유를 남기고 사용자에게 보이게 한다

기존 `PlayerAppearanceController`의 요청→서버→전파 흐름은 그대로 두고 **타입만 교체**한다.

## 11. Animator

기존 이동 상태(`PlayerAnimState`)와 연결한다. 최소 Idle / Walk / Run이 재생되어야 한다.

⚠️ **T-27 재발 주의**: 조립된 캐릭터에 Animator가 붙어 있어도 **Controller가 비어 있으면 T포즈로 굳는다.**
조립 직후 Animator의 Controller와 Avatar(휴머노이드 정의)가 채워졌는지 확인하고, 비어 있으면 명시적으로 채운다.
채우지 못하면 조용히 넘어가지 말고 원인을 로그로 남긴다.

애니메이션 클립의 Rig는 **Humanoid**여야 리타게팅된다.

## 12. 용량 — 이번 작업의 최대 리스크 ⚠️

**현재 Web 빌드는 약 87MB다. 새 에셋은 소스 기준 약 141MB이며 그중 텍스처가 약 80MB다.**

기존 아바타 에셋(약 22MB)까지 함께 두면 빌드가 감당 못 할 가능성이 높다.
이건 "나중에 최적화"로 미룰 문제가 아니다 — 018(층 구조)에서 이미 확인했듯 **이 프로젝트의 지배적 제약은 Web 다운로드 용량**이다.

**따라서 순서를 이렇게 잡는다:**

1. **먼저 최소 구성으로 Web 빌드를 한 번 만들어 용량을 실측한다.** 캐릭터 1종만 넣어도 된다
2. 실측 결과를 보고 아래를 판단한다
   - 텍스처 최대 해상도 축소 / 압축 포맷 조정
   - 사용하지 않는 파츠·샘플·HDRP/URP 패키지 파일 제외
   - 카테고리별 아이템 수 제한
3. **기존 아바타 에셋과 관련 코드를 제거한다** — 새 방식이 동작하는 것을 확인한 뒤
   (`SidekickRuntimeService.cs`, Resources의 파츠 DB, 벤더 폴더). 두 에셋을 동시에 유지하지 않는다
4. 목표를 정하고 그 안에서 아이템 수를 결정한다. **"일단 다 넣고 나중에 줄이자"는 금지**

WebGL 확인 항목: 렌더러 수, 머티리얼 수, SkinnedMeshRenderer 수, Animator 수, 텍스처 크기, 그림자 설정, BlendShape 사용량.

## 13. 머티리얼 / 색상

공유 머티리얼을 직접 수정하면 **모든 플레이어의 색이 함께 바뀐다.**
`MaterialPropertyBlock` 또는 벤더가 권장하는 색상 변경 방식을 조사해서 사용한다.
WebGL에서 불필요한 머티리얼 인스턴스가 수십 개씩 생기지 않게 한다.

## 14. 구현 순서 (각 단계가 동작한 뒤 다음으로)

```text
1. 에셋 구조 + 데모 분석          ← 여기서 카테고리 확정
2. Web 빌드 용량 실측 (최소 구성)  ← §12. 여기서 막히면 설계가 바뀐다
3. AvatarConfig / ItemDefinition / Catalog
4. AvatarAssembler
5. Preview 캐릭터
6. CharacterLobby UI
7. 로컬 저장
8. 월드 NetworkPlayer 외형 적용
9. NGO 외형 동기화
10. 브라우저 2개 검증
11. 기존 에셋·코드 제거 + 재빌드
12. 문서 정리
```

**2번을 3번보다 먼저 하는 이유**: 용량이 안 맞으면 카테고리 수와 아이템 수가 바뀌고, 그러면 Catalog 설계가 바뀐다.

## 15. 테스트

**에디터**: Lobby 실행 → 남/녀 전환 → 각 카테고리 변경 → 색상 변경 → 초기화 → 랜덤 → 확인

**씬 전환**: 커스터마이징 → 확인 → 월드 입장 → **선택한 외형 유지**

**멀티플레이 (브라우저 2개)**:

```text
A: 헤어 A / 상의 A       B: 헤어 B / 상의 B
→ A 화면에 B의 실제 외형, B 화면에 A의 실제 외형
→ 이동·Spawn·Despawn·Booth Runtime 정상 (회귀 없음)
```

⚠️ **네트워크 변수 타입을 바꾸므로 Web 빌드와 Linux Server 빌드를 반드시 둘 다 다시 만든다** (T-24/T-25).
컨테이너는 `docker ps`로 확인 후 이름을 맞춰 교체한다 (`festa-world-01`).

**WebGL**: 빌드 에러 0 / 런타임 에러 0 / 콘솔 치명적 에러 0

## 18. 완료 조건

```text
CharacterLobby → 외형 선택 → 프리뷰 즉시 반영 → 확인 → 저장
→ 월드 입장 → 내 NetworkPlayer에 적용 → 다른 클라이언트에도 동일 외형
→ Idle / Walk / Run 정상
```

그리고 **Dedicated Server / 멀티플레이 / Spawn·Despawn / 이동 동기화 / Booth Runtime이 깨지지 않을 것.**

기존 시스템을 최대한 보존하고 아바타 기능만 Vertical Slice로 추가한다.
