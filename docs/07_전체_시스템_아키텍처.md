# SSAFY FESTA 전체 시스템 아키텍처

> **문서 목적**: SSAFY FESTA를 구성하는 시스템의 경계, 책임, 데이터 소유권, 주요 데이터 흐름을 정의한다.  
> AWS 세부 리소스는 Infra 문서, API 계약은 각 API 문서, 실시간 이벤트는 Realtime 문서에서 관리한다.

---

## 1. 아키텍처 목표

1. Web 관리 기능과 Unity 실시간 경험을 분리한다.
2. 영구 상태와 실시간 상태를 분리한다.
3. AI 장애가 월드 접속을 중단시키지 않도록 독립시킨다.
4. Booth를 코드가 아닌 Layout 데이터로 생성한다.
5. 한 서버에 전체 사용자를 넣지 않고 World Instance 수평 확장을 고려한다.

## 3. Client 책임

### 3.1 React Web

담당:

- 인증 UI
- Home / My Booth
- Booth Studio
- AI Agent Builder
- Project 관리
- Survey Builder
- Staff / Permission 관리
- Consultation 운영 UI
- Wallet / Inventory
- Dashboard
- Admin

담당하지 않음:

- Player authoritative state
- World movement sync
- LLM 추론
- 영구 Coin 계산 로직

### 3.2 Unity Web

담당:

- SSAFY World 렌더링
- Player 입력·표현
- Multiplayer 연결
- Booth Published Layout Runtime 생성
- AI NPC / Video / Survey / Consultation UI 진입
- Minigame

담당하지 않음:

- Booth 영구 저장의 Source of Truth
- Coin Ledger 직접 수정
- Vector Search
- Staff 권한 최종 판정

---

## 4. Server 책임

### 4.1 Spring Boot

서비스의 영구 비즈니스 상태를 담당한다.

- Authentication / User
- Booth / Booth Slot / Lease
- Booth Layout / Version / Publish
- Wallet / Coin Ledger
- Inventory
- Project
- Survey
- Staff / Permission
- Consultation Metadata
- Event / Competition / Reward
- Dashboard 집계에 필요한 운영 데이터
- World Session/Channel 연계용 서비스 데이터

### 4.2 FastAPI

AI 실행 영역을 담당한다.

- Agent Prompt 실행
- Document Processing
- Chunking / Embedding
- RAG Search
- LLM 호출
- Streaming 응답
- Conversation Context
- Human Handoff Summary
- 향후 STT / TTS

Agent 설정의 최종 저장 Source of Truth는 Spring으로 두고 FastAPI가 실행 시 필요한 설정을 전달받거나 조회하는 구조를 기본으로 한다.

### 4.3 Unity Dedicated Server

실시간 월드의 authoritative state를 담당한다.

- 접속 Player Spawn / Despawn
- Position / Rotation
- 필요한 Animation State
- Presence에 필요한 월드 상태
- Current Booth / Zone
- 일부 공동 Interaction
- Minigame authoritative state
- World Instance / Channel 실행 단위

## 7. AI 흐름

```text
Owner
→ Agent Config 저장(Spring)
→ Document Upload(S3)
→ FastAPI Process 요청
→ Parsing / Chunking / Embedding
→ pgvector

Visitor
→ AI 이용 가능 여부 확인(Spring)
→ Conversation 생성(FastAPI)
→ 질문
→ boothId / agentId Vector Search
→ LLM
→ Streaming
```

사람 상담 전환:

```text
Visitor Handoff Request
→ Spring Consultation
→ FastAPI Summary
→ Redis Presence 기반 Staff Notify
→ Staff Accept
→ Spring Realtime Consultation
```

## 8. World / Channel 구조

### 8.1 MVP

```text
Unity Web Clients
      ↓
World-01 Dedicated Server
      ↓
11F World + Booth Zone
```

### 8.2 확장

```text
SSAFY FESTA
     │
Session / Channel Manager
     │
 ┌───┼────────────┐
 │   │            │
W-01 W-02        W-03
 │
 └─ Booth Instance(P2)
```

각 채널은 동일한 Spring Published Booth 데이터를 읽는다. 따라서 World가 여러 개여도 Booth 콘텐츠를 복제 관리하지 않는다.

## 11. 장애 격리

### AI 서버 장애

- World 접속 유지
- Booth의 AI 기능만 오류 상태 표시
- Project / Video / Survey 등 비AI 기능은 계속 사용

### Spring API 장애

- 신규 Lease / Publish / Survey 등 서비스 작업은 제한
- 이미 접속한 Unity 월드의 즉시 종료를 강제하지 않는 방향을 검토

### Unity Server 장애

- 해당 World Instance 사용자에게 연결 오류 처리
- 영구 Booth / Coin / Survey 데이터는 손상되지 않아야 함

---

## 12. 확장 원칙

### Horizontal Scale

목표는 한 서버에 100명을 넣는 것이 아니다.

```text
30~40명 World Instance
× 여러 Channel
+ 필요 시 Booth Instance
= 전체 서비스 동접 확장
```

### AI Scale

- API 실행과 긴 Document Processing을 분리할 수 있게 설계
- 필요 시 Queue / Worker 확장

### Data Scale

- PostgreSQL은 영구 데이터
- Redis는 임시·실시간 데이터
- S3는 파일

역할을 혼합하지 않는다.

## 14. Architecture Decision 기록 대상

다음 결정은 실제 POC 후 ADR로 남기는 것이 좋다.

1. Unity Web ↔ Dedicated Server 최종 Transport
2. Spring/FastAPI 배포 단위 EC2 vs ECS
3. SSE vs WebSocket AI Streaming 최종 선택
4. Conversation 저장 위치
5. World Session / Channel Manager 구현 방식
6. pgvector를 서비스 DB와 공유할지 AI 전용 DB로 분리할지
7. Booth Layout JSONB vs 정규화 범위
