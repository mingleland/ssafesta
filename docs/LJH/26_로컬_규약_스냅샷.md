```markdown
## 문서 규칙 — 상태 서술은 교체, 덧붙이기 금지

- **덧붙이기(append) 절대 금지.** `대기 → ✅ 확정`, `— 이후 #NN로 확정`, 취소선 뒤 새 값 병기 등

- **상태 변경은 정본화 작업.** 확정 시 해당 ID로 파일 전체 grep → SSOT 외 상태 복제를

## 이슈·브랜치 확인 규칙

- **이슈 응답 확인은 내용까지.** 코멘트 개수·타임스탬프 비교로 "새 응답 없음" 판정 금지.
  마지막 코멘트의 작성자를 확인하고, 내가 아니면 본문 전문을 읽고 backlog와 대조한다.
  (근거: #60 즉답을 "코멘트 1개뿐"으로 오판한 사고, 2026-08-23)
- **작업 착수 전 `git fetch origin` 전 브랜치 필수.** develop·game·back·ai가 계약 정본을
  먼저 갱신하는 구조라 front만 봐서는 낡는다.

## 게시 전 대기 범위

- **원격 공개 게시(이슈·PR·코멘트·리뷰 등)는 예외 없이 항상 초안 작성 후 대기.** 사용자 승인 없이 게시 안 함.

  바로 작성·커밋 진행 — 매번 승인 구하지 않는다.

## "브랜치 최신화"에는 공용 문서 pull이 항상 포함된다

- 사용자가 "브랜치 최신화"를 지시하면 **코드 fetch/sync뿐 아니라 develop의 공용 문서

  문서는 별도 확인 없이 넘어가지 않는다.
  (근거: #59→PR#61이 develop에만 반영된 채 front가 못 받아온 것을 뒤늦게 발견, 2026-08-23)
```

```markdown
---
name: feedback-doc-replace-not-append
description: 문서 갱신 시 "대기 → ✅ 확정" 덧붙이기 절대 금지 — 최종 상태 문장으로 교체 서술

문서(spec·docs)의 낡은 서술을 갱신할 때 `— ✅ 이후 #NN로 확정` 같은 마커를 **덧붙이는 방식 절대 금지**. 낡은 문장을 내용 누락 없이 **최종 상태 문장으로 다시 쓴다**. 이력은 Git/Issue가 담당.

**Why:** 2026-08-22 spec 005 정본화 작업에서 8곳을 전부 "덧붙이기"로 처리했다가 사용자 지적 — "문서를 무겁게 하면서 동시에 복잡하게 만듦. 사실상 재발 불가능할 정도로 금지한다." 덧붙이기는 자기모순(#45 사고)의 변형일 뿐이다 — 낡은 상태어가 본문에 계속 남는다.

**How to apply:**
- 갱신 = 교체. 확정 근거는 이슈 링크를 문장 안에 자연스럽게(`**막지 않고 경고**(#45로 채택)`), 화살표·✅·"이후 확정" 금지
- 날짜 박힌 검토 기록도 상태 꼬리("승인 대기")는 떼고 의견 본문만 남긴다 — 상태는 SSOT(Clarifications 표)가 담당
- 완료 조건: 해당 ID 파일 전체 grep → 전 occurrence 교체 확인
- 프로젝트 CLAUDE.md "필수: 문서 규칙" 섹션에 팀 강제 규칙으로 등록됨 (2026-08-22)
```

### B-2. feedback-issue-check-read-content.md

```markdown
---
name: feedback-issue-check-read-content
description: 이슈 응답 확인은 코멘트 개수·시각 비교가 아니라 "마지막 코멘트 작성자+내용"까지 읽어야 함. 세션 시작 시 전 브랜치 fetch 필수
metadata:
  type: feedback
---

이슈/PR 응답 확인 시 **코멘트 개수나 타임스탬프 비교만으로 "새 응답 없음" 판정 금지**. 마지막 코멘트의 **작성자와 내용**까지 읽는다 — 마지막 코멘트가 상대방이면 그게 미처리 응답일 수 있다. 그리고 **모든 작업 시작 전 `git fetch origin`(전 브랜치) 필수**.

**Why:** 2026-08-23 #60에서 재발 — 게시 직후 kanghyunsoon이 즉답(빌드 URL 확정+credential BE 이관)을 달았는데, "코멘트 1개 = 내가 아는 그 상태"로 오판해 '응답 없음' 보고. 실제로는 resolver 주석 갱신·BE 질의 이관이 필요한 실질 답변이었다. backlog #30·#34 stale도 같은 뿌리(상태 재확인 없이 기록 신뢰).

**How to apply:**
- 응답 확인 절차: 마지막 코멘트 `author` 확인 → 내가 아닌 사람이면 **본문 전문 읽기** → backlog 반영 여부 대조
- backlog의 "회신 완료—대기" 표 항목은 확인 시마다 마지막 코멘트 작성자를 실제 조회
- 세션 시작·작업 착수 전 `git fetch origin` — front만이 아니라 전 브랜치(develop·game·back·ai가 계약 정본을 먼저 갱신하는 구조)
- 관련 기존 규칙: [[feedback-doc-replace-not-append]](backlog 자체도 stale해질 수 있음 전제)
```

### B-3. feedback-publish-wait-scope.md

```markdown
---
name: feedback-publish-wait-scope
description: 게시 전 대기는 원격 공개 게시(이슈·PR·코멘트·리뷰)에만 예외 없이 적용. 내부 문서(작업일지·backlog)는 중요 사안일 때만 대기, 일반 갱신은 바로 진행
metadata:
  type: feedback
---

**원격 공개 게시**(GitHub 이슈·PR·코멘트·리뷰 등, 팀원이 보는 것)는 **예외 없이 항상** 초안 작성 후 사용자 승인 대기.

**내부 문서**(작업일지·backlog 등, 세션 간 인수인계용)는 **사용자 판단이 필요할 정도로 중요한 사안일 때만** 대기하고, 일반적인 기록·상태 갱신은 승인 없이 바로 작성·커밋 진행.

**Why:** 2026-08-23, 4건 처리 후 작업일지·backlog 갱신 초안을 만들어 대기했는데 사용자가 "이건 그냥 반영해서 커밋하라"고 정정 — 매번 대기시키는 게 오히려 비효율. 동시에 "게시는 예외 없이 항상 대기"를 재확인.

**How to apply:**
- 이슈/PR/코멘트/리뷰 게시 → 무조건 초안 먼저, 승인 후 게시(안전 규칙 그대로 유지)
- 작업일지 1줄 기록, backlog 상태 갱신, 트러블슈팅 T-번호 등록 같은 **일상 기록**은 바로 작성해 커밋
- 판단 필요 기준 예시: 문서 구조를 바꾸는 대규모 재작성(예: backlog 105→85줄 정리), 팀 규칙 신설·수정, 여러 파일에 걸친 일괄 정정 — 이런 건 여전히 방향 확인 후 진행
```

### B-4. feedback-branch-sync-includes-docs.md

```markdown

description: "브랜치 최신화" 지시에는 코드뿐 아니라 develop의 공용 문서(docs/00·docs/17·docs/26 등) 회수도 항상 포함

사용자가 "브랜치 최신화"를 지시하면 코드 `git fetch`/sync만이 아니라 **develop의 공용 문서(팀 규칙·결정 로그) 회수도 항상 세트**로 수행한다.

**Why:** 2026-08-23, #59 재발 방지 규칙이 PR #61로 develop에 머지됐는데 front는 이후 "브랜치 최신화"를 여러 차례 지시받고도 코드 fetch만 하고 `docs/00`·`docs/17`을 안 끌어와 규칙 3건이 front 문서 정본에 없는 채로 방치됐다. 사용자가 "브랜치 최신화에는 공용 문서 pull도 반드시 포함된 세트여야 함"이라고 명시 정정.

**How to apply:**
- "브랜치 최신화" 지시 시: `git fetch origin` 전 브랜치([[feedback-issue-check-read-content]]) + **develop 대비 공용 문서(`docs/00`·`docs/17`·`docs/26` 등) diff 확인** → front 고유 변경 없으면 파일 단위 checkout으로 회수
- front 고유 변경이 있으면 회수 전 사용자에게 보고(Block A 절차와 동일)
- 이 규칙은 [[feedback-doc-replace-not-append]]가 실제로 팀 공식 문서에 반영돼 있는지를 담보하는 전제 조건이기도 하다 — 문서가 안 오면 규칙 자체가 front에서는 "로컬 관행"에 머문다
```
