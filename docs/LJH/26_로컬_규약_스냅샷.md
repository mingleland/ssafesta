## 문서 규칙 — 상태 서술은 교체, 덧붙이기 금지

- **덧붙이기(append) 절대 금지.** `대기 → ✅ 확정`, `— 이후 #NN로 확정`, 취소선 뒤 새 값 병기 등

  다른 섹션은 상태를 복제하지 않고 확정된 동작·정책만 기술.
- **상태 변경은 정본화 작업.** 확정 시 해당 ID로 파일 전체 grep → SSOT 외 상태 복제를

## Jira ↔ GitLab Issue 경계 — "이슈"는 기본적으로 GitLab Issue다

- **Jira = Task 단위.** 목적·담당·범위·완료조건·구현 상태·MR 링크·검증 결과·왜 아직 Done 이 아닌지.
  팀 실측 기준으로 조사 기록·중간 실측·원인 분석도 Jira 코멘트에 남기는 것이 관행이다
  (강형순 `-419`·`-420` 코멘트가 그 형태다). 넣지 않는 것은 docs/18 §29 의 "전문" 뿐이다.
- **GitLab Issue = 타 파트를 향한 조율 표면.** 제목이 `[part,part] 주제 — 확정 요청 / 구현 통보 /
  결함 N건` 형태인 것이 팀 관행이다. 다른 파트가 **읽고 답해야 하는 것**은 여기 있어야 한다.
- **MR = 코드 변경·리뷰·머지.**
- **판정 기준 한 줄: "이걸 타 파트가 읽고 답해야 하는가?"** 그렇다면 GitLab Issue 에도 있어야 한다.
  Jira 코멘트에만 두면 그 파트는 볼 자리가 없다 — 내 문서(`docs/LJH/`)에만 두는 것은 더 나쁘다.
- **사용자가 "이슈"라고 하면 GitLab Issue**로 읽는다. Jira 를 뜻할 때는 "Jira / 티켓 / Task" 라고 한다.
  "별도 이슈로 분리해라" 를 Jira Task 생성으로만 처리하지 않는다.
  (근거: 2026-09-05 — 50~84초·백그라운드 재접속을 Jira Task 로만 갈라 놓고 팀 공유 표면을 안 만들었다.
  G-8 Input Lock 은 08-31 부터 `decision-queue.md` 에만 있어 Unity 파트가 5일간 몰랐다. #129·#131·#132·#133)
- 양방향 링크를 건다 — GitLab Issue 에 `관련 Jira`, Jira 에 `팀 공유·논의 정본: GitLab #NNN`.

## 게시 전 대기 범위

## 선처리·후통보 — 승인은 예외다 (2026-08-26 개정)

- **기본값은 담당 영역 선처리·후통보, 경계 밖 결정만 선질의.** approval 을 만들기 전에 반드시
  답한다 — **"왜 현재 Actor 가 이 결정을 직접 내릴 수 없는가?"** 근거가 없으면 요청하지 않는다.
- **STOP & ASK 는 7가지가 실제로 성립할 때만**: ⑴ 타 파트 ownership 침범 ⑵ 공용 API·계약·정책
  변경 ⑶ Jira acceptance·scope·완료조건 변경 ⑷ Secret·권한·외부 계정·자격증명 ⑸ 데이터 손실·
  비가역 작업 ⑹ 팀 규약이 명시적으로 사전 승인을 요구 ⑺ 두 정본이 충돌하고 실측으로도 우열
  판정 불가.
- **단순한 불확실성·구현 선택지 존재·리뷰어 취향 가능성은 STOP 사유가 아니다.** 외부 결정이
  하나 남아 있어도 독립적으로 진행 가능한 범위는 멈추지 않는다.
- 판단 순서: ownership → 정본/계약 → 코드·Git·Jira·실측 → 직접 결정 가능 여부 → 실행 → 검증
  → checkpoint → **계속 진행**. checkpoint 는 진행 증거이지 승인 요청이 아니다.
- 보고 형식: `처리 완료 / 스스로 판단한 것(판단·근거·검증) / 외부 결정 필요(STOP&ASK 해당분만)`.
  외부 결정 항목이 없으면 질문으로 끝내지 말고 **다음 Ready 작업으로 계속 진행**한다.
- **이 절은 위 "게시 전 대기 범위"·"자율 처리 판정"을 대체한다** — 그 둘은 리드 확인을 줄이는
  방향이었고, 이 절은 승인 자체를 예외로 둔다. 충돌하면 이 절이 우선이다.
  (근거: 2026-08-26 사용자 지시 — "질문은 불확실성을 넘기는 수단이 아니라 결정권 경계를

  선택까지 승인을 구해 진행이 끊긴 것이 계기다)

### B-3. feedback-publish-wait-scope.md

```markdown
---
name: feedback-publish-wait-scope
description: 게시 전 대기는 원격 공개 게시(이슈·PR·코멘트·리뷰)에만 예외 없이 적용. 내부 문서(작업일지·backlog)는 중요 사안일 때만 대기, 일반 갱신은 바로 진행
metadata:
  type: feedback
---

**원격 공개 게시**(GitHub 이슈·PR·코멘트·리뷰 등, 팀원이 보는 것)는 **예외 없이 항상** 초안 작성 후 사용자 승인 대기.

**내부 문서**(작업일지·backlog 등, 세션 간 인수인계용)는 **사용자 판단이 필요할 정도로 중요한 사안일 때만** 대기하고, 일반적인 기록·상태 갱신은 승인 없이 바로 작성·커밋 진행.

**Why:** 2026-08-23, 4건 처리 후 작업일지·backlog 갱신 초안을 만들어 대기했는데 사용자가 "이건 그냥 반영해서 커밋하라"고 정정 — 매번 대기시키는 게 오히려 비효율. 동시에 "게시는 예외 없이 항상 대기"를 재확인.

**How to apply:**
- 이슈/PR/코멘트/리뷰 게시 → 무조건 초안 먼저, 승인 후 게시(안전 규칙 그대로 유지)
- 작업일지 1줄 기록, backlog 상태 갱신, 트러블슈팅 T-번호 등록 같은 **일상 기록**은 바로 작성해 커밋
- 판단 필요 기준 예시: 문서 구조를 바꾸는 대규모 재작성(예: backlog 105→85줄 정리), 팀 규칙 신설·수정, 여러 파일에 걸친 일괄 정정 — 이런 건 여전히 방향 확인 후 진행
```

```markdown
사용자가 "브랜치 최신화"를 지시하면 코드 `git fetch`/sync만이 아니라 **develop의 공용 문서(팀 규칙·결정 로그) 회수도 항상 세트**로 수행한다.

**Why:** 2026-08-23, #59 재발 방지 규칙이 PR #61로 develop에 머지됐는데 front는 이후 "브랜치 최신화"를 여러 차례 지시받고도 코드 fetch만 하고 `docs/00`·`docs/17`을 안 끌어와 규칙 3건이 front 문서 정본에 없는 채로 방치됐다. 사용자가 "브랜치 최신화에는 공용 문서 pull도 반드시 포함된 세트여야 함"이라고 명시 정정.

**How to apply:**
- "브랜치 최신화" 지시 시: `git fetch origin` 전 브랜치([[feedback-issue-check-read-content]]) + **develop 대비 공용 문서(`docs/00`·`docs/17`·`docs/26` 등) diff 확인** → front 고유 변경 없으면 파일 단위 checkout으로 회수
- front 고유 변경이 있으면 회수 전 사용자에게 보고(Block A 절차와 동일)
- 이 규칙은 [[feedback-doc-replace-not-append]]가 실제로 팀 공식 문서에 반영돼 있는지를 담보하는 전제 조건이기도 하다 — 문서가 안 오면 규칙 자체가 front에서는 "로컬 관행"에 머문다
```

### C-5. 개인 개발도구는 프로젝트 공유 설정과 분리

**원칙**: 팀이 채택하지 않은 개인 도구(JAM 등)를 `.mcp.json`(project-scope, 커밋됨·팀 전체 자동 로드 대상)에 넣지 않는다. 2026-08-25 세션이 JAM을 project-scope로 등록했다가(`ae4aa58`) 2026-08-26 세션에서 발견·정정(`claude mcp add-json jam --scope local`로 이관 후 `.mcp.json` 삭제) — 팀은 JAM의 존재 자체를 모르는데 파일만 조용히 project-scope에 박혀 팀원 전원 세션이 자동 로드 시도하는 상태였다.

- 개인 도구는 `claude mcp add-json <name> '<json>' --scope local`(이 프로젝트+이 머신 한정, `~/.claude.json`에 저장, 커밋 안 됨) 또는 `--scope user`(전 프로젝트 공통)로 등록한다
- `.mcp.json`(project-scope)에는 팀이 합의한 도구만 넣는다 — 지금은 없음
- 개인 도구를 project-scope로 승격하려면 팀 합의가 먼저다(CLAUDE.local.md "팀 규칙 승격은 리드 승인 사안"과 같은 원칙)

**같은 원칙의 두 번째 축 — 저장소 안에 생기는 개인 도구 산출물**. 개인 도구는 MCP 등록만 남기지 않는다. 프로젝트 루트에 runtime 디렉터리·설정·작업 산출물을 만들며, 그것이 `git status`에 untracked로 뜨는 동안은 `git add .` 한 번에 커밋된다(2026-08-26 실측: 4종 노출). 막는 자리는 `.gitignore`가 아니라 `.git/info/exclude`다 — `.gitignore`는 커밋되므로 파일 자체는 안 올라가도 **팀 파일에 개인 도구 이름이 남는다.** 이것은 `.mcp.json` 건과 같은 원칙의 약한 형태다.

- `.git/info/exclude`는 clone을 따라가지 않는다 — 새 머신마다 재등록해야 한다
- **그 패턴 목록을 이 문서에 적지 않는다.** 팀 문서(front에 커밋됨)에 개인 도구 이름을 남기지 않는다는 같은 이유다 — 여기 적으면 `.gitignore`에 적는 것과 결과가 같아진다
- 목록의 이전 가능 사본은 **팀 저장소 밖**이 보관한다. 우선순위: ⑴ 각 도구 저장소가 자기 흔적을 스스로 등록한다(설치 시 자동 — 도구가 자기 산출물 경로를 아는 유일한 주체다) ⑵ 도구 저장소가 없는 산출물(host·플러그인 작업물)은 개인 설정 저장소에 둔다
- 이 문서가 담당하는 것은 **원칙과 복원 순서까지**이고, 값은 담당하지 않는다

### C-6. 개인 스킬 백업·복원 (`festa-*`)

**대상**: `festa-boot` · `festa-inbox` · `festa-handoff` — SSAFY FESTA front 파트 전용 절차 스킬 3종.
2026-08-25 세션이 user scope(`~/.claude/skills/`)에 만들었다. `.claude/skills/`(project scope)는 팀 전체가
자동 로드하는 자리라 개인 절차를 넣지 않는다는 판단이었고, 그 판단은 유지한다.

**문제**: user scope는 홈 디렉터리라 git 밖이고, `~/.claude`는 git 저장소가 아니다.
`~/.claude/backups/`에는 transcripts만 있다. 2026-09-01 실측 시점까지 사본이 원본 1벌뿐이었다 —
소실되면 복구 수단이 없었다. C-5가 "개인 도구 산출물의 이전 가능 사본은 팀 저장소 밖"을 말하지만,
그 문장이 배제하는 것은 **`.git/info/exclude` 패턴 목록**이고 `docs/LJH/`는 개인 트리다.
이 문서 자체가 이미 JAM을 본문에 이름으로 언급하고 있으며, 같은 자리에 스킬 사본을 둔다.

**사본 경로**: `docs/LJH/skills/festa-{boot,inbox,handoff}/SKILL.md`

**A·B절과 다른 방식을 쓴 이유**: A·B절은 본문 코드블록으로 옮겨 적었지만 스킬은 **파일 그대로 복사**다.
코드블록 사본은 드리프트를 사람 눈으로만 잡을 수 있는 데 비해, 파일 사본은 `diff -r`가 기계적으로 잡는다.
스킬 3종 합계 약 19KB라 본문에 넣으면 이 문서가 배로 부푸는 문제도 있다.

**복원**:

```bash
mkdir -p ~/.claude/skills
cp -r docs/LJH/skills/festa-* ~/.claude/skills/
```

**검증**:

```bash
ls ~/.claude/skills/          # festa-boot / festa-inbox / festa-handoff 3개
diff -r ~/.claude/skills/festa-boot docs/LJH/skills/festa-boot     # 출력 없어야 정상
```

**줄바꿈 고정**: 이 저장소는 `core.autocrlf=true`라 새 머신에서 clone하면 사본이 CRLF로 체크아웃되고,
원본(`~/.claude/skills/`, LF)과의 `diff -r`가 실질 차이가 없는데도 항상 차이를 보고하게 된다.
루트 `.gitattributes`에 `docs/LJH/skills/** text eol=lf` 한 줄로 이 경로만 LF로 고정했다 —
`git check-attr` 실측상 다른 경로는 `unspecified`로 영향이 없다.

**유지 원칙**: 스킬을 고치면 **같은 커밋에서** `cp -r ~/.claude/skills/festa-* docs/LJH/skills/`로 사본을
갱신한다(A·B절의 교체 원칙과 같다 — 덧붙이기가 아니라 파일 교체). 드리프트 점검은 위 `diff -r` 3줄이고,
차이가 나면 **원본(`~/.claude/skills/`)이 정본**이다.

**범위 밖**: `~/.claude/skills/`의 나머지 7개(`pinlog-pr` · `pinlog-status` · `asc` · `asc-inbox` ·
`asc-review` · `orca-cli` · `design-taste-frontend`)는 이 저장소와 무관한 다른 프로젝트용이라
여기 두지 않는다. 그쪽은 여전히 사본이 없다 — 각 프로젝트 저장소 또는 개인 설정 저장소가 담당할 몫이다
(C-5 우선순위 ⑴·⑵).
