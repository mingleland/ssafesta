### T-6. 이슈 종결 가능 여부를 이슈 본문 확인 없이 판정 (2026-08-20, 해결)

- **증상**: Issue #2([front] Overlay·Unity 브릿지 계약 리뷰 요청)의 종결 가능 여부를 물었을 때 "FE `events.ts` 타입 추가와 Unity 구현이 미착수라 닫을 수 없다"고 보고했다. 사용자가 "해당 이슈는 계약 확인이지 구현까지 포함하지 않는다"고 지적해 다시 확인하니 이슈 본문의 요청은 "확인 요청" 2건뿐이었고 구현은 범위 밖이었다. 판정을 뒤집고 종결했다.
- **원인**: 이슈 본문을 읽지 않고 코멘트 스레드 내용만으로 판정했다. 스레드 후반에 구현 계획이 오갔다는 이유로 그것을 완료 조건에 포함시켰으나, 그 구현은 확인 결과로 파생된 별개 작업이었다. 종결 조건은 이슈를 연 사람이 본문에 적어둔 것인데 그 원문을 확인하지 않았다.
- **해결**: `gh issue view --json title,body`로 본문을 읽어 요청 항목이 "확인 요청" 2건임을 확인하고 판정을 정정했다. 종결 코멘트에 후속 구현이 이 이슈에 묶여 있던 것이 아님을 명시해 추적이 끊기지 않게 했다. 같은 방식으로 Issue #5는 본문 체크리스트 2건 중 "문서 기입"이 미완이라 종결 불가로 판정했다 — 본문을 읽었기 때문에 두 이슈의 차이를 구분할 수 있었다.
- **예방**: 이슈 종결 가능 여부를 판정할 때는 **코멘트 스레드보다 이슈 본문의 요청·체크리스트를 먼저 읽는다.** 스레드에서 파생된 후속 작업과 이슈 본문이 정의한 완료 조건은 별개다. T-4(값의 생성 지점만 보고 소비 지점을 안 봄)와 같은 형태의 실수 — 근거의 원본을 건너뛰고 중간 정보로 판단했다.

### T-5. 왕복 검증 실행 절차가 3곳에서 막힘 — FE가 작성한 절차의 환경 전제 누락 (2026-08-20, 해결)

- **증상**: FE가 `docs/LJH/verify/block1-roundtrip.md`에 적어 Issue #6으로 넘긴 실행 절차를 Unity 담당이 그대로 따르자 세 곳에서 막혔다. ⑴ 엔드포인트를 복수형으로 고친 뒤라 Unity는 `/layouts/published`를 호출하는데 mock 파일은 여전히 단수 경로(`layout/published`)에 있어 404 ⑵ 씬의 `BoothSlot_7`이 `activeSelf=false`라 재생해도 `Start()`가 돌지 않아 아무 오브젝트도 생성되지 않음 ⑶ 절차에 적은 `python -m http.server`가 해당 환경에서 실행되지 않음(Windows Store 별칭 가로챔).
- **원인**: 절차를 쓴 시점의 코드·씬 상태를 그대로 전제했다. ⑴은 같은 이슈에서 내가 요청한 복수형 전환이 반영되면 mock 파일 경로도 함께 옮겨야 한다는 연쇄를 못 짚었다. ⑵는 `main.unity`를 서브에이전트 보고로만 읽고 `BoothRuntime` 컴포넌트 존재까지만 확인했지 GameObject 활성 상태를 직접 확인하지 않았다. ⑶은 다른 사람의 실행 환경을 내 환경 기준으로 가정했다.
- **해결**: Unity 담당이 세 곳 모두 임시 우회(복수 경로에 mock 파일 임시 생성, `BoothSlot_7` 임시 활성화, `py -m http.server`)해 검증을 완료하고 저장소 상태를 원복했다. 검증 자체는 통과했다.
- **예방**: 타 파트가 실행할 절차를 쓸 때는 ⑴ 같은 요청에 포함된 코드 변경이 절차의 전제를 무너뜨리지 않는지 연쇄를 따진다 ⑵ 씬·설정 상태는 "컴포넌트가 붙어 있는가"가 아니라 "실제로 실행되는 상태인가"까지 확인한다 ⑶ 실행 명령은 환경 의존적일 수 있음을 명시하거나 대안을 병기한다.

### T-1. 마감 직전 마지막 커밋이 작업일지·트러블슈팅에 반영되지 않음 (2026-08-14, 소급 해결)

- **증상**: `.gitignore`에 `local/`을 추가한 커밋이 작업일지에 기록되지 않았고, 그 커밋이 다룬 문제(개인 분석 파일이 실수로 커밋될 수 있던 상태) 자체도 등록되지 않았다. 실제 유출은 없었다.
- **원인**: 작업일지 커밋 뒤에 `.gitignore` 커밋을 만들어 마지막 커밋이 일지 작성 시점 밖으로 밀렸다. 세션 종료 전 확인을 수행하지 않아 걸러지지 않았다.
- **해결**: 소급 등록했다. 작업일지 2026-08-14 섹션에 항목을 추가하고 T-1로 링크했다.
- **예방**: 기록 커밋(작업일지·트러블슈팅)을 세션의 마지막 커밋으로 둔다. 세션 종료 전 `git log --since=<당일> --oneline`으로 당일 커밋 전수와 일지 항목을 대조한다. 사고가 나지 않은 예방 조치도 등록한다.

### T-2. 다항목 Codex 검증 프롬프트가 응답 없이 타임아웃 (2026-08-17, 우회)

- **증상**: 커밋 검증을 Codex CLI(`codex exec -s read-only`)에 맡겼을 때 8개 항목·전체 diff 대조를 한 프롬프트에 담자 10분·7분 두 차례 모두 응답 없이 타임아웃되어 백그라운드로 밀렸다. 헬스체크용 단문 요청은 같은 설정에서 5.3초에 응답했다.
- **원인**: Codex CLI 자체 장애가 아니라 프롬프트 부하 문제였다. 검증 항목마다 여러 문서를 교차 대조하도록 요구해 한 번의 실행에서 수행할 도구 호출과 판정량이 과도했다.
- **해결**: 검증 항목을 5~7개로 줄이고 각 항목이 확인할 파일을 명시해 재실행하니 정상 응답했다. 타임아웃된 결과를 기다리는 대신 같은 항목을 직접 `git`·`grep`으로 대조해 병행 확인했다.
- **예방**: Codex 검증 프롬프트는 항목 수와 대조 범위를 줄여 나눠 던진다. 검증 결과를 기다리는 동안 확인 가능한 항목은 직접 대조해 세션이 외부 도구 응답에 묶이지 않게 한다.

### T-4. 코드 경로를 끝까지 추적하지 않고 버그 증상을 단정해 이슈에 발행 (2026-08-18, 해결)

- **증상**: spec 005 왕복 검증 준비 중 Unity `BoothLayoutDto`의 식별자 필드가 계약(`objectId`)과 달리 `id`인 것을 발견하고, 그 영향을 "`BOOTH_LAPTOP_INTERACT`의 objectId가 항상 빈 값으로 전송된다"고 단정해 Issue #6 본문에 실었다. 사용자 승인도 받지 않고 발행했다. 이후 Codex 독립 검증에서 이 서술이 REFUTED로 뒤집혔다 — 실제로는 `BoothInteractBridge.cs:18-26`의 `string.IsNullOrEmpty(objectId)` 가드에 걸려 **이벤트 자체가 전송되지 않는다**. 증상은 "빈 값 전송"이 아니라 "노트북 클릭 무반응"이었다.
- **원인**: DTO 필드명 불일치라는 근인만 확인하고 그 값이 소비되는 지점까지 추적하지 않았다. `dto.id → BoothRuntimeObject.ObjectId → LaptopInteractable → BoothInteractBridge` 체인의 마지막 단계에 조기 반환 가드가 있는데 이를 읽지 않고 "빈 값이 그대로 흘러간다"고 넘겨짚었다. 발행 전 검토 요청도 하지 않아 오류가 외부에 그대로 나갔다.
- **해결**: Codex 검증 결과를 근거로 Issue #6에 정정 댓글을 게시했다(사용자 승인 후). Unity 리드가 동일 체인으로 재현을 확인하고 수정 방향(DTO 정식 필드를 `objectId`로 변경, 구 `id`는 하위 호환 보정값)을 회신했다. 로컬 기록 3곳(`backlog.md`·`24_작업일지.md`·`verify/block1-roundtrip.md`)의 틀린 서술도 함께 정정했다.
- **예방**: 버그 증상을 서술할 때는 값의 **생성 지점이 아니라 소비 지점까지** 코드를 읽는다 — 중간의 가드·조기 반환·기본값 처리가 증상을 바꾼다. 타 파트에 나가는 이슈·댓글·PR 본문은 발행 전 사용자 검토를 받는다. 코드 근거가 있는 주장은 발행 전에 독립 검증(Codex 등)을 한 번 태운다.

### T-3. GitHub API 일시 장애로 협업자 조회 실패 (2026-08-17, 해결)

- **증상**: Issue 담당자를 지정하기 전 `gh api repos/<owner>/<repo>/collaborators`가 `HTTP 503 No server is currently available to service your request`로 두 차례 연속 실패했다.
- **원인**: 로컬 인증이나 권한 문제가 아니라 GitHub API 측 일시 장애였다. 같은 시점에 `git fetch`(git 프로토콜)와 `gh issue create`는 정상 동작해 전면 장애가 아님을 확인했다.
- **해결**: 협업자 목록은 같은 세션에서 앞서 조회해 둔 값을 사용하고, Issue 생성·담당자 지정·라벨 부착을 재시도해 모두 성공했다.
- **예방**: `gh` 명령이 503으로 실패하면 인증·권한을 의심하기 전에 다른 엔드포인트와 git 프로토콜로 범위를 먼저 가른다. 조회가 막혀도 이미 확인된 값이 있으면 작업을 중단하지 않는다.
