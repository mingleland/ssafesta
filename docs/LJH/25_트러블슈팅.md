### T-76. Unity prefab 로더가 음수 fileID 를 못 읽어 메시를 통째로 놓쳤다 — 조용히 (2026-09-08, 해결)

- **증상**: Facade 18종 실측에서 `FACADE_CART_POPCORN` 이 **0 tri · 0 mesh** 로 나왔다. prefab 은 정상이고 FBX 를 직접 로드하면 5 mesh · 6,314 tri 가 나온다. 경고도 오류도 없었다.
- **원인**: `unity-prefab.mjs` 의 fileID 정규식이 전부 `\d+` 였다. FBX 안 서브에셋(메시·재질)을 가리키는 fileID 는 Unity 내부 해시라 **자주 음수**다(`m_Mesh: {fileID: -6737146398385819516, ...}`). 매치 실패는 `null` 을 돌려주고 `continue` 로 넘어가 **경고조차 남기지 않는다.** CarnivalKit 42 prefab 의 `m_Mesh` 288 건 중 **136 건이 음수**였다.
- **해결**: `ref`·`fileIdList`·`readMaterialSlots`·`readInstanceMaterialOverrides`·컴포넌트 목록 5곳을 `-?\d+` 로 열었다. 내부 Booth 자산 4종은 tri·mesh·node·재질이 전부 동일해 회귀 없음을 확인했다. 테스트: `tools/assets/__tests__/unityPrefabNegativeFileId.test.mjs`.
- **예방**: **"조용히 기본값으로 떨어지는" 경로를 만들지 않는다**(CLAUDE.md 의 T-24 교훈과 같은 자리). 참조를 못 읽었으면 `ctx.warn` 을 남겨야 했다. 이 결함은 tri 합계만 보면 "가벼운 자산" 으로 보여서 **수치가 정상 범위면 의심하지 않게 된다** — 개별 자산이 0 인지 반드시 본다.

### T-77. 그 수정 뒤 tri 가 2배로 뛰었다 — FBX 전체를 MeshFilter 마다 붙이고 있었다 (2026-09-08, 해결)

- **증상**: T-76 수정 후 Facade 18종 합계가 5.76M → 10.57M tri 로 늘었다. 팝콘 카트는 31,570 tri 였는데 FBX 원본은 6,314 tri — **정확히 5배**다.
- **원인**: `loadPrefab` 이 `m_Mesh` 의 guid 로 FBX 를 찾은 뒤 **파일 전체**를 붙였다. FBX 하나에 메시가 여러 개면 MeshFilter 마다 전체가 들어가 mesh 수만큼 중복된다. fileID 는 Unity 내부 해시라 FBXLoader 로 되짚을 수 없다.
- **해결**: Unity 가 import 할 때 GameObject 이름을 메시 이름 그대로 붙인다는 점을 이용해 **이름으로 고른다**(`selectSubMesh`). 고른 것을 새 그룹에 옮겨 담지 않고 **나머지를 제거**한다 — FBX 루트의 축·단위 보정이 부모 체인에 걸려 있어서 메시만 뽑으면 자세가 틀어진다. 이름이 안 맞거나 메시가 하나면 원본 그대로 쓴다. 교정 후 실측: **791,006 tri**.
- **예방**: 수정 뒤 수치가 **늘면** 그것도 결함 신호다. 줄어드는 것만 검증하지 않는다. 자릿수가 바뀌면 앞뒤 두 수치 다 의심한다 — 이번에는 둘 다 틀렸다.

### T-78. 런타임 GLB 가 스펙 위반이었다 — quantize 확장이 안 써지고 있었다 (2026-09-08, 해결)

- **증상**: 컴파일 로그에 `Some extensions were not registered for I/O, and will not be written.` 가 매번 찍혔다. 자체 썸네일은 원본조차 알아볼 수 없는 파편 덩어리로 나왔다. 컴파일은 성공으로 끝났다.
- **원인**: `createIO()` 가 `new NodeIO()` 뿐이라 확장을 등록하지 않았다. `quantize()` 가 붙인 `KHR_mesh_quantization` 이 파일에 안 써져, `POSITION` 은 정규화된 SHORT(`componentType 5122`)인데 그것을 선언하는 extension 이 없는 **glTF 스펙 위반 GLB** 가 나갔다. `-480` 이후 모든 런타임 산출물이 이 상태였다.
- **해결**: `new NodeIO().registerExtensions(ALL_EXTENSIONS)`. 이후 `extensionsUsed`·`extensionsRequired` 에 `KHR_mesh_quantization` 이 들어간다. 테스트: `tools/assets/compiler/__tests__/runtimeGlbSpec.test.mjs` — 실제 quantize → writeBinary → JSON chunk 왕복으로 검증한다.
- **예방**: 파이프라인 라이브러리의 경고 로그를 노이즈로 넘기지 않는다. three GLTFLoader 는 관대해서 읽어 줬고 그래서 **웹에서는 멀쩡해 보였다** — 관대한 로더 하나가 통과시킨다고 산출물이 맞는 것이 아니다.

### T-79. 썸네일 z-test 가 뒤집혀 가장 먼 면을 그리고 있었다 (2026-09-08, 해결)

- **증상**: 자체 래스터라이저가 만든 썸네일이 뾰족뾰족한 파편 덩어리였다. 경량화 전 원본도 마찬가지라 simplify 문제가 아니었다.
- **원인**: `rasterizer.mjs` 의 `project()` 가 `depth: dot(rel, forward)` 를 냈다. `forward` 는 물체에서 **카메라 쪽**을 가리키므로 이 값은 **클수록 가깝다**. 그런데 z-buffer 는 `depth < depthBuffer[idx]` 로 작은 값을 채택한다 — 가장 먼 면이 살아남아 모델이 속을 뒤집은 모양이 됐다.
- **해결**: `depth: -z`. mutation 테스트로 확인했다 — 부호를 되돌리면 테스트가 실패한다.
- **예방**: 렌더 결과가 "이상하다" 로 끝나면 도구 자체를 의심한다. 이 썸네일은 `-480` 부터 팔레트에 쓰이고 parity 근거로도 쓰였다. **판정 도구가 틀리면 그 도구로 내린 판정이 전부 무효다** — 이번에도 simplify 품질을 그것으로 볼 뻔했다.

### T-75. `glab api --raw-field` 가 `@파일` 을 확장하지 않아 MR 설명 2개를 경로 문자열로 덮었다 (2026-09-08, 해결)

- **증상**: `-539` 행위 귀속 정정으로 `!473`·`!479` 의 description 을 갱신했다. 명령은 성공(exit 0)했고 read-back 에서 **낡은 문구가 사라진 것도 확인**됐다. 그런데 새로 넣은 정정 문단이 없었다. 실제 description 은 **137자짜리 파일 경로 한 줄**이었다.

  ```
  @C:\Users\SSAFY\AppData\Local\Temp\...\mr473.desc.new.md
  ```

  같은 방식으로 올린 `#114` 코멘트도 경로 한 줄로 게시됐다(note `2776336`).
- **원인**: `@` 파일 확장은 **`--field` 의 동작이고 `--raw-field` 는 값을 문자열 그대로 보낸다.** `glab api --help` 의 `@` 설명이 `--field` 문단에 있는데 그것이 `--raw-field` 에도 적용되는 것으로 읽었다. 한글이 셸 인자로 깨지는 것(cp949)을 피하려 파일 경유를 택했고, 그 목적만 보고 플래그 문법을 확인하지 않았다.
- **왜 안 잡혔나**: 내 read-back 이 사실상 **"낡은 문구가 사라졌나" 만 물었다.** 본문이 통째로 날아가도 그 조건은 통과한다. 새 문구의 존재를 묻는 항목이 함께 있었는데 그 MISS 를 **인코딩 오탐으로 의심**했다 — 같은 세션에서 cp949 오탐을 두 번 겪은 직후라 그쪽을 먼저 의심한 것이다. 실제로는 진짜 실패였다.
- **해결**: 저장해 둔 `.desc.new.md` 로 `--field description=@<파일>` 재전송. `#114` 코멘트는 **삭제하지 않고** `PUT .../notes/2776336` 으로 본문만 교체했다(편집 표시는 남는다). 파손 노출 약 3분.
- **예방**: ① 원격 본문을 바꾼 뒤 read-back 은 **삭제 확인과 삽입 확인을 쌍으로** 둔다 — 한쪽만 보면 전체 소실이 통과한다. ② 값을 파일로 넘길 때 그 플래그가 그 문법을 지원하는지 먼저 확인한다. `--field` 와 `--raw-field` 는 `@` 처리가 다르다. ③ **exit 0 은 의도 달성의 증거가 아니다** (T-25 와 같은 부류). ④ MISS 를 도구 오탐으로 넘기기 전에 **원본을 한 번 떠서 눈으로 본다.**

### T-74. 데이터 파일만 보고 "그 기능이 없다" 고 단정했다 — 읽는 코드를 안 읽었다 (2026-09-08, 해결)

- **증상**: 부스 에셋 매핑 조사에서 *"Unity `BoothObjectRegistry` 에 `assetCode` 개념이 없다. 타입 하나에 prefab 하나다"* 라고 적고, 그 위에 *"타입당 prefab 1개라 `DECORATION` 하나에 패널·빔·기둥·게이트·화분이 다 들어갈 자리가 없다"* 는 결론을 세웠다. 그 결론이 **"Unity 가 구조를 바꿔 줘야 FE 가 움직인다"** 로 이어졌다.
- **원인**: `BoothObjectRegistry.asset`(데이터)만 읽고 `BoothObjectRegistry.cs`(그 데이터를 읽는 코드)를 안 읽었다. 코드에는 `assetCode` 필드와 `GetPrefab(type, assetCode)` 2단 조회가 이미 있었다(`:35`·`:45`·`:103`). `.asset` 을 훑을 때 `assetCode:` 가 대부분 빈 문자열이라 **"필드가 없다" 와 "값이 비어 있다" 를 구분하지 못했다.** 실제로는 11 엔트리 중 2개가 채워져 있기까지 했다.
- **파장**: 조사 결론이 "타 파트가 먼저 움직여야 한다" 였다. 실제로는 데이터만 채우면 되는 일이라 FE 가 바로 진행할 수 있었다. 게임 파트가 회신에서 짚어 주지 않았으면 그 전제로 계속 갔을 것이다.
- **해결**: 조사 문서 §0-1 에 대조표를 넣고, **틀린 문장은 지우지 않고** 취소선 + 사유로 남겼다(T-68 과 같은 처리). 결론이 바뀐 부분도 함께 적었다.
- **예방 1**: **`.asset`·`.json`·`.yaml` 같은 데이터 파일에서 "이 개념이 없다" 를 결론 내지 않는다.** 그 파일을 읽는 코드를 열어 필드와 조회 경로를 확인한다. 빈 값과 없는 필드는 다르다.
- **예방 2**: 같은 회차에 상대도 대칭적인 실수를 했다 — prefab 의 **직접** `.FBX` 참조만 세어 "모델 참조 없음" 으로 판정했는데, 실제로는 중첩 prefab 을 통해 참조한다. **참조를 셀 때 한 단계만 보고 0 을 결론으로 쓰지 않는다.** 양쪽 다 "한 층만 보고 단정" 이라는 같은 형태였다.

### T-73. 워크트리로 옮기자 개인 도구가 조용히 죽었고, 나는 그것을 서버 장애로 보고했다 (2026-09-08, 해결)

- **증상**: JAM MCP 가 `CONNECTION_CLOSED`. Jira 검색도 생성도 못 한다. 나는 "JAM 이 끊겼다, 다음 세션에서 재연결하라" 로 보고했다.
- **원인**: 세션을 `ssafesta` → `ssafesta-25dv` 워크트리로 옮긴 것. JAM 은 레포 안 `.jira-agent/project.yaml` 로 프로젝트를 잡고, 그 경로는 `.git/info/exclude` 에 있어 워크트리에 따라오지 않는다. launcher 를 직접 돌리면 한 줄로 나온다 — `JAM_SETUP_REQUIRED: No .jira-agent/project.yaml found under …ssafesta-25dv`.
- **오진 1**: 하니스가 준 오류 문자열을 원인으로 썼다. `CONNECTION_CLOSED` 는 "붙지 못했다" 일 뿐 **왜** 를 안 담는다. 사용자가 "니가 옮겼잖아" 라고 짚기 전까지 launcher 를 한 번도 안 돌렸다.
- **오진 2**: 고치겠다고 "`.jira-agent` 를 커밋해 워크트리가 물려받게 하자" 고 제안했다. 그 제외에는 이유가 주석으로 바로 위에 적혀 있었다 — "개인 도구 runtime — 팀 미채택. `.gitignore`(커밋됨)가 아니라 여기 두는 이유: `docs/LJH/26` C-5". 커밋했으면 팀 결정을 뒤집는 변경을 MR 로 올렸을 것이다.
- **해결**: `.git/info/exclude` 는 손대지 않았다. 워크트리 5곳(`ssafesta`·`-25dv`·`-oauth`·`-fe0907`·`.claude/worktrees/S15P21A604-527-multi-material`)에 `project.yaml` 을 복사했다. 실행 중 세션은 MCP 를 다시 붙일 수 없어(`claude mcp` 하위명령은 add/get/list/login/logout/remove/serve/reset-project-choices 뿐, `/mcp` 는 이 앱 세션에서 못 연다) **JAM CLI 로 읽기를 살렸다** — `jam jira search|context|full`. 그 도움말이 이 경우를 명시한다: "Read Jira from the shell - the same reads the MCP tools do, for a session that cannot see them yet". 쓰기는 CLI 에 없어 Atlassian Rovo 로 처리했다.
- **예방 1**: **도구가 죽으면 그 도구를 직접 실행해 본다.** MCP 하니스가 넘기는 문자열은 연결 결과일 뿐 진단이 아니다. 한 줄 돌리는 데 30초 걸렸고, 안 돌려서 두 회차를 썼다.
- **예방 2**: **제외 목록을 고치기 전에 왜 제외됐는지를 먼저 읽는다.** `.git/info/exclude` 는 공용 git dir 에 있어 모든 워크트리에 적용되지만 그 안의 파일은 복사되지 않는다. 워크트리를 팔 때 **무추적 런타임 설정은 안 따라온다**를 전제로 둔다.

### T-72. 자산 하나를 재질 하나로 축약해서 태블릿 화면이 사라졌다 — 그리고 그것을 형상 문제로 오해했다 (2026-09-08, 부분 해결)

- **증상**: `SURVEY_KIOSK_DEFAULT` 가 8각도 전부 정상적인 카운터로 나오는데도 "설문 키오스크로 안 보인다". 상판 위 태블릿이 옅은 사각 자국으로만 보인다.
- **원인**: **재질 파이프라인이 자산당 대표 `.mat` 하나만 옮긴다.** 자산 설정이 `material: PlasticWhite.mat` 하나를 지정하고, 런타임 GLB 의 `materials` 도 1개다. 원본은 `PlasticWhite.mat` + `Tablet.mat`(baseColor `Tablet.jpg` = 화면 이미지) + `AluminiumBrushed.mat` 세 개다. 그래서 태블릿이 **검은 화면 대신 흰 판**이 된다.
- **오해가 있었다**: 앞선 두 회차에서 이 인상을 **형상 문제로 읽었다.** `.prefab` CRLF(T-64)를 고쳐 세운 뒤에도 인상이 그대로라 "아직 뭔가 누워 있나" 를 계속 팠다. 실제로는 자식 5개가 전부 제자리에 있었고 — intermediate GLB 에서 `Counter01`·`Counter01Top`·`Counter01Cloth01`·`CounterShelf`·`Tablet` 확인 — 태블릿도 `m_LocalPosition (0, 0.9233265, 0.02)` 로 상판 위에 정확히 놓여 있었다. **틀린 것은 색이지 자리가 아니었다.**
- **해결**: 재질 축약은 안 고쳤다 — Compiler v2 범위이고 `S15P21A604-527` 로 끊어 냈다. 대신 **known difference 로 명시**하고 gate-matrix `D-2` 에 `다중 재질 보존 = FAIL` 행을 새로 만들었다. 키오스크 판정은 `PARTIAL` 유지, 의자는 `PASS_CANDIDATE` 로 올렸다.
- **예방 1 — 인상을 형상 가설로 바로 옮기지 않는다.** "안 보인다" 는 형상·자리·색 셋 중 어느 것이든 원인일 수 있다. **원본 파일에서 자식 목록과 transform 을 먼저 읽으면** 형상·자리는 몇 분 만에 배제된다. 그 순서를 안 지켜 두 회차를 형상 쪽에서 보냈다.
- **예방 2 — 막힌 것이 "사람 손" 이라고 결론 내리기 전에 경로를 하나 더 찾는다.** 이 회차 직전까지 8각도가 두 번 미확보로 남았고 사유는 "크롬 창이 앞에 있어야 한다" 였다. 실제로는 CDP 스크린샷을 안 쓰고 페이지 안에서 `canvas.toDataURL()` 로 읽으면 끝이었고, 그걸 가능하게 하는 `preserveDrawingBuffer: true` 는 **이미 코드에 있었다.** 블로커를 사람에게 넘기기 전에 "이 도구 말고 다른 경로가 있나" 를 한 번 묻는다.

### T-71. 같은 refresh token 을 curl 과 브라우저 두 경로로 써서 서버가 세션을 폐기했다 (2026-09-07, 해결)

- **증상**: 로컬 회원 세션을 만들어 편집기(`/app/games/1/edit`)를 열려는데, curl 로는 `POST /auth/refresh` 가 200 인데 같은 토큰으로 브라우저에서는 401 `INVALID_MEMBER_TOKEN` 이었다. 그 401 뒤에는 방금 발급받은 새 토큰까지 죽어 있었다.
- **원인**: 설계대로 동작한 것이다. `MemberSessionService.refresh()` 는 `getAndDelete` 로 토큰을 **소비**하고(`:55` 주석), 이미 소비된 토큰이 다시 오면 재사용으로 보고 `revoke(userId)` 로 **그 사용자의 세션 전체를 지운다**(`:60-64`). curl 이 먼저 소비한 토큰을 브라우저가 뒤늦게 보내면서 재사용 탐지가 걸렸다.
- **왜 브라우저가 낡은 토큰을 보냈나**: `document.cookie` 로 심은 `path=/` 쿠키가 남아 있었고, 서버가 내려주는 쿠키는 `Path=/api/v1/auth/refresh` 라 **경로가 다른 두 쿠키가 공존**했다. 페이지에서 보이는 것은 `/` 쪽이었다.
- **해결**: 쿠키 경로를 통하지 않는다. `enterAsDeveloper()`(`devEntry.ts:47`)가 하는 일을 그대로 해서 — curl 로 Access Token 을 받아 `session.ts` 의 `setMemberSession()` 에 주입 — 편집기에 들어갔다.
- **교훈**: **로컬 검증에서 하나의 refresh token 을 두 클라이언트로 쓰지 않는다.** 재사용 탐지는 공격자와 나를 구분하지 않는다. 확인은 Redis 키 잔존으로 한다 — 소비되면 `local:auth:refresh:<hash>` 가 사라지므로, 키가 남아 있으면 그 요청은 애초에 토큰을 보내지 않은 것이다.
- **부수 확인**: Redis 에 저장되는 것은 원문이 아니라 **sha256 을 base64url(패딩 없음)로 인코딩한 해시**다(`MemberSessionService.java:107`). `local:auth:active:{userId}` 값으로 원문을 역산할 수 없으니, 세션을 손으로 만들 때는 raw·hash 쌍을 같은 방식으로 함께 만들어 넣어야 한다.

### T-66. 테스트가 제너레이터 인스턴스를 공유해 두 번째 소비가 빈 스트림이 됐다 (2026-09-07, 해결)

- **증상**: `AiChatOverlay.test.tsx` 2건이 develop 에서 계속 red 였다(T-58 이 "타 소관" 으로 남겨 둔 그것). `-516` 이 같은 파일을 건드리므로 원인을 갈랐다. **둘 다 제품 코드가 아니라 테스트 결함이었다.**
- **원인 ①** `streamMessage.mockReturnValue(mockStreamSuccess())` — `mockStreamSuccess()` 를 **한 번만 호출**해 그 제너레이터 **인스턴스**를 두 질문이 공유한다. 첫 질문이 소진하면 두 번째는 빈 스트림이다. 실행으로 확인했다:

  ```
  1회차: "ab" | 2회차: ""            ← mockReturnValue(g())
  factory 1회차: "ab" | 2회차: "ab"  ← mockImplementation(() => g())
  ```

  같은 파일의 `error envelope` 테스트는 이미 `vi.fn(() => mockStreamError())` 로 옳게 쓰고 있었다 — 한 파일 안에 두 관용구가 공존했다.
- **원인 ②** `streamMessage.mockRejectedValueOnce({...403})` — `streamMessage` 는 **async generator** 인데 `mockRejectedValueOnce` 는 **Promise** 를 준다. `consumeSseStream` 의 `for await` 가 그것을 못 돌린다:

  ```
  Promise 를 for-await 로 돌리면: TypeError | rejected is not async iterable
  던지는 async generator 는: status = 403 | isAiHttpError 통과
  ```

  TypeError 는 `isAiHttpError` 를 통과하지 못해 `shouldResetConversation` 이 아예 안 돈다. **즉 이 테스트는 검증하려던 403 초기화 경로를 한 번도 밟은 적이 없다.**
- **해결**: ①은 factory 형태로, ②는 던지는 async generator 로 바꿨다. 제품 코드는 손대지 않았다.
- **예방**: **제너레이터·이터러블을 돌려주는 함수는 `mockReturnValue` 가 아니라 `mockImplementation(() => …)`** 으로 준다. 그리고 async generator 의 실패는 `mockRejectedValue` 가 아니라 **던지는 제너레이터**로 재현한다 — 타입이 `AsyncGenerator` 인데 mock 이 `Promise` 를 주면 컴파일은 통과하고 런타임에서만 다른 경로를 탄다.

- **해결**: 개행 패턴 3곳을 `\r?\n` 으로. 파서 계층에 LF/CRLF 동일 결과 회귀를 걸었다(`unityPrefabCrlf.test.mjs`). **산출물을 읽는 단언은 후속 과제로 남긴다.**
- **예방**: **`T-61` 과 같은 결함군의 두 번째 파일이다.** Unity 직렬화 파일(`.mat`·`.prefab`·`.asset`·`.meta`)을 정규식으로 읽는 자리는 개행을 반드시 `\r?\n` 으로 쓴다. 그리고 **"수정했다" 는 기록이 있는데 증상이 재현되면, 그 수정이 코드에 있는지가 아니라 그 코드에 값이 도달하는지를 본다.**

### T-61. CRLF 하나로 `.mat` 텍스처 인식이 전멸했는데 LF 픽스처 테스트는 통과하고 있었다 (2026-09-07, 해결)

- **증상**: Runtime Asset Compiler 가 대표 재질 두 개를 `채널 [없음] · 원본 0 B` 로 리포트했다. "색만 있는 재질" 로 읽힌 것이라 오류도 경고도 아니다. 그런데 `.mat` 원본은 `_BaseMap`·`_BumpMap`·`_MetallicGlossMap` 을 정상 참조하고 있었다.
- **원인**: `compiler/material.mjs` 의 `textureOf` 정규식이 **키 바로 뒤에 LF** 를 요구했다. Unity 가 저장한 `.mat` 은 Windows 에서 CRLF 라 캐리지리턴이 먼저 온다. 공백 흡수(`\s*`)는 LF **뒤**에 있어서 그것을 먹지 못한다.
- **판정 근거**: 같은 파서에 같은 파일을 두 형태로 넣어 갈랐다 — 원본(CRLF)에서 `textures = []`, CRLF 를 LF 로 치환하면 `textures = [baseColor, normal, metallicRoughness]`. **정규식을 다시 타이핑하지 않고 실제 모듈을 import 해서** 돌린 것이 중요했다. 셸 히어독으로 정규식을 재입력했을 때는 백슬래시가 한 겹 먹혀 "고친 쪽도 실패" 라는 엉뚱한 결론이 나왔다.
- **왜 안 잡혔나**: 회귀 테스트의 픽스처 `MAT` 가 템플릿 리터럴이라 **LF 전용**이다. 파서는 픽스처에서 통과하고 실물에서만 실패했다. 테스트가 있다는 사실이 오히려 안심을 줬다.
- **해결**: 개행 패턴을 `\r?\n` 으로 넓혔다. 픽스처를 CRLF 로 바꿔 같은 채널이 나오는지 보는 케이스를 추가했고, 수정을 stash 로 되돌리면 그 테스트가 실제로 붉어지는 것까지 확인했다.
- **예방**: **외부 도구가 만든 파일을 파싱하는 정규식은 개행을 `\r?\n` 으로 쓴다.** 그리고 그런 파서의 픽스처에는 CRLF 케이스를 함께 둔다 — 저장소가 `.gitattributes` 로 정규화하더라도 작업 디렉터리의 실제 바이트는 플랫폼을 탄다.

### T-47. R3F 픽킹 테스트가 계속 빗나갔다 — 합성 PointerEvent 의 `offsetX` (2026-09-07, 해결)

- **증상**: `-470` 에서 R3F 캔버스의 오브젝트 선택을 합성 `PointerEvent` 로 검증하려는데 121개 지점을 훑어도 한 번도 선택되지 않았다. 수동 raycast 로는 같은 좌표에서 오브젝트가 정확히 잡혔고, R3F 의 내부 interaction 목록에도 핸들러가 등록돼 있었다. "이벤트는 도달하는데 엉뚱한 것이 잡힌다" 는 상태였다.
- **원인**: R3F 의 기본 `events.compute` 가 NDC 를 **`event.offsetX` / `offsetY`** 로 계산한다. `new PointerEvent(...)` 로 만든 이벤트는 `clientX/clientY` 만 넣어도 `offsetX/offsetY` 가 **0** 이라 항상 캔버스 좌상단(−1, 1)을 가리켰고, 그 지점에서 유일하게 걸리는 거대한 바닥 평면만 반응했다.
- **해결**: 합성 이벤트에 `Object.defineProperty(e, 'offsetX', …)` 로 두 값을 심었다. 그러자 선택·이동(0.25m snap)·회전(15° snap)·bounds clamp 가 전부 정상 동작했다. **렌더러 결함이 아니라 테스트 작성법 문제였다.**

### T-23. Git Bash 콜론 오변환 — `git show <ref>:<path>` 실패를 "0건"으로 읽어 판정을 두 번 뒤집음 (2026-08-25, 해결)

- **증상**: CI 정지 규칙(`when: never`)이 어느 브랜치에 반영됐는지 확인하려고 `for B in front develop back ai game; do git show origin/$B:.gitlab-ci.yml | grep -c "when: never"; done`을 돌렸더니 **전 브랜치 0개**가 나와 "아무 데도 미반영"으로 보고했다. 실제로는 명령 자체가 실패하고 있었다 — `git show origin/game:.gitlab-ci.yml`이 `fatal: ambiguous argument 'origin\game;.gitlab-ci.yml'`로 죽는다. **Git Bash(MSYS)가 인자를 Windows 경로로 오인해 `:`→`;`, `/`→`\`로 변환**한다.
- **원인**: ⑴ 직접 원인 — MSYS path conversion. `ref:path` 문법에 콜론이 있어 경로로 오탐된다. ⑵ **더 나쁜 것 — 실패를 0으로 읽었다.** `git show`가 stderr로 죽으면 파이프의 `grep -c`는 빈 입력을 받아 정상적으로 `0`을 반환한다. 종료 코드를 안 봤기 때문에 "명령 실패"와 "매치 0건"이 구분되지 않았다. **바로 그날 세 스킬에 "실패를 0건으로 바꾸지 마라"를 최상위 원칙으로 박아놓고 내가 어겼다.** ⑶ PowerShell로 재확인했을 때도 `when: never` 문자열 존재만 세서 "전 브랜치 반영됨"이라는 **반대 방향 오판**을 했다 — 그 문자열은 원래 workflow.rules의 표준 중복방지 규칙에도 있어서, 문맥 없이 문자열만 세면 안 된다.
- **해결**: `MSYS_NO_PATHCONV=1`을 앞에 붙이거나 PowerShell에서 `git show "origin/${b}:path"`로 실행. 판정은 문자열 개수가 아니라 **문맥(어느 rules 블록에 있는가)**으로 했다. 최종 사실: 정지 규칙은 `game`에만 있었고 front·develop·back·ai는 어제 배포본 그대로였다.
- **예방**: ⑴ **Git Bash에서 `ref:path` 문법을 쓸 때는 `MSYS_NO_PATHCONV=1`을 붙이거나 PowerShell을 쓴다.** `git show`·`git cat-file`·`git checkout ref -- path`가 해당한다(뒤의 것은 `--` 뒤라 안전). ⑵ **파이프 앞 명령의 성공 여부를 확인하지 않은 채 뒤의 카운트를 판정 근거로 쓰지 않는다.** 최소한 `set -o pipefail`이나 `git show ... || echo FAILED`로 실패를 드러낸다. ⑶ **문자열 존재로 설정 상태를 판정하지 않는다** — 같은 토큰이 다른 목적으로 쓰일 수 있다. 블록 구조를 직접 본다.

### T-17. 부트스트랩 refresh와 라우트 가드의 레이스 — 새로고침 로그인 유지가 항상 실패 (2026-08-23, 해결)

- **예방**: **비동기 초기화와 그 결과를 소비하는 가드/분기는 "미완료" 상태를 명시적 3번째 값으로 모델링**한다 — 초기값을 실패값과 겸용하면 레이스가 타입에 안 드러난다. 단위 테스트가 각 모듈을 따로 검증할 때 조합 경로는 브라우저 실측이 유일한 그물이다(T-11·T-12와 같은 계열 — 상태를 가진 UI는 러너로 안 잡힌다).

### T-15. useMemo를 early return 뒤에 둬 hooks 순서 오류 — HMR이 깨진 채로 남아 브라우저 검증이 거짓 실패를 냄 (2026-08-22, 즉시 수정)

- **증상**: T023 통행 판정을 `useMemo`로 감싸 `preErrors`·`preWarnings` 계산 위에 뒀는데, `StudioPage.tsx`의 `draftQuery.isLoading`/`isLeaseExpired` early return **아래**에 넣었다. `oxlint`가 `react-hooks(rules-of-hooks)`로 즉시 잡았지만, 그 전에 브라우저에서 먼저 렌더돼 `ReferenceError` 없이도 `EditorCanvas`가 `OBJECT_SIZE_M is not defined`(다른 리네이밍 잔재)로 크래시하고 Vite HMR이 `Failed to reload ... 500`을 반복했다. 이후 저장 버튼을 눌러도 상태가 계속 `dirty`로 보여 "서버가 거부한 줄" 착각할 뻔했다.
- **원인**: hooks는 조건부 return 위에서 항상 같은 순서로 호출돼야 하는데(rules-of-hooks), early return 아래 `useMemo`를 두면 렌더 경로에 따라 훅 호출 수가 달라진다. 브라우저는 그 오류를 삼키고 이전(깨진) 모듈 그래프로 계속 렌더해, `버튼 클릭 → 상태 무반응`이 **저장 로직 결함처럼** 보였다 — 실제 원인은 HMR이 새 코드를 못 실었을 뿐이었다.
- **해결**: `oxlint` 오류를 보고 `useMemo`를 early return 위로 옮겨 즉시 수정. 브라우저는 `preview_stop`→`preview_start`로 dev 서버를 완전히 재시작해야 깨진 HMR 그래프가 걷혔다(단순 새로고침으로는 안 걷힘 — 이미 로드된 모듈 캐시가 낡은 상태였다).
- **예방**: **lint를 브라우저 실측보다 먼저 통과시킨다** — `react-hooks` 규칙 위반은 런타임에서 항상 같은 방식으로 실패하지 않아(early return 경로에 따라 다름) 브라우저에서 먼저 잡으면 오진단하기 쉽다. HMR이 에러를 낸 뒤(`Failed to reload`)에는 새로고침이 아니라 **dev 서버 자체를 재시작**해서 모듈 그래프를 초기화한다.

### T-12. 브라우저 "통과" 판정이 실제 검증이 아닌 경우 — quickstart §5는 mock으로 재현 불가였다 (2026-08-21, 미해결·설계 한계)

### T-11. PropertiesPanel 로컬 상태가 prop 변경을 반영하지 않아 좌표를 되돌릴 수 있었다 (2026-08-21, 해결)

- **증상**: 중간 검증에서 캔버스 드래그로 오브젝트를 옮겼는데 PropertiesPanel의 `x`·`z` 입력값이 `0`에 멈춰 있었다. 저장 JSON은 `x: 1.5, z: -1.5`로 정상인데 화면 숫자만 `0`이라, 사용자가 실제와 다른 값을 보게 된다.
- **원인**: `useState(String(object.position.x))`로 로컬 문자열 상태를 두고 `useEffect` 동기화를 넣지 않았다. `useState` 초기화 인자는 재평가되지 않고 `StudioPage`가 `key`도 주지 않아 같은 인스턴스가 재사용되므로, 드래그·다른 오브젝트 선택 어느 쪽도 반영되지 않았다. **표시 오류에 그치지 않는다** — 그 상태에서 다른 칸을 blur하면 `commitPosition(옛 xText, 새 zText)`가 나가 방금 드래그한 좌표를 되돌리고, 다른 오브젝트를 선택한 뒤 blur하면 새 오브젝트가 이전 오브젝트 좌표로 순간이동한다.
- **해결**: `object.objectId`·`position.x`·`position.z`·`configId`를 의존성으로 하는 `useEffect` 두 개로 외부 변경을 되맞췄다. 브라우저 실측으로 드래그 후 SVG `translate(1.5 -0.75)`와 패널 `x=1.5·z=0.75` 일치, 다른 오브젝트 선택 시 `x=-2·z=2.25` 갱신 확인(커밋 `7b463a1`). 같은 함수에 있던 `configId` Int32 검증 부재(계약 §1 위반 — 0·음수·소수 통과)도 함께 고쳤다.
- **예방**: **로컬 `useState`로 prop을 미러링할 때는 그 prop이 외부에서 바뀔 수 있는지 먼저 따진다.** 이 패널은 "입력 중 빈 문자열 허용"을 위해 로컬 상태가 필요했지만, 같은 값이 캔버스 드래그로도 바뀐다는 사실을 설계 시점에 놓쳤다. 브라우저 실측이 없었으면 `tsc`·lint 통과만으로 넘어갔을 결함이다 — 상태를 가진 UI는 타입 검증으로 잡히지 않는다.

### T-7. Issue #5 서명 가이드 초안이 develop 직접 push를 안내할 뻔함 (2026-08-20, 자체 발견·해결)

- **예방**: 브랜치 운영 규칙을 다루는 안내문(가이드·코멘트)을 쓸 때는 게시 직전에 `docs/17`(또는 해당 컨벤션 문서) 대조를 **매번** 다시 한다 — 같은 세션에서 이미 검토한 규칙이라도 새 안내를 쓸 때 자동으로 지켜지지 않는다.

### T-6. 이슈 종결 가능 여부를 이슈 본문 확인 없이 판정 (2026-08-20, 해결)

- **증상**: Issue #2([front] Overlay·Unity 브릿지 계약 리뷰 요청)의 종결 가능 여부를 물었을 때 "FE `events.ts` 타입 추가와 Unity 구현이 미착수라 닫을 수 없다"고 보고했다. 사용자가 "해당 이슈는 계약 확인이지 구현까지 포함하지 않는다"고 지적해 다시 확인하니 이슈 본문의 요청은 "확인 요청" 2건뿐이었고 구현은 범위 밖이었다. 판정을 뒤집고 종결했다.

- **예방**: 이슈 종결 가능 여부를 판정할 때는 **코멘트 스레드보다 이슈 본문의 요청·체크리스트를 먼저 읽는다.** 스레드에서 파생된 후속 작업과 이슈 본문이 정의한 완료 조건은 별개다. T-4(값의 생성 지점만 보고 소비 지점을 안 봄)와 같은 형태의 실수 — 근거의 원본을 건너뛰고 중간 정보로 판단했다.
