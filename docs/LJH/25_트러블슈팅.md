### T-41. 개인 스킬을 팀 scope(`.claude/skills`·`.agents/skills`)에 넣고 develop 까지 머지했다 (2026-09-06, 해결)

- **증상**: `festa-outbox`(내가 밖에 물어 놓고 답을 못 받은 것을 ASC 조율 view 로 보는 개인 절차 스킬)를 `.claude/skills/`·`.agents/skills/` 에 만들어 [!316](https://lab.ssafy.com/s15-metaverse-game-sub1/S15P21A604/-/merge_requests/316) 으로 develop 에 머지했다. 두 경로는 **팀 전체가 자동 로드하는 자리**다. 약 1시간 뒤 사용자 지적으로 발견.
- **원인**: 작업 지시가 "SSAFESTA 저장소에 PR-E 로 festa 정책을 넣어라" 였고, 그 문장의 "저장소" 를 팀 scope 로 읽었다. 그러나 `26_로컬_규약_스냅샷.md` C-6 이 08-25 부터 **"`.claude/skills/`(project scope)는 팀 전체가 자동 로드하는 자리라 개인 절차를 넣지 않는다"** 고 못박고 있고, `CLAUDE.local.md` 도 "팀 규칙 승격은 리드 승인 사안" 이다. 기존 `festa-*` 3종이 전부 `~/.claude/skills/` + `docs/LJH/skills/` 사본 구조인 것을 **작업 전에 보지 않았다** — 이름 충돌(`festa-inbox`)을 발견하고도 그 스킬이 *어디에* 있는지(user scope)를 배치 판단에 연결하지 않았다.
- **함께 어긴 것**: !316 설명이 `.gitlab/merge_request_templates/Default.md` 골격(`## Jira Issue`·`## 주요 변경 사항`·`## Reviewer 참고사항`)을 안 따르고 CLAUDE.md 요약본의 4 항목만 썼다. squash 머지로 커밋 본문이 MR 제목 한 줄로 대체돼 경위가 develop 이력에 남지 않았다(팀 결정 §9 그대로이지만, 그래서 **경위는 MR 설명에 있어야** 한다).
- **해결**: [!317](https://lab.ssafy.com/s15-metaverse-game-sub1/S15P21A604/-/merge_requests/317) 로 `ebf46ba9` 를 그대로 되돌렸다(history rewrite 없음). 스킬은 `~/.claude/skills/festa-outbox/` 로 옮기고 사본을 `docs/LJH/skills/festa-outbox/` 에 뒀다(C-6 방식, LF 고정은 `.gitattributes` 기존 규칙이 덮는다). !317 설명은 Default 템플릿 골격을 그대로 썼다.
- **예방**: **스킬·훅·설정을 만들기 전에 같은 접두사의 기존 것이 어느 scope 에 있는지 확인한다** — `ls ~/.claude/skills .claude/skills .agents/skills` 세 줄이면 된다. 개인 절차는 user scope, 사본은 `docs/LJH/`. 팀 scope 에 무언가를 넣는 것은 리드 승인 뒤다. 지시문의 "저장소에 넣어라" 는 **어느 브랜치·어느 scope 인지를 내 규칙으로 다시 판정**한 뒤 실행한다.

### T-40. 작업일지 양식이 조용히 무너졌다 — 사람/AI 구분·관련 파일·트러블슈팅 종결줄 (2026-09-05, 해결·규칙화)

- **증상**: 전수조사에서 원 양식 3요소가 시점을 달리해 사라진 것이 드러났다. `📎 관련 파일` 은 08-20 까지 18/18 이었다가 **08-21 부터 붕괴**하고 08-22~08-27 은 0, `📎 트러블슈팅` 도 같은 궤적, `👤`(사람/AI 구분)은 08-26 까지 유지되다 **08-28 이후 0건**이다. 규칙 2(관련 파일·커밋·태그)·규칙 4(누가 했는지 구분)를 위반한 상태로 열흘 넘게 썼다.
- **원인**: 한 항목이 길어지면서 서술 안에 파일·커밋·근거가 다 들어가니 **종결줄이 중복처럼 느껴져 빠뜨렸다.** `👤` 는 세션이 길어지고 내가 연속 실행하는 비중이 늘면서 "전부 AI 가 한 것" 으로 뭉뚱그려졌다 — 실제로는 사용자가 방향을 정하고 판단한 지점이 매 라운드 있었다. 어느 쪽도 한 번에 깨진 것이 아니라 **한 항목씩 조용히 빠졌고, 스스로 점검하는 절차가 없어 아무도 못 봤다.**
- **발견**: 사용자가 "언젠가부터 양식·규약을 위반하거나 누락하기 시작했다" 며 전수조사를 지시했다. 자기 점검으로는 못 잡았다 — 매 세션 끝에 "기록했나" 만 확인하고 "양식대로 기록했나" 는 확인하지 않았다.
- **해결**: 09-05 섹션부터 원 양식(`👤`/`🤖` 구분 + `📎 관련 파일` + `📎 트러블슈팅`)을 복구한다. 과거 항목은 다시 쓰지 않는다 — 그 시점의 기록이고, 사후 편집하면 무엇이 실제 기록이었는지가 사라진다.
- **예방**: **세션 종료 전 마지막 항목 하나를 원 양식과 눈으로 대조한다.** 규칙 위반은 "기록 안 함" 이 아니라 "기록은 했는데 양식이 빠짐" 으로 온다. 누락 날짜(08-19·08-29·09-02)는 확인 결과 내 커밋이 0건인 비작업일이라 위반이 아니다.

### T-38. 초안 파일을 섹션으로 잘라 게시하면서 문서 헤더까지 함께 나갔다 — MR !259 코멘트에 "게시 초안 (승인 후 게시)" 노출 (2026-09-05, 해결)

- **증상**: `!259` 에 남긴 첫 리뷰 코멘트(note 2765362)가 `# 게시 초안 — 2026-09-05 (승인 후 게시)` 로 시작했다. 타 파트가 보는 자리에 내 내부 작업 파일의 제목과 승인 대기 상태가 그대로 노출됐다. 본문 판정 내용은 정상이었다.

- **예방**: **게시 직후 그 코멘트를 다시 읽는다.** 보내는 것과 보이는 것은 다르다 — 특히 파일을 잘라 만든 본문은 앞뒤 한 줄을 눈으로 확인한다. 초안 파일에는 문서 제목을 두지 않거나, 자를 때 첫 조각도 다른 조각과 같은 모양이 되도록 맨 앞에 구분자를 넣는다. T-13(내부 메타데이터 블록을 이슈에 그대로 게시)과 같은 계열이고, 그때의 교훈이 "본문만 보고 넘기지 않는다" 였는데 이번엔 본문이 맞아서 헤더를 못 봤다.

### T-36. ASC 0.3.0 이 Node 24+ 를 요구하는데 호스트 기본이 v22 — 매 호출 PATH 우회 (2026-08-30, 우회)

- **증상**: `asc setup status` 가 실행되지 않는다.
  ```
  ASC 0.3.0 needs Node 24 or newer; this process is v22.23.2.
  A newer Node is already on this machine — use it for the same command.
    v26.7.0 at /opt/homebrew/opt/node/bin
  ```
- **원인**: 호스트 기본 PATH 의 node 가 v22.23.2 다. 머신에 v26.7.0 이 있지만 PATH 우선순위가 낮다.
- **해결**: 우회만 했다. 이 세션의 **모든** ASC 호출에 `PATH="/opt/homebrew/opt/node/bin:$PATH"` 를 붙였다. 누락하면 즉시 실패한다.
- **부수 함정**: `asc progress report --milestone "…"` 처럼 **하이픈으로 시작하는 값**을 넘기면 Node `parseArgs` 가 거부한다 — `TypeError [ERR_PARSE_ARGS_INVALID_OPTION_VALUE]: Option '--milestone' argument is ambiguous.` 한국어 문장에 `—`(em dash)가 아닌 `-`(hyphen)로 시작하는 절이 들어가면 재현된다. `--milestone=값` 형태로 우회한다.
- **예방**: ⑴ ASC 호출은 래퍼나 alias 로 감싸 PATH 를 고정하는 편이 낫다 — 매번 손으로 붙이는 것은 언젠가 빠진다. ⑵ ASC 에 넘기는 값은 처음부터 `--opt=value` 로 쓴다. ⑶ 근본 해결(런타임 요구 완화 / 호스트 node 승격)은 관제 센터 판단 사항으로 넘겼다.

### T-27. Docker Desktop이 stale 소켓 하나 때문에 기동 중단 — 프로세스는 떠 있어 "기동 중"으로 보였다 (2026-08-26, 운영상 복구·잔재 존속)

### T-24. 환경 이전이 remote·자격증명·MCP 경로 3층에서 각각 따로 끊김 — 코드 동기화 문제로 오인하기 쉬운 구조 (2026-08-26, 해결)

- **증상**: 집(macOS) 환경 저장소가 여전히 GitHub `origin`·`5022335`(08-23) HEAD에 멈춰 있었다. 원격을 GitLab으로 바꾸자 `git fetch origin`이 `fatal: could not read Username for 'https://lab.ssafy.com': terminal prompts disabled`로 실패. 같은 이전에서 `.mcp.json`의 JAM 경로가 `C:\\colosair\\...` Windows 절대경로라 이 macOS 세션에서 애초에 기동 대상이 아니었고, `docs/LJH/26_로컬_규약_스냅샷.md` B섹션은 "현재 Windows 환경에는 B-1~B-4가 없다"고 서술돼 있었는데 정작 이 macOS 환경엔 그 4건이 정확히 살아 있었다(사실과 반대).

### T-23. Git Bash 콜론 오변환 — `git show <ref>:<path>` 실패를 "0건"으로 읽어 판정을 두 번 뒤집음 (2026-08-25, 해결)

- **증상**: CI 정지 규칙(`when: never`)이 어느 브랜치에 반영됐는지 확인하려고 `for B in front develop back ai game; do git show origin/$B:.gitlab-ci.yml | grep -c "when: never"; done`을 돌렸더니 **전 브랜치 0개**가 나와 "아무 데도 미반영"으로 보고했다. 실제로는 명령 자체가 실패하고 있었다 — `git show origin/game:.gitlab-ci.yml`이 `fatal: ambiguous argument 'origin\game;.gitlab-ci.yml'`로 죽는다. **Git Bash(MSYS)가 인자를 Windows 경로로 오인해 `:`→`;`, `/`→`\`로 변환**한다.
- **원인**: ⑴ 직접 원인 — MSYS path conversion. `ref:path` 문법에 콜론이 있어 경로로 오탐된다. ⑵ **더 나쁜 것 — 실패를 0으로 읽었다.** `git show`가 stderr로 죽으면 파이프의 `grep -c`는 빈 입력을 받아 정상적으로 `0`을 반환한다. 종료 코드를 안 봤기 때문에 "명령 실패"와 "매치 0건"이 구분되지 않았다. **바로 그날 세 스킬에 "실패를 0건으로 바꾸지 마라"를 최상위 원칙으로 박아놓고 내가 어겼다.** ⑶ PowerShell로 재확인했을 때도 `when: never` 문자열 존재만 세서 "전 브랜치 반영됨"이라는 **반대 방향 오판**을 했다 — 그 문자열은 원래 workflow.rules의 표준 중복방지 규칙에도 있어서, 문맥 없이 문자열만 세면 안 된다.
- **해결**: `MSYS_NO_PATHCONV=1`을 앞에 붙이거나 PowerShell에서 `git show "origin/${b}:path"`로 실행. 판정은 문자열 개수가 아니라 **문맥(어느 rules 블록에 있는가)**으로 했다. 최종 사실: 정지 규칙은 `game`에만 있었고 front·develop·back·ai는 어제 배포본 그대로였다.
- **예방**: ⑴ **Git Bash에서 `ref:path` 문법을 쓸 때는 `MSYS_NO_PATHCONV=1`을 붙이거나 PowerShell을 쓴다.** `git show`·`git cat-file`·`git checkout ref -- path`가 해당한다(뒤의 것은 `--` 뒤라 안전). ⑵ **파이프 앞 명령의 성공 여부를 확인하지 않은 채 뒤의 카운트를 판정 근거로 쓰지 않는다.** 최소한 `set -o pipefail`이나 `git show ... || echo FAILED`로 실패를 드러낸다. ⑶ **문자열 존재로 설정 상태를 판정하지 않는다** — 같은 토큰이 다른 목적으로 쓰일 수 있다. 블록 구조를 직접 본다.

### T-17. 부트스트랩 refresh와 라우트 가드의 레이스 — 새로고침 로그인 유지가 항상 실패 (2026-08-23, 해결)

- **증상**: 001 Auth 완료 범위 감사의 quickstart §6 실측에서 로그인 후 새로고침하면 항상 `/login`으로 밀렸다. vitest는 129개 전부 그린인 상태 — bootstrap 모듈 단위 테스트(refresh 호출→`setMemberSession`)와 가드 판정 함수 테스트가 각각은 통과하는데, 둘의 **조합**이 깨져 있었다.
- **원인**: `bootstrapAuth()`의 refresh는 useEffect 비동기인데 `RequireAuth`는 첫 렌더에서 초기 `anonymous`로 즉시 `<Navigate to="/login" replace>`를 확정했다. refresh가 이길 수 없는 결정적 레이스 — 초기 anonymous는 "미확인"인데 "비로그인 확정"으로 취급한 것.

- **예방**: **비동기 초기화와 그 결과를 소비하는 가드/분기는 "미완료" 상태를 명시적 3번째 값으로 모델링**한다 — 초기값을 실패값과 겸용하면 레이스가 타입에 안 드러난다. 단위 테스트가 각 모듈을 따로 검증할 때 조합 경로는 브라우저 실측이 유일한 그물이다(T-11·T-12와 같은 계열 — 상태를 가진 UI는 러너로 안 잡힌다).

### T-15. useMemo를 early return 뒤에 둬 hooks 순서 오류 — HMR이 깨진 채로 남아 브라우저 검증이 거짓 실패를 냄 (2026-08-22, 즉시 수정)

- **증상**: T023 통행 판정을 `useMemo`로 감싸 `preErrors`·`preWarnings` 계산 위에 뒀는데, `StudioPage.tsx`의 `draftQuery.isLoading`/`isLeaseExpired` early return **아래**에 넣었다. `oxlint`가 `react-hooks(rules-of-hooks)`로 즉시 잡았지만, 그 전에 브라우저에서 먼저 렌더돼 `ReferenceError` 없이도 `EditorCanvas`가 `OBJECT_SIZE_M is not defined`(다른 리네이밍 잔재)로 크래시하고 Vite HMR이 `Failed to reload ... 500`을 반복했다. 이후 저장 버튼을 눌러도 상태가 계속 `dirty`로 보여 "서버가 거부한 줄" 착각할 뻔했다.
- **원인**: hooks는 조건부 return 위에서 항상 같은 순서로 호출돼야 하는데(rules-of-hooks), early return 아래 `useMemo`를 두면 렌더 경로에 따라 훅 호출 수가 달라진다. 브라우저는 그 오류를 삼키고 이전(깨진) 모듈 그래프로 계속 렌더해, `버튼 클릭 → 상태 무반응`이 **저장 로직 결함처럼** 보였다 — 실제 원인은 HMR이 새 코드를 못 실었을 뿐이었다.
- **해결**: `oxlint` 오류를 보고 `useMemo`를 early return 위로 옮겨 즉시 수정. 브라우저는 `preview_stop`→`preview_start`로 dev 서버를 완전히 재시작해야 깨진 HMR 그래프가 걷혔다(단순 새로고침으로는 안 걷힘 — 이미 로드된 모듈 캐시가 낡은 상태였다).
- **예방**: **lint를 브라우저 실측보다 먼저 통과시킨다** — `react-hooks` 규칙 위반은 런타임에서 항상 같은 방식으로 실패하지 않아(early return 경로에 따라 다름) 브라우저에서 먼저 잡으면 오진단하기 쉽다. HMR이 에러를 낸 뒤(`Failed to reload`)에는 새로고침이 아니라 **dev 서버 자체를 재시작**해서 모듈 그래프를 초기화한다.

### T-12. 브라우저 "통과" 판정이 실제 검증이 아닌 경우 — quickstart §5는 mock으로 재현 불가였다 (2026-08-21, 미해결·설계 한계)

### T-11. PropertiesPanel 로컬 상태가 prop 변경을 반영하지 않아 좌표를 되돌릴 수 있었다 (2026-08-21, 해결)

- **증상**: 중간 검증에서 캔버스 드래그로 오브젝트를 옮겼는데 PropertiesPanel의 `x`·`z` 입력값이 `0`에 멈춰 있었다. 저장 JSON은 `x: 1.5, z: -1.5`로 정상인데 화면 숫자만 `0`이라, 사용자가 실제와 다른 값을 보게 된다.
- **원인**: `useState(String(object.position.x))`로 로컬 문자열 상태를 두고 `useEffect` 동기화를 넣지 않았다. `useState` 초기화 인자는 재평가되지 않고 `StudioPage`가 `key`도 주지 않아 같은 인스턴스가 재사용되므로, 드래그·다른 오브젝트 선택 어느 쪽도 반영되지 않았다. **표시 오류에 그치지 않는다** — 그 상태에서 다른 칸을 blur하면 `commitPosition(옛 xText, 새 zText)`가 나가 방금 드래그한 좌표를 되돌리고, 다른 오브젝트를 선택한 뒤 blur하면 새 오브젝트가 이전 오브젝트 좌표로 순간이동한다.
- **해결**: `object.objectId`·`position.x`·`position.z`·`configId`를 의존성으로 하는 `useEffect` 두 개로 외부 변경을 되맞췄다. 브라우저 실측으로 드래그 후 SVG `translate(1.5 -0.75)`와 패널 `x=1.5·z=0.75` 일치, 다른 오브젝트 선택 시 `x=-2·z=2.25` 갱신 확인(커밋 `7b463a1`). 같은 함수에 있던 `configId` Int32 검증 부재(계약 §1 위반 — 0·음수·소수 통과)도 함께 고쳤다.
- **예방**: **로컬 `useState`로 prop을 미러링할 때는 그 prop이 외부에서 바뀔 수 있는지 먼저 따진다.** 이 패널은 "입력 중 빈 문자열 허용"을 위해 로컬 상태가 필요했지만, 같은 값이 캔버스 드래그로도 바뀐다는 사실을 설계 시점에 놓쳤다. 브라우저 실측이 없었으면 `tsc`·lint 통과만으로 넘어갔을 결함이다 — 상태를 가진 UI는 타입 검증으로 잡히지 않는다.

### T-7. Issue #5 서명 가이드 초안이 develop 직접 push를 안내할 뻔함 (2026-08-20, 자체 발견·해결)

- **증상**: 서명 방식이 "front로 전환해 서명"에서 "develop에 작은 PR"로 바뀌어 Issue #5 안내를 정정하는 코멘트 초안을 작성했는데, 절차에 `git push origin develop`을 넣었다 — `docs/17` §2 "develop: MR을 통해 Merge"를 정면으로 어기는 안내였다. 게시 직전 자체 검토로 발견해 PR 방식(`git switch -c` + `gh pr create --base develop`)으로 고쳐서 게시했다.
- **원인**: "develop에 직접"이라는 표현을 "PR로 develop을 대상"이 아니라 "develop 브랜치에 바로 push"로 잘못 치환했다. 직전에 같은 종류의 실수(§4 커밋 타입·브랜치명·PR 제목 컨벤션 위반)를 PR #3 사례에서 검토해놓고도, 서명 가이드를 짤 때는 그 검토를 다시 적용하지 않았다.
- **해결**: 초안을 게시 전에 다시 훑어 `docs/17` §2와 대조하고 절차를 PR 기반으로 교체했다.
- **예방**: 브랜치 운영 규칙을 다루는 안내문(가이드·코멘트)을 쓸 때는 게시 직전에 `docs/17`(또는 해당 컨벤션 문서) 대조를 **매번** 다시 한다 — 같은 세션에서 이미 검토한 규칙이라도 새 안내를 쓸 때 자동으로 지켜지지 않는다.

### T-6. 이슈 종결 가능 여부를 이슈 본문 확인 없이 판정 (2026-08-20, 해결)

- **증상**: Issue #2([front] Overlay·Unity 브릿지 계약 리뷰 요청)의 종결 가능 여부를 물었을 때 "FE `events.ts` 타입 추가와 Unity 구현이 미착수라 닫을 수 없다"고 보고했다. 사용자가 "해당 이슈는 계약 확인이지 구현까지 포함하지 않는다"고 지적해 다시 확인하니 이슈 본문의 요청은 "확인 요청" 2건뿐이었고 구현은 범위 밖이었다. 판정을 뒤집고 종결했다.
- **원인**: 이슈 본문을 읽지 않고 코멘트 스레드 내용만으로 판정했다. 스레드 후반에 구현 계획이 오갔다는 이유로 그것을 완료 조건에 포함시켰으나, 그 구현은 확인 결과로 파생된 별개 작업이었다. 종결 조건은 이슈를 연 사람이 본문에 적어둔 것인데 그 원문을 확인하지 않았다.
- **해결**: `gh issue view --json title,body`로 본문을 읽어 요청 항목이 "확인 요청" 2건임을 확인하고 판정을 정정했다. 종결 코멘트에 후속 구현이 이 이슈에 묶여 있던 것이 아님을 명시해 추적이 끊기지 않게 했다. 같은 방식으로 Issue #5는 본문 체크리스트 2건 중 "문서 기입"이 미완이라 종결 불가로 판정했다 — 본문을 읽었기 때문에 두 이슈의 차이를 구분할 수 있었다.
- **예방**: 이슈 종결 가능 여부를 판정할 때는 **코멘트 스레드보다 이슈 본문의 요청·체크리스트를 먼저 읽는다.** 스레드에서 파생된 후속 작업과 이슈 본문이 정의한 완료 조건은 별개다. T-4(값의 생성 지점만 보고 소비 지점을 안 봄)와 같은 형태의 실수 — 근거의 원본을 건너뛰고 중간 정보로 판단했다.

### T-5. 왕복 검증 실행 절차가 3곳에서 막힘 — FE가 작성한 절차의 환경 전제 누락 (2026-08-20, 해결)

- **증상**: FE가 `docs/LJH/verify/block1-roundtrip.md`에 적어 Issue #6으로 넘긴 실행 절차를 Unity 담당이 그대로 따르자 세 곳에서 막혔다. ⑴ 엔드포인트를 복수형으로 고친 뒤라 Unity는 `/layouts/published`를 호출하는데 mock 파일은 여전히 단수 경로(`layout/published`)에 있어 404 ⑵ 씬의 `BoothSlot_7`이 `activeSelf=false`라 재생해도 `Start()`가 돌지 않아 아무 오브젝트도 생성되지 않음 ⑶ 절차에 적은 `python -m http.server`가 해당 환경에서 실행되지 않음(Windows Store 별칭 가로챔).

### T-4. 코드 경로를 끝까지 추적하지 않고 버그 증상을 단정해 이슈에 발행 (2026-08-18, 해결)

- **증상**: spec 005 왕복 검증 준비 중 Unity `BoothLayoutDto`의 식별자 필드가 계약(`objectId`)과 달리 `id`인 것을 발견하고, 그 영향을 "`BOOTH_LAPTOP_INTERACT`의 objectId가 항상 빈 값으로 전송된다"고 단정해 Issue #6 본문에 실었다. 사용자 승인도 받지 않고 발행했다. 이후 Codex 독립 검증에서 이 서술이 REFUTED로 뒤집혔다 — 실제로는 `BoothInteractBridge.cs:18-26`의 `string.IsNullOrEmpty(objectId)` 가드에 걸려 **이벤트 자체가 전송되지 않는다**. 증상은 "빈 값 전송"이 아니라 "노트북 클릭 무반응"이었다.
- **원인**: DTO 필드명 불일치라는 근인만 확인하고 그 값이 소비되는 지점까지 추적하지 않았다. `dto.id → BoothRuntimeObject.ObjectId → LaptopInteractable → BoothInteractBridge` 체인의 마지막 단계에 조기 반환 가드가 있는데 이를 읽지 않고 "빈 값이 그대로 흘러간다"고 넘겨짚었다. 발행 전 검토 요청도 하지 않아 오류가 외부에 그대로 나갔다.
- **해결**: Codex 검증 결과를 근거로 Issue #6에 정정 댓글을 게시했다(사용자 승인 후). Unity 리드가 동일 체인으로 재현을 확인하고 수정 방향(DTO 정식 필드를 `objectId`로 변경, 구 `id`는 하위 호환 보정값)을 회신했다. 로컬 기록 3곳(`backlog.md`·`24_작업일지.md`·`verify/block1-roundtrip.md`)의 틀린 서술도 함께 정정했다.
- **예방**: 버그 증상을 서술할 때는 값의 **생성 지점이 아니라 소비 지점까지** 코드를 읽는다 — 중간의 가드·조기 반환·기본값 처리가 증상을 바꾼다. 타 파트에 나가는 이슈·댓글·PR 본문은 발행 전 사용자 검토를 받는다. 코드 근거가 있는 주장은 발행 전에 독립 검증(Codex 등)을 한 번 태운다.

### T-3. GitHub API 일시 장애로 협업자 조회 실패 (2026-08-17, 해결)

- **증상**: Issue 담당자를 지정하기 전 `gh api repos/<owner>/<repo>/collaborators`가 `HTTP 503 No server is currently available to service your request`로 두 차례 연속 실패했다.
- **원인**: 로컬 인증이나 권한 문제가 아니라 GitHub API 측 일시 장애였다. 같은 시점에 `git fetch`(git 프로토콜)와 `gh issue create`는 정상 동작해 전면 장애가 아님을 확인했다.
- **해결**: 협업자 목록은 같은 세션에서 앞서 조회해 둔 값을 사용하고, Issue 생성·담당자 지정·라벨 부착을 재시도해 모두 성공했다.
- **예방**: `gh` 명령이 503으로 실패하면 인증·권한을 의심하기 전에 다른 엔드포인트와 git 프로토콜로 범위를 먼저 가른다. 조회가 막혀도 이미 확인된 값이 있으면 작업을 중단하지 않는다.
### T-2. 다항목 Codex 검증 프롬프트가 응답 없이 타임아웃 (2026-08-17, 우회)
