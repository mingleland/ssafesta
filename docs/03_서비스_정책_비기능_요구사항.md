# SSAFY FESTA 서비스 정책 / 비기능 요구사항

> **문서 목적**: 서비스 전반에 공통 적용되는 운영 정책, 데이터 원칙, 보안·성능·신뢰성 요구사항을 정의한다.  
> 수치가 기존 기획에서 확정되지 않은 항목은 `TBD`로 둔다.

---

## 1. 정책 원칙

1. 영구 서비스 데이터의 Source of Truth는 Spring/PostgreSQL을 기본으로 한다.
2. AI 문서 검색은 `boothId`, `agentId`를 기준으로 격리한다.
3. 실시간 월드 상태와 영구 Booth 콘텐츠를 분리한다.
4. Coin은 잔액만 수정하지 않고 거래 원장으로 추적한다.
5. 중복 요청이 금전·재고·임대 상태를 이중 반영하지 않도록 한다.
6. P0/P1 기능 안정성을 P2 기능보다 우선한다.

---

## 2. 계정 정책

### 2.1 인증

- 보호된 서비스 기능은 로그인 사용자를 기준으로 한다.
- Spring Boot가 사용자 인증 및 JWT 발급의 기준 시스템이 된다.
- React / Unity / FastAPI가 동일 사용자의 권한을 임의로 확장하지 않는다.
- JWT 저장 방식과 Refresh Token 정책은 Backend 보안 설계에서 확정한다.

### 2.2 회원 탈퇴

회원 탈퇴는 **확정 즉시 관련 데이터 전체 hard delete** 정책이다. 상태는 `ACTIVE` / `SUSPENDED`만 사용한다.

- 요청 즉시 모든 토큰·Unity 세션 종료, 프로필·Booth Publish·공개 콘텐츠 비노출 후 삭제 Workflow를 시작한다.
- 탈퇴 취소와 대기 상태는 제공하지 않는다.
- User를 마지막으로 hard delete한다. User와 직접 연결된 소유·참여 데이터, Wallet·Coin Ledger, 파일, AI Document·Vector, OAuth 연결과 외부 provider revoke/unlink를 포함한다.
- 다른 사용자가 탈퇴자의 콘텐츠에 참여한 데이터와 탈퇴자가 타인 콘텐츠에 참여한 데이터도 모두 삭제한다. 익명화 보존은 하지 않는다.
- 삭제 Job은 DB·Redis·파일 저장소·Vector·OAuth의 부분 실패를 재실행할 수 있게 idempotent하게 설계한다.

## 4. 부스 정책

### 4.1 기본 슬롯

| 구분 | 수량 |
|---|---:|
| 관리자 상시 부스 | 3 |
| 사용자 임대 부스 | 7 |
| 경쟁관 | 1 |
| 이벤트 부스 | 1 |

### 4.2 임대

- 사용자 임대 부스만 일반 임대 대상이다.
- 기본 기획값은 `1일 100 Coin`이다.
- 이미 임대 중인 슬롯을 동시에 여러 사용자가 획득할 수 없어야 한다.
- 임대 생성과 Coin 차감은 논리적으로 하나의 거래로 처리해야 한다.

### 4.3 임대 종료 후 보존

임대가 종료돼도 다음 데이터는 유지한다.

- Booth Layout
- Inventory / 구매 장식
- AI Agent
- AI Document 메타데이터 및 정책상 보존 대상
- Survey
- Project 정보

월드에서의 물리적 Booth 점유와 사용자의 콘텐츠 소유는 분리한다.

임대 만료 처리 순서는 다음과 같다.

1. Lease를 만료 처리하고 해당 Booth와 물리 Slot의 연결을 해제한다.
2. 신규 입장을 차단한다.
3. 내부 방문자에게 만료를 알리고 외부 복귀 지점으로 이동시킨다.
4. 각 Unity Client는 내부 Runtime Object를 제거한다.
5. 외부 슬롯은 기본 건물과 `임대 가능` 간판만 남긴다.
6. 기존 소유자의 Published Layout은 슬롯에서 비공개 처리하고 편집 가능한 Draft 데이터로 보존한다.

새 임차인에게 이전 소유자의 Layout이나 Facade를 승계하지 않는다. 새 임차인은 빈 템플릿에서 시작하며, 이전 소유자는 나중에 다른 슬롯을 임대했을 때 보존된 콘텐츠를 다시 편집·공개할 수 있다.

### 4.4 Published Booth

- 일반 방문자에게는 Published Layout만 제공한다.
- Draft는 Owner/허용된 Editor만 조회한다.
- 운영자가 오프라인이어도 활성 Lease가 유지되는 동안 Published Booth는 표시된다.
- 활성 Lease가 없는 Booth의 Published Layout은 외부 슬롯이나 일반 방문자에게 노출하지 않는다.

### 4.5 내부 공유·예약 정책

- 일반 Booth 내부는 여러 방문자가 동시에 이용하는 공유 공간이다.
- 한 사용자가 일반 Booth 전체를 독점하는 예약 기능은 P0에서 제외한다.
- 사람 상담, 비공개 면접, 예약 행사처럼 실제 독점이 필요한 기능만 별도의 예약/세션 단위로 설계한다.
- Owner와 Staff의 동시 편집 충돌 처리는 방문 예약과 분리하며 Layout version 또는 편집 잠금으로 해결한다.

## 5. 코인 경제 정책

### 5.1 기본 기획값

| 항목 | 값 |
|---|---:|
| 신규 가입 | +200 |
| 일일 지급 | +50 |
| 부스 1일 임대 | -100 |
| AI 서비스 이용 | 10~50 후보 |
| 설문 참여 보상 | +5~10 후보 |
| 장식 구매 | 20~300 후보 |
| 관리자 게임 | 일일 최대 약 +50 후보 |

후보 값은 밸런스 테스트 후 변경할 수 있다.

### 5.2 Ledger 원칙

모든 코인 변동은 최소 다음 정보를 추적한다.

```text
userId
amount
balanceAfter
type
referenceId
idempotencyKey
createdAt
```

### 5.3 중복 처리

다음 요청에는 중복 방지 키 또는 동등한 서버 측 보호가 필요하다.

- Booth 임대
- 일일 지급
- AI 서비스 결제
- Survey 보상
- Minigame 보상
- 아이템 구매
- 이벤트 교환

## 6. AI 서비스 정책

### 6.1 MVP 방식

```text
Base LLM + System Prompt + RAG
```

Fine-tuning은 MVP 필수 범위가 아니다.

### 6.2 데이터 격리

Vector Search에서 최소 다음 조건을 강제한다.

```text
boothId == currentBooth
agentId == currentAgent 또는 명시된 공유 Scope
documentStatus == ACTIVE/READY
```

다른 Booth의 문서는 절대 검색 결과에 포함되면 안 된다.

### 6.3 결제 책임

- FastAPI가 Coin Balance를 직접 수정하지 않는다.
- 사용 가능 여부와 결제는 Spring이 책임진다.
- AI 호출 실패 시 환불 정책은 `TBD`이며 Backend 계약 확정 전 임의 구현하지 않는다.

### 6.4 대화 기록

다음은 구현 전 확정이 필요하다.

- 원문 대화 저장 여부
- 저장 기간
- 운영자가 열람할 수 있는 범위
- 로그 마스킹 기준
- 삭제 요청 처리

## 7. 사람 상담 정책

### 7.1 Presence

```text
AVAILABLE / BUSY / AWAY / OFFLINE
```

### 7.2 상담 전환

- 사용자가 직접 사람 상담을 요청하는 흐름을 우선 구현한다.

## 10. 비기능 요구사항 — 성능

### NFR-PERF-01 World 수용 목표

- 한 World Channel 운영 목표: 30~40명
- 부하 테스트: 최대 50명 수준
- Booth Instance 확장 목표: 8~12명

이는 성능 보장치가 아니라 현재 개발 목표다.

### NFR-PERF-02 정적 Booth Object

소파·책상·화분·벽·바닥·정적 간판 등은 기본적으로 NetworkObject로 동기화하지 않는다.

```text
Spring Layout JSON → Unity Client → Local Prefab Spawn
```

### NFR-PERF-03 Web 최적화

- Unity Web 빌드 크기와 초기 로딩을 측정한다.
- Avatar, Animator, SkinnedMesh 비용을 프로파일링한다.
- 필요 시 거리/Zone 기반 Visibility 또는 저빈도 Sync를 P2로 적용한다.

---

## 11. 비기능 요구사항 — 신뢰성 / 장애 격리

### NFR-REL-01 AI 장애 격리

AI 서버 장애가 Unity World 접속 자체를 막아서는 안 된다.

### NFR-REL-02 부분 실패

하나의 Booth Object 로딩 실패로 전체 Booth가 사라지지 않도록 개별 Object 단위로 예외를 격리한다.

### NFR-REL-03 재시도

재시도 가능한 요청과 재시도하면 위험한 요청을 구분한다.

- 조회: 재시도 가능
- 결제·임대·보상: idempotency 보장 후 재시도
- Publish: 버전 기반 충돌 검토

## 12. 비기능 요구사항 — 보안

### NFR-SEC-01 인증 / 인가

- 모든 보호 API는 인증을 검증한다.
- boothId, agentId를 클라이언트가 전달해도 접근 권한을 서버에서 검증한다.
- Admin API는 별도 관리자 권한이 필요하다.

### NFR-SEC-02 파일 업로드

지원 확장자·최대 크기는 `TBD`다. 최소한 다음을 적용한다.

- 허용 확장자 검증
- MIME 검증
- 임의 실행 파일 차단
- S3 Key를 사용자 입력 그대로 사용하지 않음

### NFR-SEC-03 비밀정보

JWT Secret, DB 비밀번호, LLM API Key, AWS Credential은 저장소에 커밋하지 않는다.

### NFR-SEC-04 로그

Access Token, 비밀번호, API Key를 로그에 기록하지 않는다.

## 13. 비기능 요구사항 — 데이터 일관성

### NFR-DATA-01 Source of Truth

| 데이터 | 기준 시스템 |
|---|---|
| 사용자 / 권한 | Spring + PostgreSQL |
| Booth / Lease / Layout | Spring + PostgreSQL |
| Coin / Inventory | Spring + PostgreSQL |
| Survey / Event / Vote | Spring + PostgreSQL |
| Staff Presence / Channel / Session | Redis 중심의 실시간 상태 |
| AI Chunk / Embedding | AI 시스템의 pgvector 저장소 |
| 정적 파일 | S3 |
| Player 실시간 Transform | Unity Dedicated Server |

### NFR-DATA-02 버전

Published Layout은 버전 식별이 가능해야 한다.

## 14. 비기능 요구사항 — 관측성

최소 추적 항목:

- requestId / trace 식별자
- HTTP status / API latency
- AI: conversationId, boothId, agentId, RAG/LLM latency, token usage
- Unity Server: instanceId, channelId, connected players, disconnect reason
- Coin: transaction id / idempotency key
- 오류 코드

CloudWatch 등 실제 수집 도구는 Infra 문서에서 정의한다.

---

## 15. 비기능 요구사항 — UX / 접근성

- 색상만으로 상태를 구분하지 않는다.
- Loading / Empty / Error 상태를 모든 주요 화면에 제공한다.
- Booth Studio 정밀 편집은 PC를 기준으로 한다.
- 모바일은 탐색·AI·영상·설문 등 핵심 이용 기능을 우선 검토한다.
- Unity HUD가 World View를 과도하게 가리지 않도록 한다.
