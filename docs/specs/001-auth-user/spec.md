## User Scenarios & Testing

### User Story 1 — 가입하고 로그인한다 (Priority: P0)

SSAFY 구성원이 계정을 만들고 로그인해 보호된 기능(부스 임대, 스튜디오, 월드 입장)을 사용한다.

**Why this priority**: 이것이 안 되면 다른 모든 spec이 착수 불가다.

**Independent Test**: 신규 계정 생성 → 로그아웃 → 같은 자격으로 재로그인 → 내 정보 조회 성공.

**Acceptance Scenarios**:

1. **Given** 가입하지 않은 사용자, **When** 유효한 자격 정보로 가입하면, **Then** 계정이 생성되고 정책상 초기 코인이 지급된다.
2. **Given** 가입한 사용자, **When** 올바른 자격으로 로그인하면, **Then** 보호된 API를 호출할 수 있다.
3. **Given** 가입한 사용자, **When** 잘못된 비밀번호로 로그인하면, **Then** 실패 사유가 계정 존재 여부를 노출하지 않는 형태로 반환된다.
4. **Given** 로그인한 사용자, **When** 내 정보를 조회하면, **Then** 닉네임·코인 잔액·내 부스 상태·아바타 코드를 확인할 수 있다.

### User Story 2 — 월드에 안전하게 입장한다 (Priority: P0)

로그인한 사용자가 Unity 월드에 접속할 때, 게임 서버에는 **재사용 불가능한 짧은 수명의 토큰만** 전달된다.

**Why this priority**: 토큰 구조는 002(world-session)·016 등 여러 spec의 전제이며, 나중에 바꾸면 전 파트가 영향받는다.

**Independent Test**: 월드 입장용 토큰을 발급받아 1회 사용 → 같은 토큰 재사용 시 거부되는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 월드 입장을 요청하면, **Then** 짧은 수명의 1회용 접속 토큰이 발급된다.
2. **Given** 발급된 접속 토큰, **When** 이미 한 번 사용되었다면, **Then** 재사용이 거부된다.
3. **Given** 발급된 접속 토큰, **When** 유효 시간이 지났다면, **Then** 접속이 거부된다.
4. **Given** 어떤 경우에도, **When** Unity 클라이언트나 게임 서버를 조사해도, **Then** 갱신 토큰(Refresh)은 발견되지 않는다.

### User Story 3 — 로그아웃 / 탈퇴 (Priority: P1)

**Acceptance Scenarios**:

1. **Given** 로그인 상태, **When** 로그아웃하면, **Then** 기존 인증 수단으로 보호 API를 호출할 수 없다.
2. **Given** 로그인 상태, **When** 탈퇴하면, **Then** 개인 식별 정보는 정책상 기간 뒤 제거되고 부스·설문 등 타인이 참조하는 데이터는 무결성이 유지된다.

### Edge Cases

- 동일 이메일로 동시에 두 번 가입 요청이 들어오는 경우
- 접속 토큰 발급 직후 사용자가 정지·탈퇴된 경우 → 게임 서버가 승인해서는 안 된다
- 여러 브라우저 탭에서 동시에 월드 접속을 시도하는 경우 [NEEDS CLARIFICATION: 동일 계정 중복 접속 허용 여부]
- 인증 서버 장애 시 이미 월드에 접속해 있는 사용자의 처리

## Requirements

### Functional Requirements

- **FR-001**: 시스템은 이메일과 비밀번호로 계정을 생성할 수 있어야 한다.
- **FR-002**: 시스템은 비밀번호를 복원 불가능한 형태로 저장해야 한다.
- **FR-003**: 시스템은 로그인 성공 시 보호된 기능 호출에 사용할 인증 수단을 제공해야 한다.
- **FR-004**: 시스템은 인증 수단을 **4계층으로 분리**해야 한다 — 갱신용 / API 호출용 / **월드 접속용** / 실시간 상담용.
- **FR-005**: 시스템은 갱신용 토큰을 Unity 클라이언트와 게임 서버에 **전달해서는 안 된다** (헌법 10조).
- **FR-006**: 월드 접속용 토큰은 **1회용**이며 짧은 수명을 가져야 한다.
- **FR-007**: 게임 서버는 접속 승인 시 이 토큰의 유효성과 사용자 신원을 확인할 수 있어야 한다.
- **FR-008**: 시스템은 클라이언트가 보낸 사용자 식별자·닉네임을 검증 없이 신뢰해서는 안 된다 (헌법 12조).
- **FR-009**: 시스템은 내 정보(닉네임, 코인 잔액, 부스 상태, 아바타 코드)를 조회하는 수단을 제공해야 한다.
- **FR-010**: 로그인 실패 응답은 계정 존재 여부를 구분할 수 있게 노출해서는 안 된다.
- **FR-011**: 시스템은 로그아웃 시 해당 세션의 인증 수단을 무효화해야 한다.
- **FR-012**: 신규 계정 생성 시 정책상 초기 코인이 지급되어야 한다 (spec 003과 계약 공유).

### Key Entities

- **User**: 사용자 계정. 식별자, 이메일, 비밀번호 해시, 닉네임, 아바타 코드, 가입 시각, 상태(활성/정지/탈퇴)
- **Session / Token**: 인증 수단. 종류, 소유자, 발급 시각, 만료 시각, 사용 여부(1회용의 경우)

## Success Criteria

- **SC-001**: 신규 사용자가 가입부터 첫 로그인까지 1분 이내에 완료할 수 있다.
- **SC-002**: 발급된 월드 접속 토큰을 두 번째로 사용하면 100% 거부된다.
- **SC-003**: Unity 빌드 산출물과 게임 서버 로그·메모리 어디에서도 갱신 토큰이 발견되지 않는다.
- **SC-004**: 만료된 접속 토큰으로 월드에 진입한 사례가 0건이다.
- **SC-005**: 인증이 필요한 모든 API가 미인증 요청을 100% 차단한다.

## 부록 — 기존 구현과의 접점 (참고용, 요구사항 아님)

Unity 측에는 이미 다음 경계가 준비되어 있다. BE 구현 시 이 형태를 참고하면 연동 비용이 낮다.

- `IAccessTokenProvider` — 토큰 주입 경계 (현재 Empty/Mock 구현)
- `WorldSessionDto { sessionId, worldId, channelId, endpoint{scheme,host,port}, connectionToken, expiresAt }`
- `UserProfileDto { userId, nickname, avatarCode }`
- Unity의 Connection Approval은 접속 시 `connectionToken`을 payload로 받아 서버에서 검증하는 구조로 동작 중 (POC 검증 완료)
