## User Scenarios & Testing

### User Story 1 — 내 캐릭터를 꾸미고, 남들이 바로 본다 (Priority: P0) [Unity 구현됨]

사용자가 캐릭터의 머리·머리카락·상의·하의 등을 파츠 단위로 바꾸면, 같은 월드에 있는 다른 사용자 화면에서 **즉시** 그 모습이 보인다.

**Why this priority**: 팀이 필수로 지정. 메타버스에서 "나"의 정체성이며, 접속 유지 동기의 핵심.

**Independent Test**: 브라우저 2개 접속 → A가 파츠를 바꿈 → B 화면에서 A의 모습이 바뀌는지 확인 (새로고침 없이).

**Acceptance Scenarios**:

1. **Given** 월드에 접속한 사용자, **When** 커스터마이징 창을 열면, **Then** 파츠 종류별로 선택 가능한 항목들이 보인다.
2. **Given** 커스터마이징 창, **When** 특정 파츠를 다른 것으로 바꾸면, **Then** 내 캐릭터가 즉시 바뀐다.
3. **Given** A가 파츠를 바꿈, **When** 같은 월드의 B가 A를 보면, **Then** **별도 조작 없이** 바뀐 모습이 보인다.
4. **Given** 커스터마이징 창, **When** 색상을 선택하면, **Then** 캐릭터 색상이 즉시 바뀌고 전원에게 전파된다.
5. **Given** 저장 외형이 없는 최초 사용자, **When** 커스터마이징 창을 열면, **Then** 자연스러운 피부·머리·의상 테마의 추천 무작위 캐릭터가 상의 탭과 함께 표시된다.
6. **Given** 저장된 모듈형 외형이 있는 사용자, **When** 커스터마이징 창을 다시 열면, **Then** 새 무작위가 아니라 본인의 마지막 외형이 복원된다.
7. **Given** 커스터마이징 창, **When** 무작위 버튼을 누르면, **Then** 과도한 색·액세서리 조합 없이 조화된 전체 파츠가 새로 조합된다.
8. **Given** Rukha93 모듈 아바타, **When** 얼굴·의상 조합을 변경하면, **Then** 홍채와 얼굴 텍스처가 유지되고 목 분리·중복 얼굴·피부 관통이 보이지 않는다.
9. **Given** 같은 월드의 A와 B, **When** A가 Rukha93 외형을 게임 중 변경하면, **Then** A와 B 화면 모두 같은 외형으로 1초 이내 갱신된다.

### User Story 2 — 다음에 들어와도 그 모습이다 (Priority: P0) [신규 — BE]

**Independent Test**: 외형 변경 → 브라우저 완전 종료 → 재접속 → 같은 외형인지 확인.

**Acceptance Scenarios**:

1. **Given** 외형을 변경한 사용자, **When** 월드를 나갔다가 다시 들어오면, **Then** 마지막 외형이 그대로 복원된다.
2. **Given** 저장이 실패한 경우, **When** 사용자가 계속 플레이하면, **Then** **이번 세션에서는 변경된 외형이 유지**되고 월드 이용이 중단되지 않는다.
3. **Given** 저장된 외형 값이 이 클라이언트가 모르는 형식인 경우, **When** 접속하면, **Then** 기본 외형으로 대체되고 오류로 중단되지 않는다.

### User Story 3 — 정식 Unity 커스터마이징 화면 (Priority: P0) [Unity 구현됨]

Unity `CharacterLobby` 화면에서 캐릭터를 계속 보면서 파츠·색상·무작위를 조작한다.

**Why this priority**: 파츠 썸네일, 아이템별 색상 영역, 자연스러운 무작위, 드래그 가능한 색상 팝업까지 Unity에서 완성·검증됐으므로 동일 기능을 React로 중복 구현하지 않는다. AI 채팅·상담처럼 장문 입력이 필요한 화면만 기존 React 오버레이 원칙을 유지한다.

**Acceptance Scenarios**:

1. **Given** 커스터마이징 진입, **When** 정식 화면이 열리면, **Then** Unity 좌·우 패널 사이에 내 캐릭터가 보인다.
2. **Given** 창에서 파츠를 고르면, **When** 선택 즉시, **Then** 뒤의 캐릭터가 바뀐다 (별도 미리보기 3D 불필요).
3. **Given** 창에서 외형을 확정하면, **When** Spring 저장 요청이 끝나면, **Then** 저장 결과(성공/실패)가 Unity UI에 표시되고 실패해도 현재 세션 외형은 유지된다.

### Edge Cases

- 외형 데이터가 매우 길어지는 경우 → **실제로 터진 적 있음 (T-24)**. 길이 상한과 초과 시 동작이 명세되어야 한다
- 파츠 데이터 로딩이 끝나기 전에 사용자가 접속한 경우 → 준비되면 자동 반영되어야 한다
- 좌우 짝이 있는 파츠(팔·다리)에서 한쪽만 바뀌는 경우 → 자동으로 짝이 맞아야 한다
- 다른 사용자가 조작된 외형 값을 보내는 경우 → 서버가 검증해야 한다
- 30~40명이 각자 다른 외형인 경우 → 렌더링 비용

## Requirements

### Functional Requirements

- **FR-001** [구현됨]: 사용자는 파츠 종류별로 외형을 선택할 수 있어야 한다.
- **FR-002** [구현됨]: 사용자는 색상을 선택할 수 있어야 한다.
- **FR-003** [구현됨]: 외형 변경은 **같은 월드의 모든 사용자에게 즉시** 반영되어야 한다.
- **FR-004** [구현됨]: 외형은 **문자열 하나로 표현**되어 동기화되며, 3D 데이터가 네트워크로 오가서는 안 된다 (헌법 5조).
- **FR-005** [구현됨]: 외형 3D 표현은 각 클라이언트가 로컬 생성하며 네트워크 오브젝트가 아니어야 한다.
- **FR-006** [구현됨]: 좌우 대칭 파츠는 한쪽 변경 시 반대쪽이 자동으로 맞춰져야 한다.
- **FR-007**: 외형 문자열은 **길이 상한**을 가지며, 초과 시 **사용자에게 명확히 거부 사유가 표시**되어야 한다. *조용히 기본값으로 대체해서는 안 된다 (T-24의 교훈).*
- **FR-008** [구현됨]: 알 수 없는 외형 세그먼트는 무시하고 나머지를 적용해야 한다 (구버전 클라이언트 호환).
- **FR-009** [신규]: 시스템은 사용자의 외형을 **영구 저장**하고 재접속 시 복원해야 한다.
- **FR-010** [신규]: 저장 실패가 월드 이용을 중단시켜서는 안 된다.
- **FR-011** [신규]: 서버는 클라이언트가 보낸 외형 값의 형식과 길이를 검증해야 한다 (헌법 12조).
- **FR-012** [확정·구현됨]: 정식 커스터마이징 화면은 Unity `CharacterLobby`가 제공한다. React는 동일 화면을 재구현하지 않으며, 외부 호스트 연동이 필요할 때만 `AvatarBridge`를 선택적으로 사용한다.
- **FR-013**: 변경 요청이 서버에 반영되지 않으면 사용자에게 알려야 한다. *(T-24 후속으로 구현됨)*
- **FR-014**: 로비와 멀티플레이 월드는 동일한 Rukha93 `AvatarConfig`와 Catalog를 사용해야 하며 Sidekick 런타임에 의존하지 않아야 한다.
- **FR-015**: 눈·입·눈썹 등 얼굴 디테일 텍스처와 노멀맵을 유지해야 한다.
- **FR-016**: 의상 ItemDefinition의 숨김 신체 부위를 적용해 피부가 의상 표면을 뚫고 보이지 않아야 한다.
- **FR-017**: 주요 탭과 선택 버튼은 1920×1080 기준 최소 높이 44px, 권장 48px 이상이며 스크롤 가능한 2열 선택 영역을 제공해야 한다.
- **FR-018**: UI는 한국어를 기본으로 하고 캐릭터가 중심이 되는 어두운 반투명 패널, 따뜻한 키라이트와 차가운 림라이트를 사용한다.
- **FR-019**: 색상은 고정 팔레트뿐 아니라 Hue와 채도·명도를 마우스로 연속 조절할 수 있어야 하며, 정밀 RGB 값이 네트워크 외형 문자열에 포함되어야 한다.
- **FR-020**: 선택 파츠 생성에 실패한 경우 신체 숨김부터 적용해 머리나 목만 떠 보이게 해서는 안 된다. 기본 신체는 유효한 대체 메시가 생성된 뒤에만 숨긴다.
- **FR-021**: 얼굴 색상은 피부·흰자위·홍채·동공·눈썹·입술을 각각 독립적으로 조절하고 네트워크 외형 문자열에 저장해야 한다. 입술색은 원본 얼굴 명암을 보존하도록 피부색과 혼합한 자연스러운 색조로 적용해야 한다.
- **FR-022**: 파츠·색상·확정 버튼 등 UI 위에서 포인터를 조작하는 동안 캐릭터 회전, 카메라 회전, 카메라 줌이 발생해서는 안 된다.
- **FR-023**: 눈·입술 형태가 얼굴형 메시 안에 포함된 경우 이를 독립 파츠 탭으로 표현해서는 안 되며, 얼굴형 선택 목록 아래에는 피부·흰자위·홍채·동공·눈썹·입술 색상 이름과 현재 색상을 명확히 표시해야 한다.
- **FR-024**: 마우스 휠 줌은 화면 중앙이 아니라 현재 포인터가 가리키는 미리보기 지점을 초점으로 확대·축소해야 하며, UI 위에서는 FR-022에 따라 줌을 차단해야 한다.
- **FR-025**: 피부색 변경은 얼굴뿐 아니라 목·몸통·팔·손·다리·발의 모든 노출 피부에 동시에 적용되어야 하며, 얼굴과 신체가 동일한 조명 계산을 사용해 경계선이 생기지 않아야 한다.
- **FR-026**: 상의·하의·한벌옷·신발은 왼쪽 의상 패널 안에서 큰 이미지 탭으로 전환해야 한다. 사용자 UI에는 RGB 마스크 A/B/C의 내부 채널명을 노출하지 않고, FR-031·FR-032에 따라 현재 아이템에서 실제로 보이는 부위만 하나의 색상 컨트롤로 조절해야 한다.
- **FR-028**: 안경은 오른쪽 액세서리 탭에서 큰 2열 썸네일로 선택하며, 전·후면 렌더에서 확인된 프레임과 브리지·다리 등 실제로 보이는 부위만 색상 컨트롤로 제공해야 한다. 렌즈는 별도 투명 머티리얼을 유지하면서 두 번째 부위 색을 사용하며, `w=`에는 상의·하의·한벌옷·신발·모자·안경 순서의 기존 36색 포맷을 유지하고 기존 24색·30색 문자열도 읽어야 한다.
- **FR-027**: 상의·하의·한벌옷을 모두 해제해 기본 Body가 노출될 때 속옷은 원본 Body RGB 마스크의 전용 영역으로 표시하고 고정된 검정색을 사용해야 한다. 피부색 변경은 속옷 영역에 적용되어서는 안 된다.
- **FR-029**: WebGL 커스터마이징 UI는 1600×900 논리 해상도의 단일 16:9 기준 프레임을 사용해야 한다. 브라우저 창 비율이 바뀌어도 좌·중앙·우 패널, 선택 카드, 패딩과 스크롤 간격의 상대 배치가 유지되어야 하며, 기준 비율 밖의 영역은 UI를 비균등하게 늘리는 대신 안전 여백으로 처리해야 한다.
- **FR-030**: 캐릭터 회전·카메라 Orbit·Zoom 입력 가능 영역은 화면 폭에 대한 하드코딩 비율이 아니라 실제 중앙 미리보기 RectTransform 경계로 판정해야 한다.
- **FR-031**: 상의·하의·한벌옷·신발·모자·안경은 A/B/C나 어두운 톤·밝은 톤 같은 내부 슬롯을 사용자에게 노출하지 않고, 실제 변경 부위마다 하나의 색상 컨트롤만 제공해야 한다. 부위명은 카테고리 공통 문구가 아니라 현재 아이템에 맞춰 `서스펜더 반바지: 상의 원단/반바지 원단/멜빵·단추`, `카고 조거팬츠: 조거팬츠 원단/카고 포켓·허리선`처럼 구체적으로 표시하며, 사용자가 고른 한 색을 해당 RGB 마스크 부위의 내부 두 슬롯에 동일하게 기록해야 한다.
- **FR-032**: 색상 컨트롤의 개수는 카테고리 공통으로 고정하지 않고 아이템별로 결정해야 한다. 전·후면 렌더에서 강한 시험색을 적용했을 때 가장 잘 보이는 영역 대비 화면 변화가 5% 미만인 영역은 해당 아이템의 UI에서 숨기며, 상의·하의·한벌옷·신발·모자·안경 선택을 바꿀 때 즉시 다시 계산된 목록을 표시해야 한다.
- **FR-033**: 16:9 커스터마이징 UI의 좌·우 패널은 같은 상단 패딩과 수직 기준선을 사용해야 한다. 양쪽 모두 `제목 → 120px 탭 → 섹션 제목 → 2열 아이템 목록 → 하단 색상 영역` 순서를 유지하고, 탭 아이콘 설명은 아이콘 아래에 분리한다. 색상 영역은 필요한 행 높이만 하단에 고정해 남는 공간을 아이템 목록에 배정한다.
- **FR-034**: 카드·버튼·색상 행·팝업은 따뜻한 중성 계열의 둥근 표면, 한 종류의 선택 강조색, 일관된 저대비 외곽선을 사용해야 한다. 얼굴·의상·모자·안경 썸네일 배경은 같은 중성 회색을 사용하고, 어두운 헤어만 식별을 위한 밝은 중성 배경을 허용한다. 색상 행의 장식 이미지는 깨진 프레임으로 보이지 않는 단색 마커를 사용하며 색상칩은 고정 정사각형이어야 한다.
- **FR-035**: 색상 팝업은 화면을 과도하게 가리지 않는 컴팩트 모달이어야 하며, 실제 부위명, 색상환·밝기, 현재 색상, HEX 입력, 취소·완료만 표시한다. 전체 화면을 덮는 별도 스크림은 두지 않고 실제 팝업 Rect 안에서만 캐릭터 회전·카메라 입력을 차단하며, 사용자는 제목 영역을 드래그해 팝업을 옮길 수 있어야 한다. 동작 없이 개발 정보를 출력하던 `미리보기 설정`·`현재 외형 정보` 버튼은 사용자 UI에 표시하지 않는다.
- **FR-036**: 최초 커스터마이징 진입은 고정 기본 캐릭터가 아니라 자연스러운 추천 무작위 외형으로 시작해야 한다. 최초 추천은 상의·하의 조합을 사용해 기본 의상 탭을 `상의`로 유지하며, 저장된 `fa` 모듈형 외형이나 현재 로컬 플레이어 외형이 있으면 무작위보다 이를 우선 복원해야 한다. 무작위 버튼은 자연스러운 피부·머리·눈·입술 팔레트와 조화된 의상 테마를 사용하고, 모자와 안경을 동시에 강제하지 않아야 한다.
- **FR-037**: 왼쪽 의상 탭의 상의·하의·한벌옷·신발 아이콘은 원본 이미지의 카드 배경·장식 프레임을 포함하지 않는 투명 누끼여야 한다. 네 탭은 오른쪽 외형 탭과 비슷한 카드 간격을 유지하고 아이콘과 프레임 사이에 내부 여백을 두며, 라벨은 아이콘 프레임 아래에서 일정 간격 떨어져야 한다.

> 의상 영역 판정은 공통 임계값이나 RGB 가중 평균을 사용하지 않는다. 각 원본 머티리얼의 `_MaskRemap`과 `_Mask_Factor`를 보존하고, 원본 서브그래프와 동일하게 A 적용 후 B, C를 순차 선택한다. A1/A2·B1/B2·C1/C2는 네트워크 하위 호환을 위해 남아 있는 내부 슬롯이며, 현재 UI는 부위별 한 색을 각 쌍에 동일하게 기록한다.

### Key Entities

- **Avatar Appearance**: 한 사용자의 외형. 파츠 구성 또는 프리셋 코드, 색상
- **Part Catalog**: 선택 가능한 파츠 목록. 파츠 종류별 항목들

## 계약 — 외형 문자열 (3파트 공통)

> 현재 계약은 Rukha93 모듈형 `fa` 포맷을 기준으로 한다. 과거 `sk`/`rt` 값은 읽기 호환만 유지한다.

```
fa|g=1|i=<8개 파츠 ID>|p=<9개 팔레트 ID>|q=<9개 RGB>|w=<36개 영역 RGB>
```

| 규칙 | 값 |
|---|---|
| 구분자 | `\|`, 세그먼트는 `키=값` |
| 첫 세그먼트 `fa` | Rukha93 모듈 파츠 조립 모드 |
| 알 수 없는 세그먼트 | 무시 (forward compatible) |
| 최대 길이 | **3800자** (Unity `FixedString4096Bytes` 안전 범위) |
| 오류/빈 값 | 기본 외형으로 폴백 |

**BE에 필요한 것**: 사용자 외형 저장 필드(**VARCHAR(3800) 이상 또는 TEXT**)와 조회·저장 수단.

## Success Criteria

- **SC-001**: A가 파츠를 바꾸면 B 화면에 1초 이내에 반영된다.
- **SC-002**: 재접속 후 외형이 복원되는 비율이 100%다.
- **SC-003**: 저장 서버가 죽어 있어도 월드 이용과 외형 변경(세션 한정)이 계속된다.
- **SC-004**: 사용자가 안내 없이 창을 열어 외형을 바꾸고 저장까지 완료할 수 있다.
- **SC-005**: 외형 변경 요청이 무반응으로 끝나는 사례가 0건이다 (실패 시 반드시 사유 표시).
