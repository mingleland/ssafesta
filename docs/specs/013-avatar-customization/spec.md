## User Scenarios & Testing

### User Story 1 — 내 캐릭터를 꾸미고, 남들이 바로 본다 (Priority: P0) [Unity 구현됨]

사용자가 캐릭터의 머리·머리카락·상의·하의 등을 파츠 단위로 바꾸면, 같은 월드에 있는 다른 사용자 화면에서 **즉시** 그 모습이 보인다.

**Why this priority**: 팀이 필수로 지정. 메타버스에서 "나"의 정체성이며, 접속 유지 동기의 핵심.

**Independent Test**: 브라우저 2개 접속 → A가 파츠를 바꿈 → B 화면에서 A의 모습이 바뀌는지 확인 (새로고침 없이).

**Acceptance Scenarios**:

1. **Given** 월드에 접속한 사용자, **When** 커스터마이징 창을 열면, **Then** 파츠 종류별로 선택 가능한 항목들이 보인다.
2. **Given** 커스터마이징 창, **When** 특정 파츠를 다른 것으로 바꾸면, **Then** 내 캐릭터가 즉시 바뀐다.
3. **Given** A가 파츠를 바꿈, **When** 같은 월드의 B가 A를 보면, **Then** **별도 조작 없이** 바뀐 모습이 보인다.
4. **Given** 커스터마이징 창, **When** 색상을 선택하면, **Then** 캐릭터 색상이 즉시 바뀌고 전원에게 전파된다.
5. **Given** 커스터마이징 창, **When** 무작위 버튼을 누르면, **Then** 전체 파츠가 무작위로 조합된다.

### User Story 2 — 다음에 들어와도 그 모습이다 (Priority: P0) [신규 — BE]

**Independent Test**: 외형 변경 → 브라우저 완전 종료 → 재접속 → 같은 외형인지 확인.

**Acceptance Scenarios**:

1. **Given** 외형을 변경한 사용자, **When** 월드를 나갔다가 다시 들어오면, **Then** 마지막 외형이 그대로 복원된다.
2. **Given** 저장이 실패한 경우, **When** 사용자가 계속 플레이하면, **Then** **이번 세션에서는 변경된 외형이 유지**되고 월드 이용이 중단되지 않는다.
3. **Given** 저장된 외형 값이 이 클라이언트가 모르는 형식인 경우, **When** 접속하면, **Then** 기본 외형으로 대체되고 오류로 중단되지 않는다.

### User Story 3 — 정식 커스터마이징 창 (Priority: P0) [신규 — FE]

현재의 임시 Unity 창을 대체하는 React 오버레이.

**Why this priority**: 임시 창은 한글 표시가 안 되고(T-22) 디자인이 불가능하다. 정식 UX가 필요하다.

**Acceptance Scenarios**:

1. **Given** 월드 화면, **When** 커스터마이징을 열면, **Then** 웹 오버레이로 창이 열리고 뒤의 내 캐릭터가 보인다.
2. **Given** 창에서 파츠를 고르면, **When** 선택 즉시, **Then** 뒤의 캐릭터가 바뀐다 (별도 미리보기 3D 불필요).
3. **Given** 창, **When** 저장하면, **Then** 저장 결과(성공/실패)가 사용자에게 표시된다.

### Edge Cases

- 외형 데이터가 매우 길어지는 경우 → **실제로 터진 적 있음 (T-24)**. 길이 상한과 초과 시 동작이 명세되어야 한다
- 파츠 데이터 로딩이 끝나기 전에 사용자가 접속한 경우 → 준비되면 자동 반영되어야 한다
- 좌우 짝이 있는 파츠(팔·다리)에서 한쪽만 바뀌는 경우 → 자동으로 짝이 맞아야 한다
- 다른 사용자가 조작된 외형 값을 보내는 경우 → 서버가 검증해야 한다
- 30~40명이 각자 다른 외형인 경우 → 렌더링 비용

## Requirements

### Functional Requirements

- **FR-001** [구현됨]: 사용자는 파츠 종류별로 외형을 선택할 수 있어야 한다.
- **FR-002** [구현됨]: 사용자는 색상을 선택할 수 있어야 한다.
- **FR-003** [구현됨]: 외형 변경은 **같은 월드의 모든 사용자에게 즉시** 반영되어야 한다.
- **FR-004** [구현됨]: 외형은 **문자열 하나로 표현**되어 동기화되며, 3D 데이터가 네트워크로 오가서는 안 된다 (헌법 5조).
- **FR-005** [구현됨]: 외형 3D 표현은 각 클라이언트가 로컬 생성하며 네트워크 오브젝트가 아니어야 한다.
- **FR-006** [구현됨]: 좌우 대칭 파츠는 한쪽 변경 시 반대쪽이 자동으로 맞춰져야 한다.
- **FR-007**: 외형 문자열은 **길이 상한**을 가지며, 초과 시 **사용자에게 명확히 거부 사유가 표시**되어야 한다. *조용히 기본값으로 대체해서는 안 된다 (T-24의 교훈).*
- **FR-008** [구현됨]: 알 수 없는 외형 세그먼트는 무시하고 나머지를 적용해야 한다 (구버전 클라이언트 호환).
- **FR-009** [신규]: 시스템은 사용자의 외형을 **영구 저장**하고 재접속 시 복원해야 한다.
- **FR-010** [신규]: 저장 실패가 월드 이용을 중단시켜서는 안 된다.
- **FR-011** [신규]: 서버는 클라이언트가 보낸 외형 값의 형식과 길이를 검증해야 한다 (헌법 12조).
- **FR-012** [신규]: 정식 커스터마이징 창은 **웹 레이어**가 제공해야 한다 (헌법 17조).
- **FR-013**: 변경 요청이 서버에 반영되지 않으면 사용자에게 알려야 한다. *(T-24 후속으로 구현됨)*

### Key Entities

- **Avatar Appearance**: 한 사용자의 외형. 파츠 구성 또는 프리셋 코드, 색상
- **Part Catalog**: 선택 가능한 파츠 목록. 파츠 종류별 항목들

## 계약 — 외형 문자열 (3파트 공통)

> 기존 계약서(`festa-unity/Docs/avatar-customization-contract.md`)는 프리셋 방식 기준으로 작성되어
> **최대 29자**로 되어 있으나, 파츠 조립 방식 채택으로 실제로는 **수백 자**가 된다. 계약서 갱신 필요.

```
sk_01                                     프리셋만
sk_01|c=E85D5D                            프리셋 + 색상
rt|1=SK_HUMN_BASE_02_01HEAD_HU01|10=...   파츠 조립 (실사용 약 600자)
```

| 규칙 | 값 |
|---|---|
| 구분자 | `\|`, 세그먼트는 `키=값` |
| 첫 세그먼트 `rt` | 파츠 조립 모드 |
| 알 수 없는 세그먼트 | 무시 (forward compatible) |
| 최대 길이 | **[NEEDS CLARIFICATION: 저장 컬럼 크기와 함께 확정 — Unity 현재 상한 3800]** |
| 오류/빈 값 | 기본 외형으로 폴백 |

**BE에 필요한 것**: 사용자 외형 저장 필드(**VARCHAR(32) 아님 — 최소 1000자 이상 또는 TEXT**)와 조회·저장 수단.

## Success Criteria

- **SC-001**: A가 파츠를 바꾸면 B 화면에 1초 이내에 반영된다.
- **SC-002**: 재접속 후 외형이 복원되는 비율이 100%다.
- **SC-003**: 저장 서버가 죽어 있어도 월드 이용과 외형 변경(세션 한정)이 계속된다.
- **SC-004**: 사용자가 안내 없이 창을 열어 외형을 바꾸고 저장까지 완료할 수 있다.
- **SC-005**: 외형 변경 요청이 무반응으로 끝나는 사례가 0건이다 (실패 시 반드시 사유 표시).
