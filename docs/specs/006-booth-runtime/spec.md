## User Scenarios & Testing

### User Story 1 — 남이 만든 부스가 월드에 보인다 (Priority: P0) [대부분 구현됨]

방문자가 월드에서 부스 구역에 가면, 그 부스 소유자가 웹에서 배치한 대로 3D 오브젝트가 놓여 있다.

**Why this priority**: 005(만들기)와 짝을 이루는 나머지 절반. 이 두 개가 붙어야 UGC가 완성된다.

**Independent Test**: 배치 데이터를 바꾼 뒤 월드에 들어가면, **Unity를 재빌드하지 않고** 바뀐 배치가 보인다.

**Acceptance Scenarios**:

1. **Given** 공개된 배치가 있는 부스, **When** 방문자가 그 부스를 보면, **Then** 배치된 오브젝트들이 저장된 위치·방향대로 보인다. **[구현됨 — 공개본 연동만 신규]**
2. **Given** 배치 데이터만 변경, **When** 방문자가 다시 방문하면, **Then** 클라이언트 재빌드 없이 변경이 반영된다. **[구현됨]**
3. **Given** 배치에 이 클라이언트가 모르는 오브젝트 종류가 포함, **When** 부스를 생성하면, **Then** 그 오브젝트만 제외되고 **나머지는 정상 표시**된다. **[구현됨 — 검증 완료]**
4. **Given** 배치 데이터를 가져오지 못한 경우, **When** 방문자가 접근하면, **Then** 월드 전체가 중단되지 않고 해당 부스만 비어 보인다. **[구현됨 — 404 graceful skip 검증 완료]**

### User Story 2 — 부스 오브젝트와 상호작용한다 (Priority: P0/P1 혼합) [신규]

방문자가 부스의 오브젝트를 클릭하면 그에 맞는 기능이 열린다.

**Acceptance Scenarios**:

1. **Given** AI 오브젝트가 배치된 부스, **When** 방문자가 상호작용하면, **Then** 연결된 AI와 대화할 수 있는 창이 열린다. **[신규 — spec 008]**
2. **Given** 노트북 오브젝트, **When** 방문자가 상호작용하면, **Then** 소유자가 등록한 홈페이지가 열린다. **[신규 — spec 016]**
3. **Given** 어떤 기능 오브젝트든, **When** 상호작용하면, **Then** Unity는 **트리거만 발생**시키고 실제 UI는 웹 레이어가 담당한다 (헌법 17조).

### Edge Cases

- 오브젝트가 서로 겹쳐 배치된 경우 [NEEDS CLARIFICATION: Unity가 보정하는가, 편집기가 막는가 — 005 C-02와 연관]
- 배치 좌표가 부스 영역을 벗어난 경우
- 배치 데이터의 버전이 이 클라이언트보다 높은 경우 → 알 수 없는 필드는 무시하고 동작해야 한다
- 부스 임대가 만료된 순간 방문 중인 사용자 (004의 만료 정책과 연동)
- 오브젝트가 매우 많은 부스에 여러 명이 동시에 있는 경우 → 성능

## Requirements

## 공간 운영 기준 — 외부 슬롯 + 내부 슬롯 풀 (2026-08-14 1차 MVP 결정)

> 1차 MVP의 확정 공간 모델이다. 사용자마다 Dedicated Server나 Scene을 따로 만들지 않고, 물리 임대 슬롯 수만큼 외부 슬롯과 내부 앵커를 운용한다.

1. 메인 월드에는 임대 슬롯마다 고정 `BoothExteriorSlot`을 둔다. 외부는 기본 건물·문·간판을 유지하고 부스명, 로고, 대표색, 영업 상태 정도만 제한적으로 표현한다.
2. 같은 World Scene의 시야 밖 먼 위치에는 물리 슬롯 수만큼 `BoothInteriorAnchor`를 미리 둔다. 사용자 수만큼 만들지 않고 7개 임대 슬롯에 대응하는 7개 내부 앵커만 사용한다.
3. 방문자가 외부 문에서 입장을 확인하면 서버가 활성 임대와 입장 가능 상태를 확인하고 해당 내부 앵커로 플레이어를 이동시킨다. 클라이언트는 그 시점에만 해당 Booth의 Published Layout을 조회·로컬 생성하며 퇴장 시 제거한다.
4. 외부와 내부 데이터는 분리한다. 1차 MVP에서는 내부만 자유 배치 Layout으로 제공하고 외부는 제한된 Facade 설정만 허용한다. 외부까지 자유 배치가 필요해지면 별도 `exteriorLayout`과 강한 경계·개수 제한을 추가한다.
5. 임대 만료 시 기존 소유자의 Layout·AI·문서 데이터는 삭제하지 않고 Draft로 보존하되 슬롯에서는 연결을 해제한다. 신규 입장을 막고 내부 방문자를 외부로 이동시킨 뒤 `BoothRuntime.Clear()`를 수행하며, 외부는 기본 빈 간판 상태로 되돌린다.
6. 일반 방문은 여러 사용자가 동시에 들어가는 공유 공간으로 운영한다. 부스 전체 예약·독점은 P0에서 제외하고, 사람 상담·비공개 행사처럼 실제 독점이 필요한 기능에만 별도 세션/예약을 둔다.

부스 수나 내부 자산이 크게 늘어 같은 Scene의 슬롯 풀이 메모리·좌표 정밀도에 부담을 주는 시점에 Additive Scene 또는 Booth Instance로 교체한다. Layout·Lease 계약은 그대로 유지해 전환 비용을 제한한다.

### Functional Requirements

- **FR-001** [구현됨]: 클라이언트는 부스의 배치 데이터를 조회할 수 있어야 한다.
- **FR-002** [신규]: 클라이언트는 **공개본(Published)만** 조회해야 한다. 작업본을 표시해서는 안 된다.
- **FR-003** [구현됨]: 클라이언트는 배치 데이터의 오브젝트 종류에 맞는 3D 표현을 생성해야 한다.
- **FR-004** [구현됨]: 저장된 위치·회전이 그대로 반영되어야 한다.
- **FR-005** [구현됨]: 알 수 없는 오브젝트 종류는 **건너뛰되 부스 전체를 실패시켜서는 안 된다**.
- **FR-006** [구현됨]: 배치 조회 실패가 월드 접속이나 다른 부스에 영향을 주어서는 안 된다.
- **FR-007** [구현됨]: 부스 오브젝트는 **네트워크 동기화 대상이 아니어야 한다** — 각 클라이언트가 같은 데이터로 각자 생성한다 (헌법 4조). *정적 오브젝트를 동기화하면 30~40명 월드에서 대역폭이 감당되지 않는다.*
- **FR-008** [신규]: 부스 콘텐츠를 추가할 때 **Unity 재빌드가 필요해서는 안 된다** (헌법 4조).
- **FR-009** [신규]: 기능 오브젝트는 상호작용 가능해야 하며, 상호작용 시 **웹 레이어에 전달할 이벤트**를 발생시켜야 한다.
- **FR-010** [신규]: 상호작용 이벤트에는 어떤 부스의 어떤 오브젝트인지 식별 정보가 포함되어야 한다.
- **FR-011** [신규]: 배치가 변경되어 재조회가 필요할 때 기존 오브젝트를 정리하고 다시 생성해야 한다. [NEEDS CLARIFICATION: 갱신 시점 — 진입 시 / 주기적 / 이벤트 수신 시]

### Unity → React 상호작용 이벤트 계약 (2026-08-18 확정)

Unity WebGL은 기존 합의 네임스페이스인 `window.FestaUnity`를 사용하며, 부스 상호작용 이벤트를 JSON 문자열로 전달한다.

```text
window.FestaUnity.onBoothInteract(json)
```

노트북 상호작용의 최초 확정 이벤트는 다음과 같다.

```json
{
  "type": "BOOTH_LAPTOP_INTERACT",
  "boothId": 7,
  "objectId": "laptop-1",
  "url": "https://example.com"
}
```

- `type`: `BOOTH_LAPTOP_INTERACT` 고정. 이후 기능 오브젝트는 같은 이벤트 union에 추가한다.
- `boothId`: 필수 `number`. 상호작용이 발생한 부스 식별자다.
- `objectId`: 필수 `string`. Layout과 Runtime Object가 공유하는 오브젝트 식별자다.
- `url`: LAPTOP 전용 선택 `string`. 주소가 없어도 이벤트는 발생하며 FE는 오류 대신 안내를 표시한다.
- FE는 JSON 파싱 실패를 해당 이벤트 하나로 격리하고 다른 부스 기능을 계속 처리한다.

> **구현 상태**: Unity의 `LAPTOP` 클릭 컴포넌트와 WebGL `.jslib` 송신부가 구현되었다. 프리팹의 Collider가 자식에 있는 경우에도 클릭 릴레이를 통해 루트의 `BoothRuntimeObject` 식별자를 송신하며, C#/JavaScript 양쪽의 콜백 예외는 해당 이벤트 하나로 격리한다. URL 저장 위치는 아직 미확정이므로 현재 이벤트는 `boothId + objectId`를 필수로 송신하고, URL 값이 생긴 경우에만 선택 필드를 포함한다.

### Key Entities

- **Booth Runtime Instance**: 월드에 생성된 부스 하나. 부스 식별자, 적용된 배치 버전, 생성된 오브젝트 목록
- **Runtime Object**: 생성된 오브젝트 하나. 배치 식별자, 종류, 연결된 콘텐츠 식별자, 상호작용 가능 여부

## Success Criteria

- **SC-001**: 배치 데이터만 바꾸고 클라이언트를 재빌드하지 않아도 월드 표현이 바뀐다. *(POC 달성)*
- **SC-002**: 알 수 없는 오브젝트가 포함된 배치에서 나머지 오브젝트의 표시 성공률이 100%다. *(POC 달성)*
- **SC-003**: 부스 7개가 모두 채워진 상태에서 목표 인원이 접속해도 프레임이 유지된다. [NEEDS CLARIFICATION: 목표 프레임]
- **SC-004**: 배치 조회 실패 시에도 월드 접속과 이동이 정상 유지된다. *(POC 달성)*
- **SC-005**: 방문자가 기능 오브젝트를 클릭했을 때 해당 기능이 열리는 비율이 100%다.
