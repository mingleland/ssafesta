## 되돌린 것 — 라이트맵 베이크

**시도했고, 측정했고, 철회했다.** 기록으로 남기는 이유는 다음 사람이 같은 길을 다시 걷지
않게 하기 위해서다.

| 단계 | 기준 대비 밝기 |
|---|---|
| 시험 0.25텍셀/유닛 | 0.71배 |
| 정품 1.0 + AO 30유닛 | 0.59배 |
| AO 끔 | 0.76배 |
| 세기 2.0배 + 배정 보정 | 0.977배 |
| 최종 (AO 끔) | **0.996배** |

밝기는 기준선을 회복했고 실시간 광원 부담도 29→1개로 떨어졌지만, **로비 전체에 각진 얼룩**이
남아 철회했다. 가설 4개(총 텍셀·삼각형당 텍셀·메시 노멀·UV2 패킹)를 전부 실측으로 기각했으나
원인을 찾지 못했다. 경위는 T-222.

**얻는 것보다 잃는 것이 컸다.** 성능은 오클루전 컬링만으로 드로우콜 79%·삼각형 90%를
시각적 부작용 없이 확보했다.

건진 것:
- **베이크 규모는 굽기 전에 잰다** — 전나무가 라이트맵 예산의 96%(92개 렌더러, LOD0~3 전부)를
  먹고 있었다. 제외하니 아틀라스 12장 → 1장, 베이크 48초
- `LightProbeGroup` 이 0개다. Baked 광원을 쓰려면 필수 — 없으면 동적 오브젝트가 평면 환경광만 받는다
- AO 거리는 이 월드(1m=10유닛)에서 **8유닛 이하**여야 한다. 30유닛은 3m 로 과하다

## 잡은 무언(無言) 결함 셋

성능 수치는 아니지만, **유니티가 에러를 내지 않아 사람 눈으로만 발견된** 것들이다.
셋 다 지금은 CI 테스트가 막는다 (S15P21A604-321).

| 결함 | 증상 | 왜 안 걸렸나 |
|---|---|---|
| 서브메시 소실 (T-223) | 사물함 자물쇠·거울·디테일이 통째로 미출력 | 재질 슬롯 5 > 서브메시 1 인데 유니티는 침묵. 정점 수만 보면 성공으로 보인다 |
| `.meta` 누락 (T-221) | 받는 쪽에서 Missing Script | 내 머신엔 `.meta` 가 있어 전부 정상으로 보였다 |
| HDR 버퍼 NaN (T-224) | 씬 뷰만 흰 웅덩이 | `Camera.Render()` 는 씬 뷰 Fx 를 안 타서 재현되지 않았다 |

**공통점 — 로컬이 멀쩡한 것은 저장소·타깃이 멀쩡하다는 증거가 아니다.** 원칙 0-2, 0-5 의 연장이다.

## 0. 이 프로젝트에서 얻은 원칙 다섯

작업 순서를 정하는 기준이라 맨 앞에 둔다. 다섯 다 **틀려 본 뒤에** 얻은 것이다.

### 0-1. 추론하지 말고 실측한다

에디터가 심하게 버벅여 "렌더가 무겁다" 고 추론하고 렌더 최적화를 하려던 참이었다.
Profiler 를 돌리자 **렌더 2.9~5.4 ms 인데 프레임은 99.5 ms** 였다. 범인은 그리기가 아니라
메모리(관리 힙 1.0 GB · 텍스처 921 MB)였다. 렌더를 아무리 깎아도 99.5 ms 는 줄지 않았을 것이다.

### 0-2. 타깃 플랫폼에서 잰다 — 에디터는 3.8배 낙관적이었다

| | 아바타 1기당 프레임 비용 |
|---|---|
| 에디터 | 0.19 ms |
| WebGL(크롬) | **0.72 ms** |

에디터 40기 12.07 ms(83 fps)만 보면 "여유 있다" 가 되지만, 실제 WebGL 은 **38.8 ms(25.7 fps)** 로
목표 미달이다. 더 나쁜 것은 **병목의 종류까지 달랐다**(0-3).

### 0-3. 병목의 정체는 "줄여 보고" 가른다

무엇이 잡고 있는지 모를 때, 한 축만 크게 줄여 프레임이 따라오는지 본다.

- 에디터: 드로우콜 157 감소 → **프레임 무변화** → 드로우콜 병목 아님
- WebGL: 픽셀 9분의 1(1920×1200→640×400) → **12% 개선뿐** → 픽셀 병목 아님 = **CPU/드로우콜**

같은 실험이 플랫폼마다 반대 결론을 냈다. 이 판별을 건너뛰고 최적화하면 헛수고한다.

### 0-4. 계측 도구도 코드다 — 틀리면 우선순위가 틀어진다

부하 측정 도구가 아바타를 **1.3 m 지면에 묻은 채**(T-201), **루트 모션이 켜진 채**,
**프로덕션에는 없는 실시간 그림자를 켠 채** 재고 있었다. 셋 다 수치를 왜곡했다.
도구를 만들 때는 **프로덕션과 같은 설정인지**부터 맞춘다.


### 0-5. 에디터에서 통과한 것이 빌드에서도 되는 것은 아니다

0-2 가 **측정**의 문제라면 이것은 **동작**의 문제다. 같은 코드가 에디터에서는 멀쩡하고
빌드에서만 깨지는 부류가 있다.

스킨메시 결합(§10)을 에디터에서 검증하고 넘겼는데, **빌드에서 아바타 피부가 통째로 사라졌다**(T-203).
원인은 `Read/Write Enabled` 가 꺼진 메시다 — 에디터는 CPU 사본을 들고 있어 `mesh.vertices` 가
읽히지만, 빌드는 GPU 로만 올려서 접근이 **예외를 던진다.** 그 예외가 `Apply()` 를 중단시켜
결합 실패에 색·애니메이터 설정 누락까지 함께 끌고 갔다.

**에디터 검증만으로는 부족한 것들** — 이 목록에 걸리면 반드시 빌드에서 확인한다.

| 부류 | 왜 에디터에서 안 드러나나 |
|---|---|
| 런타임 메시 조작 (`vertices`·`triangles`·`BakeMesh`) | 에디터는 CPU 사본 보유, 빌드는 `isReadable` 필요 |
| 셰이더 변형(variant) | 에디터는 즉시 컴파일, 빌드는 미포함 시 마젠타 |
| 리소스 경로 로드 (`Resources.Load`) | 에디터는 파일 탐색, 빌드는 번들에 포함돼야 함 |
| IMGUI·입력 처리 | 빌드 설정(Active Input Handling)에 따라 통째로 빠짐 |
| 프로파일러 통계 (`ProfilerRecorder`) | 릴리즈 빌드에서는 계측 자체가 제거됨 |

**방어**: 값을 읽기 전에 가능 여부를 먼저 확인하고(`isReadable`), 불가능하면 **기능을 끄되
나머지는 살린다**. 예외가 조립 파이프라인 전체를 중단시키게 두지 않는다.

## 1. 씬 지오메트리 — 렌더러 병합

- **현상** — 씬 렌더러 977개. 부스·전구·엘리베이터·사물함이 오브젝트 단위로 쪼개져 있어
  드로우콜이 형태 수만큼 나갔다. 11층 방만 오브젝트 2,043개.
- **방법** — 재질별 `Mesh.CombineMeshes` 로 서브트리를 하나의 메시로 굽고, 원본은
  **비활성으로 보존**(재배치 시 다시 병합). 정점 64k 초과 시 `IndexFormat.UInt32`.
- **성과** — 렌더러 **977 → 398**. 엘리베이터 드로우 정점 **1,221,414 → 8,850(138배)**.
  11층 오브젝트 2,043 → 156, 렌더러 1,425 → 138.
- **남은 문제** — ① **병합과 정적 배칭은 양자택일**이다. 64k 정점을 넘긴 병합 메시에
  `BatchingStatic` 을 같이 켜면 Play 에서 파손된다(T-191) → 병합본은 `OccludeeStatic` 만 켠다.
  ② 병합하면 개별 오브젝트를 못 끄므로, **바뀔 수 있는 것은 병합하지 않는다**(부스 슬롯 콘텐츠 등).

## 2. 텍스처 메모리 — 임포트 상한

- **현상** — 로드 텍스처 **649 MB**. 노트북 소품 하나가 비압축 TGA 163 MB 였다.
  WebGL 은 탭 힙 상한(실질 1~1.5 GB)에 걸리면 느려지는 게 아니라 **탭이 죽는다.**
- **방법** — 에셋별 `maxTextureSize` 캡 + 압축 포맷 지정. 원본은 그대로 두고 임포트 설정만.
- **성과** — **649 → 357 MB (−292 MB)**.
- **남은 문제** — 아바타 텍스처는 아직 손대지 않았다. 인원수만큼 늘어나는 쪽이라
  30~40인 목표에서는 여기가 다음 표적이다.

## 3. 가시성 — 오클루전 컬링 베이크

- **현상** — 벽 너머 부스·소품까지 매 프레임 제출.
- **방법** — 정적 지오메트리에 `OccludeeStatic`/`OccluderStatic` 을 주고 오클루전 베이크.
  산출물 `Scenes/main/OcclusionCullingData.asset` 은 **커밋 필수**다.
- **성과** — 실내에서 시야 밖 지오메트리 제출 제거(그림자 캐스터 969 → 220 과 함께 적용).
- **남은 문제** — **카메라 연출과 충돌한다.** 카메라를 보간으로 당기면 전환 한 순간에 실내
  전체가 컬링돼 "바깥 세상이 번쩍" 한다(T-190). 당김은 즉시(하드 클램프), 복귀만 보간으로 바꿔 해결.

## 3-1. 가시성 — 셸을 오클루더로 승격 (S15P21A604-322)

오클루전을 구워도 **가리는 물체가 지정돼 있지 않으면 아무것도 가려지지 않는다.**
부스 셸(벽·천장) 렌더러 7장에 Occluder/Occludee 플래그가 없어, 부스 안에 서 있어도
축제장 전체가 그려지고 있었다.

| 시점 | 전 | 후 | 절감 |
|---|---|---|---|
| 부스 내부 | 1,088 | **231** | 79% |
| 벽 밀착 | 1,088 | **109** | 90% |

**계측 도구를 한 번 갈아탔다.** 처음엔 `Renderer.isVisible` 로 셌는데 절감이 0.0% 로 나왔다 —
벽 밀착 시점과 실외 시점이 **둘 다 1088** 이라 계측이 틀렸음을 알았다. `isVisible` 은
"어느 카메라에든" 보이면 true 라 수동 `cam.Render()` 결과를 반영하지 않는다.
`UnityStats.drawCalls` 로 바꾸고 나서야 실제 수치가 잡혔다. **원칙 0-4 의 사례다.**

화질 회귀는 7개 시점 전/후 픽셀 비교로 확인했다 — 변화 **0.0%**. 컬링이 과해서 보여야 할 것이

  ① **아바타별 아틀라스는 답이 아니다.** 조합마다 아틀라스가 갈리면 텍스처 메모리가 인원수만큼
     늘고 배칭도 깨진다 — 반드시 **카탈로그 단위로 한 번** 구워 공유해야 한다.
  ② 색 시스템을 다시 설계해야 한다. 지금은 부위별 재질 + MaterialPropertyBlock 으로 색을 넣는데,
     하나의 재질로 합치면 **어느 픽셀이 어느 부위인지 마스크로 구분**해야 한다
     (GarmentTint 가 이미 6슬롯 마스크 방식이라 확장의 실마리는 있다).
  ③ 외형 시스템 전체가 여기에 얹혀 있어 회귀 범위가 넓다. 오늘 T-203·T-204 가 보여줬듯
     **에디터 통과 ≠ 빌드 동작**이라, 착수하면 빌드 검증까지 한 묶음으로 봐야 한다.
- **판단 필요** — 효과(드로우콜 800 → 40)는 크지만 작업량과 회귀 위험도 크다.

## 14. 아바타 텍스처 해상도 캡 — 카탈로그 메모리 490 MB → 194 MB

### 현상
WebGL 40기 실측에서 드로우콜(990)이 병목으로 잡혔고, 그 해결책으로 "셰이더 통합 + 아틀라스"를
검토했다. 그런데 아틀라스 가능 여부를 재려고 텍스처를 전수 조사하다 **더 큰 문제**가 나왔다.

- 아바타 카탈로그의 고유 텍스처 **124종 / 259.8 M 픽셀 / 런타임 메모리 490.3 MB**
- 그중 **2048px 이 50종**. 파츠마다 마스크가 달라(61종) 공유가 안 된다.
- 40명이 서로 다른 옷을 입으면 카탈로그 대부분이 로드된다 → WebGL 에서 드로우콜보다
  **메모리가 먼저 터진다.**

### 방법
`TextureImporter.maxTextureSize` 를 **1024 로 캡**했다(126종). 코드 변경 0.
- WebGL 플랫폼 오버라이드가 **0종**임을 먼저 확인했다 — 오버라이드가 켜져 있으면 기본값을
  바꿔도 무효라 캡이 조용히 무시된다.
- 마스크는 **RGB 영역 마스크**(색을 칠할 구역 구분)라 알베도보다 해상도 민감도가 낮다.
- 무늬가 있는 것(`top.008 ... -STRIPES`)은 원래 1024 여서 **이번 캡의 영향을 받지 않는다.**

### 성과
| | 이전 | 이후 |
|---|---|---|
| 고유 텍스처 | 124종 | 124종 |
| 총 픽셀 | 259.8 M | **102.5 M** (−61%) |
| 런타임 메모리 | 490.3 MB | **194.3 MB** (−60%) |
| 2048px | 50종 | **0종** |

### 거기서 나온 문제
1. **아틀라스는 여전히 1024 로도 불가능하다.** RGBMap 62종 × 1024² ≈ 65 M 픽셀 →
   8192² 아틀라스(44 MB DXT1)가 필요하다. 파츠를 한 재질로 합치려면 **512 캡이 전제**다.
   즉 "드로우콜 990 → ~150" 은 **옷 마스크를 16분의 1 해상도로 줄이는 대가**를 요구한다.
2. **드로우콜이 실제로 얼마나 줄어드는지는 아직 모른다.** 이 캡은 메모리·대역폭을 줄이지만
   드로우콜은 그대로다(파츠 수·재질 수가 안 바뀜). WebGL 재측정으로 확인해야 한다.
3. 워킹트리에 **.meta 126개 변경**이 남는다. 텍스처 자체는 바뀌지 않고 임포트 설정만 바뀐다.
4. 시각 확인이 필요하다 — 2048 → 1024 가 된 것은 상의·하의·신체 마스크다.

## 14-1. UI 텍스처 — 표시 크기가 상한이다 (S15P21A604-324)

`Resources/Avatar/UI` 49개가 배포 빌드에서 **65.70 MB**, 빌드 138.78 MB 의 **47%** 였다.

원인 둘이 겹쳤다.

1. 원본이 **1254×1254** — 목록 칸에 **188×156** 으로 그려지는 그림인데
2. 1254 는 2의 거듭제곱이 아니라(**NPOT**) 블록 압축을 쓸 수 없어 **RGBA32 무압축**으로 들어간다
   → `1254×1254×4 = 6.0 MB`, 관측치 **6.1 MB** 와 일치

**목표 해상도를 추측할 필요가 없었다.** 런타임 코드가 이미 스스로 줄여 쓰고 있었기 때문이다.

```csharp
// CharacterLobbyController — 원본을 RenderTexture 로 blit 하며 상한을 건다
float resize = Mathf.Min(1f, 224f / Mathf.Max(sourceWidth, sourceHeight));
```

| 경로 | 코드상 상한 | 정한 `maxTextureSize` |
|---|---|---|
| 일반 썸네일 | 224 | 256 |
| 색상 아이콘 | 256 | 256 |
| 얼굴 시트(4칸) | 셀당 320 → 전체 640 | 1024 (셀 512) |

**65.7 MB → 8.7 MB.** 빌드 리포트와 런타임 계측 **두 독립 경로가 65.7 MB 로 일치**했다 —
서로 맞아떨어져야 믿을 수 있다.

**화질 비교의 대상을 한 번 바로잡았다.** 처음엔 "원본 PNG vs 임포트 결과" 로 재서 9건이
걸렸는데, **그중 8건은 내가 손대지 않은 파일**이었다 — 내가 오기 전부터 있던 차이다.
같은 파일을 옛/새 설정으로 각각 임포트해 비교하니 평균 차이 **0.58~2.97 / 255** 로,
**실제 표시 크기(188×156)** 에서 육안 구분이 불가능했다.

> **비교 대상과 비교 해상도를 둘 다 의심해라.** 원본 해상도로 재면 사용자가 보지 않는
> 조건에서 판정하게 되고(T-222), 절대 비교를 하면 내 변경이 아닌 차이까지 내 탓이 된다.

재빌드로 확인했다. **둘을 섞어 말하면 과장이 된다.**

## 15. 아틀라스를 하지 않기로 한 근거 — 드로우콜 −32% 가 프레임 −7.7% 만 줬다

> ⚠ **2026-08-26 단서** — 이 절의 수치는 **WebGL 빌드**의 4초 창 평균이라 §16(에디터)보다
> 안정적이지만, 각 조건을 **한 번씩만** 쟀다. 결론의 방향(드로우콜이 지배적 비용이 아니다)은
> 유지하되, "+3.7 FPS 가 상한" 같은 구체 수치는 **추정**으로 읽어야 한다. 아틀라스 착수 여부를
> 최종 결정하기 전에 ABAB 로 다시 재는 것이 맞다 ([T-211](25_트러블슈팅.md)).


### 현상
"셰이더 통합 + 아틀라스" 로 40기 드로우콜 990 → 약 150 을 노렸다. 착수 전에 **아틀라스가
품질 대가(옷 마스크 2048 → 512, 16분의 1)를 요구한다**는 것을 확인했으므로, 그 대가를 낼
가치가 있는지 먼저 재기로 했다.

### 방법
WebGL Development Build, 11층 전시실, 서버 접속 상태, 스트레스 아바타를 **전부 화면에 담고**
0 / 5 / 20 / 40기를 측정했다. 캔버스 1920×1200 (devicePixelRatio 2).

**측정 전 반드시 확인한 것** — `document.hidden` 과 rAF 60프레임 실측. 창이 가려지면
브라우저가 rAF 를 정지시켜 HUD 가 0.1 FPS / 32000 ms 같은 **가짜 수치**를 낸다. 읽기 직전마다
확인하지 않으면 스로틀링을 성능으로 오독한다.

| 아바타 | FPS | 평균 ms | 드로우콜 | SetPass | 삼각형 | 시스템 메모리 |
|---|---|---|---|---|---|---|
| 0기 | 76.2 | 13.1 | 202 | 46 | 1,269,024 | 517 MB |
| 5기 | 61.4 | 16.3 | 261 | 72 | 1,347,554 | 521 MB |
| 20기 | 44.3 | 22.6 | 436 | 132 | 1,578,774 | 526 MB |
| 40기 | 27.9 | 35.8 | 676 | 210 | 1,892,798 | 526 MB |

1기당 한계비용은 구간마다 **0.42~0.66 ms / 11.7~12.0 드로우콜** 로 선형이다 — 특정 구간에서
무너지는 절벽이 없다.

### 성과 — 그리고 결정적 수치
스킨메시 결합(§10)의 효과가 여기서 확인됐다. 이전 기준선과 비교하면:

| 40기 | 이전 | 지금 | 변화 |
|---|---|---|---|
| 드로우콜 | 990 | **676** | **−31.7%** |
| 평균 프레임 | 38.8 ms | **35.8 ms** | **−7.7%** |
| FPS | 25.7 | **27.9** | +8.6% |

**드로우콜을 32% 줄였는데 프레임은 7.7% 밖에 줄지 않았다.** 즉 드로우콜 1개당 약 0.0096 ms다.

이 값으로 아틀라스의 상한을 계산할 수 있다. 완벽하게 성공해서 아바타당 렌더러가 1개가 되면
40기 드로우콜은 202 + 40 ≈ 242, 즉 **434개를 없앤다** → 약 4.2 ms → 35.8 → **31.6 ms (31.6 FPS)**.

즉 **아틀라스의 최대 이득은 +3.7 FPS 다.** 그 대가는 옷 마스크 16분의 1 해상도 + 통합 셰이더·
아틀라스·병합·색 팔레트 전면 재작성 + T-203 류 빌드 위험이다. **대가가 이득보다 크다 — 하지 않는다.**

### 거기서 나온 문제 (다음에 볼 곳)
40기가 더하는 22.7 ms 중 드로우콜은 약 4.5 ms(20%)뿐이다. **나머지 80% 는 스키닝·애니메이터·
본 갱신**이다(1기당 삼각형 15,594 / 본 665). 그러므로 다음 축은 드로우콜이 아니다:
1. **본 수 줄이기** — 665본은 군중용으로 과하다. 거리별로 본을 줄인 LOD 리그.
2. **아바타 LOD** — 멀리 있는 아바타의 정점·본·애니메이터 갱신 빈도를 낮춘다.
3. **애니메이터 갱신 빈도** — `CullUpdateTransforms`(§?) 위에 거리별 업데이트 스킵.
메모리는 40기에서 +9 MB 에 그쳤다(517 → 526). 텍스처·메시 공유가 잘 되고 있어 1024 캡(§14)의
효과가 유지된다. 단 스트레스 아바타는 외형 다양성이 낮아 실제 사용자보다 공유율이 높다.

## 8. 네트워크 트래픽 — NetworkTransform 동기화 축·임계값

**현상** — 동접 26명에서 클라이언트 수신 **8.2 MB/s (1인당 약 316 KB/s)**. 이 트래픽이
트랜스포트 수신 큐(기본 128)를 넘겨 접속 자체가 실패했다 (T-220).
큐를 키우는 건 대증요법이라 트래픽 자체를 봤다.

**방법** — Player 프리팹 `NetworkTransform` 설정을 실측으로 점검했다.

| 항목 | 전 | 후 | 근거 |
|---|---|---|---|
| `SyncRotAngleX` / `Z` | 1 | **0** | `PlayerMovement` 가 `Quaternion.Euler(0f, next, 0f)` 로 **Y축만** 돌린다. X/Z 는 항상 0 인데 매 틱 실려 갔다 |
| `PositionThreshold` | 0.001 | **0.05** | 이 월드는 1 m = 10 유닛이다. 0.001 유닛 = **0.1 mm** — 미세 떨림마다 패킷이 나갔다 |
| `RotAngleThreshold` | 0.01 | **1** | 0.01도. 같은 이유 |

**성과** — 같은 조건(11명, 봇 10기)에서 수신 **4,529 → 3,290~3,505 KB/s, 약 25% 감소.**

**빗나간 것 — `UseHalfFloatPrecision` 은 오히려 늘었다**

위치를 반정밀도로 보내면 절반이 될 거라 보고 켰는데 **3,290 → 3,816 KB/s (+16%)** 였다.
NGO 의 반정밀도 모드는 기준 위치로부터의 델타를 보내고 주기적으로 재기준화하는데,
이 월드는 좌표가 수천 유닛까지 가서 재기준화가 잦아진 것으로 추정한다. **껐다.**
→ 교훈: "절반 크기니 절반 트래픽" 은 인코딩만 본 추론이다. 재기준화 비용까지 재야 한다.

**남은 문제**

- 1인당 약 300 KB/s 는 여전히 과하다. 다음 후보는 **틱 레이트**(현재 30 Hz) 인데,
  전역 설정이라 부드러움과 맞바꾸는 결정이다 — 혼자 정할 게 아니라 팀 판단이 필요하다
- 관심 영역(AOI) 기반 컬링이 없다. 40명이 한 방에 있으면 전원이 전원을 받는다
- 이 측정은 **한 머신에서 봇을 돌린 값**이라 절대치는 참고용이다. 비율(25%)만 신뢰한다

## 17. 서버는 그리지 않는다 (S15P21A604-314)

데디케이티드 서버가 머티리얼·폰트를 만들고 있었다. 셰이더가 스트립된 빌드라 만들 때마다
`Trying to access a shader…` 경고가 부스 수만큼 반복돼 **실제 로그를 덮었다.**

판정 기준이 이 절의 핵심이다.

| 후보 | 왜 안 되나 |
|---|---|
| `#if UNITY_SERVER` | **빌드 타깃이 Dedicated Server 면 에디터에도 정의된다** (T-182·T-228) |
| `Application.isBatchMode` | `-nographics` 없이 `-batchmode` 만 주면 장치가 살아 있다 |
| **`SystemInfo.graphicsDeviceType == Null`** | 판단하려는 것이 정확히 "그릴 대상이 있는가" 다 |

`Core/HeadlessRuntime` 으로 한 곳에 모으고 세 지점을 막았다 —
`PlayerAvatarVisual.Rebuild`(접속자 수만큼 곱해져 가장 크다), `BoothObjectFactory`,
`BoothFacadeApplier`.

**일부러 지킨 것 둘:**

- **콜라이더·트랜스폼은 남겼다.** 서버의 충돌 권위다 — 같이 걷어내면 벽 뚫림이 재발한다
- `BoothFacadeApplier` 는 **대상 슬롯 개수를 그대로 센다.** 0 을 반환하면 호출부가
  "대상을 못 찾았다" 고 경고하는데, **서버에서만 뜨는 가짜 경고는 진짜 계약 불일치를 가린다**

`OnGUI` 경고는 성격이 다르다 — **메서드가 존재한다는 사실만으로** 뜨므로 내부 가드로는 못 막고
컴파일에서 빼야 한다. 조건은 `#if UNITY_EDITOR || !UNITY_SERVER` 다. `UNITY_EDITOR` 를 빼면
**빌드 타깃을 서버로 둔 순간 에디터에서 개발 HUD 가 사라진다.**
