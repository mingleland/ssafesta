## 0. 이 프로젝트에서 얻은 원칙 다섯

작업 순서를 정하는 기준이라 맨 앞에 둔다. 다섯 다 **틀려 본 뒤에** 얻은 것이다.

### 0-1. 추론하지 말고 실측한다

에디터가 심하게 버벅여 "렌더가 무겁다" 고 추론하고 렌더 최적화를 하려던 참이었다.
Profiler 를 돌리자 **렌더 2.9~5.4 ms 인데 프레임은 99.5 ms** 였다. 범인은 그리기가 아니라
메모리(관리 힙 1.0 GB · 텍스처 921 MB)였다. 렌더를 아무리 깎아도 99.5 ms 는 줄지 않았을 것이다.

### 0-2. 타깃 플랫폼에서 잰다 — 에디터는 3.8배 낙관적이었다

| | 아바타 1기당 프레임 비용 |
|---|---|
| 에디터 | 0.19 ms |
| WebGL(크롬) | **0.72 ms** |

에디터 40기 12.07 ms(83 fps)만 보면 "여유 있다" 가 되지만, 실제 WebGL 은 **38.8 ms(25.7 fps)** 로
목표 미달이다. 더 나쁜 것은 **병목의 종류까지 달랐다**(0-3).

### 0-3. 병목의 정체는 "줄여 보고" 가른다

무엇이 잡고 있는지 모를 때, 한 축만 크게 줄여 프레임이 따라오는지 본다.

- 에디터: 드로우콜 157 감소 → **프레임 무변화** → 드로우콜 병목 아님
- WebGL: 픽셀 9분의 1(1920×1200→640×400) → **12% 개선뿐** → 픽셀 병목 아님 = **CPU/드로우콜**

같은 실험이 플랫폼마다 반대 결론을 냈다. 이 판별을 건너뛰고 최적화하면 헛수고한다.

### 0-4. 계측 도구도 코드다 — 틀리면 우선순위가 틀어진다

부하 측정 도구가 아바타를 **1.3 m 지면에 묻은 채**(T-201), **루트 모션이 켜진 채**,
**프로덕션에는 없는 실시간 그림자를 켠 채** 재고 있었다. 셋 다 수치를 왜곡했다.
도구를 만들 때는 **프로덕션과 같은 설정인지**부터 맞춘다.


### 0-5. 에디터에서 통과한 것이 빌드에서도 되는 것은 아니다

0-2 가 **측정**의 문제라면 이것은 **동작**의 문제다. 같은 코드가 에디터에서는 멀쩡하고
빌드에서만 깨지는 부류가 있다.

스킨메시 결합(§10)을 에디터에서 검증하고 넘겼는데, **빌드에서 아바타 피부가 통째로 사라졌다**(T-203).
원인은 `Read/Write Enabled` 가 꺼진 메시다 — 에디터는 CPU 사본을 들고 있어 `mesh.vertices` 가
읽히지만, 빌드는 GPU 로만 올려서 접근이 **예외를 던진다.** 그 예외가 `Apply()` 를 중단시켜
결합 실패에 색·애니메이터 설정 누락까지 함께 끌고 갔다.

**에디터 검증만으로는 부족한 것들** — 이 목록에 걸리면 반드시 빌드에서 확인한다.

| 부류 | 왜 에디터에서 안 드러나나 |
|---|---|
| 런타임 메시 조작 (`vertices`·`triangles`·`BakeMesh`) | 에디터는 CPU 사본 보유, 빌드는 `isReadable` 필요 |
| 셰이더 변형(variant) | 에디터는 즉시 컴파일, 빌드는 미포함 시 마젠타 |
| 리소스 경로 로드 (`Resources.Load`) | 에디터는 파일 탐색, 빌드는 번들에 포함돼야 함 |
| IMGUI·입력 처리 | 빌드 설정(Active Input Handling)에 따라 통째로 빠짐 |
| 프로파일러 통계 (`ProfilerRecorder`) | 릴리즈 빌드에서는 계측 자체가 제거됨 |

**방어**: 값을 읽기 전에 가능 여부를 먼저 확인하고(`isReadable`), 불가능하면 **기능을 끄되
나머지는 살린다**. 예외가 조립 파이프라인 전체를 중단시키게 두지 않는다.

## 1. 씬 지오메트리 — 렌더러 병합

- **현상** — 씬 렌더러 977개. 부스·전구·엘리베이터·사물함이 오브젝트 단위로 쪼개져 있어
  드로우콜이 형태 수만큼 나갔다. 11층 방만 오브젝트 2,043개.
- **방법** — 재질별 `Mesh.CombineMeshes` 로 서브트리를 하나의 메시로 굽고, 원본은
  **비활성으로 보존**(재배치 시 다시 병합). 정점 64k 초과 시 `IndexFormat.UInt32`.
- **성과** — 렌더러 **977 → 398**. 엘리베이터 드로우 정점 **1,221,414 → 8,850(138배)**.
  11층 오브젝트 2,043 → 156, 렌더러 1,425 → 138.
- **남은 문제** — ① **병합과 정적 배칭은 양자택일**이다. 64k 정점을 넘긴 병합 메시에
  `BatchingStatic` 을 같이 켜면 Play 에서 파손된다(T-191) → 병합본은 `OccludeeStatic` 만 켠다.
  ② 병합하면 개별 오브젝트를 못 끄므로, **바뀔 수 있는 것은 병합하지 않는다**(부스 슬롯 콘텐츠 등).

## 2. 텍스처 메모리 — 임포트 상한

- **현상** — 로드 텍스처 **649 MB**. 노트북 소품 하나가 비압축 TGA 163 MB 였다.
  WebGL 은 탭 힙 상한(실질 1~1.5 GB)에 걸리면 느려지는 게 아니라 **탭이 죽는다.**
- **방법** — 에셋별 `maxTextureSize` 캡 + 압축 포맷 지정. 원본은 그대로 두고 임포트 설정만.
- **성과** — **649 → 357 MB (−292 MB)**.
- **남은 문제** — 아바타 텍스처는 아직 손대지 않았다. 인원수만큼 늘어나는 쪽이라
  30~40인 목표에서는 여기가 다음 표적이다.

## 3. 가시성 — 오클루전 컬링 베이크

- **현상** — 벽 너머 부스·소품까지 매 프레임 제출.
- **방법** — 정적 지오메트리에 `OccludeeStatic`/`OccluderStatic` 을 주고 오클루전 베이크.
  산출물 `Scenes/main/OcclusionCullingData.asset` 은 **커밋 필수**다.
- **성과** — 실내에서 시야 밖 지오메트리 제출 제거(그림자 캐스터 969 → 220 과 함께 적용).
- **남은 문제** — **카메라 연출과 충돌한다.** 카메라를 보간으로 당기면 전환 한 순간에 실내
  전체가 컬링돼 "바깥 세상이 번쩍" 한다(T-190). 당김은 즉시(하드 클램프), 복귀만 보간으로 바꿔 해결.

## 4. 원거리 표현 — LOD

- **현상** — 나무가 거리에 따라 **뚝 바뀌는 팝핑**이 눈에 띔.
- **방법** — LODGroup 23개를 `CrossFade` 로 전환 + `QualitySettings.lodBias 1.5`.
- **성과** — 팝핑 제거. 원거리 정점 부담 감소.
- **남은 문제** — 크로스페이드는 전환 구간에서 **두 LOD 를 동시에 그린다**. 나무처럼 수가
  적을 때는 이득이지만, 아바타 40기에 그대로 적용하면 오히려 손해일 수 있다 — 미검증.

## 5. 그림자

- **현상** — 그림자 캐스터 969개. 아바타 스킨 메시 그림자는 골격 Bounds 문제로 **머리만 남는** 등 품질도 나빴다.
- **방법** — 정적 소품 캐스터 정리 + **아바타는 실시간 그림자를 끄고 접지용 블롭 하나**로 대체.
- **성과** — 캐스터 **969 → 220**. 아바타 40기 기준 드로우콜 1,311 → 1,154.
- **남은 문제** — 그림자를 꺼도 **프레임은 거의 안 변했다**(에디터 −12% 드로우콜, 프레임 무변화).
  즉 그림자는 드로우콜 지표만 낮췄고 실제 병목이 아니었다 — 0-3 판별의 사례다.

## 6. 프레임 상한 — 한 PC 두 인스턴스

- **현상** — 둘이서 테스트하는데 양쪽 다 버벅였다. "통신이 느린가?" 로 의심.
- **방법** — 통신은 정상(NT 보간 확인). 원인은 `targetFrameRate = -1`(무제한)이라
  호스트·클라이언트 두 프로세스가 CPU/GPU 를 무한 경쟁한 것 → **60 상한**(WebGL 제외, 브라우저 vsync 담당).
- **성과** — 두 인스턴스 동시 실행 시 체감 개선.
- **남은 문제** — 측정할 때는 이 상한이 **여유를 가린다**. 실측 전 `-1` 로 풀고, 끝나면 되돌린다.

## 7. GC — per-frame 할당 제거

- **현상** — 상호작용 프롬프트가 떠 있는 동안 주기적 끊김.
- **방법** — `OnGUI` 에서 매 프레임 `new GUIStyle` 하던 것을 캐시. 계측 HUD 도 같은 규칙 적용.
- **성과** — 프롬프트 표시 중 GC 쓰레기 제거.
- **남은 문제** — **WebGL 은 단일 스레드라 GC 가 프레임을 직접 끊는다.** 개별 수정이 아니라
  **규칙**으로 못박아야 한다 — `Update`/`OnGUI` 에서 할당 금지를 코드 리뷰 상시 항목으로.

## 8. 원격 아바타 — Animator 컬링

- **현상** — 넓은 축제 부지에서 화면 밖 아바타도 본(bone) 갱신을 계속했다.
- **방법** — `Animator.cullingMode = CullUpdateTransforms`. 상태 머신은 계속 돌아 다시 보일 때
  포즈가 어긋나지 않는다.
- **성과** — **화면 밖 40기 9.17 → 6.46 ms (−2.71 ms, −29.5%)**.
- **남은 문제** — 화면 **안**에 있는 아바타에는 효과가 없다. 축제장에서 다 같이 모여 있는
  상황(가장 무거운 경우)은 이 기법으로 못 줄인다.

## 9. 원격 아바타 — 런타임 재질 공유 ★

- **현상** — 아바타 1기당 **고유 재질 12개**. 40기면 480개가 생겨 SRP Batcher 가 배칭할 수 없었다.
- **방법** — 변환된 런타임 재질이 `(원본 재질 + 카테고리)`의 **순수 함수**이고 아바타별 색은
  전부 `MaterialPropertyBlock` 으로 나간다는 것을 코드로 확인한 뒤, 인스턴스별 캐시를
  **프로세스 공유 static 캐시**로 바꿨다(키에 카테고리 포함, 파괴된 재질 유효성 검사).
- **성과** — 고유 재질 **480 → 14**, SetPass **835 → 613(−26%)**, 아바타 조립 시간
  **20.7 → 2.4 ms/기(8.5배)**.
- **남은 문제** — ① **캐시 키를 `GetInstanceID()` 로 잡아 씬 전환 뒤 머리카락이 사라졌다**(T-204).
  ID 는 수명을 보장하지 않아 해제된 뒤 재사용된다 → 키를 **재질 오브젝트 참조**로 교체.
  ② **드로우콜은 그대로 1,311.** 렌더러 수(1기당 11개)가 줄지 않았기 때문이다.
  → 10번으로 이어진다.

## 10. 원격 아바타 — 스킨메시 결합 ★

- **현상** — WebGL 40기에서 **드로우콜 990 · 25.7 FPS**(목표 30 미달). 픽셀을 9분의 1로 줄여도
  12% 개선뿐이라 **CPU/드로우콜 병목**이 확정됐다. 원인은 **1기당 SkinnedMeshRenderer 11개**
  (팔 상/하·손·다리·몸통·머리·헤어·앞머리·상의·하의·신발).
- **방법** — 조립·가시성·색이 확정된 뒤 활성 SMR 을 **재질별로 묶어 하나의 스킨메시로 결합**.
  뼈 배열을 마스터 골격 기준으로 재매핑하고, 결합 렌더러당 재질이 하나이므로 MPB 를 그대로 쓴다.
  원본 렌더러는 비활성 보존(외형 변경 시 재결합).
- **성과** — 렌더러 **1기당 11 → 7 (−36%)**. 신체 파츠 5개(팔 상·하·손·다리·몸통)가 같은 재질·같은
  71뼈 골격이라 무손실 결합됐다 — 정점 1,784·인덱스 8,460 이 원본 합계와 정확히 일치하고,
  외형 비교 캡처에서도 차이가 없다. **드로우콜 40기 기준 약 160 감소 예상**(WebGL 재측정 대기).
- **남은 문제** — ⓪ **빌드에서는 메시가 읽기 불가라 결합이 실패했다** (T-203) — 에디터에서만
  통과하고 빌드에서 피부가 사라졌다. `isReadable` 가드 + 신체 FBX 2개만 Read/Write 활성화로 해결.
  ① 파츠별 가시성 토글(옷에 가려지는 신체)이 결합 후에는 불가 →
  **가시성 확정 후 결합**해야 한다. ② 서로 다른 셰이더(Skin/Face/Iris/Mouth/Garment)는
  합칠 수 없어 드로우콜이 1기당 1개까지 내려가지는 않는다 — 셰이더 종류 수가 하한이다.
  ③ 외형 회귀 위험이 커서 단계마다 캡처 비교가 필요하다.

## 11. 네트워크 — 하지 않기로 한 것

- **현상** — `PositionThreshold 0.001`(1 mm)로 과민 설정, 인원수 제곱으로 늘어나는 릴레이 트래픽.
- **방법(검토)** — 임계값 완화·HalfFloat·쿼터니언 압축.
- **성과** — **측정 결과 착수하지 않기로 했다.** 봇 12기 실측에서 클라이언트 1대 수신
  4.0~4.5 KB/s, 40명 환산 **약 15 KB/s(0.12 Mbps)** — 예산 1 Mbps 의 1/8이다.
- **남은 문제** — 없음. **아낄 절대량이 작다는 것을 알고 안 하는 것**과 모르고 안 하는 것은 다르다.
  트래픽이 커지는 기능(음성·물리 동기화)이 들어오면 다시 본다.

## 12. 원격 아바타 — 텍스처 아틀라스 (Mesh Baker) · 미착수, 판단 필요

- **현상** — 스킨메시 결합(§10)으로 1기당 렌더러 11 → 7 까지 줄였지만, **재질이 다르면
  드로우콜은 갈린다.** WebGL 40기에서 여전히 드로우콜 800 대가 아바타 몫이다.
- **조사** — 보유 중인 **Mesh Baker Free** 에 텍스처 아틀라스 기능(`MB3_TextureBaker`)이
  포함돼 있음을 확인했다. 다만 **아틀라스도 셰이더가 다르면 못 합친다.** 실측한 우리 아바타의
  셰이더 구성이 곧 하한이다:

  | 셰이더 | 재질 수 | 아틀라스 후 |
  |---|---|---|
  | `Universal Render Pipeline/Lit` (헤어) | 2 | 1 |
  | `Festa/Avatar/SkinTint` | 1 | 1 |
  | `Festa/Avatar/FaceTint` | 1 | 1 |
  | `Festa/Avatar/GarmentTint` (상의·하의·신발) | 3 | 1 |
  | **합계** | **7** | **4** |

- **성과(예상)** — 1기당 7 → **4**. 40기 기준 드로우콜 약 120 감소(−14%). **판을 바꾸지는 못한다.**
- **더 큰 길 — 셰이더 통합** — 1기당 **1~2 드로우콜**까지 내리려면 네 셰이더를
  **마스크 기반 단일 틴트 셰이더 하나로 합치고**, 카탈로그 전체(모든 의상·피부)를 담은
  **아틀라스 한 장을 미리 구워** 모든 아바타가 공유해야 한다.
  40기 드로우콜이 약 800 → 40 수준이 되므로 이것이 진짜 해결이다.
- **남은 문제 / 위험**
  ① **아바타별 아틀라스는 답이 아니다.** 조합마다 아틀라스가 갈리면 텍스처 메모리가 인원수만큼
     늘고 배칭도 깨진다 — 반드시 **카탈로그 단위로 한 번** 구워 공유해야 한다.
  ② 색 시스템을 다시 설계해야 한다. 지금은 부위별 재질 + MaterialPropertyBlock 으로 색을 넣는데,
     하나의 재질로 합치면 **어느 픽셀이 어느 부위인지 마스크로 구분**해야 한다
     (GarmentTint 가 이미 6슬롯 마스크 방식이라 확장의 실마리는 있다).
  ③ 외형 시스템 전체가 여기에 얹혀 있어 회귀 범위가 넓다. 오늘 T-203·T-204 가 보여줬듯
     **에디터 통과 ≠ 빌드 동작**이라, 착수하면 빌드 검증까지 한 묶음으로 봐야 한다.
- **판단 필요** — 효과(드로우콜 800 → 40)는 크지만 작업량과 회귀 위험도 크다.
  발표까지 남은 일정과 견줘 **할지 말지 결정**하고 착수한다.

## 13. 애니메이션 자산 — 보유 현황과 공백

- **현상** — 30~40명이 모이는 축제인데 아바타가 할 수 있는 동작이 **걷기·달리기·점프**뿐이다.
  체류시간·상호작용을 늘릴 표현이 없다.
- **조사(2026-08-25)** — 계정 보유 에셋 770개를 키워드로 훑었다.
  · `optimization` → **Mesh Baker Free** 보유 (§12 에서 활용 검토)
  · `instanc` → 0건 (GPU Instancer 없음)
  · `dance` → 1건이지만 쥐 캐릭터용, **사람 댄스·이모트 없음**
  · `crowd` → 0건 (군중 렌더링 시스템 없음)
  · `animation` → 62건 (Interaction Mocap, Pick Up & Carry, Sleep Anim, Run Animations 등)
- **임포트됨** — `Kevin Iglesias / Human Animations` **121 클립, 120개가 Humanoid**.
  우리 아바타도 Humanoid(`F_bodyAvatar`, `isHuman=true`)라 **리타게팅이 그대로 된다.**
  구성: Idle 2종·전환, Walk/Run/Sprint **8방향**, Turn 좌우, Jump(Begin/Land 분리), Fall, Talk01.
  루트모션 버전(`[RM]`)이 따로 있어 선택할 수 있다.
- **성과** — *(미적용)* 현재 애니메이터는 자체 클립으로 동작 중이라 **교체는 별개 작업**이다.
- **남은 문제**
  ① **이 팩은 로코모션이지 이모트가 아니다.** 인사·박수·춤·앉기는 여전히 없다 — 공백은 그대로다.
  ② 교체하면 점프 감각이 바뀐다. 지금 값(발구르기 0.18 s · 체공 0.75 s · 클립 speed 1.667/0.844)은
     사용자 피드백으로 맞춘 것이라, 교체 시 **다시 맞춰야 한다.**
     다만 이 팩은 Jump 를 Begin/Land 로 이미 나눠 놔서 우리가 손으로 만든 구조와 같다.
  ③ 8방향 로코모션을 쓰려면 블렌드 트리를 새로 짜야 한다 — 이동 느낌이 달라지는 변경이다.
