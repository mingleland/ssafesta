# SSAFY FESTA — 게임 파트 기술 기록

Unity 6 / URP / WebGL / Netcode for GameObjects 기반 메타버스 축제 월드에서 클라이언트와 게임 서버를 맡았다.
판단이 필요했던 작업만 추렸다. 각 항목은 상황 → 시도 → 그 시도가 만든 문제 → 최종 해결 순이다.

측정은 에디터 플레이 모드(`UnityStats`)와 배포 WebGL 빌드(크롬, 캔버스 1920×1200) 두 곳에서 했고, 지표가 다르므로 섞어 쓰지 않았다.

---

## 1. 드로우콜과 프레임타임은 비례하지 않는다 — 아틀라스를 착수 전에 접은 근거

**최대 이득 +3.7 FPS 로 계산돼 기능 하나를 접었다. 근거는 드로우콜당 0.0096 ms.**

WebGL 40기 실측에서 드로우콜 990이 병목으로 잡혔다. 다음 수는 셰이더 통합과 텍스처 아틀라스였는데, 마스크 텍스처를
2048에서 512로 낮추는 게 전제였다. 착수하면 몇 주가 든다.

먼저 스킨드 메시 결합을 적용했더니 40기 드로우콜이 990 → 676(−31.7%)이 됐는데 프레임타임은 38.8 → 35.8 ms(−7.7%)만
줄었다. 여기서 드로우콜 단가가 나온다. 3.0 ms / 314 = 약 0.0096 ms.

이 값으로 아틀라스의 상한을 계산했다. 아바타당 렌더러가 1개까지 줄어든다고 가정하면 40기 드로우콜은 202 + 40 ≈ 242 다.
676에서 434를 없애니 약 4.2 ms, 35.8 → 31.6 ms. 최대 이득이 +3.7 FPS 다. 대가는 마스크 해상도 16분의 1과
유니파이드 셰이더·머티리얼 병합·컬러 팔레트 전면 재작성이다. 대가가 이득보다 커서 접었다.

| 아바타 | FPS | 프레임타임 | 드로우콜 | 트라이앵글 |
|---|---|---|---|---|
| 0기 | 76.2 | 13.1 ms | 202 | 1,269,024 |
| 20기 | 44.3 | 22.6 ms | 436 | 1,578,774 |
| 40기 | 27.9 | 35.8 ms | 676 | 1,892,798 |

아바타 1기당 한계비용은 0.42~0.66 ms / 11.7~12.0 드로우콜로 구간마다 일정하다. 특정 인원에서 급격히 무너지는 구간이
없으니 비용이 인원에 비례해 누적되는 구조다.

프로파일링으로 비용을 분해하니 40기가 더하는 22.7 ms 중 드로우콜은 약 4.5 ms(20%)였고 나머지 80% 가 스키닝과
애니메이터 평가, 본 트랜스폼 갱신이었다(1기당 트라이앵글 15,594 / 본 665). 본 665개는 군중 표현용으로 과하다.
다음 작업 축을 드로우콜에서 본 수와 애니메이터 갱신 빈도로 바꿨다.

## 2. 오클루전 컬링 — 드로우콜 79% 감축

**복도 드로우콜 618 → 130(−79%), 로비 트라이앵글 1,483,176 → 149,296(−90%).**

먼저 렌더러 병합과 LOD 를 적용했다. 버텍스는 줄었지만 드로우콜은 그대로였다. 벽 하나 너머의 부스 전체가 여전히
배칭돼 제출되고 있었기 때문이다. 문제는 개별 메시의 무게가 아니라 컬링되지 않는다는 점이었다.

오클루전 컬링을 베이크하고 건물 셸을 오클루더로 승격했다. 축제 구역 드로우콜 1,088 → 231(−79%), 벽 밀착 시 109(−90%).

배포 빌드에서 살아 있는지는 따로 확인해야 했다. 성능 HUD 는 릴리스 빌드에서 비활성인데, 활성화하려고 빌드 설정을
바꾸면 측정 대상이 배포본이 아니게 된다. 그래서 빌드를 수정하지 않고 `WebGL2RenderingContext` 의 draw 계열을
프로토타입에서 후킹해 카운트했다.

| 시점 | 드로우콜 |
|---|---|
| 로비 — 사물함 벽 방향 | 568 |
| 사물함 벽 근접 | 248 (−56%) |
| 뒤로 물러남 | 660 |

정적 씬에서 카메라 위치만으로 2.7배가 변동한다. FPS 중앙값 122, 프레임타임 8.2 ms / p95 11.1 / 최악 15.8.
오클루전 데이터는 빌드 138.78 MB 중 160.5 KB 로 0.1% 다.

한계도 적어 둔다. 이 표는 컬링을 끈 빌드와의 비교가 아니라 시점 간 비교다. 79% 는 에디터 실측값으로 남긴다.

## 3. 동시 접속 — 병목은 서버 리소스가 아니라 트랜스포트 수신 큐였다

**25인에서 접속 불가 → 26명 접속 유지, 43~47 FPS.**

봇 25기가 붙은 서버에 클라이언트가 접속을 완료하지 못했다. 서버 리소스를 의심하기 쉬운 상황인데, 서버는 승인을
내주고 있었고(`Approved client=32 slot=25`) 거부 로그가 없었다. 같은 시점 CPU 28~55%, 메모리 295 MB 로 여유가 있었다.
서버가 거부하지 않는데 클라이언트가 붙지 못하면 서버 문제가 아니다.

클라이언트 콘솔에 원인이 있었다.

```
Receive queue is full, some packets could be dropped (128).
```

`UnityTransport.MaxPacketQueueSize` 기본값 128이 병목이었다. 동접 25명을 넘으면 한 틱에 도착하는 스냅샷과 스폰
메시지가 큐를 넘겨 핸드셰이크 패킷이 드롭됐다. 1024로 올려 26명 접속과 43.4 FPS 를 확인했다.
1024 packet × 약 1.4 KB ≈ 1.4 MB 로 메모리 비용은 무시할 수준이다.

그 다음이 더 중요했다. 큐를 올려도 60~90초 뒤 다시 끊겼다. `OnClientDisconnectCallback` 으로 사유를 받으니
`DisconnectReason` 이 빈 문자열이었다. 서버가 명시적으로 끊은 게 아니라 트랜스포트 레벨 드롭이라는 뜻이다.
접속 시점에 최악 프레임타임 기록을 리셋하고 재현하니 20.5초짜리 스톨이 찍혔다. 타임아웃이 30초니 그동안 하트비트가
나가지 못하면 연결이 끊긴다.

원인은 서버가 아니라 측정 환경이었다. 한 머신에 봇 25기와 에디터, Docker 를 모두 올려 호스트 여유 메모리가 3~4 GB 까지
떨어져 있었다. 그래서 큐 상향만 반영하고 동접 한계 수치는 확정하지 않았다. 이 구성에서 나온 끊김을 서버 한계로 적으면
틀린 기록이 된다.

## 4. 전송 신뢰성 — 연속 상태와 이산 이벤트를 분리

**원격 이동의 1~2초 지연 후 급가속 제거. 11인 기준 수신 4,529 KB/s → 3,290~3,505 KB/s(−25%).**

원격 플레이어의 이동 시작과 정지가 늦고, 지연이 해소되면 밀린 만큼 급가속했다. 이동 델타까지 Reliable 로 보내서
패킷 하나가 지연되면 뒤에 도착한 최신 위치가 헤드 오브 라인 블로킹에 걸렸고, 보간이 오래된 버퍼를 연속 소비했다.

이동은 최신 값만 유효하고 중간 값은 폐기해도 된다. 반면 초기 스폰 위치와 텔레포트는 유실되면 이후 보간의 기준 자체가
어긋난다. 이동 델타를 Unreliable 로 내리고 보간을 NGO 2.4 Lerp 로 교체하되, 초기 상태와 텔레포트는 Reliable 을 유지했다.

트래픽은 `NetworkTransform` 설정에서 줄였다.

| 항목 | 전 | 후 | 근거 |
|---|---|---|---|
| 회전 X / Z 동기화 | 켜짐 | 끔 | 캐릭터는 Y축만 회전한다. X/Z 는 항상 0인데 매 틱 실려 갔다 |
| 포지션 임계값 | 0.001 | 0.05 | 1 m = 10 유닛이라 0.001은 0.1 mm. 미세 진동마다 패킷이 나갔다 |
| 회전 임계값 | 0.01도 | 1도 | 같은 이유 |

반정밀도 인코딩은 켰다가 껐다. 3,290 → 3,816 KB/s 로 16% 늘었다. NGO 의 반정밀도 모드는 기준 위치 기준 델타를
보내고 주기적으로 리베이스하는데, 이 월드는 좌표가 수천 유닛까지 가서 리베이스가 잦아진 것으로 본다.
페이로드 크기만 보고 추론한 것이 빗나간 사례다.

1인당 약 300 KB/s 는 여전히 과하다. AOI 컬링이 없어 한 방의 전원이 전원의 상태를 받는 O(n²) 구조다.
다음 후보인 틱레이트 하향(현재 30 Hz)과 AOI 컬링은 전역 영향이라 단독으로 정하지 않고 팀 결정 항목으로 올렸다.

## 5. 아바타 — 식별자만 동기화하고 메모리는 임포트 단계에서 잡는다

**카탈로그 런타임 메모리 490.3 MB → 194.3 MB(−60%), 2048px 텍스처 50종 → 0종.**

아바타 동기화는 파츠 ID 만 전송하고 메시 조립은 각 클라이언트가 로컬에서 한다. 캐릭터당 NetworkObject 는 하나다.
파츠마다 NetworkObject 를 두면 대역폭과 스폰 메시지가 파츠 수만큼 곱해진다. 25인에서 수신 큐가 넘친 걸 보면 그 방향은
애초에 불가능했다.

메모리 문제는 다른 작업 중에 발견했다. 아틀라스 가능 여부를 판단하려고 텍스처를 전수 조사했더니 고유 텍스처 124종 /
259.8 M 픽셀 / 런타임 490.3 MB 였고 그중 2048px 이 50종이었다. 파츠마다 마스크가 달라 공유되지 않으므로 40명이 서로
다른 의상을 입으면 카탈로그 대부분이 로드된다. WebGL 에서는 드로우콜보다 메모리가 먼저 한계에 닿는 구조였다.

`TextureImporter.maxTextureSize` 를 1024로 캡했다. 코드 변경은 없다. 착수 전에 WebGL 플랫폼 오버라이드가 0종임을
먼저 확인했다. 오버라이드가 설정돼 있으면 기본값을 바꿔도 캡이 무시된다.

| | 이전 | 이후 |
|---|---|---|
| 총 픽셀 | 259.8 M | 102.5 M (−61%) |
| 런타임 메모리 | 490.3 MB | 194.3 MB (−60%) |
| 2048px | 50종 | 0종 |

## 6. WebGL 셰이더 워밍업 — 단가를 모르면 분할도 성립하지 않는다

**월드 진입 240초 → 30초 이내. 워밍업 코드와 프리로드 목록을 전부 제거했다.**

첫 프레임 힛치를 없애려고 추적된 셰이더 베리언트 192개를 `GraphicsSettings.m_PreloadedShaders` 에 등록했다.
이 목록은 플레이어 시작 시점에 일괄 워밍업되는데, WebGL 은 셰이더 컴파일이 메인 스레드 동기라 그동안 rAF 가 서지
않는다. 로딩이 1~2분 블로킹됐다. 첫 프레임 힛치를 로딩으로 옮기려던 것이 로딩 전체를 멈춘 셈이다.

그래서 `WarmUpProgressively(4)` 로 프레임당 4개씩 분할 컴파일하도록 바꿨다. 이번엔 월드 씬에서 블로킹이 발생하고
접속까지 끊겼다. 실측 프레임 길이가 3.4 / 10.8 / 13.8 / 45.9 / 58.0 / 53.6초, 완료 로그가 클릭 기준 +240초였다.

분할이 성립하려면 단위 작업이 수십 ms 여야 한다. 실제로는 크롬/Windows(ANGLE→D3D11 FXC)에서 URP Lit 베리언트
하나가 평균 1.8초, 큰 것은 10초를 넘었다. 4개를 묶으면 한 프레임이 수십 초다. 결국 같은 235초를 로딩 화면에서 월드
씬으로 옮긴 것뿐이었고, 월드 씬에서 블로킹되니 NGO 하트비트까지 끊겨 더 나빠졌다.

워밍업을 전부 제거하고 실제 사용되는 베리언트만 온디맨드 컴파일하도록 되돌렸다. 30초 안에 진입한다.
에디터는 셰이더 캐시와 병렬 컴파일 때문에 어느 쪽도 재현되지 않으므로 판정 기준을 빌드로 옮겼다.
접속 완료가 클릭 기준 30초 이내, longtask 최대 5초 미만.

## 7. 적응형 vSync — 관측값이 부하에 왜곡되면 제어가 진동한다

**6초 주기 120↔60Hz 왕복과 20초 주기 vSync 2↔1 왕복을 각각 제거.**

사용자가 며칠째 프레임이 오르내린다고 보고했는데, 원인이 프레임을 조절하려고 넣은 로직 자체였다.

첫째는 관측값 왜곡이다. 주사율 프로브가 rAF 간격의 하위 10% 분위수로 리프레시 레이트를 추정하는데, 메인 스레드가
프레임마다 18~25 ms 를 쓰면 rAF 는 16.7 ms 배수로만 찍힌다. 최소 표본조차 16.7 ms 라 120Hz 디스플레이가 60Hz 로 읽힌다.
그 오판이 판정을 리셋하고 vSyncCount 를 되돌려 무한 왕복이 됐다.
해결은 방향별로 신뢰 조건을 나눈 것이다. 하향 판독은 미스율 5% 미만일 때만 수용하고, 상향은 부하로 만들 수 없는
값이라 항상 수용한다.

둘째는 승급 조건이다. 주사율 왕복이 사라지자 vSync 2↔1 왕복이 드러났다. 승급 판정이 현재 프레임 예산 기준 미스율만
봤기 때문이다. vSync 2(예산 16.7 ms)에서 10~17 ms 프레임은 미스가 0~1% 지만, 승급 후 예산 8.3 ms 기준으로는 대부분
미스다. 현재 상태를 버티는가와 다음 상태를 버티는가는 다른 질문인데 같은 지표로 답하고 있었다.
승급은 승급 후 예산으로, 강등은 현재 예산으로 평가하도록 분리했다.

검증 기준도 같이 정했다. 릴리스 빌드 60초 콘솔에서 vSyncCount 변경 2회 이하.

## 8. 품질 저하 로직의 트리거를 인원 수에서 프레임타임으로

**고정 24기 상한 제거. 22 ms 초과 시에만 45프레임마다 2기씩 감축, 하한 16기, 16 ms 이하 회복 시 복원.**

드로우콜을 줄이려고 근거리 24기 고정 상한을 넣었더니, 프레임에 여유가 있는 환경에서도 25번째부터 렌더링되지 않아
축제 밀도가 실제보다 낮아 보였다. 상한의 기준이 인원 수뿐이라 비용 발생 여부와 무관하게 항상 같은 수를 잘랐다.
성능을 위한 로직인데 트리거가 성능 지표가 아니었다.

상한을 평활 프레임타임이 결정하도록 바꿨다. 감축과 복원 임계값을 22 ms 와 16 ms 로 벌려 히스테리시스를 뒀다.

## 9. 헤드리스 서버에서 렌더링 리소스 차단

**접속자 수만큼 생성되던 서버 런타임 머티리얼 0개. 아바타 렌더러 11개 → 7개/아바타.**

데디케이티드 서버는 리눅스 헤드리스인데 아바타 조립 경로를 클라이언트와 공유해서 접속자마다 머티리얼을 생성하고
있었다. 셰이더가 스트립된 빌드라 생성할 때마다 경고가 부스 수만큼 반복돼 실제 로그를 덮기도 했다.

판정 기준이 핵심이었다. `#if UNITY_SERVER` 는 빌드 타깃이 Dedicated Server 면 에디터에도 정의되고,
`Application.isBatchMode` 는 `-nographics` 없이 `-batchmode` 만 주면 디바이스가 살아 있다.
판단하려는 것이 정확히 렌더 타깃이 있는가이므로 `SystemInfo.graphicsDeviceType == Null` 로 판정했다.

콜라이더와 트랜스폼은 남겼다. 서버의 충돌 권위라 같이 걷어내면 벽 뚫림이 재발한다.

## 10. 측정 — 틀린 방법으로 얻은 수치를 철회한 기록

**측정 순서가 결과를 만든다.** 거리 기반 애니메이터 갱신 조절을 −17% 개선으로 적었다가 철회했다.
40기 스폰 직후에는 아무 조작 없이도 프레임타임이 계속 수렴하는데 그 변화를 개선으로 읽었다. 조건을 번갈아 재니
ON 10.25 ms / OFF 10.34 ms 로 차이가 0.09 ms 였고, 같은 조건의 회차 간 변동폭 2.8 ms 가 개선이라 부른 값보다 컸다.
코드는 스위치로 끌 수 있어 남겼지만 수치 주장은 철회했다. 이후 A/B 를 교차로 재고 회차 간 변동폭보다 큰 차이만
개선으로 인정한다.

**에디터와 빌드는 같은 지표가 아니다.** 에디터 451과 빌드 483을 나란히 놓은 적이 있는데 후자는 그림자와 UI 패스를
포함한 WebGL API 호출 수다. 자릿수 일치로 에디터 측정의 타당성만 뒷받침하고 같은 값으로 쓰지 않는다.

**절감은 사용자가 내려받는 양으로 적는다.** 아바타 UI 텍스처에서 에셋 기준 61.4 MB 를 줄였는데 빌드 총량은
8.0 MB 만 줄었다. `.data.unityweb` 가 내부적으로 압축돼서 무압축 RGBA32 는 에셋 인벤토리에서만 크게 잡힌다.
에셋 수치를 빌드 성과로 옮겼으면 7배 부풀린 보고가 됐다.

**측정 직전 조건을 확인한다.** 탭이 백그라운드면 브라우저가 rAF 를 스로틀링해 0.1 FPS 같은 값이 찍힌다.
읽기 직전마다 `document.hidden` 과 rAF 60프레임을 확인하지 않으면 스로틀링을 성능으로 오독한다.

## 11. 채택하지 않은 것 — 라이트맵 베이크

**실시간 광원 29 → 1개, 기준 대비 휘도 0.996배까지 맞췄으나 철회.**

베이크 전에 규모부터 확인했다. 전나무가 라이트맵 예산의 96%(92개 렌더러)를 점유하고 있었고, 제외하니 아틀라스
12장 → 1장, 베이크 시간 48초가 됐다.

휘도는 0.71 → 0.59 → 0.76 → 0.977 → 0.996배로 회복시켰는데 로비 전역에 각진 아티팩트가 남았다.
가설 네 개(총 텍셀·트라이앵글당 텍셀·메시 노멀·UV2 패킹)를 전부 실측으로 기각했지만 원인을 특정하지 못해 철회했다.

성능은 이미 오클루전 컬링만으로 드로우콜 79% 를 시각적 부작용 없이 확보한 상태였다. 얻는 것보다 잃는 것이 컸다.

## 12. 플랫폼 제약에서 나온 구조 결정

**텍스트 입력과 외부 페이지는 웹 레이어가 맡는다.** Unity 는 트리거만 보낸다. WebGL 에서 한글 IME 조합 문자를
안정적으로 받기 어렵고, iframe 차단 시 새 탭 폴백도 웹 쪽에서만 처리할 수 있다.

**음성은 브라우저 WebRTC 로 처리한다.** Unity WebGL 은 마이크 입력을 받을 수 없다. 게임 서버를 경유시키면 지연과
서버 부하가 같이 늘어난다.

**영구 상태의 소유권은 게임 서버에 두지 않는다.** 코인과 부스 임대는 백엔드가 단일 진실 원천이고 게임 서버는
실시간 상태만 권위를 갖는다. 두 곳에서 쓰면 세션이 끊길 때 정합성을 판단할 근거가 없어진다.

**정적 월드 오브젝트에는 NetworkObject 를 붙이지 않는다.** 부스 구조물과 게임기는 월드 고정물이고 상호작용 판정은
로컬에서 한다.

## 13. 에디터에서 통과해도 빌드에서 깨지는 것들

| 항목 | 증상 | 원인 |
|---|---|---|
| `Task.Delay` | 로딩이 완료되지 않음 | WebGL 에서 완료되지 않는다. `Awaitable` 로 대체 |
| `Application.targetFrameRate` | 120Hz 디스플레이에서 무효 | rAF 기반이라 vSyncCount 로 제어해야 한다 |
| 셰이더 프리로드 | 로딩 1~2분 블로킹 | 메인 스레드 동기 컴파일 |
| NPOT 텍스처 | RGBA32 무압축으로 편입 | POT 가 아니면 블록 압축 불가 |
| 밉맵 + NPOT | DXT 지정이 무시됨 | 한 단계 큰 POT 로 리사이즈해 해결 |

마지막 항목은 안내판 텍스처에서 나왔다. 판 17장 런타임 메모리 58 MB → 19 MB.
