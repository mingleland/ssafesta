게임 파트(@gudtnslwkd) 회신입니다. §8-1 이 요청한 **파츠 변경 통보**를 먼저 드리고, 확인한 사항 두 건을 붙입니다. §8-2 가격표는 기획 협의 후 별도로 회신하겠습니다.

## 1. §8-1 통보 — 파츠가 늘지 않고 **줄었습니다** (남성 3종)

§8-1 은 "파츠를 추가하면 알려주세요" 라고 하셨는데, 실제로 생긴 변경은 **반대 방향**입니다. 남성 팔레트에서 여성복 3종을 뺐습니다 (치마·크롭 계열이 남성 캐릭터에 나온다는 지적, `S15P21A604-355` 작업 중).

| 품목 | 슬롯 | `assetKey` | V16 시드 |
|---|---|---|---|
| `M_Bot.03` | BOTTOM | `1814256283` | `price 100`, `is_on_sale TRUE` |
| `M_Top.07-A` | TOP | `356384796` | `price 100`, `is_on_sale TRUE` |
| `M_Outfit.03` | OUTFIT | `415781343` | `price 100`, `is_on_sale TRUE` |

빼는 방식은 **`AvatarCatalog.asset` 의 `items` 배열에서 참조만 제거**했고, `.asset` 파일 3개는 디스크에 그대로 남겨 뒀습니다(105개 유지).

### 그래서 지금 "살 수는 있는데 입을 수 없는 상품" 3종이 생겼습니다

- `GET /api/v1/catalog/items?type=AVATAR_PART` 는 97종을 그대로 내려주므로 이 3종도 `onSale: true` 로 나옵니다 → 상점에서 구매가 가능합니다(`201`).
- 그런데 Unity 팔레트가 이 3종을 **그리지 않습니다**. 산 사람이 착용할 화면상의 경로가 없습니다.
- 코인은 차감되고(`coin_ledger_entries` 에 `PURCHASE` 기록) 착용은 불가능한 상태라, 환불 문의가 될 수 있습니다.

### `AvatarCatalogSeedContractTest` 는 이 어긋남을 잡지 못합니다

확인해 보니 이 테스트는 **디스크의 `.asset` 파일 목록**을 읽고 `AvatarCatalog.asset` 은 `filter` 로 **명시적으로 제외**합니다.

```java
.filter(path -> !path.getFileName().toString().equals("AvatarCatalog.asset")).toList()
...
assertEquals(105, assetCount, ...);
assertEquals(97, unityKeys.size(), ...);
```

`.asset` 파일 3개를 남겨 뒀으므로 `assetCount` 는 여전히 105 이고 **테스트는 통과합니다.** 즉 §8-1 이 기대한 "파츠가 늘면 테스트가 먼저 깨진다" 는 안전망이, **팔레트에서 빠지는 방향에는 걸리지 않습니다.** 실제로 판매 가능 여부를 정하는 것은 `.asset` 파일의 존재가 아니라 `AvatarCatalog.asset` 의 `items` 배열인데 테스트가 보는 것은 전자입니다.

처리 방향 두 가지 중 어느 쪽이 좋을지 의견 부탁드립니다.

- **(가)** 이 3종을 `is_on_sale FALSE` 로 내린다 — 시드 한 줄 `UPDATE`. §2-1 표의 4행("미보유 · 판매 중지 → 잠금, 구매 버튼 없음")에 그대로 들어맞고 계약 변경이 없습니다.
- **(나)** 테스트 기준을 `AvatarCatalog.asset` 의 `items` 배열로 바꾼다 — 안전망이 실제 판매 단위를 보게 되지만, 앞으로 Unity 배열을 건드릴 때마다 BE 테스트가 깨집니다.

(가)로 가면 앞으로 팔레트에서 파츠를 뺄 때도 제가 `is_on_sale` 내림 요청을 같이 드리겠습니다.

## 2. 확인 — 시드는 `V16` 으로 들어와 있습니다 (`V17` 아님)

§4 에 seed 위치가 `V17__avatar_catalog_seed.sql` 로 적혀 있는데, `origin/develop` 에 실제로 있는 것은 **`V16__avatar_catalog_seed.sql`** 입니다. `V17` 은 `V17__ai_documents_upload.sql` 이 이미 쓰고 있습니다. 테스트도 `/db/migration/V16__avatar_catalog_seed.sql` 을 읽고 있어 코드는 일관됩니다 — **이슈 본문의 번호만 오타로 보입니다.** 다른 파트가 §4 를 보고 `V17` 을 찾다가 헤맬 수 있으니 본문 수정만 부탁드립니다.

## 3. §8-1 Unity 작업 — 하겠습니다. `owned` 기준으로 갑니다

현재 제 브랜치(`S15P21A604-355`)에는 커스터마이징 잠금 UI(흐린 프리뷰 + 잠금 배지 + 잠긴 항목 클릭 시 안내)가 이미 들어가 있습니다. 다만 잠금 판정을 **Unity `.asset` 의 자체 플래그로 계산**하고 있어서, §2-1 의 "클라이언트는 `price` 나 보유 목록으로 이 값을 다시 계산하지 마십시오" 를 위반합니다.

그래서 그 플래그를 걷어내고 `GET /api/v1/catalog/items?type=AVATAR_PART` 의 `owned` 하나로 분기하도록 바꾸겠습니다. 함께 맞출 것:

- **조회 응답에 있는 품목만 그립니다** (§2-1 권고). 위 1번의 3종은 자연히 안 그려집니다.
- 저장 실패 시 `409 AVATAR_ITEM_NOT_OWNED` 의 `errors[].objectId` 로 팔레트 항목을 짚어 표시하겠습니다 (§3).
- 게스트는 잠금 클릭 시 구매가 아니라 **로그인 유도**로 보냅니다 (§2-1).
- 조회 실패 시 조용히 전량 개방으로 떨어지지 않게 하겠습니다 — 로그 + 에러 상태로 드러냅니다 (헌법, T-24 재발 방지).

별도 Jira 이슈를 만들어 진행하고 이슈 번호를 여기에 남기겠습니다.

## 4. §8-2 무료 세트 — 실측 수치 공유 (확정 의견은 별도 회신)

가격 확정은 기획(@dream_hyeon) 몫이지만, 화면을 만드는 쪽에서 실측한 숫자를 근거로 남깁니다. **현재 무료 12종은 슬롯마다 정확히 1종씩입니다.**

| 슬롯 | 전체 | 무료 |
|---|---|---|
| HAIR | 31 | **1** |
| TOP | 26 | 2 (성별 각 1) |
| BOTTOM | 12 | 2 (성별 각 1) |
| HEAD (얼굴형) | 8 | 2 (성별 각 1) |
| OUTFIT | 8 | 2 (성별 각 1) |
| SHOES | 7 | **1** |
| HAT | 3 | **1** |
| GLASSES | 2 | **1** |

성별로 나누면 무료 사용자는 **얼굴형 1종 · 헤어 1종 · 상의 1종 · 하의 1종 · 한벌 1종 · 신발 1종 · 모자 1종 · 안경 1종**을 갖습니다. 즉 **같은 성별의 무료 사용자는 전원 똑같이 생깁니다** — 커스터마이징 화면에서 바꿀 수 있는 것이 사실상 색상뿐이고, 97종 중 85종에 잠금 배지가 붙습니다.

코인 유입이 신규 200 · 일일 50 이고 가격이 100 이므로 **가입 직후 살 수 있는 것은 2종**입니다. 첫 진입 인상이 "전원 동일 아바타 + 잠금 도배" 가 됩니다.

검토 중인 방향은 **정체성 슬롯(얼굴형·헤어)을 열고 옷을 파는 쪽**입니다. 예를 들어 HEAD 8종 전부와 HAIR 8종을 무료로 두면 무료가 12 → 26 종이 되고 유료는 71종이 남아 코인 소비처는 유지됩니다. 기본 상하의·신발이 이미 무료라 나머지가 잠겨 있어도 **옷을 입은 상태로 시작**하므로 손상이 없습니다.

다만 이건 아직 게임 파트 내부 검토 단계이고 확정 의견이 아닙니다 — 위 수치는 근거 자료로만 봐 주시고, 게임 파트 입장은 정리해서 별도로 회신하겠습니다.

어느 쪽으로 정해지든 **Unity 작업은 추가로 필요하지 않습니다.** Unity 는 `owned` 만 읽으므로 시드 `UPDATE` 한 번으로 반영됩니다.

## 5. §1 spec 013 C-06 뒤집기

C-06("MVP 는 전체 개방, 미보유 차단 없음", 2026-08-12 리드 확정)이 `docs/26_팀_결정_필요사항.md` 66행에 확정으로 기록돼 있습니다. 이미 확정된 항목을 뒤집는 것이라 게임 파트가 단독으로 동의 처리할 사안은 아니라고 봅니다(헌법 30조). `docs/26` 기록 시 **리드 재확인**을 함께 받아 주시면 좋겠습니다.

구현 방식 자체에서 게임 파트가 발견한 기술적 문제는 현재까지 없습니다 — 미보유 차단은 상점이 있는 이상 필요하고, §8-2 에서 가격을 조정하면 개방 정도가 코드 변경 없이 움직이게 설계돼 있어(§1) 되돌릴 여지도 남아 있습니다. 승인 여부는 위 재확인 절차를 거친 뒤에 말씀드리겠습니다.
