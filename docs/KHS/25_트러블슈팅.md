### T-187. 스크립트로 만든 발광 재질이 어느 순간 전부 안 빛나고 있었다 — _EMISSION 키워드 (2026-08-22, 해결)

- **증상**: 야시장이 전체적으로 칙칙하다. 가로등 헤드가 발광값을 아무리 올려도 램버트
  음영이 지는 "칠해진 구슬"이고, 줄전구 155개도 마찬가지였다.

- **원인**: URP Lit 의 발광은 `_EmissionColor` 값만으로는 안 켜진다 — **`_EMISSION`
  셰이더 키워드**가 함께 켜져 있어야 한다. 생성 시점에는 `EnableKeyword` 를 호출했지만,
  이후 다른 스크립트 패스에서 재질을 다시 만지는 동안 키워드가 풀렸고
  (`giFlags=EmissiveIsBlack` 상태로 발견), 값(`_EmissionColor` = 16배)은 멀쩡히
  들어 있어서 **인스펙터 숫자만 보면 정상으로 보였다.**

- **해결**: 발광 재질 6종 전부 `EnableKeyword("_EMISSION")` +
  `globalIlluminationFlags = RealtimeEmissive` 재적용.

- **예방**: 스크립트로 발광 재질을 만들거나 수정한 뒤에는 값이 아니라
  **`material.IsKeywordEnabled("_EMISSION")` 을 검증**한다. 값은 키워드가 꺼져 있어도
  저장되므로 증거가 되지 못한다.

- **곁들여**: 에디터 확인 없이 밝기를 두 배씩 올리는 삽질을 여러 번 했다 — 원인이
  키워드였으므로 전부 헛손질이었다. "값을 올려도 변화가 없다" 는 순간 키워드부터 본다.

### T-186. 맵 구버전 124 MB 를 히스토리에서 걷어냈다 — 범위 판정과 검증 절차 (2026-08-22, 해결)

- **배경**: `.git` 이 592 MB 였고 그중 **11층 맵이 5벌**(156 MB) 들어 있었다. 워킹트리에는
  1벌(31.7 MB)만 있고 나머지는 지웠는데도 히스토리에 남아 있었다. 4일 만에 5번 교체됐고
  **매번 파일명이 달라서**(`11th.skp` → `11th-0818.fbx` → `11th-0819.fbx` → …) git 이
  전부 별개 파일로 보관했다.

- **범위 판정이 결론을 뒤집었다.** 처음에는 "팀 전원 재클론 + 열린 PR 2개 깨짐" 이라
  하지 말자고 판단했다. 실제로 재보니 아니었다.

  | 확인 | 명령 | 결과 |
  |---|---|---|
  | 어느 브랜치에 있나 | `git branch -r --contains <추가커밋>` | 맵 4개 전부 `origin/game` 전용 |
  | game 이 머지됐나 | `git merge-base --is-ancestor origin/game origin/main` | 아직 안 됨 |
  | 다른 브랜치를 삼켰나 | `git merge-base --is-ancestor origin/<b> origin/game` | main/develop/front/back/ai 전부 무관 |

  → `origin/main..game` 110개 커밋만 재작성하면 되고, 열린 PR(`codex/*`)·다른 브랜치·
  `main` 은 건드리지 않는다. **반면 Sidekick 아바타(34 MB)·Rukha93(25 MB)는 `main` 포함
  전 브랜치에 있어 범위에서 제외했다** — 그건 정말 팀 전원이 재클론해야 한다.

- **검증은 트리 해시로 한다.** 재작성 전 `git rev-parse game^{tree}` 를 적어 두고,
  재작성 후 같은 값이면 **파일 내용이 하나도 안 바뀌었다는 증거**다. 커밋 SHA 는 당연히
  바뀌므로 그것으로는 확인할 수 없다.

  ```
  재작성 전/후  dd94557e6865b77fe80ca379ba40c67e72f7159b   ← 일치
  현재 맵 파일  2개 (0821 skp + meta)   구버전 잔존  0개
  ```

- **결과**: `.git` **592 MB → 494 MB**. force-push 후 `rm -rf .git/refs/original` +
  `git reflog expire --expire=now --all` + `git gc --prune=now` 까지 해야 실제로 줄어든다
  (재작성만으로는 옛 커밋이 `refs/original` 과 reflog 에 붙들려 있다).

- **함정 1 — PowerShell 에서 실행하면 안 된다.** Windows PowerShell 5.1 은 `&&` 를 모르고,
  더 위험한 것은 `--index-filter ..."경로"...` 처럼 **작은따옴표 안에 큰따옴표가 든 인자**를
  네이티브 명령에 넘길 때 제대로 이스케이프하지 못한다. 조용히 잘못된 인자로 실행될 수
  있다. `bash` 로 들어가서 했다.

- **함정 2 — 워킹트리가 깨끗해야 한다.** `filter-branch` 는 미커밋 변경이 있으면 거부한다.
  씬 편집분을 스태시했다가 끝나고 되돌렸는데, **이 저장소에는 예전 스태시가 2개 더 쌓여
  있어서** `git stash pop` 을 한 번 더 치면 500개 파일짜리 엉뚱한 스태시가 풀린다.
  스태시는 넣은 직후에 꺼내고, 중간에 다른 stash 명령을 끼우지 않는다.

- **예방**: 모델러가 새 맵을 보내면 **파일명을 바꾸지 말고 같은 이름으로 덮어쓴다.**
  이번 156 MB 는 전적으로 이름이 매번 달라서 생긴 비용이다. 백업 브랜치
  `origin/backup/game-before-history-purge-20260822` 는 며칠 뒤 삭제한다.

### T-185. 에셋스토어 팩은 기본 설정이 틀려 있다 — 4K 참조, 노멀맵 미지정, 데이터 맵 sRGB (2026-08-22, 해결)

Carnival & Funfair Stalls (3DreaMax, 984 MB / 423 파일) 병합 중 확인한 것들. **에셋스토어
팩을 그대로 쓰면 안 되는 이유**가 한 팩에 다 들어 있어서 남긴다.

- **증상 1 — 용량.** 984 MB 중 실제로 쓰이는 것은 155 MB 뿐이었다. 벤더가 모든
  파이프라인(BuiltIn/HDRP/URP)과 모든 해상도(2K/4K)를 다 넣어 주기 때문이다.

- **증상 2 — URP 머티리얼이 4K 를 물고 있었다.** 2K 세트(213 MB)가 통째로 놀고 있었다.
  `AssetDatabase.GetDependencies` 로 재보니 URP 프리팹 48개가 4K 48장(414 MB)만 참조했다.
  머티리얼의 `m_SavedProperties.m_TexEnvs` 를 훑어 같은 파일명의 2K 로 바꿔 끼웠다(59곳).

- **증상 3 — 텍스처 임포트 설정이 전부 틀려 있었다.** 48장이 예외 없이
  `textureType = Default`, `sRGBTexture = true` 였다.

  | 접미사 | 벤더 설정 | 옳은 설정 | 틀리면 |
  |---|---|---|---|
  | `_Normal` ×11 | Default / sRGB | **NormalMap** / linear | 압축·언팩 방식이 달라 굴곡이 틀어진다 |
  | `_AO` ×11 | sRGB | **linear** | 차폐가 감마 보정돼 과하게 어두워진다 |
  | `_Metallic` ×11 | sRGB | **linear** | 금속감·매끄러움이 어긋난다 |
  | `_BaseColor` ×11 | sRGB | sRGB (맞음) | |
  | `_Emissive` ×4 | sRGB | sRGB (맞음) | |

  **조용히 틀린다** — 에러도 경고도 안 나고 그냥 재질이 이상해 보일 뿐이다.

- **판정은 `AssetDatabase.GetDependencies` 로 한다.** 이 팩은 프리팹→머티리얼→텍스처가
  3단이라 GUID 텍스트 검색으로는 무엇이 살아 있는지 알 수 없다. 삭제 전에 `_Project`
  전체(370개 에셋)를 훑어 벤더 폴더를 참조하는 것이 0개임을 확인하고 지웠다.

- **삭제는 커밋 전에 한다.** 984 MB 를 커밋한 뒤 지우면 히스토리에 영원히 남는다.
  이 저장소는 `.git` 이 이미 464 MB 이고 **Git LFS 가 설정돼 있지 않다**(`.gitattributes` 없음).
  untracked 인 동안 828 MB 를 지워 히스토리 유입을 막았다.

- **소스 크기와 빌드 크기는 별개다.** 저장소에 들어가는 것은 PNG 원본 크기이고, 빌드에
  들어가는 것은 `maxTextureSize`·압축이 결정한다. WebGL 타깃이라 1024 로 낮췄다 —
  2048 대비 텍스처 런타임 메모리가 1/4 이 된다 (현재 87 MB). 원본은 2K 로 남겨 뒀으므로
  설정만 되돌리면 언제든 복구된다.

- **예방**: 에셋스토어 팩을 넣으면 커밋 **전에** ① 안 쓰는 파이프라인·해상도 제거
  ② `GetDependencies` 로 실사용 판정 ③ 노멀맵 타입·데이터 맵 색공간 확인
  ④ 타깃에 맞는 `maxTextureSize` — 이 넷을 먼저 한다.

### T-184. 점프가 몸보다 늦게 나왔다 — Mixamo 클립 앞 0.5초가 웅크림이었다 (2026-08-22, 해결)

- **증상**: 스페이스바를 누르면 **몸이 먼저 뜨고 애니메이션이 나중에** 나온다. 뛰는 자세가 전혀 안 맞는다.

- **원인**: `Jumping.fbx`(Mixamo, 1.90초 / 57프레임)를 **자르지 않고 통째로** Jump 상태에 넣었다.
  루트 높이 커브(`RootT.y`)를 뽑아 보면 클립 자체의 구조가 이렇다.

  | 구간 | 프레임 | 시간 | 내용 |
  |---|---|---|---|
  | 웅크림 | 0~14 | 0.000~0.500s | 무릎 접고 준비 |
  | 도약 | 15 | 0.500s | 발이 뜬다 |
  | 정점 | 23 | 0.767s | |
  | 착지 | 34 | 1.133s | 발이 닿는다 |
  | 착지 흡수 | 34~51 | 1.133~1.700s | 깊게 앉았다 복귀 |

  우리 물리는 스페이스바에 **즉시** 도약하는데 클립은 t=0 부터 재생됐다. 즉 상승하는
  0.5초 동안 화면에는 준비 동작(웅크림)이 나오고, 클립이 겨우 발을 뗄 때(0.5s)
  물리는 이미 착지 직전(체공 0.61초)이었다. 애니메이션이 늦은 게 아니라 **애니메이션의
  0.5초가 통째로 낭비**되고 있었다.

- **해결**: 두 가지를 같이 맞췄다 — 하나만 해도 안 맞는다.

  1. **클립을 자른다.** `clipAnimations` 서브클립 `Jump` = **f15~f40** (도약 → 착지 흡수 최저점).
     0.833초. 앞의 웅크림을 버리므로 클립 첫 프레임이 곧 도약 자세다.
  2. **물리를 클립에 맞춘다** (반대로 하면 또 어긋난다). 클립 체공은 f15~f34 = **0.633초**.
     `v = g·T/2 = 98.1 × 0.633 / 2 = 31.1` 로 두면 포물선과 포즈가 프레임 단위로 겹친다.
     도달 4.9 unit = 0.49 m.

  착지 흡수는 별도 상태를 만들지 않았다 — Jump 상태에서 나가는 블렌드를 0.15초로 늘리면
  그 동안 클립이 f34 이후로 계속 재생돼 무릎 접기가 자연히 보인다.

- **함정 1 — `LoadAllAssetsAtPath` 는 숨은 프리뷰 클립을 준다.** 처음에
  `.OfType<AnimationClip>().FirstOrDefault()` 로 집었더니 `__preview__mixamo.com`(1.90초, 트림 전
  원본)이 나와서 Animator 의 Jump 상태를 **원본에 다시 연결**해 버렸다. `HideFlags.HideInHierarchy`
  와 `__preview__` 접두사로 걸러야 한다.

- **함정 2 — 서브클립을 만들 때 루트 모션 플래그를 손으로 고르지 않는다.**
  `defaultClipAnimations[0]` 을 물려받아 `firstFrame`/`lastFrame` 만 바꿨다. 현재 값은
  `lockRootHeightY=False`(Bake Into Pose 꺼짐) 인데, 이걸 켜면 클립의 수직 이동이 포즈에
  남아 **CharacterController 의 상승과 겹쳐 두 배로 뜬다**. Animator 는
  `applyRootMotion = false` 이므로 지금 설정이 맞다 — 물리가 올리고 클립은 자세만 준다.

- **예방**: 애니메이션 클립을 새로 붙일 때는 **먼저 `RootT.y` 커브를 떠서 도약·착지 프레임을
  재고**, 그 체공 시간에 물리 파라미터를 맞춘다. 클립 길이를 그대로 믿으면 안 된다 —
  Mixamo 클립은 앞뒤에 준비·회복 동작이 붙어 있는 것이 기본이다.

- **곁들여 고친 것 — 접지 끊김에 점프 포즈가 번쩍이는 문제.** `_airborne` 이 "접지 아님"
  전부였으므로 바닥 이음새·경사에서 한두 프레임 접지가 끊길 때마다 점프 자세가 튀었다.
  의도한 도약(`_jumped`)이 아니면 `AirborneAnimGrace = 0.12초` 유예 뒤에 공중 포즈로 넘긴다.

- **후속 (같은 날) — "애니메이션 속도랑 점프 속도 자체도 너무 빨라".** 위 수정으로 타이밍은
  맞았지만 전체가 눈으로 읽히기 전에 끝났다. 원인은 **현실 중력**이다. `_gravity = 98.1`
  (= 9.81 m/s² × 10)에서 체공은 도달 높이로 완전히 결정된다 — `T = √(8h/g)`. 0.6 m 를
  뛰면 0.70초, 체공을 0.9초로 늘리려면 **1 m 를 뛰어야** 하는데 로비 천장에 맞지 않는다.

  그래서 게임들이 하는 대로 **도약 구간만 중력을 낮췄다**: `_jumpGravity = 59`,
  `_jumpSpeed = 26.5` → 체공 0.898초, 도달 0.60 m. 발판에서 그냥 벗어나는 낙하는
  `_gravity = 98.1` 을 그대로 쓴다 (`_jumped` 로 구분).

  애니메이션도 같이 늦춰야 한다 — 안 그러면 다시 어긋난다. Jump **상태의** speed 를
  `0.633 / 0.898 = 0.705` 로 두면 오차 0 ms 로 겹친다 (`Animator.speed` 는 전역
  배율이라 여기 쓰면 안 된다 — 상태 speed 가 그것을 다시 곱한다).

  체공·애니메이션 모두 이전의 **1.42배**로 느려졌다.

- **곁들여 — Jump 를 "걷는 중" 으로 신고하던 것.** `moving = state != Idle` 이라 Jump 일 때
  `IsWalking = true` 가 됐다. 이 컨트롤러에는 `IsWalking` 으로 걸린 Idle↔Walk 트랜지션이
  있어서 제자리 점프 시 Idle→Walk 가 동시에 유효해진다. 진행 중인 크로스페이드는
  그래프 트랜지션에 끊기지 않으므로(interruptionSource 기본 None) 지금 증상은 없지만,
  상태를 거짓으로 알리는 것 자체가 함정이라 `Walk || Run` 으로 좁혔다.

- **재발 (3회) — 원인을 잘못 짚고 있었다.** 트림·속도를 두 번 손봤는데 증상이 그대로였다.
  "몸이 올라간 다음 애니메이션이 나온다." 놓친 것은 이것이다.

  **트림 지점을 `RootT.y`(엉덩이 높이)로 정했는데, 그 커브는 화면에 나오지 않는다.**
  Animator 가 `applyRootMotion = false` 이므로 루트 수직 이동은 추출돼 버려진다.
  실제로 보이는 것은 **엉덩이 기준의 다리 포즈**뿐이다.

  그래서 도약 프레임(f15)부터 재생하면 시작 포즈가 "다리 펴고 선" 자세이고, 눈에
  보이는 동작(다리 접기)은 f18~f23 = 0.1~0.3초 뒤에 나온다. 그 사이 몸은 물리로 이미
  올라가고 있다 — 증상과 정확히 일치한다. **발 구르기를 잘라낸 것이 원인이었다.**

- **최종 해결 — 선행 동작을 몸보다 먼저 낸다 (2단 구성).** 게임에서 점프가 점프로 읽히는
  이유는 도약 전에 발을 구르기 때문이다. 클립을 두 개로 쪼갰다.

  | 상태 | 프레임 | 클립 | speed | 실제 재생 | 루트 Y 베이크 |
  |---|---|---|---|---|---|
  | `Jump_Launch` | f7~f15 | 0.267s | 2.051 | **0.130s** | **켬** |
  | `Jump_Air` | f15~f40 | 0.833s | 0.705 | 1.182s (체공 0.898s) | 끔 |

  `PlayerMovement` 는 스페이스를 받으면 **애니메이션만 먼저** 시작하고
  (`_jumpPending`), `JumpAnticipation = 0.13초` 뒤에 도약한다. 즉 화면에 항상
  애니메이션이 **먼저** 나온다.

- **루트 Y 베이크를 두 클립에서 반대로 둔 이유.** 서브클립마다 따로 지정할 수 있다.
  - `Jump_Launch` 는 **켠다**. 웅크릴 때 엉덩이가 내려가고 발이 바닥에 붙어 있어야 한다.
    끄면 루트가 추출돼 엉덩이는 그대로고 다리만 굽어 **발이 떠 보인다**.
  - `Jump_Air` 는 **끈다**. 켜면 클립의 상승이 CharacterController 상승에 겹쳐 두 배로 뜬다.
  - 이음새(f15)에서 `RootT.y` 는 f0 대비 +0.0286 뿐이라 단차는 무시할 수준이다.

- **`JumpAnticipation` 과 `Jump_Launch` 재생 시간은 한 쌍이다.** 한쪽만 바꾸면 도약
  순간이 다시 어긋난다. 재생 시간 = (lastFrame − firstFrame) / 30 / state.speed.

- **교훈**: 루트 모션을 끈 상태에서 클립을 자를 때 `RootT.y` 로 구간을 판단하면 안 된다.
  그 커브는 버려지는 값이다. **보이는 것은 관절 포즈**이므로, 자를 구간은 "눈에 보이는
  동작이 언제 시작하는가" 로 정해야 한다.

- **후속 — "너무 뚝 끊기면서 점프뛰고 높이가 되게 낮아졌네".** 선행 동작을 넣은 방식이
  거칠었다. 두 가지가 같은 원인에서 나왔다.

  `Jump_Launch` 를 **f7 부터 0.03초 블렌드로** 넣었는데, f7 은 이미 엉덩이가
  `RootT.y` 0.7024(rest 0.9431 대비 **-0.24**) 인 **깊은 웅크림**이다. 선 자세에서 거기로
  0.03초에 건너뛰니 순간이동처럼 뚝 끊긴다. 그리고 그 웅크림은 최저 -0.34 까지 내려가는데
  (루트 Y 를 포즈에 베이크했으므로 화면에 그대로 나온다) 도약 높이가 0.60 m 였으니
  **웅크린 깊이가 도약 높이의 3분의 1 이상**이라 낮게 보였다.

  | | 이전 | 이후 |
  |---|---|---|
  | Jump_Launch 구간 | f7~f15 (0.267s) | **f6~f15 (0.300s)** |
  | Jump_Launch speed | 2.051 | **1.250** |
  | 선행 동작 시간 | 0.130s | **0.240s** |
  | 들어가는 블렌드 | 0.03s | **0.10s** |
  | Launch→Air 블렌드 | 0.03s | **0.06s** (베이크 반대라 3 cm 단차) |
  | 착지 블렌드 | 0.15s | **0.25s** |
  | 도약 속도 / 중력 | 26.5 / 59 | **40.2 / 90** |
  | 도달 | 0.60 m | **0.90 m** |
  | 체공 | 0.898s | 0.893s (거의 그대로) |

  체공을 그대로 두고 높이만 1.5배로 올렸기 때문에 `Jump_Air` 재생 속도(0.709)는
  건드리지 않았다 — 애니메이션 속도는 이미 맞다는 확인을 받은 값이다.

- **선행 동작을 조일 때 같이 움직여야 하는 값이 넷이다**: 클립 구간, state speed,
  `JumpAnticipation`, 들어가는 블렌드. 앞의 셋 중 하나만 바꾸면 도약 순간이 어긋나고,
  블렌드만 짧게 두면 자세가 뚝 끊긴다.

- **남은 한계**: 체공이 0.833초를 넘으면(높은 데서 떨어지면) 클립이 끝나 **착지 흡수 자세로
  공중에 멈춘다.** 정석은 낙하 루프를 분리하는 것이다. 지금 맵은 평면이라 보류.

### T-183. 근접 숨김이 "꺼 둔 렌더러" 를 되살려 발밑에 회색 봉이 따라다녔다 (2026-08-21, 해결)

- **증상**: 아바타 발밑에 회색 봉 같은 물체가 따라다니고, 접지 그림자는 보이지 않는다.

- **원인 1 — 내가 만든 버그.** 직전에 넣은 카메라 근접 숨김(`UpdateSelfVisibility`)이 복귀할 때
  **모든 렌더러를 무조건 켰다.**

  ```csharp
  foreach (var r in GetComponentsInChildren<Renderer>(true))
      r.enabled = !shouldHide;   // ← 원래 꺼져 있던 것까지 켠다
  ```

  `PlayerAvatar` 프리팹 **루트에는 POC 시절 Capsule 메시(550 verts)가 `MeshRenderer.enabled = false`
  로 남아 있다.** 조립 아바타가 자식으로 붙어 가려져 있었는데, 이 코드가 켜 버려서 몸 안의 캡슐
  하단이 발 사이로 튀어나왔다. **그게 "봉" 이다.**

  → 숨길 때 **켜져 있던 렌더러만 기록**하고 복귀 시 그 목록만 되살린다(`HideSelf`/`RestoreSelf`).

- **원인 2 — 그림자가 아예 만들어지지 않았다.** `ConfigureAvatarShadows` 가
  `TryFindGroundHeight` 실패 시 **조기 반환**했다. 스폰 경합(T-177)으로 플레이어가 아직 방 밖
  원점에 있는 동안 `Rebuild` 가 돌면 아래에 바닥이 없어 그림자 오브젝트 자체가 생기지 않고,
  **외형을 다시 바꿀 때까지 복구되지 않는다.**

  → 바닥을 못 찾아도 **만들어 두고 숨긴다.** 새로 넣은 `LateUpdate` 가 매 프레임 바닥을 다시
  찾아 위치를 맞추고 보이기/숨기기를 정한다. 아바타당 레이캐스트 1회라 40명이어도 무시할 수 있다.
  덤으로 층높이가 다른 곳(라운지 데크 0.32 단차)에서 그림자가 뜨는 문제도 사라진다.

- **원인 3 — 얇은 기물 뒤에서 화면이 튀었다.** 오클루전 거리를 **당길 때는 즉시** 적용했다.
  벽처럼 넓은 면은 궤도를 돌며 가림 정도가 서서히 바뀌어 괜찮지만, **사람 모형·기둥처럼 얇은
  기물**은 캐스트가 맞았다/안 맞았다를 급히 오가며 거리가 계단처럼 뛴다.

  → 당길 때도 보간한다(`_collisionPullLerp = 18`, 밀려나는 쪽 5 보다 빠르게).
  단 **근평면이 지오메트리에 닿을 만큼 가까우면(반경 × 2 이하) 즉시** 당긴다 —
  거기서 보간하면 한두 프레임 벽을 뚫고 밖이 보인다.

- **예방**:
  - **상태를 토글하는 코드는 "원래 상태" 를 기록해야 한다.** `enabled = true` 로 일괄 복구하면
    의도적으로 꺼 둔 것을 되살린다. 특히 프리팹에 **과거 잔재가 꺼진 채 남아 있는 경우**가 있다.
  - **프리팹 루트에 남은 POC 잔재를 확인한다.** `PlayerAvatar` 루트의 Capsule MeshFilter/MeshRenderer
    는 지금 아무 역할이 없다 — 제거 후보다(이번엔 동작을 바꾸지 않으려 남겼다).
  - **한 번만 배치하는 보조 오브젝트는 실패를 흡수하지 못한다.** 생성 시점의 물리 상태에 의존하면
    스폰 경합·씬 로드 순서에 따라 조용히 없어진다. 매 프레임 갱신이 싸다면 그쪽이 안전하다.

### T-182. "Failed to connect to server." — 빌드 타깃이 Server 라 에디터가 스스로 서버가 돼 있었다 (2026-08-21, 해결)

- **증상**: Play 하면 `UnityTransport` 가 `Failed to connect to server.` 만 남긴다. 스택은 전송
  계층 내부라 원인을 전혀 알려주지 않는다.

- **진단**: 콘솔 로그 **순서**가 답이었다.

  ```
  [NetworkBootstrap] Dedicated server start=True port=7777 maxPlayers=40 (WebSocket)
  ...
  [DevConnectionHud] session=ws_mock_001 channel=11F-01 → ws://127.0.0.1:7777
  [ConnectionManager] StartClient ws://127.0.0.1:7777 → True
  Failed to connect to server.
  ```

  **같은 인스턴스에서 서버가 뜬 뒤 클라이언트 접속을 요청했다.** `NetworkManager` 는
  싱글턴이라 둘을 겸할 수 없다(Host 는 별개 API 다).

- **원인**: 두 개가 겹쳤다.
  1. `EditorUserBuildSettings` 가 `StandaloneLinux64` + 서브타깃 **`Server`** 였다.
     이 조합은 **에디터 스크립트에도 `UNITY_SERVER` 를 정의한다.** 그래서
     `NetworkBootstrap.Start()` 의 `#if UNITY_SERVER` 분기가 타서 Play 하는 순간
     에디터가 dedicated server 로 떴다. `-server` 인자도, batch mode 도 아니었다.
  2. 로비에서 월드로 넘어오면 `DevConnectionHud.Start()` 가
     `AvatarSceneHandoff.ConsumeWorldConnectionRequest()` 를 보고 `ConnectViaSessionApi()` 를
     부른다. **여기에 "이미 네트워크가 떠 있나" 가드가 없었다.**

- **해결**:
  - `NetworkBootstrap` 의 자동 시작 조건을 `#if UNITY_SERVER` 에서
    **`!Application.isEditor || isBatchMode || -server`** 로 바꿨다. 즉 **에디터는 빌드 타깃이
    무엇이든 자동으로 서버가 되지 않는다.** 실제 서버 빌드·배치 모드·명시 인자만 자동 시작한다.
    에디터에서 서버를 띄우려면 HUD 버튼이나 `-server` 를 쓴다. 자동 시작을 건너뛸 때 그 사실을
    로그로 남긴다.
  - `ConnectViaSessionApi` 에 **`IsListening || IsClient` 가드**를 넣고, 걸리면 상태를 담은
    경고를 남긴다 — 다음에 같은 상황이 오면 로그가 원인을 말한다.
  - `ConnectionManager.StartHost` + HUD 의 **"Start Host"** 버튼을 추가했다. 스폰·이동·상호작용은
    에디터 하나로 검증하는 쪽이 빠르고, 승인 콜백과 스폰 슬롯 배정이 클라이언트와 같은 경로를
    타므로 검증 가치가 유지된다. 원격 표현까지 보려면 인스턴스 둘이 필요하다.
  - **빌드 타깃은 건드리지 않았다.** 서버 빌드를 뽑을 때 필요한 설정이고, 이제 에디터 동작에
    영향이 없다.

- **예방**:
  - **`UNITY_SERVER` 는 "서버 빌드" 가 아니라 "빌드 타깃이 서버" 를 뜻한다** — 에디터에도
    정의된다. 런타임 동작을 이 심볼만으로 갈라선 안 되고, `Application.isEditor` 를 함께 본다.
  - **네트워크 시작 API 는 이미 떠 있는지 먼저 확인한다.** 겹쳐 부르면 전송 계층이 원인을
    감춘 한 줄만 남긴다.
  - 원인을 모를 때는 **에러 한 줄이 아니라 그 앞 로그 순서**를 본다. 이번 건은 순서만으로 특정됐다.

### T-181. Windows 경로 길이 제한으로 git worktree 체크아웃이 실패해 인덱스까지 깨졌다 (2026-08-21, 해결)

- **증상**: PR #53 충돌 해소를 위해 scratchpad 에 worktree 를 만들자 체크아웃 도중 실패했다.

  ```
  error: unable to create file festa-unity/Assets/Rukha93/ModularAnimeCharacter/Samples/
  Preview/MaterialVariations_Toon/mat_hair_tied.001 - ponytail alt toon.mat.meta: Filename too long
  fatal: Could not reset index file to revision 'HEAD'
  ```

  `git worktree list` 에 등록조차 안 됐고 `git worktree remove` 는 `is not a working tree` 로 거부했다.
  `git worktree prune` 으로만 정리됐다.

- **원인**: 두 경로 길이가 **합산**된다.
  1. scratchpad 경로가 이미 길다 — `C:/Users/SSAFY/AppData/Local/Temp/claude/C--Users-SSAFY-Desktop-SSAFESTA/<세션UUID>/scratchpad/` (약 110자)
  2. Unity 에셋 경로가 길다 — `Rukha93/ModularAnimeCharacter/.../mat_hair_tied.001 - ponytail alt toon.mat.meta` (약 130자)

  합치면 260자(Win32 `MAX_PATH`)를 넘는다. 메인 워킹트리(`C:/Users/SSAFY/Desktop/SSAFESTA`, 30자)에서는
  같은 파일이 문제없이 체크아웃되므로 **에셋 탓이 아니라 대상 경로 탓**이다.

- **해결**: **문서 전용 작업에는 워킹트리를 만들지 않았다.** 충돌 파일이 1개뿐이라
  오브젝트 DB 플럼빙으로 끝냈다 — 체크아웃 0회.

  ```bash
  git merge-tree --write-tree --name-only origin/develop origin/<branch>   # 충돌 파일 식별
  git show <mergedtree>:specs/README.md > resolved.md                       # 해소
  BLOB=$(git hash-object -w resolved.md)
  GIT_INDEX_FILE=tmpidx git read-tree <mergedtree>
  GIT_INDEX_FILE=tmpidx git update-index --cacheinfo 100644,$BLOB,specs/README.md
  TREE=$(GIT_INDEX_FILE=tmpidx git write-tree)
  git commit-tree $TREE -p origin/<branch> -p origin/develop -F msg.txt
  ```

  메인 워킹트리를 전혀 건드리지 않아 **Unity 에디터가 열려 있어도 안전하다** — 브랜치 전환이 없으니
  씬·프리팹이 리로드되지 않는다.

- **예방**:
  - `festa-unity/` 를 포함하는 저장소에서 **긴 임시 경로에 worktree 를 만들지 않는다.**
    필요하면 `C:/wt/<짧은이름>` 처럼 루트 근처 짧은 경로를 쓴다
    (기존 `C:/Users/SSAFY/AppData/Local/Temp/ssafesta-game-studio-foundation` 은 성공한 전례 — 세션 UUID 가 없어 짧다).
  - **문서·spec 만 건드리는 병합 해소에는 워킹트리가 필요 없다.** 위 플럼빙이 더 빠르고 안전하다.
  - `git config core.longpaths true` 는 Git 쪽만 풀어 준다. Unity·탐색기는 여전히 못 여는 경로가 생기므로
    이 저장소에서는 우회책으로 쓰지 않는다.

### T-179. 임포터 탄젠트 제거를 폴더 전체에 걸어 노멀맵 에셋을 망칠 뻔했다 (2026-08-21, 수정)

- **증상**: 아직 드러나지 않은 **잠복 버그**. 엘리베이터 모델을 넣으려고 `Models/` 폴더를 열어보니
  `Models/Laptop/laptop.FBX` 가 있고 `laptop.mat` 이 `_NORMALMAP` 키워드와 `_BumpMap` 슬롯을 쓴다.
  그런데 내가 넣은 `OnPreprocessModel` 은 **`Assets/_Project/Models/` 하위 전체**에
  `importTangents = None` 을 적용한다. **탄젠트 없이 노멀맵을 쓰면 음영이 조용히 틀어진다.**

- **왜 아직 안 터졌나**: `laptop.FBX.meta` 가 여전히 `tangentImportMode: 3`(CalculateMikk) 이다 —
  후처리기를 넣은 뒤 이 파일이 **재임포트되지 않았기 때문**이다. 누군가 재임포트하거나
  Library 가 재생성되는 순간(에디터 버전 변경, `Library` 삭제, 애셋 재임포트) 적용된다.
  즉 **지금은 정상이고 나중에 조용히 깨지는** 형태였다.

- **원인**: 최적화의 **근거를 범위 없이 일반화**했다. 탄젠트 제거의 근거는
  "월드 모델 머티리얼 42개 중 노멀맵 사용 0개" 라는 실측이다. 그 사실은 그 모델에 대한
  것이고 같은 폴더의 다른 모델로 전이되지 않는다. 코드 주석에 "노멀맵 있는 에셋을 이 폴더에
  넣으면 음영이 깨지니 그때는 조건부로 바꾼다" 라고 **스스로 위험을 적어두고도 폴더에 이미
  그런 에셋이 있는지 확인하지 않았다.**

- **해결**: 적용 범위를 **`Models/` 직속 파일**로 좁혔다 (`IsArchitecturalModel`).
  건축 모델(11층 월드·엘리베이터)은 직속에 두고, 노멀맵을 쓰는 소품은 하위 폴더에 둔다.
  검산: 월드·엘리베이터는 적용, `Laptop/laptop.FBX`·`MapTexture/*`·`Art/Avatar/*` 는 제외.
  추가로 `OnPostprocessModel` 에 **`WarnIfNormalMapWithoutTangents`** 를 넣어, 이 범위에 들어온
  모델이 실제로 `_BumpMap` 을 쓰면 머티리얼 이름과 함께 경고하고 해결책을 안내한다.
  경로 규칙에 의존하지 않는 **런타임 안전망**이다.

- **예방**:
  - **최적화를 적용할 때는 "무엇을 측정했고 그 측정이 어디까지 유효한지" 를 범위로 표현한다.**
    폴더 전체 같은 넓은 조건은 나중에 들어올 에셋까지 포함한다.
  - **주석에 위험을 적었으면 그 위험이 이미 실현돼 있는지 지금 확인한다.** 이번엔 확인 한 번이면
    (`ls Models/`) 잡혔다.
  - **경로 기반 판정에는 감지 경고를 함께 둔다.** 규칙은 어기기 쉽지만 경고는 로그로 남는다.
  - 재임포트되지 않은 `.meta` 는 **아직 옛 설정을 들고 있다** — `.meta` 를 보고 "적용 안 됐네" 로
    안심하지 말고, 언제 적용될지를 본다.

### T-178. spec 019 가 "기존 오류 봉투 재사용" 이라 써놓고 봉투가 아닌 예시를 실었다 (2026-08-21, 수정 대기)

- **증상**: `specs/019-game-studio/contracts/game-api.md` §공통 오류 봉투가 이렇게 적혀 있다.

  ```json
  { "code": "GAME_REVISION_CONFLICT", "message": "다른 편집 내용이 먼저 저장되었습니다.",
    "details": { "currentRevision": 8 } }
  ```

  바로 윗줄은 "기존 FESTA 오류 봉투를 재사용한다" 다. 그런데 **FESTA 봉투에 `details` 는 없다.**
  `requestId` 도 `errors`·`warnings` 도 빠져 있다.

- **원인**: 문장으로만 "재사용" 을 선언하고 **예시를 실제 봉투에서 복사해 오지 않았다.**
  spec 019 를 쓰는 시점에 005 의 봉투 정의(`contracts/layout-api.md` §오류 봉투)를 열어보지 않고
  일반적인 REST 오류 모양을 손으로 적었다. 선언과 예시가 같은 문단에 있어서 **읽는 사람은
  예시를 계약으로 받는다** — 선언 쪽이 아니라 예시 쪽이 구현된다.

- **더 나쁜 점**: 같은 의미가 이미 다른 모양으로 확정돼 있다. 005 는 revision 충돌을
  `errors[].rule = "CURRENT_REVISION"` 으로 표현하고 구현도 그렇다
  (`LayoutRevisionConflictException.java:21`). 즉 **한 시스템 안에 revision 충돌 표현이 두 개**가
  된다. BE 가 019 를 구현할 때 어느 쪽을 따르든 다른 쪽과 어긋난다.

- **해결**: 미수정. PR #53 이 아직 열려 있어 거기서 고친다. **#58(오류 봉투 A/B/C)이 봉투 모양
  자체를 다시 정하는 중이라 그 결론에 맞춰야 한다** — 지금 고치면 두 번 고친다. #58 에
  이 사실과 함께 "결론 나면 맞추겠다" 를 남겼다.

- **예방**: **"기존 X 를 재사용한다" 고 쓸 때 예시를 손으로 적지 않는다.** 정본에서 복사하거나,
  복사할 수 없으면 예시를 아예 싣지 말고 정본 링크만 건다. 잘못된 예시는 링크 없는 것보다
  나쁘다 — 링크가 없으면 찾아보지만 예시가 있으면 그걸 믿는다.
  같은 부류로 이미 겪은 것: 이관된 `quickstart.md` 가 자기 옛 경로를 예시로 들고 있던 #43 건.
  **문서 안의 예시는 문서와 함께 낡는다.**

### T-177. 대부분 허공(원점)에서 스폰돼 떨어진다 — Owner 권위 이동이 서버 스폰 위치를 덮는 경합 (2026-08-21, 수정·실기 검증 대기)

  - 서버 승인 위치: 40 슬롯 모두 바닥 위 y 0.18, 겹침 0 — 실측 검증돼 있다 (T-175)

  - `WorldSceneLayout.PlayerSpawnPoints`: 마커만 만들고 **사용처 없음** — 죽은 코드

  바닥이 없고 → 허공에서 낙하. 경합 타이밍에 따라 서버 값이 이기면 정상 스폰 — "가끔만
  맵에서" 라는 무작위성이 여기서 나온다. 사용자의 "맵이 원점에 없어서 생기는 이격" 이라는
  직관은 절반이 맞다 — 원점으로 가는 것 자체가 버그이고, 맵이 원점에 있었다면 증상이

- **왜 맵을 원점으로 옮기지 않았나**: 봉쇄·조명(모두 `@World_11F` 자식)·`BoothSlot_7`(씬 루트)·
  스폰 상수·문서의 좌표가 전부 연쇄 이동해야 하고, **경합은 그대로 남아 증상만 가려진다**

### T-176. "Screen position out of view frustum" 경고 폭주 — 레거시 마우스 디스패처가 아직 돌고 있었다 (2026-08-21, 해결)

- **증상**: Play 중 콘솔에 아래가 마우스를 움직일 때마다 수십 줄씩 쌓인다.

  ```
  Screen position out of view frustum (screen pos 509.0, 483.0) (Camera rect 0 0 901 550)
  UnityEngine.SendMouseEvents:DoSendMouseEvents (int)
  ```

- **성격**: **에러가 아니라 경고다.** 기능이 깨진 신호는 아니다. 다만 스택의
  `SendMouseEvents.DoSendMouseEvents` 가 **진짜 문제를 가리키고 있었다.**

- **원인**: Unity 는 씬에 `OnMouseDown`/`OnMouseEnter` 같은 메서드를 가진 컴포넌트가
  **하나라도 있으면** 매 프레임 레거시 마우스 디스패처를 돌리고, 그 안에서 카메라
  레이캐스트를 한다. T-166 에서 `LaptopInteractable` 은 `BoothInteractionInput`
  (Input System + `Physics.Raycast`) 으로 옮겼는데 **두 곳이 남아 있었다.**

  - `AiNpcInteractable.OnMouseDown`
  - `BoothInteractionTarget.OnMouseEnter` / `OnMouseExit` (호버 하이라이트)

  씬을 편집 모드에서 보면 이 컴포넌트가 0개다 — **`BoothRuntime` 이 Play 에서
  스폰하는 부스 오브젝트에 붙어 있어서** Play 중에만 디스패처가 살아난다.
  그래서 편집 중에는 재현되지 않는다.

- **경고 자체보다 중요한 것**: `OnMouseXXX` 는 **Unity 6 WebGL 에서 발생하지 않는다**(T-166).
  즉 이 두 상호작용은 **배포 환경에서 이미 죽어 있었다** — AI NPC 클릭도, 부스 호버
  하이라이트도 브라우저에서는 동작하지 않는다. 경고는 그 죽은 코드를 알려주고 있었다.

- **해결**: 둘을 중앙 디스패처로 옮기고 `OnMouse*` 를 전부 제거했다.
  - `BoothInteractionInput` 이 매 프레임 포인터 레이캐스트로 **호버**를 추적해
    `BoothInteractionTarget.SetHighlight(bool)` 을 호출한다(진입/이탈 시에만).

### T-175. 스폰 위치가 재접속마다 바뀐다 — 슬롯을 `clientId` 로 계산했다 (2026-08-21, 해결)

- **증상**: 접속할 때마다 아바타가 다른 자리에 나타난다. 사용자 화면 녹화로 신고.

- **원인**: `ConnectionManager.GetSpawnPosition(clientId)` 가 스폰 슬롯을 **`clientId % 40`** 으로 계산했다.

  ```csharp

  `clientId` 는 **서버 프로세스가 살아 있는 동안 접속마다 1씩 증가**한다(1, 2, 3 …).
  `StartServer` 를 한 번 띄우고 `StartClient` 로 붙었다 끊는 개발 루프에서는 매번 다른 슬롯이

  `ClientDisconnected` 에서 반납한다. 혼자 테스트하면 항상 0번 = 같은 자리이고,
  40명이 동시에 있어도 슬롯은 겹치지 않으며, 중간에 나간 자리는 다음 접속이 재사용한다.

  실측: 서로 다른 `clientId` 1~5 로 접속/해제를 반복해도 전부 slot 0, 좌표 동일.
  동시 5명은 slot 0~4 로 분리. slot 1 반납 후 새 접속이 slot 1 재사용.

- **예방**:

### T-173. 임계값을 월드 단위로 두고 계측만 로컬 공간으로 바꿔 스케일 마커를 벽으로 잡았다 (2026-08-21, 해결)

  const float EndWallZTolerance = 8f;   // 월드 단위로 쓰던 값
  const float FlatThreshold = 2f;
  ```

  씬 스케일이 12.5 라서 **로컬 1 단위 = 월드 12.5 단위**다. 즉 허용 오차 8 이 실질 **100 world unit** 이 되고, "두께 2 이하면 평면" 이 **25 world unit 이하**가 됐다. `mock-floor` 는 로컬 두께 0.8(월드 10), 방 z 끝단에서 로컬 2.29(월드 29) 떨어져 있어 두 조건을 모두 통과했다.

- **왜 조용히 지나갔나**: `SideNames` 가 3장이 아닐 때 `01·02…` 로 **폴백**하도록 되어 있었다. 그래서 잘못 잡아도 그럴듯한 이름이 나오고 에러도 경고도 없었다. **폴백이 오류를 감췄다.**

- **해결**:
  1. 임계값을 **방 크기에 대한 비율**로 바꿨다 — 단위계에 무관해진다.
     `EndWallZToleranceRatio 0.04` · `FlatRatio 0.02`

     **방 x 범위 안**인지로 외곽 벽(`wall-flat`)을 배제한다.
  3. **3장이 아니면 경고를 띄운다.** 폴백으로 조용히 넘기지 않는다.
  4. 마커 비활성화를 재명명보다 **먼저** 실행한다 — 이름으로 찾으므로 개명 뒤에는 못 찾는다.
  - 재임포트 결과 `rear 3 / front 3`, `mock-floor`·`mock-wall` 은 이름 유지하며 비활성.

- **예방**:
  - **좌표 공간을 바꾸면 그 공간의 상수를 전부 다시 본다.** 계측 코드만 고치고 임계값을 두면 스케일 배수만큼 어긋난다. 애초에 **절대값 임계값을 쓰지 않고 대상 크기에 대한 비율로 쓰면** 이 실수가 성립하지 않는다.

### T-172. 천장 정렬이 한 번에 안 맞고 매번 오차가 남았다 — localPosition 을 자기 스케일로 나눴다 (2026-08-21, 해결)

- **증상**: 새 월드 모델(`11th-0821-complete textures (without elevator)`)로 교체하고 `Festa/World/천장을 벽 상단에 맞춤` 을 실행했는데 로그가 `오차 -16.6435 world unit` 을 남겼다. 정렬 함수는 "벽 상단에 붙인다" 는 목적이므로 실행 직후 오차가 0 이어야 한다.

- **원인**: `AlignCeiling` 이 이동량을 **자기 자신의** `lossyScale.y` 로 나눴다.

  ```csharp
  float scaleY = ceiling.lossyScale.y;              // ← 10
  float delta  = wallTop - Bounds(ceiling).min.y;   // 월드 거리
  ceiling.localPosition += new Vector3(0f, delta / scaleY, 0f);
  ```

  `localPosition` 은 **부모 공간**이다. 월드 거리를 로컬 이동량으로 바꿀 때 나눠야 하는 값은
  **부모의** lossyScale 이지 자기 lossyScale 이 아니다. 이 천장은 `localScale 0.8`, 부모(모델 루트)가
  `12.5` 라 자기 lossyScale 은 `12.5 × 0.8 = 10` 이다. 12.5 로 나눠야 하는데 10 으로 나눠서
  **정확히 1.25배 과다 이동**했다.

  ```
  필요 이동   = 49.5557 - 116.1298 = -66.5741 world
  올바른 local = -66.5741 / 12.5 = -5.3259
  실제 적용    = -66.5741 / 10   = -6.6574   (실측 8.7629 → 2.1054)
  초과         = -1.3315 local × 12.5 = -16.6435 world  ← 보고된 오차와 일치
  ```

- **왜 여태 안 드러났나**: **구 모델도 `localScale 0.8` 로 같은 구조였다. 즉 버그는 원래 있었다.**
  그런데 과다 이동이 1.25배라서 매 실행마다 오차가 `e → -0.25e` 로 **¼씩 줄며 수렴한다.**
  몇 번 더 누르면 눈에 안 보이는 값이 되므로, "한 번에 안 맞네" 하고 다시 누르는 것으로
  덮여 버렸다. 구 모델의 `ceiling.localPosition.y = 3.39` 는 그렇게 수렴한 값이다.
  새 모델은 천장 원본 높이가 5.373 로컬(≈67 world) 더 높아 **첫 오차가 16.6 로 커져서** 드러났다.

- **해결**: 부모 스케일로 나눈다. 한 번 실행으로 `오차 0.0000` 수렴을 확인했다.

  ```csharp
  float scaleY = ceiling.parent != null ? ceiling.parent.lossyScale.y : 1f;
  ```

- **예방**:
  - **`localPosition` 에 월드 거리를 넣을 때는 부모 스케일로 나눈다.** 자기 `lossyScale` 은
    자기 메시가 얼마나 커 보이는지의 값이고, 자기 위치가 부모 공간에서 얼마나 움직이는지와 무관하다.
    자기 localScale 이 1 이면 두 값이 같아서 틀린 코드가 통과한다 — 그래서 조용히 남는다.
    더 안전한 대안은 `ceiling.position += Vector3.up * delta` 로 **월드 좌표를 직접 쓰는 것**이다.
  - **"보정 함수는 실행 직후 오차 0 을 보고해야 한다."** 오차를 반환하도록 만들어 둔 게 이번에
    버그를 잡았다. 0 이 아닌 값을 반환하는데 "여러 번 누르면 되네" 로 넘기지 않는다.
    **수렴하는 버그는 결과가 맞아 보이므로 가장 오래 산다.**
  - 모델 교체는 이런 잠복 버그를 드러내는 계기다. 교체 후에는 도구 로그의 **숫자를 읽는다.**

### T-171. 저장 길이 상한이 "부족하다"고 단정했는데 실제로는 충분했다 (2026-08-21, 해결)

- **증상**: 이슈 #24 회신을 쓰면서 "Spring 의 `avatar` 컬럼 500자 상한은 Unity 의 실제 외형 값을 거부한다" 고 인수인계 문서에 적었다. 근거는 `AvatarAppearance.MaxEncodedLength = 3800` 과 T-24(길이 초과로 저장이 조용히 잘려 무반응) 였다. **틀렸다.** 보내기 전에 실제로 재 보니 최악 케이스가 414자였다.

- **원인**: **상수를 계약으로 착각했다.** `MaxEncodedLength = 3800` 은 현재 저장 형식(`fa`)의 길이가 아니라 **구 `rt` 모드**를 위해 잡힌 값이다. `rt` 는 Sidekick 파츠 이름을 그대로 문자열에 실어서(파츠당 ~25자 × 16종) 500자를 쉽게 넘었고, T-24 가 바로 그 사고였다. 그래서 상한을 3800 으로 올린 것이다.

  그런데 신규 저장 형식인 `fa` 는 **파츠 이름을 싣지 않는다.** 카탈로그 ID 와 hex 색만 넣고, 필드 수가 고정이다.

  ```
  fa|g=1|i=<8개>|p=<9개>|q=<9개 hex>|w=<36개 hex>[|c=hex]
  ```

  `Encode()` 의 `fa` 분기를 그대로 재현해 재 본 결과:

  | 케이스 | 길이 |
  |---|---|
  | 기본값 (색 미지정 → `-` 1자) | 138자 |
  | 색 전부 지정 + tint | 406자 |
  | item ID 가 4자리여도 | 414자 |

  즉 T-24 의 교훈(길이 상한을 얕보지 마라)은 맞지만, **그 교훈이 나온 형식과 지금 쓰는 형식이 다르다.** 옛 사고의 근거 수치를 새 형식에 그대로 옮겨 붙인 것이 오류다.

- **해결**: 인수인계 문서의 "⚠️ 500자는 실제 값을 거부한다" 를 실측 근거와 함께 정정하고, 이슈 #24 회신에도 "제 우려가 틀렸다" 를 명시했다. `BE.md` 의 500자는 그대로 두어도 된다. 남긴 단서 하나 — **여유가 86자(17%)뿐**이라 `w`(의상 색 슬롯, 현재 36개)가 12개만 늘어도 500을 넘으므로 컬럼은 `TEXT` 를 권한다. spec 계약서도 `TEXT` 를 규정하고 `VARCHAR(32)` 를 금지한다.

- **예방**:
  - **상한 상수는 "현재 형식의 실제 길이" 가 아니다.** 여유를 얹어 잡은 값이거나 과거 형식의 잔재일 수 있다. 다른 파트에 "이 값이면 부족하다" 고 말하기 전에 **인코더를 재현해 실제 길이를 재라.** 이번엔 노드 스크립트 한 번이었다.
  - 상수 정의에 붙은 주석이 근거를 알려준다. `MaxEncodedLength` 주석은 이미 "Sidekick 파츠 이름이 길어서(파츠당 ~25자 × 16종) 500자를 넘을 수 있다" 로 **`rt` 를 가리키고 있었다.** 읽었으면 알 수 있었다.
  - 과거 트러블슈팅을 근거로 쓸 때는 **그 사고가 일어난 형식·경로가 지금과 같은지** 먼저 확인한다. T-24 는 `rt`, 이번 건은 `fa` 였다.
  - 남에게 요구 사항을 넘기는 회신은 특히 실측 후에 쓴다. 틀린 요구를 보내면 상대가 필요 없는 마이그레이션을 한다.

### T-131. 월드 입장 후 몸체만 보이고 헤어·의상 파츠가 조립되지 않음 (2026-08-17, 수정 및 E2E 재검증 대기)

- **증상**: CharacterLobby에서는 선택한 헤어와 의상이 보이지만, WebGL 월드 입장 후에는 기본 몸체/속옷만 보이거나 검은 실루엣처럼 보였다.
- **원인**: 모듈 외형 `fa` 문자열은 최대 3800자까지 가능하지만 기존 접속 승인/`NetworkPlayer.AvatarCode` 경로는 32-byte 호환 필드다. 긴 외형값을 그 경로에 실으면 파츠 ID와 색상 정보가 온전히 전달될 수 없다. 또한 Spawn 직후의 첫 외형 RPC가 Scene 전환과 경합하면 기본값이 남을 수 있다.
- **해결**: 접속 승인에는 짧은 preset만 사용하고, Owner Spawn 뒤 전체 `fa` 문자열을 `PlayerAppearanceController.Encoded` (`FixedString4096Bytes`)로 서버에 전달하도록 분리했다. 서버가 검증 후 동기화 값을 갱신하며, Owner는 값이 되돌아올 때까지 제한 시간 동안 재시도한다. 동일 실행 안의 Scene 전환은 runtime handoff cache를 우선 사용한다.
- **검증/배포**: Dedicated Server와 WebGL은 반드시 같은 코드 리비전으로 빌드한다. 서버는 새 Linux build로 교체한 뒤 컨테이너/프로세스를 재시작하고, WebGL은 새 build를 배포한 뒤 브라우저 hard refresh로 확인한다. 이 조합에서 헤어·상의·하의·모자·안경과 색상값이 모든 Client에 조립되는 E2E 검증이 남아 있다.

> **운영 규칙 (필수)**
> 1. 작업 중 문제가 발생하면 **해결 여부와 무관하게 즉시 여기 등록**한다. "나중에 정리"는 없다 — 그 자리에서 T-번호를 따고 한 줄이라도 적는다.
> 2. 형식: 증상 / 원인 / 해결 / 예방. 원인 미상이면 원인란에 "조사 중"으로 두고 해결되면 갱신한다.
> 3. 같은 폴더의 `24_작업일지.md`에서 T-번호로 참조한다.
> 4. 같은 증상이 재발하면 새 항목을 만들지 말고 기존 항목에 재발 기록을 추가한다.

## Unity 에디터 / 씬

### T-01. 캡슐·오브젝트가 납작한 원반/종잇장으로 보임
- **증상**: 플레이어 캡슐이 파란 원반처럼 찌부러져 렌더링
- **원인**: "NetworkTransform의 Scale 동기화 체크 해제" 지시를 **Transform 컴포넌트의 Scale 값에 0 입력**으로 오해 → Scale (0,1,0)
- **해결**: 프리팹/부모 오브젝트 Transform Scale을 (1,1,1)로 복원
- **예방**: Scale "체크 해제"는 NetworkTransform의 Syncing 체크박스를 뜻함. Transform 숫자값 아님. 부모 오브젝트 Scale도 자식 전체를 찌그러뜨리므로 함께 확인

### T-02. 알록달록한 소용돌이/얼룩이 떠다님 (글자 깨짐)
- **증상**: 이름표·라벨 위치에 글리치 텍스처 얼룩
- **원인**: **Unity 6는 런타임 생성 TextMesh에 기본 폰트를 자동 지정하지 않음**
- **해결**: `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")` 지정 + MeshRenderer material에 font.material 할당
- **예방**: 코드로 TextMesh를 만들면 폰트 지정 필수 (NetworkPlayer, BoothObjectFactory에 반영됨)

### T-03. 라벨 글자가 찌그러져 보임
- **증상**: 비디오 스크린 등 위의 라벨이 눌린 형태
- **원인**: 비균등 스케일(2.4×1.4×0.1) 오브젝트의 **자식**으로 라벨을 붙여 부모 스케일이 글자에 전파
- **해결**: 라벨 localScale에 부모 스케일의 역수 적용
- **예방**: 비균등 스케일 오브젝트의 자식에 텍스트/UI를 두지 말거나 역스케일 보정

### T-04. 오브젝트가 바닥에 절반 묻힘
- **증상**: 스폰된 캡슐/부스 도형의 하반이 지면 아래
- **원인**: Unity primitive는 **피벗이 중심** — Y=0에 스폰하면 절반이 묻힘
- **해결**: 스폰 위치에 절반 높이 가산 (Player 스폰 Y=1, BoothObjectFactory groundLift)
- **예방**: 프리팹 제작 시 피벗을 바닥 기준으로 만들거나, 코드 스폰 시 높이 보정

### T-05. 코드를 고쳤는데 실행 결과가 그대로
- **증상**: 파일은 갱신됐는데 Play 결과 불변
- **원인**: 에디터가 Play 중이거나 포커스를 안 받아 재컴파일이 안 됨 (외부에서 파일이 변경된 경우)
- **해결**: Play 정지 → Unity 창 포커스 → Ctrl+R → 우하단 스피너 종료 후 Play
- **예방**: 외부(AI 세션 등)에서 파일을 수정하면 반드시 Play 정지 상태에서 Refresh
- **2026-08-14 재확인**: 플레이 중 스크립트 컴파일 뒤 첫 캡처가 이전 의상 레일을 유지했다. `Stop → Play`로 도메인을 새로 시작한 뒤 왼쪽 탭형 UI가 반영된 화면을 다시 검증했다.

### T-14. 자기 캡슐이 화면에 안 보임
- **증상**: 접속은 되는데 캡슐이 화면 밖
- **원인**: 카메라가 고정이라 스폰 위치를 안 비춤
- **해결**: `PlayerCameraFollow` (Owner 전용 3인칭 추적) 프리팹에 추가
- **예방**: POC용 — 정식 카메라 워크는 spec 확정 후 교체

## Web(WebGL) 빌드

### T-06. 빌드했더니 빈 씬만 나옴 (HUD/부스/바닥 없음)
- **증상**: 브라우저에 스카이박스만 렌더링
- **원인**: Build Profiles **Scene List**에 Main 씬 누락/순서 문제, 또는 씬 미저장(`main*`) 상태로 빌드
- **해결**: Scene List에 Main만 남기고 맨 위 + 씬 저장 후 재빌드
- **예방**: 빌드 전 타이틀바 `*`(미저장) 확인 습관

### T-07. WebGL에서 부스/AI Mock이 영원히 로딩 안 됨
- **증상**: `[BoothRuntime] built` 로그가 안 찍힘. 에디터는 정상
- **원인**: **`Task.Delay`는 WebGL(단일 스레드)에서 완료되지 않음**
- **해결**: Mock 3종을 `Awaitable.WaitForSecondsAsync`로 교체
- **예방**: WebGL 타깃 코드에서 Task.Delay/스레드 API 금지. Unity `Awaitable` 사용
- **부수효과**: 에디터의 무해한 `TaskCanceledException`도 함께 사라짐

### T-08. 런타임 생성 오브젝트가 전부 마젠타(핑크)
- **증상**: 에디터는 정상, 빌드에서만 핑크
- **원인**: `CreatePrimitive` 기본 머티리얼의 셰이더가 빌드에 포함되지 않음
- **해결**: `Shader.Find("Universal Render Pipeline/Lit")`로 머티리얼 명시 생성 (씬 머티리얼이 이미 셰이더를 빌드에 포함시키므로 Find 가능)
- **예방**: 런타임 생성 렌더러는 항상 명시적 셰이더/머티리얼 사용

### T-09. 빌드에서 IMGUI(OnGUI) 패널이 아예 안 보임
- **증상**: 에디터에선 보이는 Dev HUD가 브라우저에서 사라짐
- **원인**: **Active Input Handling이 "Input System Package (New)"만이면 플레이어 빌드에서 OnGUI가 렌더링되지 않음**
- **해결**: Project Settings > Player > Other Settings > Configuration > Active Input Handling = **Both** (에디터 재시작)
- **예방**: DevConnectionHud를 정식 uGUI로 교체하면 원복 검토

### T-10. HUD에 웹페이지 주소를 넣어 접속 실패
- **증상**: Connect 무반응
- **원인**: 웹페이지 http 포트(예: 62385/8000)와 **게임 서버 포트(7777)** 혼동
- **해결**: 브라우저 주소창 = 웹페이지(localhost:8000), HUD Addr/Port = 게임 서버(127.0.0.1:7777)
- **예방**: 정식 구현에서는 world-sessions API가 endpoint를 내려주므로 수동 입력 자체가 사라짐

### T-13. Build And Run 포트가 매번 바뀌고 플랫폼에 묶임
- **증상**: 테스트 URL 고정 불가, Linux Server로 스위치하면 웹 서빙 불가
- **원인**: Build And Run은 에디터 임시 서버 (랜덤 포트, 에디터 종속)
- **해결**: Web Publishing Settings **Compression Format = Disabled** (개발용) 후 빌드 → `python -m http.server 8000 --directory Builds/web` → localhost:8000 고정
- **예방**: 빌드 산출물은 에디터와 무관하게 서빙 가능. 실배포는 Brotli + CloudFront 헤더로 복원 (deployment-handoff.md)

### T-17. `python -m http.server --directory`로 띄웠는데 404
- **증상**: 빌드 폴더에 index.html이 있는데도 브라우저가 404
- **원인**: PowerShell의 현재 위치가 달라 상대경로 `--directory Builds/web-...`가 엉뚱한 폴더를 가리킴
- **해결**: 대상 폴더로 `cd` 후 `python -m http.server <port>` (옵션 없이) 또는 절대경로 지정
- **예방**: 서버 실행 후 브라우저 접속 시 PowerShell에 요청 로그가 찍히는지로 정상 서빙 확인

### T-18. Sidekick 툴 등 에디터 창이 안 열림 (`Attempted to open unsupported window in cloned player systems`)
- **증상**: Synty 툴 창이 열리지 않고 `NullReferenceException` + 이어서 `Failed to load tool data`
- **원인**: **Multiplayer Play Mode의 가상 플레이어(Player 2/3)가 활성 상태**이면 MPPM이 복제 에디터에서 에디터 창 열기를 차단한다
- **해결**: Play 정지 → Window > Multiplayer > Multiplayer Play Mode → Player 2/3 **체크 해제** → **Unity 재시작**(부트스트랩이 이미 꼬였으면 필수)
- **예방**: 에디터 툴(Sidekick 등) 작업 시엔 가상 플레이어를 끈다. 멀티 테스트할 때만 켠다

### T-19. `WebAssembly streaming compilation failed` / Content-Encoding 에러
- **증상**: 브라우저에서 빌드 로드 실패
- **원인**: 빌드가 압축(Brotli/Gzip)돼 있는데 로컬 서버가 `Content-Encoding` 헤더를 안 보냄 (또는 반대)
- **해결**: Build Profiles > Web > Player Settings > Publishing Settings > **Compression Format = Disabled** 후 재빌드 (개발용). 실배포는 Brotli + CloudFront 헤더 설정
- **확인법**: `Builds/web/Build/`에 `.br`/`.gz` 확장자가 있으면 압축된 것
- **부가**: `Tools/serve.py` 사용 시 wasm MIME·캐시 문제도 함께 예방됨

### T-20. `LinkError: wasi_snapshot_preview1 / fd_sync` (Sidekick SQLite)
- **증상**: WebGL 빌드가 아예 로드되지 않음
- **원인**: Sidekick의 SQLite 플러그인이 요구하는 WASI 호출을 런타임이 제공하지 못함. **재빌드 후 정상 동작** — 정확한 트리거는 미확정 (스테일 빌드/캐시 가능성)
- **해결**: 재빌드 + 캐시 무시 새로고침으로 해소됨
- ⚠️ **판정 정정**: 이 에러를 근거로 "Sidekick 런타임은 WebGL 불가, Synty 폴더 삭제 필요"라고 결론 냈으나 **오판**이었다. 근거:
  - Synty 체인지로그 v1.0.2 *"Updated SQLite build targets to allow Web build targets"*
  - `sqlite3.c.meta`에 `WebGL: enabled: 1`
  - `DatabaseManager`는 플레이어 빌드에서 파일 I/O를 쓰지 않음 (TextAsset → `:memory:` Deserialize)
  - 실제로 Synty를 둔 채 WebGL 빌드 성공
- **교훈**: 에러 하나로 "플랫폼 미지원"을 단정하지 말 것. 벤더 문서·플러그인 메타·실제 재현을 교차 확인한다

### T-21. SerializeField 이름을 바꿨더니 Inspector 값이 전부 사라짐
- **증상**: ScriptableObject/프리팹에 입력해둔 값이 빈 값으로 초기화됨 (AvatarCatalog의 preset 코드 소실)
- **원인**: Unity 직렬화는 **필드 이름 기준**. `avatarCode` → `presetCode`로 리팩터링하면 기존 asset 데이터와 매칭이 끊긴다
- **해결**: `[FormerlySerializedAs("이전이름")]` 부착 (`using UnityEngine.Serialization;`)
- **예방**: 직렬화 필드 이름 변경 시 **항상** FormerlySerializedAs를 함께 붙인다. 이미 값이 날아갔다면 붙인 뒤 재입력

### T-24. 커스터마이징 Custom 버튼이 무반응 — 인코딩 길이 초과가 조용히 삼켜짐 (2026-08-12)
- **증상**: HUD의 Custom 버튼을 눌러도 아무 변화 없음. 에러도 안 보임. 서버(Docker)를 재빌드해도 동일
- **원인**: `AvatarAppearance.Encode()`가 500자 초과 시 **조용히 `sk_01`을 반환**하도록 되어 있었음. Sidekick 파츠 이름이 길어(파츠당 ~25자 × 16종) 런타임 조립 인코딩이 500자를 넘으면, 서버에 "현재와 같은 값"이 전송되어 OnValueChanged가 발화하지 않음 → 완전한 무반응
- **해결**:
  1. 동기화 필드를 `FixedString512Bytes` → **`FixedString4096Bytes`**로 확대, `MaxEncodedLength` 500 → 3800
  2. Encode의 몰래 되돌리기 제거 — 초과 판단은 호출자(RequestChange)가 하고 거부 사유를 `LastRequestError`로 노출
  3. HUD가 `LastRequestError`를 **화면에 표시** (콘솔을 안 봐도 원인이 보이게)
  4. `SyncMirrorParts`의 이름 치환 실패 시 인덱스 매칭 폴백 (오른팔/오른다리 소실 방지)
- **주의**: NetworkVariable **타입이 바뀌었으므로 Web 빌드와 Linux Server(Docker) 빌드를 반드시 둘 다 다시** 해야 한다 (한쪽만 바꾸면 직렬화 불일치)
- **교훈**: 실패를 조용히 기본값으로 대체하는 코드는 "무반응 버그"가 된다. 거부/실패는 반드시 사용자 또는 로그에 드러낸다

#### T-24 후속 — "클라만 새 빌드, 서버는 옛 빌드"의 함정
- **증상**: 클라 로그에는 `[MockUserApi] 아바타 저장(모의): rt|1=SK_HUMN...`처럼 **긴 인코딩이 정상 생성**되는데, `[AvatarVisual] 적용`은 계속 `runtime=False`
- **판독법**: 이 조합은 "클라는 새 코드 / 서버는 옛 코드"의 지문이다
  - 클라(새 코드)는 600자 인코딩을 만들어 RPC 전송 ✅
  - 서버(옛 코드)의 `RequestChangeServerRpc`가 `Decode(...).Encode()`로 재인코딩 → 옛 500자 제한에 걸려 **`sk_01` 반환** → 현재 값과 동일 → `OnValueChanged` 미발화 → 화면 무변화
- **해결**: Linux Server 빌드 → 이미지 재빌드 → 컨테이너 교체 (Web 빌드와 **항상 쌍으로**)
- **재발 방지 (코드에 반영)**:
  1. 서버 RPC에서 **재인코딩 제거** — 길이 검증 후 받은 값을 그대로 기록
  2. 클라가 요청 후 2초 내 반영이 없으면 HUD에 `server did not apply the change — 서버(Docker) 빌드가 최신인지 확인` 표시
- **서버 로그 확인법**: 브라우저 콘솔에는 서버 로그가 안 나온다. `docker logs -f festa-world`로 `[Appearance] 서버 반영: client=.. len=..`이 찍히는지 본다 (안 찍히면 서버가 옛 빌드)

### T-25. 서버를 새로 빌드했는데 계속 옛 동작 — 이름 다른 옛 컨테이너가 포트를 점유 (2026-08-12)

### T-26. Docker 빌드가 `chmod: cannot access '/app/festa-unity.x86_64'`로 실패 (2026-08-12)
- **증상**: `[6/6] RUN chmod +x /app/festa-unity.x86_64` 단계에서 no such file. 로그의 `transferring context: 3.57kB`가 단서
- **원인**: **빌드 컨텍스트를 `Docker/` 폴더로 지정**했다. 이 Dockerfile은 `COPY . /app`으로 컨텍스트 전체를 복사하므로 컨텍스트가 **Linux Server 빌드 출력 폴더**여야 한다
- **해결**: `docker build -t festa-world:dev -f Docker/Dockerfile Builds/linux-server` (festa-unity 폴더에서 실행)
- **판별법**: `transferring context`가 수 KB면 실행 파일이 안 들어간 것 (정상은 수십~수백 MB)

### T-27. 파츠를 바꾸면 캐릭터가 T포즈로 굳는다 (2026-08-12)
- **증상**: Custom 모드로 파츠를 조립하면 외형은 정상인데 애니메이션이 전혀 재생되지 않고 T포즈. 프리셋 모드에서는 정상
- **원인**: Sidekick `SidekickRuntime.CreateCharacter()`는 생성한 캐릭터에 Animator를 붙이고 **avatar(휴머노이드 정의)까지 복사**하지만, `runtimeAnimatorController`는 **생성자에 넘긴 컨트롤러가 있을 때만** 설정한다.
  ```csharp
  // Synty 원본 (SidekickRuntime.cs)
  Animator newModelAnimator = newSpawn.AddComponent<Animator>();
  newModelAnimator.avatar = baseModelAnimator.avatar;
  newModelAnimator.Rebind();
  if (_currentAnimationController != null)          // ← 우리는 null로 생성했다
      newModelAnimator.runtimeAnimatorController = _currentAnimationController;
  ```
  우리는 `new SidekickRuntime(baseModel, material, null, _db)`로 만들었으므로 **Controller가 비어 있는 Animator**가 생성된다 → 재생할 상태 머신이 없어 바인드 포즈(T포즈) 그대로 멈춘다
- **해결**:
  1. `PlayerAvatarVisual`의 인스펙터 슬롯 **Animator Controller에 `AvatarAnimator` 할당** (근본 해결)
  2. 코드: 슬롯이 비어 있으면 **Player 루트 Animator의 Controller를 폴백**으로 사용하고, 그것도 없으면 콘솔에 원인을 명시
- **확인 사항**: 애니메이션 FBX(Idle/Walking)의 **Rig가 Humanoid**여야 리타게팅된다. Generic이면 다른 스켈레톤에 적용되지 않는다. Animator 인스펙터의 `Clip Count: 0`은 컨트롤러에 클립이 없다는 신호
- **교훈**: 외부 SDK가 컴포넌트를 "붙여준다"고 해서 **설정까지 채워주는 건 아니다**. 생성 직후 상태를 확인하고 부족분을 우리 코드가 메운다

### T-28. Codex 첨부 한글 작업지시가 깨져 보임 (2026-08-13)
- **증상**: `Get-Content`로 첨부된 작업지시를 읽으면 한글이 `?덈뒗` 같은 문자로 깨지고, 여러 문서를 한 번에 읽는 조회가 응답 없이 멈춤
- **원인**: Windows PowerShell의 기본 출력 인코딩과 UTF-8 첨부 파일 인코딩이 일치하지 않음. 대용량 문서 일괄 출력도 도구 응답을 지연시킴

- **예방**: 한글 문서는 처음부터 UTF-8을 명시해 읽고, 긴 문서는 필요한 파일별로 나눠 출력한다

### T-32. CharacterLobby 플레이 시 Catalog 참조 NullReference (2026-08-13)

### T-35. Unity MCP로 프로젝트 외부 한글 폰트를 직접 임포트할 수 없음 (2026-08-13)

### T-54. 플레이 중 Game View 강제 갱신으로 PlayerLoop 재귀 오류 발생 (2026-08-14)
- **증상**: 최종 화면 캡처를 강제로 갱신하는 과정에서 `PlayerLoop internal function has been called recursively` 오류가 기록되고 Unity MCP 연결이 일시적으로 끊겼다.
- **원인**: 플레이 모드에서 `EditorApplication.QueuePlayerLoopUpdate()`와 `InternalEditorUtility.RepaintAllViews()`를 함께 호출해 실행 중인 PlayerLoop 안에서 추가 PlayerLoop 갱신을 요청했다.
- **해결**: Unity 연결을 복구한 뒤 강제 갱신 호출을 제거하고, Game View 창에 포커스만 준 다음 한 프레임 이상 기다려 일반 스크린샷을 촬영했다. 최종 재컴파일 후 Console Error 0건을 확인했다.
- **예방**: 플레이 모드 캡처에서는 PlayerLoop/Repaint 강제 호출을 사용하지 않고 `GameView.Focus()` → 대기 → 캡처 순서만 사용한다.

- **예방**: 외부 ShaderGraph는 속성 존재만 보고 재사용하지 않고 실제 플레이 렌더를 확인하며, 비호환이면 원본 텍스처·속성 계약을 유지하는 프로젝트 전용 셰이더를 사용한다.

### T-88. 의상 셰이더에서 `_BaseMap` 재정의 컴파일 오류 (2026-08-14)

### T-89. 벤더 셰이더 JSON 조사 도구와 PowerShell 인라인 명령 호환 문제 (2026-08-14)
- **증상**: 벤더 ShaderGraph 내부 계산식을 조사하는 과정에서 `jq`와 기본 `python` 실행 파일을 찾을 수 없었고, Node 인라인 코드와 PowerShell 와일드카드 경로는 따옴표·경로 해석 오류로 여러 번 중단됐다.
- **원인**: 현재 작업 환경의 기본 PATH에 JSON 분석 도구가 없었으며 PowerShell, `cmd`, Node가 각각 따옴표와 와일드카드를 다르게 해석했다.

- **예방**: 대형 ShaderGraph JSON을 조사하기 전 사용할 런타임과 명령 해석기를 먼저 고정하고, Windows에서는 셸 사이에 와일드카드나 중첩 따옴표를 넘기지 않는다.

### T-91. 아키텍처 점검 중 문서 경로와 검색 정규식 가정 오류 (2026-08-14)
- **증상**: Frontend·Unity 설계 문서를 읽는 첫 호출이 실제 파일명의 `설계서` 접미사를 누락해 실패했고, 여러 검색어를 한 정규식으로 묶은 명령은 PowerShell 따옴표 해석 때문에 정규식이 닫히지 않았다. 후속 Markdown 검사에서는 Git이 한글 경로를 따옴표와 8진 escape로 출력한 값을 실제 경로로 넘겨 `Test-Path`가 실패했다.
- **원인**: 파일명을 먼저 열거하지 않고 문서 인덱스의 표시명을 경로로 추정했으며, 셸 명령 문자열 안에 중첩 따옴표를 사용했다. 또한 `git diff --name-only`의 기본 `core.quotePath` 출력을 PowerShell 경로로 바로 재사용했다.

- **예방**: 문서 경로는 `rg --files` 또는 디렉터리 목록으로 확인한 뒤 사용하고, PowerShell에서 복수 검색어는 복잡한 그룹 정규식보다 여러 `-e` 옵션을 사용한다. Git 경로 목록을 재사용할 때는 `-c core.quotePath=false`를 지정하거나 셸의 파일 객체를 직접 사용한다.

### T-95. 피부색 변경이 기본 Body 속옷까지 피부색으로 덮음 (2026-08-15, 해결)

- **예방**: 브랜치 간 문서 동기화는 전체 브랜치 포인터를 이동하지 말고 docs 전용 커밋만 적용한다. spec 디렉터리 이동 여부와 브랜치별 기록 차이를 먼저 비교하고, 충돌 시 최신 내용으로 덮어쓰기보다 양쪽 이력을 병합한다.

### T-100. WebGL 창 비율 변경 시 패널 내부 카드와 패딩이 제각각 이동함 (2026-08-15, 해결)

- **증상**: Game View 또는 웹 캔버스의 폭을 줄이거나 넓히면 좌·우 패널의 고정 크기 카드와 정규화 Anchor가 서로 다른 스케일 기준을 사용해 간격과 정렬이 달라졌다.
- **원인**: CanvasScaler가 폭과 높이를 항상 0.5로 혼합했지만 UI는 1600×900 고정 픽셀 크기 LayoutGroup과 비율 Anchor를 함께 사용했다. 화면 비율이 기준과 달라질수록 유효 좌표계가 1600×900에서 벗어났다.
- **해결**: 전체 UI를 `AspectRatioFitter(FitInParent)`가 적용된 16:9 프레임으로 묶고, 좁은 화면은 폭 기준·넓은 화면은 높이 기준으로 CanvasScaler를 전환했다. 미리보기 입력 경계도 실제 중앙 패널 RectTransform을 사용하도록 바꿨다.
- **예방**: WebGL용 고정 구도 UI는 최상위 기준 프레임을 하나만 두고, 패널 Anchor·LayoutGroup·입력 Hit Area를 모두 그 프레임의 자식으로 둔다. 16:9뿐 아니라 세로형·초광폭 Game View에서 프레임 내부 좌표와 카드 간격이 동일한지 확인한다.

- **예방:** 씬 전환 데이터, 접속 승인 데이터, 서버 동기화 데이터를 같은 필드로 재사용하지 않는다. WebGL 외형 검증은 파츠 존재뿐 아니라 Shader 포함·텍스처 속성·유효 색상까지 확인하고 Dedicated Server와 WebGL을 같은 리비전으로 배포한다.
- **검증:** Unity MCP 강제 Refresh/Compile 완료 후 Console Error 0건을 확인했다. 실제 배포 E2E는 같은 리비전의 새 Dedicated Server와 WebGL 조합에서 별도로 확인한다. 요청에 따라 이번 작업에서는 빌드를 수행하지 않았다.

### T-142. GitHub CLI가 설치돼 있는데도 세션에서 `gh: command not found` (2026-08-20, 해결)

- **증상:** `gh --version`이 `command not found`로 실패해 GitHub PR 생성·머지 경로가 없다고 판단했다. 실제로는 `C:\Program Files\GitHub CLI\gh.exe`가 존재하고 `kanghyunsoon` 계정으로 로그인까지 돼 있었다(`repo`, `workflow` 스코프 / 저장소 권한 ADMIN).
- **원인:** `C:\Program Files\GitHub CLI\`가 **영구 Machine PATH에는 있지만 현재 프로세스의 PATH에는 없다.** Windows에서 PATH는 프로세스 생성 시점에 복사되므로, Claude Code를 띄운 뒤에 gh를 설치하면 그 세션은 끝까지 새 PATH를 보지 못한다. `where.exe gh` 실패를 "미설치"로 읽은 것이 오판의 원인이다.
- **해결:** 세션 안에서는 `export PATH="$PATH:/c/Program Files/GitHub CLI"`로 즉시 사용 가능하다. 영구 해결은 **Claude Code 재시작** — Machine PATH에 이미 등록돼 있으므로 새 프로세스는 그대로 잡는다.
- **예방:** CLI가 "없다"고 판단하기 전에 프로세스 PATH와 영구 PATH를 나눠서 확인한다.
  - 프로세스: `powershell -NoProfile -Command '$env:Path'`
  - 영구: `[Environment]::GetEnvironmentVariable('Path','Machine')` / `...('Path','User')`
  - 둘이 다르면 미설치가 아니라 **재시작 필요**다.
- **비고:** 같은 이유로 이전 세션 기록의 "GitHub는 직접 연결 경로가 없다"는 판단은 사실과 다르다. GitKraken 플러그인 로그인 없이도 `gh` CLI로 PR 생성·리뷰·머지가 모두 가능하다.

### T-144. GitHub Issue에 스크린샷을 첨부할 수단이 없음 (2026-08-20, 해결)

- **증상**: 검증 스크린샷을 이슈 댓글에 붙이려는데 방법이 없었다. `gh` CLI에는 이미지 업로드 명령이 없고, 웹 UI의 드래그앤드롭은 `user-images.githubusercontent.com` 업로드용 **브라우저 세션 전용 엔드포인트**라 PAT/OAuth 토큰으로 호출할 수 없다. 로컬 `git add`로 커밋하는 우회로도 `.git/index.lock` 잔여 파일 때문에 막혀 있었다 (T-127 재발).
- **원인**: GitHub은 이슈 첨부 이미지 업로드를 공개 API로 제공하지 않는다. 커밋된 저장소 파일을 참조하는 방식만 API로 가능하다.
- **해결**: **Contents API로 원격에 직접 커밋**했다. 로컬 인덱스를 거치지 않으므로 `index.lock`과 무관하다.

  ```bash
  gh api --method PUT repos/{owner}/{repo}/contents/{path} --input payload.json
  # payload.json = {"message": "...", "content": "<base64>", "branch": "game"}
  ```

  그 뒤 댓글에서 `https://github.com/{owner}/{repo}/blob/{branch}/{path}?raw=true` 로 참조했다.
- **검증**: 비공개 저장소라 실제로 보이는지가 관건이었다. 확인 결과 GitHub이 이 URL을 **camo 프록시로 다시 쓰지 않고 그대로 둔다** — 동일 출처(github.com)라 브라우저가 로그인 세션 쿠키로 직접 받아온다. 실제 Chrome에서 `img.complete=true`, `naturalWidth=900` 으로 렌더링을 확인했다.
- **예방**: 비공개 저장소 이슈에 이미지를 넣을 때는 이 경로를 쓴다. **Bearer 토큰으로 `github.com/.../blob/...?raw=true` 를 curl하면 404가 나오는데 이는 실패가 아니다** — 그 엔드포인트는 세션 쿠키만 받는다. 파일 존재 확인은 `raw.githubusercontent.com` 이나 Contents API로 한다.
- **비고**: 프로젝트 규칙상 `Assets/Screenshots/`는 커밋 대상이 아니므로, 검증 근거만 기존 `docs/LJH/verify/` 관례에 맞춰 `docs/KHS/verify/`에 두었다.

### T-145. 잘못된 `assetCode`가 아무 신호 없이 기본 자산으로 대체됨 (2026-08-20, 미해결 — 정책 판단 대기)

- **증상**: Layout JSON에 등록되지 않은 `assetCode`(예: `BOGUS_CODE_999`)를 보내면 오브젝트가 타입 기본 프리팹으로 정상 생성되고 **경고 로그가 한 줄도 남지 않는다.** 화면에 뭔가 그려지므로 FE 편집기에서 오타를 냈을 때 틀린 사실을 알 방법이 없다.
- **원인**: `BoothObjectRegistry.GetPrefab`이 asset map 조회 실패 시 조용히 타입 기본 맵으로 넘어간다. fallback 자체는 의도된 동작(오브젝트를 잃지 않음)이지만, 조회 실패와 `assetCode` 미지정을 구분하지 않는다.
- **성격**: T-134(`objectId` 누락으로 이벤트가 조용히 차단됨)와 **같은 계열**이다. 실패가 관측되지 않아 원인 추적이 어렵다.
- **해결**: 미해결. `assetCode`가 비어 있지 않은데 asset map에 없을 때만 `Debug.LogWarning`을 남기는 방향을 GitHub Issue #6에 제안해 두었다. FE 편집기 저장 시점 검증으로 갈 수도 있어 파트 간 판단이 필요하다.
- **예방**: fallback을 넣을 때 "값이 없어서 기본을 쓴 경우"와 "값이 있는데 못 찾아서 기본을 쓴 경우"를 구분한다. 후자는 거의 항상 오류이므로 로그를 남긴다.

### T-146. 타입마다 프리팹이 1개뿐이라 `assetCode` 선택 로직을 종단 검증할 수 없음 (2026-08-20, 구조적 제약 — 카탈로그 확장 후 재검증)

- **증상**: `assetCode`를 지정한 오브젝트와 지정하지 않은(또는 틀린 값을 준) 오브젝트가 **완전히 동일하게 생성된다.** 생성 결과만 보고는 `assetCode`가 실제로 사용됐는지 판정할 수 없다.
- **원인**: 버그가 아니라 카탈로그 상태다. `BoothObjectRegistry`에 타입별 프리팹이 정확히 1개씩 등록돼 있어 `assetMap[Furniture:FURNITURE_DEFAULT]`와 `_map[Furniture]`가 같은 자산을 가리킨다. 두 코드 경로의 결과가 구분되지 않는다.
- **해결**: 종단 대신 `GetPrefab`을 직접 호출해 로직을 검증했다. 특히 `(SurveyKiosk, "FURNITURE_DEFAULT")` → `SurveyKiosk` 반환으로 조회 키가 `type:assetCode` 복합키임을 확인했고, 대소문자 무시(`OrdinalIgnoreCase`)와 미등록 코드 fallback도 확인했다.
- **예방**: 자산 선택 로직을 검증할 때는 **선택지가 2개 이상인지 먼저 확인**한다. 선택지가 하나면 어떤 분기를 타도 결과가 같아 검증이 성립하지 않는다. 이런 경우 블랙박스 관측이 아니라 조회 함수를 직접 호출해 분기를 확인한다.
- **후속**: 프리팹 카탈로그를 한 타입 2개 이상으로 확장한 뒤 종단 재검증이 필요하다. FE에서 사용할 `assetCode` 목록을 받아 카탈로그에 맞춰 등록하기로 Issue #6에 남겼다.

- **원인**: 판단 착오였다. 등록 전에 서버가 OAuth 메타데이터를 광고하는 것만 확인했다 — `www-authenticate` 헤더의 `resource_metadata`, 그리고 `authorization_servers: ["https://github.com/login/oauth"]`. **그러나 Claude Code의 자동 OAuth는 동적 클라이언트 등록(DCR, RFC 7591)을 요구하고 GitHub OAuth 서버는 이를 지원하지 않는다.** "OAuth 메타데이터를 광고한다"와 "이 클라이언트가 OAuth로 붙을 수 있다"는 별개다.
- **해결**: 플러그인 원본 설정대로 PAT 헤더 방식으로 되돌렸다.

  ```json
  "github": {
    "type": "http",
    "url": "https://api.githubcopilot.com/mcp/",
    "headers": { "Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}" }
  }
  ```

  토큰은 `gh` CLI가 이미 보유한 것을 파이프로 넘겨 환경변수에 심는다(화면에 노출되지 않음).

  ```powershell
  [Environment]::SetEnvironmentVariable('GITHUB_PERSONAL_ACCESS_TOKEN', (gh auth token), 'User')
  ```
- **예방**: 원격 MCP 서버의 인증 방식은 메타데이터 광고만으로 판단하지 않는다. **`claude mcp list`로 실제 연결 결과를 확인**한 뒤 결론을 낸다. 이번엔 등록 후 health check를 돌리지 않아 실패를 늦게 발견했다.
- **비고**: 앱(Cowork/데스크톱)에서 `github`가 목록에 아예 안 보이는 것은 별개 원인이다 — T-140과 같은 세션별 노출 범위 차이로, 프로젝트 `.mcp.json`은 CLI만 읽는다. 앱에서도 쓰려면 앱 쪽 MCP 설정에 같은 서버를 등록해야 한다.

### T-148. 타입 기본 자산이 Registry 배열 순서로 결정되고, 조회 맵 캐시가 무효화되지 않음 (2026-08-20, 미해결 — 정책 판단 대기)

### T-149. 새 월드 모델(.skp)이 구 모델(.fbx)과 축·스케일이 달라 그대로 놓으면 스폰 좌표가 어긋남 (2026-08-20, 해결)

### T-151. 방을 다시 만든 모델은 랜드마크가 아니라 방 쉘 기준으로 정렬해야 한다 (2026-08-20, 해결)

- **증상**: `11th-0820-size(0.8).skp`로 월드를 교체했더니 **사물함 패널 16장이 방 벽 바깥으로 흩어졌다.** 좌표·바닥 높이(`y=0.082`)·머티리얼 검증은 전부 통과했는데도 방이 무너져 보였다.
- **배경**: 이 모델은 엘리베이터 칸을 다시 만들어 받은 것이고, 그 과정에서 전체가 0.8배가 됐다. 즉 **크기 변경과 형상 변경이 같이 들어온 파일**이다.
- **원인 — 정렬 기준을 잘못 골랐다**
  - 방 쉘 치수를 비교하면 **X와 Y는 정확히 0.8배**(`21.7642×0.8=17.4114`, `5.5353×0.8=4.4282`)인데 **Z만 0.8배가 아니다**(`24.8949×0.8=19.9159`인데 실제 `17.0346`). 엘리베이터 쪽이 짧아졌기 때문이다.
  - 그런데 나는 **패널 텍스트 랜드마크 23개**로 평행이동을 역산했다. 그 랜드마크들은 방이 아니라 벽면 패널 클러스터에 몰려 있어서, 결과적으로 **방이 아니라 패널을 기준으로 정렬**됐다. 방 길이가 바뀐 모델에서는 이 둘이 같지 않다.
- **해결 — 두 단계**
  1. **방 쉘(`ssafy-11th-room`) 기준으로 정렬한다.** 기존 방의 world 범위(`x -202.20~15.44`, 바닥 `y=-5.80`, `z -332.95~-84.00`)에 맞춰 역산하면 `localPosition (-5.125, 1.45, 94.0375)` / `localRotation (0,180,0)` / `localScale (12.5, 12.5, 12.5)`. 방 X와 바닥 Y는 정확히 일치하고, Z는 **먼 쪽 벽을 고정**한다(엘리베이터가 있는 반대쪽이 기준).
  2. **패널 두 줄을 방 끝벽으로 스냅한다.** 방이 짧아진 만큼(약 36) 패널이 양 끝에서 바깥으로 밀려 있다. 깊이≈0·높이≈49인 얇은 패널만 골라 방 바깥에 있는 것을 두 줄로 나누고, 각 줄을 해당 끝벽에 맞춘다 — 먼 줄 `-25.77`, 가까운 줄 `+23.86`. 줄 내부의 엇갈린 배치(알코브)는 균일 이동이므로 보존된다.
- **검증**: 스폰 5개 지점 전부 `y=0.082`. 바닥 격자 레이캐스트(x −195~10, z −330~−130) **441/441 전부 명중, 구멍 0**. 콜라이더 바운즈 `(217.64, 55.35, 212.93)`. 머티리얼 1681개 전부 URP/Lit. Console Error 0건.
- **예방**
  - **형상이 바뀐 모델은 랜드마크로 정렬하지 않는다.** 랜드마크는 "모델이 같고 크기만 다를 때"만 유효하다. 방 치수를 축별로 비교해 **어느 축이 0.8배가 아닌지** 먼저 확인하면 형상 변경을 바로 알 수 있다.
  - 정렬 기준은 **가장 큰 불변 구조물(방 쉘)** 로 잡는다. 그리고 길이가 바뀐 축은 **어느 끝을 고정할지** 명시적으로 정한다.
  - **육안 검증은 방 전체가 보이는 외부 시점에서 한다.** 지상 시점 스크린샷은 좌표가 맞았는지만 보여주고 배치 붕괴는 감춘다 — 이번에 그래서 한 번 놓쳤다.
- **주의 — 씬 레벨 보정이다**: 패널 스냅은 씬 인스턴스의 자식 Transform을 옮긴 것이다. 모델을 재임포트하거나 인스턴스를 다시 만들면 사라진다. 근본 수정은 SketchUp에서 패널을 새 방 길이에 맞춰 옮겨 재익스포트하는 것이다. 그때까지는 이 문서의 스냅값이 복구 절차다.

### T-152. Asset Store 팩(2018)을 임포트하면 전부 마젠타 — Standard 셰이더와 빈 머티리얼 슬롯 (2026-08-20, 해결)

- **증상**: Stand Expo Pack(Unity 5.6 기준, 2018) 임포트 후 프리팹이 URP에서 마젠타로 보인다.
- **원인 두 가지**
  1. 팩 머티리얼 23개가 전부 `Standard` / `Standard (Specular setup)` 셰이더다. URP는 이 셰이더를 렌더할 수 없다.
  2. 일부 서브메시가 **머티리얼 슬롯이 비어 있어** Unity 기본 `Default-Material`(`Resources/unity_builtin_extra`, Standard)로 폴백한다. 이건 머티리얼 변환으로 해결되지 않는다 — GUID 검색·머티리얼 순회로도 안 잡히고, 프리팹의 렌더러 슬롯을 직접 봐야 보인다.
- **해결**
  1. 23개 머티리얼을 `Universal Render Pipeline/Lit`으로 변환하고 프로퍼티를 옮겼다: `_MainTex→_BaseMap`, `_Color→_BaseColor`, `_Glossiness→_Smoothness`, `_BumpMap`·`_MetallicGlossMap`·`_OcclusionMap`·`_EmissionMap`은 이름 동일. 타일링·오프셋도 이전하고 `_NORMALMAP`·`_METALLICSPECGLOSSMAP`·`_OCCLUSIONMAP`·`_EMISSION` 키워드를 켰다. Specular setup 은 `_Metallic = 0` 으로 뒀다.
  2. 조립한 프리팹 10개를 `LoadPrefabContents`로 열어 렌더러 슬롯을 순회하며 빈/Standard 슬롯 **17개**에 팩 머티리얼(PlasticWhite·PlasticBlack·Aluminium)을 오브젝트 이름 기준으로 할당했다.
- **예방**: 외부 팩 임포트 직후 **① 머티리얼 셰이더 분포 ② 프리팹 렌더러의 빈 슬롯** 두 개를 먼저 확인한다. ①만 고치면 ②가 남아 일부만 마젠타로 보인다.
- **비고**: 팩 프리팹은 루트에 회전이 박혀 있다(대부분 `(270,0,0)`, 트러스 일부는 `(0,270,90)`). **회전을 초기화하면 눕는다.** 조립 시 `localRotation = Euler(0,yaw,0) * prefab.transform.rotation` 으로 프리팹 회전 위에 yaw 만 곱해야 한다.

### T-153. 부스 오브젝트가 아바타 옆에서 9배 작았다 — 월드 1m = 10 unit (2026-08-20, 해결)

- **증상**: 부스 프리팹을 배치해도 아바타에 비해 터무니없이 작다.

### T-160. 1 m = 10 unit 월드에서는 점광원 세기가 100배 필요하다 (2026-08-20, 해결)

- **증상** — 천장 기구마다 Spot 광원을 넣었는데 바닥이 거의 어두웠다.
  세기를 9 → 26 으로 올려도 체감 차이가 거의 없었다.
- **원인** — URP 점광원 감쇠는 `1/d²` 다. 이 월드는 **1 m = 10 unit** 이므로(T-153)
  천장까지 4.95 m 가 **49.5 unit** 이고, 감쇠는 `1/49.5² ≈ 0.000385` 다.
  세기 26 이면 바닥에 0.01 밖에 안 닿는다. 1:1 스케일 감각으로 잡은 값이 전부 무의미했다.
  그동안 밝기는 사실상 **환경광이 전부 담당**하고 있었다.
- **해결** — 감쇠를 실제로 계산해서 역산했다. 바닥에서 1.0 을 얻는 단일 광원 세기는
  `1/0.000385 ≈ 2600`. 광원이 겹치는 것을 감안해 Spot 420 / Point 260 으로 잡으니
  사진과 비슷한 밝기가 됐다. 환경광은 0.46 → 0.20 으로 낮춰 빛 웅덩이가 보이게 했다.
- **예방** — 스케일이 1 이 아닌 월드에서 조명을 잡을 때는 **감쇠를 먼저 계산한다.**
  `atten = (1/d²) × (1 - (d²/range²))²`. 세기를 눈대중으로 올리며 스크린샷을
  반복하는 것은 자릿수가 틀린 경우 아무 효과가 없어 시간만 버린다.
- **연관** — T-153(부스 파츠가 9배 작았던 것)과 같은 뿌리다. 이 월드에서
  **길이·조명·물리 값은 전부 10 배(또는 10²) 보정**이 필요한지 먼저 따진다.

- **부수** — `ClearCache` 가 `Object.Destroy` 를 써서 에디트 모드에서
  `Destroy may not be called from edit mode` 가 났다. `Application.isPlaying` 으로

### T-165. 합성 마우스 이벤트는 Unity WebGL 입력에 닿지 않는다 (2026-08-20, 우회)

- **증상** — 브라우저에서 `PointerEvent`/`MouseEvent` 를 캔버스에 dispatch 해
  Unity 오브젝트를 클릭하려 했다. 캔버스 전체에 **2,560 발**을 뿌렸는데 반응 0건.
- **원인** — Unity WebGL 입력은 브라우저의 신뢰된(trusted) 이벤트만 처리한다.
  `dispatchEvent` 로 만든 합성 이벤트는 `isTrusted=false` 라 무시된다.
- **해결(우회)** — 두 가지 중 하나를 쓴다.
  1. 실제 클릭 도구(브라우저 자동화의 진짜 마우스 입력)를 쓴다.
  2. **입력을 우회해 `unityInstance.SendMessage(오브젝트명, 메서드, 인자)` 로 직접 호출**한다.
     이번 브리지 검증은 이 방법으로 했다 — 입력 계층이 아니라 JS 경계를 시험하는 것이 목적이었다.
- **주의** — 기본 WebGL 템플릿은 `unityInstance` 를 `.then()` 클로저에 갇혀 두고
  전역에 노출하지 않는다. 검증용 호스트 페이지를 따로 만들어
  `window.unityInstance = inst` 로 노출해야 `SendMessage` 를 쓸 수 있다.
  (FE 도 실제로 이렇게 붙이므로 계약 검증에도 더 가깝다.)

### T-167. 콜라이더가 없어서가 아니라 이동이 물리를 쓰지 않았다 (2026-08-21, 해결)

- **증상** — 11층 맵에서 벽·구조물을 다 통과한다. "콜라이더가 없다" 로 보였다.
- **원인** — `PlayerMovement` 가 `transform.position += dir * speed * dt` 로 직접 옮겼다.
  물리 질의를 하지 않으므로 **콜라이더를 아무리 붙여도 효과가 없다.**
  코드 주석에 `POC 수준 — CharacterController/물리는 월드 확정 후` 로 예고돼 있었다.
- **해결** — `CharacterController` 로 이동한다.
  - 프리팹의 기존 `CapsuleCollider`(radius 2.2 / height 13.5 / center y 6.75) 값을 그대로 옮기고
    캡슐은 제거했다. 둘을 함께 두면 서로 밀어낸다.
  - `stepOffset 3.0`(0.3 m 문턱), `slopeLimit 45`, `skinWidth = radius × 0.08`.
  - **중력은 1 m = 10 unit 보정이 필요하다** — 9.81 m/s² = **98.1 unit/s²** (T-160 과 같은 함정).
  - 접지 중에는 하강 속도를 −20 로 유지해 경사·단차에서 붙어 있게 했다.
  - `CharacterController` 가 없으면 예전처럼 transform 을 옮긴다 — 구 프리팹·테스트 씬이 멈추지 않게.
- **멀티플레이** — 이동은 client-authoritative 다(`OnIsServerAuthoritative() => false`).
  각 Owner 가 자기 클라이언트에서 충돌을 해결하고 결과 위치만 복제되므로 월드 콜라이더는
  각 클라이언트 씬에 있으면 되고, 월드는 로컬 씬 오브젝트라 자동으로 충족된다.
  **원격 플레이어는 `CharacterController` 를 끈다** — NetworkTransform 의 transform 대입과 싸운다.
- **`Player` 레이어를 만들고 Player↔Player 충돌을 껐다.** client-authoritative 에서 서로 밀면
  클라이언트마다 밀린 결과가 달라 위치가 어긋나고 떨린다. 40명 로비에서 서로 막는 것도
  통행을 방해한다. 되돌리려면 충돌 매트릭스에서 다시 켜면 된다.

### T-168. `GetComponent<T>() ?? AddComponent<T>()` 는 동작하지 않는다 (2026-08-21, 해결)

- **증상** — 콜라이더를 붙이는 코드에서
  `MissingComponentException: There is no 'MeshCollider' attached to the "Group 50" game object` 가 났다.
- **원인** — Unity 의 `GetComponent<T>()` 는 컴포넌트가 없을 때 **진짜 null 이 아니라
  네이티브 포인터가 빈 래퍼**를 돌려준다. 실측:
  ```
  existing == null                    → True
  ReferenceEquals(existing, null)     → False
  ```
  `==` 는 `UnityEngine.Object` 가 연산자를 재정의해 true 지만, `??` 는 참조로만 판단하므로
  **단축평가되지 않는다.** 그 래퍼가 그대로 반환되고 값을 대입할 때 예외가 난다.
- **해결** — `GetOrAdd<T>` 헬퍼로 통일했다. `c == null ? AddComponent<T>() : c`.
- **왜 안 드러났나** — 기존 코드도 같은 패턴이었는데 대상에 이미 콜라이더가 있어서
  `GetComponent` 가 실물을 돌려줬다. **처음 붙이는 경로에서만 터진다.**
- **예방** — `UnityEngine.Object` 에는 `??`·`?.` 를 쓰지 않는다. `== null` 로 비교한다.
