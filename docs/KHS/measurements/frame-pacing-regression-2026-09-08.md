# 프레임 출렁임 회귀 분석 — "늘어난 게 없는데 왜 갑자기 느려졌나" (2026-09-08)

> **이 문서의 목적**
> 지금까지 이 증상을 **최적화 문제**("씬이 무겁다")로 다뤘다. 그 전제가 틀렸을 수 있다.
> 사용자 지적 — *"아무리 생각해봐도 렉이 안 걸렸을 때보다 오브젝트나 광원이 늘어난 적이 없는데
> 갑자기 이렇게 빨라졌다 느려졌다 렉이 걸리는 이유를 모르겠네"*
>
> 늘어난 게 없다면 이건 **회귀(regression)** 다. 물어야 할 것은 "무엇이 무거운가" 가 아니라
> **"멀쩡했을 때와 지금 사이에 무엇이 바뀌었나"** 다.
>
> 이 문서는 그 조사를 처음부터 다시, 증거를 붙여 가며 기록한다. 컨텍스트가 길어져 생기는
> 노이즈를 피하려고 결론과 근거를 여기에만 쌓는다.

## 1. 확정된 사실 (근거 있는 것만)

측정으로 확인했고 아직 반박되지 않은 것들.

| 사실 | 근거 | 날짜 |
|---|---|---|

| 같은 자리에서 **시야 방향만 바꿔도 936 ↔ 239** | 위 동일 | 09-07 |

| 세 고정 포즈 모두 **vsync 바닥 100%** (p50 9.7~11.0 ms) | 고정 포즈 벤치마크 | 09-07 |
| 탭 백그라운드 복귀 시 42.6초·15.9초짜리 "한 프레임" 이 잡힌다 (draws·tris 증분 0) | HitchLogger | 09-07 |
| DPR 상한 적용 후 백버퍼 4.08 → 2.30 MP | 브라우저 실측 | 09-07 |

### 여기서 이상한 점 — 이 조사의 출발점

**고정 포즈에서는 세 곳 다 p50 9.7~11.0 ms 로 예산(16.7 ms)에 한참 못 미친다.**
그런데 걸어다니면 34~42 ms 가 나온다. 정지 상태가 멀쩡한데 이동 중에만 무너진다는 것은
**"씬이 무겁다" 로 설명되지 않는다.** 무거우면 서 있어도 무겁다.

→ 원인은 **정적 부하가 아니라 이동이 유발하는 무언가**에 있다. 이 문서는 그것을 찾는다.

## 3. 회귀 가설 — 무엇이 바뀌었나

`(조사 진행 중 — 아래는 확인해야 할 목록이고 결론이 아니다)`

### H1. 렌더 설정이 어느 시점에 바뀌었다
`Mobile_RPAsset` · `PC_RPAsset` · `Mobile_Renderer` · `QualitySettings` · `GraphicsSettings` 의 커밋 이력.
누가 언제 무엇을 왜 바꿨는지. 특히 **렉이 없었다는 시점 전후**.

### H2. 사용자 전제("늘어난 게 없다")를 데이터로 검증
`main.unity` 의 커밋별 Light / Renderer 개수. 정말 안 늘었는가?
늘었다면 언제, 무엇이. 안 늘었다면 H1·H3~H7 로 간다.

### H3. 엔진·패키지 버전이 올랐다
`manifest.json` · `packages-lock.json` · `ProjectVersion.txt` 이력. URP 마이너 버전 하나로 동작이 바뀔 수 있다.

### H4. 프레임 페이싱 설정 자체가 바뀌었다
`Application.targetFrameRate` · `QualitySettings.vSyncCount` · `Time.maximumDeltaTime` · `Time.fixedDeltaTime`.
**"빨라졌다 느려졌다" 는 물리 캐치업의 전형적 증상이기도 하다** — fixedDeltaTime 이 작거나
maximumDeltaTime 이 크면 한 프레임이 늦은 뒤 FixedUpdate 를 여러 번 돌려 다음 프레임을 또 늦춘다.
이건 정지 상태에서는 안 나고 **이동 중에만** 난다. 1절의 이상한 점과 맞는다.

### H5. 이동이 유발하는 비용
컬링 재계산 · 셰이더 변형 첫 사용 · 텍스처 스트리밍 · Forward+ 라이트 비닝 ·
NetworkTransform 송수신 · 애니메이터 LOD. **정지 시 멀쩡하고 이동 시 무너지는 것을 설명할 후보.**

### H6. FE 임베드 쪽 변화
캔버스 크기 · DPR · 오버레이 · React 리렌더가 rAF 를 밀어내는지.

### H7. 빌드 설정
개발 빌드 여부 · IL2CPP 설정 · 스트리핑 · 압축 · WebGL 메모리.
**개발 빌드는 릴리스보다 느리다** — 지금까지 전부 개발 빌드로 쟀다. 릴리스에서도 같은지 확인 필요.

## 4. 조사 로그

### 09-08 — 기준 자체가 틀렸다: 이 화면은 120 Hz 다

Unity 가 직접 잰 `Time.unscaledDeltaTime` 고정 포즈 p50 이 **9.0 / 10.0 / 11.0 ms** 였다.
60 Hz 디스플레이에서는 rAF 가 16.7 ms 보다 빨리 프레임을 주지 않으므로 **나올 수 없는 값**이다.

사용자 확인 결과:

```
내부 디스플레이 — 2880 × 1800, 120 Hz
가변 새로 고침 빈도: 지원함 (24 Hz ~ 120 Hz)
디스플레이 1: Intel(R) Arc(TM) Graphics 에 연결됨
```

| | 내가 쓰던 기준 | 실제 |
|---|---|---|
| 프레임 예산 | 16.7 ms (60 Hz) | **8.33 ms (120 Hz)** |
| 정지 상태 9.7~11 ms 판정 | "예산에 한참 여유" | **겨우 맞추는 중** |
| 이동 시 34~42 ms | 2배 초과 | **4~5배 초과** |

**어제·그제의 "예산 아래라 괜찮다" 판정은 전부 무효다.** 다만 사용자 지적대로 주사율이 계속 120 Hz
였다면 그것은 상수이므로 **"갑자기 나빠짐" 의 원인은 아니다.** 원인 후보를 바꾸는 것이 아니라
**합격선을 바꾸는** 발견이다.

### 09-08 — GPU 가 둘이고, 어느 쪽으로 그릴지 고정돼 있지 않다

```
NVIDIA GeForce RTX 4050 Laptop GPU   드라이버 32.0.15.9144 (2025-12-02)
Intel(R) Arc(TM) Graphics            드라이버 32.0.101.8424 (2026-01-06)  ← 내부 디스플레이 연결
```

`HKCU\Software\Microsoft\DirectX\UserGpuPreferences` 에 **항목이 0개**다. 즉 Chrome 이 어느 GPU 로
WebGL 을 돌릴지 **Windows 가 자동으로 고르고, 고정돼 있지 않다.**

**이건 "설정을 한 번도 안 바꿨는데 갑자기 느려졌다" 를 설명할 수 있는 몇 안 되는 후보다** —
드라이버 업데이트(인텔 쪽이 더 최신이다), Chrome 업데이트, 전원 상태 변화로 렌더 GPU 가 바뀔 수 있다.

⚠️ **이 프로젝트는 지금까지 `SystemInfo.graphicsDeviceName` 을 한 번도 기록한 적이 없다.**
어느 GPU 로 돌았는지 아무 기록이 없어서 과거와 비교가 불가능하다.
→ `FixedPoseBenchmark.LogSystemReport()` 를 추가해 앞으로 매 실행마다 남긴다.

### 09-08 — 측정 오염원: 진단 단축키가 겹쳐 있었다

`@Diagnostics` 에 붙은 컴포넌트들의 단축키가 서로 겹쳐 있었다.

| 키 | 겹친 것 |
|---|---|
| **F9** | `RenderCostProbe` 결정 스윕 **+ `PerfHud` 아바타 거리 LOD 토글** |
| **F7** | `RenderCostProbe` 조명 A/B **+ `AvatarStressSpawner` 아바타 제거** |

**즉 스윕을 돌릴 때마다 아바타 애니메이션 LOD 가 같이 뒤집히고 있었다.** 09-07 스윕 결과의
변동 일부가 여기서 왔을 수 있고, 어느 실행이 어느 LOD 상태였는지 이제 와서 복원할 수 없다.

→ 키를 전부 재배치하고 `PerfHud.cs` 에 배치표를 주석으로 박아 재발을 막았다.

**교훈**: 한 빌드 안에서 여러 A/B 도구를 쓰려면 키 배치표를 먼저 만들어라. 겹치면
**한 번 누를 때 두 가지가 바뀌고, 그것을 로그만 봐서는 알 수 없다.**

### 09-08 — TimeManager · 스트리밍은 기본값 (혐의 없음)

### 09-08 — ★ WebGL 이 내장 GPU 로 돌고 있다. RTX 4050 은 놀고 있다

`chrome://gpu` 덤프에서 확정.

```
GPU0 : VENDOR=0x8086 [Intel(R) Arc(TM) Graphics], DRIVER_VERSION=32.0.101.8424  *ACTIVE*
GPU1 : VENDOR=0x10de [NVIDIA GeForce RTX 4050 Laptop GPU], DRIVER_VERSION=32.0.15.9144
GL_RENDERER : ANGLE (Intel, Intel(R) Arc(TM) Graphics (0x00007D55) Direct3D11 vs_5_0 ps_5_0)
Optimus     : false
Has Discrete GPU : yes
```

**RTX 4050 을 두고 인텔 내장 그래픽으로 2880×1800(백버퍼 2160×1064)을 그리고 있다.**
`Optimus: false` 라 Chrome 이 자동으로 외장으로 넘어가지도 않는다.
Windows 앱별 GPU 선호(`UserGpuPreferences`)에 Chrome 항목이 없어 **고정돼 있지도 않다.**

이것이 "왜 느린가" 는 설명한다. "왜 갑자기" 는 아래와 함께 봐야 한다.

기본값 60 을 보고한다. 실제 rAF 간격은 히스토그램으로 재야 한다 — 이 값을 근거로 쓰면 안 된다.

### 09-08 — 진단 키 충돌 2차: 입력 시스템이 두 개다

키 배치를 정리했다고 했는데 **또 겹쳤다.** F2 를 히스토그램에 배정했더니 개발 접속 패널이 열리고
씬이 재로드됐다(`[Bench] 준비` 가 다시 찍혔다).

원인: **이 프로젝트는 입력 시스템을 두 개 쓴다.**

```
레거시  Input.GetKeyDown(KeyCode.F2)          — 진단 도구 전부
신규    Keyboard.current.f2Key.wasPressed…    — DevConnectionHud(F2)
                                                게임플레이 F·C·H·Space·Esc·Alt
```

1차 감사에서 `KeyCode.F<숫자>` 리터럴만 grep 해서 `f2Key` 를 놓쳤다.
**두 물리 키가 같은 입력을 각자 받으므로 한 번 누르면 둘 다 발동한다.**

→ 히스토그램 키를 `Backslash(\)` 로 옮겼다. 앞으로 진단 키를 추가할 때는
   **두 입력 시스템을 모두 훑어야 한다** — `Input.GetKeyDown` 과 `Keyboard.current.*Key` 둘 다.

### 09-08 — ★ 화면이 둘인데 주사율이 다르다 (120 Hz / 60 Hz)


**rAF 는 창이 놓인 화면의 주사율을 따른다.** 브라우저 창을 화면 사이로 옮기거나 걸쳐 두면
프레임 간격이 **8.3 ms ↔ 16.7 ms** 로 바뀐다. 설정을 하나도 안 건드려도 창 위치만으로
"빨라졌다 느려졌다" 가 만들어진다. 측정할 때 창이 어느 화면에 있었는지 기록한 적이 한 번도 없다.

### 09-08 — ★ Chrome 이 나흘 전에 업데이트됐다

## 6. 결론

> **⚠️ 2026-09-08 정정** — 아래 6-1 은 처음에 "씬에 아무것도 추가되지 않았다, 사용자 관찰이 정확했다"
> 고 썼는데 **틀렸다.** 씬은 늘었다(6-0 참조). 다만 **늘어난 방향이 사용자가 생각한 방향과 다르다.**
> 그리고 6-1 의 `da3f05ec` 는 회귀의 **일부**이지 단독 원인이 아니다.

### 6-0. ★ 정정 — 씬은 늘었다. 그런데 결정적인 것은 far clip 이다

**씬 파일 기준 실측** (`grep -c "^Light:"` 등을 커밋마다):

| 날짜 | 커밋 | Light | MeshRenderer | GameObject |
|---|---|---:|---:|---:|
| 08-26 | `8d0951f6` | 143 | 266 | 596 |
| 08-29 | `169d8cf8` | 158 | 277 | 851 |
| 09-01 | `be720cb7` | 180 | 267 | 877 |
| 09-02 | `5f95b6a0` | 175 | 312 | 933 |
| 09-07 | `59cdb072` | **193** | 325 | 635 |

조명 143 → 193 (+35%), 메시 266 → 325 (+22%). **늘었다.**
(프리팹 인스턴스는 씬 파일에서 안 펼쳐지므로 런타임 실제 수는 더 크다 — 09-07 런타임 실측 활성 조명 233개.)

**그런데 더 큰 변화가 같은 날 있었다:**

```
81f790cc   2026-09-01
feat(world): 축제존에 성·관람차 원경 배경과 카지노 직원·오락기 도입 (S15P21A604-355)

-  far clip plane: 2800      (211 m)
+  far clip plane: 5200      (392 m)
```

**시야 거리가 2배가 됐다.** 오브젝트를 새로 놓지 않아도 **원래 멀리 있던 것들이 시야에 끌려 들어온다.**
어제 T-135 에 적은 "far clip 5200 이라 맵 밖 부스 12실이 일직선으로 들어온다" 가 바로 이것의 결과다.

**이것이 사용자 관찰과 실제 데이터를 화해시킨다.**
- 사용자: *"오브젝트나 광원이 늘어난 적이 없다"* → 눈에 띄게 새로 놓은 것은 별로 없다는 뜻으로는 **맞다**
- 데이터: 조명 +35%, 메시 +22% → **늘긴 늘었다**
- 결정타: **far clip 2배** → 화면은 비슷해 보이는데 그리는 양만 급증한다

08-29 vs 09-05 같은 자리 실측이 이 모양을 그대로 보여준다 (`docs/KHS/28_최적화_기법_정리.md`):

```
드로우콜  568 → 577   (거의 불변)
삼각형    443,122 → 1,009,960   (2.3배)
```

**드로우콜은 안 늘고 삼각형만 2.3배** — 물건 수가 는 것이 아니라 **먼 곳의 큰 것들이 시야에 들어온** 형태다.

### 6-0-b. ★ 내가 저지른 측정 오류 — 두 숫자는 다른 빌드다

내가 "정지 9.7~11 ms / 이동 34~42 ms" 를 나란히 놓고 "이동이 유발하는 무언가" 라고 했는데,

| | 빌드 | 포함 |
|---|---|---|
| 이동 34~42 ms | 09-07 16:23~17:00 | `aaf4d9e4` 까지 |
| 고정 포즈 9.7~11 ms | **09-08 09:18** | `623bca64` · `ea54aa11` · **`59cdb072`** |

`59cdb072` 는 **축제장 동향 시야의 렌더러를 936 → 564 로 39% 깎았다.** 고정 포즈 3지점 중
"축제서끝 동향" 이 바로 그 방향이다. **즉 어제 고친 효과가 고정 포즈 쪽에만 반영된 비교였다.**

**오늘 같은 빌드로 다시 재니 정지 54.8 fps / 이동 54.5 fps 로 평균이 같았다.**
→ "이동이 평균을 무너뜨린다" 는 **성립하지 않는다.** 이동은 **분산을 키운다.**

### 6-0-c. 시야 방향 하나로 3.9배가 난다

| 실측 | 값 |
|---|---|
| 같은 자리, yaw 271 ↔ yaw 85 | 렌더러 **239 ↔ 936**, draws **278 ↔ 1,120** |
| 같은 걷기 코스 F9 스윕 | 삼각형 **430k ~ 1,229k** (2.9배) |

**고정 포즈는 표본 3개다. 걷는 사람은 분포 전체를 밟는다.**
"이동이 유발한다" 가 아니라 **"이동이 무거운 시야를 표집한다"** 가 더 정확하다.

### 6-1. 그래도 `da3f05ec` 의 매 프레임 낭비는 실재한다

`(아래는 유효하다 — 다만 단독 원인이 아니라 여러 요인 중 하나다)`

```
da3f05ec   2026-09-01   강형순
feat(world): 축제존 조명·부스 직원 NPC·상호작용 사거리와 UI 통일 (S15P21A604-355)
```

`Content/BoothInteractionInput.cs` 의 근접 스캔이 이렇게 바뀌었다.

```diff
- float sqr = (t.transform.position - origin.Value).sqrMagnitude;   // 산술 한 줄, 할당 0
+ float d = t.DistanceFrom(origin.Value);                            // ↓
+ return target.DistanceFrom(origin.Value) <= target.MaxDistance;    // ↓
+ var (pos, radius) = target.HighlightFootprint();                   // ↓
```

세 곳 모두 `BoothInteractionTarget.WorldBounds()` 를 탄다.

```csharp
// Booth/Interaction/BoothInteractionTarget.cs
Bounds? WorldBounds()
{
    foreach (var c in GetComponentsInChildren<Collider>(true))   // ← 호출마다 배열 새로 할당 + 계층 순회
    ...
    foreach (var r in GetComponentsInChildren<Renderer>(true))   // ← 콜라이더 없으면 한 번 더
}
```

**변경 의도 자체는 옳다** — 피벗 거리로 재면 큰 오브젝트가 부당하게 멀게 잡히는 문제(T-232)를
표면 거리로 고친 것이다. 문제는 그 표면 거리를 **매 프레임 새로 계산**한다는 것이다.

### 6-2. 프레임당 실제 비용

`BoothInteractionInput.Update()` 한 프레임에서 `WorldBounds()` 가 도는 횟수:

| 위치 | 조건 | 횟수 |
|---|---|---|
| `IsInRange(aimed)` | 마우스가 대상을 조준 중 | 1 |
| `NearestInteractableInRange()` | **항상** — 활성 대상 전수 순회 | **N** |
| `ShowHint(targeted)` → `HighlightFootprint()` | **사거리 안에 대상이 있을 때** | 1 |
| `_passive` 판정 → `IsInRange(aimed)` | 조준 중 | 1 |

→ **프레임당 `GetComponentsInChildren<Collider>` 가 N + 최대 3회.**

### 6-3. 왜 "정지는 멀쩡, 이동하면 무너짐" 인가

- `NearestInteractableInRange()` 의 N회는 **정지든 이동이든 항상** 돈다 → 바닥을 올린다.
- `ShowHint` 의 추가 호출은 **사거리 안에 대상이 있을 때만** 돈다 → **부스 사이를 걸을 때만** 붙는다.
- 개활지에 서 있으면 대상이 없어 이 경로가 빠진다.

사용자 표현 *"축제벽 끝쪽에 가면 갑자기 조금씩 그런다"* 와 맞는다.

### 6-4. 같은 창에 들어온 두 번째 회귀

```
954c535a   2026-09-05   외곽선 하이라이트 (S15P21A604-437)
```

`BoothInteractionTarget.ApplyHighlightMaterials()` 가 대상이 바뀔 때마다
**렌더러 개수만큼 `new GameObject` + `SkinnedMeshRenderer` 복제본**을 만들고 `new Material` 을 하나 만든다.
해제 시 전부 `Destroy`. 걸어 다니면 대상이 계속 바뀌므로 **초당 여러 번** 생성·파괴가 돈다.
복제본이 살아 있는 동안은 **스키닝 비용도 두 배**다.

### 6-5. 이번 히스토그램 실측이 말해 주는 것

정지 20초(1095프레임) vs 이동 20초(1089프레임), 캐릭터가 11F 홀 → 축제 서쪽 끝(-874)까지 실제 이동.

| | 정지 | 이동 |
|---|---|---|
| 평균 | 54.8 fps | 54.5 fps |
| 봉우리 | 16~18 ms (36%) | 16~17 ms (18%) |
| 분포 폭 | 10~41 ms | **8~60 ms** |

- **주사율 계단이 아니다** — 8.3/16.7/25/33.3 에 봉우리가 안 선다. **R2·R12(VRR·듀얼 모니터) 기각.**
- **이동은 평균을 낮추지 않고 분산을 키운다.** "느려지는" 것이 아니라 **일정하지 않은** 것이다.
  6-2 의 "N회는 항상 + 근접 시 추가" 구조와 정확히 맞는다.
- 정지 상태에서도 120 Hz 화면에 **55 fps** 다. 이건 별개 문제(Intel 내장 GPU 한계)이고 실험 2 로 가른다.

### 6-6. 조치

**A. 바운즈 캐시** (최우선, 동작 변화 0)
부스 오브젝트는 배치 후 움직이지 않는다 → `WorldBounds()` 결과를 대상별로 한 번만 계산해 보관한다.
`DistanceFrom`·`HighlightFootprint` 가 그 값만 읽게 한다. **약 10줄.**

**B. 하이라이트 복제본 재사용** (그다음)
전환마다 만들고 부수는 대신 대상별로 만들어 두고 켜고 끈다.

**C. 검증**
A 적용 전후로 **같은 코스**를 걸어 히스토그램을 비교한다. 분포 폭이 좁아지면 확정이다.
이번 측정(정지/이동 각 20초)이 그대로 기준선이 된다.

## 8. 09-08 오전: 측정 환경이 깨져 있었다 — 그 시간대 수치는 전부 무효

### 8-1. 무슨 일이 있었나

09:47~09:59 에 인프라 전달용 **릴리스 WebGL** 을 떴다. 이때 모달을 피하려고
`FestaReleaseBuilder.BuildAll()` 대신 `LoadApiConfig` → `ForceApiEnvironment(Prod)` → `BuildWebGL()`
을 리플렉션으로 **따로** 불렀다. `BuildAll()` 의 `try/finally` 를 건너뛴 것이고,
`ForceApiEnvironment` 는 **ApiConfig.asset 을 디스크에 저장한다.**

그래서 그 뒤 10:07~10:21 에 뜬 개발 빌드에는 `useMockApi=0 / activeEnvironment=Prod` 가 **구워졌다.**
로컬에서 실행하면 `https://api.ssafesta.world` 로 붙어 전부 CORS 로 실패한다.

관측된 결과:

```
[ApiServices] Init — mock=False spring=https://api.ssafesta.world
[HttpBoothApiClient] GET .../booth-slots/*/layouts/published 실패: Unknown Error (CORS)
[HttpUserApi] POST /world-sessions 실패: Unknown Error (CORS)
[PublishedLayoutLoader] 12슬롯 병렬 조회 완료 — 게시 0 / 미게시·실패 12
```

### 8-2. 왜 치명적인가 — 빠르게 나와서 더 나쁘다

부스가 **전부 빈 채로** 떴다. 그 상태의 히스토그램은 10:24:19 에 **1382 프레임 / 20초 = 69.1 fps**
로, 정상 환경보다 오히려 **좋게** 나온다. 성능이 좋아진 것처럼 보이는 오측정이라 그냥 지나칠 뻔했다.

더 나쁜 점: 지금 검증하려던 것이 `BoothInteractionInput` 이 **부스 프롭 N개마다** 매 프레임
`GetComponentsInChildren<Collider>` 를 돌던 회귀(`da3f05ec`)의 수정이다.
프롭이 0개면 N=0 이라 **회귀도 수정 효과도 아예 나타나지 않는다.** 빈 월드로는 이 항목을 못 잰다.

**따라서 09:47~10:32 사이의 모든 측정치는 폐기한다.**

### 8-3. 재빌드 없이 복구한 방법

`ApiConfig` 는 빌드에 구워지지만, `ApiServices.Init` 이 호스트 주입을 **빌드 타임 값보다 우선**한다
(S15P21A604-459, `HostRuntimeConfig` → `window.__FESTA_CONFIG__.apiBaseUrl`). 그래서 15분짜리
재빌드 없이 주소만 갈아끼웠다.

1. `ApiConfig.asset` 원복 — `git checkout` (useMockApi=1 / Local)
2. `festa-frontend/public/runtime-config.js` 에 `apiBaseUrl` 주입 **(로컬 전용, 커밋하지 않는다)**
3. 로컬 Spring(18080)에는 게시 레이아웃이 **0건**이었다(슬롯1 409, 나머지 404) — 여전히 빈 월드다.
   그래서 `festa-unity/Tools/serve.js` 에 `FESTA_MOCK_LAYOUTS=1` 게이트를 달아
   `GET /api/v1/booth-slots/{id}/layouts/published` 만 가로채고 나머지는 Spring 으로 프록시했다.
   규칙은 `MockBoothApiClient` 와 동일 — **홀수 슬롯만 게시**(`slotId % 2 == 0 → null`),
   내용은 같은 프롭 13종(`Tools/mock-api/booth-slot-layout.json`).

복구 확인:

```
[ApiServices] Init — mock=False spring=http://localhost:8000
[PublishedLayoutLoader] 12슬롯 병렬 조회 완료 — 게시 6 / 미게시·실패 6   ← Mock 과 동일
[ConnectionManager] StartClient ws://127.0.0.1:7777 → True
[NetworkPlayer] Spawned owner=11 isOwner=True
```

> 부수 효과: 주입은 **FE 자신의 API base 도** 바꾼다(`shared/config/runtime.ts` 가 같은 키를 읽는다).
> 이 때문에 게스트 세션이 끊겨 `/login` 으로 튕겼다 — 게스트 재진입으로 해결.

### 8-4. 정상 환경에서 다시 잰 값 (빌드 `9a557721`, far clip 2800, 바운즈 캐시 적용)

| 조건 | 프레임/20초 | 평균 fps | 범위 | 33 ms 초과 |
|---|---|---|---|---|
| 정지 | 1282 | **64.1** | 7–33 ms | **0건** |
| 이동(전진+스트레이프 20초) | 1442 | **72.1** | 7–33 ms | **0건** |
| (무효) 빈 월드·정지 | 1382 | 69.1 | 6–38 ms | 2건 |

2,724 프레임 전체에서 **33 ms 를 넘긴 프레임이 하나도 없다.** 분포도 단봉이고 주사율 계단
(8.3/16.7/25/33.3 ms)에 뭉치지 않는다 — R2·R12 기각 상태 유지.

**단, 이것으로 "수정이 효과 있었다" 라고 말할 수는 없다.** 같은 빌드 안의 A/B 가 없고,
이전 기준선(정지 54.8 fps / 이동 54.5 fps)은 **다른 빌드**라 비교 불가다(§4 의 교훈).
지금 말할 수 있는 것은 "현재 빌드·정상 환경에서 33 ms 초과 프레임이 관측되지 않는다" 까지다.
체감 확인은 사용자가 직접 걷는 것으로 한다 — 특히 **축제벽 끝쪽**(사용자가 지목한 구간).

### 8-5. 재발 방지

`Assets/_Project/Scripts/Editor/ApiConfigGuard.cs` 를 추가했다.
에디터 기동·재컴파일 때마다 `ApiConfig.asset` 이 Prod 로 남아 있으면 경고를 띄운다.
자동으로 되돌리지는 않는다 — Dev/Prod 로 일부러 맞춰 두는 경우가 있어 판단은 사람이 한다.

**규칙: 릴리스 산출물은 `FestaReleaseBuilder.BuildAll()` 로만 뽑는다.**
단계를 따로 부르면 `finally` 의 `RestoreApiEnvironment` 가 실행되지 않는다.

## 9. 최종 판정 — 원인은 두 겹이다

### 9-1. 1층: vsync 2단 양자화 (증폭기)

사용자 실브라우저 `requestAnimationFrame` 간격, 3,749 프레임 / 49초:

```
 8ms(120Hz)  1792회  47.8%
17ms(60Hz)   1647회  43.9%     <- 둘이 합쳐 91.7%
25ms(40Hz)    212회   5.7%
33ms(30Hz)     13회   0.3%
p50 16.5ms · p90 16.7ms · p99 25.1ms · 최대 41.8ms
초당 fps: 50 ~ 107 왕복
```

**렌더 부하가 만드는 연속 분포가 아니다.** 계단에만 붙어 있다. 8.33ms 를 살짝 넘으면 vsync 가 한 틱을
통째로 건너뛰어 즉시 절반이 되고, 여유가 생기면 되돌아온다. 게임이 **120Hz 경계선 위에 걸터앉아 있어서**
작은 부하 변동이 2배 스윙으로 증폭된다.

§6 에서 "히스토그램이 매끄러운 단봉이라 주사율 계단은 기각" 이라고 적었던 것은 **틀렸다.** 그 판정은
Unity 자체 히스토그램(`Time.unscaledDeltaTime`, 1ms 빈) 기준이었고, 브라우저 rAF 간격을 직접 재니
계단이 선명하게 드러났다. **rAF 간격이 사용자가 실제로 보는 것이고, Unity 의 deltaTime 이 아니다.**

교차 검증 — 창을 60Hz 외부 모니터로 옮기고 재측정:

| | 120Hz 화면 | 60Hz 화면 |
|---|---|---|
| 8ms 비중 | 47.8% | 1% |
| 17ms 비중 | 43.9% | 89% |
| 초당 fps 범위 | 50~107 (**2.1배**) | 46~60 (**1.3배**) |

사용자 체감: "느려졌다 빨라졌다 하는건 좀 괜찮은데 프레임은 좀 떨어지는 느낌."
즉 **진동은 사라지고 60 상한만 남았다** — 예측대로다.

### 9-2. 2층: 시야 방향 부하 (방아쇠)

"구역을 벗어나도 유지된다" 는 **잔류 상태가 아니라 시야 방향**이었다.

| 위치 / 방향 | 렌더러 | 삼각형 | 절두체 광원 |
|---|---|---|---|
| 끝벽 (-890,20,150) 서향(벽) | 41 | 194k | 18 |
| 끝벽 (-890,20,150) **동향** | **641** | **1,320k** | **99** |
| x=-760 동향 | 573 | 1,177k | — |
| x=-575 동향 | 444 | 1,029k | — |
| 포어코트 | 136 | 139k | — |

끝벽은 월드 서쪽 막다른 곳이라 **되돌아오려면 반드시 동쪽을 봐야 한다.** 그래서 그 자리를 벗어나도
포어코트에 닿기 전에는 회복되지 않는다. 사용자가 "확 돌면 벽쪽이 아니어도 느려졌다 빨라졌다 한다" 고
한 것과 정확히 맞는다. 제자리 회전만으로 삼각형이 6.8배 바뀐다.
