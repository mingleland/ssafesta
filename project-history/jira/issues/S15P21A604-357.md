## 설명

### 작업 목적

Google·Kakao 에 SSAFY 를 더해 소셜 로그인 3종을 제공한다. 자격증명과 wire 값이 모두 확보되어 착수 가능하다.

### 작업 내용

- `OAuthProvider` enum 에 `SSAFY` 추가
- `OAuthLoginSuccessHandler` 의 subject 추출을 `principal.getName()` 으로 교체 — provider 별 3항 연산자를 제거한다. 지금은 `provider == GOOGLE ? "sub" : "id"` 라서 SSAFY 가 `id` 로 조용히 떨어진다
- `application.yml` 에 `registration.ssafy` · `provider.ssafy` 추가
- 헌법 11조 · spec 001 FR-001 및 시나리오 1·9·10 · `docs/08_Backend_API_명세서.md` 의 "Google / Kakao" 문면 개정

### wire 값

| 항목 | 값 |
|---|---|
| authorization-uri | https://project.ssafy.com/oauth/sso-check |
| token-uri | https://project.ssafy.com/ssafy/oauth2/token |
| user-info-uri | https://project.ssafy.com/ssafy/resources/userInfo |
| user-name-attribute | userId |
| client-authentication-method | client_secret_post |
| scope | 없음 — 인가 요청 파라미터에 scope 가 없다 |

userInfo 응답은 `userId` · `email` · `name` 평면 구조다. Kakao 처럼 중첩되지 않는다.

### 완료 조건

- SSAFY 실계정 최초 로그인 후 계정이 자동 생성되고 `/auth/callback` 에 도달한다
- Google·Kakao 경로에 회귀가 없다
- provider 3종의 subject 해석을 고정하는 테스트가 있다

### 선행 작업 / Dependency

없음. 자격증명·wire 값 확보 완료.

### 참고

- GitLab 이슈 #114
- **위험 1 — state** SSAFY 문서의 인가 요청 파라미터는 `client_id` · `redirect_uri` · `response_type` 셋뿐이고 콜백 응답도 `code` 하나다. Spring 은 `state` 를 항상 보내고 돌아온 값을 검증한다. SSAFY 가 echo 하지 않으면 `authorization_request_not_found` 로 실패한다
- **위험 2 — userInfo Content-type** 문서가 GET 요청에 `application/x-www-form-urlencoded` 를 요구한다. Spring 기본 userinfo 호출은 GET 에 Content-Type 을 붙이지 않는다. 거부되면 `OAuth2UserService` 교체가 필요하다
- 두 위험 모두 코드로 미리 막지 않고 실계정 관통 후 대응한다
- DB 변경 없음 — `V1__initial_schema.sql` 의 `provider VARCHAR(20)` 에 `SSAFY` 가 들어간다

### 테스트 방법

1. SSAFY 실계정으로 로그인을 관통한다
2. 같은 이메일 중복 가입 차단(spec 001 시나리오 9)을 확인한다
3. 기존 Google·Kakao 테스트 스위트를 돌린다
