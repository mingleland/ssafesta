## 설명

배경: 지금은 사용자가 /app/world 에 도달한 뒤에야 Unity 정적 자산(loader·framework·wasm·data, ≈239MB)을 받기 시작한다. Landing·로그인·OAuth 왕복에 머무는 시간이 그대로 버려진다. 그 시간을 다운로드에 쓴다.

원칙
- Landing 에서 Unity 인스턴스를 실행하지 않는다. world/game 세션도 만들지 않는다. 공개 정적 자산 warm-up 만 한다.
- best-effort 다 — prefetch 실패·네트워크 오류·미지원 API·abort 가 실제 진입 실패로 이어지면 안 된다. 정상 loader 가 다시 처리할 수 있어야 한다.
- 단계적으로 받는다. Landing 첫 페인트와 경쟁시키지 않고, 큰 .data 는 로그인 의도가 높아진 뒤에 강화한다.
- 느린 회선은 navigator.connection(saveData·effectiveType)을 참고하되 필수 계약으로 만들지 않는다 — 미지원 브라우저는 정상 fallback.
- 기존 Runtime Asset Delivery(runtime-config → unityBuildBase() → resolveAssetUrl() → new URL) 를 그대로 재사용한다. 새 URL 체계를 만들지 않는다.

범위 밖: Service Worker·CacheStorage 즉시 도입(문서 캐시 실측 후 P2 후보), R3F·GLB·Booth 에셋 이관, 전체 .data 무조건 최우선 preload.

계측: PerformanceResourceTiming 으로 manifest·loader·framework·wasm·data 각각의 duration·transferSize·encodedBodySize·decodedBodySize 를 cold(캐시 제거 후 Landing→Auth→World)와 warm(같은 빌드 재방문)으로 나누어 비교한다. 실 transfer bytes · Unity boot · Lobby→Main · World playable 을 보고한다.

완료 조건: Landing 첫 페인트가 warm-up 으로 늦어지지 않는다 / warm-up 실패가 진입을 막지 않는다 / 재방문 시 실 transfer bytes 감소를 숫자로 보인다 / Landing 에서 Unity 인스턴스가 생성되지 않는다 / 단위 테스트로 고정.

### 이정헌 · 2026-09-05 19:57 KST

MR !274 develop 병합 완료 (2026-09-05). 실측까지 끝냈다.

단계별 warm-up: Landing(idle) manifest+loader / 로그인 화면 +framework / OAuth callback +wasm+data. 순차 요청이라 같은 화면의 이미지·API 와 연결을 다투지 않는다. 어느 화면에서도 Unity 인스턴스·세션을 만들지 않는다.

실측 (FE 컨테이너 + 가짜 산출물 loader 200KB · framework 2MB · wasm 6MB · data 25MB, 실 브라우저)
- /login 도달 시점: manifest+loader+framework 이미 받음(2.2MB)
- /auth/callback: loader·framework 는 304, wasm·data 신규(31MB)
- 재방문(immutable 헤더 있을 때): loader·framework·wasm 8.2MB 의 요청 자체가 사라짐(transferSize 0)

한계로 확인된 것: 25MB .data 는 immutable 을 붙여도 매번 전량 재다운로드된다(재현 3회, navigator.storage.estimate() usage 0). 브라우저 HTTP 캐시가 이 크기의 단일 항목을 보관하지 않는 것으로 보인다 — 6MB wasm 은 캐시된다. 이건 FE 가 풀 수 없는 문제라 Unity Data Caching(S15P21A604-431 §3)과 인프라 캐시 정책(GitLab #127)으로 넘겼다.

검증: 단위 테스트 11건(단계별 대상·saveData·2g·base 미설정·manifest 실패·네트워크 실패·중단·인스턴스 미생성·계측 필터·요약 합산). develop head 기준 tsc 0 · vitest 514/514 · vite build.

완료 전환하지 않는 이유: 실 Unity 빌드(239MB)로의 cold/warm 실측이 남아 있다. 가짜 산출물로는 단계·캐시 거동까지만 확인했고, 실제 체감 개선폭은 #127 배포 후에 재다. Closes 미사용.
