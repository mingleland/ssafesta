## 설명

S15P21A604-920 으로 추가한 `/user/queue/coin` 알림에서 발견된 결함 2건이다.

h3. P1 — 구독 전에 발행되어 알림이 유실된다

STOMP 는 구독 시점 이후의 메시지만 전달하고 재전송이 없다. 그런데 코인 지급 두 가지는 구조적으로 구독보다 먼저 일어난다.

- *INITIAL_GRANT (항상 유실)* — 가입 트랜잭션 안에서 `WalletService.openWallet()` 이 지급한다. 이 시점에는 WS 토큰 발급도, STOMP CONNECT 도 일어나지 않았다.
- *DAILY_GRANT (일반적인 첫 접속에서 유실)* — `DailyCoinGrantInterceptor` 가 인증된 모든 요청의 `preHandle` 에서 지급한다. 여기에는 `POST /api/v1/realtime/ws-token` 자신도 포함되므로, 그날 첫 접속의 지급은 소켓이 연결되기 전에 발행된다.

현재 테스트(`CoinGrantNotificationIntegrationTest`)는 `SimpMessagingTemplate` 을 Mockito 로 검증하기 때문에 발행 호출만 확인하고 통과한다. 실제 사용자는 알림을 받지 못한다.

h3. P2 — docs/16 §8 표의 참조값이 실제 payload 와 다르다

`docs/16_Realtime_통신_명세서.md` 는 `MINIGAME_REWARD` · `SLOT_PAYOUT` 의 `referenceType`/`referenceId` 를 "없음" 으로 적었으나 실제 발행되는 값은 다음과 같다.

- `MINIGAME_REWARD` — `MINIGAME_SESSION` / 세션 UUID (`TimerStopService.REWARD_REFERENCE_TYPE`)
- `SLOT_PAYOUT` — `SLOT_SPIN` / 스핀 UUID (`SlotMachineService.SPIN_REFERENCE_TYPE`)

h3. 해결 방향 (승인 전 초안)

P1 은 푸시 타이밍을 바꿔서는 풀 수 없다(지급 자체가 연결보다 먼저 일어난다). 복구 경로를 계약으로 정하는 쪽이 맞다.

- 후보 A — 구독 시점 재전송: `SessionSubscribeEvent` 리스너에서 최근 지급 원장 항목을 다시 발행한다. 다만 Spring 은 SUBSCRIBE 메시지를 비동기 inbound 채널로 보낸 뒤 이벤트를 발행하므로, 브로커의 구독 등록과 재전송 사이에 경합이 남는다.
- 후보 B — REST 복구 (권장): 큐를 best-effort 로 명시하고, 누락분은 이미 있는 `GET /api/v1/wallets/me/transactions` 로 회수한다. 이 응답은 큐 봉투와 동일한 필드(`id`·`amount`·`balanceAfter`·`reasonType`·`referenceType`·`referenceId`·`createdAt`)를 모두 담고 있어 BE 신규 코드가 필요 없다. 클라이언트는 마지막으로 처리한 원장 id 를 기준으로 신규 증액만 표시하고, 중복은 원장 id 로 거른다.

어느 쪽이든 `docs/16` §8 과 `docs/08` 의 해당 문단에 전달 보장 수준을 명시하고, FE 에 통보한다.

h3. 완료 조건

- P1 의 전달 보장/복구 경로가 문서 계약에 확정되어 있고, 선택한 방식이 구현·검증되어 있다.
- `docs/16` §8 표의 `MINIGAME_REWARD` · `SLOT_PAYOUT` 행이 실제 payload 와 일치한다.
