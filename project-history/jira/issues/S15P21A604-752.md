## 설명

## 작업 목적

S15P21A604-744에서 FE·BE GameProject 스키마 정합성은 확인했지만, 지금까지 QA는 전부  
"성공/실패 여부"만 봤고 실제 응답 속도는 한 번도 재지 않았다. Game Studio 핵심 흐름 4가지의  
실제 소요 시간을 실측해 기존 설계(자동저장 800ms 디바운스, 다중 업로드 순차 처리 등)가 실제  
네트워크 조건에서도 타당한지 확인한다.

## 작업 내용

- Draft 저장 왕복 시간 측정 — 2MB 근접 프로젝트(500 오브젝트 + 10,000 타일)로 `PUT /draft`  
   N회 반복, p50/p95 기록. 자동저장 800ms 디바운스가 실측 응답 시간보다 여유로운지 비교
- 자산 업로드 소요 시간 측정 — 5MB 상한 파일 기준 presigned 발급→전송→complete 확정  
   3단계 각각 시간 기록. 다중 업로드 시 "n/총" 카운터 갱신 간격이 자연스러운 템포인지 관찰
- Published 조회 응답 시간 측정 — 최초 조회와 캐시 조건(ETag/If-None-Match) 재조회를 구분해  
   게스트 첫 로딩 체감 확인
- 동시 저장 충돌 발생 빈도 확인 — 테스트 계정 2개로 같은 게임을 거의 동시에 저장해  
   `GAME_REVISION_CONFLICT` 재현 빈도 확인

기능적 정합성(스키마·검증 규칙)은 범위 밖 — #697·#701·#708·#709·#744에서 이미 확인됨.  
이 티켓은 관측 결과에 따라 최소 2가지를 담당자와 조율해야 한다: ① 자동저장 디바운스 값이  
실측 기준으로 여유로운지 판단 기준(FE 담당자), ② 동시 저장 충돌 재현 빈도가 실제 사용  
패턴상 의미 있는 우선순위인지(기획/PM).

## 테스트 방법

1. #744 페이딩 로직으로 500 오브젝트+10,000 타일 프로젝트를 만들어 `PUT /draft`를 20회  
   반복 호출, 왕복 시간을 기록한다. 에디터에서 실제 연속 편집→자동저장도 함께 확인한다.
2. 5MB 파일로 업로드 흐름 전체를 실행하며 발급/전송/확정 각 구간 시간을 기록한다. 다중  
   업로드로 한 번 더 측정해 카운터 갱신 간격을 관찰한다.
3. 발행된 게임을 최초 1회, ETag 재조회 1회 측정해 비교한다.
4. 계정 2개로 같은 게임 Draft를 거의 동시에 저장해 몇 회 시도해야 충돌이 발생하는지,  
   정상 순차 편집에서는 충돌이 없는지 확인한다.
