## 착수 전제 정정 — 구현은 이미 develop에 있습니다

제가 08-24에 남긴 코멘트("BE 계약 문서가 나와야 착수 가능")는 **계약 문서 기준으로는 여전히 맞지만 구현 기준으로는 낡았습니다.** `origin/develop` 실측 결과 endpoint가 전부 있습니다.

| 경로 | 컨트롤러 | 응답 |
|---|---|---|
| POST /api/v1/auth/guest | GuestAuthController | GuestTokenResponse(accessToken, expiresAt) |
| POST /api/v1/auth/refresh | 위와 같음 (@CookieValue refresh_token) | 동일 |
| POST /api/v1/auth/logout | 위와 같음 | 204 |
| POST /api/v1/auth/oauth/complete | OAuthCompletionController | OAuthCompletionResponse(status, accessToken, expiresAt) |
| GET /api/v1/auth/oauth/{provider} | OAuthAuthorizationController | 302 |

`specs/001-auth-user/contracts/` 에는 여전히 oauth-completion·nickname-policy 2종뿐이고, `docs/08` §2는 `/auth/signup`·`/auth/login` 이 적힌 낡은 스텁이라(헌법 11·12조가 금지한 자체 가입) 계약 근거로 쓸 수 없습니다. 팀장 지시대로 **BE 구현을 계약 정본으로 삼아 FE를 맞추고 착수합니다.**

## 로컬 BE 기동 후 실측한 것

`backend/compose.yaml`(postgres+redis) + `mvnw spring-boot:run` 으로 띄워 직접 호출했습니다.

```
POST /api/v1/auth/guest  (Origin: http://localhost:5173)
200 {"accessToken":"eyJ...","expiresAt":"2026-08-26T09:08:03.738586500Z"}
Set-Cookie 없음 / Access-Control-Allow-Credentials: true / Expose-Headers: Set-Cookie, X-Request-Id
```

- **status 필드가 없음을 확인했습니다.** FE가 complete 전용 union 을 게스트·refresh 에 재사용하고 있어 그대로 전환하면 401 복구·새로고침 세션 복원·게스트 입장 3곳이 조용히 실패합니다. BE 기준 타입(TokenResponse)을 새로 두고 성공 판정을 "예외 없음"으로 바꿉니다
- expiresAt 이 나노초 9자리인데 JS Date 파싱은 정상입니다(밀리초로 절삭)
- guest 는 Origin 없이도 200 — requireTrustedOrigin 이 refresh·logout 에만 걸려 있는 것과 일치합니다
- Origin 불일치는 `UNTRUSTED_ORIGIN` 이 아니라 **CORS 단계에서 먼저 차단**됩니다(`Invalid CORS request`). requireTrustedOrigin 은 CORS 를 통과한 요청에 대한 2차 방어입니다

### BE 확인 요청 1건 (blocker 아님)

`POST /api/v1/auth/refresh` 를 **쿠키 없이** 호출하면 `500 INTERNAL_ERROR` 가 납니다.

```
{"code":"INTERNAL_ERROR","message":"서버 오류가 발생했습니다.","requestId":"req_5d28d8b3", ...}
```

`@CookieValue(name = "refresh_token")` 가 필수인데 없을 때 `MissingRequestCookieException` 이 500 으로 떨어지는 것으로 보입니다. FE 의 `bootstrapAuth` 는 새로고침마다 refresh 를 시도하므로 **비로그인·게스트 상태에서 매번 서버 500 이 찍힙니다.** FE 는 catch 해서 조용히 anonymous 로 두기 때문에 동작에는 지장이 없으나, 계약상 4xx 가 맞다고 봅니다. BE 파트 판단 부탁드립니다.

## 결정 요청 2건

### D4 — 이 티켓의 완료 조건

현재 완료 조건 중 "소셜 로그인→닉네임→입장 실서버 관통" 은 **OAuth 자격증명 없이 채울 수 없습니다**(D5). 둘 중 정해 주세요.

1. 완료 조건을 **"로컬 BE 관통"으로 하향**하고 소셜 로그인 검증을 별도 티켓으로 분리
2. **원래 조건 유지** — D5 키를 받아 이 티켓에서 끝까지 수행

배포된 실서버 주소가 문서 어디에도 없다는 점도 함께 봐 주세요. `docs/sdd/parts/INFRA.md` 는 "상태: 권장안(2026-08-12)" 이고 CI 러너가 없어 자동 배포 경로가 없습니다. 현재 검증 가능한 것은 로컬 기동뿐입니다.

### D5 — OAuth 개발용 자격증명 6종

`application-local.yml` 이 요구하며 기본값이 없어 미설정이면 앱이 뜨지 않습니다.

```
GOOGLE_CLIENT_ID  GOOGLE_CLIENT_SECRET  GOOGLE_REDIRECT_URI
KAKAO_REST_API_KEY  KAKAO_CLIENT_SECRET  KAKAO_REDIRECT_URI
```

**누가 발급하고 어떻게 전달할지** 정해 주세요. 제 `backend/.env` 에는 앱 기동용 자리표시자가 들어 있어 소셜 로그인은 되지 않습니다. Secret 이므로 추측하거나 만들어 넣지 않았습니다(헌법 15조).
