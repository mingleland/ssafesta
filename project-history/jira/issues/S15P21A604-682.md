## 설명

### 증상

`GET` 슬롯 목록이 다음과 같은 조합을 돌려줄 수 있다.

```
status=OCCUPIED
entryAvailable=true
boothId=<이미 삭제된 id>
boothName=null
facade=null
```

방문자가 그 간판을 보고 입장을 시도하면 404 다. DB 불변식상 성립할 수 없는 상태가 응답에 나온다.

### 원인 (2026-09-13, develop `0ede2eae` 확인)

`BoothQueryService.listSlots` 가 임대 목록과 부스를 **따로** 읽는다.

```java
@Transactional(readOnly = true)
public List<SlotView> listSlots(Long viewerUserId) {
    ...
    for (BoothLease lease : leases.findAllValid(now)) { ... }      // 질의 1
    ...
        Booth booth = booths.findById(lease.getBoothId()).orElse(null);   // 질의 2
        return SlotView.occupied(slot, lease, booth, mine, now);
```

`@Transactional(readOnly = true)` 이지만 **격리 수준이 READ COMMITTED** 다(서버 기동 로그에서 확인). READ COMMITTED 에서는 트랜잭션이 아니라 **문장마다** 새 스냅샷이 잡히므로, 두 질의 사이에 회원 탈퇴가 커밋되면 임대는 보이고 부스는 사라진 상태를 읽는다.

그 결과를 `SlotView.occupied` 가 그대로 싣는다.

```java
return new SlotView(..., "OCCUPIED", lease.getBoothId(), booth == null ? null : booth.getName(),
        ..., true, mine, booth == null ? null : BoothFacadeService.FacadeView.of(booth));
```

`boothId` 는 임대에서 오므로 **부스가 없어도 값이 실린다**. `orElse(null)` 이 불변식 위반을 조용히 통과시키는 자리다.

### 영향

일시적이고 다음 요청에서 사라진다. 잘못된 데이터가 저장되지는 않는다. 다만 그 순간 목록을 받은 방문자에게는 들어갈 수 없는 부스가 입장 가능으로 보인다.

### 수정 방향

임대와 부스를 **한 번의 조인 projection** 으로 읽어 같은 스냅샷을 보장한다. 조인 결과가 없으면 그 슬롯은 `AVAILABLE` 로 떨어지는 편이 응답으로 성립한다 — 부스가 없는 `OCCUPIED` 보다 낫다.

`orElse(null)` 로 덮는 대신, 조인으로도 부스가 없는 경우가 남는다면 그것은 로그로 드러낸다(조용한 기본값으로 되돌리지 않는다 — T-24 의 교훈).

### 완료 조건

- [ ] 슬롯 응답에 `boothId` 가 실리면 그 부스는 반드시 존재한다
- [ ] 부스 없는 임대 행이 있을 때 응답이 어떤 모양인지 테스트로 고정한다
