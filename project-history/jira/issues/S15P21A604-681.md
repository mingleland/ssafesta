## 설명

### 증상

휴지통이 가득 찬 상태에서 게임을 하나 더 삭제하면 가장 오래된 삭제 게임이 영구 삭제되는데(`GameLifecycleService.softDelete` → `hardDelete`), 그 게임이 오락기에 걸려 있으면 `games.delete(game)` 이 외래키 위반으로 실패하고 **요청 전체가 롤백**된다. 사용자는 게임을 더 삭제할 수 없게 된다.

### 원인 (2026-09-13, develop `0ede2eae` 확인)

`V27__arcade_machine_bindings.sql`

```sql
CREATE TABLE arcade_machine_bindings (
  machine_id VARCHAR(64) PRIMARY KEY,
  game_id    BIGINT NOT NULL REFERENCES games(id),
  ...
);
```

`ON DELETE` 가 없고, 같은 파일 주석이 CASCADE 를 **일부러 걸지 않았다**고 적는다 — 탈퇴 경로가 자식 표를 순서대로 지우는 방식이라 CASCADE 를 걸면 그 파일만 읽어서는 무엇이 함께 지워지는지 알 수 없다는 판단이다.

그런데 `GameLifecycleService.hardDelete` 는 asset·draft·published 만 지우고 바인딩을 건드리지 않는다.

```java
private void hardDelete(Game game) {
    assets.enqueueAllObjects(game.getId());
    assets.deleteAllByGameId(game.getId());
    drafts.findById(game.getId()).ifPresent(drafts::delete);
    published.deleteAll(published.findAllByGameIdOrderByVersionNoDesc(game.getId()));
    games.flush();
    games.delete(game);   // ← arcade_machine_bindings 가 남아 있으면 여기서 터진다
}
```

**같은 사고가 이미 한 번 있었다.** 그 메서드의 javadoc 이 asset 을 빠뜨려 `game_id` 외래키에서 실패했던 일(`S15P21A604-485`)을 기록하고 있다. 바인딩은 그 목록에 추가되지 않은 채 V27 이 들어왔다.

`AccountDeletionService` 는 반대로 제대로 지운다 — `DELETE FROM arcade_machine_bindings WHERE game_id IN (...)`. 즉 이 표가 수동 정리 대상이라는 것은 알려져 있었고, `hardDelete` 만 빠졌다.

### 지금은 발화하지 않는다 — 그러나 곧 무장된다

`arcade_machine_bindings` 에 **행을 만드는 운영 코드가 0줄**이다. 쓰기 경로는 `AccountDeletionService` 의 DELETE 뿐이고 INSERT 는 테스트(`GameWithdrawalIntegrationTest`)에만 있다. V27 도 "기계가 게임 전용 부스로 이전될 예정이라" 시드를 비워 두었다.

따라서 현재 운영 DB 에서는 재현되지 않는다. **게임 전용 부스에 오락기를 배치하고 바인딩을 넣는 순간 무장된다** — 그 배치가 `S15P21A604-108`(Published 게임 유료 입장)의 재개 조건이므로, 배치 작업보다 먼저 닫아야 한다.

### 수정 방향

`hardDelete` 에서 바인딩을 먼저 지운다. V27 의 판단(CASCADE 를 걸지 않고 삭제 순서를 코드에 드러낸다)을 유지하는 쪽이 일관적이다.

### 완료 조건

- [ ] 오락기에 걸린 게임을 영구 삭제해도 요청이 성공한다
- [ ] 회귀 테스트 — 휴지통 한도가 찬 상태에서 **바인딩이 있는 가장 오래된 삭제 게임**이 축출되는 경로를 실제로 밟는다
- [ ] 수정 전 그 테스트가 실패하는 것을 확인한다 (변이 확인)
