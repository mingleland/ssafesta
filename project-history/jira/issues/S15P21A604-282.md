## 다만 -313 수정으로 사라졌을 가능성이 크다

`-313` 의 원인은 `main` 씬을 다시 로드할 때마다 `@Network`(NetworkManager + ConnectionManager + NetworkBootstrap + DevConnectionHud)가 **중복 누적**되는 것이었다 (실측: 3회 로드 후 각 3개). 중복 인스턴스가 남아 있으면 이 건의 두 증상이 자연스럽게 설명된다.

- **증상 1** 승인 메시지 중복 수신 — 승인 경로를 듣는 인스턴스가 둘 이상이면 그대로 나온다
- **증상 2** `Failed to find any loaded scene named main!` — 이전 씬 로드 때 만들어져 `DontDestroyOnLoad` 로 살아남은 옛 NetworkManager 가 **이미 언로드된 씬**을 참조하면 정확히 이 모양이 된다

관측 조건도 겹친다 — 이 건은 "에디터 SERVER 모드 + 클라이언트 1" 에서 봤고, `-313` 은 씬 왕복에서 재현된다. 둘 다 인스턴스가 여러 벌 살아 있는 상황이다.

MR !135 로 1차 조사 반영. **고치지 않았다** — 이 이슈가 요구한 "재현 조건 확정" 까지다. 이슈는 열어 둔다. 상세: `docs/KHS/25_트러블슈팅.md` T-230

**① 이 이슈 본문의 진단이 반대였다.** 본문은 `Failed to find any loaded scene named main!` 을 *"씬 로드 시점/이름 불일치"* 로 적었는데, NGO 소스를 읽으니 그 반대다.

```csharp
// NetworkSceneManager.cs:955  GetAndAddNewlyLoadedSceneByName
if (sceneLoaded.name == sceneName) {
    if (!ScenesLoaded.ContainsKey(sceneLoaded.handle)) {   // ← 이미 추적 중이면 후보에서 빠진다
        ScenesLoaded.Add(...); return sceneLoaded;
    }
}
throw new Exception($"Failed to find any loaded scene named {sceneName}!");
```

**이름은 맞고 **`main` 은 로드되어 있다. 던지는 조건은 "이름이 같은 씬이 전부 이미 `ScenesLoaded` 에 등록돼 있어 새로 등록할 게 없다" 이다 — 메서드 이름이 `GetAndAddNewly**Loaded**SceneByName` 인 이유다. **같은 씬을 두 번 등록하려는 상황**이다.

배경도 실측했다 — `NetworkConfig.EnableSceneManagement = true` 인데 프로젝트는 `CharacterLobbyController` 에서 `SceneManager.LoadScene("main")` 으로 직접 넘긴다. 씬 소유권이 둘로 갈려 있다.

**② 재현 시도 — 에러가 안 났다. 그것도 결과다.**

기존 봇 빌드(8/28 23:26)는 S15P21A604-85(8/29 22:31)보다 이전이라 고정 토큰을 보내 승인에서 거부된다. 그래서 현재 코드로 **다시 빌드**했다(535 MB, 9.7분).

에디터를 **SERVER 모드**(`StartServer`, Host 아님, 활성 씬 `main`)로 띄우고 봇·서버에 같은 `CONNECTION_TOKEN_SECRET` 을 주입해 실제 승인 경로로 붙였다. → **정상 접속·스폰, 두 에러 모두 없음.** 봇 로그상 봇은 씬을 직접 로드하지 않고 NGO 동기화(`ClientLoadedSynchronization`)만 탔다.

**따라서 "SERVER + NGO 주도 클라이언트" 조건은 제외된다.** 혐의는 **클라이언트가 **`main` 을 직접 로드한 뒤 접속하는 경로 — 즉 실제 로비→월드 핸드오프로 좁혀졌다. 그 상태면 클라이언트에 이미 추적 중인 `main` 이 있어 위 예외 조건과 정확히 맞는다.

**③ 다음에 할 일.** 봇에 "먼저 `main` 을 직접 로드한 뒤 접속" 옵션을 넣어 재현하거나, WebGL 빌드를 에디터 서버에 붙여 실제 핸드오프 경로를 태운다.

**④ 의도적으로 하지 않은 것.**

- `ConnectionManager.cs` — 동결 기준선(헌법 27조). 원인 확정 전에는 손대지 않는다.
- `EnableSceneManagement` 끄기 — in-scene NetworkObject 동기화 방식이 통째로 바뀐다. **"에러가 사라졌다" 를 해결로 착각하기 딱 좋은 우회**라 하지 않았다.

부수 확인 — 봇 빌드가 타깃을 StandaloneWindows64 로 바꿨다가 WebGL 로 정상 복원했고 `UNITY_SERVER` 도 미정의다 (T-182·T-219 재발 없음).

**태운 경로:** `main` 접속 → `ReturnToCustomization`(Shutdown + `LoadScene(CharacterLobby)`) → `EnterWorld()`(`LoadScene("main")` → 자동 접속)

**결과 — **`ConnectionApproverMessage … already established` 도, `Failed to find any loaded scene named main!` 도 나오지 않았다. 대신 **다른 버그**가 나왔고 그건 S15P21A604-332 로 분리해 고쳤다(재진입 시 접속 자체가 안 되던 문제).

`-332` 를 고친 뒤 재진입이 정상 동작하는 상태에서도 두 에러는 재현되지 않는다 — 서버 로그 `Approved client=3`, 클라이언트 `IsConnectedClient=True`.

**따라서 제외 조건이 하나 더 늘었다:**

| 조건 | 결과 |
|---|---|
| SERVER + NGO 주도 클라이언트 (봇) | 에러 없음 — 제외 |
| SERVER + **로비→월드 핸드오프** 클라이언트 | **에러 없음 — 제외** |
| SERVER + 월드→로비→월드 재진입 | 에러 없음 (`-332` 수정 후) |

**남은 차이를 다시 생각해야 한다.** 원 관측(2026-08-27)은 `-85`(입장 토큰)·`-332` 이전 코드다. 그 사이 접속 경로가 여러 번 바뀌었으므로, **이미 고쳐졌을 가능성**도 배제할 수 없다. 다음 다인 테스트에서 재발하는지 보고, 재발하지 않으면 이 이슈를 닫는 쪽이 맞다고 본다 — 지금 코드에서 재현되지 않는 에러를 계속 추적하는 것보다 낫다.
