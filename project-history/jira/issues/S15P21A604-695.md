## 설명

## 작업 목적

`S15P21A604-693` 코드리뷰에서 남긴 하드닝 1건. `WalletService.applyEntry` 는 지갑 행을 잠근 뒤 `ledger.findByIdempotencyKey(key)` 로 중복을 보는데, 이 조회가 **전역**이다 — 키가 같은 항목이 **다른 지갑**에 있어도 `alreadyApplied` 로 돌려준다. 그러면 호출자는 "이미 반영됐다" 고 믿고 자기 지갑에는 아무 변화가 없는 채로 성공을 받는다(설문 보상·미니게임 보상이면 코인이 안 들어오고, 임대·구매면 돈을 안 냈는데 성공).

지금은 안전하다 — 키는 전부 서버가 만들고 `userId`·`leaseId`·세션 `nonce` 를 포함해 지갑 간에 겹치지 않는다. 하지만 이 성질을 지키는 것은 각 호출자의 키 조립 규약이고, `WalletService` 는 그것을 검사하지 않는다. 새 호출자가 `REASON:referenceId` 처럼 지갑을 안 넣은 키를 만들면 이 구멍이 열린다. 헌법 20조(코인 변경 단일 경로)가 지키는 자리이므로 경로 자체가 막아야 한다.

## 작업 내용

- `WalletService.applyEntry`: 기록된 항목이 있으면 `entry.getWalletId().equals(wallet.getId())` 를 단정한다. 다르면 `IllegalStateException` 으로 크게 던진다(500 + ERROR 로그) — 조용히 새 항목을 만들면 `UNIQUE` 에 걸리고, 409 로 번역하면 서버 키 조립 실수가 클라이언트 오류로 위장된다. 메시지에는 키와 두 지갑 id 를 싣고 금액은 싣지 않는다.
- Javadoc: "왜 전역 조회인가 → 키는 전역 UNIQUE 이므로 조회도 전역이 맞고, 주인 검사가 그 다음이다" 를 적는다.
- 프로덕션 호출자 5곳(초기·일일 지급, 임대, 구매, 설문, 미니게임)의 키 조립은 바꾸지 않는다 — 전부 지갑 식별자를 포함하고 있음을 티켓에 기록.
