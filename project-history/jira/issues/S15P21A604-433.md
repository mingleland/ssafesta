## 설명

배경 (docs/26 결정 로그 2026-08-27 AS-5, specs/001 contracts/oauth-completion.md §정지 계정 redirect):

정지(SUSPENDED) 계정이 소셜 인증에 성공하면 서버는 세션을 발급하지 않고 302 {FRONTEND_BASE_URL}/auth/callback?error=ACCOUNT_SUSPENDED 로 돌려보내며 잔존 handoff 쿼키를 지운다. BE 는 전달까지 완료됐다.

그런데 FE CallbackPage.tsx 는 URL query 를 전혀 읽지 않고 도착 즉시 authApi.complete() 를 무조건 부른다. handoff 쿼키가 지워졌으므로 그 호출은 400 으로 실패하고 restart 화면이 뜼다 — 정지 회원에게 '입장 정보가 만료됐어요 / 처음부터 다시 로그인해 주세요' 라는 **사실과 다른 안내**를 보이고, 그대로 다시 로그인해도 같은 곳으로 돌아온다.

spec 001 Acceptance Scenario 5 — '정지 상태의 계정으로 인증하면 보호 기능에 로그인되지 않고 해당 상태와 가능한 후속 행동이 안내된다' — 의 앞절만 충족되고 뒷절이 안 된다.

수정:
1. CallbackPage 가 마운트 시 URL 의 error 파라미터를 먼저 읽는다. 값이 있으면 complete() 를 부르지 않는다 — 서버가 이미 실패를 알렸고 handoff 도 지워졌다.
2. ACCOUNT_SUSPENDED 면 정지 안내 화면을 보인다 — 상태(이용 제한)와 후속 행동(운영자 문의로 해제 요청, 로그인 화면으로 돌아가기). 문의 채널 URL 은 발명하지 않는다(헌법 30조).
3. 그 밖의 알 수 없는 error 값은 재시작 화면으로 보내되 complete() 는 건너뛴다 — 모르는 값을 아는 것으로 넘기지 않는다.
4. StrictMode 이중 effect 방어용 모듈 guard 가 error 경로에서 이상한 상태로 남지 않게 한다.

범위 밖: 관리자 정지·해제 API(S15P21A604-165, Deferred) · 문의 채널 신설 · ErrorCode enum 확장(이 값은 JSON 봉투가 아니라 navigation 채널의 어휘다).

완료 조건: ?error=ACCOUNT_SUSPENDED 로 도착하면 정지 안내가 뜼고 complete() 가 호출되지 않는다 / 파라미터가 없으면 기존 흐름 그대로 / 알 수 없는 error 는 재시작 화면 / 단위 테스트로 고정.
