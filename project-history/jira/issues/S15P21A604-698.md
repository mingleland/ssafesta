## 설명

### 작업 목적

부스 배치 가능 면적이 실제 부스 방의 34%뿐이다. 사용자에게는 "부스를 꾸며 놨는데 방 한가운데에만 옹기종기 모여 있다"로 보인다.

게임 파트 실측(GitLab #181, 2026-09-11):

- 실제 방(셸 내부): x −4.88 ~ +5.00 (9.9 m) · z −3.81 ~ +6.97 (10.8 m) ≈ 107 m2
- 스튜디오 배치 가능 범위: x −3 ~ +3 · z −3 ~ +3 = 36 m2

같은 실측에서 배치·회전은 8/8 정확히 일치했다. 좌표계 문제가 아니라 계약의 경계값 문제다.

게임 쪽 `BoothObjectFactory`의 방 경계 검사는 이미 x ±5 m / z −3.8 ~ +7.0 m 기준이라, 계약만 넓히면 게임 쪽 수정 없이 동작한다.

### 작업 내용

**x만 넓힌다. z(depth 6)는 유지한다.**

게임 파트가 depth 6 유지를 권했다 — 입구 쪽 4 m는 추적 카메라(기본 1.7 m·최대 3.4 m)가 벽에 눌리지 않게 두는 의도된 여백이고 플레이어 스폰도 그 안(z=+3.9)이다.

z를 더 쓰려면 방의 z 중심이 +1.58이라 비대칭 범위(−3.6 ~ +5.0)가 돼야 하는데, 그러면 `footprint {width, depth, height}` 스키마로 표현할 수 없고 FE `clampToBooth`가 ±half 대칭 전제라 구조까지 바뀐다. 필요해지면 그때 min/max 형태로 계약을 바꾼다.

구현:

1. `booth/LayoutValidator.java:42` — 상수 `MAX_HORIZONTAL`(3) 하나를 `MAX_X`(4.8)와 `MAX_Z`(3) 둘로 가른다. x·z에 같은 값을 쓰던 곳이 4군데다.
   
   - `:148`·`:255` 중심점 검증
   - `:183-186` 회전 반영 AABB 검증 (`HALF_WIDTH` 대칭)
2. 오류 메시지 2곳(`:148`·`:190`)이 지금 "x·z는 ±3m 이내여야 합니다"로 한 값을 말한다. x와 z를 따로 말하게 고친다.
3. `booth/BoothLayoutTemplateController.java:47-48` — `Footprint(9.6, 6, 2.72)`. 지금은 `MAX_HORIZONTAL * 2`를 width·depth 양쪽에 쓴다.

**마이그레이션 없음.** 넓히는 방향이라 기존 게시본은 전부 그대로 유효하다.

### 완료 조건

- [ ] `GET /booth-layout-templates` 응답이 `width: 9.6`, `depth: 6`, `height: 2.72`
- [ ] x = 4.8 저장 통과, x = 4.9 거부
- [ ] z = 3.0 저장 통과, z = 3.1 거부 (기존과 동일)
- [ ] 회전 반영 실물(AABB)도 x·z를 각자의 경계로 판정한다
- [ ] 오류 메시지가 x 경계와 z 경계를 따로 말한다
- [ ] 기존 게시본이 전부 유효하다 (회귀 없음)

### 선행 작업 / Dependency

없다. 이 티켓만으로 닫힌다.

후속(BE 범위 밖): FE가 `BOOTH_SIZE_FALLBACK`(`src/shared/config/studio.ts`)을 갱신해야 편집기 경계가 같이 넓어진다. 대칭을 유지하므로 `clampToBooth`(`src/features/studio/lib/coords.ts`) 구조는 바꿀 필요 없다. 게임 파트는 값이 정해지면 방 경계 상수(`BoothObjectFactory`·`FestaInteriorBuilder`)를 정렬하겠다고 회신했다.

## 리드 승인 요청 — spec 개정 시 plan/tasks 전면 재생성 면제

이 티켓이 부스 치수 계약을 `6×6` → `9.6×6` 으로 바꾸면서 `specs/005-booth-studio-layout/spec.md` 를 고쳐야 합니다. 그런데 `AGENTS.md` §2-4 가 *"spec을 고치면 plan/tasks를 다시 만든다"* 를 요구합니다. **그 재생성의 면제를 승인해 주시기를 요청드립니다.**

### 왜 spec 을 고쳐야 하는가

spec 005 의 Clarification **C-06** 줄이 부스 크기를 `6m × 6m × 2.72m` 로 적고 있습니다(#19·#45 인용). 계약 문서(`contracts/layout-api.md`)와 구현만 `9.6` 으로 바꾸고 spec 을 그대로 두면 **확정 spec 과 구현이 정면으로 모순**됩니다. 같은 숫자가 `FE/research.md` 와 `docs/26_팀_결정_필요사항.md` 에도 확정값으로 박혀 있어 함께 정정 대상입니다.

### 왜 전면 재생성은 과하다고 보는가

- **기능 요구사항(FR)이 하나도 바뀌지 않습니다.** 바뀌는 것은 치수 하나이고, `AGENTS.md` §2-4 표에서 치수는 *"파트 간 주고받는 형식 → §7 계약 절차"* 행에 해당합니다. 재생성을 부르는 *"요구사항(무엇을 만들 것인가)"* 행이 아닙니다.
- spec 005 는 **plan·tasks 가 이미 상당히 진행돼 완료 표시가 붙어 있습니다.** 재생성하면 그 완료 상태를 손으로 복원해야 하고, 그 과정에서 기록이 유실될 위험이 재생성으로 얻는 정합성보다 크다고 판단했습니다.

다만 §2-4 의 조건이 *"고치면"* 이라 문언상으로는 재생성이 발동합니다. 제가 임의로 예외를 만들지 않고 승인을 받는 이유입니다.

1. `spec.md` C-06 의 **치수만** 고치고 갱신 근거(`S15P21A604-698`, GitLab #181)를 주석으로 남깁니다
