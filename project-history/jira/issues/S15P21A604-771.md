## 설명

## 증상

같은 초대를 동시에 두 번 수락하면 두 요청이 모두 성공한다. 두 번째 호출은 409(STAFF_ALREADY_MEMBER)를 받아야 하는데 200 을 받고, 초대가 두 번 수락 처리된다.

2026-09-14 CI back-test job 533602 에서 `StaffInvitationConcurrencyIntegrationTest.acceptingTheSameInvitationTwiceAtOnceSeatsTheStaffOnceAndRefusesTheOther` 가 `expected: <1> but was: <2>` 로 실패하며 드러났다. 같은 브랜치에서 직전·직후 실행은 통과해 간헐 실패로 보였다.

## 원인

`StaffInvitationService.accept` 는 "두 번째 INSERT 가 booth_staffs 의 PK 에 걸린다" 를 전제로 try/catch + translateAccept 를 두고 있었으나, 그 INSERT 가 실제로는 일어나지 않는다.

`BoothStaff` 는 `@IdClass` 조립키라 id 가 항상 non-null 이다. Spring Data 의 `save()` 는 이를 이미 영속된 인스턴스로 보아 `persist` 가 아니라 `merge` 를 호출하고, merge 는 쓰기 전에 SELECT 를 수행한다. 경합에서 진 쪽의 merge-SELECT 가 이긴 쪽 커밋 이후에 도착하면 행을 찾아 UPDATE 를 발행한다. 제약 위반이 없으므로 예외도 없고, `translateAccept` 의 `booth_staffs_pkey` 분기는 이 경로에서 한 번도 실행되지 않았다.

사전 조회(`staffs.findRole`)가 보통 두 요청을 직렬화하기 때문에 로컬에서는 재현되지 않는다. CI 의 자원 경합이 그 틈을 벌렸다.

## 확인

- 수정 전 develop 에서 같은 (booth_id, user_id) 로 saveAndFlush 를 직접 호출 → 예외 없이 행이 갱신된다.
- `ON CONFLICT DO NOTHING` 을 제거한 변이에서는 `duplicate key value violates unique constraint "booth_staffs_pkey"` 가 발생한다. 제약 자체는 정상이며 쓰기가 INSERT 가 아니었던 것이 원인이다.

## 조치

- `BoothStaffRepository.seatIfAbsent` 신설: `INSERT ... ON CONFLICT (booth_id, user_id) DO NOTHING` 네이티브 쿼리로, 거절을 예외가 아니라 영향 행 수 0 으로 알린다.
- `accept` 의 try/catch 와 `translateAccept` 제거(호출부 없음). 초대 경로의 `translateInvite` 는 유지 — 부분 유니크 인덱스 위반을 예외로 받는 것이 맞다.
- 사전 조회는 흔한 경우를 싸게 거르는 용도로 유지.

## 회귀 고정

`writingOverATakenSeatChangesNothingAndReportsIt` 이 진 쪽의 쓰기만 분리해 결정적으로 검증한다. 두 호출에 서로 다른 role 을 주어 행 수뿐 아니라 role 덮어쓰기까지 단정한다 — 기존 merge 동작은 자리를 빼앗지 않고 role 만 덮어쓰므로 행 수 단정만으로는 잡히지 않는다.

## 완료 조건

- 같은 초대를 동시에 두 번 수락하면 성공 1 + 409 1, 500 은 0
- 진 쪽이 기존 행의 role 을 덮어쓰지 않음
- backend 전체 테스트 통과
