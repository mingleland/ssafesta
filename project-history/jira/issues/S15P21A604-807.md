## 설명

2026-09-15 에 도입한 파트 브랜치 배칭 규약(S15P21A604-185)과 .gitlab-ci.yml 의 workflow rule 이 어긋나 있다. 규약이 정한 마지막 단계를 설정이 구현하지 않는다.

h3. 현상
.gitlab-ci.yml 주석은 "각 파트가 자기 브랜치에 모아 둔 뒤 한 번에 develop 으로 올리기로 했다" 고 적고 있으나, develop 대상 MR 의 rule 은 source branch 를 타입 접두사(feat|feature|fix|refactor|test|docs|chore|build|ci|hotfix|perf 뒤 슬래시)로만 제한한다. 파트 브랜치 이름(ai/back/front/game)은 슬래시가 없어 어느 rule 에도 걸리지 않고 when: never 로 떨어진다.

결과적으로 back → develop MR 은 파이프라인이 0개로 생성되고, 프로젝트 설정이 only_allow_merge_if_pipeline_succeeds=true / allow_merge_on_skipped_pipeline=false 라 병합이 불가능하다. 규약이 지시한 경로에 출구가 없는 상태다.

h3. 확인한 사실

- 프로젝트 API 조회 — only_allow_merge_if_pipeline_succeeds=true, allow_merge_on_skipped_pipeline=false
- back 을 source 로 하는 MR 은 과거 이력 0건. 이 경로가 실제로 쓰인 적이 없다
- mr-status job 주석이 "파이프라인 없는 MR 을 skipped 로 취급하지 않게 한다" 고 적은 것과 같은 성격의 문제다

h3. 제안
develop 대상 + 파트 브랜치 source 조합을 받는 rule 을 하나 추가한다. 기존 타입 접두사 정규식은 건드리지 않는다.

target 이 develop 이므로 .{ai,back,front,game}-changes 의 target 가드가 풀려 컴포넌트 CI(test/build)와 Unity dispatch 가 전부 실행된다. 즉 이 변경은 검사를 줄이지 않고, 현재 0회인 구간에 전체 파이프라인을 붙인다.

h3. 리뷰가 판단해야 할 것
AGENTS.md / CLAUDE.md 8항은 "파트 브랜치 전체를 develop 에 머지하지 마라" 고 정하고 있다. 이 변경은 그 경로를 CI 상 가능하게 만든다. 8항의 근거였던 부분 트리 문제는 현재 back 기준으로는 해당하지 않으나(전체 트리 보유, develop 대비 삭제 파일 0개), 규약 문서와의 정합은 사람이 결정해야 한다. 승인 시 8항도 함께 갱신하는 것이 맞다.

h3. 해제
S15P21A604-185 주석의 해제 조건(러너 동시 실행 한도 증가 또는 배칭 종료)이 성립하면 이 rule 도 긴급 규약 rule 과 함께 지운다.
