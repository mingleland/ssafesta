## 설명

### 작업 목적

**어느 API 가 느린지 판정할 수단이 지금 하나도 없다.** 특정 기능이 아니라 백엔드 전체에 대해, 새 endpoint 가 생겨도 추가 작업 없이 자동으로 잡히는 상시 계측을 깐다.

계측이 있어야 개선 후보(ETag 재검증, 응답 압축, HTTP/2, 배치 endpoint, 인덱스 추가)의 우선순위를 정하고 적용 후 효과를 확인할 수 있다. 개선 작업 자체는 이 티켓 결과를 보고 별도로 편성한다.

### 왜 범용이어야 하는가

지금 endpoint 가 19개 컨트롤러에 걸쳐 있고 계속 늘어난다. endpoint 마다 측정 코드를 넣는 방식은 새로 만드는 사람이 빠뜨리는 순간 사각이 생기고, 빠뜨린 사실도 드러나지 않는다.

Spring 의 `http.server.requests` 는 **모든 HTTP endpoint 를 자동으로** 잡고 `uri` 태그에 경로 변수를 치환하지 않은 패턴(`/api/v1/booth-slots/{slotId}/layouts/published`)을 쓴다. 슬롯 12개가 12행으로 흩어지지 않고 한 행에 모인다. 새 endpoint 는 배포와 동시에 계측된다. 애플리케이션 코드 변경 0줄이다.

### 작업 내용

`spring-boot-starter-actuator` 는 이미 의존성에 있다. 설정과 의존성 하나만 더한다.

**⑴ metrics 노출**

`management.endpoints.web.exposure.include` 에 `metrics` 와 `prometheus` 추가.

**⑵ 백분위 히스토그램**

`management.metrics.distribution.percentiles-histogram.http.server.requests` 활성화, `percentiles` 에 0.5, 0.95, 0.99. 이게 없으면 평균과 최대만 나온다. 평균은 느린 요청을 숨기므로 판정에 쓸 수 없다.

**⑶ SLO 경계**

`management.metrics.distribution.slo.http.server.requests` 에 경계값 몇 개(예: 50ms, 200ms, 1s). "200ms 를 넘은 요청이 endpoint 별로 몇 건인가" 를 전 API 에 대해 한 번에 물을 수 있다. 느린 endpoint 를 찾는 것이 이 티켓의 목적이므로 이 항목이 실질이다.

**⑷ **`micrometer-registry-prometheus` 의존성 추가

**Prometheus 서버를 세우자는 것이 아니다.** `/actuator/prometheus` 가 주는 텍스트 한 덩어리에 **전 endpoint 의 수치가 한꺼번에** 담기기 때문이다.

`/actuator/metrics/http.server.requests?tag=uri:...` 는 endpoint 이름을 미리 알아야 하고 한 번에 하나씩만 읽힌다. 전체를 훑으려면 호출을 endpoint 수만큼 반복해야 한다. Prometheus 텍스트는 `curl` 한 번에 전부 나오고 `sort` 로 느린 순 정렬이 된다. 범용 도구가 되려면 이쪽이어야 한다.

**⑸ 관리 포트 분리**

`management.server.port` 를 애플리케이션 포트와 분리한다. 아래 보안 항목 참고.

**⑹ 기준선 기록**

전 endpoint 의 p50/p95/p99 와 표본 수를 `docs/HDD/작업일지.md` 에 한 번 남긴다. 이후 개선 작업이 비교할 대상이 된다.

### 덤으로 따라오는 것 — 추가 작업 없음

Actuator 가 이미 수집하고 있어서 노출만 켜면 함께 보인다.

- `hikaricp.connections.*` — 커넥션 풀 대기 시간과 고갈. 지연이 DB 대기인지 앱인지 가른다
- `jvm.gc.pause`, `jvm.memory.used` — GC 로 인한 지연 튐
- `lettuce.command.completion` — Redis 왕복 시간

### 보안 — 관리 포트를 분리해야 하는 이유

`SecurityConfiguration` 은 `/actuator/health` 만 `permitAll` 이고 나머지는 `.anyRequest().authenticated()` 다. 그런데 **게스트 토큰도 인증된 토큰이다.** `POST /api/v1/auth/guest` 는 인증 없이 누구나 호출할 수 있으므로, 관리 endpoint 를 같은 포트에 그냥 열면 사실상 공개가 된다. `/actuator/prometheus` 는 전 endpoint 목록과 트래픽 규모를 한꺼번에 노출한다.

`management.server.port` 를 별도 포트로 두면 compose 와 Nginx 가 그 포트를 외부에 공개하지 않는 것만으로 차단된다. Security 코드를 건드리지 않아도 되고, 내부 네트워크와 `docker exec` 로는 그대로 읽힌다. **포트 번호는 Infra 와 맞춰야 한다.**

### 이 티켓에서 하지 않는 것

측정 수단을 까는 것이 목적이므로 최소로 간다.

- Prometheus 서버, Grafana, 알림 — 단일 EC2 에 컨테이너를 더 얹을 근거가 아직 없다. 텍스트 endpoint 와 `curl` 로 충분하다
- 커스텀 지연 측정 필터나 응답 헤더 — `http.server.requests` 가 같은 값을 더 정확히 준다
- APM, 분산 추적
- 부하 생성 도구 — 반복 가능한 트래픽이 필요하면 `backend/bruno` 컬렉션(12개 도메인)을 재사용한다. 새로 만들지 않는다
- 개선 작업 자체 (ETag, 압축, HTTP/2, 배치 endpoint, 인덱스) — 이 티켓 결과를 보고 편성한다

### 완료 조건

- [ ] `/actuator/prometheus` 한 번의 호출로 **전 endpoint** 의 요청 수와 지연이 나온다
- [ ] `uri` 태그가 경로 변수를 패턴으로 유지한다 — 슬롯 12개가 12행으로 흩어지지 않는다
- [ ] p50, p95, p99 가 값으로 나온다. 평균만 나오면 미달이다
- [ ] SLO 경계별 누적 건수로 "기준을 넘은 요청" 을 endpoint 별로 셀 수 있다
- [ ] 관리 endpoint 가 애플리케이션 포트에서는 응답하지 않는다. 게스트 토큰으로 호출해도 마찬가지다
- [ ] 기존 `/actuator/health` 공개 동작이 유지된다
- [ ] 전 endpoint 기준선 수치가 작업일지에 남는다

### 테스트 방법

1. 애플리케이션을 띄우고 여러 도메인의 endpoint 를 호출한다. `backend/bruno` 컬렉션으로 인증·지갑·부스·프로젝트·게임을 한 바퀴 돌리면 충분하다
2. 관리 포트에서 `/actuator/prometheus` 를 호출하고 `http_server_requests` 행에 호출한 endpoint 가 전부 있는지 확인한다
3. 경로 변수가 다른 요청(슬롯 1번과 5번)이 같은 `uri` 태그로 합쳐지는지 확인한다
4. 게스트 토큰을 발급받아 애플리케이션 포트의 `/actuator/prometheus` 와 `/actuator/metrics` 를 호출하고 거부되는지 확인한다
5. `/actuator/health` 를 인증 없이 호출해 종전대로 응답하는지 확인한다

**⑴ 관리 포트를 고정값으로 박아 머지하면 dev 컨테이너가 unhealthy 로 떨어진다**

`infra/deploy/compose/dev/back.compose.yaml` 의 healthcheck 가 `wget -qO- http://127.0.0.1:8080/actuator/health` 다. `management.server.port` 를 옮기면 `/actuator/health` 도 함께 옮겨가므로 8080 에서 404 가 되고 healthcheck 가 실패한다. 그 파일은 Infra 소유라 BE 가 같이 못 고친다.

**대응 — 환경변수로 빼고 기본을 비운다.**

```yaml
management:
  server:
    port: ${MANAGEMENT_PORT:}
```

비어 있으면 Spring 이 애플리케이션 포트를 그대로 쓴다. 머지해도 dev 동작이 안 바뀐다. `application-local.yml` 에는 값을 박아 분리 동작을 검증한다. 배포 전환은 Infra 가 `MANAGEMENT_PORT` 주입과 healthcheck 줄을 한 MR 에서 같이 바꾸면 끝나고, 머지 순서 의존이 사라진다.

**⑵ 검증은 Infra 없이 로컬에서 전부 된다**

`backend/compose.yaml` 은 PostgreSQL·Redis 만 띄우고 애플리케이션은 `mvnw spring-boot:run` 으로 직접 돌린다. 완료 조건 7개 중 6개를 로컬에서 확인할 수 있다. 게스트 토큰으로 애플리케이션 포트의 관리 endpoint 를 호출해 거부되는지 보는 보안 검증도 로컬에서 그대로 재현된다. 트래픽은 `backend/bruno` 컬렉션으로 만든다.

Infra 가 실제로 필요한 것은 **배포 환경의 포트 번호 충돌 여부 하나**다. 현재 8081(back), 3001(front), 8000(ai), 7777(world) 이 쓰인다.

**⑶ 지금 dev 는 노출되지 않지만 demo 는 아직 판단할 자료가 없다**

dev 는 `ports: ["127.0.0.1:8081:8080"]` 로 loopback 바인딩이고, `infra/environments/nginx/sites/dev.conf` 가 allowlist + `deny all` 을 건다. 두 겹이라 당장은 닫혀 있다. 다만 allowlist 에 들어간 사람은 `/__dev/api/actuator/...` 로 도달할 수 있다.

`sites/` 에는 `dev.conf` 하나뿐이고 demo 용 Nginx 설정이 저장소에 없다. demo 가 넓은 `location /api/` 로 열리면 관리 포트를 분리하지 않는 한 `/api/actuator/prometheus` 가 인터넷에 공개된다. 게스트 토큰은 누구나 발급받으므로 인증이 방벽이 되지 못한다.

**따라서 이 티켓의 전환은 demo 공개보다 먼저 끝나야 한다.**

**Infra 에 통보할 항목 (아직 게시 안 함)**

GitLab 이슈 #123 이 열려 있고 dev Backend Compose MR 이 미머지 상태라 그 스레드에 코멘트하는 것이 맞다. 물을 것 1개, 알릴 것 2개.
