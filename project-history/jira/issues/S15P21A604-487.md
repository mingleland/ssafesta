## 설명

### 작업 목적

문서 Job 의 재시도 경로가 lease 보호와 attempt 펜싱을 둘 다 잃는다. S15P21A604-400 2차 커밋(daf91533)의 회귀다. 첫 시도가 실패한 모든 문서가 이 상태로 들어가므로 예외 경로가 아니라 주 경로다.

### 원인

daf91533 이 `markRunning` 을 지우고 그 일을 `extendLease` 안의 CASE 로 합쳤다. 옛 메서드는 상태를 무조건 `RUNNING` 으로 올렸는데, 새 CASE 는 `WHEN status = 'QUEUED'` 만 본다. 회수된 Job 의 상태는 `RETRY_WAIT` 이므로 그 가드에 걸리지 않고 그대로 남는다.

AiDocumentJobRepository.extendLease 의 다음 줄이다.

```
status = CASE WHEN status = 'QUEUED' THEN 'RUNNING' ELSE status END
```

### 연쇄

1. attempt 0 이 실패하거나 lease 가 만료되면 sweeper 가 `attempt_no = 1`, `status = RETRY_WAIT` 로 회수한다
2. 워커 B 가 attempt 1 로 집어 batch 나 heartbeat 를 보낸다. lease 는 잡히지만 상태는 `RETRY_WAIT` 그대로다
3. 워커 B 도 죽는다. sweeper 조건이 `status = 'RUNNING'` 이고 인덱스도 `ix_ai_document_jobs_lease ... WHERE status = 'RUNNING'` 이라 이 Job 은 영구히 회수되지 않는다
4. `ix_ai_document_jobs_active_document` 가 `RETRY_WAIT` 를 살아 있는 Job 으로 세므로 그 문서의 새 Job 도 영구히 막힌다. 문서는 READY 에 도달하지 못하고 재업로드로도 풀 수 없다
5. `attempt_no` 가 1 에 얼어 있으므로 FastAPI 가 `(status, next_retry_at)` 인덱스로 다시 집으면 워커 B 와 C 가 둘 다 attempt 1 로 펜싱을 통과한다

### 작업 내용

`extendLease` 의 승격 조건을 `RETRY_WAIT` 까지 넓힌다. 한 줄이다.

```
status = CASE WHEN status IN ('QUEUED','RETRY_WAIT') THEN 'RUNNING' ELSE status END
```

`SUCCEEDED`·`DEAD`·`CANCELLED` 는 그대로 둔다. 그 세 상태는 `AiDocumentResultService.live` 가 이미 410 으로 막으므로 여기에 도달하지 않지만, CASE 가 상태를 보존하는 편이 방어적으로 맞다.

### 완료 조건

- [ ] 회수된 Job 의 다음 attempt 가 신호를 보내면 상태가 RUNNING 으로 올라간다
- [ ] 그 attempt 의 워커가 죽어도 sweeper 가 회수해 attempt_no 가 다시 오른다
- [ ] 회귀 테스트 1개. 고치기 전에 실패하는 것을 확인한다

### 영향 범위

- AiDocumentJobRepository.extendLease 한 줄
- 마이그레이션 없음. 스키마 변경 없음. API 계약 변경 없음
- FastAPI 워커 쪽 변경 불필요 — 서버가 보내는 상태 전이만 고친다

### 테스트 방법

1. Job 을 만들고 batch 를 보내 RUNNING·lease 를 잡는다
2. lease 를 만료시키고 sweeper 를 돌려 RETRY_WAIT·attempt 1 로 회수한다
3. attempt 1 로 heartbeat 를 보내고 상태가 RUNNING 인지 본다
4. 다시 lease 를 만료시키고 sweeper 를 돌려 attempt_no 가 2 가 되는지 본다

- 상태 기계 자체가 틀렸고, 배차가 이 위에 얹히면 그때부터는 첫 시도가 실패한 모든 문서에서 재현됩니다
