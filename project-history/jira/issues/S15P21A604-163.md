## 설명

작업 목적

chunk-search 호출 경로에서 FastAPI가 자체적으로 부담하는 부분(질문 임베딩 계산·Spring까지의 HTTP client 왕복)이 SC-006 P95 1초 예산 안에 안정적으로 들어오는지 확인한다.

작업 내용

- VectorSearchService가 질문 임베딩 계산(GMS 실 Provider) → SpringChunkSearchClient HTTP 호출까지 거치는 자체 지연시간을 측정한다 (Spring 응답은 fake/mock으로 고정 지연 주입 가능)
- 임베딩 계산 자체의 지연시간과 HTTP client 오버헤드를 분리 측정해 SC-006 예산(1초)에서 AI 쪽이 차지하는 비중을 기록한다

완료 조건

- AI 쪽(임베딩 계산+HTTP client) 오버헤드 수치가 측정되고 기록된다

선행 작업 / Dependency

- https://ssafy.atlassian.net/browse/S15P21A604-148#icft=S15P21A604-148 (실 Provider)

참고

- specs/007 SC-006/007

비고

원래 이 이슈(tasks.md T067)는 검색 P95·Top-K 포함률 검증 전체를 festa-ai/tests/performance/test_rag_retrieval.py로 맡는 것이었으나, S15P21A604-449(검색 Spring 단독 소유 이관) 이후 P95의 실질 병목(pgvector 쿼리)과 Top-K 포함률(chunk-search 응답 자체)이 전부 Spring 프로세스·DB 안에서 결정됨을 확인해 범위를 AI 쪽 자체 오버헤드 측정만으로 축소했다. 검색 P95·Top-K 포함률 핵심 검증(Testcontainers 기반)은 신규 분리된 https://ssafy.atlassian.net/browse/S15P21A604-521#icft=S15P21A604-521 (Backend)가 담당한다.

테스트 방법

1. 질문 N개로 VectorSearchService 호출 반복 실행 → 임베딩 계산·HTTP client 구간별 지연시간 리포트
