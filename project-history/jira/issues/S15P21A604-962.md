## 설명

front-test 가 MR 마다 174 파일 전부를 돈다. 테스트를 지우지 않고, 전체 회귀를 develop 경계에서 한 번만 하도록 옮긴다.

정책
- 파트 브랜치(front/back/ai/game)행 MR: 변경이 실제로 닿는 테스트만 실행
- develop 행 MR: 기존 non-Game-Studio 전체 회귀 그대로
- CI 에서만 maxWorkers=2 (4코어 호스트에서 vitest 가 코어를 전부 쥐지 않게). 로컬 npm test 는 ci/test 를 거치지 않아 무변경

vitest --changed 를 쓰지 않은 이유 (실측)
- 이 저장소는 git 루트가 festa-frontend 의 상위다. vitest 가 제 root 에서 부른 git 이 돌려주는 경로(festa-frontend/src/...)를 다시 festa-frontend 기준으로 풀어 아무것도 맞지 않는다.
- 결과적으로 좁혀지지 않는다: list --changed 253, 필터 없음 253, 변경 0 인 상태에서 --run --changed 도 174 전량.
- 경로 계산을 ci/test 에서 하고(git diff --relative 가 이미 festa-frontend 기준 경로를 준다) vitest related 에 넘기면 그 구멍이 없다.

좁히지 않는 안전장치
- src/ 밖이 하나라도 바뀌면 전체를 돈다. vite.config·package.json·tsconfig 는 스위트 전체의 전제라 related 가 영향을 따라가지 못한다.
- base SHA 가 없거나 그 커밋이 클론에 없으면(shallow clone·수동 실행) 전체를 돈다.

실측
- 파트 MR(coinGrantNotification.ts 단일 변경): 15 파일 / 104 건 / 11.85s
- develop MR 전체: 174 파일 / 1258 건 / 66s (3회 64.50·66.21·67.75)
- 기존 테스트 삭제 0건

GitLab !1324(INFRA, front CI 고정 오버헤드 제거)와 겹치지 않는다 — 그쪽은 .gitlab-ci.yml·Jenkins 이고 ci/test 는 건드리지 않았다. front-test 에는 .junit-report 가 걸려 있지 않아 리포트 glob 과도 무관하다.
