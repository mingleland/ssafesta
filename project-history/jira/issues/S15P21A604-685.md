## 설명

### 증상

`ArcadeMachineSingleQueryTest.resolvingAMachineIssuesExactlyOneStatement` 가 **단독으로는 통과하고 전체 스위트에서는 실패**한다.

```
expected: <1> but was: <2>
```

2026-09-13 에 spec 011 의 초대 만료 스위퍼가 여덟 번째 `@Scheduled` 로 붙었을 때 실제로 깨졌다. 경위는 `docs/HDD/트러블슈팅.md` T-154.

### 원인

그 테스트는 `statistics.clear()` 뒤 `resolve()` 를 부르고 `getPrepareStatementCount()` 를 읽는다. **이 카운터는 세션이 아니라 **`SessionFactory` 전역이다. 같은 컨텍스트에서 도는 `@Scheduled` 스위퍼가 그 사이에 문장을 하나 쏘면 그대로 합산된다.

기존 스위퍼 7개와 새 것 모두 `initialDelay` 없이 **부팅 즉시 한 번** 돈다. 그 실행이 측정 구간에 겹치면 깨진다 — 지금까지 통과한 것은 타이밍이 맞아떨어졌기 때문이다.

### 지금 상태

`S15P21A604-137` 에서 새 스위퍼 둘에 `initialDelay` 를 줘서 **이번 충돌은 피했다.** 그러나 **구조는 그대로다** — 기존 7개는 여전히 부팅 즉시 돌고 카운터는 여전히 전역이다. 다음에 스위퍼가 하나 더 붙거나 기존 것의 주기가 바뀌면 같은 방식으로 깨진다.

### 수정 방향

`S15P21A604-682` 에서 같은 문제를 푼 방법이 그대로 적용된다 — **SQL 본문을 캡처해 텍스트로 거른다.**

`CapturingStatementInspector`(`booth` 패키지 테스트)가 이미 있다. `arcade_machine_bindings` 를 읽는 문장만 세면 다른 표를 건드리는 배경 작업은 애초에 집계에 들어오지 않는다. 전역 수집이지만 **판정이 SQL 텍스트에 매여 있어** 관계없는 문장에 흔들리지 않는다.

인스펙터를 공용 테스트 지원으로 옮길지, `game` 패키지에 같은 것을 둘지는 구현에서 정한다.

### 완료 조건

- [ ] 배경 스위퍼가 늘어도 그 테스트가 깨지지 않는다
- [ ] 두 질의로 되돌리는 변이에서는 여전히 실패한다 — 그물이 성한지 확인한다
- [ ] 같은 취약성을 가진 다른 테스트가 있는지 훑는다 (`getPrepareStatementCount`·`getQueryExecutionCount` 사용처)
