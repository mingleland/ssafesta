## 설명

### 작업 목적

"Coin 시스템 유효성은 배포 후 사용자 반응으로 검증하라"는 피드백을 실행 가능하게 만든다.

검증하려면 배포 전에 계측이 심어져 있어야 한다 — 배포 후에는 늦다.  
Coin·Lease 등 영구 상태의 Source of Truth 가 Spring 이므로 서버에서 기록하는 것이 정확하다.

### 작업 내용

- Booth 방문 이벤트 (boothId, userId, timestamp)
- Booth 체류시간 (입장/퇴장 쌍)
- Coin 획득·사용 흐름 (사유 코드 포함)
- 관리자용 집계 조회 1건 (Booth 별 방문수·평균 체류·Coin 순환량)
- Unity 클라이언트가 호출할 이벤트 API 계약 문서화

### 완료 조건

- [ ] 이벤트 API 계약 확정·문서화 (Unity 발신 지점과 합의)
- [ ] 방문·체류·Coin 3종 기록 동작
- [ ] 집계 조회 1건 동작

### 선행 작업 / Dependency

- 게임 클라이언트 발신 훅은 Booth 포털 텔레포트 지점 (BoothPortal/PortalInteractor)

### 참고

- GitLab 이슈 #94
- 검증 지표: Coin 획득 동기 / 사용처 / 방문·체류 증가 여부 / 보상 구조 실효성 / 운영 복잡도 대비 효과

### 테스트 방법

1. Booth 입장·퇴장 후 집계 조회로 방문수·체류시간 반영 확인

구현 완료. MR !777 (CI 초록, 머지 대기).

**새 표는 없습니다.** booth_visit_events 와 booth_daily_metrics 가 V1__initial_schema.sql 부터 있었고, 비어 있던 것은 쓰는 코드뿐이었습니다. 마이그레이션이 없습니다.

- POST /api/v1/booths/{boothId}/visits — 입장. 201 + visitId·enteredAt
- POST /api/v1/booths/{boothId}/visits/{visitId}/exit — 퇴장. 204
- GET /api/v1/booths/{boothId}/visit-metrics?from=&to= — 부스 운영자용 집계

세 가지 판단:

- **게스트도 셉니다.** visitor_user_id 가 nullable 인 것이 그 뜻이고, 부스 구경은 게스트에게 열려 있습니다(헌법 12조가 막는 것은 소유·결제). 통계에서 빼면 실제 트래픽을 절반만 봅니다
- **회원의 입장 신호가 두 번 와도 방문은 하나입니다.** 브릿지 이벤트는 재전송될 수 있고, 그때마다 행이 늘면 그 수로 "Coin 이 방문을 늘렸는가" 를 판단하게 됩니다
- **닫히지 않은 방문을 오류로 다루지 않습니다.** 브라우저를 그냥 닫으면 퇴장 신호가 오지 않습니다. 평균 체류에서 빼고 그 수를 openVisits 로 따로 보고합니다 — 임의의 timeout 으로 닫으면 체류시간이 실제 값이 아니라 서버가 고른 상수가 됩니다

일부러 하지 않은 것 셋: 코인 순환량(이미 원장에 사유 코드와 함께 남습니다. 부스별 집계는 S15P21A604-501 몫), 플랫폼 전체 집계(전역 관리자 권한 모델 미정 — S15P21A604-165), booth_daily_metrics 선집계(부스 12개 규모에서는 실시간이 맞습니다).

**첫 완료 조건이 남아 있습니다.** "이벤트 API 계약 확정·문서화 (Unity 발신 지점과 합의)" 의 합의가 아직입니다. docs/08 §14-1 에 계약과 함께 물어야 할 것 세 가지를 적어 두었고, 통보 초안도 준비했습니다(게시는 승인 대기).

1. Unity 가 부스 구역 이탈을 브릿지로 알리는가 — 이것이 체류시간 표본을 가릅니다
2. worldChannel 값의 형식
3. 진입 이벤트 재전송을 발신 쪽에서 억제할 수 있는가
