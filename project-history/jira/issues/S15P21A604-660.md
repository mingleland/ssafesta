## 재현 방법

1. 브라우저/프로필 A 에서 로그인한다.
2. 브라우저/프로필 B 에서 같은 계정으로 로그인한다.
3. A 가 보유 중인 기존 Refresh Token 으로 `POST /api/v1/auth/refresh` 를 호출한다.

같은 브라우저의 탭끼리는 HttpOnly Refresh 쿠키를 공유하므로 탭 두 개로는 재현되지 않는다. 재로그인하면 옛 탭도 새 쿠키를 보내기 때문이다. 쿠키 저장소가 분리된 두 프로필이 필요하다.

## 기대 결과

- A 만 `401` 로 거부되고 B 의 세션은 유지된다.
- spec 001 시나리오 4 가 보장하는 상태다 — "같은 계정으로 브라우저 B에서 새 로그인을 완료하면 A의 인증 세션·Refresh Token·월드 접속은 즉시 종료되고 B의 새 세션만 보호 기능과 월드를 이용할 수 있다."

## 실제 결과

- A 가 `401` 을 받는 동시에 B 도 로그아웃된다. B 사용자는 아무것도 하지 않았는데 로그인 화면으로 돌아간다.

경로는 다음과 같다.

- `issue()` 가 새 로그인마다 직전 해시를 `markReused` 로 기록한다 (`backend/src/main/java/com/example/ssafesta/auth/MemberSessionService.java:34-37`).
- A 의 재시도는 `refresh()` 에서 `getAndDelete` 가 `null` 을 받아 재사용 분기로 들어간다 (`:60-65`).
- 그 분기가 `revoke(userId)` 를 호출해 `auth:active:{userId}` 와 `auth:session:{userId}` 를 지운다 (`:75-83`).
- `SessionRevocationFilter` 가 `auth:session:{userId}` 로 세션 유효성을 판정하므로 B 의 Access Token 이 즉시 무효가 된다.

명시적 로그아웃 뒤 재로그인해도 같은 결과가 나온다. `revoke()` 역시 `markReused` 를 기록하기 때문이다 (`:78`).

### 왜 "설계대로"가 아닌가

spec 001 시나리오 7 은 "이미 교체되어 폐기된 Refresh Token 이 다시 사용된 상황"을 말한다. 즉 정상 rotation 으로 소비된 토큰이다. A 의 토큰은 rotation 이 아니라 새 로그인에 밀려 폐기됐다. 구현이 두 폐기 사유를 구분하지 않아, 시나리오 7 의 처분이 시나리오 4 의 보장을 덮어쓴다.

`docs/LJH/25_트러블슈팅.md` T-71 이 같은 동작을 관측하고 "설계대로"로 판정한 적이 있다. 그때의 재현은 curl 과 브라우저로 같은 토큰을 동시에 쓴 상황이었고, 위 재현은 정상 사용 경로다.

## 수정 방향 (확정이 아니라 후보다)

폐기 사유만 구분하면 다음 순서에서 여전히 새 세션이 종료된다.

1. A 로그인 → R1 발급
2. A 갱신 → R1 은 rotation 소비분이 되고 R2 발급
3. B 새 로그인 → A 계열을 밀어내고 R3 발급
4. 한참 뒤 R1 재사용 → "rotation 소비분"이라는 이유만으로 `revoke(userId)` → B 의 R3 까지 종료

그래서 폐기 사유와 로그인 계보(session family) 둘 다 필요하다. 현재 `refresh()` 는 갱신마다 `sessionId` 를 새로 만들므로 (`:40`) 당시 `sessionId` 를 저장해 비교하는 것으로는 연속 rotation 을 한 계보로 묶을 수 없다.

- 새 로그인마다 새 `sessionFamilyId` 를 만든다.
- rotation 은 같은 family 를 물려받는다.
- 소비된 토큰에 `ROTATED` + `familyId` 를, 밀려난 토큰에 `SUPERSEDED` 를 기록한다.
- 재사용 시 현재 활성 family 와 같을 때만 세션을 차단한다.
- `SUPERSEDED` 이거나 다른 family 면 `401` 만 낸다.

`refresh()` 에서 `revoke()` 를 무조건 제거하면 시나리오 7 이 깨지므로 그 방향은 쓰지 않는다.

### Redis 값 스키마 호환 (DB 마이그레이션은 없다)

`app.auth.refresh-token-ttl` 이 `P7D` 라서 배포 뒤 최대 7일 동안 구형 값이 남는다. `refresh()` 는 현재 `split(":", 2)` 뒤 `values.length != 2` 면 거부하므로 (`:67-70`), 새 코드가 `reason` 과 `familyId` 를 무조건 기대하면 배포 직후 전 회원의 갱신이 실패한다.

정책은 키마다 다르다. 하나로 묶으면 "구형 토큰도 갱신된다"와 "필드가 모자라면 401"이 서로를 부순다.

| 구형 키 | 구형 값 | 처분 |
|---|---|---|
| `auth:refresh:{hash}` | `userId:sessionId` | 살아 있는 토큰이다. 기존 세션 유효성을 확인하고 갱신 1회를 허용한다. 이때 `familyId` 를 만들어 새 포맷으로 전환한다 |
| `auth:refresh:used:{hash}` | `userId` | 원래 family 도 폐기 사유도 알 수 없다. `401` 만 내고 현재 활성 세션은 건드리지 않는다 |
| `auth:session:{userId}` | `sessionId` | 기존 검증을 그대로 쓴다. 최초 정상 갱신 때 family 정보를 함께 초기화한다 |

구형 `used` 를 "알 수 없으니 차단" 쪽으로 두면 배포 직후 며칠간 이 결함이 그대로 재현된다.

## 테스트 방법

1. A/B 프로필 — A 로그인 → B 로그인 → A 최초 토큰 재사용 → B 유지
2. 계보 경계 — A 로그인 → A rotation → B 로그인 → A 의 최초 토큰(rotation 소비분) 재사용 → B 유지
3. 다단 회전 — A 로그인 R1 → R2 → R3 연속 회전 후 R1 재사용 → 현재 R3 세션 차단
4. 구형 활성 토큰 — 구형 `auth:refresh` 값을 심어 두면 갱신이 정상 성공하고 새 포맷으로 전환된다
5. 구형 used 토큰 — 구형 `auth:refresh:used` 값을 재사용하면 `401` 이지만 현재 로그인 세션은 유지된다
6. 경합 — 재사용 판정이 활성 family 를 읽은 직후 B 가 로그인해도 B 세션이 유지된다

3번은 한 번짜리 기존 테스트로도 "회전마다 새 family 를 발급하는" 구현은 잡히지만(활성 family 가 달라져 revoke 를 기대하는 단정이 깨진다), 여러 홉을 지나며 family 가 흘러내리는 구현은 이것으로만 잡힌다. 6번은 기존 `twoSimultaneousRefreshesWithOneTokenIssueOnce` 와 같은 자리에 둔다.

기준 테스트 파일: `backend/src/test/java/com/example/ssafesta/auth/MemberSessionServiceIntegrationTest.java`
