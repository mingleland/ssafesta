## 설명

## 증상

`BoothLeaseConcurrencyIntegrationTest.aSweeperThatLocksFirstMakesTheReturnWaitAndThenRefusesIt()` 가 CI 에서 간헐적으로 실패한다. 프로덕션 코드 변경과 무관하게 실행할 때마다 결과가 달라진다.

- 관측: GitLab MR !905 파이프라인 195600 back-test (job 539192), 1413개 중 1건 실패
- 실패 단언: `BoothLeaseConcurrencyIntegrationTest.java:134` 의 `assertEquals(1, leaseService.expireStaleLeases())` 에서 `expected: <1> but was: <0>`
- 같은 브랜치를 로컬에서 전체 실행(1405 tests)했을 때는 실패 0건. MR !905 가 바꾼 파일은 상담(consultation) 쪽이고 이 테스트와 겹치는 파일은 없다.

## 원인

테스트가 증명하려는 것은 "만료 배치가 임대 행을 먼저 잠그면, 반납은 락이 풀릴 때까지 기다렸다가 거절된다" 인데, 코드가 그 순서를 강제하지 않는다.

반납 스레드를 `pool.submit()` 으로 먼저 띄운 뒤에 메인 스레드가 `expireStaleLeases()` 를 호출한다. 두 스레드가 그대로 경쟁한다. 현재 쓰이는 `returnStarted` 래치는 워커 스레드가 스스로 내리는 것이라 "스레드가 시작됐다"만 증명하고 배치와의 선후 관계는 증명하지 않는다. `@RepeatedTest(REPEATS=5)` 이므로 실행마다 이 경쟁을 5번 반복한다.

반납이 먼저 이겼을 때 배치가 0을 돌려주는 이유는 **SKIP LOCKED** 다. `BoothLeaseRepository.findStaleActive` 는 `jakarta.persistence.lock.timeout = -2`, 즉 `SKIP LOCKED` 로 행을 집는다. 같은 리포지토리의 javadoc 이 두 순서를 모두 정의해 두었다 — 반납이 먼저 잠그면 배치가 그 행을 건너뛰고, 배치가 먼저 잠그면 반납의 `SELECT ... FOR UPDATE` 가 대기한다. 반납 스레드가 `findActiveByLesseeUserIdForUpdate` 로 행 락을 쥐고 있는 동안 배치가 돌면 배치는 그 행을 세지 못하고 0을 돌려준다.

임대 상태가 CANCELLED 로 바뀌어서가 아니다. `cancel()` 은 `ends_at` 이 지난 임대를 만나면 `ActiveLeaseNotFoundException` 을 던지고 롤백하므로 (`BoothLeaseService.java:167-173`) 이 시나리오에서 상태를 바꾸지 못한다. 반납에 300ms 선행을 준 실험에서 `expireStaleLeases()` 는 그대로 1을 돌려줬다.

같은 파일의 쌍둥이 테스트 `aReturnThatLocksFirstMakesTheSweeperPassTheRowOver()` 가 반대 순서를 이미 덮는다. 두 순서 모두 정상 동작이며 프로덕션 코드에는 결함이 없다.

### 왜 로컬에서 재현되지 않나

한가한 장비에서는 두 스레드가 겹치는 창이 좁다. 해당 테스트만 8회(40 invocation) 실행해 실패 0건. CI 는 러너가 1대뿐이라 back-test 가 서로 겹쳐 돌면서 창이 넓어진다 — job 538640(13:26:20~13:34:08)과 538643(13:27:17~13:36:11)이 7분 겹쳤다.

## 확인

반납과 같은 방식으로 행 락을 쥔 채 배치를 돌리는 probe 로 `expected: <1> but was: <0>` 를 1/1 재현했다. CI 실패와 같은 시그니처다.

## 수정

`sweeperLocked` 래치를 추가해 반납 스레드가 배치의 락 확보 이후에만 출발하도록 한다.

- 워커: `cancel()` 호출 전에 `sweeperLocked.await(10s)` 로 대기
- 메인: `assertEquals(1, expireStaleLeases())` 직후 `sweeperLocked.countDown()`
- `finally` 에서도 `countDown()` — 앞에서 실패해도 워커가 매달리지 않게

프로덕션 코드는 변경하지 않는다. 테스트가 원래 증명하려던 성질은 그대로이며, 순서가 강제되면서 비로소 실제로 증명된다.

## 완료 조건

- 동일한 300ms 선행 probe 로 전후 비교: 수정 전 실패, 수정 후 통과
- probe 없이 해당 테스트 반복 실행에서 실패 0건
- backend 전체 테스트 스위트 통과
