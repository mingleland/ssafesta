## 설명

Booth Studio 2.5D 캔버스가 컴파일된 GLB 의 authored 색을 일부만 유지하고 나머지는 계약 색으로 덮어쓴다. 한 모델 안에서 면마다 색이 갈린다.

실측 (.generated/runtime GLB 재질 덤프):
  FURN_CHAIR_01_WHITE_2   metallicRoughnessTexture 만 · baseColorTexture 없음
  FURN_COUNTER_02_6 / _8  metallicRoughnessTexture 만
  FURN_COUNTER_02_7       텍스처 없음
  STRUCT_PANEL_01_2       metallicRoughnessTexture 만
  FURN_CHAIR_02_WHITE_2   baseColorTexture + normal + metallicRoughness (정상)

source 경계 판정 — 컴파일러 결함이 아니다:
  intermediate GLB 는 unityMaterialPath extras 로 원본 .mat 를 그대로 물고 있다
  (AluminiumBrushed.mat · PlasticWhite.mat · Default-Material_URP.mat).
  PlasticWhite.mat 실측: _BaseMap.m_Texture = fileID 0, _MainTex.m_Texture = fileID 0.
  즉 원본 Unity 재질에 albedo 맵이 아예 없다. 색은 _BaseColor/_Color factor 로만 존재하고
  compiler(material.mjs)가 그것을 baseColorFactor 로 정확히 옮긴다.

FE 결함:
  AssetMesh.hasTexture() 가 map || normalMap || metalnessMap 로 판정한다.
  맵이 하나라도 있으면 계약 색을 건너뛰고, 하나도 없으면 OBJECT_FILL[type] 로 덮는다.
  그런데 컴파일된 GLB 는 항상 authored baseColorFactor 를 들고 온다.
  결과: metallicRoughness 만 든 재질은 authored 색 유지, 맵 없는 재질은 타입 색으로 덮임.
  FURN_COUNTER_02 는 한 모델 안에서 두 경우가 섞여 면마다 색이 다르게 나온다.

판정 축이 틀렸다. 기준은 '맵이 있는가' 가 아니라 '실물 GLB 인가 파라메트릭 박스인가' 여야 한다.
실물 GLB 는 자기 색을 들고 오므로 계약 색으로 덮을 이유가 없고, 계약 색은 asset 이 없을 때의
파라메트릭 박스 전용이다.

주의 — 겹침/경계 이탈 표시(invalid)가 지금 같은 색 경로를 탄다. 덮어쓰기를 걷으면 그 표시를
재질 교체가 아닌 다른 수단으로 옮겨야 한다. 설계 결정이 하나 필요하다.

착수 순서: R3FBoothRenderer 의 색 결정부를 S15P21A604-754(회전 반영 AABB 클램프)가 같이 만지고
있어 그것이 develop 에 닿은 뒤에 얹는다.
