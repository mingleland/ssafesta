## 설명

걸을 때 프레임이 느려졌다 빨라졌다 한다는 사용자 지적을 실측했다. 원인이 둘이고, 이 이슈는 그중 첫째를 다룬다.

측정 환경: FE 임베드(localhost:5173) + 게스트 접속, 개발 빌드, 보이는 탭, RTT 25 ms.

1. 해상도 과잉 (이 이슈)

백버퍼 2880x1530 = 4.41 M 픽셀
CSS 표시 1309x695 = 0.91 M 픽셀
devicePixelRatio 2.2 → 필요한 것의 4.84배를 렌더링한다.

스폰 지점 GPU 시간이 22.0 ms 다. vsync 예산 16.7 ms 를 이미 넘는다. 즉 가만히 서 있어도 60 fps 를 지킬 수 없다.

정지 상태 프레임 분포 (5초, 246 샘플):
p50 16.7 ms / p95 25.1 ms / p99 33.4 ms / max 41.6 ms
16.7 ms 초과가 63% (156/246), 33 ms 초과 8회

p50 이 정확히 16.7, 스파이크가 정확히 33.4 다. 한 프레임을 놓치면 즉시 절반으로 떨어지는 vsync 드롭 패턴이고, 그래서 부드럽지 않고 툭툭 끊기게 느껴진다.

1. 드로우콜 변동 (별건으로 분리)

아케이드 골목(벽이 시야를 막음) 드로우콜 136 / SetPass 35 / 삼각형 168 K
부스 거리 개활지 드로우콜 724 / SetPass 120 / 삼각형 1.32 M

시야가 트일 때마다 5.3배로 뛴다. 오클루전 컬링 점검이 필요하다.

조치

DPR 상한을 두어 백버퍼를 실제 표시 크기에 가깝게 맞춘다. 1.0 이면 4.84배가 1배, 1.5 면 2.25배가 된다. 화면이 선명한 정도와 프레임 사이의 균형은 실측으로 정한다.

주의: 캔버스 백버퍼를 JS 에서 직접 바꾸면 안 된다. 검증 중에 canvas.width/height 를 직접 수정했더니 유니티 렌더 루프가 멈췄고 rAF 정지로 NGO 연결까지 끊겼다(재접속 UI 노출, 렌더러 프리즈). 반드시 유니티 쪽에서 Screen.SetResolution 또는 WebGL 템플릿으로 처리한다.

검증: 같은 지점에서 GPU 시간과 프레임 분포를 다시 재고, 화면 선명도를 눈으로 확인한다. 용량이 아니라 보이는 품질과 부드러움으로 판단한다.

### 강형순 · 2026-09-07 13:13 KST

해상도 상한은 유니티 쪽에서 못 막는다. 시도했고 역효과를 확인해서 되돌렸다.

Screen.SetResolution 으로 상한을 걸면 줄어들긴 하는데, 로더의 matchWebGLToCanvasSize 가 다음 프레임에 원래 크기로 되돌린다. 그래서 0.5초마다 백버퍼가 재생성되고 없던 끊김이 새로 생겼다. 로그가 146회 이상 같은 줄을 반복했다.

원인 지점은 FE 다. src/unity/host/loader.ts 가 createUnityInstance 를 부르면서 config 에 devicePixelRatio 를 넘기지 않아 유니티가 기본값(window.devicePixelRatio = 2.2)을 쓴다. 이 값은 createUnityInstance 를 부르는 쪽에서만 정할 수 있다.

GitLab #143 으로 FE 에 요청했다. Math.min(window.devicePixelRatio ?? 1, 1.5) 한 줄이면 4.84배가 2.25배가 된다.

이 이슈는 FE 대응 대기로 둔다. 게임 파트가 코드로 할 일은 없다.

### 강형순 · 2026-09-07 14:14 KST

근거 수치를 정정한다. 코덱스 진단이 지적했고 확인 결과 내가 틀렸다.

1. "GPU 시간" 이 아니었다

내가 근거로 쓴 22.0 ms · 35~67 ms · 49→27 ms 는 GPU 시간이 아니라 최근 1초 창의 최악 프레임 시간이다. PerfHud.cs:204 가 한 줄에 FPS / 평균 ms / 최악 ms 세 값을 찍는데, FE 조작 안내 카드가 앞의 두 값을 가려서 오른쪽 끝 값만 보였고 그것을 GPU 시간이라 단정했다. 이 클래스에 GPU 계측은 0건이다.

1. 과잉 배율도 과장이었다

Mobile_RPAsset 에 m_RenderScale: 0.8 이 이미 적용돼 있었다(da286556, 내 커밋 아님). 그래서 "표시 픽셀의 4.84배" 가 아니라 실효 약 3.1배다.

1. 무엇이 남는가

49 → 27 이라는 값 자체는 사실이고, "1초 창 최악 프레임" 은 체감(툭툭 끊김)과 오히려 더 직결되는 지표다. 조명 Per Vertex 전환의 방향은 유효하고 Mobile_RPAsset 변경은 유지한다.

다만 GPU 병목을 확정한 근거는 아니다. 정식 GPU trace 가 없다. 그리고 통제된 A/B 도 아니다 — 같은 지점이라고 했지만 카메라 각도를 통제하지 못했고, 워밍업·반복 측정·p95/p99 없이 한 번 읽은 값이다. "DPR 한 줄이면 60 fps" 라고 쓴 것도 근거 없는 단정이라 취소한다.

1. 다음에 이 작업을 이어받는 사람에게

측정 표시부터 고쳐야 한다. HUD 가 FPS·평균·p95·p99·최악·GC·RTT 를 분리해 보여주고 조작 안내와 겹치지 않아야 한다. 그 전에는 어떤 최적화 A/B 도 신뢰할 수 없다. 그리고 Editor 는 PC_RPAsset(PerPixel/4/renderScale 1.0), WebGL 은 Mobile_RPAsset(PerVertex/4/renderScale 0.8) 로 파이프라인이 다르므로 Editor FPS 로 WebGL 을 판정하면 안 된다.

정정 기록: 작업일지 해당 절 머리 + 트러블슈팅 T-133. GitLab #143 에도 같은 내용으로 회신했다.
