## 설명

## 1. 요약

"사용자가 자신의 공간을 스캔해서 서비스 안의 3D 공간으로 반영한다"는 기능은 3단계 하위 기능으로  
구성되어 있었다. 조사 및 실험 결과, 아래와 같이 판단하여 **기능 전체를 진행하지 않기로 결정**했다.

| 하위 기능 | 상태 | 근거 |
|---|---|---|
| ① 실시간 3D 스캔 → 모델 파일 저장  | 기각 (기술적으로 불가능)  | `reason-scanning-unavailable.md`  |
| ② 사용자 제공 고폴리 모델 → 로우폴리 변환  | 검증 완료 (기술적으로 가능함을 확인)  | `low-poly-conversion-story.md`  |
| ③ 로우폴리 공간을 서비스 내 실제 공간으로 편입  | 미착수 (착수 전 리스크 근거로 보류)  | 본 문서 6장  |

①은 웹 플랫폼 자체의 원천적 제약으로 막혀 있고, ②는 기술적으로는 증명됐으나 그 결과를 실제  
서비스 공간으로 쓰기 위한 ③단계에서 감수해야 할 리스크가 부가기능 대비 과도하다고 판단하여,  
①②③ 전체를 하나의 기능으로 보고 진행하지 않기로 결정했다.

## 2. 목적

이 문서는 "왜 이 기능을 하지 않기로 했는가"에 대한 의사결정 근거를 기록하여, 추후 동일한 논의가  
반복되지 않도록 하고, 관련 조사·실험 결과를 재사용 가능한 형태로 남기는 것을 목적으로 한다.

## 3. 조사 범위 및 방법

①의 실현 가능성 조사(iOS/Android 플랫폼별 스캔 기술 및 웹 접근성 조사)와, ②의 실현 가능성 검증  
(6개 이상의 저폴리 변환 방법론을 실제 44.8만 폴리곤 규모 모델에 적용해 비교 실험, 이 중 최종  
후보는 Unity C#으로 포팅하여 실제 WebGL 빌드로 브라우저에서 실측)까지 진행했다.

| 조사한 방법론 | 채택 여부 |
|---|---|
| QEM 기반 일반 메시 디시메이션  | 기각 (콜리전 안전성 없음)  |
| CGAL Kinetic Surface Reconstruction (KSR)  | 기각 (서버 전용, 텍스처 미보존, WebGL 실행 불가)  |
| Robust Low-Poly Meshing (SIGGRAPH 2023)  | 기각 (처리시간/메모리 비용 과다)  |
| Voxelization + Greedy Meshing  | **최종 채택 후보** (②의 검증 완료 방법론)  |

## 4. 기능 ① — 실시간 스캔: 기각 근거

iOS는 Safari가 WebXR Depth Sensing 자체를 지원하지 않아 완전히 막혀 있고, Android는 Chrome  
브라우저에서만 우회 가능하나 일반 페이지가 아닌 immersive AR 세션으로만 동작 가능하다. 이는  
Unity WebGL, React SPA 등 프론트엔드 프레임워크와 무관한 **브라우저/OS 레벨의 근본 제약**이라,  
프레임워크를 바꿔도 결론이 달라지지 않는다.

|  | 실시간 스캔 기술 | 기기 제약 | 웹(브라우저) 접근 |
|---|---|---|---|
| iOS  | RoomPlan (LiDAR 기반)  | LiDAR 탑재 Pro 기종만  | 불가 — Safari가 WebXR Depth Sensing 자체를 미지원  |
| Android  | ARCore Depth API (카메라만으로도 가능)  | LiDAR 불필요, 대부분 기종  | Chrome 전용 우회 경로만 존재, 그마저도 immersive AR 세션 필요  |

## 5. 기능 ② — 로우폴리 변환: 검증 결과

콜리전 안전성(바닥 평탄화), 텍스처 보존, Unity WebGL 클라이언트 실행 가능성 3가지 요구사항을  
모두 만족하는 방법론(Voxelization + Greedy Meshing)을 찾아 실제로 구현하고 실측했다.

| 방법론 | 처리시간 (44.8만 폴리곤 기준) | 콜리전 안전 | 텍스처 보존 | WebGL 클라이언트 실행 |
|---|---|---|---|---|
| QEM 디시메이션  | 매우 빠름  | ✗  | ✓  | ✓  |
| CGAL KSR  | 약 17초 (서버 전용)  | ✓  | ✗ (별도 베이킹 필요)  | ✗ (WASM rounding mode 이슈)  |
| Robust Low-Poly Meshing  | n=300 기준 20분 30초, 메모리 24GB+  | ✓  | 미검증 (기각)  | 미검증  |
| **Voxel + Greedy Mesh**  | **0.1~0.9m: 0.6~0.9초 (네이티브), 브라우저 실측도 유사**  | **✓**  | **✓ (텍스처 색상 샘플링 검증 완료)**  | **✓ (실측 완료)**  |

## 6. 기능 ③ — 서비스 공간 편입: 미착수 사유 및 예상 리스크

②가 검증됐다고 해서 그 결과물을 실제 서비스 공간으로 바로 쓸 수 있는 것은 아니며, 착수 전  
아래 3가지 리스크가 식별되어 실험 자체를 시작하지 않기로 했다.

| 리스크 유형 | 내용 |
|---|---|
| 기술  | ②에서 증명한 것은 "바닥의 콜리전 평탄화"이며, 벽면 전체를 게임 공간으로 쓸 수 있는 수준의 매끈한 실루엣으로 만드는 것은 별도의 미해결 난제로 예상됨  |
| 설계  | 사용자마다 다른 형태·크기로 생성되는 공간을, 기존 서비스의 공간 체계에 어떻게 연결할지에 대한 설계가 전무함  |
| 운영/자원  | 부가기능에 불과한 이 파이프라인이, 사용자 공간 수 증가에 따라 서버 자원의 대부분을 차지하는 주객전도가 발생할 수 있음 (사전 부하 테스트에서 확인한 코어당 처리 비용 기준)  |

## 7. 종합 의사결정 (Go / No-Go)

①은 플랫폼 제약으로 원천 봉쇄되어 대안이 없다. ②는 기술적으로는 증명됐으나, 이는 전체 기능의  
일부에 불과하며 ③단계의 리스크(기술 난이도·설계 공백·자원 리스크)가 해소되지 않은 상태다.  
부가기능 하나에 이 정도 규모의 추가 리스크를 감수할 근거가 부족하다고 판단하여, ①②③ 전체를  
**현재 시점에는 진행하지 않는다**로 최종 결정한다.
