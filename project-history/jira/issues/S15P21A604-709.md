## 설명

# 작업 목적

Game Studio에서 업로드한 자산을 "삭제"하면 화면에서는 사라지지만 실제로는 서버에 삭제 요청조차 도달하지 못하고 그대로 남는다. 이 상태 불일치를 문서화하고, BE 구현 여부·FE 처리 방향을 팀이 결정하도록 한다.

# 배경

`remoteAssetRepository.ts:157-169`의 `delete`는 `DELETE /api/v1/games/{gameId}/assets/{assetId}`를 호출하는데, `GameAssetController.java`에 `@DeleteMapping`이 아예 없다(계약 §7만 있고 미구현).

실제 로컬 백엔드로 재현한 결과, 단순 미구현 이상의 문제가 확인됐다. `GameStudioShell.tsx:816-827`의 `deleteAsset`은 **로컬 프로젝트에서 자산 참조를 먼저 지우고**, 그 다음 서버에 삭제 요청을 보낸다. 서버 요청이 실패해도 이미 지운 로컬 참조는 되돌리지 않는다. 그 결과:

- `DELETE .../assets/{assetId}` → `404 Not Found`
- 토스트: `"요청한 리소스를 찾을 수 없습니다."` (자산과 무관한 일반 문구)
- 그런데도 ASSETS 패널에서는 자산이 즉시 사라짐(59/300 → 58/300)
- 서버 자산 행·MinIO 객체는 그대로 남고, 저장해도 스키마상 문제가 없어 이 상태가 그대로 굳어짐 — 정리할 방법이 없는 고아 리소스가 된다

즉 "삭제 실패"가 아니라 **"실패했다고 알리면서 실제로는 로컬만 삭제된 것처럼 보이는" 모순된 UX**다.

# 작업 내용

1. (완료) BE endpoint 부재와 실제 UI 동작을 코드+실측으로 확인
2. BE 구현 여부·우선순위 결정 (계약 §7 기준으로 구현할지, 언제)
3. 결정 전까지 FE 임시 처리 방향 결정 — 아래 중 택 1
   
   - 로컬 참조 제거를 서버 삭제 성공 이후로 순서 반전
   - 실패 시 로컬 상태 원복(rollback)
   - 서버 모드에서 삭제 버튼 임시 비활성화
4. 결정된 방향에 따라 구현 (필요 시 후속 티켓 분리)

# 테스트 방법 (재현 절차, 실측 완료)

1. 커스텀 자산 업로드 후 저장
2. 해당 자산 "삭제" → 확인 모달에서 삭제 확정
3. Network 탭에서 `DELETE .../assets/{assetId}` → `404` 확인
4. ASSETS 패널에서 자산이 사라짐(로컬 상태만 변경됨) 확인
5. 서버 재조회로 자산이 실제로는 남아있음 확인
6. 저장 후 새로고침해도 이 불일치가 지속됨을 확인
