## 설명

### 작업 목적

FastAPI가 DB에 직접 접속하지 않게 되면서(GitLab 이슈 #119), 처리 API와 별개로 검색 경로가 반드시 필요하다. 이 API가 없으면 RAG 답변 생성이 아예 동작하지 않는다. FastAPI가 질의 임베딩만 계산해 Spring에 넘기고, Spring이 scope를 서버에서 강제한 뒤 chunk를 돌려준다.

### 계약 정본 — GitLab MR !344 (2026-09-06 개정)

**계약 파일은 AI 파트가 이미 작성했다:** `specs/008-ai-conversation-rag/contracts/spring-chunk-search-api.yaml` (MR !344, 브랜치 `docs/S15P21A604-449-ai-document-contract`, 2026-09-06 시점 develop 미머지). 이 티켓은 그 계약을 구현한다.

- 엔드포인트: `POST /internal/ai/chunk-search`
- 요청: `boothId`, `agentId`, `queryEmbedding`(1536차원), `topK`(1~20)
- **응답 필드 7개(camelCase):** `content`, `chunkNo`, `pageNumber`, `section`, `documentId`, `originalFilename`, `distance` — 인용 시 "몇 페이지 / 어느 문서"를 답변에 표기해야 해서 `pageNumber`·`section`·문서명이 필수다
- `distance` = pgvector 코사인 거리(`<=>`) 값 그대로. 낮을수록 유사하고 서버가 뒤집거나 정규화하지 않는다. **최소 유사도 임계값은 걸지 않는다** (GitLab #119, 2026-09-03 AI 파트 확정 · 09-05 BE 확인)
- 정렬은 `distance` 오름차순, `topK` 상한 20, 타임아웃 3초, 성능 목표 P95 1초

> ⚠️ 2026-09-02 회신 기준의 snake_case 표기(`chunk_no`·`page_number`·`original_filename`)는 **폐기됐다.** 계약 작성자이자 소비자인 AI 파트가 camelCase로 확정했다.

### 오류 봉투 — 이 티켓에서 확정 (MR !344 note_2766717 로 회신)

계약 yaml의 `x-contract-status`가 응답·오류 봉투 확정을 이 티켓에 넘겼다. 전용 봉투를 만들지 않고 **프로젝트 전역 봉투**(`docs/08` §1.3 `ApiErrorResponse`)를 쓴다.

- `400` → `VALIDATION_FAILED` · `401` → `UNAUTHORIZED` · `500` → `INTERNAL_ERROR`
- `403`은 이 경로에서 실질적으로 나오지 않는다. `/internal/**` 체인은 토큰이 없거나 틀리면 익명으로 남아 401이 된다
- 3초 타임아웃 초과는 `500` + `INTERNAL_ERROR`. `504`를 쓰지 않는다
- 결과 0건은 `200` + `items: []`. `404`가 아니며, scope 불일치와 문서 비`READY`를 구분해 알려주지 않는다

### 작업 내용

- `POST /internal/ai/chunk-search` 구현 — 신규 파일 3개(컨트롤러·서비스·통합테스트). 기존 코드 수정 없음
- **필터는 클라이언트에서 받지 않는다.** 서버가 `booth_id` + `agent_id` + `searchable = true` + Document `READY`를 강제하고, 그 밖의 조건은 요청으로 넘길 수 없다
- **계약에 없는 필드가 오면 무시하지 않고 **`400` + `VALIDATION_FAILED`로 거부한다 (계약의 `additionalProperties: false`). 문제 필드 이름은 `errors[].field`에 담고 `rule`은 전역 `FIELD_INVALID`를 재사용한다 — 조용히 버리면 보내는 쪽이 필터가 먹었다고 착각한다. 전역 `FAIL_ON_UNKNOWN_PROPERTIES`는 켜지 않는다 (전 endpoint 동작이 바뀐다)
- `originalFilename`은 `ai_document_chunks`에 없다 — `ai_documents`를 조인해서 가져온다. `ai_document_jobs`에도 같은 이름의 컬럼이 있지만 검색 응답은 문서 기준이므로 `ai_documents.original_filename`(VARCHAR(255), V1)이 출처다
- 인증은 S15P21A604-327에서 들어간 `/internal/**` 체인 재사용 — `AiInternalSecurityConfiguration` + `InternalServiceTokenFilter`, 규칙 없는 경로 fail-closed. FastAPI에서 Spring으로 오는 방향이므로 `INTERNAL_AI_TO_SPRING_TOKENS`. **보안 설정 변경 0줄** — `/internal/ai/**` 규칙이 새 경로를 이미 덮는다
- 조회는 `NamedParameterJdbcTemplate` + 네이티브 SQL 한 방. JPA 엔티티를 만들지 않고 pgvector 자바 의존성도 추가하지 않는다 — 질의 임베딩은 문자열로 바인딩해 `CAST(:queryEmbedding AS vector)`로 넘긴다
- **벡터 인덱스에 기대지 않는다.** `WHERE` 4개 + `JOIN`이 붙으면 HNSW는 후필터라 `topK`보다 적게 돌려줄 수 있다(over-filtering). 조용히 결과가 줄어드는 것보다 순차 스캔의 정확성을 택한다. 규모가 커지면 `hnsw.iterative_scan` 또는 partial index로 올린다
- **OpenAPI 계약을 신설하지 않는다** — MR !344가 소유한다. 어긋난 것이 보이면 그 MR에 리뷰로 요청한다
- `docs/08_Backend_API_명세서.md` §20 내부 API 절에 추가

### 확정되지 않은 것

- 벡터 인덱스 연산자가 코사인 잠정이다. S15P21A604-373에서 거리 기준이 바뀌면 이 API의 정렬 연산자도 함께 바뀐다
- MR !344가 develop 미머지 상태다. 머지 전에 계약이 바뀌면 구현도 따라 바뀐다 (해당 스레드로 통보 요청함)

### 완료 조건

- [ ] 다른 booth·agent의 chunk가 응답에 섞이지 않는다 — 교차 접근 테스트 전부 차단
- [ ] 요청으로 필터를 추가하거나 우회할 수 없다
- [ ] 계약에 없는 필드를 보내면 400 + `errors[].field`로 거부된다
- [ ] `searchable = false` chunk와 `READY`가 아닌 문서의 chunk가 제외된다
- [ ] 응답 7개 필드가 전부 채워지고 `distance` 오름차순이다
- [ ] 조건에 맞는 chunk가 있으면 `topK` 개수를 채워서 돌려준다 (인덱스 후필터로 줄어들지 않는다)
- [ ] 결과 0건이 `200` + 빈 배열이다

### 테스트 방법

1. booth A/B × agent 소속/타부스 교차 매트릭스로 scope 혼입 0건 확인
2. `searchable = false`, 문서가 `READY` 아님 각각 제외 확인
3. 서비스 토큰 3종 — 정상 200 / 헤더 누락 401 / 틀린 값 401. **반대 방향 토큰(**`INTERNAL_SPRING_TO_AI_TOKENS`)은 아직 설정 키가 없어 검증 대상이 아니다 — S15P21A604-175 몫이다
4. 사용자 Access Token으로 호출 시 401
5. `topK` 0 / 20 / 21 경계, `queryEmbedding` 1535 / 1536 / 1537 차원
6. 계약에 없는 필드(예: `minScore`)를 넣어 400 + `errors[0].field` 확인
7. 결과 0건 요청이 200 + `items: []`
8. 1만 chunk 규모에서 P95 측정 (로컬)
