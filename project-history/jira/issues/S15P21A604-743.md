## 설명

상위 추적 이슈 S15P21A604-742 의 블록 1. 나머지 블록 전부가 이 이슈에 의존한다.

## 범위

- `users.is_master` 컬럼과 "마스터는 최대 1명" 부분 유니크 인덱스
- `admin_actions` 통합 감사 테이블 (대상·행위자는 FK 없이 id 만 — 탈퇴를 막지 않기 위해)
- 초기 마스터 시드: 닉네임 `구글 황덕` + provider `GOOGLE`
- `AdminGuard` — `requireAdmin(Jwt)` / `requireAdmin(Long)` / `requireTargetNotMaster` / `requireOwnerNotMaster`
- `AdminActionRecorder` — 관리자 행위 기록. 트랜잭션 `beforeCommit` 예약 방식 포함
- `GET/POST/DELETE /api/v1/admin/admins[/{userId}]` — 관리자 목록·승격·강등
- `ErrorCode` 추가: `MASTER_PROTECTED(403)`, `ADMIN_LAST_ONE(409)`, `ADMIN_ALREADY(409)`

## 설계 결정

JWT `role` 은 `MEMBER` 로 유지하고 관리자 판정은 매 요청 DB 조회로 한다. `MemberPrincipal` 이 `"MEMBER".equals(role)` 로 판정하고 컨트롤러 20여 곳이 이를 경유하므로, `role` 을 `ADMIN` 으로 발급하면 관리자 토큰이 게스트로 읽혀 본인 지갑·부스까지 `403 MEMBER_ONLY` 가 된다. DB 조회는 강등이 즉시 반영되는 이점도 있다.

마스터 표시는 `account_type` 이 아니라 별도 boolean 이다. 승격·강등이 `account_type` 을 덮어쓰기 때문에 한 칸에 두 개념을 섞으면 강등 한 번에 마스터가 사라진다.

## 불변식

1. 마지막 관리자는 강등·정지·탈퇴할 수 없다
2. 마스터는 직접·간접(소유 자원 경유) 모두 관리자 동작의 대상이 될 수 없다. 조회는 허용
3. `is_master` 를 세우는 API 는 만들지 않는다 — 마이그레이션이 유일한 경로다
4. 정지 계정은 승격할 수 없다

## 배포 순서

배포된 서비스에 구글 계정으로 먼저 가입해 닉네임을 `구글 황덕` 으로 잡은 **뒤에** 마이그레이션을 올린다. 먼저 올리면 0행 no-op 으로 소진되고 Flyway 가 적용됨으로 기록해 다시 돌지 않는다. 그 경우 같은 조건의 UPDATE 를 다음 가용 버전으로 다시 올린다(provider 조건은 빼지 않는다).

## 완료 조건

- 일반 회원이 관리자 API 를 호출하면 403, 마스터는 200
- 마스터 강등 시도 403 `MASTER_PROTECTED`
- 관리자가 1명일 때 그 관리자 강등 시도 409 `ADMIN_LAST_ONE`
- 승격 1회에 `admin_actions` 1행
- 승격 → 강등 → 탈퇴 통합 테스트 통과 (감사에 FK 가 없어야 통과한다)
- 강등된 계정이 다음 요청부터 즉시 거부된다
