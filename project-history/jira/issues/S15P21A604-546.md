## 설명

GitLab #133 에서 FE 가 요청한 3건 중 실제 서버 변경이 필요한 1건.

## 문제

GET /api/v1/surveys/{surveyId}/results 의 perQuestion 항목이 questionId 만 싣고 문항 문구를 싣지 않는다. 그래서 결과 화면의 주관식 답변 묶음에 "문항 101" 처럼 번호만 표시된다.

FE 는 GET /booths/{boothId}/survey 를 한 번 더 불러 조인할 수 있었지만, 계약이 확정되지 않은 상태에서 곧 죽을 코드를 만들지 않는 쪽을 택하고 대기 중이다.

## 변경

SurveyResultService.QuestionAggregateView 에 prompt 필드를 추가하고 집계 시점에 채운다. 집계 루프가 이미 SurveyQuestion 엔티티를 손에 들고 있으므로 추가 조회가 없다.

필드명은 prompt 로 한다. 도메인 컬럼은 question_text 지만 GET /booths/{boothId}/survey (편집자 조회) 와 GET /booths/{boothId}/survey/run (방문자 조회) 이 이미 prompt 로 내보낸다. 같은 값이 경로마다 다른 이름으로 나가면 FE 어댑터가 갈린다.

응답에 필드를 더하는 것이므로 후방 호환이다. 기존 FE 가 읽지 않아도 깨지지 않는다.

## 함께 처리하는 문서 수정

specs/010-survey/contracts/survey-api.md 4절 (PUT upsert) 에 200 응답 본문 절이 없다. 서버는 이미 surveyId 를 포함한 SurveyView 를 돌려주고 있으나 계약 문서에 적혀 있지 않아, FE 가 첫 저장 직후 surveyId 를 알 방법이 없다고 판단했다. 코드 변경 없이 문서만 보강한다.

7절 예시 JSON 에 prompt 를 추가한다.

## 하지 않는 것

GET /booths/{boothId}/survey/results 별칭은 만들지 않는다. 4절 응답이 문서화되면 FE 는 PUT 응답과 3절 편집자 조회 양쪽에서 surveyId 를 받으므로, 같은 데이터에 경로를 하나 더 두는 것이 된다. GitLab #133 에 이 판단을 적어 회신한다.

## 완료 조건

- results 응답의 각 perQuestion 항목에 prompt 가 실린다
- 문항 유형과 무관하게 (선택형·평점·주관식) 모두 실린다
- 계약 문서 4절에 200 응답 본문, 7절 예시에 prompt 가 반영된다
- backend 통합 테스트가 prompt 값을 단정한다 (필드를 지우면 실패한다)
