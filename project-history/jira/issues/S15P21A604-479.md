## 설명

코드는 -470 -> -473 -> -476 으로 R3F / Unity FBX->GLB / Nested Prefab Assembly 까지 실제 Spike 가 진행됐는데, docs/LJH/ui-design 은 여전히 DEFERRED / 미착수 를 정본처럼 서술하고 있다. 더구나 D-05 가 요구한 기존 15개 Spike Gate 와 실제 검증 결과가 한 번도 대조된 적이 없다.

이번은 문서 보충이 아니라 구조 정상화다. 다음이 한 방향으로 읽히게 만든다.

현재 결정 -> 실제 Spike Evidence -> D-05 Gate -> 신규 Runtime Asset Compiler 설계 -> Tooling -> Visual Review -> 다음 구현계획

[수정]

[D-05 canonical 15 Gate]
새 Gate 를 만들지 않는다. 기존 문서 원문에서 추출한다 — booth-studio-r3f-asset-pipeline-plan.md 47절의 Spike PASS 6항 + MVP PASS 9항 = 15항 이 D-05 가 말하는 그 15항 이다. 자동화 PASS 7항 은 별도 계층이다.

-470 에서 쓴 8개 Gate 는 사용자 지시에서 온 것이므로 canonical 15 와 혼동하지 않는다. evidence 로만 쓴다.

상태는 PASS / PARTIAL / NOT_TESTED / BLOCKED / OBSOLETE 만 쓴다. 근거 없는 PASS 금지. Unity + R3F 동시 상주 같은 항목은 PASS 가 아니라 PARTIAL 이다 — 전환 중 충돌/누수만 확인했고 Persistent GameShell 이 없어 동시 상주 실측은 못 했다.

[불변]
D-04 = ADOPTED 유지. D-05 = PASS_CANDIDATE 이지 ADOPTED 가 아니다. Runtime Asset Compiler 는 PROPOSAL 이지 DECISION 이 아니다. OBJECT_LOCAL_BOUNDS 가 Domain Truth 이고 Runtime Asset 은 Visual Representation 이다 — 모델 치수를 근거로 저장·이동·bounds 규칙을 바꾸지 않는다.
