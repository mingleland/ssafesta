## 설명

## 배경

GitLab #210 — 정상 사용 중에 React realtime `/ws` 소켓이 `code=1006 reason="" clean=false` 로 반복해서 끊긴다는 보고. 조사 결과 원인이 확정됐다.

`1006` 은 서버가 보낸 Close 코드가 아니라, 정상 close handshake 없이 transport 가 사라진 것을 브라우저가 관측했을 때 스스로 붙이는 값이다. 즉 중간 계층이 유휴 소켓을 조용히 정리하고 있었다.

## 확정된 원인

STOMP heartbeat 가 양쪽 모두 꺼져 있어 소켓 위에 오가는 바이트가 0 이었다.

- FE — `realtimeClient.ts` 의 CONNECT 헤더가 `heart-beat: '0,0'` (보내지도 받지도 않겠다)
- BE — `WebSocketConfig.configureMessageBroker` 가 `enableSimpleBroker("/topic", "/queue")` 만 호출한다. `setTaskScheduler` 도 `setHeartbeatValue` 도 없고, 저장소 전체에 STOMP heartbeat 설정이 한 줄도 없다

이 소켓에 실제로 흐르는 트래픽은 구독 둘(`/topic/world/chat`, `/user/queue/world/chat/errors`)뿐이라, 아무도 채팅을 치지 않으면 완전히 유휴 상태가 된다.

실측으로 확인된 값이다.

| 출처 | 값 |
|---|---|
| FE 클라이언트 유휴 구간 측정 (2구간 재현) | 약 127초 (편차 0.15초) |
| Infra Nginx `/ws` 101 핸드셰이크 간격 | 128.3초 · 128.5초 |
| 배포본 Nginx `proxy_read_timeout` | 180초 (불일치) |
| Cloudflare 와 EC2 Nginx 사이 중간 계층 | ALB · NLB · 터널 없음 |

클라이언트 측정과 서버 액세스 로그가 초 단위까지 일치한다. 끊는 주체는 Cloudflare 엣지 프록시의 WebSocket idle connection 절단으로 보는 것이 Infra 판단이다.

## 할 일

`WebSocketConfig.configureMessageBroker` 에서 simple broker 에 송신 heartbeat 를 붙인다.

```
registry.enableSimpleBroker("/topic", "/queue")
        .setTaskScheduler(taskScheduler)
        .setHeartbeatValue(new long[] {25_000, 0});
```

25초는 128초 창의 약 1/5 이라 여유가 충분하다. 실제 끊는 값이 25초보다 짧은 계층에 있다면 그때 다시 조정한다.

구현 시 확인이 필요한 것이 하나 있다. `setTaskScheduler` 에 넘길 `TaskScheduler` 를 어디서 얻을지다. Spring 이 `messageBrokerTaskScheduler` 빈을 이미 제공하지만, 그것을 이 설정 클래스 자신에 생성자로 주입하면 순환 참조가 날 수 있다. 주입 방식은 구현할 때 실제로 기동시켜 확인한다.

## 짝이 되는 변경 — 이미 반영됨

FE 쪽 한 줄이 반드시 함께 가야 한다. STOMP 협상에서 서버가 보내는 heartbeat 주기는 `max(서버 송신값, 클라이언트 수신 희망값)` 인데, 클라이언트가 `0` 이면 "받지 않겠다" 라서 BE 만 고치면 서버가 아무것도 보내지 않는다.

FE 는 `S15P21A604-819` / MR !1017 로 `heart-beat: '0,20000'` 을 이미 `front` 에 반영했다. 그래서 지금 BE 가 유일한 병목이다.

반대로 이 변경만 먼저 들어가도 FE 동작은 종전과 같다 — 클라이언트가 수신을 희망하지 않으면 서버가 보내지 않으므로 무해하다.

## 범위 밖

- 재시도 횟수를 줄이거나 재접속을 끄거나 disconnect 를 화면에서 숨기는 방향은 하지 않는다. 증상만 감추면 사용자는 같은 순간에 조용히 끊긴 채로 남는다.
- Unity World 단절은 별건이다. UTP 가 heartbeat 500ms · disconnect timeout 30000ms 로 돌아 유휴 상태가 생기지 않으므로 같은 원인으로 묶지 않는다. 계측은 `S15P21A604-210` / MR !1007 에서 Game 파트가 이미 넣었다.
- 재접속 이후의 위치 · 회전 복원은 GitLab #200 의 주제이며 게임 파트 소관이다.
- Nginx `proxy_read_timeout` 이나 Cloudflare 설정 변경은 Infra 소관이고, heartbeat 가 세 값(100 · 128 · 180초) 어느 쪽이든 덮으므로 이 티켓에서는 건드리지 않는다.

## 미해결로 남기는 것

128초의 주체가 실제로 무엇인지는 아직 확정되지 않았다. Infra 는 같은 스레드에서 앞서 101초 · 102초 구간을 Cloudflare 로, 183초 구간을 Nginx 로 보고했는데, Cloudflare 의 유휴 타임아웃이 100초이면서 동시에 128초일 수는 없다. 조치에는 영향이 없지만 원인을 "확정" 으로 기록하지 않는다.

## 완료 조건

- BE 가 25초마다 heartbeat 를 송신한다 (FE 수신 희망값 20초와 협상된 결과).
- 채팅 트래픽이 없는 상태로 5분 이상 유지해도 `1006` 이 발생하지 않는다.
- 기존 상담 알림 · 월드 채팅 destination 동작과 `StompAuthChannelInterceptor` 의 allowlist 판정은 변하지 않는다.
- in-memory simple broker 의 단일 인스턴스 전제는 그대로 유지한다.
