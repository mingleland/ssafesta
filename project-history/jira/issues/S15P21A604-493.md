## 설명

"걸으면 느려졌다 빨라졌다" 의 남은 원인을 측정으로 확정했다. 상시 부하가 아니라 처음 보는 것을 준비하는 비용이다.

측정 (FE 임베드 게스트 접속, DPR 상한 d5c8cba6 + 조명 PerVertex a351b5ff 적용, PerfHud 개편본 c9ef7d59, 보이는 탭)

같은 경로를 두 번 돌았다. 1차는 첫 방문, 2차는 같은 지점 재방문이다.

|  | 1차 (첫 방문) | 2차 (재방문) |
|---|---|---|
| 100 ms 초과 | 5회 | 0회 |
| 50 ms 초과 | 9회 | 0회 |
| max | 2,700 ms | 41.1 ms |
| p50 | 16.5 ms | 16.7 ms |
| p95 | 25.0 ms | 24.9 ms |
| 샘플 | 5,249 (72.9초) | 1,656 (28초) |

정상 프레임(p50·p95)은 1차와 2차가 사실상 같은데 스파이크만 사라졌다. 렌더 작업량이 무거워서가 아니라, 처음 만나는 셰이더 변형을 컴파일하고 텍스처를 GPU 에 올리고 에셋을 처음 읽는 비용이다. 한 번 겪으면 캐시돼 두 번째에는 없다.

1차 스파이크 위치: 1.2s(200ms) 12.3s(117) 21.0s(133) 31.3s(58) 31.4s(75) 37.3s(125) 66.1s(2700) 66.6s(67)

왜 지금 중요한가

09-08 사용자 테스트 참가자는 전원 첫 방문자다. 지금 상태로는 모두가 1차 순회의 hitch 를 그대로 겪는다. 걸어다니며 새 부스·새 이펙트가 시야에 들어올 때마다 멈췄다가 되돌아오면 멀쩡하니, 정확히 "느려졌다 빨라졌다" 로 느껴진다.

조치

ShaderVariantCollection 으로 실제 쓰이는 셰이더 변형을 모아 로딩 화면에서 미리 컴파일한다. 비용을 없애는 것이 아니라 월드 진입 후에서 진입 전으로 옮기는 것이다. 로딩이 조금 길어지는 대신 걸을 때 멈추지 않는다.

1. 에디터에서 변형 수집 — Graphics Settings 의 Shader Preloading, 또는 플레이 중 기록해 .shadervariants 로 저장한다.
2. 로딩 시점에 WarmUp 을 호출한다. 진입 게이트가 이미 있으므로(WorldEntryGate) 그 앞에 붙인다.
3. 진행률 표시와 겹치지 않게 한다 — 프리워밍 중 화면이 멈춘 것처럼 보이면 안 된다.

검증

같은 경로 1차 순회를 다시 잰다. 프리워밍 전 1차와 비교해 100 ms 초과 5회가 줄어야 하고, 2차 수준(0회)에 가까울수록 좋다. 로딩 시간 증가분도 함께 기록한다 — 진입이 과도하게 길어지면 득실을 다시 따진다.

주의: 텍스처 GPU 업로드와 에셋 첫 로드는 셰이더 프리워밍으로 해결되지 않는다. 셰이더만으로 부족하면 남은 스파이크의 성격을 다시 분리해야 한다.

### 강형순 · 2026-09-07 15:21 KST

셰이더 프리워밍은 접는다. 근거가 안 나왔다.

에디터에서 변형을 수집해 보니 22 셰이더 / 54 변형뿐이다. 이 양으로는 2.7초 정지를 만들 수 없다. 게다가 에디터는 PC_RPAsset(PerPixel), WebGL 은 Mobile_RPAsset(PerVertex) 이라 여기서 모은 변형이 빌드와 맞지도 않는다. "원인 1순위는 셰이더 컴파일" 은 내 추정이었고 근거가 약했다. 코드는 아무것도 바꾸지 않았다.

대신 측정을 다시 해서 문제를 둘로 갈랐다.

1. 이동 중 hitch — 이게 "걸으면 느려졌다 빨라졌다" 다

정지 20초 vs 이동·회전 23.8초 (같은 빌드, 같은 접속, 계측 후킹 없이)

|  | 정지 | 이동·회전 |
|---|---|---|
| p50 | 16.6 ms | 16.7 ms |
| p95 | 24.9 ms | 25.1 ms |
| p99 | 25.1 ms | 33.4 ms |
| max | 25.2 ms | 158 ms |
| 33 ms 초과 | 0회 | 27회 |
| 100 ms 초과 | 0회 | 3회 |

정지하면 완벽하고 움직이면 끊긴다. 앞서 "이동 중 스파이크 0회" 라고 적은 것은 틀렸다 — 그때는 텔레포트로 순간이동만 했지 걷거나 시야를 돌리지 않았다. 사용자가 실제로 하는 조작을 재현하지 않은 측정이었다.

1. 진입 지연 — 별개 문제

로딩 구간에 씬 로드 16.9초, 부스 게시본 12슬롯 병렬 조회 + BoothRuntime 조립 3.8초가 있다. 26.5초 지점 스파이크가 HttpBoothApiClient 로그와 정확히 겹쳤다. #129 와 같은 뿌리다.

다음 조치

브라우저 rAF 로는 "언제" 만 알고 "무엇 때문" 인지 모른다. PerfHud 에 hitch 로거를 넣어 프레임이 임계값을 넘는 순간 유니티가 직접 컨텍스트를 찍게 한다 — 플레이어 위치, 드로우콜·삼각형의 직전 프레임 대비 증분, GC 발생 여부, 힙 변화. 그 로그를 모아 원인을 가른다.

주의: 브라우저에서 console 후킹·fetch 후킹으로 계측하면 그 자체가 부하가 된다. 실제로 후킹을 켠 채 잰 값과 끈 값이 달랐다. 계측은 유니티 안에서 하고 브라우저는 로그만 받는다.
