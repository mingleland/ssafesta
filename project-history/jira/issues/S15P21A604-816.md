## 설명

## 배경

GitLab #211 — 단일 탭 정상 세션에서 POST /api/v1/auth/refresh 가 401 을 내고 강제 로그아웃됐다는 보고. 원인 규명을 위해 origin/develop 코드와 인프라 설정을 조사한 결과, **서버가 어떤 이유로 401 을 냈는지 사후에 읽을 방법이 없다**는 사실이 먼저 드러났다.

조사 결과는 GitLab #211 에 전문을 올렸다. 이 티켓은 그중 BE 가 할 수 있는 부분만 담는다.

## 문제

401 을 내는 ApiException 은 전부 GlobalExceptionHandler 의 한 줄을 지나간다.

```
log.debug("거부 — code={} message={}", code, exception.getMessage());
```

그런데 backend/src/main/resources 의 어느 파일에도 logging 설정 블록이 없다. 루트 레벨이 Spring 기본값 INFO 이므로 이 줄은 배포 환경에서 찍히지 않는다.

그 결과 아래 셋을 구분할 수 없다.

| 실제로 일어난 일 | 지금 남는 것 |
|---|---|
| INVALID_MEMBER_TOKEN (Redis 에 키가 없다) | 없음 |
| REFRESH_TOKEN_ROTATED (회전 직후 재생, 세션은 살아 있다) | 없음 |
| refresh_token 쿠키가 서버에 도달하지 않았다 | 없음 |

SessionRevocationFilter 의 거절도 로그가 없다. 이것은 **세션이 통째로 사라진 사건을 서버 쪽에서 알아차릴 수 있는 유일한 신호**인데 지금은 조용히 401 만 나간다.

## 할 일

1. MemberSessionService.refresh 와 GuestAuthController.refresh 의 401 분기에 WARN 로그를 남긴다. 남길 값은 오류 코드, 쿠키 도달 여부, refresh 키 존재 여부, 재사용 표식의 사유다.
2. SessionRevocationFilter 의 거절에도 WARN 로그를 남긴다. userId 와 sid 불일치인지 세션 키 부재인지를 가른다.
3. 두 로그 모두 Refresh Token 원문과 그 해시를 남기지 않는다 (헌법 13조).

## 범위 밖

- 401 자체를 숨기거나 우회하는 변경은 하지 않는다. 인증 판정 로직은 건드리지 않고 관측만 늘린다.
- REFRESH_TOKEN_ROTATED 재시도는 FE 쪽이며 S15P21A604-812 가 맡고 있다.
- Redis 영속성 설정 (appendonly / save point / maxmemory) 은 Infra 소관이라 이 티켓에 넣지 않았다. GitLab #211 에 확인 요청을 올려 두었다. 조사에서 나온 가장 유력한 원인 후보가 그쪽이다 — 현재 redis.conf 는 appendonly no 이고 save point 가 없어, 컨테이너가 한 번 재시작하면 그 시점 로그인 사용자 전원의 세션이 사라지고 아무 로그도 남지 않는다.

## 완료 조건

- 재현이 다시 일어났을 때 서버 로그만으로 위 표의 세 갈래를 구분할 수 있다.
- 세션이 통째로 사라진 사건이 로그에 드러난다.
- 기존 401 응답 봉투와 상태 코드는 변하지 않는다 (회귀 테스트로 확인).
