## 설명

### 작업 목적

`/topic/world/chat` 으로 나가는 한 줄에 비속어가 실리지 않게 한다. 광장은 접속한 모든 회원에게 동시에 보이는 화면이고, 시연 중 한 줄이 그대로 방송되면 되돌릴 방법이 없다(저장하지 않으므로 삭제 기능도 없다).

### 선행 확인 — 계약 개정이 동반된다

`specs/002-world-session/contracts/world-chat-api.md` 의 "안 하는 것" 표에 `신고·차단·금칙어` 가 박혀 있고, 사유는 "운영 인력을 전제하는 기능이다. 시연 규모에 맞지 않는다" 이다. `docs/16` 310행도 같은 문장이다.

그 사유는 신고·차단에는 맞지만 정적 금칙어 목록에는 맞지 않는다. 목록 대조는 운영 인력도 신고 큐도 필요 없다. 따라서 이 티켓은 구현과 함께 두 문서에서 `금칙어` 를 "안 하는 것" 에서 빼고 계약에 넣는 개정을 포함한다. 신고·차단은 그대로 범위 밖이다.

### 목록을 새로 만들지 않는다

`NicknamePolicy` 가 이미 금칙어 목록과 정규화(NFKC → 소문자 → 공백·기호 제거 → leet 치환)를 들고 있다. 정책 정본은 `specs/001-auth-user/contracts/nickname-policy.md` 다. 채팅용 목록을 따로 두면 두 목록이 갈리고, 어느 쪽이 정본인지 알 수 없게 된다.

`common/ProfanityFilter` 를 신설해 `BLOCKED_TERMS`·`LEET`·`normalize` 를 옮기고, `NicknamePolicy` 는 거기에 위임한다. static 메서드로 둔다 — 상태가 없고, 이렇게 해야 `WorldChatService` 의 생성자와 기존 테스트가 그대로 있다.

`RESERVED_TERMS`(관리자·admin)는 옮기지 않는다. 닉네임 사칭 방지용이라 채팅에 걸면 "관리자님 계신가요" 가 막힌다.

### 게이트 위치

`WorldChatService.normalized()` 안, 길이 검사 뒤. 기존 순서 계약(내용 검증 → 도배 판정 → 신원 확인 → 방송)을 바꾸지 않는다. 내용 검증 단계에서 걸리므로 거절된 줄은 3초 쿨다운을 소비하지 않는다.

검사는 정규화본으로 하고, 방송은 원문(`strip()` 적용본)으로 한다. 마스킹(부분 치환)은 하지 않는다 — 정규화 과정에서 공백과 기호가 지워져 정규화본의 일치 위치를 원문 위치로 되돌릴 수 없다.

### 에러 코드를 신설하지 않는다

`ApiException.fieldInvalid("content", ...)` → `VALIDATION_FAILED`. 프런트엔드가 이미 `CHAT_ERROR_MESSAGE` 에서 `VALIDATION_FAILED` 를 "보낼 수 없는 내용입니다" 로 매핑하고 있어 FE 변경이 0줄이다.

어떤 단어가 걸렸는지 알려주지 않는 것은 닉네임 정책 4항(금칙어 종류나 일치 단어를 사용자에게 노출하지 않는다)과 같은 이유다. 알려주면 우회 표기를 찾는 데 쓰인다.

### 프런트엔드에 같은 검사를 두지 않는다

계약 문서의 원칙 "같은 판정을 두 곳에 두면 둘이 갈린다" 를 따른다. 목록이 서버에만 있어야 브라우저에서 읽어갈 수도 없다. 길이·도배와 달리 왕복 한 번을 아낄 이유도 없다 — 비속어는 정상 사용자가 마주치는 경로가 아니다.

### 완료 조건

- [ ] 금칙어가 든 줄이 `/topic/world/chat` 에 나가지 않는다
- [ ] 우회 표기가 막힌다 — `씨---1---발`, `F_U_C_K` (닉네임과 같은 정규화를 거치므로)
- [ ] 거절 사유가 `/user/queue/world/chat/errors` 로 `VALIDATION_FAILED` 로 간다 (신규 코드 없음)
- [ ] 거절된 줄이 3초 쿨다운을 소비하지 않는다 — 곧바로 정상 메시지를 보낼 수 있다
- [ ] 방송되는 내용은 원문이다 — 검사용 정규화본이 실려 나가지 않는다
- [ ] `관리자` 가 든 채팅은 통과한다 (`RESERVED_TERMS` 는 채팅에 적용되지 않는다)
- [ ] `NicknamePolicyTest`·`RegistrationServiceTest` 가 수정 없이 통과한다 (닉네임 동작 불변)
- [ ] `world-chat-api.md` 와 `docs/16` 에서 `금칙어` 가 "안 하는 것" 에서 빠지고 계약에 들어간다

### 오탐 처리 — (c) 화이트리스트 확정 (2026-09-15)

공백·기호를 지운 뒤 부분 문자열로 검사한다. 닉네임(2~30자)에서는 감수할 만했지만 100자 문장에서는 오탐이 늘어난다: `고추장` 이 `고추` 에, `혼자 지내` 가 `자지` 에, `sussex` 가 `sex` 에, `analysis` 가 `anal` 에 걸린다.

검토한 안은 세 가지였다. (a) 목록을 그대로 쓰고 오탐을 한계로 기록한다. (b) 채팅에서만 오탐 위험 단어를 제외한다. (c) 예외 목록(화이트리스트)을 둔다.

**(c) 로 확정했다.** (b) 는 목록이 둘로 갈린다. (c) 는 업계 표준이고 — 교과서 사례가 영국 지명 `Scunthorpe` 다 — 목록을 하나로 유지한다.

확정된 규칙:

- 판정 순서는 정규화 → 예외 제거 → 금칙어 대조다. 예외를 먼저 지우면 `F_U_C_K` 같은 우회 표기를 예외 목록이 알아보지 못한다
- 예외를 지운 자리에는 공백 하나를 남긴다. 빈 문자열로 지우면 앞뒤가 붙어 없던 금칙어가 생긴다 — `씨class발` 에서 `class` 를 지우면 `씨발` 이 된다
- 긴 것부터 지운다 — `고추장찌개` 가 `고추장` 보다 먼저 걸려야 한다
- 예외 목록은 닉네임에도 함께 적용된다. 닉네임 `고추장` 이 허용되는데, 이는 의도한 변화다
- 목록 원문은 `specs/001-auth-user/contracts/nickname-policy.md` 의 "오탐 예외(화이트리스트)" 절에 둔다

남는 한계:

- `-아/어보지` 는 어미라 예외가 끝없이 만들어진다(`뛰어보지`·`물러보지` …). 대표형만 넣고 오탐이 보고될 때 한 줄씩 늘린다
- 예외 단어를 욕 사이에 끼우는 우회는 통과한다 — `씨class발`. 공백을 남기는 대가이며, 멀쩡한 문장을 우연히 막는 쪽보다 낫다고 판단했다
- `혼자 지내` 는 여전히 막힌다. 예외 목록에 `혼자`·`과자` 를 넣으면 풀리지만 지금은 넣지 않았다
