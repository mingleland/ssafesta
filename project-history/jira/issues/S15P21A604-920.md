## 설명

## 배경

코인이 지급되어도 클라이언트는 다음 REST 조회 전까지 모른다. 슬롯머신 보상, 타이머스톱 보상, 데일리 미션, 설문 보상, 일일 접속 지급 — 다섯 경로 모두 지급 직후 사용자에게 알려줄 수단이 없다.

SSE 신설도 검토했으나 기존 STOMP over WebSocket 인프라(`/ws`, `POST /api/v1/realtime/ws-token`, 25초 heartbeat, `/user/queue` 개인 대상 발행)가 이미 인증·연결 유지·FE 클라이언트까지 갖추고 있어 재사용하기로 했다(2026-09-18 결정). SSE로 가면 SseEmitter 레지스트리, EventSource의 헤더 부재로 인한 토큰 전달 방식 재설계, keepalive 핑, FE 신규 클라이언트를 모두 새로 만들어야 한다.

## 변경 사항

- `wallet/CoinEventPublisher` 신설. `ConsultationEventPublisher`·`EventShopEventPublisher`와 같은 형태 — 트랜잭션 커밋 후 발행, 발행 실패는 WARN 로그만 남기고 예외를 던지지 않는다(알림 유실이 이미 확정된 지급을 되돌리면 안 된다).
- `WalletService.applyEntry`에서 증액(양수 금액) 항목이 새로 기록된 경우에만 발행. 멱등키로 걸러진 재요청(`alreadyApplied`)은 발행하지 않는다 — 같은 지급이 두 번 알림으로 뜨면 안 된다.
- 목적지: `convertAndSendToUser(String.valueOf(userId), "/queue/coin", event)`. STOMP Principal 이름이 회원 id 문자열이라 그대로 쓴다.
- 페이로드: `{ type: "granted", amount, balanceAfter, reasonType, entryId, occurredAt }`.

## 테스트 방법

- 단위 테스트: 증액 시 커밋 후 1회 발행, 차감 시 미발행, 멱등 재요청 시 미발행, 발행 실패가 지급 트랜잭션을 롤백하지 않음.
- 통합 확인: 일일 접속 지급 경로에서 `/user/queue/coin` 수신.

## 영향 범위

- 백엔드 wallet 패키지, 기존 WebSocket 설정 변경 없음(destination 추가만).
- FE는 기존 realtimeClient에 구독 하나 추가하면 된다 — 별도 티켓으로 통보 필요.
- 잔액의 정본은 여전히 REST다. 이 채널은 알림이며 유실을 허용한다(단일 인스턴스 in-memory broker 전제, 기존 채널과 동일).
