## 설명

### 작업 목적

FastAPI가 Conversation을 만들기 전에 Spring에 물어야 하는 검증 경로를 연다. spec 008 FR-024가 "Spring이 Lease 유효성, agentId의 boothId 소속 여부, Agent의 ACTIVE 상태를 검증한다"로 확정(C-08, GitLab 이슈 #14)했지만 Spring 쪽 구현·태스크·이슈가 모두 없다.

Unity는 2026-08-30 AI_AGENT_INTERACT 송신부를 완료해 Mock AI 호출을 걷어냈다. FE(S15P21A604-118) → FastAPI(S15P21A604-126)로 이어지는 경로의 끝이 Spring에서 끊긴다.

### 작업 내용

- GET /internal/ai/booth-access?boothId=&agentId= 구현 (정본: specs/008-ai-conversation-rag/contracts/spring-booth-access-api.yaml)
- 응답 필드: allowed, boothId, agentId, agentStatus, leaseEndsAt, remainingSeconds, serverTime, denialCode
- denialCode 값: BOOTH_LEASE_EXPIRED / AGENT_NOT_IN_BOOTH / AGENT_INACTIVE / null
- 서비스 토큰 인증 — INTERNAL_AI_TO_SPRING_TOKENS 목록 전체를 MessageDigest.isEqual로 상수 시간 비교, 누락·오류·반대 방향 토큰은 401, /internal/* 공개 경로 차단

### 인증 방식은 확정돼 있다 (GitLab 이슈 #102, 2026-08-25)

#102는 내부 호출 3종을 열거하며 그 중 하나로 "FastAPI → Spring: 부스 접근·임대 상태 검증"을 명시했고, 방향별 2토큰으로 확정했다(BE·AI·Infra 3파트 동의).

따라서 booth-access는 FastAPI → Spring 방향이므로 INTERNAL_AI_TO_SPRING_TOKENS를 사용한다. 새로 정할 것이 없다. spec 008의 contracts/spring-booth-access-api.yaml이 serviceToken을 bearer opaque로만 적어 두어 이름이 드러나지 않으므로, 구현과 함께 그 description에 방향과 변수명을 적는다.

#102에서 함께 확정된 것:

- 콤마 구분 리스트 1변수. 송신은 첫 값, 검증은 목록 전체
- 회전 순서 [old] → [old,new] → [new,old] → [new]
- 토큰 검증은 네트워크(SG) 설정과 독립적으로 항상 수행
- 상수 시간 비교 (MessageDigest.isEqual)

이 토큰 검증 부품은 spec 007 T020과 동일하며 S15P21A604-175도 같은 것을 쓴다. AI 쪽 대응 구현(T019)은 S15P21A604-121로 완료됐고, AI는 SPRING_INTERNAL_BASE_URL과 INTERNAL_AI_TO_SPRING_TOKENS 설정을 이미 갖고 있다.

### 완료 조건

- [ ] 유효 임대 + 소속 + ACTIVE 이면 allowed=true 이고 leaseEndsAt·remainingSeconds 가 정확하다
- [ ] 세 조건 각각의 실패가 서로 다른 denialCode 로 구분된다
- [ ] 토큰 누락·오류·반대 방향(INTERNAL_SPRING_TO_AI_TOKENS) 전부 401
- [ ] /internal/* 가 사용자 Access Token 으로는 접근 불가
- [ ] docs/08_Backend_API_명세서.md 에 내부 API 절 신설
- [ ] spec 008 계약 yaml의 serviceToken description에 방향·변수명 명시

### 테스트 방법

1. 유효/만료 임대 x 소속/타부스 Agent x ACTIVE/INACTIVE 매트릭스
2. 토큰 4종(정상·누락·오류·반대 방향)
3. 사용자 Access Token 으로 /internal/ai/booth-access 호출 시 401
