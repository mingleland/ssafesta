## 설명

### 배경

140 작업 중 회귀 테스트에서 `test_document_processing_api.py` 실패를 발견해 파보면서 단순 operationId 네이밍 차이가 아니라 계약 자체가 큰 폭으로 어긍난 것을 확인함 (S15P21A604-449 문서 개정 이후 코드 미반영).

### 작업 내용

- `specs/007-ai-agent-document/contracts/document-processing-api.yaml`: operationId `startDocumentProcessing`, `ProcessDocumentRequest`에 `jobId`+`attemptNo` 필수(Spring이 Job을 먼저 만들고 push), 202 응답 body 없음
- 실제 `festa-ai/app/api/v1/documents.py`/`app/api/schemas/documents.py`: operationId `enqueueDocumentProcessing`, `ProcessDocumentRequest`에 `jobId`/`attemptNo` 필드 없음, FastAPI가 자체 AI DB에 Job을 생성하고 `job_id`/`status`/`existing`을 202 응답으로 돌려줌 (구조가 새 아키텍처와 반대 방향)
- `ApiModel`이 `extra="forbid"`라 Spring이 새 계약대로 `jobId`+`attemptNo`를 보내면 FastAPI가 422로 거부함 — 실제 연동 시점에 즉시 깨지는 계약 불일치

### 현재 영향

Spring 쪽(`backend/`)에 이 endpoint를 호출하는 코드가 아직 없어(grep 확인) 실서비스 영향 0건 — 단, 124/125/398 등이 이 endpoint를 실제로 연결하는 순간 바로 터지는 문제임.

### 완료 조건

- [ ] `documents.py`가 `jobId`+`attemptNo`를 받아 fencing하고, FastAPI 자체 Job 생성을 제거한다 (Spring이 유일생성자)
- [ ] 202 응답이 계약대로 body 없이 나간다 (또는 계약을 실제 필요에 맞게 재확정)
- [ ] `test_document_processing_api.py` 계약 비교 테스트 GREEN
- [ ] AI DB 직접 Job 생성 코드 제거 (124/125의 AI DB 이탈 작업과 함께 정리 가능)
