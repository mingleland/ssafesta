## 설명

Contract Gap G-3. 구현 티켓이 아니라 **제품·계약 결정 티켓**이다.

## 핵심 질문

새 상담을 시작할 때 target boothId 는 어느 World / Product Context 에서 결정되는가?

## 배경

상담은 요청→대기→수락→진행→만료→종료 의 **시간 지속성**을 갖는 유일한 방문자 기능이라, 오버레이를 닫고 World 로 돌아간 뒤에도 상태에 닿을 경로가 필요하다. 그래서 World HUD 우상단 Quick Access 가 hud-decisions 의 예외로 허용됐고(허용 4번), 구현돼 develop 에 반입됐다(S15P21A604-413, !240).

그러나 HUD 는 **전역** 진입점이다. 진행 중인 상담으로 돌아가는 것은 기존 boothId 로 되지만, **새 상담을 시작할 때 어느 부스가 대상인지**를 FE 가 알 방법이 없다.

## 현재 동작 (2026-09-04 실측)

- ConsultationQuickAccess 는 진행 중인 상담이 있을 때만 활성이고, idle 상태에서는 비활성 + "상담은 부스의 상담 데스크에서 시작합니다" 안내만 한다.
- 이것은 계약이 없다는 사실을 정직하게 드러낸 상태이지 최종 UX 가 아니다.

## 금지 (이미 합의된 제약)

- 임의 Booth Picker 발명 금지
- Booth Directory 발명 금지
- FE 가 현재 부스를 추측하는 것 금지

## 검토할 후보 (이 티켓에서 결정)

- (a) 부스 상담 데스크 Unity F 상호작용으로만 시작 — 그 경우 CONSULTATION 이벤트 계약이 필요하며 G-2 와 같은 성격의 작업이 된다
- (b) Unity 가 현재 플레이어 위치의 booth context 를 지속적으로 FE 에 알려주는 경로 신설
- (c) 다른 방식

## 완료조건

- target context source 확정
- boothId 전달 경계 확정 (Unity -> FE, 또는 BE 응답)
- Unity / FE / BE 공통 계약 정리
- G-7(상담 transport, -137) payload 에 사용할 기준 확정
- 확정 후 HUD idle 상태 동작 재설계

## 의존

- G-7 상담 transport(-137, BE) — destination·payload 에 boothId 가 들어가므로 이 결정이 선행하거나 함께 정해야 한다
- spec 011 은 STOMP 정책(FR-012·FR-019·FR-020, C-05·C-13)까지만 확정돼 있고 destination·payload schema 는 없다

### 이정헌 · 2026-09-04 18:52 KST

상담 신규 요청의 대상 부스를 어떻게 정하느냐는 제품 결정으로 넘길 사안이 아니라 이미 spec 에 답이 있었습니다. spec 011 FR-005 가 "AI 상담 중 사람 상담 요청" 을 MVP 경로로 명시하고 있어 그대로 확정하고 구현했습니다.

MR: !250 (feat/S15P21A604-415-world-interaction-events -> develop)

확정
- MVP 진입점은 AI 대화 에스컬레이션 하나다. 대상 부스는 그 대화가 시작된 AI_AGENT_INTERACT 의 boothId 다.
- 이 경로는 Unity 변경이 0 이다. AI_AGENT_INTERACT 는 이미 오고 있고 요청은 그 대화 안에서 일어난다. 별도의 Booth Picker UI 를 만들지 않았다.
- 부스 상담 데스크(CONSULTATION_DESK) 는 MVP 에서 활성화하지 않는다. BoothObjectFactory 에도 일부러 붙이지 않았고 그 이유를 주석으로 남겼다.

구현 경계
기존에는 ConsultationOverlay 가 열리자마자 스스로 requestConsultation 을 불렀습니다. 그래서 어느 부스에 왜 요청했는지가 어디에도 남지 않았습니다. 이번에 ConsultationStartContext { boothId, source, handoffSummary? } 를 두고 진입점이 이것을 만들어 상태 기계에 넘기도록 바꿨습니다.

source 는 AI_HANDOFF | CONSULTATION_DESK 이고, handoffSummary 는 optional 입니다. 데스크 진입에는 선행 대화가 없어 그 값이 존재할 수 없기 때문입니다. 나중에 데스크를 붙일 때는 source 를 바꿔 같은 requestConsultation 을 부르면 되고 상태 기계는 그대로입니다.

BE 확인 부탁드릴 것
- 대기열 API(G-6)와 실시간 전송(G-7)은 이번 범위가 아닙니다. 다만 요청 생성 payload 에 handoffSummary(AI 대화 요약)가 필요합니다 — 직원 대기열 카드에 그대로 노출되는 값입니다. 계약 확정 시점에 이 필드를 반영해 주세요.

검증
AI 대화 -> 사람 상담 요청 -> 상담 대기 중 -> 오버레이 닫기 -> HUD 에 상태 유지 -> 재진입 시 카운트다운 이어짐 -> 명시적 취소 후에야 HUD 비활성. 닫기와 취소가 다르다는 기존 동작은 유지됩니다.
