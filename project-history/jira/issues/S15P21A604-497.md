## 설명

사용자 지적: "로딩 구간을 사용자한테 때우게 하면 안 된다. 그만큼 엘리베이터 로딩 씬을 늘려서 안 불편하게 해라."

측정 (HitchLogger, FE 임베드 게스트 접속, 개발 빌드)

진입 직후 큰 정지가 넷 났고 전부 게이트가 열린 뒤였다.

[Hitch#2] 2797ms draws 1101(+1101) tris 897608(+897608) gc 1 heap +3.7MB pos(-92,18,0)
  [Hitch#3]  172ms draws 593(-18)    tris 896410(-218)     gc 0                pos(-92,18,0)
  [Hitch#5]  323ms draws 870(+277)   tris 672514(-223896)  gc 1 heap -5.9MB    pos(-25,0,-248)
  [Hitch#6]  160ms draws 1088(+218)  tris 1457216(+784702) gc 0                pos(-25,0,-248)

#2 는 처음 화면을 그리는 순간이다 — 드로우콜이 0 에서 1101 로, 삼각형이 0 에서 89.8만으로 뛴다. #5 는 GC(힙 5.9MB 해제), #6 은 시야 전환으로 78.5만 삼각형 추가다.

원인

WorldEntryGate 의 IsPlayerReady() 는 씬 로드·접속 승인·오너 스폰 셋만 본다. 그런데 스폰됐다고 그릴 준비가 된 것은 아니다. 스폰 직후 첫 프레임이 2.8초 걸리는데 게이트는 그 전에 도착을 예약하고 문을 연다. 결과적으로 사용자는 문이 열린 뒤 멈춘 화면을 본다.

조치

게이트 해제 조건에 렌더 안정화를 추가한다. 스폰 이후 연속 N 프레임이 임계 이하로 돌았을 때 비로소 도착을 예약한다. 무거운 프레임이 끼면 카운터를 리셋해 다시 센다. 그러면 첫 렌더 2.8초와 뒤따르는 323ms·160ms 가 전부 닫힌 문 안에서 소진된다.

기존 안전장치는 그대로 둔다 — _forceOpenSeconds 30초 타임아웃이 있으므로 워밍업이 끝나지 않아도 영원히 갇히지 않는다. 층수 표시(FR-013)도 그대로다. 준비가 안 됐는데 11층에 닿지 않는다는 원칙은 오히려 강화된다.

주의: 대기를 늘리는 것이 목적이 아니다. 같은 시간을 어디서 보내느냐의 문제다 — 멈춘 월드 화면 대신 엘리베이터 안에서 층수가 올라가는 것을 본다.

검증

HitchLogger 로 진입을 다시 잰다. 100ms 이상 정지가 게이트 개방(BeginOpen) 이전에 오는지, 개방 이후에는 사라지는지 확인한다. 진입 총 시간도 함께 기록해 과도하게 길어지지 않았는지 본다.
