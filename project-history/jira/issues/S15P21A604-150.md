### 황덕 · 2026-09-07 13:32 KST

진행 체크. 어댑터 4종 중 현재 상태입니다.

- Redis 세션 — 됨. `AccountLifecycleService.withdraw` 가 `sessions.revoke` 를 부릅니다
- 스토리지 — 됨. 게임 에셋은 기존, AI 문서는 S15P21A604-485 (MR !392) 에서 삭제 큐로 넘깁니다
- 벡터 — 판별 필요. V21 이 `ai_document_chunks.document_id` 를 CASCADE 로 바꿔서 청크가 서비스 PG 안에만 있으면 문서 삭제로 이미 지워집니다. 외부 벡터 저장소가 따로 있는지만 확인하면 됩니다
- OAuth unlink — 남음. `oauth_identities` 행은 지우지만 제공자 쪽 연결은 그대로입니다

남은 실제 구현은 OAuth unlink 하나일 가능성이 높습니다. Sprint 6 산정 때 참고하면 됩니다.

### 황덕 · 2026-09-09 16:57 KST

선행 작업란의 "AI 벡터 삭제 인터페이스 협의"는 더 이상 유효하지 않습니다 — V21(GitLab #119, 2026-09-05)에서 ai_document_chunks.document_id가 ON DELETE CASCADE로 바뀌어 ai_documents 삭제만으로 벡터도 함께 지워집니다. 관계형·Redis 세션·객체 스토리지도 이미 구현돼 있고, 남은 구멍은 provider OAuth 연결 해제(S15P21A604-199) 하나입니다 — 같은 내용을 그 티켓에도 남겼습니다.

참고로 이 티켓 선행작업란은 "-199에 막힘"인데, -199 본문은 반대로 "BLOCKED BY -150"으로 적혀 있어 방향이 서로 어긋나 있습니다. 실제로는 -199(토큰 저장 결정) → -150(unlink 어댑터 완성) 순으로 보입니다.

### 황덕 · 2026-09-13 17:37 KST

MR !781. **넷 중 셋은 이미 돌아가고 있었고, 넷째는 지금 저장하는 것으로 부를 수 없습니다.**

| 자원 | 상태 |
|---|---|
| Redis 세션 | 이미 됨 — withdraw 가 sessions.revoke 를 먼저 부릅니다 |
| 객체 저장소 바이트 | 이미 됨 — 문서·게임 에셋 좌표를 같은 트랜잭션에서 삭제 큐로 옮기고 sweeper 가 지웁니다 |
| 벡터 | 이미 됨 — **별도 저장소가 아닙니다.** ai_document_chunks.embedding 이라 문서 삭제에 CASCADE 로 따라갑니다 |
| Google·Kakao 연결 해제 | **불가** |

선행조건이던 "AI 벡터 삭제 인터페이스 협의" 는 이미 해소돼 있었습니다. GitLab #119 에서 Spring 이 chunk 를 소유하기로 정한 순간 벡터는 우리 표 안의 컬럼이 됐고, 협의할 외부 인터페이스가 없습니다.

**연결 해제가 불가능한 이유**: oauth_identities 가 담는 것은 provider 와 provider_subject 둘뿐입니다. Google 의 revoke 는 그 사용자의 토큰을 요구하는데 우리는 로그인 교환 순간 말고는 그 토큰을 갖지 않습니다. Kakao 만 admin key + target_id 로 서버 단독 해제가 되어 두 provider 가 비대칭입니다.

개인정보 처리방침 문구가 따라 바뀌는 결정이라 임의로 정하지 않고 docs/26 에 네 선택지로 올렸습니다 — (a) 로그인 때 provider 토큰 저장, (b) 탈퇴 시 재인증, (c) Kakao 만 해제, (d) 우리 쪽 행만 지우고 안내(현재 동작).

**그래서 이 MR 의 산출물은 테스트입니다.** 프로덕션 코드는 한 줄도 고치지 않았습니다. 없던 것은 완료 조건 두 개를 실제로 재는 수단이었습니다.

- "4계 자원 잔존 0건" — Redis 키 소멸(active·session·family + refresh 해시) · chunk 소멸 · 큐 적재 후 sweep 으로 바이트 소멸 · oauth_identities 행 소멸
- "중복 호출 안전" — 같은 회원을 두 번 지워도 예외 없음

Closes 를 넣지 않았습니다. 네 번째가 결정 대기라 "4계 자원 잔존 0건" 이 아직 셋까지입니다. S15P21A604-199 도 이 결정을 기다립니다 — (a) 가 아니면 그 티켓의 "provider unlink 호출" 자체가 성립하지 않습니다.

검증: 전용 5건, clean test 1274건 통과. sessions.revoke 제거와 문서 좌표 enqueue 제거를 각각 테스트가 잡는 것까지 확인했습니다.
