## 설명

`S15P21A604-742` 블록 2 의 계정 부분(기능 4·5·6). 상위 추적 이슈는 `-742` 이고 이 이슈는 닫지 않는다.

## Deferred 해제

선행이던 "admin 권한 모델 팀 결정" 은 `S15P21A604-743`(AdminGuard·마스터 계정·`admin_actions` 감사, 2026-09-15 완료)으로 해소됐다. 더 기다릴 것이 없다.

## 배경 — 서비스는 이미 있고 HTTP 경로만 없다

`AccountLifecycleService.suspend/unsuspend` 와 `account_status_histories` 는 서비스·테이블·테스트까지 완비인데 컨트롤러가 없어 도달할 수 없다. spec 003 계약에 "HTTP 노출 없음 (U-01 확정까지 보류)" 로 명문화돼 있던 것이 `-743` 으로 풀렸다.

다만 **순수 노출 작업이 아니다.** 아래 셋이 함께 들어간다.

## 범위

| # | 기능 |
|---|---|
| 4 | 계정 정지 |
| 5 | 정지 해제 |
| 6 | 정지 이력 조회 |

`/api/v1/admin/users` 를 맡는 컨트롤러를 **새로 만든다.** 기존 `AdminController` 는 `@RequestMapping("/api/v1/admin/admins")` 로 고정돼 있어 여기에 메서드를 더하면 원하는 경로가 나오지 않는다.

## 반드시 함께 해결할 것

### 1. 감사 기록은 트랜잭션 안에서만 남는다

`AdminActionRecorder.record()` 는 `@Transactional(propagation = MANDATORY)` 다. 컨트롤러에는 트랜잭션이 없고 `AccountLifecycleService` 는 recorder 를 주입받지 않는다. 컨트롤러가 서비스 호출 뒤에 감사를 남기면 예외가 난다.

`AdminAccountService.promote` 와 같은 모양의 **오케스트레이션 서비스**를 두고 정지/해제 + 상태 이력 + `admin_actions` 를 한 트랜잭션에 묶는다.

### 2. 마지막 관리자 판정이 두 군데 틀렸다

현재 `AdminAccountService.demote` 의 판정은 `countByAccountType(ADMIN) <= 1` 이다.

- **평범한 count 라 경쟁한다.** 동시 요청 둘이 각각 2를 읽고 둘 다 통과해 0명이 될 수 있다.
- **세는 대상이 틀렸다.** `accountType` 과 `status` 는 별도 필드이고 `suspend()` 는 `status` 만 바꾼다. 정지된 관리자도 `account_type = ADMIN` 이라, 전체 ADMIN 을 세면 동작 가능한 관리자가 0명인데 판정은 통과한다.

→ `account_type = ADMIN AND status = ACTIVE` 행을 `ORDER BY id ASC FOR UPDATE` 로 잠그고 센다. **기존 **`demote` 의 판정도 같이 고친다 — 정지 쪽만 고치면 우회로가 남는다.

### 3. 잠금 순서 — 활성 관리자 집합이 먼저다

대상 사용자를 먼저 잠그면 교착한다. 관리자 A·B 를 동시에 정지할 때 한쪽은 A 를 쥐고 B 를, 다른 쪽은 B 를 쥐고 A 를 기다린다.

**활성 관리자 집합(id 오름차순) → 대상 사용자** 순서로 고정하고, 활성 관리자를 줄일 수 있는 모든 경로(정지·강등)가 같은 순서를 쓴다. 일반 회원 정지에도 같은 순서를 적용한다 — 관리자 API 는 호출 빈도가 낮아 경로를 하나로 두는 편이 낫다.

### 4. 정지·해제가 멱등이 아니다

`AccountLifecycleService.change()` 에 같은 상태 검사가 없다. 이미 `SUSPENDED` 인 계정을 다시 정지하면 `SUSPENDED → SUSPENDED` 이력이 한 줄 더 쌓이고 세션도 다시 끊는다. `findById` 라 대상 행 잠금도 없다.

→ 대상 사용자 행을 `FOR UPDATE` 로 잠그고, **이미 목표 상태면 이력·감사 없이 no-op** 으로 성공을 돌려준다.

### 5. 정지 이력 조회는 새로 만들어야 한다

`AccountStatusHistoryRepository` 는 쿼리가 하나도 없는 빈 `JpaRepository` 이고 엔티티에도 조회용 접근자가 없다. 사용자별 최신순 쿼리 + pagination + 응답 DTO 가 필요하다.

## 착수 전 — 계약 표 확정

코드를 쓰기 전에 method / path / header / request / response / error / pagination 표를 확정하고 `docs/08` 에 올린다. 정지 이력의 페이지네이션 파라미터가 여기서 정해져야 테스트를 먼저 쓸 수 있다.

## 완료 조건

- 일반 회원이 관리자 API 를 호출하면 403
- 마스터 대상 정지 시도 403 `MASTER_PROTECTED`
- 정지 1회에 상태 이력 1행 + `admin_actions` 1행, 해제도 대칭
- 같은 사용자 정지 2회에 이력·감사 각 1행 (2회째 no-op), 해제 2회도 대칭
- 정지+해제 동시 요청을 latch 로 순서 고정해 두 경우를 각각 검증한다 — 해제 먼저면 이력 1행, 정지 먼저면 2행. 실제 전이마다 정확히 한 행이고 no-op 에는 없다
- 마지막 활성 관리자 정지·강등 시도 409 `ADMIN_LAST_ONE`
- 동시 경쟁 3종(강등+강등 / 정지+정지 / 정지+강등) 어느 조합에서도 활성 관리자가 0명이 되지 않는다
- 정지 이력이 최신순·페이지네이션으로 조회된다
- 강등·정지된 계정이 다음 요청부터 즉시 거부된다
