## 설명

`S15P21A604-742` 블록 2 의 코인 부분(기능 9·10·11·12). 상위 추적 이슈는 `-742` 이고 이 이슈는 그것을 닫지 않는다. 계정 부분은 `S15P21A604-165` 다.

## 배경 — 서비스는 있고 컨트롤러가 없다

`WalletService.adjustByAdmin(CoinAdminAdjustCommand)` 와 `history`·`balanceOf` 는 이미 있고 `CoinReconciliationIntegrationTest` 가 조정 경로를 검증하고 있다. 그런데 이 셋에 도달하는 HTTP 경로가 없다. spec 003 계약의 "HTTP 노출 없음 (U-01 확정까지 보류)" 가 `S15P21A604-743` 으로 풀렸다.

**순수 노출 작업이 아니다.** 관리자 조정은 멱등키를 클라이언트가 만드는 첫 경로라, 지금 구조의 구멍 셋이 그대로 드러난다.

## 범위

| # | 기능 |
|---|---|
| 9 | 코인 지급 |
| 10 | 코인 회수 |
| 11 | 거래내역 조회 |

`/api/v1/admin/wallets` 를 맡는 컨트롤러를 새로 만든다. `AdminController` 는 user 패키지이고 `/api/v1/admin/admins` 로 고정돼 있어 지갑을 섞지 않는다.

13(정합성 점검)은 `CoinReconciliationSweeper` 가 도는 영역이라 별건으로 둔다.

## 반드시 함께 해결할 것

### 1. 멱등키 — 기존 관례를 그대로 쓰면 조정이 한 건으로 합쳐진다

기존 관례는 `REASON:REFERENCE_TYPE:{id}` 다. 관리자 조정에서 `{id}` 를 참조 id 로 읽으면 `ADMIN_ADJUSTMENT:ADMIN_USER:{actorUserId}` 가 되고, **같은 관리자의 두 번째 조정부터 전부 첫 요청으로 흡수된다.** `adjustByAdmin` 이 `referenceId` 에 `actorUserId` 를 넣고 있어 오해하기 쉬운 자리다.

갈라서 정의한다.

|  | 무엇 | 값 |
|---|---|---|
| `reference_type` / `reference_id` | 누가 했는가 | `ADMIN_USER` / `{actorUserId}` |
| `Idempotency-Key` 헤더 | 어떤 작업인가 | 조정 1건당 한 번 생성하는 `operationId` |
| 서버 멱등키 | 원장 저장값 | `ADMIN_ADJUSTMENT:{targetUserId}:{operationId}` |

`operationId` 는 UUID 형식으로 고정한다. 금지되는 것은 재시도마다 새 값을 만드는 것이지 UUID 자체가 아니다 — 클라이언트는 재시도할 때 같은 값을 다시 보낸다. 자유 문자열을 받으면 `coin_ledger_entries.idempotency_key` 가 `VARCHAR(100)` 이라 긴 값이 DB 제약에서 터져 500 이 된다.

멱등 범위는 대상 사용자별이다. 키에 `targetUserId` 가 들어가므로 대상이 다르면 키 자체가 달라진다.

`note` 는 멱등 동일성에 넣지 않는다. 자유 서술이고 `applyEntry` 가 받지 않아 원장에 저장되지도 않는다. 다른 `note` 로 재시도해도 충돌이 아니며 처음 것이 남는다 — 이것을 계약에 명시한다. 추적을 위해 `admin_actions.detail` 에 `operationId` 를 함께 남긴다.

### 2. 멱등 충돌이 조용히 통과한다 — 공용 경로를 고친다

`WalletService.applyEntry` 는 기존 키를 찾으면 지갑 주인만 확인하고 바로 `alreadyApplied` 를 돌려준다. 금액·사유·참조를 비교하지 않는다. 같은 키에 다른 금액을 실어 보내면 아무 일도 안 하고 "이미 반영됐다" 와 함께 이전 요청의 결과가 돌아간다.

→ 멱등 분기에서 저장된 항목과 요청을 비교한다. 비교 항목은 `walletId` · `entryType` · `signedAmount` · `reasonType` · `referenceType` · `referenceId` 여섯이다.

| 불일치 | 처리 |
|---|---|
| `walletId` | 지금대로 `IllegalStateException` (500 계열) |
| 나머지 다섯 중 하나라도 | `409 IDEMPOTENCY_CONFLICT` |

`walletId` 를 409 로 내리지 않는 이유는 기존 주석에 있다(T-24 · `S15P21A604-695`) — 서버가 만든 키가 지갑 사이에서 겹친 것은 클라이언트 잘못이 아니라 서버 결함이라 409 로 위장하면 원인이 묻힌다.

`ErrorCode` 에 `IDEMPOTENCY_CONFLICT(HttpStatus.CONFLICT, ...)` 를 신설한다.

**공용 경로를 고치는 것이 맞다.** 호출자마다 막으면 다음 기능이 또 뚫린다. 기존 호출자는 키를 참조 엔티티에서 결정론적으로 뽑으므로(`LEASE_PAYMENT:BOOTH_LEASE:{leaseId}` 등) 같은 키에 다른 payload 가 올 수 없어, 이 검사에 새로 걸릴 기존 경로는 없다. 다만 지갑은 전 도메인이 쓰므로 전체 스위트를 돌려 회귀 0 을 확인한 뒤 낸다.

### 3. 감사 기록은 트랜잭션 안에서만 남는다

`AdminActionRecorder.record()` 는 `@Transactional(propagation = MANDATORY)` 다. 컨트롤러에는 트랜잭션이 없으므로 `AdminAccountService.promote` 와 같은 모양의 오케스트레이션 서비스를 두고 원장·잔액·`admin_actions` 를 한 트랜잭션에 묶는다. `adjustByAdmin` 은 `REQUIRED` 라 바깥 트랜잭션에 합류한다.

**멱등 재요청은 원장뿐 아니라 **`admin_actions` 도 늘리지 않아야 한다. `applyEntry` 가 `alreadyApplied` 를 돌려주므로 그 결과를 보고 감사 기록을 건너뛴다.

### 4. 지금 500 이 나는 입력들

- `signedAmount == 0` 과 빈 멱등키 — `WalletService` 가 `IllegalArgumentException` 을 던지는데 `GlobalExceptionHandler` 에 매핑이 없다. 컨트롤러가 직접 검증해 400 으로 돌린다. 서비스는 공용 경로라 거기서 바꾸지 않는다.
- `signedAmount == Integer.MIN_VALUE` — `applyEntry` 의 `!wallet.canAfford(-signedAmount)` 에서 `-signedAmount` 가 오버플로해 다시 음수가 되고, 사용자용 `409 INSUFFICIENT_COIN` 관문을 그냥 통과한다. 뒤의 `Wallet.apply` 가 `long` 으로 승격해 걸러 주지만 그건 마지막 방어선이라 500 으로 나간다.
- 증액 후 잔액이 표현 범위 초과 — `balance INTEGER CHECK(balance >= 0)`, `balance_after INTEGER` 라 같은 자리에서 터진다.

## 착수 전 — 계약 표 확정

코드를 쓰기 전에 method / path / header / request / response / error / pagination 표를 확정하고 `docs/08` 에 올린다. `Idempotency-Key` 헤더의 필수 여부와 형식, 거래내역 페이지네이션 파라미터, 그리고 금액 경계가 여기서 정해져야 테스트를 먼저 쓸 수 있다.

금액 경계에 못박을 것:

|  |  |
|---|---|
| 허용 금액 범위 | 상·하한 |
| `Integer.MIN_VALUE` | 거부 — 400 |
| 증액 후 잔액 표현 범위 초과 | 400 인지 409 인지 명시 |
| 잔액을 넘는 회수 | `409 INSUFFICIENT_COIN` (기존 경로) |

**제품상 조정 상한이 필요하다면 임의로 정하지 않는다** — `docs/26` 결정 대상으로 올린다(헌법 30조). 기술적 오버플로 방지와 "한 번에 얼마까지" 는 다른 문제다.

## 완료 조건

- 일반 회원이 관리자 API 를 호출하면 403
- 마스터 대상 코인 회수 시도 403 `MASTER_PROTECTED`
- 코인 조정 1회에 원장 1행 + `admin_actions` 1행
- 같은 대상·같은 `operationId` 로 같은 요청 재전송 시 원장·감사 둘 다 증가 없음
- 같은 대상·같은 `operationId` 에 금액 또는 행위자가 다르면 `409 IDEMPOTENCY_CONFLICT`, 원장·감사 무변화
- 같은 대상·같은 `operationId` 동시 요청 2건에 정확히 원장 1행·감사 1행
- 충돌 응답이 기존 항목의 `balanceAfter` 를 돌려주지 않는다
- `operationId` 가 UUID 형식이 아니거나 과도하게 길면 400
- `signedAmount = 0` 이면 400 (현재 경로는 500)
- `Integer.MIN_VALUE` 회수 400, 증액 후 표현범위 초과는 계약에 정한 코드, 잔액 초과 회수 `409 INSUFFICIENT_COIN`
- 거래내역이 최신순·페이지네이션으로 조회된다
- 모든 시나리오 끝에 `WalletTestSupport.assertBalanceMatchesLedger` (불변식 I-1)
- `WalletService` 변경 후 backend 전체 스위트 회귀 0

`CoinReconciliationIntegrationTest` 는 서비스 레벨이라 새 HTTP 경로의 인증·요청 검증을 보장하지 않는다. `AdminWalletApiIntegrationTest` 를 신설한다.
