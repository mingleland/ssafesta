## 설명

GitLab 이슈 #120 (BE S15P21A604-378, develop 반입 완료) 의 §8-1 회신 이행.

[배경]
BE 가 아바타 파츠에 보유·구매·미보유 착용 차단을 넣었고 develop 에 들어와 있다 (시드 V16__avatar_catalog_seed.sql 97행, CatalogController, InventoryService).

현재 Unity 는 잠금 여부를 AvatarItemDefinition.isDefaultUnlocked 라는 자체 플래그로 계산한다. #120 §2-1 이 "클라이언트는 price 나 보유 목록으로 이 값을 다시 계산하지 마십시오" 라고 명시하므로 이 방식은 계약 위반이다. 서버가 내려주는 owned 하나만 근거로 삼아야 팔레트 표시와 저장 거부가 어긋나지 않는다.

[작업 범위]
1. GET /api/v1/catalog/items?type=AVATAR_PART 호출 추가. 현재 Unity 가 부르는 Spring endpoint 는 6개뿐이다 (HttpBoothApiClient 3 + HttpUserApiClient 3).
2. 잠금 판정을 응답의 owned 로 교체하고 AvatarItemDefinition.isDefaultUnlocked 와 AvatarOwnership 의 클라이언트 재계산 경로를 걷어낸다.
3. 조회 응답에 있는 품목만 그린다 (§2-1 권고). 카탈로그 미등록 파츠를 그리면 고를 수는 있어도 저장이 409 로 거부된다.
4. 저장 실패 시 409 AVATAR_ITEM_NOT_OWNED 의 errors[].objectId (= assetKey) 로 팔레트의 해당 항목을 짚어 표시한다.
5. 게스트는 잠금 클릭 시 구매가 아니라 로그인 유도로 보낸다 (구매는 MEMBER_ONLY 로 거부됨).
6. 조회 실패 시 조용히 전량 개방으로 떨어지지 않게 한다 — 로그 + 에러 상태로 드러낸다 (헌법, T-24 재발 방지).

[무료 파츠 개수와의 관계]
Unity 는 owned 만 읽으므로 무료 세트 규모가 어떻게 정해져도 Unity 추가 작업은 없다. 시드 UPDATE 로 반영된다. (#120 §8-2, 기획 확정 대기)

[함께 처리할 결함 — BE 요청분, #120 회신에 기재]
S15P21A604-355 에서 남성 팔레트의 여성복 3종을 AvatarCatalog.asset 의 items 배열에서 제거했으나 V16 시드에는 price 100 판매중으로 남아 있다.
  M_Bot.03    assetKey 1814256283
  M_Top.07-A  assetKey 356384796
  M_Outfit.03 assetKey 415781343
지금 상태로는 상점에서 살 수 있고 Unity 팔레트가 그리지 않아 착용 경로가 없다. BE 에 is_on_sale FALSE 요청함. 작업 범위 3번(응답에 있는 품목만 그림)을 지키면 Unity 쪽은 자연히 정합된다.

또한 AvatarCatalogSeedContractTest 는 디스크의 .asset 파일 105개를 세고 AvatarCatalog.asset 은 filter 로 제외하므로 이 어긋남을 잡지 못한다 (파일은 남겨두고 배열 참조만 뺐기 때문). #120 에 보고함.

[완료 조건]
- 팔레트 잠금이 서버 owned 와 100% 일치한다 (클라이언트 재계산 코드 0)
- 미보유 파츠를 고를 수 없어 409 AVATAR_ITEM_NOT_OWNED 가 정상 경로에서 발생하지 않는다
- 카탈로그 조회 실패가 전량 개방으로 이어지지 않고 에러로 드러난다
- 게스트 잠금 클릭이 로그인 유도로 간다
