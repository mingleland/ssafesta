## 설명

### 마이그레이션 번호 변경 — V19 에서 V21 로 (2026-09-05)

작업 중 V20(S15P21A604-424, 아바타 파츠 판매 중지)이 develop 에 먼저 들어갔다. Flyway 는 out-of-order 를 켜지 않았으므로(기본값 false) 이미 V20 을 적용한 DB 에는 뒤늦게 온 V19 가 적용되지 않고 기동 시 validate 에서 멈춘다. 그래서 이 작업의 번호를 V21 로 옮겼다. 파일 내용은 그대로다.

아래 본문의 V19 표기는 모두 V21 로 읽는다.

### 작업 목적

GitLab 이슈 #119에서 AI 문서 DB 소유권이 Spring으로 넘어왔다. FastAPI는 DB credential 없이 파싱·청킹·임베딩·질의 임베딩만 담당한다. AI 파트가 2026-09-02 코멘트로 올린 스키마 초안을 Flyway V21로 이관한다. 스키마 정의는 AI 파트 안을 따르고 새로 설계하지 않는다.

### 확정된 것 (GitLab 이슈 #119, 2026-09-02 AI 파트 회신)

- 기존 `ai_document_chunks`(V1)를 **확장**한다. 새 테이블을 만들지 않는다
- `metadata JSONB` 드롭, `embedding_model_id`를 TEXT로 확대
- `ai_document_jobs` 신규. `callback_*` 5개 컬럼은 **제외** — finalize 호출 자체가 Spring 로컬 트랜잭션으로 확정하므로 push 전달 추적 대상이 없다
- staging PK는 `(job_id, batch_seq, chunk_no)`. batch 재전송은 `ON CONFLICT DO NOTHING`으로 멱등 수신하고, finalize 성공·CANCELLED·DEAD 시 `DELETE WHERE job_id = :id`로 정리한다. 별도 TTL 스케줄러를 두지 않는다
- 벡터 인덱스는 `hnsw (embedding vector_cosine_ops)` — 코사인
- AI DB에 보존할 실데이터가 없다. Alembic 마이그레이션 1개뿐이고 seed/backfill 스크립트가 없어 **backfill 없이 스키마 이식으로 끝난다**
- `max_retries` 기본 3

### 작업 내용

- `ai_document_jobs` 신규 — `document_id`, `booth_id`, `agent_id`, `source_hash`, `original_filename`, `content_type`, `file_size_bytes`, `storage_provider`/`storage_bucket`/`object_key`, `status`(QUEUED/RUNNING/RETRY_WAIT/SUCCEEDED/DEAD/CANCELLED), `attempt_no`, `max_retries`, `worker_id`, `lease_expires_at`, `next_retry_at`, `last_error_code`/`last_error`, `chunk_count`, `created_at`/`updated_at`/`finished_at`
- 인덱스 3종 — `ix_ai_document_jobs_active_document`(document_id 부분 unique, 활성 3상태), `_pickup`(status, next_retry_at), `_lease`(lease_expires_at WHERE RUNNING)
- `ai_document_chunks` 확장 — `job_id`, `page_number`, `section`, `searchable`(default false) 추가. `metadata` 드롭, `embedding_model_id` TEXT 전환
- `ai_document_chunk_staging` 신규
- 벡터 인덱스 `ix_ai_document_chunks_embedding_cosine` 신설 — 현재 btree 3개뿐이고 벡터 인덱스가 없다. P95 1초 목표가 이 인덱스에 걸린다
- rollback 스크립트와 cutover 순서 문서화

### 확인 필요 4건 — 2026-09-03 AI 파트 회신으로 전부 확정됨

초안대로 적용하면 문서 삭제와 회원 탈퇴가 FK에서 막힌다. 아래 4건을 확정하고 반영해야 했고, AI 파트가 2026-09-03 코멘트로 넷 다 답했다.

**1.** `ai_document_chunks.document_id`의 CASCADE 전환이 초안에 빠져 있다. V1 실측은 `document_id BIGINT NOT NULL REFERENCES ai_documents(id)`로 ON DELETE 절이 없다(NO ACTION). 문서를 지우면 chunk FK가 삭제를 막는다. → **확정: FK를 드롭하고 ON DELETE CASCADE로 재생성한다.**

**2.** `ai_document_chunks.job_id`의 FK는 걸지 않는 편이 맞다. Job이 문서 CASCADE로 지워질 때 이 FK가 삭제를 막고, 이미 `searchable=TRUE`로 나간 청크의 출처 추적도 끊긴다. → **확정: FK 없이 값만 유지한다.**

**3.** `embedding`의 NOT NULL 전환이 초안에 빠져 있다. V1은 nullable인데 AI 파트 원본 모델은 NOT NULL이다. → **확정: NOT NULL로 전환한다. staging → finalize에서 완성된 값으로 한 번에 쓴다.**

**4.** `AccountDeletionService` 회귀. `backend/src/main/java/com/example/ssafesta/user/AccountDeletionService.java`가 chunk를 먼저 지우고 document를 지운다 — FK가 NO ACTION이라 순서가 강제된 코드다. → **확정: 1·2번을 CASCADE로 정리하면 이 두 줄이 document 삭제 한 줄로 줄어든다. AI 파트 쪽에 처리할 것은 없다.**

### 보류 — 벡터 인덱스 연산자는 잠정이다

AI 파트 회신에 따르면 **서비스용 임베딩 모델 ID가 아직 미확정**이다(`festa-ai/app/core/config.py`의 `EMBEDDING_MODEL_ID`가 optional, no fixed default). 코사인 제안의 근거는 `spikes/ai-rag`의 실험 코드가 `<=>`를 써 왔다는 것이고, AI 파트도 "확정 값은 아니다"라고 명시했다. 차원 1536은 헌법 18조·FR-009로 고정이다.

S15P21A604-373 [AI][ADR] RAG 최종 모델·검색 파라미터 확정에서 거리 기준이 내적이나 L2로 바뀌면 **인덱스를 재생성해야 한다.** 코사인으로 진행하되 이 사실을 마이그레이션 주석에 남긴다.
