## 설명

h3. 작업 목적

CI 에서 Game Studio 테스트 2건이 코드 변경 없이 간헐적으로 red 가 된다(GitLab #168). 재시도하면 통과한다.

{code}
editorPerformance.test.ts                 100ms interaction budget 초과
  MR !620(-607) 103.44ms · !627(-616) 155.00ms · !633(-620) 117.94ms
projectDataPanelVariableCreate.test.tsx   Test timed out in 5000ms
  MR !598(-592) 1건
{code}

실패한 MR 은 모두 Game Studio 코드 변경이 0건이다.

h3. 조사 결과 — production 회귀가 아니라 테스트 설계 문제다

h4. 회귀 아님

측정 대상 코드가 최초 반입 이후 바뀌지 않았다.

{code}
gameProjectStore.ts        1695ba74 이후 변경 0
moveObject (403~418행)     1695ba74 이후 변경 0
editorPerformance.test.ts  1695ba74 이후 변경 0
{code}

h4. editorPerformance — 재는 비용의 99.86%가 부대 작업이고, 판정이 p100 이다

{{store.update(moveObject)}} 1회의 구간 분해(단독 실행 median):

|| 구간 || median ||
| moveObject 알고리즘만 | *0.01ms* |
| structuredClone(present) | 0.82ms |
| moveObject 안의 parseGameProject | 1.20ms |
| snapshot: parse + clone + deepFreeze | 3.32ms |
| sameProject: JSON.stringify x2 | 0.58ms |
| *store.update 전체* | *7.31ms* |

한 번의 commit 이 프로젝트 전체를 structuredClone 2회 · JSON.stringify 3회 · 스키마 검증 2회({{moveObject}} 안의 {{validated}} + store 의 {{snapshot}}) · deepFreeze 1회 거친다. 할당이 많아 GC 를 부르고 측정 구간이 한 자릿수 ms 라, 스케줄러 대기 하나가 그대로 배수로 들어온다.

같은 코드·같은 머신에서 worker 부하만 바꾼 실측(22코어):

|| 조건 || median || max ||
| worker 1개 | 7.25ms | 9.65ms |
| worker 4개 | 8.30ms | 12.95ms |
| worker 44개 | 17.75ms | 27.03ms |
| 전체 스위트 | 16.41ms | *45.46ms* |

*max 만 4.7배 튀고 median 은 2.3배다.* 테스트는 5샘플 중 {{Math.max}} 를 100ms 에 걸고 있어, 스파이크 하나가 곧 red 다.

h4. projectDataPanelVariableCreate — 쿼리 비용이 렌더보다 크다

이 파일에는 {{findBy*}}·{{waitFor}}·{{userEvent}}·fake timer 가 하나도 없다. 전부 동기다. 실패한 "변수 100개 상한" 케이스의 구간 분해(median):

|| 구간 || median || p95 ||
| 프로젝트 생성 | 0.0ms | 0.3ms |
| render | 64.0ms | 86.9ms |
| *getByRole x3* | *138.2ms* | *240.6ms* |
| (참고) getByText x3 | 51.5ms | 68.5ms |

{{getByRole}} 은 DOM 을 순회하며 요소마다 role 과 accessible name 을 계산한다. 변수 개수에 비례한다 — 1회 기준 vars=3 은 3.9ms, vars=100 은 30.5ms(p95 88.5ms).

*재는 대상은 "상한에서 버튼이 비활성화되는가"인데 테스트 시간의 65%가 그와 무관한 쿼리 비용이다.*

h3. 작업 내용 — 테스트만 고친다

# {{editorPerformance.test.ts}} — 판정 통계를 {{Math.max}} 에서 *중앙값*으로. 샘플 5 -> 10(warm-up 2회 유지). 실패 시 분포 전체를 메시지에 남긴다.
# {{projectDataPanelVariableCreate.test.tsx}} — 실패한 케이스에서만 {{getByRole}} 을 {{getByText}} 로. 세 버튼이 텍스트를 직접 담고 있어 같은 button 요소를 돌려준다. 변수가 적은 다른 두 케이스는 3.9ms 라 그대로 둔다.

*예산 100ms · 5000ms, 측정 대상, 단언 내용은 모두 그대로다.* Game Studio production 코드는 건드리지 않는다.

h3. 회귀 검출력이 유지되는 근거

알고리즘이나 store 경로가 느려지면 특정 샘플이 아니라 분포 전체가 옮겨 가므로 중앙값이 그대로 잡는다. 반대로 GC·스케줄러 스파이크는 소수 샘플에만 나타나 중앙값이 걸러 낸다.

h3. 검토했지만 택하지 않은 안

* *threshold 상향(100 -> 300ms)* — 지금 median 은 예산의 16%다. 여유가 없어서가 아니라 통계가 p100 이라 깨진다. 숫자를 올리면 증상만 가리고 검출력이 함께 떨어진다.
* *순수 {{moveObject}} 만 benchmark 로 분리* — 알고리즘이 0.01ms 라 100ms 예산 테스트로서 의미가 없고, 비용의 99.86%인 store 경로 회귀를 놓친다.
* *별도 performance job 분리* — 러너가 1대라 job 을 나눠도 같은 CPU 를 공유한다. 전용 환경이 생기면 그때 유효하다.
* *{{testTimeout}} 상향* — 근거 없이 숫자만 늘리는 것이라 마지막 수단으로 뒀다. 쿼리 비용을 줄이는 쪽이 원인에 가깝다.
