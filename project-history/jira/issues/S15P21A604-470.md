## 설명

이번 작업은 R3F 채택 여부를 검증하는 Spike 다. R3F 정식 도입 확정도, GLB 파이프라인 구축도 아니다.

[배경]
D-04 는 Booth Studio 를 2.5D 로 확정했고, D-05 는 R3F + three + drei 를 1순위 후보로 두되 "Spike PASS 후에만 정식 채택" 이라고 명시했다. 현재 구현은 TemporaryIsoRenderer.tsx(357줄) — SVG 직접 아이소메트릭 투영이고 three 계열은 미설치다.

시안(booth-2_5d-reference.png) 대비 격차는 캔버스 한 곳이다 — Inspector(위치/회전/크기 XYZ)·TopToolbar·ModeRail·StatusBar 는 이미 시안과 같다.

시안 vs 현재:
- 오브젝트: 실제 모델 vs 타입별 색 박스
- 재질: 무광/유광/유리 vs flat + 면별 명도
- 그림자: 생성/받기 vs 바닥 타원 1개
- 기즈모: 3축 화살 vs X/Z 축선 + 회전 링
- 조명: 실광원 vs 원 + 방사 그라디언트

[에셋 파이프라인을 이번에 열지 않는 이유]
R3F 도입과 GLB 파이프라인은 분리 가능한 두 결정인데 스파이크 문서가 하나로 묶어 둔다. 위 격차 5줄 중 4줄(재질·그림자·조명·3축 기즈모)은 에셋 없이 실광원·실카메라만으로 닫힌다. 남는 것은 실루에스 하나다.

또 실측 결과 전 3D 에셋이 벤더팩(ExpoKit·ithappy·Synty·Rukha93, 라이선스 파일 0건)이다. GLB 를 정적 URL 로 서빙하면 추출 가능한 형태의 재배포라 팀 결정 사항이다(헌법 30조). P2 에서만 걸리므로 이번 Spike 는 그 결정 없이 진행한다.

[작업 범위]
기존 BoothCanvasViewport seam 뒤에서만 교체/추가한다.

유지: Palette · Inspector · Toolbar · ModeRail · StatusBar · X/Z 이동 · Y 고정 · Y축 회전 · grid snap · bounds · 선택 상태/편집 계약

구현:
- R3F + three + drei 최소 도입
- 고정 Orthographic iso camera
- OBJECT_LOCAL_BOUNDS 기반 파라메트릭 geometry
- 바닥/벽/트러스/오브젝트 입체화
- 실제 light + shadow + 기본 material
- 3축 gizmo + 회전 표현
- 기존 선택/이동/회전 흐름 유지
- Studio route lazy chunk 분리

[범위 밖 — 명시]
GLB/FBX 변환 / Unity vendor asset 웹 배포 / Blender·FBX2glTF 파이프라인 / 실제 텍스처 반입 / AiAgent 스킨드 메시 / Booth Studio 전체 재작성 / Shell·Inspector 재설계 / Unity 신규 작업

[Spike Gate — 반드시 실측]
1. 기존 편집 기능 회귀 없음
2. SVG 대비 깊이/조명/그림자/재질/gizmo 개선
3. Unity WebGL + R3F WebGL context 공존
4. Studio 진입/이탈 반복 시 context leak 없음
5. main bundle 에 three/R3F 강제 포함 없음
6. Studio lazy chunk 분리
7. 초기 로드/Studio 진입 성능
8. 메모리/프레임 치명 문제 없음

가능하면 실브라우저 풀스택에서 World -> Studio -> World 왕복까지 확인한다.

[PASS / FAIL 판정]
PASS 후보: 기존 editor 계약 유지 + 시각 품질 명확히 개선 + lazy loading 성립 + Unity 와 context 공존 + 성능/메모리 치명 문제 없음
FAIL 후보: context 충돌 / bundle 과다 증가 / 성능 저하 / interaction 회귀 / 복잡도 대비 개선 미미

실패 시 억지로 살리지 않고 SVG 유지 방향으로 복귀한다.

[품질 게이트]
npm run build / vitest 전체 / tsc / oxlint 전부 green. npm run build 를 최종 배포 게이트로 반드시 포함한다(S15P21A604-469 교훈).
