## 설명

## 작업 목적

편집기에서 "저장"한 초안이 실제 백엔드에 왕복 저장·조회되는지 확인한다. 지금까지는 로컬(IndexedDB/브라우저 mock) 저장소 기준으로만 QA해왔고, 서버 어댑터(`createApiGameDraftRepository`)는 한 번도 실제 서버에 붙어본 적이 없다.

## 작업 내용

- `PUT /api/v1/games/{gameId}/draft` — 초안 저장 검증 (`gameAuthoringApi.ts:126`)
- `GET /api/v1/games/{gameId}/draft` — 초안 불러오기 검증 (`gameAuthoringApi.ts:118`)
- revision 필드 왕복(요청 `expectedRevision` → 응답 `revision`) 정합성 확인
- 저장 응답의 `updatedAt`/`warnings` 필드 파싱(`parseGameDraftResponse`) 확인
- 다음 기대 동작을 실제로 재현해 대조한다:
   
   - 저장 → 새로고침 → 저장한 내용 그대로 불러와짐
   - 저장할 때마다 `revision`이 1씩 증가
   - 다른 클라이언트가 먼저 저장해 revision이 앞서 있으면 `GAME_REVISION_CONFLICT`로 거부되고 FE가 안내 문구를 보여줌(`gameAuthoringApi.ts:97-103`)
   - 서버 응답의 `project.gameId`/`revision`이 요청과 다른 경우가 실제로 발생하지 않는지 확인(`GAME_API_RESPONSE_INVALID` 방어가 필요할 만한 응답이 오는지)

이 작업은 구현이 아니라 **검증**이 목적이며, 조율 필요 여부는 낮음 — FE `gameAuthoringApi.ts`와 BE `GameController.draft`/`saveDraft`(`GameController.java:206`, `:258`) 모두 이미 구현돼 있어 FE 단독으로 연결·확인 가능하다. 다만 응답 필드명이나 revision 규칙이 계약과 다르게 나오면 그 시점부터 BE와 조율이 필요하다.

## 완료 조건

- [ ] 저장 → 새로고침 → 불러오기 왕복이 실제로 확인된다
- [ ] revision 증가 규칙이 FE 기대와 일치한다
- [ ] 동시 저장 충돌(`GAME_REVISION_CONFLICT`) 시나리오가 재현되고 FE 안내 문구가 정상 노출된다
- [ ] 발견된 불일치(필드명, 에러 코드 등)는 후속 티켓 또는 `docs/26_팀_결정_필요사항.md`로 연결된다

## 선행 작업 / Dependency

- 로컬에서 백엔드 기동 가능해야 함(미확인 — `backend/bruno/`의 API 클라이언트 컬렉션부터 점검)
- `VITE_GAME_STUDIO_API_ENABLED=true`로 FE를 서버 어댑터 모드로 전환
- 테스트용 게임(`POST /api/v1/games`로 생성) 1개 이상 필요

## 테스트 방법

1. `VITE_GAME_STUDIO_API_ENABLED=true`로 FE 기동, 로컬 백엔드 기동
2. 새 게임 생성 → 에디터에서 오브젝트/이벤트 추가 → 저장
3. 새로고침 후 같은 게임을 열어 저장한 내용이 그대로 불러와지는지 확인
4. 브라우저 탭 2개로 같은 게임을 열고, 한쪽에서 먼저 저장 → 다른 쪽에서 저장 시도 → `GAME_REVISION_CONFLICT` 안내가 실제로 뜨는지 확인
5. Network 탭에서 실제 요청/응답 payload가 계약(필드명, revision 값)과 일치하는지 확인
