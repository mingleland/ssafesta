## 설명

### 작업 목적

도메인별 통합 테스트 50여 개는 서비스와 리포지토리를 주입해 세팅하고 검증한다. 지름길이 있으니 **도메인 사이 이음매를 지나지 않는다.** 한 사용자의 흐름이 가입에서 임대·게시·방문까지 HTTP 만으로 이어지는지 확인하는 테스트가 없다.

docs/19 §5 의 E2E-001·002·004 중 백엔드가 소유한 부분을 코드로 고정한다. E2E-003(멀티플레이)은 Unity 몫이고, E2E-101·102·103 은 상담·설문·미니게임 컨트롤러가 아직 없어 범위 밖이다.

### 규칙 — 이것이 기존 통합 테스트와의 차이 전부다

1. **HTTP 만 쓴다.** 리포지토리·서비스 주입 금지. 세팅도 검증도 API 응답으로만 한다.
2. 예외 하나 — OAuthHandoffService.createRegistration. OAuth 제공자 화면은 대체할 수 없다. 그 뒤 POST /auth/oauth/complete 부터는 실제 HTTP 다.
3. **한 클래스 = 한 플로우, @Test 하나.** 단계별로 쪼개지 않는다. 순서 의존이 곧 플로우다.
4. 새 프레임워크를 넣지 않는다. 기존 MockMvc + TestcontainersConfiguration 을 그대로 쓴다.
5. **기존 동시성 테스트 9개와 겹치는 케이스는 넣지 않는다.** 교차 도메인 경합과 결과가 밖으로 새는지만 본다.

위치: backend/src/test/java/com/example/ssafesta/e2e/

### 플로우 A — 부스 주인

가입 → 지갑 → 슬롯 조회 → 임대 → 부스 → AI 직원 → 배치 작업본 → 프로젝트 → 외관·홈페이지 → 게시 → 익명 공개본 조회

흐름 안에 박는 것:

- 멱등 — 같은 임대 요청 재전송이 200 과 같은 leaseId 를 주고 잔액은 한 번만 준다
- 멱등 — 같은 handoff 재사용은 410, AI 직원 두 번째 생성은 AGENT_LIMIT_EXCEEDED, 프로젝트 두 번째는 PROJECT_ALREADY_EXISTS
- 동시성 — 같은 슬롯에 두 회원. 한 명만 201, 진 쪽은 409 이고 코인이 0 차감이다
- 동시성 — 같은 expectedRevision 으로 두 번 저장. 하나 200, 하나 409 LAYOUT_REVISION_CONFLICT. **패자의 내용이 작업본에 없다**
- 동시성 — publish 와 DELETE agent 를 동시에. 한쪽만 이기고, **익명 공개본 조회에 유령 configId 가 보이지 않는다**
- 정합성 — 돈이 움직인 단계마다 잔액과 거래 내역 합계가 같다. 경합에서 진 쪽도 같다
- 정합성 — 게시본 오브젝트가 작업본에 넣은 것과 같고, 슬롯 경로와 부스 경로의 응답이 같다
- 회차 — publish 두 번이면 v1, v2 다. 공개본 조회는 v2 다 (spec 005:113, GitLab 이슈 #36 합의)
- 실패 경로 — 잔액 부족, 규칙 위반 배치

### 플로우 B — 방문자

A 의 결과를 이어받는다. 게스트 로그인 → 공개본 조회 → 월드 세션 → 부스 상세 → 공개 프로젝트 → 좋아요

- 멱등 — 좋아요 PUT 동시 3회에 카운트 1, DELETE 두 번에 0 유지
- 경계 — 게스트 토큰으로 임대·작업본 저장은 403 MEMBER_ONLY
- 경계 — A 의 비공개 프로젝트가 방문자에게 보이지 않는다
- 입장 토큰 1회용 계약 확인

내부 API(/internal/ai/*) 경계와 문서 격리는 **S15P21A604-173** 이 이미 담고 있다. 이 티켓에서 중복하지 않는다.

### 완료 조건

- 플로우 A·B 가 각각 한 클래스로 존재하고 전부 통과한다
- 규칙 1(HTTP 만)이 지켜진다 — 예외는 규칙 2 하나뿐이다
- 기존 동시성 테스트 9개와 중복되는 케이스가 없다
