## 설명

## 배경

S15P21A604-484 로 넣은 DPR 상한(1.5)은 동작하지만, 게임 파트가 후속 결함을 실측해 GitLab #143 에 보냈다.

resolveDevicePixelRatio() 의 계산식은 맞다. 문제는 그 값이 createUnityInstance config 로 한 번만 전달되고 재평가가 없다는 것이다. 내장 화면(DPR 2)에서 로드해 상한 1.5 가 박히고, 외부 1080p(DPR 1)로 창을 옮긴 뒤에도 계속 1.5배로 그린다.

게임 파트 실측(2026-09-08 11:07)
  캔버스 CSS 1920 x 889 · 백버퍼 2880 x 1334 · window.devicePixelRatio 1
  min(1, 1.5) = 1 이어야 하는데 1.5 로 그린다 — 필요보다 2.25배 픽셀

이 게임은 120Hz 경계선(8.33ms) 위에 걸터앉아 있어 2.25배 픽셀 낭비가 경계를 넘기는 방아쇠가 된다고 보고받았다. 그쪽은 오전 측정을 한 번 버렸다.

## 사전 조사 (2026-09-10)

서빙 중인 WebGL framework 를 압축 해제해 읽었다.

function _JS_SystemInfo_GetPreferredDevicePixelRatio(){
    return Module.matchWebGLToCanvasSize==false ? 1 : Module.devicePixelRatio || window.devicePixelRatio || 1
  }

즉 framework 는 Module.devicePixelRatio 를 호출마다 다시 읽는다 — 게임 파트가 제안한 2안(런타임 갱신)이 성립할 여지가 있다.

다만 미확인이 둘 남았다.
1. Module 에 접근할 경로. window.unityFramework 는 null 이었다(typeof null === 'object' 에 한 번 속았다). createUnityInstance 가 반환하는 인스턴스에 Module 이 달려 오는지 부팅 후킹으로 확인해야 한다.
2. Unity 가 _JS_SystemInfo_GetPreferredDevicePixelRatio 를 언제 호출하는가. 매 프레임이 아니라 리사이즈 시점이면 갱신만으로는 반영되지 않을 수 있다.

이미 실패로 확인된 경로 둘은 다시 시도하지 않는다(loader.ts 주석·게임 파트 실측이 일치).
  Screen.SetResolution — 로더의 matchWebGLToCanvasSize 가 다음 프레임에 되돌린다
  캔버스 width/height 직접 대입 — 렌더 루프가 멈춘다(rAF 정지, NGO 연결까지 끊긴다)

## 범위

1. Module 접근 경로와 호출 시점을 실측으로 확정한다.
2. 그 결과에 따라 해법을 고른다.
   2안 가능 — DPR 변화 감지(matchMedia resolution change) 후 Module.devicePixelRatio 갱신
   2안 불가 — 1안(캔버스 CSS 크기만 조정해 백버퍼가 따라오게) 검토
   둘 다 불가 — 3안(콘솔 경고)을 최소한 넣는다. 지금은 조용히 2.25배를 그려 성능 측정이 오염된다
3. 별건 — 캔버스 위 backdrop-filter: blur(8px) 3곳 비용 측정.
   src/features/world/ui/worldHud.css:22 · :92 · src/features/world/ui/consultationQuickAccess.css:20
   뒤 표면이 매 프레임 바뀌는 WebGL 캔버스라 합성기가 매번 다시 블러한다. Unity 프로파일러에 안 잡혀 게임 파트가 볼 수 없는 비용이다.
   끄고 켜며 프레임을 비교하고, 유의미하면 불투명 배경으로 교체한다.

### 이정헌 · 2026-09-10 11:31 KST

1번 목표(Module 접근 경로와 호출 시점 실측 확정)을 마치고, 그 결과로 2번 선택지를 골라 구현까지 넣었다. MR !565.

h3. Module 접근 경로

앞 회차에 window.unityFramework 를 Module 이라 적은 것은 틀렸다. 실제 값은 null 이고 typeof null === 'object' 라 확인이 통과한 것이었다.

로더 파일 내용으로 확인한 정답: 로더는 E = { Module: w, SetFullscreen, SendMessage, Quit, GetMetricsInfo } 를 만들고 w.postRun 에서 그 E 를 resolve 한다. 즉 createUnityInstance 가 resolve 한 인스턴스의 .Module 이 유일한 경로다. 브라우저에서 인스턴스 키를 읽어 [Module, SetFullscreen, SendMessage, Quit, GetMetricsInfo] 로 일치를 확인했다.

h3. 호출 시점

프레임워크의 _JS_SystemInfo_GetPreferredDevicePixelRatio 는 Module.matchWebGLToCanvasSize==false ? 1 : Module.devicePixelRatio || window.devicePixelRatio || 1 이다.

Module.devicePixelRatio 에 getter 를 걸어 읽힌 시각을 재었다 — 5초 동안 5회, 112890 / 113891 / 114891 / 115890 / 116892 ms. 약 1초 주기로 계속 다시 읽는다. 부팅 1회가 아니다. rAF 가 멈춘 동안에도 계속 읽혔으므로 렌더 루프가 아니라 타이머 경로다.

h3. 런타임 갱신이 먹는가

먹는다. Module.devicePixelRatio = 1.0 을 쓰자 2.5초 뒤 백버퍼가 1008x575 에서 672x383 으로 줄었고, 1.5 로 되돌리자 원래대로 돌아왔다. 렌더 루프도 멈추지 않았다.

캔버스 width/height 를 직접 바꾸면 rAF 가 멈춘다는 기존 실패 경로를 건드리지 않고 이 한 값만 바꾸면 된다는 뜻이다.

h3. 결정 — 2번 선택지

상한 1.5 자체는 그대로 둔다(이번 실측에서도 정확히 1.5 로 걸려 있었다). 고치는 것은 적용 시점이다 — 부팅 1회에서 밀도 변화마다로 바꿈. loader.ts 에 watchDevicePixelRatio 를 두고 UnityHost 가 인스턴스 수명에 맞춰 걸고 푸는 구조다.

1번(캔버스 CSS 크기)과 3번(콘솔 경고)은 버렸다. 2번이 실측으로 동작하는 것을 확인한 이상, 사용자 화면을 실제로 고치는 것은 그것 하나다.

h3. 검증

tsc · vitest 173파일 1130테스트 · build 전부 green. 단위 테스트 3건 추가. 프로덕션 산출물에 진단용 전역 잔존 0건 확인.

못 한 것: 상한보다 낮은 밀도로 바뀔 때의 실 브라우저 A/B. 이 환경의 브라우저 pane 이 내주는 밀도가 1.75·2.0 뿐이라 상한 아래 값을 만들 수 없었다. 그 구간은 단위 테스트와 위의 런타임 쓰기 실측 두 조각으로 덮여 있고, 한 번에 이어서 본 것은 아니다.

h3. 남은 것

backdrop-filter 비용 측정(worldHud.css:22 · :92 · consultationQuickAccess.css:20)은 이번에 못 했다. 프레임 타임 A/B 가 필요한데 브라우저 pane 이 숨겨지면 rAF 가 멈춰 측정이 성립하지 않는다. 이 티켓에 그대로 남긴다.
