## 설명

## 증상

`BoothLayoutConfigLinkIntegrationTest.aLaptopCarryingAConfigIdIsReportedAsUnverified` 가 죽는다.

```
DataIntegrityViolation could not execute statement
[ERROR: value too long for type character varying(30)]
[insert into users (account_type,avatar_code,created_at,nickname,status,...)]
  at BoothLayoutConfigLinkIntegrationTest.leasedOwner:216
```

**그 클래스만 단독 실행하면 10건 전부 통과한다.** 전체 스위트에서만 실패한다. `develop` 이 이 1건으로 red 상태이고, 러너가 없어 아무도 신호를 받지 못한다.

## 원인

`users.nickname` 은 `VARCHAR(30) NOT NULL UNIQUE` 다 (`V1__initial_schema.sql:6`). 그런데 테스트 헬퍼가 만드는 닉네임이 그 예산을 거의 다 쓴다.

```java
// backend/src/test/java/com/example/ssafesta/booth/BoothTestSupport.java:21
new User(prefix + SEQUENCE.incrementAndGet() + "_" + System.nanoTime())
```

`System.nanoTime()` 하나가 16~19자리를 차지한다. 실패한 호출부의 prefix 는 `"노트북configId"` 로 11자다.

| 실행 | 계산 | 결과 |
|---|---|---|
| 그 클래스만 | 11 + 순번 1자리 + 1 + nanoTime 17 = 30 | 상한에 딱 걸려 통과 |
| 전체 스위트 | 11 + 순번 3자리 + 1 + nanoTime 17 = 32 | **초과** |

즉 `SEQUENCE` 가 몇 자리인지가 통과와 실패를 가른다. 전체 스위트에서는 앞선 클래스들이 이미 수백 번 호출해 순번이 3자리가 되고, 그 두 글자 때문에 넘친다. 순서 의존이라 단독 실행으로는 재현되지 않는다.

## 해결

`System.nanoTime()` 을 뺀다. `SEQUENCE` 는 `AtomicLong` 으로 JVM 당 유일하고, `TestcontainersConfiguration` 의 PostgreSQL 컨테이너는 `withReuse` 를 쓰지 않아 실행마다 새로 뜬다 — 실행 간 닉네임 충돌이 애초에 불가능하다. `nanoTime` 은 존재하지 않는 위험을 막느라 30자 예산에서 17자를 쓰고 있었다.

```diff
-new User(prefix + SEQUENCE.incrementAndGet() + "_" + System.nanoTime())
+new User(prefix + SEQUENCE.incrementAndGet())
```

## 예방

테스트 픽스처가 만드는 문자열은 **컬럼 폭 안에 여유를 두고** 만든다. 유일성 재료를 두 개(순번 + 타임스탬프) 겹치면 폭을 넘기기 쉽고, 넘긴 뒤에도 실행 순서에 따라 통과해 버려서 회귀로 잡히지 않는다. 유일성이 이미 보장되는 재료가 있으면 하나로 충분하다.
