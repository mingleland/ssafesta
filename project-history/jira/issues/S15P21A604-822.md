## 설명

POST /ai/v1/conversations 가 demo 환경에서 500 Internal Server Error 반환.

원인 추정: ConversationService.create()(festa-ai/app/services/conversation_service.py)에서 Spring booth-access 응답의 leaseEndsAt(Java Instant, 나노초 정밀도 소수점 포함 가능: 예 2026-09-16T12:34:56.123456789Z)를 datetime.fromisoformat()으로 파싱하는데, Python datetime.fromisoformat은 소수점 6자리(마이크로초)까지만 지원해 7~9자리 나노초 문자열에서 ValueError 발생. try/except 없이 그대로 노출되어 FastAPI 기본 500으로 새어나감.

tests/ 전체에 이 케이스(나노초 소수점) 테스트가 없어 지금까지 발견되지 못함 — 테스트 픽스처는 전부 초 단위 깔끔한 문자열만 사용.

재현: demo.ssafesta.world 에서 AI 상담 위젯으로 대화 시작 시 500 (Network 탭 확인, 응답 본문 없음).

부수적으로 festa-ai/app/repositories/conversation_repository.py의 Redis 호출과 main.py 에 global exception handler 부재도 함께 확인 필요(미분류 예외가 조용히 빈 500으로 새는 구조 자체가 헌법상 실패 처리 원칙 위반).

## 댓글 (2)

### 김가현 · 2026-09-16 13:54 KST

정정: 처음 가설(leaseEndsAt 나노초 파싱 실패)은 테스트로 직접 확인해보니 틀렸습니다. Python datetime.fromisoformat()이 9자리 나노초 소수점도 정상 파싱(마이크로초 이하 절단)합니다 — 이 경로는 버그 아님.

실제 500의 정확한 트리거는 로그 접근이 없어 확정 못함(demo 서버 shell/log 접근 권한 없음). 대신 확인된 구조적 결함을 먼저 고침: main.py에 미분류 Exception을 잡는 global handler가 없어서(booth-access 통과 후 Redis 저장 등 어떤 단계에서든) 미분류 예외가 그대로 FastAPI 기본 빈 500으로 새고 있었음.

적용한 수정:
1. app/api/errors.py — unhandled_exception_handler 추가, INTERNAL_ERROR 코드의 JSON 500 반환 + logger.error(exc_info=exc)로 서버측 로그에 남김
2. main.py — app.add_exception_handler(Exception, unhandled_exception_handler) 등록
3. app/core/logging.py — StructuredLogFormatter가 exc_info가 있으면 traceback을 함께 찍도록 수정(원래는 exc_info 넣어도 traceback이 조용히 사라지는 별도 결함이었음)

이제는 demo에서 같은 500이 다시 나면 응답 본문에 code:INTERNAL_ERROR가 찍히고(Network 탭으로도 확인 가능), 서버 로그에는 실제 traceback이 남아 진짜 트리거(Redis인지 다른 것인지)를 다음 재현 때 확인할 수 있음. 진짜 트리거 확정은 별도 후속 이슈로 남김.
