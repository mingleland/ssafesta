## 설명

### 증상

같은 DB 연결에서 `POST /internal/ai/chunk-search` 를 반복하면 **6번째 호출부터 응답이 3초 statement 상한에 붙어 실패한다.** S15P21A604-521(최대 부하 검증)에서 발견했다.

최대 부하(문서 10개·chunk 145,646)에서 측정한 지연을 순서대로 보면 계단이 또렷하다.

```
[460, 564, 461, 420, 400, 394, 393, 395, 389, 3038, 3026, 3018, ...]
```

앞 9번은 400ms 대, 그 뒤로는 전부 3초를 넘고 **회복하지 않는다.** 100회 중 96회가 timeout 이었다.

### 원인

1. pgjdbc 가 `prepareThreshold=5` 기본값에 따라 같은 SQL 을 서버 측 prepared statement 로 승격시킨다
2. Postgres 가 그 시점부터 **generic plan** 으로 전환한다
3. generic plan 에서는 `CAST($1 AS vector)` 가 상수 폴딩되지 않는다. 그래서 약 3,000자짜리 질의 벡터 리터럴을 `vector_in` 이 **행마다 다시 파싱**한다. 이 식은 SELECT 목록과 `<> 'NaN'` 가드에 두 번 나온다
4. 비용 모델은 그 파싱 비용을 보지 못하므로 generic plan 이 항상 이긴다

세 가지로 교차 확인했다.

| 확인 | 결과 |
|---|---|
| 최대 부하에서 `EXPLAIN (ANALYZE, BUFFERS)` | Execution Time **465 / 521 / 665 ms** (parallel seq scan, 질의 벡터가 `Const` 로 폴딩됨) |
| `SET LOCAL plan_cache_mode = force_custom_plan` | 14/14 호출이 **565~765 ms**, 계단 없음 |
| 다시 `auto` 로 | 14/14 호출이 **3030 ms 이상** — 한 번 굳으면 유지된다 |

즉 순차 스캔 자체는 문제가 아니다. 정확 스캔은 145,646행에서 약 395ms 이고, 1초 예산까지 **약 368,000행**(부하 있는 장비에서 220,000행)의 여유가 있다.

### 영향

- 운영에서 RAG 검색이 같은 풀 연결로 6번째부터 3초 상한에 걸려 **사용자에게 500** 이 된다
- 심각도는 코퍼스 크기에 비례한다 — 행마다 파싱이므로 문서가 적으면 눈에 안 띄고, 상한(에이전트당 100MB) 근처에서는 확실히 터진다
- SC-006(P95 1초)·SC-007a(Top-K 포함률)를 지금 상태로는 측정할 수 없다. S15P21A604-521 의 stress 테스트 2건이 이 결함 때문에 붉다(기본 빌드·CI 에서는 `@Tag("stress")` 로 제외되므로 파이프라인은 영향 없음)

### 후보 해법

1. `MATERIALIZED` CTE 로 캐스트를 한 번만 하게 만든다(권장) — 질의 벡터를 CTE 에서 한 번 `vector` 로 바꿔 놓고 조인한다. 계획 모드와 무관하게 행별 파싱이 사라진다
2. `plan_cache_mode = force_custom_plan` 을 기존 `SET LOCAL enable_indexscan = off` 옆에 함께 건다 — 한 줄이지만 계획 재선택 비용을 매 호출 지불한다

### 완료 조건

- [ ] 같은 연결에서 100회 반복해도 계단이 생기지 않는다 (P95 가 warmup 구간과 같은 자리)
- [ ] 최대 부하에서 SC-006 P95 1초를 만족한다
- [ ] SC-007a Top-K 포함률을 실제로 측정할 수 있다 (지금은 전부 timeout 이라 0/100)
- [ ] `AiChunkSearchApiIntegrationTest` 22건 불변
