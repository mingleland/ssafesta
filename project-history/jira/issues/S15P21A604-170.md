## 설명

### 작업 목적

1회용 Connection Token 의 수명주기를 안전하게 관리한다.

### 작업 내용 (2026-08-25 축소)

- `jti` 유일성 보장 (발급마다 새 UUID)
- TTL **120초** 발급 — 계약값(`world-entry-token.md`). 이전 본문의 "예: 60s" 는 계약 확정 전 추정값이었다
- 전용 `CONNECTION_TOKEN_SECRET`(HS256) 로 서명 — Access Token 키와 분리

### 완료 조건

- [x] 만료 토큰 거부 — 발급 측 보장(TTL 120초) + 응답 `expiresAt` 이 토큰 `exp` 와 동일함을 테스트로 고정
- [x] `jti` 가 발급마다 달라짐을 테스트로 고정
- ~~사용된 토큰 재검증 거부~~ → **게임 서버 소유로 이관** (아래 근거)

### 이관 근거 — 재사용 차단은 BE 몫이 아니다 (2026-08-24 infra-003 계약)

- `contracts/world-entry-token.md` — "Before player creation it atomically consumes `jti`"
- `contracts/game-runtime.md` — replay ledger `/var/lib/festa-world/used-grants.log` (persistent volume)
- infra-003 **FR-013** — 게임 서버는 **접속 승인 시마다 Backend 에 조회해서는 안 된다**
- infra-003 **FR-014** — 사용된 식별자는 **새 릴리스 배포·컨테이너 교체·비정상 재기동 뒤에도** 원래 만료 시각까지 재사용 차단

BE 에 "사용된 토큰" 저장소를 만들면 ① 아무도 읽지 않거나 ② 읽게 만드는 순간 헌법 14조("Spring 장애가 월드 입장을 막으면 안 된다")를 위반한다. 그래서 이번 구현에 테이블·Redis 키·정리 스케줄러가 **0개**다. 만료 정리는 TTL 120초가 대신한다 — 정리할 상태 자체가 없다.

이 이슈 본문은 2026-08-21 작성이라 08-24 계약보다 낡았다. 재사용 차단 구현은 **S15P21A604-85**(Unity Approval 연동)의 게임 서버 측에서 다룬다.
