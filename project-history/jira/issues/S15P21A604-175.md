## 설명

### 작업 목적

Spring에서 FastAPI로 문서 처리를 위임하는 접수 경로를 구현한다.

**2026-09-02 범위 축소** — GitLab 이슈 #119의 새 계약에서 콜백이 5종으로 늘고 staging·fencing·finalize 트랜잭션이 붙어 한 티켓 분량을 넘었다. **결과 수신 절반은 S15P21A604-400으로 분리했다.** 이 티켓은 접수 위임만 남긴다.

**2026-09-09 개정** — 완료 조건 1번(Idempotency-Key)이 09-02 재설계로 낡았고, 문서 상태 PROCESSING·FAILED를 실제로 기록하는 일이 이 티켓 몫으로 확인되어 작업 내용에 추가했다. 아래 개정 사유 절 참조.

### 작업 내용

- Spring이 문서·소유권·임대·상태를 검증하고 Job을 먼저 생성한 뒤 FastAPI에 snapshot을 전달한다
- snapshot 필드 — jobId, documentId, boothId, agentId, 파일명·형식·크기·sourceHash, FastAPI가 원본을 읽을 수 있는 제한된 저장소 locator 또는 signed GET URL, embeddingModelId, vector dimension, chunker version/options, attempt_no, correlation/trace id
- 요청은 장시간 HTTP 연결을 유지하지 않고 `202 Accepted` 비동기 접수로 한다
- Job 행 중복 생성 방지는 V21 부분 유니크 인덱스(문서당 활성 Job 1개)가 맡는다 — 아래 개정 사유 참조
- 인증은 Spring에서 FastAPI로 가는 방향이므로 `INTERNAL_SPRING_TO_AI_TOKENS`
- **문서 상태 PROCESSING·FAILED를 기록한다** — 워커의 첫 신호(chunk batch 또는 heartbeat)에 PROCESSING, Job이 DEAD로 끝나면 FAILED

### 이 티켓에서 빠진 것

아래는 전부 S15P21A604-400이 맡는다.

- chunk batch·heartbeat·finalize·failed·cancel 수신
- `attempt_no` fencing (409 / 410)
- finalize 로컬 트랜잭션과 staging 정리
- lease 만료 Job 회수 스케줄러
- **실패 사유 문구** — FR-007이 정제된 사유를 요구하는데 워커의 failureCode가 50자 이하 자유 문자열이라 옮길 집합이 없다. writer와 함께 정해야 한다

문서 상태 DISABLED는 임대 만료가 쓰는 값이라 S15P21A604-496 몫이다.

### 완료 조건

- [x] 위임 호출이 `202 Accepted`로 즉시 반환하고 처리 완료를 기다리지 않는다
- [x] Job이 생성된 뒤에 위임 호출이 나간다 — 반대 순서면 결과가 돌아올 Job이 없다
- [x] 위임 호출 실패 시 Job이 재시도 가능한 상태로 남는다
- [x] snapshot이 OpenAPI 계약과 필드 단위로 일치한다
- [x] 한 문서에 활성 Job 행이 둘 생기지 않는다 (V21 부분 유니크 인덱스)
- [x] 워커의 첫 신호에 문서가 PROCESSING이 된다 — 위임을 보낸 순간이 아니다
- [x] Job이 DEAD로 끝나면 문서가 FAILED가 된다. RETRY_WAIT은 문서를 건드리지 않는다

### 2026-09-09 개정 사유 — Idempotency-Key

원래 완료 조건 1번은 "같은 Idempotency-Key 재전송이 Job을 중복 생성하지 않는다"였다. 이 티켓은 09-02 #119 재설계 이전에 쓰였고, 재설계가 그 요구를 헤더에서 스키마로 옮겼다. 저장소에도 계약(document-processing-api.yaml)에도 Idempotency-Key가 없고, 대신 V21이 문서당 활성 Job을 하나로 강제한다.

**다만 대체 범위를 정확히 적어 둔다.** 그 인덱스가 보장하는 것은 한 문서에 활성 Job 행이 둘 생기지 않는다까지다. 같은 Job의 HTTP 요청이 두 번 나가지 않는다는 뜻은 아니다 — dispatchQuietly가 실패로 판정한 요청을 sweeper가 재전송하므로 timeout이면 실제로 두 번 갈 수 있다. 그 중복은 계약의 jobId + attemptNo 멱등 수신이 흡수한다. exactly-once dispatch는 해결된 것이 아니라 필요하지 않은 것이다.

본문의 snapshot 필드 목록이 계약과 어긋나 **계약을 따랐습니다.** 구현은 MR !408 입니다.

본문은 2026-09-02 작성으로 GitLab #119 §2 를 옮긴 것이고, `document-processing-api.yaml` 이 2026-09-07 커밋 `2f140fcf`(S15P21A604-449, AI 파트)에서 v0.4.0 에서 v0.6.0 으로 좁아졌습니다. 계약에 없는 항목은 여섯입니다 — `Idempotency-Key` 헤더, `embeddingModelId`, vector dimension, chunker version/options, signed GET URL, correlation/trace id. 계약이 `additionalProperties: false` 이므로 본문대로 실으면 **422 로 거부됩니다.**

대신 계약은 `jobId` 와 `attemptNo` 를 required 로 요구하고, 원본은 signed URL 이 아니라 저장소 좌표(`storageProvider`·`storageBucket`·`objectKey`)로 넘깁니다. 202 에는 본문이 없습니다.

## 완료 조건 정정

"같은 `Idempotency-Key` 재전송이 Job 을 중복 생성하지 않는다" 는 **헤더 배관 없이 충족됩니다.**

멱등 기준이 `jobId + attemptNo` 로 바뀌었고, Job 중복 생성은 V21 의 `ix_ai_document_jobs_active_document`(문서당 활성 Job 1개)가 DB 수준에서 막습니다. 새 헤더도 새 컬럼도 마이그레이션도 필요하지 않았습니다.

나머지 완료 조건 넷은 그대로 충족했습니다. 202 즉시 반환, Job 생성 뒤 위임, 위임 실패 시 재시도 가능 상태 유지, snapshot 이 계약과 필드 단위로 일치입니다.

## 범위에서 하나 늘렸습니다

재배차 스케줄러를 함께 넣었습니다. 본문에는 없는데, 없으면 즉시 호출이 실패한 Job 이 `QUEUED` 로 남고 활성 Job 인덱스가 그 문서의 새 Job 을 막아 **재업로드로도 풀 수 없는 영구 정지**가 됩니다. S15P21A604-487 이 같은 모양을 한 층 위에서 낸 직후라 되풀이하지 않았습니다. `ix_ai_document_jobs_pickup(status, next_retry_at)` 이 정확히 그 질의를 위한 인덱스여서 새 스키마는 필요 없었습니다.

## 본문을 고치지 않은 이유

설명 전문 재작성이 한글 산문을 깨뜨린 적이 있어 코멘트로 남깁니다.

## 결선 상태

FastAPI 쪽은 S15P21A604-124 로 계약 구현과 cutover 가 끝나 있어 Spring 에서 손볼 것이 없었습니다.

남은 것은 인프라 하나입니다. `back` 과 `ai` 가 각각 별개 Compose 프로젝트라 서로의 서비스 이름을 해석하지 못하고, 이것은 BE 에서 AI 로 가는 위임만이 아니라 **AI 에서 BE 로 오는 결과 회신도 함께 막습니다.** GitLab #144 로 올렸습니다. 경로가 열리면 문서 업로드로 끝까지 흐르는지 확인하고 공유하겠습니다.

## 검증

전체 843건 통과입니다 (develop 기준선 813 + 30). 실제 FastAPI 호출은 검증하지 않았습니다 — 네트워크 경로가 없어 페이크까지가 이 티켓의 경계입니다.

새 기능이라 "구현 전 실패" 확인이 자동으로 성립하므로, 지키려는 규칙 쪽을 깨서 단정이 물리는지 봤습니다. `status != ACCEPTED` 를 `status >= 400` 으로 바꾸면 3건, 송신 토큰을 마지막 값으로 바꾸면 2건, 재배차에 `attempt_no + 1` 을 넣으면 1건, 상태 필터에 `RUNNING` 을 더하면 1건이 각각 실패합니다.
