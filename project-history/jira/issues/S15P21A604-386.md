## 설명

## 작업 목적

같은 문서의 수정본을 올리는 경로를 만든다. spec 007 FR-019는 "수정본 교체는 기존 `documentId`를 지정하는 명시적 요청으로 처리해야 한다"고 요구하는데, 그 경로가 없다.

## 왜 별도 티켓인가

`S15P21A604-106`(Document 업로드 API)의 완료조건은 셋이고 교체가 없다.

- 형식·크기·상한 위반 4xx 계약 준수
- R2 객체·DB 레코드 정합
- 타 Booth Owner 업로드 차단

작업 내용도 "POST 문서 업로드"뿐이다. -106 구현은 `AiDocumentController`에 `upload-url`·`complete` 둘만 두었고 서비스에도 교체 흔적이 없다. 범위 밖이므로 여기로 분리한다.

## 현재 동작 — 교체가 되지 않는 이유

`FR-019`가 중복을 "재처리하지 않는다"로 못박아 두었고, 구현은 `ux_ai_documents_agent_active_sha`(V17 부분 UNIQUE)로 그것을 강제한다. 같은 파일을 다시 올리면 `duplicate: true`가 나오고 새 문서가 만들어지지 않는다. **내용이 바뀐 수정본은 SHA가 달라 새 문서로 들어가고, 옛 문서가 그대로 남아 10개 상한을 함께 먹는다.** 운영자가 옛 것을 지울 방법도 아직 없다.

## 작업 내용

- 기존 `documentId`를 지정하는 교체 요청 endpoint (`AiDocumentController`)
- 교체 시 옛 문서·옛 object의 처리 — 상태 전이와 정리 시점 확정
- 교체와 `EXPIRED` 복구(FR-027)·provider 전환(FR-030)의 상호작용 정의
- 상한(FR-018 10개·100MB) 계산에서 교체된 옛 문서를 어떻게 셀지

## 완료 조건

- [ ] 기존 `documentId` 지정 교체가 새 문서를 만들지 않고 같은 문서를 갱신한다
- [ ] 교체 후 옛 원본이 정리되거나 보존 정책이 명시된다
- [ ] 타 Booth·비소유자 교체 차단
- [ ] `specs/007-ai-agent-document/tasks.md`의 T030·T041·T043 완료 처리

1. 문서 업로드 → 내용이 다른 수정본을 같은 `documentId`로 교체 → 문서 수가 늘지 않는다
2. 타인 문서 교체 시도 → 차단
3. 교체 후 상한 계산이 옛 문서를 중복으로 세지 않는다
