## 설명

## 배경

전역 관리자 개념이 저장소에 없다. `ROLE_ADMIN`·`isAdmin`·`AdminGuard` 검색 결과가 0건이고, 권한 판정은 부스 단위 `BoothAccessGuard`·`StaffAccessGuard` 뿐이다. 그 결과 다음이 모두 막혀 있다.

- 계정 정지·해제(`AccountLifecycleService.suspend/unsuspend`)와 코인 관리자 조정(`WalletService.adjustByAdmin`)은 서비스·테이블·테스트까지 구현되어 있으나 HTTP 경로가 없어 도달 불가하다. spec 003 계약 문서에 "HTTP 노출 없음 (U-01 확정까지 보류)"로 명문화되어 있다.
- 신고 도메인이 존재하지 않아 강제 비공개·강제 회수·닉네임 강제 변경의 입력이 없다.
- 저장소 쿼터 초과 응답이 사용자에게 "관리자에게 문의해 주세요"라고 안내하지만, 문의를 받은 관리자가 할 수 있는 조치가 없다.

이 티켓은 admin 권한 모델(docs/26, S15P21A604-165·-680)을 확정하고 그 위에 운영 기능을 얹는다.

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 관리자 판정 | `users.account_type = 'ADMIN'`을 매 요청 DB 조회. JWT `role`은 `MEMBER` 유지 |
| 초기 관리자 | 닉네임 `구글 황덕` + provider `GOOGLE` 계정을 마이그레이션으로 승격 |
| 마스터 계정 | 위 계정에 `users.is_master = TRUE`. 강등·정지·탈퇴·닉네임 강제 변경·코인 조정·강제 로그아웃 대상이 될 수 없다 |
| 관리자 증식 | 관리자가 다른 회원을 승격·강등할 수 있다. 이력은 `admin_grants`에 남긴다 |
| 강제 회수 환불 | 환불하지 않는다. S15P21A604-735(조기 반납, 환불 없음)와 같은 규칙. 사안별 보정은 `ADMIN_ADJUSTMENT`로 처리 |
| 이벤트 설문 응모자 | 관리자 명단 조회를 허용한다. spec 010 FR-009·SC-003 익명 계약에 admin 예외를 명문화하는 문서 개정이 선행 |
| 경품 | 착수 보류. 수량 규칙만 "1인 1개"로 확정(기존 멱등키 `PURCHASE:{userId}:{itemId}`를 그대로 쓴다) |

## 왜 JWT role을 바꾸지 않는가

`MemberPrincipal`이 `"MEMBER".equals(role)`로 판정하고 컨트롤러 20여 곳이 이를 경유한다. `role`을 `ADMIN`으로 발급하면 관리자 토큰이 게스트로 읽혀 본인의 지갑·부스·게임까지 `403 MEMBER_ONLY`가 된다. DB 조회 방식은 강등이 즉시 반영되는 이점도 있다.

## 불변식

1. 마지막 관리자는 강등·정지·탈퇴할 수 없다
2. 마스터 계정은 어떤 관리자 동작의 대상도 될 수 없다(조회는 허용). 본인 탈퇴도 막는다
3. 마스터 지정 API는 만들지 않는다 — 마이그레이션이 유일한 경로다
4. `is_master`는 최대 1행(부분 유니크 인덱스로 DB가 보장)
5. 마스터 대상 신고는 접수는 허용하고 조치에서 거부한다

## 반드시 함께 고쳐야 하는 기존 코드

- `BoothRepository.findByOwnerUserId`가 `Optional`이다. 운영 부스가 2개 이상이면 `IncorrectResultSizeDataAccessException`이 난다. 호출처 `BoothLeaseService.ownBooth`, `BoothQueryService.findMyBooth` 두 곳을 `operations = false` 조건으로 좁힌다
- `AccountDeletionService`에 `reports`·`admin_grants` 정리를 추가한다(둘 다 users FK). 누락하면 탈퇴가 FK 위반으로 실패한다
- 운영 부스를 보유한 계정의 탈퇴를 거부한다
- 컨트롤러가 `signedAmount == 0`·빈 멱등키를 직접 검증한다. `WalletService`는 `IllegalArgumentException`을 던지는데 `GlobalExceptionHandler`에 매핑이 없어 500이 된다

**1. 마이그레이션 번호** — 본문의 `V33` 은 틀렸습니다. `origin/develop` 최신이 `V35__project_facts.sql` 이므로 실제로는 **V36(권한·감사) · V37(운영 부스) · V38(신고)** 입니다. 시드가 0행으로 소진됐을 때의 복구본은 V37 이 아니라 **V39 이후**이며, provider(`GOOGLE`) 조건은 그대로 유지합니다.

**2. 감사 테이블** — `admin_grants` 대신 `admin_actions` 통합 테이블 하나로 갑니다. 승격·강등도 여기 들어갑니다. 대상·행위자는 **FK 없이 id 만** 저장합니다(코인 원장의 `reference_id` 와 같은 관례). FK 를 걸면 `AccountDeletionService` 의 마지막 `DELETE FROM users` 가 막혀 승격 이력이 있는 계정이 탈퇴하지 못합니다. 같은 이유로 `reports` 에도 FK 를 두지 않으므로 탈퇴 정리 코드 변경은 필요 없습니다.

**3. 범위 조정** — "만료 부스 편집"(구 기능 41)은 이번 범위에서 내립니다. `BoothAccessGuard.requireActiveLease` 는 행위자 인자가 없고 방문자 공개 조회도 쓰는 공용 메서드라, 관리자 예외를 넣으려면 의미를 바꿔야 합니다. 강제 회수·강제 비공개로 실무 요구가 대부분 덮이므로 별도 이슈로 둡니다.

**구현 중 반드시 지킬 것 세 가지** (리뷰에서 확인된 함정)

- 강제 회수 조회는 `findActiveByBoothIdForUpdate(boothId)` 로 **시간 조건 없이 **`status = ACTIVE` 만 봅니다. 기존 `findValidByBoothId` 는 `endsAt > now` 조건이 있어 "시간은 지났지만 스위퍼가 아직 안 집은" 임대를 놓치고, 그러면 회수했다고 응답하면서 실제로는 `ACTIVE` 가 남아 재임대가 막힙니다.

## 착수 조사에서 나온 것 — 둘 다 "노출 작업" 이 아니었습니다

서비스·테이블·테스트가 완비라 컨트롤러만 붙이면 되는 줄 알았는데, 코드를 끝까지 읽으니 함께 고쳐야 할 것이 나왔습니다. 두 이슈 본문에 각각 적었고 여기에는 요약만 남깁니다.

**공통**

- `AdminActionRecorder.record()` 가 `@Transactional(propagation = MANDATORY)` 인데 컨트롤러에는 트랜잭션이 없습니다. 컨트롤러에서 감사를 남기면 예외가 납니다 — `AdminAccountService.promote` 와 같은 오케스트레이션 서비스가 필요합니다.
- 멱등 재요청이 원장뿐 아니라 `admin_actions` 도 늘리지 않아야 합니다.

`-165` 쪽

- 마지막 관리자 판정(`countByAccountType(ADMIN) <= 1`)이 두 군데 틀렸습니다. 평범한 count 라 동시 요청에 0명이 될 수 있고, `accountType` 과 `status` 가 별도 필드라 **정지된 관리자도 ADMIN 으로 세어집니다.** `account_type = ADMIN AND status = ACTIVE` 를 `ORDER BY id ASC FOR UPDATE` 로 잠그고 세는 것으로 바꾸고, 기존 `demote` 의 판정도 같이 고칩니다.
- 잠금 순서는 **활성 관리자 집합(id 오름차순) → 대상 사용자** 입니다. 반대로 하면 관리자 A·B 를 동시에 정지할 때 교착합니다.
- `AccountLifecycleService.change()` 에 같은 상태 검사가 없어 이미 정지된 계정을 다시 정지하면 `SUSPENDED → SUSPENDED` 이력이 쌓입니다. 대상 행 잠금도 없습니다.
- `AccountStatusHistoryRepository` 가 쿼리 0개인 빈 인터페이스라 정지 이력 조회는 새로 만들어야 합니다.

`-806` 쪽

- 기존 멱등키 관례(`REASON:REFERENCE_TYPE:{id}`)를 그대로 쓰면 `ADMIN_ADJUSTMENT:ADMIN_USER:{actorUserId}` 가 되어 **같은 관리자의 두 번째 조정부터 전부 첫 요청으로 흡수됩니다.** `ADMIN_ADJUSTMENT:{targetUserId}:{operationId}` 로 갈랐습니다.
- `WalletService.applyEntry` 가 기존 키를 찾으면 지갑 주인만 확인하고 금액·사유를 비교하지 않습니다. 관리자 조정은 키를 클라이언트가 만드는 첫 경로라 같은 키에 다른 금액이 오면 조용히 통과합니다. **공용 경로에 payload 비교를 넣고 **`409 IDEMPOTENCY_CONFLICT` 를 신설합니다.
- `signedAmount == Integer.MIN_VALUE` 는 `-signedAmount` 오버플로로 잔액 관문을 통과해 500 이 됩니다. `signedAmount == 0` 도 `GlobalExceptionHandler` 매핑이 없어 500 입니다.
