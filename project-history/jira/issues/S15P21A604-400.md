## 설명

### 작업 목적

S15P21A604-175가 "처리 접수 위임"과 "콜백 수신"을 함께 안고 있는데, GitLab 이슈 #119의 새 계약에서 콜백이 5종으로 늘고 staging·fencing·finalize 트랜잭션이 붙어 한 티켓 분량을 넘는다. 수신 쪽 절반을 분리한다.

**S15P21A604-175는 처리 접수 위임(202 Accepted·Idempotency-Key)만 남긴다.**

### 확정된 계약 (GitLab 이슈 #119, 2026-09-02 AI 파트 회신)

- batch 상한 chunk 200개 / 8MB (1536차원 float 하나가 약 6KB)
- finalize 트랜잭션 순서: 검증 → 기존 chunk 교체 → `searchable = true` → Job `SUCCEEDED` → Document `READY`
- fencing은 `attempt_no` 기반. 불일치 409, 삭제·취소된 Job 410
- `max_retries` 기본 3
- staging은 `(job_id, batch_seq, chunk_no)` PK에 `ON CONFLICT DO NOTHING`으로 멱등 수신. finalize 성공·CANCELLED·DEAD 시 `DELETE WHERE job_id = :id`로 정리하고 별도 TTL 스케줄러를 두지 않는다
- `callback_*` 컬럼은 스키마에서 제외됐다 — finalize의 HTTP 응답이 곧 전달 확인이다

### 작업 내용

- **chunk batch 수신** — `jobId`, `batchSeq`, chunks, checksum. staging에 멱등 upsert
- **heartbeat 수신** — lease 연장 전용, 진행률 갱신
- **finalize 수신** — staging 개수·`source_hash`·`embedding_model_id`·차원을 검증한 뒤 위 순서를 **하나의 로컬 트랜잭션**으로 확정. 같은 DB가 되면서 FR-040이 경계했던 분산 트랜잭션 문제가 사라진다
- **failed 수신** — retryable 여부, 정제된 failure code/message
- **cancel** — 문서 삭제·비활성화·임대 만료 시 Job `CANCELLED` 처리, staging 정리, 실행 중 FastAPI 작업에 멱등 cancel 전송
- `attempt_no` fencing — batch·finalize 요청의 값이 Job의 현재 값과 다르면 409, 삭제·취소된 Job은 410
- lease 만료 Job 회수 스케줄러 — `attempt_no`를 올리고 재큐잉. 늦게 도착한 이전 attempt 결과는 409로 걸린다
- staging에는 `booth_id`·`agent_id`가 없다. finalize에서 chunk로 옮길 때 `ai_document_jobs`에서 가져온다 (chunk 테이블은 둘 다 NOT NULL)
- OpenAPI 계약에 DTO·멱등성·오류 코드 고정

### 완료 조건

- [ ] 같은 batch·finalize 재전송이 멱등이다 — chunk가 중복 적재되지 않는다
- [ ] out-of-order batch가 finalize 개수 검증에서 걸린다
- [ ] 이전 attempt의 늦은 batch·finalize가 409로 거부된다
- [ ] 삭제·취소된 Job의 결과가 410으로 거부된다
- [ ] finalize 도중 실패 시 기존 chunk가 남고 Document가 `READY`로 넘어가지 않는다
- [ ] cancel 전달이 실패해도 늦은 결과가 fencing으로 반영되지 않는다
- [ ] lease 만료 Job이 회수되어 `attempt_no`가 오른다
- [ ] batch 상한(200개 / 8MB) 초과 요청이 거부된다
- [ ] DTO·오류 코드가 OpenAPI 계약과 필드 단위로 일치한다

### 선행 작업 / Dependency

- BLOCKED BY: S15P21A604-397 (staging 테이블·Job 테이블)
- 관련: S15P21A604-175(접수 위임 — 범위 축소), S15P21A604-174(Document 상태 전이 — READY 전이가 finalize 트랜잭션 안에서 일어난다), S15P21A604-125 [AI] Spring 상태 콜백 클라이언트(대응 구현)

### 참고

GitLab 이슈 #119 §3·§4 및 2026-09-02 회신 3-2·3-3 · specs/007 contracts/

### 테스트 방법

1. batch 재전송 · out-of-order · 중복 finalize
2. 이전 `attempt_no`로 batch·finalize 전송 시 409
3. 삭제된 문서의 Job에 finalize 시 410
4. finalize 트랜잭션 중간 실패를 주입해 기존 chunk 보존 확인
5. lease 만료 후 회수 → 이전 worker 결과 거부 확인
6. batch 상한 경계(200개 / 201개, 8MB 초과)
