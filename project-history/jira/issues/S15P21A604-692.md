## 설명

### 증상

`S15P21A604-686` 이 넣은 인바운드 정책이 `StompCommand` 로 분기하는데, **브로커는 **`SimpMessageType` 으로 판단한다. 그 어긋남 때문에 두 프레임이 정책을 그냥 지나간다.

전 command 를 인터셉터에 태워 확인한 결과다.

```
STOMP    simpType=CONNECT  -> PASSED   ← 토큰 검증 없이 연결
CONNECT  simpType=CONNECT  -> REFUSED
SEND     simpType=MESSAGE  -> REFUSED
MESSAGE  simpType=MESSAGE  -> PASSED   ← SEND 차단 우회
```

### 우회 1 — `STOMP` 프레임으로 인증을 건너뛴다

STOMP 1.2 는 `STOMP` 를 `CONNECT` 의 동의어로 규정한다. Spring 은 그것을 별도 enum 상수 `StompCommand.STOMP` 로 두고 `SimpMessageType.CONNECT` 로 매핑한다.

정책이 `StompCommand.CONNECT` 만 보므로, 클라이언트가 `CONNECT` 대신 `STOMP` 프레임을 보내면 **WS Token 검증을 거치지 않고 연결이 성립한다.** 그 연결은 `Principal` 도 없다.

### 우회 2 — `MESSAGE` 프레임으로 SEND 차단을 지나간다

`MESSAGE` 는 원래 서버 → 클라이언트 방향이지만, 클라이언트가 그 command 로 보내면 `simpType` 이 `SEND` 와 똑같이 `MESSAGE` 다. 브로커는 `SimpMessageType` 을 보고 처리하므로 `/topic/**` 으로 그대로 나간다.

`S15P21A604-686` 이 막으려던 위조가 이 경로로 살아 있다.

### 원인

분기 기준이 틀렸다. `StompCommand` 는 와이어 표기이고 정책이 실제로 다뤄야 하는 것은 `SimpMessageType` 이다 — 브로커·핸들러가 그 값으로 동작한다.

### 고칠 방향

1. `SimpMessageType` 으로 분기한다. `CONNECT` → 토큰 검증(`STOMP`·`CONNECT` 둘 다 잡힌다), `MESSAGE` → allowlist(`SEND`·`MESSAGE` 둘 다), `SUBSCRIBE` → raw `/queue` 거부
2. **서버 전용 command 는 인바운드에서 거부한다.** `CONNECTED`·`MESSAGE`·`RECEIPT`·`ERROR` 가 클라이언트에서 오는 것은 정상 경로가 아니다

### 완료 조건

- [ ] `STOMP` 프레임이 토큰 없이 연결되지 않는다
- [ ] 유효한 토큰을 실은 `STOMP` 프레임은 `CONNECT` 와 똑같이 연결되고 `Principal` 이 심긴다
- [ ] 클라이언트가 보낸 `MESSAGE` 프레임이 거부된다
- [ ] 서버 전용 command(`CONNECTED`·`RECEIPT`·`ERROR`)가 인바운드에서 거부된다
- [ ] allowlist 에 오른 `SEND /app/world/chat` 은 그대로 통과한다
- [ ] 기존 계약 구독·`UNSUBSCRIBE`·`DISCONNECT` 는 그대로 통과한다
- [ ] **전 command 를 훑는 테스트**가 있어 새 command 가 생겨도 판정 없이 통과하지 않는다

### 왜 기존 테스트가 못 잡았나

`S15P21A604-686`·`-687` 의 테스트가 **정상 클라이언트가 쓰는 command 만** 고정했다. `SEND`·`SUBSCRIBE`·`UNSUBSCRIBE`·`DISCONNECT` 는 검증하는데, 규격에는 있고 정상 클라이언트는 안 쓰는 `STOMP`·`MESSAGE` 는 아무도 보지 않았다. 그래서 command 표를 전수로 도는 테스트를 완료 조건에 넣는다.
