## 설명

### 작업 목적

`spring-storage-reconciliation-api.yaml:32` 에 결론이 안 난 문장이 그대로 남아 있다.

> 요청에 targetBucket 을 넣어 이 추론을 없애는 안은 #100에서 논의 중이다.

계약에 "논의 중" 이 남으면 다음 사람이 이 논의를 다시 연다. 인프라가 2026-09-11 에 **닫지 말라**고 회신했다.

> `targetBucket` 논의는 닫지 않겠습니다. 현재 R2 단독 활성은 정상 운영 상태일 뿐이며, MinIO 는 R2 장기 장애 시 운영자 승인 후 전환하는 fallback 으로 남아 있습니다. 따라서 provider 별 bucket 이름이 달라질 수 있는 경로가 아직 존재합니다. (…) Infra `storage-failover.sh` 구현 전에 `targetBucket` 계약을 확정·반영하는 방향으로 유지하겠습니다.

단일 run lock(`S15P21A604-215`·`-629` 로 확정)과는 **다른 문제다.** lock 은 A → B → A 동시 실행 구간을 막는 전제이고, target bucket 은 결과가 어느 provider·bucket 으로 이동해야 하는지를 요청 자체에 명시하는 계약 문제다. 서로 대체되지 않는다.

### 현재 동작 (그대로 유지 중)

Spring 이 **배포 설정의 버킷을 권위**로 삼는다. 문서 행의 버킷이 설정과 다르면 추측하지 않고 `500 RECONCILIATION_CONFIGURATION_ERROR` 로 멈춘다. 반영 시 문서의 `storageProvider` 와 `storageBucket` 을 함께 옮긴다 — 두 provider 의 버킷 이름이 다른 배포에서 provider 만 바꾸면 이후 읽기·삭제가 존재하지 않는 좌표를 친다.

이 방어는 `targetBucket` 이 들어올 때까지 그대로 둔다(인프라 요청).

### 작업 내용

1. `targetBucket` 을 요청 스키마에 넣을지 확정하고 `spring-storage-reconciliation-api.yaml` 을 그 결론으로 고친다 — **어느 쪽이든 "논의 중" 문장은 없앤다**
2. 넣는 쪽으로 가면
   
   - 요청 필드 추가 (`maxLength` 는 원본 컬럼 폭 기준으로 다른 필드와 같은 방식)
   - 반영 시 설정 추론 대신 요청 값을 쓴다
   - 요청 값과 배포 설정이 어긋날 때의 응답을 정한다 — 지금의 `RECONCILIATION_CONFIGURATION_ERROR` 를 유지할지, 요청 오류(422)로 볼지
   - 계약 버전을 올린다 (현재 0.2.0)
3. 인프라 송신부(`storage-failover.sh`)가 붙기 전에 끝나야 한다 — 뒤에 하면 이미 보내고 있는 요청의 계약을 바꾸는 일이 된다
