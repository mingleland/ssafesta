## 설명

## 배경

관리자 콘솔에는 `강제 비공개`(POST /api/v1/admin/booths/{boothId}/unpublish)만 있다. 이 동작은 `booths.published_layout_version` 포인터만 null 로 만들고 임대는 건드리지 않는다. 슬롯 점유 판정은 임대만 보므로(`status=ACTIVE AND ends_at > now`), 비공개 처리 후에도 `GET /api/v1/booth-slots` 는 그 슬롯을 계속 `OCCUPIED` 로 보고한다. 이는 현재 설계대로의 동작이며, 자리를 실제로 비우는 경로는 회원 본인의 반납과 기간 만료뿐이다.

운영에 필요한 것은 신고 대응으로 **관리자가 자리를 회수하는 수단**이다. 지금은 존재하지 않는다.

## 범위

`POST /api/v1/admin/booth-slots/{slotId}/lease/release`

- 본문: `{ "reason": "..." }` — 필수, 최대 500자 (`unpublish` 와 동일한 형식)
- 키는 slotId. 임대 행은 슬롯 단위이고(ux_booth_leases_active_slot), 관리자는 여러 부스를 동시에 보유할 수 있어 boothId 로는 대상 자리가 정해지지 않는다. 관리자 목록 응답에 slotId 가 이미 있다.
- 관리자 전용(AdminGuard). 마스터 계정 소유 부스는 `MASTER_PROTECTED` 로 거부한다.
- 동시성: 기존 반납 경로와 같은 직렬화(임차인 지갑 행 잠금 → `findActiveBySlotIdForUpdate` → 유효성 재조회).
- 감사 로그: `admin_actions` 에 `BOOTH_LEASE_RELEASE` / target BOOTH / detail=사유. action 이 문자열 컬럼이므로 마이그레이션 불필요.

## 확정된 정책

1. **환불 없음.** spec 004 D06(변심 환불 없음)을 강제 반납에도 적용한다. 지갑을 건드리지 않는다.
2. **부스를 통째로 삭제한다 — 회원 부스도 예외가 아니다.** 슬롯 연결만 끊고 콘텐츠를 보존하는 현재 회원 경로(spec 004 FR-010 / C-01)를 강제 반납에서는 적용하지 않는다. 관리자 소유 부스에만 적용되던 삭제 경로(AdminBoothPurger, S15P21A604-905)를 강제 반납의 단일 경로로 쓴다.
   
   ⚠️ 이 삭제는 그 부스에 남은 **방문자 생성 데이터까지 지운다** — 설문 응답·답변, 방문 이벤트와 일별 통계, 상담 내역과 메시지, 프로젝트와 좋아요, AI 에이전트·문서·청크·Job, 레이아웃 Draft·공개 이력, 직원·초대. `booths` 를 참조하는 15개 외래키 중 cascade 인 것이 없어, 이들을 남기는 삭제는 애초에 실행되지 않는다. 복구 경로는 없다.
   
   → spec 004 FR-010 개정과 파트 통보가 함께 필요하다.

## 응답 계약

- 204 — 반납 완료(슬롯 즉시 AVAILABLE)
- 400 `VALIDATION_FAILED` — 사유가 비었거나 500자 초과
- 403 `FORBIDDEN` — 관리자가 아니다 / `MASTER_PROTECTED` — 마스터 소유 부스다
- 404 `BOOTH_SLOT_NOT_FOUND` — 그런 슬롯이 없다 / `ACTIVE_LEASE_NOT_FOUND` — 회수할 활성 임대가 없다

## 테스트

- 회원 임대를 강제 반납 → 슬롯이 `AVAILABLE`, 부스 행과 콘텐츠 행이 사라진다
- 관리자 소유 부스를 강제 반납 → 기존 동작과 동일(부스 삭제)
- 비관리자 403, 마스터 소유 부스 403, 임대 없는 슬롯 404
- 감사 행 1건 기록, 임차인 잔액 불변

## 범위 외 (별건)

- 관리자 콘솔의 `강제 반납` 버튼 (FE)
- `entryAvailable` 이 게시 상태를 반영하지 않는 문제 — 현재 점유 중이면 항상 true 로 고정이라 강제 비공개 결과가 어느 응답에도 드러나지 않는다
