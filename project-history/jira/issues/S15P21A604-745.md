## 설명

QA 발견 — demo 환경에서 AI 직원 등록후 문서 업로드(3단계: grant→PUT→complete)는 성공하지만(즉 S15P21A604-729 R2 CORS 건은 해결된 것으로 보임), 문서가 processing_status=QUEUED에서 멈춰 READY로 안 넘어간다. AI 직원이 이 문서를 답변 근거로 못 쓰는 상태로 이어짐(보고자 표현: "AI 직원을 활성화할 수 없음").

코드 검토(실행 재현은 안 함): QUEUED인 Job은 30초 간격 스케줄러(DocumentJobDispatchSweeper, backend/src/main/java/com/example/ssafesta/ai/DocumentJobDispatchSweeper.java)가 집어서 FastAPI POST /ai/v1/documents/process 로 위임한다(HttpDocumentProcessingClient). 이 호출이 계속 실패하면 Job은 QUEUED에 그대로 남고, 30분이 넘으면 같은 파일 안에서 warn이 error로 에스칼레이션된다(45-55번). 즉 QUEUED에서 멈췄다는 건 이 위임 호출이 계속 실패하고 있다는 뜻이다. R2 CORS(-729) 해결되면서 업로드 자체는 되는 것을 보면, 이번에는 Spring↔FastAPI 간 내부 호출이 안 되는 거라 예상하며(festa-ai 닿거나 INTERNAL_SPRING_TO_AI_TOKENS/INTERNAL_AI_TO_SPRING_TOKENS 불일치), R2 CORS와 같은 계열의 demo 환경 드리프트로 보인다.

확인 요청(demo 로그·배포 접근 권한 있는 분):
1. demo의 festa-ai(dev/demo AI 컨테이너, internalEndpoint http://ai:8000, healthCheckRef ai-readiness)가 실제 띄 있고 healthy한지.
2. demo Spring 로그에서 다음 메시지를 grep: "문서 처리 위임 호출이 실패했습니다"(연결 자체 실패 — festa-ai 닿거나 네트워크 차단) 또는 "문서 처리 위임 요청이 거부되었습니다 ... status="(응답은 받았지만 202가 아님 — 401이면 토큰 불일치, 422면 계약 불일치). 30분 넘게 전달 안된 Job은 error로 에스칼레이션되므로 그 메시지를 먼저 찾으면 빠름.
3. 토큰이 원인이면 demo의 backend .env INTERNAL_SPRING_TO_AI_TOKENS 값과 festa-ai .env 같은 키 값이 일치하는지 대조.
4. 또는 DB에서 해당 documentId의 ai_document_jobs 행을 직접 조회해 status·attempt_no·last_error_code·last_error 컴럼을 확인하면 더 빠르게 원인이 나온다.
