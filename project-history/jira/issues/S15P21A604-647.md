## 설명

### 작업 목적

`-386`·`-521`·`-637` 세 구현이 각각 spec 007 개정을 선행으로 요구한다. 셋 다 `specs/007-ai-agent-document/spec.md` 한 파일을 고치고 plan/tasks 재생성을 부르므로, 따로 진행하면 서로 텍스트 충돌한다. 한 MR로 묶어 세 게이트를 동시에 연다.

### 1. 교체된 원본의 상태 의미 (-386 게이트)

현재 `spec.md`의 상태표는 `EXPIRED`를 "업로드 미완료로 만료됨. 보존 기간 안에는 완료 요청으로 복구 가능"으로 정의한다. 교체된 원본은 복구 불가(410)라 그대로 쓰면 의미가 충돌한다.

두 갈래 중 하나를 확정한다.

- **(추천) **`EXPIRED` + `replaced_at`을 하위 상태로 명문화 — `replaced_at`이 찍힌 `EXPIRED`는 복구 대상이 아니라고 적는다. 이 안을 택하면 FR-006·FR-027·FR-028·State Model·SC-010까지 함께 갱신한다
- `REPLACED` 상태 신설 — 의미는 또렷하지만 V24 CHECK 개정, 두 스윕의 predicate, OpenAPI, FE 상태표, 기존 테스트가 모두 따라온다

### 2. SC-007 분해 + 규모 확정 (-521 게이트)

현재 SC-007은 "정답 근거 문서 Top-K 포함률 95%"이고 T067이 `festa-ai` 소관이다. 그런데 Spring의 chunk-search는 `SET LOCAL enable_indexscan = off`로 정확 스캔을 강제하므로 BE 쪽 포함률은 구조상 100%거나 버그다. 95%라는 비율을 잴 대상이 아니다.

- `SC-007a`(BE) — 최대 부하에서 정확 스캔이 유지되어 정답 청크가 Top-K에 100% 들어온다
- `SC-007b`(AI) — 자연어 질의의 의미 회수율 95%
- T067 소유권 정리 — 의미 품질은 T067(AI), BE Testcontainers 몫은 `-521`
- **100MB에 해당하는 총 chunk 수 **`N_total`을 확정한다 — 대표 코퍼스 실측값 또는 보수적 최대치. 이 값이 `-521` 픽스처 상수가 된다

### 3. FAILED 원본 삭제 정책 (-637 게이트)

MR !689가 `docs/26`에만 기록했다. spec 007(FR-028 계열)·Object Storage 계약·tasks에 반영한다.

- `updated_at` 기준 7일 유예 후 EXPIRED와 같은 스윕 경로에서 자동 삭제
- 물리 삭제는 트랜잭션 밖이라 사후 조건부 UPDATE로 되돌릴 수 없다. 조회와 삭제 사이 재처리가 끼는 경쟁은 **허용하고 ERROR 경보로 드러낸다**(기존 EXPIRED 경로와 같은 판단). 공유 claim/lock·영속 삭제 큐는 범위 밖이며 그 이유를 함께 적는다

### 4. FR-040 위반 정정

`finalize`에서 Document `READY` 전이가 0행이어도 Chunk 교체·staging 삭제·Job `SUCCEEDED`가 커밋된다. FR-040은 네 가지를 하나의 트랜잭션으로 확정하라고 요구하므로 현재 구현이 이미 어긋나 있다.

- READY 전이가 0행이면 예외를 던져 finalize 전체를 롤백한다
- 롤백하면 `markSucceeded`도 취소돼 재전송이 멱등 분기로 들어가지 못하므로, 응답은 `410 JOB_GONE`이고 반복 요청도 무변화 410이다
- `DISABLED`/`EXPIRED`가 된 문서를 `PROCESSING`으로 되돌리는 복구 정책은 범위 밖(필요해지면 별도 티켓)
