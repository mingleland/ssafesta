## 설명

GitLab #223 (FE 요청, #187 후속). 현행은 3초 고정 간격 SETNX 라 정상 대화가 3초에 한 줄로 묶이고, 반대로 3초를 지키는 매크로는 그대로 통과한다.

확정 상태 머신

- 창: 최소 간격 0.8초, 10초 안 5회, 1분 안 20회.
- 카운트 대상: 내용 검증을 통과해 rate limiter 가 허용한 전송 시도. 금칙어·길이 거절과 제한 초과 자체는 창을 소비하지 않는다. 그 뒤 신원 검증에서 실패한 요청은 이미 소비된 것으로 본다(판정 순서가 내용 → 도배 → 신원이고 rollback 을 만들지 않는다).
- 벌칙: 초과 1회째 5초, 2회째 10초, 3회째 이상 30초 상한.
- 벌칙 활성 중 재요청은 단계를 올리지 않고 남은 대기 시간만 돌려준다. 올리면 UI 재시도 타이밍을 한 번 어긋낸 것만으로 단계가 순식간에 오른다.
- 단계 초기화: 마지막 벌칙이 끝난 뒤 60초 동안 초과가 없으면 0단계로 돌아간다. 정상 메시지 한 줄로는 초기화하지 않는다.

계약 변경

- 오류 payload 에 retryAfterMs(정수 밀리초)를 신설한다. Duration 을 직렬화하면 PT5S 가 나가 FE 기대와 어긋난다. 허용될 때는 필드를 내리지 않는다.
- Redis 장애 시 fail-closed 는 유지하고 그때도 retryAfterMs 5000 을 준다. 코드는 CHAT_UNAVAILABLE 로 남긴다.

구현 제약

- 세 창과 벌칙 상태를 Lua 스크립트 1개로 원자 처리한다. 왕복을 쪼개면 동시 전송이 창을 새어 나간다.
- 사용자별 Redis 키는 전부 만료한다. 남기면 채팅 사용자 수만큼 상태가 쌓인다.
- 검증 순서(내용 → 도배 → 신원 → 방송)와 길이 100 code point, 입장 알림 제외는 그대로 둔다.

완료 조건

- 0.8초 안 두 번째 전송이 거절되고 retryAfterMs 가 양수다.
- 10초 안 5회는 통과하고 6번째가 거절된다.
- 벌칙이 5 → 10 → 30초로 오르고 상한을 넘지 않는다.
- 벌칙 중 재요청이 단계를 올리지 않는다.
- 60초 무초과 뒤 단계가 0으로 돌아가고, 정상 메시지 한 줄로는 돌아가지 않는다.
- 금칙어 거절이 창을 소비하지 않는다(기존 동작 유지).
- docs/16 의 payload 예시와 조건표가 새 값으로 갱신된다.
