## 설명

## 작업 목적

도메인 예외가 오류 봉투를 우회해 500 으로 나가는 결함을 끊는다. 같은 결함을 08-20 · 08-20 · 08-27 세 번 고쳤고 이번이 네 번째다. 이번에는 눈앞의 것만 고치지 않고 남은 형제를 전수 정리한 뒤, 5차 재발이 구조적으로 불가능하도록 검사를 남긴다.

## 원인

`GlobalExceptionHandler` 는 `ApiException` 만 code 와 status 를 실어 응답한다. 아래 6개 예외는 맨 `RuntimeException` 이라 상태 코드가 예외가 아니라 **컨트롤러의 try/catch 안에** 있다. 그 catch 를 쓰지 않는 호출자에서는 `handleUnexpected` 로 떨어져 `INTERNAL_ERROR` 500 이 된다.

T-113 예방란이 이 상황을 그대로 서술해 두었다 — "컨트롤러에서 번역하면 그 컨트롤러에서만 맞는 코드가 되고, 두 번째 사용처가 생길 때 조용히 500 이 된다. 전역 catch-all 이 있으면 이런 누락이 에러가 아니라 잘못된 성공 코드로 보인다."

해당 6개 파일은 최초 반입(`c0374a8d`) 이후 손댄 적이 없다. S15P21A604-270 의 `extends RuntimeException` 전수 스윕은 auth 패키지 3건만 잡고 wallet · booth 6건을 지나쳤다.

## 실제로 500 이 나가는 경로 (1개 예외, 2 endpoint)

`WalletNotFoundException` 은 `WalletController` 에서만 번역된다. `WalletService.lockOwner` 를 부르는 다른 두 호출자에는 catch 가 없다.

| 요청 | 지갑 없는 회원의 현재 응답 | 정상 |
|---|---|---|
| `GET /api/v1/wallets/me` | 404 `WALLET_NOT_FOUND` + error 로그 | 현행 유지 |
| `POST /api/v1/booth-slots/{slotId}/leases` | **500 **`INTERNAL_ERROR` | 404 `WALLET_NOT_FOUND` |
| `POST /api/v1/catalog/items/{itemId}/purchases` | **500 **`INTERNAL_ERROR` | 404 `WALLET_NOT_FOUND` |

경로는 둘 다 `wallets.lockOwner(userId)` 다 — `BoothLeaseService.lease`, `InventoryService.purchase`. 같은 깨진 상태가 endpoint 마다 다른 코드로 나간다.

지갑은 회원 생성 트랜잭션에서 만들어지므로 이것이 정상 상태는 아니다. 그러나 `WalletController` 가 이미 "404 + error 로그" 로 답하기로 정했고, 하나의 사건에 두 개의 답을 주지 않는다.

`DailyCoinGrantInterceptor` 는 `RuntimeException` 을 통째로 잡아 error 로그만 남기고 요청을 계속 진행하므로(헌법 3조 장애 격리) 이 경로에서는 500 이 나가지 않는다. 현행 유지한다.

## 잠재 5건 — 호출자가 하나뿐이라 아직 드러나지 않은 것

| 예외 | 번역 위치 | 현재 상태 |
|---|---|---|
| `SlotNotFoundException` | `BoothSlotController` 2블록 | 호출자 전부가 잡고 있어 노출 없음 |
| `SlotNotRentableException` | `BoothSlotController` | 호출자 1개 |
| `SlotAlreadyLeasedException` | `BoothSlotController` | 호출자 1개 |
| `ActiveLeaseLimitException` | `BoothSlotController` | 호출자 1개 |
| `InsufficientCoinException` | `BoothSlotController` · `InventoryService` | 노출 없음. 대신 동일한 메시지 조립이 2곳에 복제 |

전부 T-113 과 같은 모양이다. 지금은 우연히 호출자가 하나뿐이어서 맞고, 두 번째 호출자가 생기는 순간 500 이 된다. `BoothLayoutQueryService.findPublishedBySlot` 가 `SlotNotFoundException` 을 던지는데 마침 `BoothSlotController` 만 부르고 있는 상태다.

`BoothSlotController.published` 의 주석이 이미 이 사정을 적어 놓았다 — "Not an ApiException — 004 threw it before the error envelope existed, and the two other call sites translate it here as well rather than in a handler."

## 검토 후 현행 유지 — `LayoutParseException`

`extends RuntimeException` 7번째 항목이다. `LayoutJson.parse` 를 부르는 5곳 중 `BoothLayoutService.readRequest` 만 잡는다. 그러나 나머지 4곳이 파싱하는 것은 **우리가 **`LayoutJson.write` 로 직접 쓴 저장 데이터이므로, 파싱 실패는 DB 손상이며 서버가 설명할 수 없는 사건이다. `ProjectService` 가 이미 같은 판단을 명시해 두었다. 500 이 사실이므로 바꾸지 않고, 아래 구조 검사에서 근거 주석과 함께 허용 목록에 넣는다.

## 수정 범위

- 6개 예외를 `ApiException` 상속으로 전환하고 각자 `ErrorCode` 를 싣는다. 필요한 `ErrorCode` 상수 6개는 전부 이미 있다 — `WALLET_NOT_FOUND` · `INSUFFICIENT_COIN` · `BOOTH_SLOT_NOT_FOUND` · `BOOTH_SLOT_NOT_RENTABLE` · `BOOTH_SLOT_ALREADY_LEASED` · `ACTIVE_LEASE_LIMIT`. 신설 없음.
- 번역 catch 9블록을 삭제한다 — `BoothSlotController` 6, `WalletController` 2(+`missingWallet` helper), `InventoryService` 1. 응답 status 와 code 는 종전과 같아야 한다.
- `InsufficientCoinException` 의 "필요 · 잔액" 문장을 예외 안으로 옮긴다. `getRequired` · `getBalance` 는 `WalletServiceIntegrationTest` 가 단언하므로 남긴다.
- `WalletController` 의 `log.error` 를 `WalletService` 로 옮긴다. 발생 지점이 `requireWallet` · `lockOwner` · `applyEntry` 세 곳이므로 공통 팩토리를 거치게 해서 세 경로 전부 로그가 남게 한다. 조용한 실패를 만들지 않는다 (T-24).
- 구조 검사 테스트를 추가한다. `ClassPathScanningCandidateComponentProvider`(spring-context, 이미 의존성에 있음) 로 `com.example.ssafesta` 아래 `RuntimeException` 자손을 전수 훑어 `ApiException` 상속을 단언한다. 허용 목록은 `LayoutParseException` 1건이며 근거를 주석으로 남긴다. 신규 의존성 없음.
