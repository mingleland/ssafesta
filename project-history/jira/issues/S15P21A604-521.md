## 설명

작업 목적

chunk-search 엔드포인트의 실제 P95 지연시간과 Top-K 포함률(Recall)을 상한 부하(문서 10개·총 100MB)에서 검증한다.

작업 내용

- AiChunkSearchApiIntegrationTest와 동일한 Testcontainers 인프라(외부 서버 불필요, 자동 기동)로 실제 Postgres+pgvector를 사용한다
- 한 Agent에 문서 10개·총 100MB 상당 chunk를 repository/JDBC로 직접 seed한다 (업로드 파이프라인 왕복 없이 데이터만 구성)
- 정답 근거 문서를 사전 지정한 품질 평가 질문 세트로 POST /internal/ai/chunk-search를 반복 호출해 P95 지연시간을 측정한다
- 같은 호출 결과에서 정답 chunk가 Top-K에 포함되는 비율(포함률)을 측정한다

완료 조건

- 검색 P95 1초 이하
- Top-K 포함률 95% 이상

선행 작업 / Dependency

- S15P21A604-398 (chunk-search 구현, 완료)
- S15P21A604-163 (AI 쪽 임베딩 계산·HTTP client 오버헤드 검증 — 별도 진행, 이 이슈와 무관하게 완결)

참고

- specs/007-ai-agent-document/spec.md SC-006, SC-007
- backend/src/test/java/com/example/ssafesta/internal/ai/AiChunkSearchApiIntegrationTest.java (같은 Testcontainers 패턴 재사용 권장)

비고

S15P21A604-163(AI)은 원래 festa-ai 쪽에서 이 검증 전체를 맡을 계획이었으나, S15P21A604-449로 검색이 Spring 단독 소유가 된 뒤 P95의 실질 병목(pgvector 쿼리 자체)과 Top-K 포함률(chunk-search 응답 자체)이 전부 Spring 프로세스·DB 안에서 결정됨을 확인해 이 이슈로 분리했다. FastAPI에서 측정하면 실제 DB 쿼리 성능이 아니라 자기 오버헤드(임베딩 계산+HTTP 왕복)만 재는 것이라 신뢰할 수 없고, 실행하려면 사람이 미리 띄워둔 실제 Spring 서버가 있어야 하는 opt-in 테스트로만 가능해 CI에 못 태운다. Testcontainers를 이미 갖춘 Backend 쪽이 seed→검색→측정을 자체 완결로 처리할 수 있다.

테스트 방법

1. 신규 통합 테스트(Testcontainers) 작성·실행
2. P95·포함률 수치 리포트 첨부
