## 설명

### 작업 목적

S15P21A604-556이 EXPIRED 원본만 지우고 FAILED는 범위 밖으로 뺐다. 지금 FAILED 문서의 원본은 저장소에 무기한 남는다. 2026-09-11 확정된 정책(7일 유예 후 자동 삭제, docs/26)을 구현한다.

### 작업 내용

- `AiDocumentOriginalDeleteSweeper`의 기존 EXPIRED 경로를 확장한다. 새 클래스를 만들지 않는다 — 조회·삭제·조건부 갱신 3단 구조가 그대로 쓰인다
- 대상 조건: `processing_status = 'FAILED' AND updated_at <= now() - 7d AND s3_key IS NOT NULL`
- 유예 기간은 설정값으로 뺀다(EXPIRED의 24시간과 별개 값)
- 스냅샷 조건부 갱신에 `updated_at`을 포함한다 — 유예 기간 동안 재처리로 상태가 바뀌면 삭제 대상에서 빠져야 한다
- 배치 상한과 경보(EXPIRED의 48시간 escalate에 대응하는 값)를 FAILED 경로에도 적용한다

### 완료 조건

- [ ] 7일이 안 지난 FAILED 원본은 지우지 않는다
- [ ] 7일이 지난 FAILED 원본을 지우고 `s3_key`를 비운다
- [ ] 삭제 직전 재처리로 FAILED를 벗어난 행은 건드리지 않는다 (스냅샷 불일치 시 갱신 0행)
- [ ] 저장소 삭제는 성공했는데 갱신이 0행인 경우를 성공으로 기록하지 않는다
- [ ] EXPIRED 경로의 기존 동작이 바뀌지 않는다

### 선행 작업

- S15P21A604-636 (정책 등재) — 문서가 먼저 develop에 닿아야 구현 근거가 생긴다

### 참고

- backend `ai/AiDocumentOriginalDeleteSweeper.java` — RECOVERY_WINDOW 24h, ESCALATE_AFTER 48h, 배치 상한, 스냅샷 조건부 UPDATE
- specs/007-ai-agent-document FR-028
- docs/26_팀_결정_필요사항.md §FAILED 문서 원본 삭제 정책

### 테스트 방법

1. FAILED + `updated_at` 6일 전 → 삭제 안 됨
2. FAILED + 8일 전 → 삭제되고 `s3_key`가 NULL
3. 조회 후 갱신 전에 상태를 READY로 바꾼 행 → 갱신 0행, 완료 표시 없음
