## 설명

### 작업 목적

EXPIRED 로 전환된 지 24시간이 지난 미완료 문서의 원본을 R2 에서 삭제한다. 지금은 삭제하는 쪽이 없어서, 업로드만 되고 버려진 파일이 저장소에 영구히 남는다.

S15P21A604-174 가 1시간 만료 sweep 을 넣으면서 EXPIRED 행이 실제로 생기기 시작했다. 행은 활성 집합에서 빠져 슬롯을 돌려주지만 바이트는 그대로다.

### 작업 내용

- EXPIRED 이고 expired_at 이 24시간을 지난 문서의 원본을 저장소에서 삭제한다
- 삭제 실패 시 EXPIRED 상태와 object key 를 유지하고 성공할 때까지 재시도한다
- 삭제된 뒤에는 늦은 완료 요청이 복구로 이어지지 않아야 한다 (이미 24시간 경계로 410 이므로 동작 변화는 없고, 정리된 행이 재시도 대상에서 빠지는지가 관건이다)

### 완료 조건

- [ ] expired_at 이 24시간을 지난 미완료 원본이 저장소에서 사라진다
- [ ] 저장소 삭제 실패가 행을 잃지 않는다 - 다음 주기에 다시 시도한다
- [ ] 정리가 끝난 행은 다음 주기의 조회 대상에서 빠진다
- [ ] 24시간 이내 원본은 삭제되지 않는다 (FR-027 복구 창)

### 선행 작업 / Dependency

- BLOCKED BY: 없음. S15P21A604-174 (EXPIRED 를 만드는 쪽)이 develop 에 들어간 뒤가 자연스럽다

### 참고

- spec 007 FR-028, FR-027
- docs/08_Backend_API_명세서.md - 늦은 완료 판정표가 이미 이 sweeper 의 존재를 전제한다 ("삭제는 sweeper 가 자기 주기로 하므로 남아 있다고 받아 주면 유예 기간이 무의미해진다")
- AiDocumentService.RECOVERY_WINDOW (24시간 상수, 이미 있음)
- 저장소 삭제 실패를 큐로 재시도하는 선례: game_asset_delete_queue

### 테스트 방법

1. expired_at 을 24시간 이전으로 backdate 한 행을 만들고 주기 작업 실행 - 원본이 삭제되는지
2. 저장소가 실패를 돌려주는 상태로 같은 작업 실행 - 행과 object key 가 남고 다음 실행에서 다시 시도하는지
3. expired_at 이 23시간인 행은 건드리지 않는지

### 배경 (S15P21A604-174 조사)

이 요구사항은 spec 007 에 확정돼 있는데 어느 티켓에도 들어 있지 않았다. 스프린트 5 의 BE 티켓 17건을 전수 확인했고 -174 의 작업 내용에도 없다. 구현이 아니라 보드에 없다는 것이 문제라 티켓만 신설한다.

### 황덕 · 2026-09-09 12:17 KST

S15P21A604-175 (MR !518)이 이 티켓의 대상 경로를 하나 늘렸다. 착수 전에 알고 있어야 해서 남긴다.

### 무엇이 늘었나

-175 가 문서에 FAILED 를 처음으로 쓰기 시작한다 (처리 Job 이 DEAD 로 끝났을 때). FAILED 는 중복 판정과 쿼터 집계에서 빠지므로(FR-019b) 사용자는 같은 파일을 그대로 다시 올릴 수 있고, 그러면 새 문서 행이 생긴다.

문제는 옛 행이다. 그 행은 FAILED 인 채로 남고 object key 도 그대로 들고 있는데, 바이트를 지우는 코드가 없다. 즉 처리 실패 한 번마다 원본 하나가 저장소에 영구히 쌓인다.

전에는 이 경로가 없었다. FAILED 를 쓰는 코드 자체가 없어서 실패한 문서가 QUEUED 로 남아 슬롯을 잡고 있었고, 재업로드도 막혀 있었기 때문이다. 슬롯 문제를 푼 대신 저장소 누수가 생긴 셈이다.

### 이 티켓 범위에 미치는 영향

작업 내용에 적힌 "EXPIRED 이고 expired_at 이 24시간을 지난 문서" 만으로는 부족해 보인다. FAILED 원본도 같은 정리 대상이다.

다만 판정 기준이 다르다.

- EXPIRED 는 expired_at 기준 24시간이 FR-027 의 복구 창이라 명확하다
- FAILED 는 복구 창이 없다. /complete 가 FAILED 문서를 거부하고 재업로드는 새 행으로 가므로, 그 원본을 되살릴 경로가 애초에 없다. 그래서 유예를 둘 이유가 있는지부터 정해야 한다 (운영자가 원본을 확인할 시간을 남길지 여부)

착수할 때 이 두 갈래를 함께 설계하는 것이 맞다고 본다. 기준이 정해지면 여기에 남기겠다.
