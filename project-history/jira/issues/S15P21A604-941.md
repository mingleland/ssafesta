## 설명

## 배경

현재 백엔드 테스트는 163개 파일이 있지만, 도메인 경계를 넘는 흐름을 검증하는 것은 `BackendCrossDomainIntegrationTest` 한 파일(테스트 메서드 2개)뿐이다. 나머지는 모두 도메인 내부 통합 테스트라, 각 도메인이 개별적으로는 통과하면서 서로 어긋나 있는 상태를 아무도 잡지 못한다.

코드를 조사한 결과 다음 세 가지가 실제 미검증 구간으로 확인됐다.

1. 일일 코인 캡이 세 갈래로 나뉘어 있고 각각 자기 사유 코드만 센다. 타이밍스톱은 `MINIGAME_REWARD` 기준(`TimerStopService:189`), 일일 미션은 `DAILY_MISSION` 기준(`DailyMissionService:87`), 슬롯머신은 캡이 없는 것이 확정값이다(`SlotMachineService:30`, #205). 셋이 한 지갑에서 같은 날 동작하는 경우를 보는 테스트가 없어, 캡 산식이 사유 필터를 잃어도 세 도메인 테스트가 모두 통과한다.
2. 부스 권한 게이트는 `BoothAccessGuard` 한 곳에 모여 있으나, 호출부 25곳이 네 개 메서드 중 무엇을 쓰는지는 각자의 결정이다. 임대 종료 후 무엇이 닫히고 무엇이 열려야 하는지를 전 경로에 걸쳐 확인하는 테스트가 없다. 현재 `ExpiredBoothEditingIntegrationTest`는 쓰기 5개 경로만 본다.
3. 관리자 권한 면은 `requireModifier`를 타는 전 경로인데, `AdminBoothAccessIntegrationTest`는 homepage와 layout 두 경로만 검증한다.

## 작업 범위

`BackendCrossDomainIntegrationTest`에 `@Nested` 네 그룹을 추가한다. 동일한 `@SpringBootTest` 설정이므로 Spring TestContext 캐시가 컨텍스트를 재사용한다(현재 저장소에 `@DirtiesContext`/`@MockitoBean` 사용 파일은 6개뿐이고 병렬·fork 설정은 없다). 각 그룹 안에서도 테스트를 독립적으로 나누고, 공통 단언은 helper로 뺀다. 테스트 간 실행 순서에 의존하지 않으며, 데이터는 각 테스트가 독립적으로 생성한다.

### 1. EconomyCycle — 코인 경제 일주

- 사용자 두 명으로 캡 독립성을 양방향 검증한다. A는 미니게임 캡 포화 후 미션 claim이 통과하는지, B는 미션 캡 포화 후 미니게임 지급이 되는지. 테스트 시계를 조작하지 않는다.
- 슬롯은 양쪽 캡의 잔여량을 바꾸지 않으며, 슬롯으로 인한 잔액 변화는 `Σ SLOT_PAYOUT − Σ SLOT_BET`이다.
- 이벤트 상점 구매(`PRIZE_PURCHASE`)와 관리자 취소 환불(`PRIZE_REFUND`, `AdminEventShopService:131`)이 각각 정확히 1건씩 남고, 재시도·재취소가 추가 원장을 만들지 않는다.
- 마감 단언: `assertBalanceMatchesLedger` + 사유별 건수표 전체 + 부호 합계가 잔액과 일치. 잔액만 보면 두 사유가 서로 상쇄해도 통과하므로 건수표가 필요하다.

### 2. LeasePayment — 임대 결제와 원장

- 유료 임대가 `LEASE_PAYMENT` 원장 정확히 1건을 남기고, 참조가 실제 생성된 leaseId를 가리킨다.
- 임대 멱등키는 클라이언트가 주지 않는다. 서버가 leaseId로 만든다(`BoothLeaseService:307`). 따라서 재시도 계약은 "활성 임대 보유 중 같은 자리 재요청 = 200 + 기존 임대 + 추가 과금 0", "남의 자리 = 409", "종료 후 같은 자리 재임대 = 새 leaseId + 과금 1회 더"이다.
- 잔액 부족 시 임대·원장 모두 0건이고 슬롯 상태가 변하지 않는다.
- 관리자 무료 임대는 0코인 원장이 아니라 원장 행 자체를 만들지 않는다(`BoothLeaseService:143`).
- 대시보드의 `leaseCostCoin`이 같은 결제를 부스 쪽에서 본 값과 일치한다. 대시보드 코인 집계는 `LEASE_PAYMENT`+`BOOTH_LEASE`와 `SURVEY_REWARD`+`SURVEY` 두 쌍만 본다(`BoothDashboardService:74`). 방문·상담은 코인을 만들지 않으므로 건수 검증에만 쓴다.

결제와 임대 생성의 원자성(차감 후 저장 실패 등)은 이 아크에 넣지 않는다. 실패 주입점이 없어 테스트 전용 훅을 억지로 만들게 되므로, 트랜잭션 경계와 DB 제약을 확인한 뒤 별도 티켓으로 둔다.

### 3. LeaseTermination — 임대 종료 전파

종료 사유를 파라미터로 받아 만료·반납·관리자 강제해제 세 경우를 같은 단언으로 돈다. 세 경우는 원인만 다르고 검증 대상이 같아, 따로 쓰면 단언을 세 벌 유지하게 되고 나중에 한 벌만 고쳐진다.

소유자가 부스를 끝까지 채운 뒤(레이아웃 게시, 프로젝트, 설문, 문서 READY, 방문, 상담) 종료시키고, 종료 전에 발급한 토큰을 그대로 들고 같은 boothId로 전 경로를 재호출한다. 검증 대상은 토큰의 만료 여부가 아니라 모든 쓰기 요청이 현재 임대·소유권을 재검증해 실패하는지다.

- 거부돼야 하는 것(`requireActiveEditor` 계열): facade, homepage, layout publish, project 등록, agent 생성, survey 저장
- 열려야 하는 것(`requireEditor` 계열, FR-011 보존): layout draft, survey 편집 조회, 설문 결과, 대시보드, 방문 지표, agent 조회
- 방문자에게 닫혀야 하는 것: `booths/{id}`, published layout(부스·룸 양쪽), 프로젝트 목록, 설문 제출, 상담 시작
- 문서: chunk-search 결과 0, job CANCELLED, 문서 비활성
- 코인: `BOOTH_LEASE`를 참조하는 credit 원장 0건(`LEASE_REFUND` 사유 코드는 존재하지 않으므로 참조 기준으로 단언한다)

문서 `complete`는 `AiDocumentService:446`이 의도적으로 `requireEditor`를 쓴다고 주석에 적고 있으나, 이는 계약이 아니라 구현의 주장이다. `complete` 자체의 성공/실패는 단언하지 않고, 대신 다음을 고정한다.

- 종료 후 문서가 방문자 검색 대상으로 재활성화되지 않는다
- chunk-search 결과가 0이다
- 종료된 부스의 agent가 해당 문서를 사용하지 않는다
- `complete`가 허용되더라도 `READY + ACTIVE` 조합으로 복원되지 않는다

### 4. RoleMatrix — 권한·감사 관통

역할과 경로의 조합을 `@MethodSource` 테스트 데이터로 명시해 매트릭스로 돌린다. 역할 축은 소유자, 편집 권한 스태프, CONSULTANT, 관리자, 강등된 관리자, 무관한 회원이다.

- 관리자 쓰기 경로마다 감사행 정확히 1건(facade, homepage, layout 저장·게시, project 등록·수정·로고, agent 생성·수정·삭제, document 업로드 URL·삭제, survey 저장)
- 마스터 소유 부스는 관리자 경로에서 거부, 관리자 소유 부스는 허용
- 강등 직후 두 경로가 아니라 전 경로가 거부된다
- 편집 권한 스태프는 소유자와 같은 면을 통과하고 CONSULTANT는 전부 거부된다. 업로드 URL 발급뿐 아니라 `complete`, 게시, 타 부스 접근 거부까지 포함한다

## 착수 전 확인이 필요한 계약 3건

아래는 구현 주석에만 근거가 있고 요구사항·권한표에서 확인되지 않았다. 구현을 그대로 베낀 테스트가 되지 않도록 착수 전에 확인한다. 문서와 이슈에서 찾지 못하면 `docs/26_팀_결정_필요사항.md`에 올린다.

1. 임대 종료 후 문서 `complete`를 허용하는 것이 설계 의도인가. 종료 전 시작한 업로드의 완료를 받아 주려는 것일 수 있다.
2. 관리자의 읽기 경로(대시보드, 설문 결과, 방문 지표)가 감사행을 남기지 않는 것이 정책인가. 관리자가 타 부스의 운영 지표를 무감사로 열람하게 된다.
3. 거부된 관리자 요청을 감사 대상에서 제외하는 것이 정책인가. "실패 감사 0건"은 트랜잭션 롤백 검증인 동시에 보안 감사 정책이므로, 거부 시도도 남겨야 한다는 정책이 서면 기대값이 정반대가 된다.

1번과 3번이 미확정이면 해당 단언만 보류하고 나머지를 먼저 넣는다. EconomyCycle과 LeasePayment는 확인 없이 착수 가능하다.

## 범위 밖(후속 티켓 후보)

- 게임 발행 → 아케이드 머신 바인딩 → machineId 해석 → 발행 철회 시 바인딩 정리. 아케이드는 gameId 해석만 하고 보상 경로가 없으므로(`ArcadeMachineResolveService:52`) 코인 검증은 대상이 없다.
- 탈퇴 후 잔존물 검증. "전부 물리 삭제"로 단정하면 감사·원장 보존 정책과 충돌하므로, 활성 리소스 제거와 보존 데이터 익명화를 나누어 정의해야 한다. 익명화 대상 정책 확인이 선행 조건이다.
- 이벤트 설문 → 응모자 명단. 단일 도메인이므로 새 횡단 아크가 아니라 `EventSurveyApiIntegrationTest`에 중복 응답·응모 자격·취소된 응모 제외 케이스를 추가한다.
- 상담 → WS → 대시보드. 비동기 집계의 최종 일관성 때문에 불안정해지기 쉽다. 임의 sleep 대신 이벤트 처리 완료를 관찰할 수 있는 테스트 훅이 선행 작업이다.
