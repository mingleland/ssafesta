## 설명

MR !443(S15P21A604-132) 머지 후 리뷰에서 나온 결함 3건.

*1. 보상 지급이 락 이전 스냅샷 값을 쓴다 (SurveyResponseService)*

submit 이 Survey 를 booths.findWithSharedLockById 보다 먼저 읽었다. 편집(PUT)은 부스 write 락을 잡고 rewardCoin 과 closesAt 을 바꿀 수 있으므로(C-08 이 허용), 락을 기다렸다 통과한 제출이 편집 이전 값으로 지급한다. 마감도 같다 — 방금 마감된 설문에 답이 들어간다.

조치: 부스 id 만 스칼라로 읽어 락을 잡고, Survey 는 락 이후에 로드한다.
검증: SurveyResponseConcurrencyIntegrationTest.aSubmissionWaitingOnTheLockIsPaidTheEditedReward. 수정을 되돌리면 expected 10 but was 5 로 실패한다.

*2. 결과 집계가 서로 다른 스냅샷을 읽는다 (SurveyResultService)*

READ COMMITTED 라 집계 5문장이 각각 다른 스냅샷을 본다. 사이에 제출이 들어오면 answeredCount 가 totalResponses 보다 큰 값이 나갈 수 있고, 이는 SC-001 이 부정하는 상태다.

조치: results 와 textAnswers 를 REPEATABLE_READ 로 연다. 읽기 전용 트랜잭션은 PostgreSQL repeatable read 에서 직렬화 충돌로 실패하지 않는다.
검증: 자동 검증 없음. 어노테이션 한 개짜리 변경이고 스냅샷 경계는 DB 가 강제한다.

*3. 큰 page 값이 음수 OFFSET 이 된다 (SurveyResultService)*

page * size 를 int 로 곱해 넘친다. page=21474837 size=100 이면 offset -2147483596 이고 PostgreSQL 이 OFFSET must not be negative 로 거부해 500 이 된다. page 상한 검증은 없다.

조치: 곱셈을 long 으로, 리포지토리 offset 파라미터도 long.
검증: SurveyResultApiIntegrationTest.aHugePageNumberIsAnEmptyPageNotAnError. 수정 전 실제로 500 을 확인했다.

*함께 나온 것 — 코드 결함 아님*

게스트 응답이 헌법 12조 후단(게스트 세션은 종료 시 데이터를 삭제한다)과 어긋난다. respondent_guest_key 가 세션 종료 후에도 남고 지우는 경로가 없다. 키는 무작위 UUID 라 실질 노출은 없다. 정책 결정 사항이라 임의로 정하지 않고 docs/26 row 20 과 GitLab #133 에 선택지 3개로 올렸다.

*전체 검증*: mvnw test 924건 통과, 실패 0 (직전 922 + 신규 2).

**② 작성자 탈퇴가 FK 오류로 실패 — 진짜다. 내가 MR ①(-130)에서 만든 구멍이다.**

`surveys` 삭제에 `OR created_by_user_id = ?` 를 붙이면서 자식(문항·선택지·응답) 삭제는 부스 소유자 기준 그대로 뒀다. 남의 부스에 내가 만든 설문이 있으면 `survey_questions_survey_id_fkey` 에 걸려 **탈퇴 전체가 500** 이 된다. 테스트로 그 오류를 먼저 재현했다:

```
ERROR: update or delete on table "surveys" violates foreign key constraint
"survey_questions_survey_id_fkey" on table "survey_questions"
```

고칠 때 **지우지 않고 넘기는 쪽**을 골랐다. 지우는 쪽이면 부스 소유자의 설문과 남들이 답한 응답이 제3자의 탈퇴로 사라진다. `created_by_user_id` 는 NOT NULL 이므로 부스 소유자가 이어받고, DELETE 는 부스 소유자 기준 하나로 남는다.

**도달 가능성은 낮다** — `Booth.ownerUserId` 에 setter 가 없어 소유자가 바뀌는 경로가 없고, 서비스는 항상 소유자를 `created_by_user_id` 에 쓴다(불변식 I-5). 지금 API 로는 이 상태가 만들어지지 않는다. 그래도 그 조건을 굳이 넣어 둔 이유가 "삭제는 스키마가 허용하는 모든 값에 옳아야 한다" 였으니, 그 조건도 옳아야 한다.

검증: `SurveyApiIntegrationTest.authorWithdrawalHandsTheSurveyToTheBoothOwner`.

**③ 부스-지갑 락 순서 역전 — 오탐이다.**

두 락을 다 잡는 경로를 전수로 확인했다. `BoothLeaseService.lease`(부스 행 UPDATE → `wallets.spend`)와 `SurveyResponseService.submit`(부스 락 → `wallets.credit`) 둘뿐이고 **순서가 같다.** `InventoryService`는 지갑만 건드리고 부스를 만지지 않는다. 지갑을 먼저 잡는 경로가 없으므로 사이클이 없다.

다만 다음 사람이 "고치려고" 순서를 뒤집으면 그때 진짜 교착이 생기므로, 불변 순서를 `submit` javadoc 에 한 문단으로 박아 뒀다.

### 황덕 · 2026-09-08 10:11 KST

3차 리뷰 2건. **둘 다 진짜였고, 하나는 내가 직전 코멘트에서 "오탐" 이라고 쓴 그 건이다.** MR !451 에 추가했다.

**① 지갑-부스 락 순서 역전 — 내 판정이 틀렸다.**

직전 코멘트에서 "두 락을 다 잡는 경로를 전수로 확인했다. 순서가 같다" 고 썼는데, `BoothLeaseService.lease` 를 85행부터 읽어서 **74행의 **`wallets.lockOwner(userId)` 를 못 봤다. 저장소의 순서는 **지갑 → 부스**이고(임대·카탈로그 구매 둘 다 무엇을 하기도 전에 `lockOwner` 를 부른다), `SurveyResponseService.submit` 은 **부스 → 지갑**이었다. 진짜 역전이다.

교착을 재현했다 — 지갑 락을 쥔 트랜잭션이 부스 행을 쓰고 그동안 제출이 그 부스를 쥔 채 같은 지갑을 기다리면:

```
ERROR: deadlock detected
```

되돌린 상태로 `@RepeatedTest(3)` 3회 전부 났다. 회원이면 부스 락 **전에** 지갑을 잡도록 바꿨다. 보상 유무와 무관하게 잠그는 이유는 보상 여부를 부스 락 뒤에야 알 수 있고 그때 지갑에 손대는 것이 바로 이 역전이기 때문이다. 게스트는 지갑이 없어 건너뛴다.

검증: `SurveyResponseConcurrencyIntegrationTest.aLeaseAndASubmissionDoNotDeadlock`.

**원인은 부분만 읽고 "전수 확인" 이라고 단정한 것이다.** 메서드 중간부터 읽고 호출 순서를 결론냈다. 락 순서는 메서드 첫 줄부터 봐야 한다.

**② 게스트 세션 식별자 영구 보존 — 지시를 받아 ②안(기간 후 비움)으로 구현했다.**

`SurveyGuestKeySweeper` 가 5분마다, 제출 후 `app.auth.access-token-ttl`(30분)이 지난 응답의 `respondent_guest_key` 를 `expired:<응답 id>` 로 바꾼다.

**① 10분 유예가 실제 요청 수명과 연결돼 있지 않았다 (P1)**

지적대로 `lock_timeout` 도 트랜잭션 timeout 도 없어 제출이 부스 락에서 10분 넘게 기다릴 수 있었다. 상한이 없으면 "10분 기다린다" 는 아무것도 설명하지 못한다.

**유예를 늘리는 대신 상한을 만들었다.** `app.survey.submit-timeout-seconds`(30초)를 `@Transactional(timeoutString = "${...}")` 으로 걸어 제출이 JDBC query timeout 에서 끊기게 했고 — 부스 락 대기도 여기서 취소된다 — `SurveyProperties` 가 **유예 > 제출 상한**을 기동 시 강제한다. 어긋난 설정으로는 뜨지 않는다. 남은 차이(9분 30초)가 트랜잭션이 열리기 전 대기를 덮는 여유다.

**② V23 백필이 옛 TTL 을 30분으로 박았다 (P2)**

더 긴 TTL 을 쓰던 환경이면 아직 유효한 토큰의 키를 먼저 지운다는 지적이 맞고, 주석대로 환경마다 파일을 고치면 이미 적용된 DB 와 checksum 이 어긋난다는 지적도 맞다.

**과거를 추정하지 않고 미래로 민다** — `now() + interval '1 day'`. 배포 이전에 발급된 토큰은 그때면 어떤 TTL 이었든 죽어 있고, 정리가 하루 늦어질 뿐 이르게 지우지 않는다. TTL 을 알 필요가 없으니 환경별 수정도 없다. 대상은 V22~V23 사이에 쌓인 유한한 행뿐이고 그 뒤로는 제출이 진짜 `exp` 를 적는다.

**새로 쓴 검사가 처음엔 무력했다** — 스스로 걸린 것

compact constructor 안에서 `submitTimeout()` 접근자를 불렀는데, 그 시점엔 필드가 아직 대입 전이라 **0 을 돌려준다.** 비교가 늘 통과해 검사가 아무것도 막지 못했다. `SurveyPropertiesTest` 를 먼저 써 둔 덕에 첫 실행에서 잡혔다. **검사를 넣을 때도 그 검사가 무는지 봐야 한다** — 이번 세션에서 "방어가 있다" 와 "방어가 작동한다" 가 다르다는 것을 세 번째로 확인했다.

**검증**: `SurveyPropertiesTest` 4건(유예 ≤ 상한 거부, 상한 필수, Duration 노출, 기존 상한 3종) · `theMigrationPushesRowsThatPredateTheExpiryColumnIntoTheFuture`. `timeoutString` 이 실제로 결정되는 것은 제출을 타는 통합 테스트 31건이 통과하는 것으로 확인된다(placeholder 가 안 풀리면 첫 호출에서 죽는다).
